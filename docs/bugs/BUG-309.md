# BUG-309: 无内容 hash 去重——多源/跨频道相同字节视频必然重复占盘，且多源共享字节缺引用计数（重蹈 BUG-100 风险）

- 状态: fixed
- 发现日期: 2026-10-14
- 模块: engine
- 严重程度: mid

## 实现口径（D24=A，用户 2026-10-14 追加裁定）

- blob 位置：`<下载目录>/.blobs/ab/cd/<hash>`（两段分片；用户裁定「综合下下载目录+.blobs」，
  而非原设计文档的 `<库根>/.blobs/`）—— 使「清缓存」面板按引用计数也能回收 blob。
- hash 算法：SHA-256，在 `PartFile::write_all` 里**流式一次**累计（不二次读盘）。
- 引用计数：`media_blob.refcount`，权威算法 = `SELECT COUNT(*) FROM media_item
  WHERE content_hash = media_blob.hash`；`refcount` 只是缓存 ⇒ 每次启动 `recount_blobs()` 重算。
- 删除语义：`clear_item_bytes` release 归零 ⇒ 返回 orphan ⇒ 调用方 unlink；
  三处字节删除（`purge_item` / `clear_item` / `delete_media_item`）全部改走同一入口。

## 现象

用户需求（2026-10-14 原话）：「视频根据 hash 保存,防止重复缓存(毕竟设计多源)」。

- 同一视频被两个频道转发、或同一剧集的备用来源（media_episode_source）指向同一内容时，
  现状必然下载并保存**多份完全相同的字节**。
- media_item / 任何表均无内容 hash 列（media.rs 全库 grep 仅有 hashtag 标签 `#xxx`，无内容哈希）；
  归仓不做任何字节比对。

## 根因

- TG 落盘命名用 `<chat>/<msg>` 唯一锚：`grammers.rs:1005-1024`（BUG-100 修复时刻意为之）——
  当时裸原始名导致两个 item 共享同一 file_path，删一条即 unlink 另一条字节；改成 chat+msg 后
  「覆盖事故」没了，代价是**相同内容必存多份**。
- HTTP 下载（orig-daemon）同样无 hash 落库环节；D16 完成即入库只登记条目，不做内容去重。
- 系统无 blob/引用计数模型：一旦未来允许多条目指向同一字节而无引用计数，会重新制造 BUG-100 事故
  （删一条连字节，另一条变死链）。

## 复现

1. 频道 A、频道 B 各转发同一视频文件（字节相同）；
2. 分别缓存成功；
3. 预期（D24）：物理只存一份、两条来源记录共享；实际：磁盘两份、占用双倍。

## 修复

按 **D24=A**（2026-10-14）：

- 下载/归仓完成时**流式计算**内容 hash（不二次读盘；BLAKE3/SHA-256，算法在实施设计定），
  写入条目；hash 命中已有 blob → 引用计数 +1，不重复写字节；
- blob 引用计数：最后一个引用移除才回收字节（升级 AGENTS §5「删条目连字节」为「删最后引用连字节」）；
- 存量：不强制搬迁，旧文件记录 hash 后参与后续去重（懒纳入），或在批量整理（BUG-311）时迁入；
- 反向夹具：两条 item 共指 blob，删其一 → 文件仍在；删其二 → 文件回收。

修复过程中**发现并修掉一个真缺陷**：`recount_blobs` 的「补缺行」原为无保护 INSERT，
在 ① 的 DELETE 之后仍可能与目标行重叠时抛 UNIQUE —— 而该函数挂在 `Store::open`（每次启动）
会把「启动对账」变成「启动失败」（服务起不来）。已加 `ON CONFLICT(hash) DO NOTHING`，
权威值交由第 ③ 步重算。
