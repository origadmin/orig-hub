# BUG-445: 缺陷登记册无排期/延期机制——93 条 open 单向棘轮积压，46 条 high/critical 无计划

- 状态: fixed
- 发现日期: 2026-10-27
- 模块: build
- 严重程度: high
- 修复提交: （本轮提交）

## 现象

用户 2026-10-27 报：「为什么会有 ~95 条 open？很多问题我怀疑都过期了。修改完全违反流程……
修复是按计划的，除非显式延期，不然不应该有旧的 BUG 存在，现在感觉完全无法维护了。」

全量实测：非终态 **103** 条（open 93 / in_progress 6 / partial 4），
其中 high 41 / critical 5 / mid 46 / low 8；年龄 ≤7d 23、8–30d 54、31–90d 20、>90d 0；
带「延期/排期」说明的仅 8 条。引用腐坏仅 2 条（且为路径前缀漂移）——
即**不是过期，是无人排期**。

## 根因

`check-bugs.py` 只校**格式**（编号连续 / 索引一致 / 证据可核），**从不校年龄、排期、WIP**。
而登记是强制的、廉价的（先登记后修复 + `commit-msg` 强制引用编号），关闭是昂贵的
（证据 + 门禁 + 跨机器可核引用）⇒ **单向棘轮**，只进不出。
「除非显式延期，否则不该有旧 BUG」从未被机械化，只是口头预期，必然被违反。

另有两类掩盖：设计级 epic 与一行修复混在同一个 flat `open` 列表；10 条
in_progress/partial 开工未收尾（最久 38 天）。

## 修复

- `scripts/check-bugs.py` 新增第 9 条不变量：非终态必须带 `- 排期: YYYY-MM-DD`
  或 `- 延期至: YYYY-MM-DD（理由）`；排期已过且无未过期延期 ⇒ ERROR。
- 对 103 条非终态做分桶 triage：25 条设计级 epic 标 `- 类型: epic` + 里程碑延期
  （critical/high → 2026-12-15，mid/low → 2027-01-31）；78 条缺陷按严重度 SLA 排期
  （critical 7d / high 14d / mid 30d / low 60d）。
- `docs/rules/bug-registry.md` 增补「三·五、排期与延期」规格。

## 验收证据

- 门禁实现：`scripts/check-bugs.py`（第 9 条不变量：`datetime` 解析 + 超期判定）。
- 规格：`docs/rules/bug-registry.md`（「三·五、排期与延期」）。
- 负向证伪（本轮实测）：把 BUG-444 的 `排期` 改成 2026-01-01（过期）后，
  门禁输出 `ERROR … 排期 2026-01-01 已过期且无有效延期（今天 2026-10-27）` 且退出码 1；
  恢复后门禁回到 `OK`。缺 `排期`/`延期至` 亦已由 BUG-073/075（wontfix 误判）实测触发。
- 全量：103 条非终态全部带排期/延期，门禁 OK。
