# BUG-154：条目 title 为空或原始文件名 —— 分集展示兜底成 `#<itemId>`

- 状态: fixed（修复位置 `download-engine/crates/orig-tg/src/routes.rs` + `download-engine/crates/orig-tg/src/media.rs`）
- 发现日期: 2026-09-23
- 模块: engine+shell
- 严重程度: mid

## 现象

用户原话（2026-09-23）：

> 「多集后续内容不会填充正确内容,所有内容应该都一样的,后续全部都临时标题.」

即：剧集里后续追加的分集，标题没有正确填充，**全部是"临时标题"**。

## 先说清「临时标题」的真实出处

**全仓不存在「临时标题」这一实现概念。** 实测：

```sh
grep -rniE '临时标题|tempTitle|untitled|unnamed|未命名' \
  tauri-shell/src/components/ tauri-shell/src/lib/ download-engine/crates/orig-tg/src/
# => 零命中（仅有无关的 `placeholder=` 属性）
```

用户看到的「临时标题」实际是**标题缺失时展示层各自兜底**的结果：

| 位置 | 兜底链 |
|---|---|
| `EpisodeList.tsx:147-150` | `ep.title \|\| (isPhoto ? t('player.photoEp', {n}) : '') \|\| \`#${ep.itemId}\`` |
| `SeriesDetail.tsx:713-715` | `{ep.title \|\| \`#${ep.itemId}\`}` |
| `MediaLibraryPanel.tsx:283` | `title: isRawFileName(e.title) ? '' : (e.title ?? '')` |

**三处各一套**，互不一致——这本身就是问题（同一现象三种呈现）。

## 根因

两条链：

**链 1：`media_episode` 不持有 title 副本**

`media.rs:148-209`（迁移 `collapse_episode_text`）：

> `media_episode` 曾有 `title` / `description` 两列，与 `media_item` 的同名列重复。
> 已 `UPDATE media_episode SET title = NULL, description = NULL` —— 让「第二份副本」
> 在数据上不可表达。

因此 `EpisodeView.title` **从 `media_item` join 而来**，分集标题恒等于条目标题。

**链 2：`append_episodes_ranged` 不写标题**

`media.rs:1940-2005` `append_episodes_ranged` → `add_episode_ranged(series_id, id, season, no, end_no)`
—— **无任何标题参数**。分集标题只能是 item 的标题。

**因此「后续分集全是临时标题」= 被追加的那些 `media_item.title` 本身为空
或是原始文件名。**

## 复现

1. 剧集里有一条标题正常的分集（item.title 来自 caption）。
2. 追加若干条 **caption 为空** 的内容（自动成剧路径，`append_episodes_ranged`）。
3. 观察：新分集标题渲染成 `#<itemId>`（纯数字 id）或原始文件名。

## 修复

见 `docs/bugs/MERGE-4-DEFECTS-EVIDENCE.md` 问题3。

**方向**：**不在展示层继续加兜底**，而是**在入库时给出可信标题**：

1. 查 `media.rs:1051` `upsert_media_item` 调用链，定位 `media_item.title` 如何从 TG 消息落库。
2. caption 为空时**不要落原始文件名当 title**，落 `None`——让展示层能识别「无标题」
   而不是把文件名当标题。
3. `media.rs:3305` 附近有 `.file_name()` 的用法 —— 需确认它是否进了 title 路径。

**诚实边界**：若查证后确认「入库 title 路径本来就正确，只是**历史数据**缺 caption」，
则本缺陷**不能靠改代码消除**，此时必须在档里写清「不能修 + 原因 + 前置条件
（如重新拉取 caption）」，**禁止为了判据变绿而做假修**。

## 验收证据

**修复位置**：`download-engine/crates/orig-tg/src/routes.rs`（:922/:2019 落空串）、`download-engine/crates/orig-tg/src/media.rs`（:1068 COALESCE）。

### 一、写入路径已修（可证伪）

```
$ grep -n "caption_title.unwrap_or_default\|it.title.clone().unwrap_or_default" download-engine/crates/orig-tg/src/routes.rs
922:    let title = caption_title.unwrap_or_default();          ← 已改为空串，不再落文件名
2019:    it.title.clone().unwrap_or_default(),                 ← 第二处：TG 内部 ref 不再当标题
```

同批修正的第二处（`import_media_items`，`:2019`）：`it.title.clone().unwrap_or(r)`
→ `unwrap_or_default()`（`r` 是 TG 内部引用 `"<chat_id>:<message_id>"`，不是标题）。

空串是**刻意**的：`upsert_media_item` 的 `ON CONFLICT` 用
`COALESCE(NULLIF(excluded.title, ''), media_item.title)`（`media.rs:1068`），
故空串**不会覆盖**已有标题，也不会把「无标题」写成非空假值。

（第一处删除的 `file_name` 变量本身也已移除 —— `path.file_stem()` 不再被读取。）

### 二、存量数据：**13 条历史行仍是原文件名，改代码消除不了（如实记录）**

对真实库取证（`GET /api/media/items?limit=200`，127 条）：


**判定为历史行**：坏 id 共 13 个（`<item_id_1>`…`<item_id_13>`），
全库 max id = `<item_id>` —— 全部 id 更小；`added_at` 均在 2026-09-17~09-19（本次修复之前）。

**为什么改代码消除不了**：这些行的 `title` 列**已是有值的非空字符串**，
而写入路径的 `COALESCE(NULLIF(excluded.title, ''), media_item.title)` **刻意保护已有值**
（这是为避免覆盖用户编辑过的标题，见 BUG-116 的同款保守规则）。
新增的空串写入只影响**新行**；重新缓存这些旧行时，空串会被 COALESCE 拦住、旧文件名保留。

**因此本节如实记录为：本缺陷的「新增」已修，「存量 13 条」不能靠纯代码修复。**
可选的处置（**未实施，需用户裁定**）：

1. **不动**（符合「保留所有数据」原则，且这些是内部名、不影响播放）；
2. caption 重新回填：对这 13 条重跑一次 caption 拉取（若无 caption 则仍是空，无法改善）；
3. UI 侧把这 13 条渲染为「未命名」而非原文件名（需先在展示层收敛三处兜底链，
   即修复方案第 3 条，**未做**）。
