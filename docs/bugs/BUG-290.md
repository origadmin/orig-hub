# BUG-290: FRC 变体转码**并发无上限** —— 用户在转码窗口内多点几个倍速即在后台堆起 N 路 ffmpeg，期间 CPU 打满拖慢一切播放

- 状态: open
- 发现日期: 2026-10-12
- 模块: engine
- 严重程度: mid

> 来源：用户 2026-10-12「播放依然卡顿，为什么 TG Web 不卡、本地反而卡？」的诊断取证。
> **本档为任务文档**（用户定：纯文档任务，代码由别的组负责）。
>
> **严重程度说明**：这是**瞬态源**（会自行排空，非常驻泄漏）⇒ 定 `mid`；但**并发无上限**，
> 且排空时长**随源长度**增长，期间与前台播放争 CPU ⇒ 是「本地反而卡」的一条具体来源。
> **不推翻**「断开后继续转码」的**设计结论**（见事实 1）—— 本档只针对「**缺少并发上限**」。
>
> **数据口径**：遵循「内容数据不入库」（`docs/bugs/BUG-232.md:79`）—— 条目以 `<item_id>` 占位，时长只记区间。

## 现象

用户在**短时间内依次点了多个倍速**（每个倍速 = 一个**冷** FRC 变体转码）后：

- 后台**同时**跑起 N 路 `ffmpeg`（N = 点过的不同冷 `(item, speed)` 变体数），**没有上限**。
- 期间机器 CPU 被吃满，**其它播放 / 浏览操作明显变慢**（用户观感即「本地卡」）。
- 实测**峰值并发 5–6**；单进程 CPU ≈ **2.6–5.2 核**（口径见事实 4）⇒ 聚合可轻易超过 10 核。

## 事实

### 事实 1：客户端断开后**继续转码**是**有意设计**（本档不动它）

`download-engine/crates/orig-tg/src/routes.rs:4637-4644`（注释原文）：
> Canonical FRC variants keep transcoding to a seekable speed-specific proxy after client disconnect.

⇒ 设计意图 = 断开也把该倍速的**可 seek 代理**转完，供下次秒开。**本档不改这个结论**，只指出它缺一个并发闸门。

### 事实 2：**没有任何并发上限**

每个冷 `(item_id, speed)` 变体各起一条 `transcode_pump`（`:4411-4423`）；
全仓**无**信号量 / 队列 / 并发闸门（`transcode_inflight()` 只是**同键去重**，`TranscodeKey = (item_id, speed_hundredths)`（`:3980-3983`）—— 不同键**互不约束**）。
⇒ 并发数 = 用户点过的不同冷变体数，**无上限**。

### 事实 3：**会排空，但时长随源长度**

实测（基线 0 个 ffmpeg → 并发触发 6 个冷 FRC 变体，每个 `curl` 4 s 即断，均返回 `200` + `x-orig-stream: decimate=*` live）：

| 时刻 | 并发 ffmpeg |
|---|---|
| t=0 | 5（最短的那个 ≈61 s 源已转完） |
| +10 s | 4 |
| +15 … +50 s | 3 |
| +55 s | 1 |
| +120 s | **1**（一个 >20 分钟的长源**仍在跑**，累计 ≈7 分钟 / 1155 CPU-秒） |

⇒ **短源（61–206 s）的 5 个在 ≤ ~55 s 内全部转完**；**长源不排空**（受源时长 × 转码吞吐约束）。
⇒ 判定为**瞬态源**（会排空），**不是常驻泄漏** ⇒ 故 `mid`。

### 事实 4：CPU 口径

CPU = `Get-Process ffmpeg` 的 **per-process 累计 CPU-秒（含全部线程）跨进程求和**；计数 = `Get-Process ffmpeg` 进程数。
观测：3 个进程时聚合 ≈ **391 CPU-秒**（均摊 ≈2.6 核/进程）；单跑一个长源时该进程 ≈ **5.2 核**（Δ78.7 CPU-秒 / 15 s）。

### 事实 5：并发数 = **用户点过的冷变体数**（无上限的直接后果）

「6 个 / 持续 17 分钟」那次含**长源**，且 6 路**互相争 CPU**把彼此都拖慢 ⇒ 越点越慢、越慢越久。

## 复现

1. 正常态起 daemon + orig-tg；确认代理缓存为空（或选未转过的倍速）。
2. 对**同一或不同条目**，连续 `curl` 多个**不同倍速**的 `/stream?speed=<S>`，每个几秒即断。
3. `Get-Process ffmpeg` 计数 ⇒ 同时存在 N 路（N = 点过的冷变体数），CPU 聚合 > 10 核。
4. 等 1–2 分钟再数：短源排空、长源仍在跑。

## 修复（方向；**本档不改代码**）

**总目标：保留「断开后继续转码」的设计意图，但给它加一个可配置的并发闸门与优先级。**

1. **并发上限（P0）**：给 FRC 转码加**信号量 / 有界队列**（可配置，默认取「物理核数 / 2」量级），超限则**排队**（而非拒绝或无限起）。
2. **前台优先（P0）**：**正在被播放**的变体优先于「断开后补完」的后台转码；后台转码在争用时**让路 / 降优先级**。
3. **长源策略（P1）**：对超长源的「断开后补完」加**时长上限**或**分段策略**（避免单个长源长期独占一个槽）。
4. **不推翻既有设计**：不得取消「断开后继续转码」（那是 BUG-230 秒开体验的一部分）；不得回退 BUG-273 / BUG-274。

## 关联

- **BUG-230**（fixed，stream-first）：FRC 代理是「秒开」体验的基础 —— 本档**保留**它，只加闸门。
- **BUG-273**（32 槽阻塞泵）/ **BUG-274**（播放与缓存下载争用）：同属「播放期资源争用」缺陷簇；本档是**第三条**争用源（转码 × 转码）。
- **BUG-289**（呈现层节拍抖动）：**不同机制**（那条是上屏节奏，与 CPU 争用无关）；但两者共同构成用户「本地卡」的观感。
- **BUG-288**（单飞表泄漏）：**不同机制**（那条是表卫生）；但同属「转码生命周期」关注点。

## 验收证据

（状态 `open`，尚无验收证据。修复后必须满足的**可证伪判据（预先声明）**：）

1. **并发受限**：注入 N（> 上限）个冷 FRC 变体请求 ⇒ 断言**同时**运行的 `ffmpeg` 数 **≤ 上限**。
   **反向证伪**：回退闸门 ⇒ 并发数必回升到 N ⇒ 判据必 **FAIL**。
2. **超限排队而非丢弃**：超限的变体最终**仍会转完并落盘**（不得因限流而永久不产出代理）。
3. **前台不被拖垮**：在 N 路后台转码进行时，前台播放的**供数**不得劣化（`waiting = 0` / `stallGaps = 0`），
   或至少前台变体享有优先级（可核：前台请求优先获得转码槽）。
4. **不回归秒开**：单用户顺序浏览多倍速后，各倍速代理**仍被转完**（`x-orig-stream: proxy` 命中率不下降）。
5. **可核证据**：`Get-Process ffmpeg` 计数 + CPU-秒 + `x-orig-stream` 响应头（**真实服务，非 mock**）。
