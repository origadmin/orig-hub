# BUG-484: 「加入筛选并缓存」伪概念——筛选按标题匹配、标题本来就在消息上，不该让用户反复选/建

- 状态: fixed
- 发现日期: 2026-10-28
- 模块: shell
- 严重程度: mid
- 排期: 2026-10-28

> 来源：用户报告「**加入筛选并缓存 逻辑有问题，不存在加入筛选，筛选是根据标题筛选的，
> 既然已经有了为什么还要反复加入，这是基础逻辑和设计意图不清晰**」。

## 一、现象

单条 / 整组的「加入筛选并缓存」入口（BUG-470）弹出 `FilterCacheDialog`：

1. **让用户在「新建筛选 / 选已有筛选」两个模式里选**——默认落在「选已有」且预选第一条规则；
2. 「新建」路径把标题登记成一条 keyword 规则（`addTgMonitorFilter`）。

用户裁定：**筛选是按标题筛选的**——消息的标题（caption）本来就在，
同名标题自动归入同一剧集是筛选系统的既有语义；把「选择/新建筛选」做成用户必经步骤，
等于让用户反复「加入」一个已经存在的东西。设计意图不清晰。

## 二、根因

BUG-470 实现时把「筛选名 = 标题 = 剧集名，三者同一」的定稿拆成了**两个显式模式**：
「新建」与「选已有」。既然三者同一，这个分支就是伪分支——

- 标题对应的筛选**已存在** ⇒ 按标题匹配直接复用（这正是「筛选根据标题筛选」的含义）；
- **不存在** ⇒ 用标题落一条新规则（同关键词幂等）。

两种情况都无需用户选择。让用户手动选 = 把系统能自己推导的事推给用户，且「选已有」
默认预选第一条规则还诱导误归属。

## 三、修复（入口层，核心归档轴不动）

1. **对话框砍成一件事**：一个可编辑的标题输入框（预填 caption），没有模式选择、
   没有规则下拉。提交时按标题精确匹配（`label === title || keyword === title`）
   复用已有筛选的 id 作 `seriesKey`；没有才落新规则。
2. **入口改名**：「加入筛选并缓存」→「**缓存入库**」——「加入筛选」作为显式动作不存在，
   归属是入库的隐含结果（标题即筛选）。
3. **消灭无名入库的重复入口**（BUG-470 §三.1 认定的根因，实现时却把两条路径都留下了）：
   未落盘条目的「普通缓存」（无 titleHint/seriesKey 入队 ⇒ 无名批次）与「加入筛选并缓存」
   合并为唯一「缓存入库」。重试态（缺字节/失败）保留纯重试，不再弹名。

`seriesKey = tg:filter:{id}`（BUG-438 轴）不变——筛选面板与 TG 面板两条入库链路仍同轴。
