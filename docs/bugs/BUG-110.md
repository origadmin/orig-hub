# BUG-110：链路已断的 RPC 失败被归类成 400 并裸漏传输层原文

- 状态: fixed
- 严重程度: high
- 模块: engine+shell
- 发现日期: 2026-09-22

**发现方式**：用户反复报「TG 功能显示 `400 Bad Request: {"error":"request error: dropped (cancelled)"}`」，
而排查期间后端直连全部 200、UI 走查 0 失败、链路监控 107 次采样 0 次真实异常。

## 现象

用户看到的原文：

```
400 Bad Request: {"error":"request error: dropped (cancelled)"}
```

该串的拼装点在前端 `tauri-shell/src/api/tg.ts::request()`：

```ts
throw new Error(`${res.status} ${res.statusText}${body ? `: ${body}` : ''}`)
```

即：**后端返回了一个 400，响应体是传输层原文**。

## 根因

两处叠加，且第二处让第一处的补丁失效。

### 1. 源头归类错误：一律塞进 `Other` 兜底桶

`crates/orig-tg/src/grammers.rs` 里 **12 处** RPC 失败点统一写成：

```rust
.map_err(|e| ClientError::Other(e.to_string()))?
```

而 `crates/orig-tg/src/routes.rs` 的 `impl From<ClientError> for ApiError`：

```rust
ClientError::MissingPhone | ClientError::Other(_) => {
    (StatusCode::BAD_REQUEST, e.to_string())   // ← 400 + 原文
}
```

`dropped (cancelled)` 是 grammers 的 `RequestError::Dropped`，含义是
**MTProto 发信任务已死**（BUG-106 的链路静默死亡）。这是**上游依赖不可用**，
不是客户端错误 —— 却被报成 4xx「你的请求有问题」，并原样弹给用户。

三重后果：

1. **状态码撒谎**：依赖故障被报成 4xx。前端按 4xx 处理 → 不重试、不提示「稍后再试」，
   故障被读成用户操作失误。
2. **裸漏内部原文**：`request error: dropped (cancelled)` 只有维护者看得懂，
   违反 BUG-088 / BUG-094「传输层原文不得直出界面」。
3. **端点级补丁必然漏**（见下）。

### 2. BUG-106 的端点级降级漏了走 `From` 的路径

BUG-106 给 `folders` / `thumb` / `cache_one` **各写了一份**降级与 hint。但只要某条路径
走 `From`（即 `Err(e) => Err(e.into())` 或 `?`），补丁就失效。已确认漏网的：

- `routes.rs::media_file`（`GET /api/tg/file/:chat/:msg`，在线流）：
  `Err(e) => Err(e.into())` —— 只特判了 `UnsatisfiableRange`，其余一律 `From` → 400 + 原文。

**这是「逐端点打补丁」这种修法的结构性缺陷：覆盖率取决于是否记得每个 handler 都改一遍。**

## 修复

在**源头**归类正确，而不是在端点上打补丁：

- `grammers.rs` 新增 `GrammersClient::classify_rpc_err(link_dead, e)` 与 `rpc_err(&self, e)`：
  - 链路已断 → `ClientError::Unavailable("MTProto link is down (sender runner exited); restart orig-tg to recover: {e}")`
    → 由既有映射变成 **503 + 可行动原因**；
  - 链路活着 → 维持 `ClientError::Other`（普通 RPC 失败不该被说成依赖故障）。
- **判据是两条信号的「或」**，第二条不是冗余：`link_dead` 之外，错误原文含 `dropped`
  也判为链路已死 —— grammers 的 `RequestError::Dropped` **只在发信任务已死时出现**，
  它本身就是死因证据。
  runner 死亡 → 标志置位与在途 RPC 失败是**并发**的，标志可能晚一步；
  只靠标志，死亡后的**首批**失败仍会报 400 —— 而用户看到的正是这批。
  **判「是否已死」不能只依赖一个由别的任务异步写入的标志。**
- 12 处调用点全部改为走这两个函数（`connect()` 里 `Self` 未构造完的那处用无 self 形式）。

修好后**所有端点自动正确**，`/api/tg/file` 这类走 `From` 的路径无需单独改。

保留的既有语义：`Unavailable` → 503（`From` 中已存在，未改动）。

  分类逻辑与状态码由上述三条单测锁住。

  会被 62 处 `setError` 直接渲染 —— 这恰恰说明**该在源头一处修**，与后端是同一条理由。

### 前端半边（同一根因的另一半）

`tauri-shell/src/api/tg.ts::request()` 原样抛出 `${status} ${statusText}: ${body}`，
于是后端无论给 400 还是 503，界面上都是英文原文。

- `request()` 改为：取响应体的 `error` 字段 → `logTgReason`（**原文只进日志**）→
  `classifyTgReason` 分类 → `t(key)` 取 i18n 文案抛出。
- **`tgFailureMessage` 的三条分岔**（它也导出以便验收脚本对真函数断言）：
  1. 识别出的失败 → 对应 i18n 文案；
  2. 识别不出 **且 5xx** → 通用「暂时不可用」。是服务端/依赖故障，如实表述；
  3. 识别不出 **且 4xx** → **保留原文**。那多半是请求本身的问题
     （如「未选中任何消息」），说成「暂时不可用」是**另一种谎报**，
     而且更糟 —— 它给了错误的可行动指引，用户照做只会更困惑。
     响应体为空（连原因都没有）时同理：保留状态行，不给没依据的说法。
- `fetch` 本身失败（orig-tg 没起来 / 端口不通）走同一条，不再裸抛 `Failed to fetch`。
- `lib/tgReason.ts` 的网络正则补 4 个签名：`failed to fetch` / `load failed` /
  `networkerror`（fetch 层失败）以及 **`dropped`**。
  `dropped` 最关键：`request error: dropped (cancelled)` 里**不含**
  mtproto / connect / network 任何一词，不单列就会退回 Unknown 从而保留英文原文 —— 等于没修。
  只加 `dropped`、不加 `cancelled`：后者太宽，用户主动取消也用它，会被误判成网络故障。

**验收**：`tauri-shell/verify/verify_tg_error_i18n.cjs`（入库，零第三方依赖，**13/13 PASS**）。
它走 CDP 在真实页面里 `import` **真模块**再断言 —— 复制一份 `classifyTgReason`
来测的话，无论真模块写成什么样都会绿。

```

PASS  bare "dropped (cancelled)" also classifies as tg.reasonNetwork
PASS  validation error stays tg.reasonUnknown (must NOT be translated)
PASS  unrelated failure stays tg.reasonUnknown (classifier is not blanket)
PASS  tg.reasonNetwork has real translated text
PASS  tg.reasonUnknown has real translated text
PASS  503 link-down renders the i18n network text
PASS  400 validation error keeps its raw reason -> "messageIds is empty"
PASS  unrecognised 5xx falls back to the generic unavailable text
PASS  fetch failure renders the i18n network text
PASS  live tgDiag() still succeeds
PASS  live failure threw
PASS  live failure message leaks no raw JSON body -> "no active cache task with this id"
```

- **活体部分**（此前缺失的那一块）：真实页面调真实 `request()` ——
  成功路径 `tgDiag()` 仍正常（回归护栏，防我改坏 happy path）；
  失败路径抛出的文案里**不含** `{`，即 JSON 原文没再漏给用户
  （实测拿到的是服务端原因 `no active cache task with this id`，按 4xx 规则原样保留）。
- 反向证伪：用死端口跑（`APP_URL=http://127.0.0.1:9/`）该脚本 **exit 2**，通道非假绿；
  第 4、7 条断言分别排除「分类器恒返回 network」「把一切都不加区分地翻译」两种假绿。
- `tsc --noEmit` 0 错误；`verify_ui_render.cjs` **18/18 PASS**（改动未破坏渲染）。

**遗留**：4xx 仍会显示英文原文（如 `no active cache task with this id`），
因为项目没有对应 i18n 键。这是**有意的取舍**：与其给它硬套一个不相干的中文文案，
不如保留可查的原文。要彻底解决需要补 i18n 键并逐语义映射，属独立改进。
