# BUG-190: `media_item.kind` 可被三条生产路径改写，而挂载表不变量只在 INSERT 侧守护

- 状态: open
- 发现日期: 2026-09-29
- 模块: engine
- 严重程度: mid

## 现象

**未观测到用户可见实例**（本条是**不变量缺口**，非已复现故障；如实标注，勿写成已复现）。

潜在后果有两个，都由同一个缺口派生：

1. 一个条目先以 `photo` 身份挂为某集的**挂图**（`media_episode_image`），
   之后 kind 漂移为 `video` ⇒ 它可再被挂为**备用源**（`media_episode_source`），
   于是**同一 item 同时出现在挂图与备用源两张表**。这直接推翻 **BUG-182** 的
   「同一 itemId 不可能兼属，故摘除备用源不会误删挂图」这一前提。
2. 反向：先挂为备用源的 `video` 条目漂移成 `photo` ⇒ 一个「视频」出现在某集的
   **浏览位（挂图）**里，与 `media_episode_image` 的 photo-only 语义相悖。

## 根因

### 一、`media_item.kind` 有三条生产写路径（不是一条偶然路径）

| # | 写路径 | 位置 | 事实 |
|---|---|---|---|
| 1 | `backfill_item_bytes` | `media.rs:1281` | `UPDATE media_item SET file_path = ?2, kind = COALESCE(?3, kind) WHERE id = ?1` —— 字节落盘时按扩展名分类**校正** kind |
| 2 | `upsert_media_item` | `media.rs:1217` | `ON CONFLICT(source, ref) DO UPDATE SET ... kind = excluded.kind` —— **无条件覆盖，无 `COALESCE`、无 `NULLIF`** |
| 3 | item patch | `media.rs:1384`（值来自 `:1380` `patch.kind.clone().unwrap_or(existing.kind)`） | `UPDATE media_item SET ... kind = ?6 ...` —— **用户编辑路径** |

输入本身是不稳定的：三处传入的 kind 都是**每次调用现场推导**，不是从库里读回的既有值。

### 二、⚠️ 陷阱：`upsert_media_item` 的调用点分布，会让人把路径 2 判成「测试专用」

- 在 `media.rs` 内，`upsert_media_item` 的**全部调用点都在 `#[cfg(test)] mod tests`** 里
  （测试模块起始 `media.rs:4278`）⇒ 只 grep `media.rs` 会得出「只有测试在调它」的结论。
- **但生产调用在 `routes.rs`，且都在测试边界 `routes.rs:4016` 之前**：

| 生产调用点 | 传入 kind 的来源 |
|---|---|
| `routes.rs:1066` | 由 TG 元数据 mime 推导（`video/`→`"video"`、`audio/`→`"audio"`、**其余一律回落 `"file"`**，见 `:1049-1057`） |
| `routes.rs:1448` | 同为按次计算的 kind 变量 |
| `routes.rs:2632` | `it.kind` |

⇒ **路径 2 是三条生产路径**，不是测试专用。按「media.rs 里只有测试在调」下判断会把它降级甚至跳过。

### 三、守护侧：缺口在 `media_item`，**不在**挂载表

实测各触发器的**挂载目标**：

```
media.rs:406  AFTER DELETE ON media_item              ← media_item 上唯一的触发器
media.rs:535  BEFORE UPDATE OF item_id ON media_episode
media.rs:550  BEFORE UPDATE OF item_id ON media_episode_source
media.rs:420  BEFORE INSERT ON media_episode_image
```

- `media_item` 上**没有任何 `BEFORE UPDATE` 触发器** ⇒ kind 被改写时**无任何校验**。
- `:535` / `:550` 两个 `_upd` 守卫的触发条件是 **`UPDATE OF item_id`** ——
  只在「改这一行指向哪个 item」时触发；**item 自己的 kind 变了不会触发它们**。
- ⇒ 即使 `media_episode_image` 补一个与 `media_episode_source` 对称的 `_upd` 守卫，
  **也堵不住这个洞**（现有 `_upd` 守卫对本场景本就无效；source 那侧其实同样裸奔）。
  「两表守卫不对称」是**真事实但非本缺口成因**，按它修会得到
  「触发器装上了、断言绿了、洞还在」。

### 四、证据等级（**必须照写，勿升级为「已复现」**）

> **生产可达、机制成立、实例未观测。**

- **机制成立**：路径 2 的 SQL 无条件覆盖；三处输入均为现场推导且含 `"file"` 回落分支。
- **项目自己已文档化这种漂移**：`media.rs:1268-1271` 注释明写「T0 登记时 kind 只能来自
  `media_type`/mime … 如 octet-stream 的 .mp4 文档 **T0 登记为 `file`**，回填校正为 `video`」
  ⇒ 「同一 `(source, ref)` 先后得到不同 kind」是**已被承认的真实形态**（路径 1 正是为它而设）。
- **未观测**：尚未观测到「路径 2 单独造成一次 kind 翻转」的具体实例（未执行写操作）。

## 复现

（待实施时执行；当前为预先声明的判据。）

1. 条目 P 以 `photo` 登记 → 挂为某集挂图（`media_episode_image` 有行）。
2. 走上述三条路径**之一**把 P 的 kind 改成 `video`（建议三条各覆盖一次）。
3. 断言：操作后**不得**存在「P 同时在 `media_episode_image` 与 `media_episode_source`」的状态。

**验牙要求**：修复前该断言必须**红**。若修复前即为绿，说明断言没打在真实改写路径上。

**反向证伪**：断言**不得**写成「存在名为 `trg_media_episode_image_video_only_upd` 的触发器」
这类**实现措辞**判据 —— 那正是本条要避免的「装上了、绿了、洞还在」。

## 修复

**待修 —— 实现排队中（team-lead 已排期，排在 BUG-189 之后）。**

**修复范围约束（是要求，不是建议）**：三条写路径的可达性排序为
**#2 ≈ #3 > #1**（#2 有 3 处生产调用、登记即触发；#3 是用户编辑；#1 需可分类扩展名）。
因此：

- 若采用「**在 `media_item.kind` 的 UPDATE 侧加触发器守卫**」→ 一个触发器覆盖三条；
- 若采用「**在各写路径内同事务复核并清理挂载行**」→ **三条都必须改**，
  **漏掉任一条即等于本条未修复**。

**只堵路径 1 不算修复。**

## 关联

- **BUG-182**：本条缺口使其「同一 itemId 不可能兼属，故摘除备用源不会误删挂图」的结论
  只在「kind 不被改写」的前提下成立；而 kind **确实会被改写**。
- **BUG-044**：`media_episode_source` 只收 video 的规则级不变量（由
  `trg_media_episode_source_video_only_ins/upd` 表达）—— 其**判据是 kind**，
  故 kind 可漂移即意味着该不变量的输入本身可被改写。
- **BUG-168**：集级挂图（`media_episode_image`）的引入，使「同一 item 的两种挂载身份」
  成为可能，本缺口才有后果。
- **BUG-189**：同批发现；共同形态是「在**单条共享连接**（`store.rs:100-108`）上
  把**连接级状态**当**请求级状态**」。两处宜一并自查。
