# BUG-174: 无 BitTorrent 支持——协议抽象层已预留（`SourceKind::Bittorrent` / `DHT` / `PINNING` 全部未实现），但入口与任务模型未就绪：`magnet:` 无协议实现、`.torrent` 本地文件无入口、引擎单文件模型与种子多文件冲突、DHT 无进程级生命周期

- 状态: open
- 发现日期: 2026-09-29
- 模块: engine
- 严重程度: mid
- 类型: epic
- 延期至: 2027-01-31（理由：设计级工程，需独立里程碑；详见关联设计文档）

## 现象

用户在「新建下载」输入 BitTorrent 相关地址时，**无任何一类可用**：

| 输入形态 | 当前结果 | 证据 |
|---|---|---|
| `magnet:?xt=urn:btih:...` | **400 `unsupported scheme`** | `Registry` 仅注册 `virtual`（`mock://`）与 `http`（`http`/`https`）两个协议；`magnet` 无实现 |
| `D:\path\file.torrent` | **400 `unsupported scheme`** | `.torrent` 无 `://`，`routes.rs:140` 的 `split("://").next()` 返回**整个路径字符串**，`find_by_scheme` 必失败 |
| 拖入种子文件 | 无此入口 | `AddDownloadDialog.tsx:137` 的 placeholder 为 `https://example.com/file.zip`，无文件选择 |
| 协议徽章显示 `BT` | **不可能** | daemon 已下发 `Progress.protocol`（`protocol.rs:358`，`routes.rs:309`），但前端 `tauri-shell/src/` 全域 grep `protocol` **0 命中**——设计要求（`DESIGN_BRIEF.md:41/220`「协议徽章（HTTP/BT/IPFS/Video）」）从未实现 |

**同时存在「设计早已预留、实现从未落地」的不一致**：`orig-core/src/protocol.rs:3` 的头注释
原文即「## 关键演进：**为支持 HTTP+BT 混合下载**」，`lib.rs:5/10` 亦两处独立写明 BT 为设计目标，
`CapabilitySet::DHT`（`:44`）、`MULTI_NODE`（`:46`）、`PINNING`（`:48` 注释「BT 做种 / 长效保活
（Orig 产品特性）」）、`SourceKind::Bittorrent`（`:270`）**全部已定义、全部无实现**。
即：**协议抽象层按支持 BT 设计，但 BT 从未被实现，且无任何登记追踪这一缺口**。

## 根因

### 根因 1：`magnet` / `.torrent` 均无入口（入口层缺失）

`orig-daemon/src/routes.rs:140-149`：
```rust
let scheme = req.url.split("://").next().unwrap_or("").to_string();
let proto = match st.registry.find_by_scheme(&scheme) {
    Some(p) => p,
    None => return (StatusCode::BAD_REQUEST, ... "unsupported scheme" ...),
};
```
- `magnet:` 有 scheme 但 `Registry` 无对应 `Protocol` → 无实现，非 bug；
- `.torrent` **无 `://`** → `split("://").next()` 返回整个字符串（如 `D:\a\b.torrent`），
  `find_by_scheme("D:\a\b.torrent")` 必然 `None` → **结构上不存在本地文件入口**。

`Registry::find_by_scheme`（`orig-core/src/registry.rs:23-30`）以 `schemes()` 的字符串包含判定，
**只有 URL 通道，没有「本地文件 → 协议」通道**。

### 根因 2：引擎「一个任务 = 一个输出文件」与 BT 多文件种子不同构（模型层冲突）

`orig-core/src/engine.rs` 实测（`:220` / `:222` / `:231` / `:383` / `:416` / `:432`）：
```rust
pub output: PathBuf,                     // ← 单一输出文件
pub block_map: RwLock<BlockMap>,         // ← 单一完成位图
pub final_hash: RwLock<Option<String>>,  // ← 单一 sha256
```
`BlockMap.total` 是**单文件总字节**，`block_at(idx)` 按 `idx × block_size` 算 offset
（`protocol.rs:211-224`）——**只有一个块偏移空间**。

BT 的多文件种子：一个 info hash 下 N 个文件，且 **piece 可跨文件边界**
（一个 piece 覆盖文件 A 尾部 + 文件 B 头部）。因此：

- 输出路径不是 1 个 `PathBuf` 而是 N 个（含种子内多级目录结构）；
- 完成判定不能用单一 `BlockMap.all_done()`；
- BT 自带的是**每 piece 的 SHA-1（v1）/ SHA-256（v2）**，与 `engine.rs:416` 的
  整文件 sha256 **不同源**，`final_hash` 语义会歧义；
- 续传读的是**单文件长度**（`:383`），多文件须逐文件独立。

**注意 `engine.rs:17` 的承诺**：「引擎只跟 `Source`/`BlockMap` 对话，不感知具体协议——
**加 BT 不改这里**」。该承诺对**单文件种子成立**，对**多文件种子不成立**——
这是本 BUG 的核心工作量，且**该承诺注释本身构成一个未登记的过度承诺**
（写注释时只考虑了单文件情形）。

### 根因 3：DHT 是进程级单例，与「任务即 Source 集合」结构不同构（生命周期错位）

- `orig-daemon/src/main.rs:30-33`：协议**编译期注册**（`registry.rs:1` 原文「编译期注册」）；
- `orig-daemon/src/routes.rs:292`：**每任务**调 `proto.create_sources(...)` 建源。

DHT 的真实需求与之相反：
- **单例**：一个进程一张 DHT 路由表（BEP-5，UDP 端口监听）；
- **长生命周期**：节点表须跨任务存活并随时间积累；
- **启动期开销**：bootstrap 连接 + UDP 端口绑定；
- **持久化**：节点表落盘（应落 `download_dir` 域）。

`Protocol` trait（`protocol.rs:304-324`）**无 `startup()` / `shutdown()` 生命周期钩子**，
`AppState`（`state.rs:81` 附近）也无相应组件位。BT 首次实现时须新增进程级组件。

### 根因 4：`MULTI_NODE` bit 已被 HTTP 以不同语义占用（次要，登记备查）

`orig-protocol-http/src/lib.rs:630-639` 的 `capabilities()` 声明了 `MULTI_NODE`，
语义是「**多网卡分流**」（`:657-691` 为每个网卡建 `BoundSource`）；
而 `protocol.rs:46` 的注释写 `MULTI_NODE` 是「**BT 多 peer 并行**」。

**同一 bit 承载两种语义且已被 HTTP 占用**。BT 实现时会撞名。不影响当前行为，
但 BT 动工前须先裁定该 bit 归属或为 BT 新增独立 bit。

### 根因 5：零 BT 依赖（依赖层缺失）

`download-engine/Cargo.lock` 实测 grep `torrent|magnet|dht|bencode` **全部 0 命中**。
BT 实现须引入 crate（如 `librqbit` / `cratetorrent`），这是本仓
**首个非 HTTP 网络栈依赖**，须走依赖评审（新依赖引入面、许可证、`unsafe` 审计）。

## 复现

**复现 1（magnet 不可用）—— 已在真实 daemon 跑通，问题确证存在**：
```sh
curl -s --noproxy '*' -w '\nHTTP %{http_code}\n' -X POST http://127.0.0.1:18760/api/downloads \
  -H 'Content-Type: application/json' \
  -d '{"url":"magnet:?xt=urn:btih:0123456789abcdef0123456789abcdef01234567"}'
```
**实测返回（2026-09-29，daemon 端口 18760，release/debug 均可）**：
```
HTTP 400
{"error":"unsupported scheme","scheme":"magnet:?xt=urn:btih:0123456789abcdef0123456789abcdef01234567"}
```
→ `scheme` 字段回显了**整个 magnet 串**（`split("://")` 对 `magnet:?` 这种「冒号而非 `://`」的 scheme 语法返回整串），`find_by_scheme` 必然 `None` → 400。
**这是真实进程返回的 400，不是代码阅读推断**——证明「magnet 无协议实现」的问题真实存在。

**复现 2（.torrent 本地路径不可用）—— 已跑通，问题确证存在**：
```sh
curl -s --noproxy '*' -w '\nHTTP %{http_code}\n' -X POST http://127.0.0.1:18760/api/downloads \
  -H 'Content-Type: application/json' \
  -d '{"url":"D:/tmp/ubuntu.torrent"}'
```
**实测返回**：
```
HTTP 400
{"error":"unsupported scheme","scheme":"D:/tmp/ubuntu.torrent"}
```
→ `.torrent` 无 `://`，`split("://").next()` 返回**整个路径字符串**，`find_by_scheme("D:/tmp/ubuntu.torrent")` 必然 `None`。
**真实进程返回 400 且 scheme 回显整串**——证明「本地种子文件无入口」的问题真实存在（非推测）。

**复现 3（协议徽章不存在）—— 静态核验（非运行复现）**：
```sh
grep -rn "protocol" tauri-shell/src/   # 0 命中（而 daemon 已在传 Progress.protocol）
```
前端 `tauri-shell/src/` 全域 grep `protocol` 为 0 命中；`DESIGN_BRIEF.md:41/220` 的「协议徽章（HTTP/BT/IPFS/Video）」设计要求从未实现。此项为静态代码核验。

**反向对照（避免把「端点坏」误判成「方案坏」）**：
```sh
curl -s --noproxy '*' -w '\nHTTP %{http_code}\n' -X POST http://127.0.0.1:18760/api/downloads \
  -H 'Content-Type: application/json' \
  -d '{"url":"http://127.0.0.1:1/foo.bin"}'
# 实测: HTTP 500 {"error":"probe failed",...}
```
→ `http` 方案被正常识别（通过 scheme 校验），仅因探测目标不可达而 500，**并非 `unsupported scheme`**。
这反证了复现 1/2 的 400 是**针对未支持 scheme 的专属拒绝**，而非 daemon 没起或路由坏了——坐实问题定位在「入口/协议层」。

## 修复

**本 BUG 为需求扩展的登记项，修复 = 实现 BT 支持。** 分五层，**顺序不可颠倒**：

| 层 | 内容 | 是否改抽象 | 前置 |
|---|---|---|---|
| L0 | 依赖评审（引入 BT crate） | — | — |
| L1 | 新增 crate `orig-protocol-bittorrent`：`BtProtocol`（六方法）+ magnet 解析 + `.torrent` bencode 解析 + BEP-9 元数据交换 + BEP-5 DHT 单例 + tracker | 否（trait 签名够用，**不得改**） | L0 |
| L2 | 引擎多文件任务模型（根因 2） | **改 `Task` 结构** | L1 |
| L3 | 种子库目录 + 入口：`<download_dir>/torrents/` + `AddReq` 判别字段（打开 `.torrent` 文件）+ magnet 归一落盘（根因 1） | 改 `routes.rs` / `AddReq` | — |
| L4 | 前端协议徽章（补齐 `DESIGN_BRIEF.md:41/220` 设计要求）+ BT 专属字段（peer 数/上传速度/做种态） | — | L2 |
| L5 | DHT 进程级组件接入 `AppState` + 持久化 `<download_dir>/torrents/dht.dat`（根因 3） | 改 `AppState` | L1 |

**D1/D2/D3 三项已于 2026-09-29 由用户裁定完毕**（详见评估文档 §5，此处只记结论）：

- **D1 = 立做种能力**（原 A）。**须修订 `docs/bugs/BUG-082.md:121`** 并写明变更依据与日期。
  注：BT 规约**不要求**做种（纯 leech 亦合规），裁定理由是「回报 swarm」的产品选择。
  **配套约束：默认关闭 + 显式开启 + 可配总上传限速 + 可随时一键停止做种**
  （P2P 上传的合规提示不因裁定取消，落在开启控件处，不做常驻横幅）。
- **D2 = 专门种子库目录 + 种子/磁链统一存为种子文件 + 打开文件阅读入口**：
  - 新增 `<download_dir>/torrents/`（**与 `blob-store-design.md` C1 的 `<download_dir>/blobs/` 平级**）；
  - 种子文件以 **info_hash 命名**（`<download_dir>/torrents/<40hex>.torrent`）——
    info_hash 是 BEP-3 定义的种子唯一身份，天然去重；
  - **`magnet:` 经 BEP-9 取到元数据后合成 `.torrent` 落盘** ⇒ 磁链是种子的**来源**，
    不是独立存储形态；**入口有两条**（打开 `.torrent` 文件 / 粘贴 magnet），
    但**存储形态归一**；
  - **不采用 `torrent:///` scheme 伪装**（选原 B：`AddReq` 增判别字段），
    但 **`magnet:` scheme 仍保留**；
  - **不新增 `app_setting` key**（目录由 `download_dir` 派生）⇒ **不扩大 BUG-173 的 A1–A6 范围**。
- **D3 = 不入媒体库**（原 B）。BT 属**基础下载管理**，不是媒体管理：
  不写 `media_item`/`media_episode`、**不新增 `source` 枚举值**、
  不扩「缓存即入库」（仍限 TG 缓存）。
  **收益**：消除了原 D3-A 与拆库在途的冲突 ⇒ **BT 实现不再依赖 BUG-173 落地**。

**明确不做**（防顺手扩）：不改 `Protocol`/`Source` trait 签名；不实现 IPFS/FTP
（`SourceKind` 无 `Ipfs` 变体，用户本次只提 BT）；不动 TG 侧任何代码；
不做种默认开启；不新增 `app_setting` key；不动 BUG-173 的 A1–A6 范围；
BT 产物不入媒体库。

**与在途工作的依赖**：BT 落盘路径须纳入 `docs/design/cache-root-unification-2026-09-28.md`
的可删区判据（依赖其 C2 的 `ByteOwner` 三态 —— **不阻塞开工，但落盘判据须与之对齐**）；
BT 产物存储若走 blob store，须先对齐「piece hash（SHA-1/SHA-256）≠ 文件 sha256」的口径
（`docs/design/blob-store-design.md`）。

**须同步修订的既有文档**：
- `BUG-082`（`docs/bugs/BUG-082.md:121`「已做种/种子 → 不做」）—— D1 变更，须写明依据与日期；
- `docs/DESIGN_BRIEF.md`（协议徽章）—— 纳入 L4，非修订是补齐。

**开工前必须实测**：BT 监听端口（默认 6881 元组）在本机是否可绑——
本机 WinNAT 保留 TCP 段 `9757-9856`（见项目记忆），须实测确认不落入保留段。

> **逻辑边界（本次修正）**：本 BUG 状态为 `open`（未修复），**不存在可验收的修复**，
> 因此本节点**不是 `## 验收证据`**（`验收证据` 是修复后、须带真实可核验引用才立的，见 `docs/rules/bug-registry.md` 门禁契约）。
> 此处仅**预先声明**修复完成后必须满足的可证伪判据，作为实现清单；
> 待实施且 `状态` 转 `fixed` 时，须把本节点改名为 `## 验收证据` 并补入跨机器可核验引用
> （入库路径或真实提交 hash）。
>
> 判据的可反向证伪性在修复时务必逐条跑通，**不得改判据让测试变绿**。

修复后必须满足（每条须可反向证伪）：

1. `magnet:?xt=urn:btih:<40hex>` POST `/api/downloads` → **非 400**，返回任务 id；
   反向证伪：改 `<40hex>` 为 39 字符必须 FAIL（400）。
2. `.torrent` 本地文件可提交并进入任务；反向证伪：不存在的路径必须 FAIL；
   坏的 bencode 必须**显式报错**（不得静默降级为普通下载）。
3. 多文件种子下载完成后**每个文件**落于 `<download_dir>/<种子名>/<相对路径>`，
   且文件数与种子内 `files` 数量一致；反向证伪：单文件种子必须**不**建额外子目录。
4. **种子库目录**：`magnet:` 与 `.torrent` 两种输入，最终都产出
   `<download_dir>/torrents/<40hex>.torrent`，且**同一 info_hash 只存一份**
   （用两个 tracker 不同的同内容磁链提交，须命中同一文件）；
   反向证伪：改 info_hash 一个字符必须产出不同文件名；
   路径含中文/空格必须正确落盘（Windows 中文路径编码）。
5. 协议徽章：下载卡片对 BT 任务渲染 `BT`（或 i18n 键值），HTTP 任务渲染 `HTTP`；
   反向证伪：把 `protocol` 字段改错值必须渲染出错误徽章（证明徽章真的读了该字段，
   而非硬编码）。
6. DHT 单例：连续提交 2 个 magnet 任务，**UDP 监听端口只出现 1 个**；
   反向证伪：打桩使 `AppState` 建两份 DHT 必须被断言捕获。
7. **做种默认关闭**（D1 配套约束）：全新建配置下 `GET /api/config` 的做种开关为
   **关闭**；未显式开启时**无任何上传流量**（`Progress` 上传速度为 0）；
   反向证伪：打桩把默认值改成开启必须被断言捕获。
8. **做种可停可限**：开启做种后能一键停止（停止后上传归 0）；
   设置上传限速后实测速率 ≤ 限速值 × 容差；
   反向证伪：限速设为 0（不限）时必须超过该阈值（证明限速真的生效，而非恒 0 假绿）。
9. 落盘判据：BT 产物（含种子库目录）在 `cache-root-unification` 的 `classify_bytes`
   下归类正确（在 `download_dir` 内 → `Owned`）；
   反向证伪：指向库外路径必须归类为 `External` 且不可删。
10. **不入媒体库**（D3）：BT 下载完成后 `media_item` 行数**不变**、
    `source` 枚举**无新增值**；反向证伪：断言必须能捕获「BT 产物被写入 media_item」
    这一情况（即该断言有牙）。

**入库路径（修复时须建立）**：
- `download-engine/crates/orig-protocol-bittorrent/src/lib.rs`
- `download-engine/verify/bt_*.py`（引擎契约验收，跨机器可复核）
- `download-engine/verify/bt_seed_policy.py`（做种默认关闭 + 限速 + 可停，判据 7/8）
