# BUG-036：剧集里图片被当成视频播——播放序列未按媒体类型分流

- **状态**：fixed
- **日期**：2026-09-18
- **模块**：shell（`MediaViewer` / `media/EpisodeList` / `media/SeriesDetail` / `MediaLibraryPanel` / `lib/tgmedia`）

## 现象

用户主诉（原文）：

> 「有个严重的逻辑问题，加入剧集的时候，视频和图片全部都作为视频播放了，
> 图片应该作为浏览或者海报内容，只有视频才是播放内容，从没见过播放图片的电影的。」

## 事实取证（先复现，再定性）

剧集可以是**混合内容**——实测 8 个剧集里就有这样的分布：

| 剧集 | 分集数 | kind 分布 |
|---|---|---|
| 城市与科技合集 | 8 | **5 video + 3 photo**（混合） |
| AI成人短剧【蜜桃TV】 | 3 | 纯 photo |
| 风景图集 | 18 | 纯 photo |
| Jellyfin/Sintel/BBB/自然风光 | 9–14 | 纯 video |

`probe_mixed_series.cjs` 走「剧集详情 → 点某集」逐集记录 DOM，得到两组硬事实：

**① 混合剧集（点视频集）**

| 观测项 | 值 |
|---|---|
| 播放组位置 | **`1/8`** ← 含图片 |
| 侧栏项数 | 8（含 3 个图片项） |
| 图片项呈现 | `第 3 集 · --:--`、`第 4 集 · --:--` —— 与视频**完全同格式**，带集号 |
| 连播行为 | 播完第 2 集 → **自动连播到第 3 集（图片）** |

→ 图片确实被编进了「电影」的播放序列。

**② 纯图片剧集（点任意集）**

| 观测项 | 值 |
|---|---|
| 渲染 | `<img>`（这一点原本是对的） |
| 但 | 进入了**播放器页**：`n/N` 计数、侧栏叫「选集」、图片带集号「第 4 集/第 5 集/第 7 集」 |
| 编号 | `n/N = 1/3` 与高亮「第 **4** 集」**不一致**（`episodeNo` 断档 4、5、7） |

## 根因（四处，逐层）

1. **播放组未按类型分流**（主因）
   `MediaLibraryPanel.playItems` 把剧集全部 entries 塞进播放组，`MediaViewer` 的
   `‹ ›`、`n/N`、键盘 `←/→`、自动连播全部基于该全量组 —— 图片因此获得播放序列中的位置。

2. **侧栏不区分类型**
   `EpisodeList` 对图片与视频同排版：图片显示 `--:--` 时长、带集号、高亮时给 `Play` 图标。

3. **详情页动作标识错位**
   `SeriesDetail` 的图片分集 hover 显示 `▶`、`title="查看 / 播放"` —— 把「浏览」标成了「播放」。

4. **兜底把未知类型伪装成视频**
   `episodesToItems` 用 `e.kind ?? 'video'`：`kind` 为空的条目会被**静默当视频播**，
   异常不可见。（实测当前数据均正常下发 `kind`，故非本次触发原因，但属随时会咬人的危险兜底。）

## 修复

| 位置 | 改动 |
|---|---|
| `MediaViewer.tsx` | 引入 `modeOf(kind)`（`play`/`browse`/`none`），由当前项的 kind **派生**当前组 `group`；`‹ ›`、位置计数、键盘、自动连播全部基于 group。`viewer.index` 仍指向全量 → **store 契约零改动**，侧栏点另一种类型时组自动重建 |
| `MediaViewer.tsx` | 图片模式挂「图片浏览」标识、位置文案为「第 n / m 张」；`none` 类型显示「不支持预览」而非挂一个必然失败的元素 |
| `media/EpisodeList.tsx` | 图片项：徽标改类型图标、副行显示「图片」；视频项：徽标用**同类序列序号**（从 1 连续），原始集号以 `E<n>` 标于副行；头部标注「视频 5 · 图片 3」 |
| `media/SeriesDetail.tsx` | 图片分集 `title="浏览图片"`、hover 图标改为图片语义；emoji（`🎬/🎵/▶/✎/🖼`）全部换为 lucide 图标 |
| `MediaLibraryPanel.tsx` | `e.kind ?? 'video'` → `?? 'file'`（让异常可见）；原始文件名不再当标题 |
| `lib/tgmedia.ts` | 新增 `isRawFileName()`：`photo--123_456` 是下载器命名，不是标题 |

**关于「集号」的取舍**：图片会占用剧集集号（实测某剧集视频集号为 1、2、6、7、8，因为 3/4/5 被图片占了）。
侧栏是导航，故按「连着播第几个」呈现（视频 1–5 连续、图片 1–3 连续），
同时在副行标出原始集号 `E6/E7/E8`，避免与数据脱节。**数据层的集号分配问题另计**（见「已知残留」）。

### 验收脚本自身的两个坑（已修，留作教训）

1. **选择器把「当前高亮项」当成图片项**：视频项高亮时自身也带 `Play` 图标，
   `filter({has: svg})` 会连它一起选中；点当前项走 `if (!active)` 分支被拦掉 → 假失败。
   修正：加 `:not([aria-current="true"])`。
2. **`body.innerText` 断言过宽**：播放器是 `z-40` 覆盖层，被盖住的媒体库网格仍在 DOM 里，
   网格中合法的原始文件名会被算进来 → 假失败。修正：断言限定在播放器容器内。

### 验收环境的前置条件（本轮踩到，务必先确认）

本轮全量门禁首跑 4 项失败（4c/4d/4e/4f），**经查与被测代码无关**，是三个叠加的环境事实：

1. **HEVC 素材 `items/267` 已被删除** —— 它原本是 4e 的触发源（Chromium 不含 HEVC 解码器，
   靠它必然落入「元数据可读、`videoWidth=0`、`onError` 不触发」这一态）。
   删除后 4e 无素材可测。
2. **默认排序下网格首张卡片由视频变为图片**（也因条目增删）→ 所有用
   `button.aspect-video` 的 **`.first()`** 的脚本都点进了**图片浏览模式**（页面无 `<video>`），
   于是 `未挂载 video 元素` 连环失败。
3. 库里仍有可触发的素材：**`items/36`，title=`format_h265_640x360`**（`D:\test_videos\02_format_matrix\`，
   测试素材非用户数据）。

**为什么能确定不是回归**：4g 通过（它先切「视频」分类再逐张试），
本 BUG 的 4h 也通过 —— 两者都证明「点视频卡片仍正常挂载 video」。

处置：

- `diag_rate_storm.cjs` / `shot_speed_menu.cjs` / `verify_decode_notice.cjs`
  **不再依赖首张卡片的类型**：前两者切「视频」分类；`verify_decode_notice.cjs`
  改为**按素材标题经搜索框定位**（`MEDIA_ID` 环境变量可覆盖，默认 36）。
- 新增 `scan_codecs.py`：扫描媒体库视频条目的**实际编码**（HEVC 是当前唯一能触发
  unsupported 的编码），避免下次再靠猜。

## 已知残留（不在本次范围，另立）

- **数据层：图片占用剧集集号**（`media_episode.episode_no` 按加入顺序分配，不分类型）。
  前端已用可读序号规避显示错位，但数据本身仍混编。是否要让图片不占集号，需后端决策。
- **`SeriesDetail.tsx` 未国际化**：全文硬编码中文（「← 返回」「移除」「还没有分集…」），
  与项目双语约定不一致；本次未引入 `useTranslation` 以免做成半吊子。
- **`ItemEditDialog.tsx` 仍有 emoji 图标**（`🎬/🎵/📄`），违反 P0-1。

## 防再发

1. **播放序列必须按媒体类型分流**：任何「可连续切换的组」（播放/浏览）都不得混入使用方式不同的类型。
   判定用 `modeOf(kind)` 单一真源，不要在各处散写 `kind === 'video'`。
2. **不允许「未知类型兜底成可播类型」**：`?? 'video'` 这类兜底会让异常不可见；
   落到 `'file'`（不支持预览）比伪装成可播放更安全。
3. **验收断言禁止松判**：`新值 !== 旧值` 这类写法会被元素消失产生的 `null` 骗过；
   必须要求「有值 + 具体数值」。
4. **验收脚本的选择器要排除当前态**：`aria-current` 项往往带有与目标项相同的视觉元素。
5. **覆盖层场景下断言要限定容器**：`body.innerText`/全页查询会把被覆盖内容算进来。
6. **验收脚本禁止依赖「列表顺序」与「素材长度」**：
   `.first()` 拿到什么，取决于数据增删（本轮 `items/267` 被删后，首张卡片变成图片，
   4 个门禁连环失败，全部与被测代码无关）。需要特定素材时应**按素材定位**
   （`MEDIA_ID` + 搜索框），并在注释里写清「为什么必须是这个素材」。
   同理，测「时长/推进」的断言要选用**足够长**的素材，短素材中途播完会产生假失败。
7. **素材变更后先重扫一遍编码**：`scan_codecs.py` 可确认库里是否还存在能触发目标分支的编码
   （如 HEVC 用于 `unsupported`），避免靠猜。
