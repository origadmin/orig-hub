# BUG-158：所有 git 钩子在本仓**恒不生效** —— 外层 `core.hooksPath=NUL` 把钩子目录指向不存在的路径，且 `install-hooks.sh` 与 BUG-157 同因装错仓

- 状态: open
- 发现日期: 2026-09-23
- 模块: build
- 严重程度: high
- 档位: standard

## 现象

`AGENTS.md` §7 的门禁表把本地钩子标为**必需**（缺陷登记一致性 pre-commit、提交信息 commit-msg、
目录污染 pre-commit），并声明「CI 是最后一道闸（本地可被 `--no-verify` 绕过）」。
**实测：本地钩子在本仓一个都不执行。**

直接问 git 它认哪个钩子目录：

```sh
cd D:/workspace/project/golang/origadmin/framework
git config --get core.hooksPath
# → NUL
git rev-parse --path-format=absolute --git-path hooks
# → D:/workspace/project/golang/origadmin/framework/NUL
```

`NUL` 是 Windows 的**空设备名**，作为目录路径**不存在**。git 一旦设置了
`core.hooksPath`，就**只从该路径**查找钩子，不再回落到 `.git/hooks/`。
结果：`framework/.git/hooks/` 里即便装上钩子也**永不执行**。

## 根因

### 主因：`core.hooksPath = NUL` 屏蔽了整个钩子机制

外层 `framework/.git/config`：

```
ignorecase = true
autocrlf = true
hooksPath = NUL
```

`NUL` 显然是被当作「禁用钩子」的手段写进去的，但它的**实际语义不是「不跑钩子」，
而是「去名为 NUL 的目录找钩子」** —— 该目录不存在，于是静默地什么都不跑。
这与 INC-001 §4.1 记录的「外层 `hooksPath = NUL` → 外层 hook 全部失效」是同一件事，
但此前**只记了「外层失效」，没有指出 orig-hub 依赖的钩子同样被它屏蔽**。

### 次因：`install-hooks.sh` 与 BUG-157 同因 —— 装进了错误的仓

`projects/orig-hub/scripts/install-hooks.sh`：

```sh
ROOT=$(git rev-parse --show-toplevel)     # ← 在 orig-hub 内跑，解析到外层 framework
HOOKS="$ROOT/.git/hooks"                  # ← 于是写进 framework/.git/hooks
```

实测（在 orig-hub 内）：`git rev-parse --show-toplevel` → `D:/.../framework`。
因此该脚本**永远装不到 orig-hub 自己的 `.git/hooks/`** —— 与 BUG-157
的 `--show-toplevel` 是**同一个根因**（monorepo 视角错位）。

即便把这一点修好，**主因仍在**：外层 `hooksPath=NUL` 存在一日，
装在外层 `.git/hooks/` 的钩子就不执行；而 orig-hub 自身的提交又从外层仓走
（见 INC-001：`orig-hub/.git` 被忽略），所以**无论装哪边都不生效**。

### 证据链

| 事实 | 命令 | 结果 |
|---|---|---|
| 钩子路径被指向空设备 | `git rev-parse --git-path hooks` | `NUL` |
| 绝对路径不存在 | `git rev-parse --path-format=absolute --git-path hooks` | `.../framework/NUL` |
| 外层 `.git/hooks/` 无实体钩子 | `ls .git/hooks/` | 只有 `*.sample` |
| 权威副本存在但未安装 | `ls projects/orig-hub/scripts/hooks/` | `commit-msg` `pre-commit` |
| 安装脚本会装错仓 | 在 orig-hub 内 `git rev-parse --show-toplevel` | `.../framework` |
| 门禁从未拦住违规提交 | 见 BUG-157 | 46 个根残留长期无人告警 |

**与 BUG-157 的因果关系**：BUG-157（门禁脚本逻辑失效）能长期不被发现，
**正是因为本档（钩子根本没跑）**。两者叠加 = 「以为有两道防线，实际一道都没有」。

## 复现

```sh
cd D:/workspace/project/golang/origadmin/framework
git config --get core.hooksPath                       # → NUL
git rev-parse --path-format=absolute --git-path hooks # → .../framework/NUL（不存在）
ls .git/hooks/                                        # → 仅 *.sample
# 结论：任何提交都不会触发 pre-commit / commit-msg
```

## 5 原则

### 原则（判据，必须先写下来）

1. **「钩子已安装」必须有可证伪的运行证据** —— 不能以「配置文件里写了」或
   「脚本跑完打印了 installed」当作生效证明。
2. **门禁的效力 = 实际拦截次数**，不是文档声称的强度。零拦截不等于零违规。
3. **`--no-verify` 之所以危险，前提是默认会 verify**；默认不 verify 时，
   整个「本地门禁」叙事都是空的。
4. **同一根因（monorepo 视角错位）在两处独立出现时，必须一并修**，
   否则修一处会给人「已加固」的错觉。
5. **「禁用钩子」的正确手段不是写一个不存在的路径**，而是明确记录
   「本仓不启用本地钩子，改由 CI 兜底」并让文档与实际一致。

### 对策

**因涉及用户明确禁止擅动的 `.git/config` 与引用体系，本档只做取证与建档，
不擅自修改配置。** 建议处置（需用户拍板，三选一）：

1. **恢复钩子**：`git config --unset core.hooksPath`（或设为 orig-hub 的真实钩子目录），
   再修 `install-hooks.sh` 的自定位（同 BUG-157 手法），最后**用一次故意违规的提交
   验证钩子真的拦下来** —— 这是唯一能证明「已生效」的方式。
2. **接受无钩子**：把 `AGENTS.md` §7 的「本地钩子=必需」改成「本仓不启用本地钩子」，
   并明确**唯一的闸是 CI**，同时把 `scripts/hooks/` 的权威副本标注为「仅供 CI 调用」。
3. **维持现状但补文档**：显式记录 `hooksPath=NUL` 的含义与影响面，
   避免下一个会话再误以为钩子在跑。

> 说明：**方案 2 与 3 都满足「文档与实际一致」，但都放弃了本地防线。**
> 方案 1 才能真正兑现 §7 的承诺。我不代替决策人在此选择。

### 分析（为什么这是根因，而不是表象）

- **不是「钩子脚本写错了」**：`scripts/hooks/pre-commit` 与 `commit-msg` 是完整可用的，
  且逻辑正确（会调 `check-bugs.py --quiet` 与 `check-pollution.sh`）。
  问题在于**它们从未被执行**——执行层被 `hooksPath=NUL` 掐断。
- **不是「忘了 install」**：即便执行 `install-hooks.sh`，也因 `--show-toplevel`
  而装错仓，且装的还是被禁用的那个目录 —— **执行了也没用**。
- **两个缺陷互相掩护**：BUG-157 让门禁「跑起来也不报警」，
  本档让门禁「根本跑不起来」。只看其中一个，都会得出「防线还在」的错误结论。
  这也解释了 `AGENTS.md` §7 那句历史教训为何反复出现：
  「pre-commit 恒 exit 127 锁死提交」→ 改「缺了就跳过」→「门禁长期空转」——
  **下一环就是本档：门禁连空转都没有，因为钩子根本没挂上。**

### 防再发

1. **钩子生效性自检（可证伪）**：新增 `scripts/verify-hooks-live.sh`：
   造一个必然违规的提交（如带中文的提交信息 + 根目录残留文件），
   **断言提交被拒**；若提交成功 → FAIL。这必须作为 CI 的常驻检查，
   否则「钩子失效」会再次静默。
2. **文档与实现对齐**：`AGENTS.md` §7 的「本地钩子」列要么改成实际生效的路径，
   要么显式标注「本仓未启用」。**禁止继续声称一个不存在的能力。**
3. **`install-hooks.sh` 自定位**：与 BUG-157 统一手法（由脚本位置推根，
   不依赖 `--show-toplevel`），并在安装后**回读校验**钩子文件确实落在
   `git rev-parse --git-path hooks` 指向的位置 —— 该路径可能不是 `.git/hooks/`。
4. **`hooksPath=NUL` 记入环境坑**：任何「钩子为什么没拦」的排查，
   第一步先跑 `git rev-parse --git-path hooks`。


在 orig-hub 内：

```sh

ls scripts/hooks/               # commit-msg  pre-commit（权威副本在，但未生效）
```

**关联已修缺陷的旁证**：BUG-157 的 46 个根目录残留
（见 `BUG-157.md`「已知边界」）在整个存续期内**未被任何钩子告警**，
与本档结论一致。

**修复后必须满足的可证伪判据（预先声明）**：
1. 造一个「根目录放 `.tmp-x.txt` + 提交信息含中文」的提交 → **必须被拒**（exit≠0）。
2. 同上但移除违规内容 → **必须通过**（证明不是恒拒）。
3. `git rev-parse --git-path hooks` 指向的目录中**必须实际存在** `pre-commit` 与
   `commit-msg` 两个**可执行**文件。
4. 上述三条**必须在同一环境、同一次运行内全部成立** —— 只验一条会被
   「恒拒」或「恒过」骗过。
