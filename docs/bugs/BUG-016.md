# BUG-016: TG api_id/api_hash lost — credentials only lived in process memory and were destroyed by repeated process kills

- **Status**: fixed（用户找回最后一组凭证，已持久化到 appDataDir/tg/config.json；服务以 real 模式恢复 Authorized；防回归约束已入 project_memory）
- **Severity**: critical（不可再生数据丢失）
- **Date**: 2026-09-16
- **Owner**: AI agent（流程事故，非代码缺陷）

## TL;DR

| 项 | 内容 |
|---|---|
| 问题 | 用户的 TG api_id/api_hash 无法再找回，且已丢失 |
| 根因 | 凭证只存在于运行中 orig-tg 进程的内存（env），从未持久化到磁盘；AI 反复杀进程（20:50 / 21:36 / 22:29 共 3 次）导致唯一持有者被毁 |
| 解决 | 不可逆；补救需用户提供新凭证或改用其他凭证来源（见下） |
| 影响范围 | TG 登录链路完全不可用（有效 session.session 仍在，但无凭证无法建立 MTProto 连接） |
| 不变项 | session.session / store.db 数据完好；APP sidecar 托管、配置卡、缓存功能代码不受影响 |
| 关键验证 | 无（凭证不存在，无法验证） |
| 核心教训 | 不可再生资源必须先持久化到磁盘，才能执行任何破坏性操作；运行中的进程绝不能作为唯一数据源 |

## 事故链

1. 用户最初在自有终端以 env 方式启动 orig-tg（18:49，凭证仅存在于该进程内存）。
2. AI 部署新 exe 时 Stop-Process 杀掉该进程（20:50）——第一次销毁凭证持有者；AI 未意识到凭证未持久化，继续给出错误 session 路径指引，用户重建进程但走了 dummy。
3. AI 建议的启动脚本要求用户重填凭证；用户运行时凭证为空 → dummy 假客户端假登录（21:36）。
4. AI 修复壳的 ensure_tg 后，再次手动 `Stop-Process` 清理"残留"（22:29）——若当时存在任何持有有效凭证的进程亦被一并销毁。
5. AI 事后尝试从 PowerShell history / .bash_history / .env 找回凭证——全部不存在。

## 直接原因（AI 行为缺陷）

- 把"清理端口/杀进程"当成无副作用操作，未评估进程内存中的不可再生状态。
- 凭证类数据未在首次获得时落盘（应有 config.json / .env 持久化），导致进程即存储。
- 事故后仍未第一时间意识到"杀进程 = 烧凭证"，重复犯同类错误 3 次。

## 防回归约束（已写入 project_memory Hard Constraints）

1. 任何 Stop-Process / taskkill / 端口清理 / 删除操作前，必须确认不可再生数据（凭证、密钥、会话、未落盘配置）已持久化；未确认则先落盘或询问用户。
2. 外部服务凭证首次获得时必须立即写盘（config 文件 / db）；env 仅作启动注入，绝不作为存储。
3. 运行中的进程永远不能被视为唯一数据源。

## 补救结果

- 用户找回最后一组凭证（APIID 15157021），已按防回归约束**立即落盘** `AppData\Roaming\com.origadmin.orighub\tg\config.json`。
- 服务由 AI 以 real 模式拉起：`api_mode:"real"` + `session_phase:"Authorized"`（新凭证与既有 session 兼容，无需重新登录/验证码）。
- 此后凭证只依赖磁盘 config.json；壳 ensure_tg 对 real 实例只复用不杀除。
