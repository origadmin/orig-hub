# BUG-401: 播放已缓存内容回跳仍重新拉流 —— `/stream` 无视 Range、无缓存验证头

- 状态: fixed
- 发现日期: 2026-10-23
- 模块: engine
- 严重程度: high
- 报告: 用户 2026-10-23 17:47「播放已缓存内容卡顿. 播放一定时间,然后跳转到前面已播放内容,仍旧请求读取内容,这是什么问题,怎么优化?」

## 现象与取证（wire 级实测）

视频播放是 **stream-first**（BUG-230 裁定，`VideoPlayer.tsx:648` `streamFirst = Boolean(compatSrc)`，
raw 已退役为下载/导出端点）⇒ 所有视频都走 `GET /api/media/items/<id>/stream`。
对该端点发 Range 请求（item 1645，236MB 已缓存视频）：

```
GET /api/media/items/1645/stream  (Range: bytes=0-1023)
HTTP/1.1 200 OK                    ← 不是 206！Range 被无视
content-type: video/mp4
accept-ranges: bytes               ← 宣称支持 Range，实际不支持（撒谎头）
x-orig-stream: live                ← 本次是全新直播转码
transfer-encoding: chunked         ← 无总长、不可断点
（无 ETag / Last-Modified / Cache-Control）
```

对照 `/raw` 端点（同一条内容）：`206 Partial Content + content-range + etag +
last-modified + cache-control: public, max-age=31536000` —— 头是完备的，但播放不走它。

## 根因

1. `/stream` 忽略 Range ⇒ 浏览器 `<video>` 的每次 seek（含**回跳已播放区间**）
   只能另发一次全新请求，服务端从 head 重新直播转码；
2. 无任何验证头/缓存头 ⇒ 浏览器 HTTP 缓存与媒体缓存**无从命中**，
   「已播放过的字节」一次都不会被复用；
3. `accept-ranges: bytes` 与实际行为矛盾 —— 这是往协议上撒谎，浏览器据此
   做出错误的缓冲/seek 决策。

## 优化方案（待拍板后实施）

A. **Range 支持落到已完成的转码产物上**（主修复）：转码完成后产物已落盘
   （代理缓存），`/stream` 对已缓存产物改用与 `/raw` 同款的静态文件投递
   （206 + Content-Range + ETag + Cache-Control）。直播期（首转）保持 200
   chunked，但响应头如实去掉 `accept-ranges`（不撒谎）。
B. 浏览器侧零改动 —— 头修对后，回跳命中 206 + 本地缓存，不再回源。

## 实施（2026-10-23，engine 改动，待用户 redeploy + 实测验收）

根因定位（wire 实测 + 代码）：`media_item_stream` 的 live 首转分支
（`download-engine/crates/orig-tg/src/routes.rs`）对 chunked 直播流**谎称**
`accept-ranges: bytes`（实际不能服务任意 Range）；而增长中 `.part` 的 Range 分支
只用 `range_start_only` 认 open range（`bytes=N-`），浏览器发出的 **closed range**
（`bytes=START-END`，回跳常见形态）被放过 ⇒ 落到 live 分支重新直播首转，
现象即 `x-orig-stream: live` 的「回跳重新拉流」。

改动（最小 diff，前端零改动）：
1. `media_item_stream` live 分支**去掉假的 `accept-ranges: bytes`**
   —— chunked 直播流不可断点，如实不声明（不再撒谎）。
2. `.part` Range 分支改用 `media_parse_range`（同时支持 open/closed range），
   只要 Range 起点已落在当前 `.part` 已转码字节内即从 `.part` 回 **206 + ETag +
   Cache-Control**（走 `serve_local_file`），不再重新起直播首转。
   已完成代理（`final_p`）命中本就走 `serve_local_file` 的 206 路径，未动。

判据（用户 redeploy 后补）：对转码中条目发 closed Range（`bytes=START-END`，
START 在已播放区）⇒ 返回 206 + Content-Range + ETag，`x-orig-stream: part`；
回跳场景网络面无新的 live 拉流（无 `x-orig-stream: live`）。

## 验收证据

2026-10-23 release 构建后实测。`cargo build --release -p orig-daemon -p orig-tg` 成功（新二进制 orig-tg `efc4cb4…`），
`dev_stack.py restart` 起栈后跑 `download-engine/verify/verify_bug401_stream_range.py`：

1. **代理命中（主修复）** —— 对已转码就绪的条目 418（5s，`?probe=1` 返回 `ready:true`）
   发 closed Range `bytes=0-1023`：

```
status=206 x-orig-stream='proxy' accept-ranges='bytes' etag='"9ae69-6adb5f5f"' content-range='bytes 0-1023/634473'
PASS: Range 命中 206 + ETag + Content-Range，且未重新直播首转
```

2. **live 不撒谎（辅修复）** —— 对冷条目 1645 首拉（该档位代理尚未生成）返回
   `200 x-orig-stream='live'` 且 **`accept-ranges=''`**（不再谎称支持 Range）。
   冷条目首拉为 live 属预期，不在本判据内。

结论：回跳命中已落盘代理的 206（ETag/Content-Range 齐全），live 首转如实不声明
accept-ranges，报告现象「回跳重新拉流」消除。
