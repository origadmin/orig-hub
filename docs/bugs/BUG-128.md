# BUG-128：类型徽标文案硬编码中文 —— 英文界面会显示「视频」「图片」

- 状态: fixed
- 严重程度: low
- 模块: shell
- 发现日期: 2026-09-22

## 现象

BUG-123 为卡片新增的**常驻类型徽标**，其文案是硬编码的中文字面量：

```tsx
// tauri-shell/src/components/media/MediaCard.tsx
const KIND_LABEL: Record<string, string> = {
  video: '视频',
  photo: '图片',
  audio: '音频',
  file: '文档',
}
```

`tauri-shell` 是**双语应用**（`i18n/locales/{zh-CN,en-US}.json`，`t()` 取当前 locale）。
于是切到 `en-US` 时，卡片上仍然显示中文「视频」/「图片」/「音频」/「文档」，
**与周围所有其他文案（英文）混在一起**。

## 根因

**本仓库第一处「渲染给用户的纯文本」绕过 i18n**。此前同文件里的 `KIND_ICON` 是
emoji（`'🎬'` / `'🖼️'` / `'🎵'` / `'📄'`）—— emoji 与语言无关，所以不构成缺陷；
换成文字标签后就构成了。

即：**引入新文案时没有走 i18n 通道**，而现有门禁**不检测硬编码文案**，所以它不会红。

## 影响范围

- 仅 BUG-123 新增的 `KIND_LABEL`（4 个值）。
- **不影响 zh-CN**（值恰好就是中文），所以中文环境下完全看不出问题 —— 属**单语可见**缺陷。

## 修复（`a42381b`）

1. `zh-CN.json` / `en-US.json` 新增 `media.kindVideo` / `kindPhoto` / `kindAudio` / `kindFile`
   （zh 视频/图片/音频/文档，en Video/Photo/Audio/Document）。
   **刻意不复用** `media.videos` / `photos` / `audios` —— 那三个是**复数分类名**（左栏分类按钮的
   文案），徽标是**单数类型名**；复用会让将来改分类名时意外改掉徽标。
2. `MediaCard.tsx` 的 `KIND_LABEL` 改为 `KIND_LABEL_KEY`（存 **i18n 键**而非文案），
   渲染时用 `useTranslation()` 求值。
3. **踩过并绕开的坑**：`t` 是普通模块函数，只读 `useStore.getState()`，
   **不订阅** `settings.language`；而 `MediaCardBase` 外面包着 `memo`。
   若直接 import 裸 `t()`，用户切语言时卡片**不会重渲染**，徽标会停在上一个语言。
   故用 `useTranslation()`（它订阅 `settings.language`）。

## 验收证据

**入库验收脚本**：`tauri-shell/verify/verify_card_kind_signal.cjs`（同一个脚本，BUG-123 起就入库）。

```sh
cd tauri-shell
node verify/verify_card_kind_signal.cjs                            # 期望 44/44、exit 0
ORIG_VERIFY_REVERT_I18N=1 node verify/verify_card_kind_signal.cjs  # 本条专属证伪，期望 exit 1
```

### 正向：44/44 断言通过，exit 0

新增的关键断言（en-US 轮）：

| 断言 | 实测 |
|---|---|
| ★ en-US 图片卡片徽标文本为「Photo」 | `不符=0` |
| ★ en-US 图片卡片徽标**不含 CJK 字符** | `含 CJK=0` |
| 切回 zh-CN 后徽标文本仍为「图片」/「视频」 | 通过（BUG-123 的原有断言未被打红） |

**locale 切换是真的走设置 UI**（不是直接改 localStorage），并且**同时核对了两条独立信号**
证明切换确实生效，避免断言建立在假前提上：

- `html[lang]` 属性变化；
- 另一个**已知会变**的文案也跟着变：左栏分类按钮 `media.photos` 由 zh-CN「图片」变为 `Photos`。

> 只断言徽标变英文、却不证明 locale 真的切过去了，就是**假绿** —— 断言可能只是在一个
> 从未切换的页面上自说自话。这一条是本次验收的关键设计。

### 反向证伪（验收的验收）—— 本条专属的那一条最重要

`ORIG_VERIFY_REVERT_I18N=1`：在 en-US 那一轮把徽标文案**改回硬编码中文**（徽标仍在，只是文案错了）。

| 通道 | 期望 | 实测（独立复跑） |
|---|---|---|
| **`ORIG_VERIFY_REVERT_I18N=1`（本条专属）** | exit 1，且**只有 en-US 两条变红** | **exit 1**，`42/44`，恰为 `en-US 徽标文本为「Photo」` 与 `en-US 徽标不含 CJK` 两条 FAIL |
| `ORIG_VERIFY_REVERT=1`（BUG-123 通道） | exit 1 | exit 1，5 条判据变红（`20/25`） |
| 死端口 `APP_URL=…:59999` | exit 2 | exit 2，`RESULT: UNREACHABLE` |
| 活体篡改（注回统一播放三角） | 必须被检出 | `tamper: before=0 after=1 restored=0` |

专属通道那条的实测输出：

```
FAIL ★ en-US 图片卡片徽标文本为「Photo」                    -> 不符=30 样本=["图片","图片","图片"]
FAIL ★ en-US 图片卡片徽标不含 CJK 字符（硬编码中文在这里现形） -> 含 CJK=30 样本=["图片","图片","图片"]
[verify:card-kind] 42/44 assertions passed
[verify:card-kind] RESULT: FAIL (2 failed)
```

**为什么不能用 BUG-123 的 `ORIG_VERIFY_REVERT` 代替**：那条把徽标**整个删掉**，
它证明的是「徽标缺失会被抓到」；而本缺陷是**徽标在、文案错**。用删徽标的方式证伪，
只能证到「缺失」这一类，**证不到「硬编码」这一类** —— 这正是「失败分类要对齐失败模式」
（BUG-086 教训）。专属通道把失败**精确归因**到 en-US 场景（zh-CN 断言保持全绿），
才说明断言是按本缺陷的失败模式设计的。

### 未覆盖（如实标注）

  本轮无法在真实页面验证**，只有键存在性与源码级映射核对（与 BUG-123 同一局限）。
