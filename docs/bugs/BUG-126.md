# BUG-126：从剧集移除的分集会被「重新编回」—— 缺 tombstone 负向记录

- 状态: fixed
- 严重程度: high
- 模块: engine
- 发现日期: 2026-09-22

## 现象

用户从剧集里移除一集（或一张图片）后，**它会在下一次同步 / 重新加入时回来**。
表现为「删了又回来」，用户会认为软件坏了。

## 实测证据（本机 orig-tg，2026-09-22）

| 步骤 | 结果 |
|---|---|
| `append` item143(photo) → epId393 | 图册出现 |
| `DELETE /api/media/episodes/393` | 图册清空（移除确实生效） |
| **再次 `append` [143]** | `{"added":1}` → **epId394，图片复活** |

## 根因

**没有任何「已摘除」的负向记录**，于是所有写入路径都不知道「这条曾被用户移除过」：

1. `append_episodes_ranged`（`media.rs:1714`）**只按当前 `media_episode` 行去重** ——
   行被删掉了，去重依据就没了，于是重新编入。
2. `remove_episode`（`media.rs:1900`）只做「删行 + 重排集号 + prune 空剧集」，
   **不写任何负向记录**。
3. 全库**无外键级联**，也没有别的机制记住这次移除。

另一条独立的复活路径：移除某剧集的**唯一**分集 → `prune_empty_series` 把剧集删掉 →
下次同步按 `source_key` 查不到该剧集 → **新建剧集并重新编入全部内容**。
这条与「同槽重新 append」是两个不同触发点，**修的时候都要覆盖**。

## 影响

- **BUG-112（图片无法从剧集移除）的「移除」是半坏的**：入口已实施，但语义不成立 ——
  用户以为删掉了，同步后回来。所以 BUG-112 不能标 `fixed`，只能 `in_progress`。
- 与 BUG-029 的教训同构：**单向删除会在下次 upsert 时复活**。那条讲的是「删条目 vs 清缓存」，
  本条讲的是「删分集 vs 重新编入」——**同一个错误模式换了个位置**。

## 修复方向：tombstone（负向记录）

需要一个「这条内容曾从该剧集/该槽位被移除」的记录，让所有写入路径都尊重它：

- 形态候选：`media_episode_tombstone(series_id, item_id, season, episode_no, removed_at)`
  或复用既有表加 `removed_at` 软删列。**选哪种请架构师定**，不要直接开工。
- **必须覆盖的写入路径**（否则又变成逐点打补丁，BUG-110 的教训）：
  1. `append_episodes_ranged` / `appendEpisodes`（手动「加入剧集」）
  2. TG **自动成剧**（同步时按 `source_key` 重建）
  3. **合并剧集**（BUG-103 相关）
  4. 任何将来新增的编排路径 —— 故优先考虑**在数据层表达**（触发器/约束），
     而不是在每个调用点判断。
- **必须定义的语义**（否则 tombstone 会变成「再也加不回来」的幽灵）：
  用户**主动重新加入**时，tombstone 必须失效或被清除 ——
  「用户手动加回」与「系统自动编回」是两件事，不能一刀切。
- 与 **BUG-124**（孤儿备用源行的触发器修法）同期做：两者都是「数据层不变量」，
  一次把数据层的删除/重编语义理顺，比修两轮划算。

## 验收要求

1. 移除一集 → 触发 TG 同步 → **该集不得回来**；
2. 移除唯一分集致剧集被删 → 同步 → **剧集不得重建并重新编入**；
3. **反向证伪**：用户**主动**把该内容重新加入该剧集 → **必须能加进去**
   （tombstone 不得变成永久拒绝）—— 这条是防「修出一个新 bug」的关键。
4. 内容本身仍在资料库（移除只摘归属，不删内容）。

## 关联

- BUG-112（图片无法从剧集移除）—— 本条是它的未完成部分，两条一起才闭环。
- BUG-029（单向删除会复活的先例）、BUG-103（合并入口）、BUG-124（三个删除入口的孤儿源行）。
