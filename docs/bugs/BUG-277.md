# BUG-277: 入库流水线队列**无优先级能力** —— 无法置顶 / 切换 / 提前下载，顺序只能是严格 FIFO（`ORDER BY id ASC`）

- 状态: fixed
- 发现日期: 2026-10-10
- 模块: engine+shell
- 严重程度: high

> 来源：用户 2026-10-10 报障原话：「BUG: 入库流水线 还有问题,无法选优先级,有点需要提前下载,但是队列是死的无法切换,置顶.」
>
> **本档为任务文档**（用户 2026-10-10 定：后续一律纯文档任务，代码由别的组负责）。
>
> **与 BUG-274 / BUG-276 的关系**：那两条解释「队首为什么会被一条慢流卡 21 小时」——
> 那是**队列不健康**；本条是「即使队列健康，用户也**无法改变**谁先谁后」——这是**队列不可控**。
> 两者叠加 = 队列**既慢又不可控**：用户想「提前下载」某条时，**没有任何手段**。
> 三条应一起看：BUG-274/276 是「为什么会慢」，本条是「慢的时候用户为什么只能干等」。

## 现象

用户在入库流水线（缓存队列）里有**三类诉求，一个都表达不了**：

1. **选优先级**：想给某条打「高优先级」，没有入口。
2. **提前下载**：想让自己马上要看的那条**先下**，没有入口。
3. **切换 / 置顶**：想把自己排在第 20 位的任务**拉到队首**，没有入口 ——「队列是死的」。

实测（2026-10-10，`GET /api/tg/cache/tasks/all` + `GET /api/tg/cache/tasks`）：

| 字段 | 值 |
|---|---|
| `counts` | `queued: 24`、`running: 1`、`done: 63`、`failed: 6`、`interrupted: 4`、`cancelled: 12` |
| running 任务 | `id=134`（chat `-1004457697592`，`total=9`） |
| `currentId` | **1183**（`1181` / `1182` 被墙钟判失败后推进，见「复现」） |
| `done` | **0** |
| `createdAt` | 1791562886（距实测时刻 **21.9 小时**） |
| 其后排队 | **20 条**（`GET /api/tg/cache/tasks` 的 `queued` 摘要） |

**危害**：队首被一条慢流占 **21.9 小时**（成因见 BUG-276），而用户**只能干等** ——
想先看的条目排在第 20 位，**既不能置顶、也不能切换**。这正是用户说的「队列是死的」。

## 根因

**队列顺序是硬编码的 `ORDER BY id ASC`；`cache_task` 表没有任何优先级 / 排序列；
后端没有任何重排端点；前端没有任何排序控件。** 四处证据：

### 事实 1（schema）：`cache_task` 无优先级列

`store.rs:339-353` 的建表语句列全为
`id / chat_id / group_id / item_key / items / total / done / status / current_id / dir / error / created_at / updated_at`
—— **没有** `priority` / `position` / `sort_no` / `rank` 之类任何列。

### 事实 2（取队列首）：严格 `ORDER BY id ASC`

worker 收尾时接续下一条走 `next_queued_task()`（`store.rs:1150-1161`）：

```sql
SELECT {CACHE_TASK_COLS} FROM cache_task
 WHERE status = 'queued' ORDER BY id ASC LIMIT 1
```

`id` 是 `AUTOINCREMENT`（`store.rs:340`）⇒ 顺序 = **入队先后**，即严格 FIFO。
重启恢复 `recover_queued_cache_tasks()`（`store.rs:1240-1254`）同为 `ORDER BY id ASC`。
展示序 `list_cache_tasks()`（`store.rs:936-953`）是
`ORDER BY CASE WHEN status IN (active) THEN 0 ELSE 1 END, id DESC LIMIT ?1`
—— 只是把活跃态提前，**仍无用户可控维度**。

### 事实 3（无端点）：路由表无重排 / 置顶

`routes.rs:55-66` 的缓存任务路由全集为
`GET/POST /api/tg/cache/tasks`、`GET /api/tg/cache/tasks/all`、`GET/DELETE /api/tg/cache/tasks/:id`、
`POST /api/tg/download/:chat_id/:message_id`
—— **无** `priority` / `reorder` / `move_to_top` / `promote` 端点。
全 crate `grep -rn "priority|reorder|move_to_top|promote|sort_order|position" --include=*.rs`
**0 命中**（仅 `Iterator::position` 的无关调用：`orig-core/src/engine.rs:568` 等）。

### 事实 4（前端无入口）：`api/tg.ts` 无排序 API，面板无排序控件

`api/tg.ts:387-455` 的队列 API 全集为
`getCacheTask` / `enqueueCacheTask` / `cancelCacheTask` / `retryCacheTask` / `deleteCacheTask` / `deleteCacheTasksByIds`
—— **无**排序 / 置顶；`CacheManagerDialog.tsx` 队列列表按后端返回顺序渲染，**无排序控件**。

### 与「全局单飞」裁定的关系（**关键：本条不推翻任何用户裁定**）

`routes.rs:1431-1436` 的注释写：

> 「设计裁定（用户）：不论多少缓存在排队，`task` 端点只呈现**一个**当前任务；
> 与之配套，执行侧也必须是单飞——否则多 worker 并发写进度会把「1s 一次」的节拍打碎成「1s 多次状态变化」。」

**用户裁定只覆盖两件事**：① 单飞（同时至多一个 worker）；② 单进度呈现。
「**FIFO**」出现在同段注释里，但那是**对 `next_queued_task()` 实现的描述**，
**不是**用户裁定 —— 全库没有任何文档把「必须 FIFO」定为用户需求。
⇒ **加优先级 = 改变「单飞循环下一次取谁」，不破坏单飞、不破坏单进度**，与既有裁定相容。

## 复现

1. 入队 ≥ 3 个缓存任务（`POST /api/tg/cache/tasks`），使队列 ≥ 3 深。
2. 尝试对**非队首**的某条「置顶 / 提高优先级 / 提前下载」。
3. **观察：无任何 UI 控件、无任何 API 可调用** —— 顺序只能是 `id ASC`。
4. 后端佐证：`next_queued_task()` 的 SQL 写死 `ORDER BY id ASC`（`store.rs:1154`）。

**佐证「队列确实会被卡住、用户却动不了」（自然实验，2026-10-10 实测）**：
`GET /api/tg/logs`（内存环形日志）取到同一条任务连续两次**墙钟判失败**：

```
[1791637627] cache task 134: re-queued after restart
[1791637627] cache task 134: start 9 item(s) chat=-1004457697592
[1791639427] cache task 134: item 1181 failed: download too slow: 1800.0s for chat -1004457697592 msg 1181; wall-clock limit 1800s exceeded, aborted to keep the cache queue moving (continuing with remaining items)
[1791641227] cache task 134: item 1182 failed: download too slow: 1800.0s for chat -1004457697592 msg 1182; wall-clock limit 1800s exceeded, aborted to keep the cache queue moving (continuing with remaining items)
```

- 1791637627（重启重新入队）→ 1791639427 恰好 **1800s**（`= 1791637627 + 1800`）；
- 1791639427 → 1791641227 又是 **1800s**。

即：重启后**每条慢条目要烧满 30 分钟才被判失败**，`total=9` 的任务光烧超时就要 **9 × 30min ≈ 4.5h**。
`currentId` 从 1181 推进到 **1183** 正是这两次失败的产物（**同时验证 BUG-276 的机制**）。
**在这 21.9 小时里，排在第 20 位的条目对用户而言完全不可达** —— 没有置顶、没有切换。

## 修复（方向；**本档不改代码**）

**产品语义（已决，2026-10-10）**：「置顶」在本项目语境 = **「当前任务跑完后，下一个跑它」**，
**不是**「立即抢占当前任务」。理由：单飞 + 当前条目可能已下了 30 分钟
（见上自然实验），抢占会**丢弃已完成字节**，与 BUG-257「不弃单」相悖。
若后续要「立即」，那是**抢占语义**，须另立决策项（本条**未**采用）。

### 裁定（2026-10-10，用户拍板：**A**）

采用 **A —— 加优先级列 + 原子端点 + 面板置顶**。**裁定解读**：

- **为什么 A 够**：它把「谁先谁后」变成**用户可控的一个标量** `priority`，且
  `DEFAULT 0` ⇒ **存量顺序不变**（迁移幂等）、同优先级仍 `id ASC` ⇒ **旧行为完整保留**。
  这正对应你的原话「需要**提前下载**」——把**某一条提前**，不需要重排整个队列。
- **为什么不是 B**：拖拽重排表达力更强，但**回归面大**（每次重排要批量改写 `position`），
  且当前诉求是「把某一条提前」而非「精细编排全序」⇒ A 已覆盖，B 留作**后续增强**。
- **为什么不是 C**：C 是 A 的**入口变体**（复用同一 `priority`），**不是互斥方案** ——
  可在 A 落地后按需追加，**不阻塞**本条。
- **为什么不是 D**：你明确要这个能力，D 等于拒绝需求。

**实施边界（交实施组；本组只登记、不改码）**：

① `cache_task` 加列 `priority INTEGER NOT NULL DEFAULT 0`（幂等迁移，不删数据）；
② `next_queued_task()`（`store.rs:1150-1161`）改 `ORDER BY priority DESC, id ASC`；
③ 新增**原子端点** `POST /api/tg/cache/tasks/:id/priority`（body `{priority}`）；
   **不得**让前端循环调单条（BUG-249 先例：批量必须走原子端点）；
④ 前端 `CacheManagerDialog` 加「置顶 / 取消置顶」按钮（置顶 = 设 `priority = max+1`）；
⑤ **不抢占**：`running` 任务不被打断（`spawn_cache_task` 只在**终态后**取 `next_queued_task`）。

### 选项（原样留痕，供追溯）

- **A（推荐）加优先级列 + 端点 + 入口（最小可用）** ← **已决（2026-10-10）**：
  ① `cache_task` 加列 `priority INTEGER NOT NULL DEFAULT 0`（幂等迁移，不删数据）；
  ② `next_queued_task()` 改 `ORDER BY priority DESC, id ASC`（同优先级仍是 FIFO ⇒ 向后兼容）；
  ③ 新增**原子端点** `POST /api/tg/cache/tasks/:id/priority`（body `{priority}`）；
     **不得**让前端循环调单条（BUG-249 先例：批量必须走原子端点）；
  ④ 前端 `CacheManagerDialog` 加「置顶 / 取消置顶」按钮（置顶 = 设 `priority = max+1`）。
- **B 显式手动排序（拖拽重排）** ← **未采用（2026-10-10）**：加 `position` 列 + 重排端点 + 拖拽交互。
  表达力强于 A，但**回归面大**（每次重排要批量改写 `position`），且长列表拖拽体验差。
  建议**先 A 后 B**（A 已覆盖用户「置顶」的核心诉求）。
- **C「优先下载这一条」直达入口** ← **未采用（2026-10-10；可作 A 的后续入口）**：在 TG 面板消息气泡 / 相册上加「优先下载」，
  直接 `enqueue` 并置顶（复用 A 的 `priority`）。对「我就要看这条」最直接。
- **D 不做** ← **未采用（2026-10-10）**：登记为**已知能力缺口**，仅在文档写明「队列为严格 FIFO，不可调整」。

**不可推翻的既有裁定**（本条不触碰）：全局单飞（`routes.rs:1431-1436`）、
单进度呈现、BUG-257 不弃单、BUG-271 / BUG-276 的条目级死线、
BUG-180 停滞看门狗、BUG-181 排队可见性契约。

## 关联

- **BUG-276**（open, high）：队首被慢流占 **21.9 小时**的**成因**。本条是「用户对此**无能为力**」
  的另一半 —— 修了 BUG-276 队列会健康，但用户仍需要「优先级」来编排**自己的**观看顺序。
- **BUG-274**（open, high）：缓存下载饿死远程播放 ⇒ 用户更想「先下我要看的」⇒ 本条诉求的**动机**。
- **BUG-181**（fixed）：排队任务的可见性契约（`queued` 覆盖摘要，仍是单进度）。
  本条的「置顶」**须在该契约内**表达（不新增第二个进度）。
- **BUG-180**（fixed）：停滞看门狗治「死」；**B 档**重排不影响其语义。
- **BUG-249**（批量取消 / 重试原子端点先例）：本条若要批量置顶，**必须走原子端点**，禁前端循环。
- **BUG-188**（fixed）：纯图组误排进字节队列 ⇒ 说明「谁该排队」本身也有过错位；
  本条治的是「排了之后**顺序**不可控」，两者不重叠。
- **BUG-220**（open）：入库流水线只显示频道不显示内容 —— 与本条同属「流水线可用性」簇，
  但那条是**信息**缺失、本条是**控制**缺失。

## 验收证据

**状态 `fixed`（2026-10-11）。**

**验收方式**：隔离 mock 栈（`--features mock` 构建 + 独立端口 19877 + 唯一库 + `ORIG_TG_MOCK=1`）
+ 真实浏览器（Edge/CDP）端到端验收；脚本 `tauri-shell/verify/verify_bug_277_queue_priority.cjs`，
真实渲染截图证据 `tauri-shell/verify/evidence/BUG-277/`。

**结果**：21/21 判据 PASS（0 FAIL / 0 SKIP），判据 1–7 全覆盖：

- **A1–A4 端点契约**：置顶 200 且 `priority ≥ 1`；置顶后呈现序与执行序同向；批量置顶一次请求改多条、
  批内保持 FIFO；非法 body 一律 422、未知 id 404、越界 id 不动手不报错 —— 全绿。
- **B1 / B1b**：「置顶」入口只出现在**排队中**的行，正在跑的行不给（不抢占语义在界面上可见）。
- **B2 / B2b**：置顶后该行出现「已置顶」徽标、`data-priority > 0`、并**渲染到队列前部**（DOM 顺序可核，
  不读 className）—— 真实渲染截图 `02-after-pin.png`。
- **B3**：取消置顶 ⇒ 徽标消失、`priority` 归零、渲染顺序回退。
- **B4 / B4a / B4b / B4c**：批量置顶**只发 1 个 POST**（`fetch` 计数）、批内保持 FIFO；
  批量取消同样只发 1 个 POST。
- **C1 / C1b（不抢占 + 单飞）**：置顶生效时当前 running 任务 id/状态**一字不变**；`running` 计数恒 ≤ 1。
- **C2（判据 1，真实栈形态）**：当前任务跑完后，**下一个跑的必是被置顶的那条**（`next=4`，与期望一致）。
- **C3（判据 2）**：被置顶的跑完后回到 FIFO（同优先级仍先入先出，`next=3`）。
- **D**：夹具清理后残留为 0（与开始前基线比对）。

**反向证伪（验牙）**：引擎单测 `pin_makes_the_task_next_and_never_preempts_the_running_one_bug277`
在把 `next_queued_task()` 改回 `ORDER BY id ASC`（旧实现）时 **FAIL**
（`left: Some(2) right: Some(3)`：FIFO 返回最低 id，而非被置顶者）；恢复
`ORDER BY {CACHE_TASK_QUEUE_ORDER}` 后 PASS —— 证明该断言非平凡绿、能捕获回归。

**单元层**：`cache.rs` 另含 6 个 BUG-277 单测（迁移幂等 / 无置顶仍 FIFO / 端点互斥 422 /
批量原子 + 边界 / 不抢占 + 单飞不回退），随 `cargo test -p orig-tg` 全绿；其中
`priority_migration_is_idempotent_and_keeps_fifo_order_bug277` 用**文件库**二次/三次启动验证加列迁移幂等。
