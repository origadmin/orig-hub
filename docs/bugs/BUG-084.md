# BUG-084: 提交信息混入 CR（`\r`）→ 同内容提交哈希不同、全后代历史整体偏移

- 状态: fixed
- 发现日期: 2026-09-20
- 模块: build
- 严重程度: high

## 现象

一批提交的**提交信息（commit message）里混入了回车符 CR**。按字节统计 `git log --all --format=%B`：
本分支 78 条提交里 **76 条** message 含 CR（如 `7bcef52`、`ff63f7f`、`c648f79`）。

最刺眼的一对是根提交：

- `206ee70`：提交对象 **177 字节**，含 1 个 CR，message 结尾是 `...(main = Rust)\r\n`
- `645d2c7`：提交对象 **176 字节**，0 个 CR，message 结尾是 `...(main = Rust)\n`

两者 **tree 同为 09b3465、作者与提交时间完全相同**，内容上是一回事，仅因结尾 CRLF/LF
这一字节之差而得到两个不同的哈希 —— 于是长出两棵平行历史，**所有后代提交哈希全部不同**。
后果不是「显示不好看」：跨分支 cherry-pick / rebase / 比对全部对不上，历史无法收敛。

## 根因

三处叠加，缺一都不会酿成今天这个局面：

1. **作者侧**：Windows 上编辑或粘贴提交信息，CRLF 行尾直接进了 `%B`。git 不改写 message，
   原样落进提交对象字节。
2. **门禁侧（无规则）**：`scripts/check-commit-msgs.py` 只校验「全英文」与「`fix` 必须引用
   BUG 编号」，`scripts/hooks/commit-msg` 同样只有这两条 —— 「带 CR 的提交信息」是**可表达的**，
   没有任何一环拒绝它。
3. **门禁侧（隐藏的假阴性问题）**：脚本用 `subprocess(..., text=True)` 取 git 输出，Python 的
   通用换行转换会把 `\r` 悄悄翻译成 `\n`。**即使当时就加一条 CR 规则，检出率也是 0** ——
   所以修复必须先把 `%B` 改成按字节取，否则是装了一个永远不响的报警器。

## 复现

只读取证，不需要提交：

```sh
git cat-file commit 206ee70 | od -c | tail -3   # 结尾 \r  \n
git cat-file commit 645d2c7 | od -c | tail -3   # 结尾 \n
git cat-file commit 206ee70 | head -1           # tree 09b3465…（与 645d2c7 同）
python scripts/check-commit-msgs.py --self-test  # 修复前：无 CR 规则；修复后：自检通过
```

## 修复

堵源头，让「带 CR 的提交信息」**不可表达**（三处同源，缺一处即可绕过）：

1. `scripts/check-commit-msgs.py`：
   - `git()` 改为取**字节**后自行 decode（`text=True` 会吃掉 `\r`，见根因 3）；
   - 新增 `cr_violation()`：扫 `%B` 全文，出现 `\r` 即失败，报错自带 why（字节哈希 →
     同内容不同哈希 → 后代全变）+ fix（`core.autocrlf input`、别往 `-m`/`-F` 粘 CRLF）；
   - **生效点基线** `CR_RULE_BASELINE` = `3e85681`：该提交及其祖先属历史欠账，只计数告警；
     其后代一律阻断。理由与 `check-bugs.py` 的 RULE_FROM 同源 —— 76 条存量一上来把 CI 判恒红，
     门禁就沦为噪音；历史如实标注，新增零容忍。基线对象若被 prune 则**降级为只告警并明说**。
   - 新增 `--self-test`：合成 LF/CRLF 两条 + 真实含 CR 提交 `206ee70`，不依赖工作树即可验。
2. `scripts/hooks/commit-msg`（权威副本，随 `scripts/install-hooks.sh` 安装）：
   加 CR 规则。**本机 MSYS grep 3.0 下 `grep -P '\r'` 匹配不到 CR**，故用
   `grep -qU "$(printf '\r')"`（字面 CR + 关闭换行转换），POSIX 写法不依赖 bash 的 `$'\r'`。
   单条提交信息永远是「新增」，钩子侧无历史豁免。
3. `AGENTS.md` §2 提交约定加「提交信息必须 LF，禁止 CR」；§7 门禁表格把 CRLF 检测补进
   `check-commit-msgs.py` 的覆盖范围。

## 存量清理（已执行，2026-09-21）

**原「待拍板：是否重写历史」已批准并执行。** 实际口径与当初估计的差异，如实记录：

- **数量不是 76 条，而是 31 条**。上一轮事故修复已用 `commit-tree` 重放本地 78 条提交
  （重放时 `tr -d '\r'`），那批确已清零；剩余 31 条**全部来自 `origin/main` 的原生历史**，
  在 merge 时进入主干。这正是上一轮报出「CR 已清零」的误报来源 —— 当时只统计了重放侧，
  未覆盖 merge 进来的远端提交。
- **工具不是 `filter-repo` / `filter-branch`，而是 `commit-tree` 全量重放**。原因：
  `filter-branch` 在本仓库实测重写后哈希**不变**（MSYS 下 `--msg-filter` 未真正改写）；
  `git rebase` 也不可用（`could not mark as interactive`）。`commit-tree` 逐条重放是
  唯一可靠路径，且能正确处理 merge 提交的双父。
- **先在临时 clone 上试跑**：验证提交数 116=116、树 diff 为空、CR=0 后，才对真实仓库
  执行。两次独立执行得到**同一个**新 HEAD `59d3b14`，证明结果确定可复现。
- **推送用 `--force-with-lease` 而非裸 `--force`**：lease 基准为远端当时的 `724e75e`，
  若期间有他人推送会自动拒绝。
- **备份齐全**：tag `safe-before-cr-clean-724e75e`、分支 `backup-before-cr-clean`、
  bundle `orighub-backup-before-cr-clean.bundle`（7.2 MB，含全部对象）。

**结果**：116 条提交**含 CR 0 条**；树内容与重写前**完全一致**
（`git diff 724e75e 59d3b14` 为空 → 只改 message 字节，未动任何文件内容）；
门禁 `check-bugs OK - 84 条` 通过；工作区 0 改动。

## 检测方法学教训（本条最初误报的直接原因）

CR 检测在本环境极易产生假阴性 / 假阳，踩过的全部坑：

- `grep -P '\r'` 在 MSYS 下**不匹配** CR；
- `grep -qU "$(printf '\r')"` 可用，但加上 `-a` 后（`-acU`）行为异常，实测给出 98 这种荒谬值；
- Python `subprocess` 用 `text=True` / `encoding=` 会把 `\r` 译码成 `\n` → **100% 假阴性**；
- shell `while read` 管道同样会吞掉 CR。

**唯一可信做法**：按字节取 `git cat-file commit <h>` 的 **bytes**，再判 `b'\r' in data`。
本条最初误报「清零」正是栽在用了会吞 CR 的通道上。
