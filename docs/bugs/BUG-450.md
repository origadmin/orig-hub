# BUG-450: 进度条走了「分段轴」，时间文本走了「内容轴」——10:30 的视频刚播 1:14 条面就满了

- 状态: fixed
- 发现日期: 2026-10-27
- 模块: shell
- 严重程度: high

## 现象

用户 2026-10-27 截图（`Clipboard_Screenshot.png`）：时间文本 `1:14 / 10:30`，
但进度条已填满约 **97%**，只剩尾部一小截。

> 「进度条显示错误问题. 10分钟的视频已经跑完了, 但实际刚开始.」

同一帧里两个控件对「进度」给出完全不同的答案 —— 这不是数值偏差，是**两个分母**。

## 根因：两个叶子组件用了两条不同的时间轴

播放器的时间轴有三条，容易混：

| 轴 | 含义 | 谁该用 |
| --- | --- | --- |
| **媒体轴** `v.currentTime` / `v.duration` | 当前这条流的本地时间。**live 转码流上 `duration` 只是「已经转码到哪」**，会一直长 | 没人该直接拿它当分母 |
| **内容轴** `currentTime*speed + contentOffset`，分母 `contentDuration` | 源内容的真实时间（10:30） | 时间文本、进度条、seek |
| **分段轴** `segOffset` / `segDuration` | 「跳过片头/片尾」之后**可播放那一段**的起止（BUG-417 引入） | 只用于片头/片尾的强制跳转与徽标 |

实测两条叶子各走一条：

```
时间文本 PlayerTimeText   (VideoPlayer.tsx:1638-1643)
  contentOffset = contentOffsetRef.current      ← 内容轴 ✅
  contentDuration = contentDurationRef.current  ← 内容轴 ✅   ⇒ 显示 10:30

进度条 PlayerProgressBar  (VideoPlayer.tsx:1539-1547)
  contentOffset = segOffset                      ← 分段轴
  contentDuration = segDuration                  ← 分段轴
```

而分段轴的**默认值**是：

```ts
// VideoPlayer.tsx:720-721
const segOffset = skipStartSec > 0 ? skipStartSec : 0        // 没设跳过片头 ⇒ 0
const segDuration = skipEndSec != null && skipEndSec > segOffset
  ? skipEndSec - segOffset : null                            // 没设跳过片尾 ⇒ null
```

用户没配跳过片头/片尾 ⇒ `contentOffset = 0`、`contentDuration = null`。于是
`displayDur()` 落到最后兜底：

```ts
// VideoPlayer.tsx:368-373
const displayDur = () => {
  if (contentDuration != null && contentDuration > 0) return contentDuration
  if (!v) return 0
  return (Number.isFinite(v.duration) ? v.duration : 0) * timeScale + contentOffset   // ← 媒体轴
}
```

⇒ 分母变成 **live 转码流当前的 `v.duration`**（≈ 已经转码出来的 74 秒）。
`74 / 74 ≈ 100%` —— 条面「跑完了」，而内容其实才到 11.7%。

### 为什么 `contentDuration` 不能在挂载时补上

即使把可见条改成传 `contentDurationRef.current`，**仍然会错**，因为条面刻意不重渲染：

- BUG-216 的设计：`timeupdate` / `progress` 由 `write()` **直接写 DOM**，父组件与叶子都
  不因播放推进而重渲染（DOM 变更从 24.5 次/秒降到个位数）。
- 真源时长是**挂载之后**才学到的（换档探针 `:816`、`durationchange` 兜底 `:1080/1090`），
  写的是 `contentDurationRef.current` —— **改 ref 不触发重渲染**。
- 于是 `contentDuration={contentDurationRef.current}` 这个 prop 会**永久停在挂载那一刻的值**（`null`）。

时间文本之所以对，是因为它自己每秒 `setState`（`currentTime`/`duration`）⇒ 每秒重渲染 ⇒
每次都能读到 ref 的最新值。**同一个 ref，一个组件读得到、一个读不到** —— 差别只在会不会重渲染。

> 与 BUG-376（自定义 `memo` 比较器漏字段）/ BUG-364（`highlighted` 同型）是**同一族缺陷**：
> 状态改了、界面不动。这次换成了「ref 改了、prop 不动」。

## 修复

1. **进度条改回内容轴**（与时间文本同一分母）：
   `contentOffset={contentOffsetRef.current}`、`contentDuration={contentDurationRef.current}`。
2. **把 ref 本身传进去**，`displayDur()` / `seekToRatio()` 优先读 `contentDurationRef.current`：
   这样即使组件不重渲染，`write()` 每次被 `timeupdate` 触发时读到的都是最新真源时长。
3. `seekToRatio` 同步修正：它用同一个 `dur` 把「拖拽比例」换算成内容秒再交给
   `contentSeek(contentSec)`，而 `contentSeek` 内部是 `(contentSec - contentOffsetRef.current) / speed`
   —— **它本来就只接受内容轴秒数**（`:950-965`）。分段轴传进去时换算全错。

### 明确的产品决定（不是顺手改）

可见条从此**恒为内容轴**：0% = 内容 0:00，100% = 内容末尾，与时间文本、`contentSeek` 一致。
「跳过片头/片尾」不再改变条面的分母（它本来也不该改：用户要看的是「这部片播到哪」）。

> 后续可选（**未做**，需另行确认）：把片头/片尾画成条面上的**区间标记**，让用户看见
> 「哪一段会被跳过」。这是新 UI，不在本次修复范围内 —— 先修错，再加功能。

### 反向证伪（完整旧代码还原）

首轮只还原了调用点（`segOffset`/`segDuration`）**未能证伪**：因为 `resolvedContentDuration()`
里 ref 优先仍在，分母仍是 630 ⇒ 脚本 PASS。**只还原一半不构成证伪。**

把 `resolvedContentDuration()` 一并还原成 prop 优先（即真正的修复前实现）后：

```
[verify] FAIL - S3 条面分母 = 真源总时长 :: aria-valuemax=8 期望≈630；元素 duration=8.4
[verify] FAIL - S5 可见条宽 = 播放点/真源时长 :: bar=36.9% @3.2s 期望=0.5% Δ=36.4pt
```

恢复修复后复跑 ⇒ 全 PASS、退出码 0。

> 教训：**证伪必须还原整条因果链**（调用点 + 分母解析），只还原一处会得到假 PASS。
> 同型风险：BUG-450 的两处改动缺一不可 —— 只改调用点则 ref 优先掩盖问题，
> 只改 `resolvedContentDuration()` 则调用点仍传分段轴。
