# BUG-416: 缺少合并播放功能——多短视频合并成一段连续播放去卡顿

- 状态: fixed
- 发现日期: 2026-10-23
- 模块: shell
- 严重程度: mid

## 现象
当前剧集由大量短视频（1 分钟、几分钟）组成，逐条播放时频繁加载、切换跳转卡顿，
严重影响体验。建议提供「合并播放」：把多个视频合并成一段连续播放，去除视频切换
跳转的卡顿问题。

## 根因
播放序列逐集切换时，MediaViewer 内每集用 `<VideoPlayer key={cur.key}>` 强制整挂载 → 切集即整段重载（"下一集重新加载"），造成可感知的切换跳转卡顿。根因是「缺连播不断档的预载机制」，与「是否把 N 集物理拼成一个文件」**无关**——用户已明确：播放合并向来指 stream-first 连续播放，不涉 ffmpeg 物理拼接。关联 BUG-401（回跳重拉流，同源转码链路）、BUG-199（环回投递）。

## 2026-10-26 追加取证：用户说的「卡顿」有一半不是「缺合并」，而是流形态

用户第六次报「合并播放,连续播放,这些问题完全丢失」。为分清「缺能力」与「实现坏了」，
本轮实测了媒体源形态（细节与命令见 BUG-428）：

| 事实 | 实测值 |
|---|---|
| 播放器取的端点 | `…/api/media/items/<id>/stream`（**视频一律走它**，`streamFirst` 恒真） |
| `/stream` 响应头 | `x-orig-stream: live`、`transfer-encoding: chunked`、**无 `content-length`**、**无 `accept-ranges`** |
| `/raw` 响应头 | `content-length: 277059820`、`accept-ranges: bytes` |
| `/raw` 是否可解 | **可解**：372ms 到 `canplay`、`duration=694.07`、720×1280、零错误 |
| live 流的 `duration` | 随下载量上涨的估算值（16× 实测 9.43 → 374.07，恒比 `currentTime` 大 4~8s） |

⇒ 「逐条播放时频繁加载、切换跳转卡顿」的直接来源至少有两个，且都**不需要合并播放**就能修：

1. **live 流不可 seek**（无 `accept-ranges`）⇒ 拖动/跳转只能重锚重转码；
2. **播完判定依赖 `ended`**，而 live 流的结尾何时到达取决于转码进度 ⇒ 连播不可靠
   （已由 **BUG-428** 用「真源总时长兜底」修掉，实测剧集 219 连播 7/7 通过）。

⇒ 连播可靠性已由 BUG-428 用「真源总时长兜底」修掉（实测剧集 219 连播 7/7 通过）；本档卡顿根因收敛为「缺连播不断档预载」（见下 修复），不涉及任何文件级合并。

## 修复
对应 2026-10-26 用户最新诉求「合并播放入口(全部播放) → 合并所有集播放」= UI 连播不断档（**非** ffmpeg 拼文件），落地如下：
- 「▶ 播放全部」入口（SeriesDetail.tsx:762，`data-testid="series-play-all"`）：取首个可播集在**全量序列**里的下标 → `props.onPlay` → `playEpisode` → `playItems(episodesToItems(detail), index)` → `openViewer({items, index})` 连续播放；MediaViewer 已按 mode 分组、自动续播（`onPlayNext`）。
- 连播不断档：MediaViewer 主体后常驻隐藏预载 `<video preload="auto">`（`data-testid="next-episode-preload"`，MediaViewer.tsx:225），切集前预载下一集字节；跨集切换 MediaViewer 不卸载，下一集挂载时字节已在 HTTP 缓存，消除「下一集重新加载」，连播如单视频续播。
