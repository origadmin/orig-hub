# BUG-330: TG 面板「频道→监控→筛选」三层逻辑失载——筛选命中无内容信息、规则列表不扩展、进筛选后监控/分组点击无效

- 状态: fixed
- 发现日期: 2026-10-20
- 模块: engine+shell
- 严重程度: high

## 现象（用户原话，2026-10-20）

> 「最严重的筛选出来的内容,无法看到内容信息. 筛选过滤将来会有很多条. 而且进入筛选后下面的分组无法进去,这是层次逻辑问题. 整个层次逻辑和功能都需要重新设计排版设计, 频道->监控->筛选,这是3层逻辑. 出新BUG,重新设计排版和布局方案.」

拆成三条各自定位：

1. **最严重**：筛选出来的内容「无法看到内容信息」——命中行看不出筛到的是什么；
2. 筛选规则「将来会有很多条」——当前结构不 scale；
3. 「进入筛选后下面的分组无法进去」——层次逻辑断裂，用户裁定「整个层次逻辑和功能都需要重新设计排版」。

## 三层口径（用户 2026-10-20 澄清，实现前锁定）

> 「整条流程线的核心逻辑是监听我需要的内容,筛选添加的就是我需要监听的更新内容.
> 监控是需要监听的内容监控,只检查这些频道的实时更新.」

| 层 | 职责（用户口径） | 代码证据 |
| --- | --- | --- |
| 频道 | 全域：还没决定监听谁 | dialogs 扫描的 `channels`（`TgPanel.tsx` groupSections） |
| 监控 | **范围**：只对这些频道做实时更新检查 | `orig-tg/src/monitor.rs:91` `sync_once` 只遍历 `list_channels()`（= `monitored_channel` 行） |
| 筛选 | **内容定义**：在监控范围的更新里，什么是我要的 | `store.rs:1156` `filter_messages` JOIN `monitored_channel` 限定监控范围内；关键词匹配 caption/file_name |

流程线：频道里选出要监听的（加监控）→ 监控只检查这些频道的实时更新（sync + `+N` 未读徽标）
→ 筛选在这些更新中定义「我需要的内容」→ 命中列表勾选入库。

**由该口径直接导出的设计点（推导，非新造需求）**：

1. 筛选层必须有「新增命中」呈现——用户口径「筛选添加的就是我需要监听的更新内容」，
   而 `monitor_filter` 表（`store.rs:556-561`）**没有已读游标**（`monitored_channel` 有
   `last_read_message_id`，:553），命中只有总数、无「新命中」。「监听更新」这个核心逻辑
   在筛选层目前是断的 ⇒ 重排时补 per-filter 已读游标与「+N 新命中」徽标（与监控行 +N 同构）。
2. 左栏三节文案按此口径落：监控节 = 「只检查这些频道的实时更新」，筛选节 = 「我需要监听的内容」。

## 根因

### ① 筛选命中无内容呈现（最严重）

- **UI 层**：`tauri-shell/src/components/TgFilterPanel.tsx:195-233` —— 命中行 = 复选框 +
  `hitTitle()` 单行截断标题（:219 `truncate`）+ 一行 meta（频道/类型/大小/时间）。
  **没有展开态、没有缩略图、看不到完整 caption** ——「筛出来了」但看不出筛到了什么。
  对照组：全局搜索命中（`TgPanel.tsx:2066-2125`）点行即展开 `MessageBubble` 全文 +
  播放按钮（BUG-151 范式）；筛选面板从未获得同等待遇。
- **数据层**：`download-engine/crates/orig-tg/src/store.rs:1153-1154` —— `filter_messages`
  的 SELECT **未取 `m.mime_type` / `m.file_path`**（同文件 `get_message` :1192 两者都取）
  ⇒ `MonitorFilterHit`（`store.rs:61-84`、`types.ts:274-288`）缺这两个字段，
  即使前端想展开也驱动不了 `PhotoBlock` / `VideoBlock` / `MessageBubble`。
  标题兜底（caption 首行 → 文件名 → `#消息号`，BUG-220）只解决了「有名字」，
  没解决「看得到内容」。

### ② 筛选规则列表不 scale

- `TgPanel.tsx:1879-1929` 筛选节**无滚动上限**（监控节有 `max-h-56`，:1797）；
  规则条数增长会无限挤压下方「频道分组」节（:1983 `flex-1 min-h-0`）。
- 规则列表无检索框、无分页，`filters.map` 全量渲染。
- 命中列表本身硬顶 200（`limit=200`，后端 clamp 500，BUG-329 已知边界），无游标。

### ③ 层次逻辑断裂（进筛选后监控行/分组行点不动）

- `TgPanel.tsx:2011` 主列分流是一条**优先级链**：
  `activeFilter ? <TgFilterPanel/> : globalSearch ? … : (!detail && groupMode…) ? … : selectedChannel ? …`。
  筛选激活时 `activeFilter` **短路其余全部状态**：
  - 点分组行（:1990 `setGroupMode`）→ 主列无变化；
  - 点监控行（:1813 → `openMonitored` :1324-1336）→ 主列无变化，且
    **`markTgChannelRead` 照常执行**——未读徽标 `+N` 清零但视图没切换
    （有副作用、无反馈，用户感知「点了没反应」）；
  - 唯一出口是筛选面板内的「← 返回内容视图」（`onClose` 清 `activeFilter`）。
- **架构根因**：TG 域没有统一导航态。文件域/下载域早已用 `NavState` + `fmode`/`dlFilter`
  （`nav/index.ts:94-98`）把「域内选择」收敛成单一字符串状态；TG 域是**四个各自独立的
  状态**（`activeFilter` / `globalSearch` / `groupMode`+`detail` / `selectedId`）外加一条
  临时优先级链——「筛选激活 + 分组已选」这种错误态**可表达且不可见**，
  是「让错误状态不可表达」原则的反例。

## 复现

1. TG 面板左栏「文字筛选」节点任一规则 → 主列进入命中列表；
2. 点左栏「监控」节任一频道行：主列无变化（仍显示命中列表），但该行 `+N` 徽标消失
   （read 游标已推，`openMonitored` 静默执行）；
3. 点左栏底部「频道」分组行：主列无变化；
4. 连续 `POST /api/tg/monitor/filters` 造多条规则：筛选节无限增高、挤压分组区，
   无滚动上限；
5. 命中列表内：行只能勾选，无展开/预览，标题超长即截断，看不到内容本身。

## 修复

三层逻辑（频道 → 监控 → 筛选）重排：单一 `tgMode` 状态机取代四态优先级链
（对齐文件域 `fmode` 范式）、命中列表补内容预览（点行展开 `MessageBubble`，
BUG-151 范式）+ 分页游标、`filter_messages` SELECT 补 `mime_type`/`file_path`。

**二级菜单面板设计（本期核心交付物，v2）**：`docs/design/tg-secondary-menu-2026-10-20.md`
——监听链漏斗（两序分离：构建序由状态条承载、消费序排三节版面）、`tgMode` 五值、
per-filter 已读游标与「+N 新命中」、单一写面（监控开关只在主列频道实体）、
TGM-01~08 任务分解（全部未开工，等用户开发指令）。主列命中列表「可预览 + 分页」
规格见该文 §3.3/§4。

   - 左栏规则行：标题 `{f.label}`（:1903-1905）+ 副行 `“{f.keyword}”`（:1906）——同一个词出现两次；
   - 主列命中页头：`筛选：{label}`（`TgFilterPanel.tsx:176`）+ 副条 `“{keyword}” · 匹配…`（:184）。
   修法：`label === keyword` 时**只渲染一处**（左栏只留标题行；主列副条去掉关键词只留匹配说明），
   label 与 keyword 不同（用户自起显示名）时才两行都显。
3. **筛选规则多条后的折叠与展示（新症状）**：`tg-filter-list`（`TgPanel.tsx:1881-1929`）当前
   全量 `filters.map`，无折叠无上限。用户要求「多个显示超出规则后的折叠和展示」——即规则数超阈值时
   折叠多余条目 + 「+N 条」展开/收起（真控件，BUG-320 纪律：折叠入口是 button + 文案 + aria）。
   与 v2 §2.1「单一滚动容器」配合：默认显示 K 条（K 按最矮受支持窗口 900×600 实测），
   其余折叠；节内检索框（v2 §2.3）常驻保留。
4. **监控区突兀 ICON（新症状）**：监控节标题的 **`⭐` emoji**（`TgPanel.tsx:1779`
   `⭐ {t('tg.navMonitor')} ({monitoredList.length})`）——其余节头（文字筛选/添加监控）均无图标，
   单这一节带头像以外还挂 emoji，纯装饰且与全仓 lucide 图标体系不一类。同类待清理（行型 glyph，
   证据同级、是否同批改由用户定）：`🎵/📄` 类型字（`TgPanel.tsx:2473`/`:2729`）。
   `✕` 行尾删除（:1849/:1923）是 v2 §2.1 已登记范式（28px 热区），**不在清理范围**。
