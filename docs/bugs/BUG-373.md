# BUG-373：TG 重启风暴（daemon 每几分钟杀重启 orig-tg，用户侧「TG 完全无效 / 卡顿 / 进度不动」）

- 状态：in_progress（机制与证据已实，**触发器未定位**；未修）
- 发现日期：2026-10-22
- 模块：engine
- 严重程度：high
- 域：engine
- 用户原话（2026-10-22）：「完蛋了,系统完全坏了……TG完全无效了」「卡顿非常卡顿,进度完全不动」

## 机制（已实证）

- daemon 内建 TG supervisor（BUG-178 设计）：每 15s 探 `GET 127.0.0.1:19787/api/tg/session`（reqwest `no_proxy()` + connect 2s / 总 4s 超时，BUG-077），连续 3 轮失败即杀+重启 orig-tg（BUG-351：抖动期 5 分钟冷却）。设计前提：orig-tg 只在启动时连一次 Telegram，连不上就永远不可用，必须由巡检重启。
- **实测风暴**：`%TEMP%/orighub-dev-daemon.log` 里 `telegram link is down, restarting orig-tg` **555 次**、探针失败 643 次；`%APPDATA%/com.origadmin.orighub/logs/orig-tg.log` `listening` 626 次。BUG-351 修过同类病（当时实测 477 次），现在更严重，且 2026-10-22 02:00–03:00 仍在继续（日志当场追加 `link down (1/3)`）。
- 用户侧观感：每次重启 = 会话重建 + 在传缓存队列全变「应用重启：传输被中断」+ 进行中下载被杀；down 窗口内 `/api/activity` 的 cache 源 `available=false` ⇒ 下载域 ingest 行整片消失（这同时是 BUG-372①「不滚」的触发条件）⇒「TG 完全无效」「进度完全不动」「卡顿」。
- 数据安全原理：任务账与文件在 daemon 存储 + `D:\OrigDown`，orig-tg 只是传输通道 ⇒「系统坏了但数据还在」（27 条 cache 任务、2 条失败任务均完好）。

## 触发器（**已定案**：orig-tg 全量端点超时，非代理、非进程假死）

2026-10-22 03:4x 用户报「TG 入库任务暂时无法读取：request orig-tg: error sending request for url (http://127.0.0.1:19787/api/tg/cache/tasks/all)」时，`GET /api/tg/session` **正常返回 Authorized**（orig-tg 活着、探针健康、不重启），但 daemon 聚合层仍报 cache 源不可用。对同一端点 `GET /api/tg/cache/tasks/all` 连测三次：

| 次数 | 耗时 | daemon 4s 超时下的结果 |
|---|---|---|
| 1 | 3.18s | 勉强过关 |
| 2 | 0.03s | 过关 |
| 3 | **13.70s** | **超时 ⇒ `error sending request for url`** |

⇒ 用户看到的报错**不是 orig-tg 挂了、不是代理**，是这个端点本身会慢到超过 daemon 的 4s 总超时（reqwest 对超时的显示正是 `error sending request for url`）。慢的由来见 `activity.rs:456` 注释：该端点每次现算 519 对话 + 67 频道的合并，约 55KB 载荷，无内存快照。

**原两候选的结论**：① 本机企业代理 —— **排除**（`build_http_client` 已 `no_proxy()`，`state.rs:180`）；② orig-tg 运行时 stall —— **部分成立但表述不准**：进程不假死，是**重端点偶发极慢**（疑为 dialogs 合并的 CPU 占用或 store 同步段），慢即被 4s 超时切断。探针走轻量 `session` 端点故不受影响 ⇒ 解释了「探针绿但聚合红」的分裂。
