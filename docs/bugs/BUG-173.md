# BUG-173：共享 `store.db` 拆分的前置阻塞——5 处跨域耦合不先改造，拆库即制造数据损伤

- 状态: open
- 发现日期: 2026-09-28
- 模块: engine
- 严重程度: critical
- 档位: standard

## 现象

用户已拍板 **D2-A（把 `store.db` 拆成 TG 库 + 库库两个文件）**。施工图
`docs/design/store-db-split-design-2026-09-29.md` 已交付（637 行，T01–T05）。

但施工图把拆库当作**纯搬迁**（`ATTACH DATABASE` + `INSERT OR IGNORE … SELECT`）。实测核查发现：
现状存在 **5 处「单连接跨两域」的代码路径**，它们在共库时靠「同一个连接、同一张表、同一次语句」
隐式成立；一旦表分到两个文件，这些路径**不是报错退出，而是静默降级 / 静默跳过 / 数据被清**。

即：**拆库的前置条件不是迁移脚本正确，而是这 5 处耦合先被显式改造。**
若直接按 T01–T05 施工，预期的失败形态是「数据没搬丢，但运行时行为悄悄变坏」，属本项目最难排查的一类故障。

**5 处路径的后果分级**：

| # | 路径 | 拆库后行为 | 用户可见后果 |
|---|---|---|---|
| 1 | `purge_item` 跨域清字节 | 单函数内写两个库、**无事务** | 「清缓存后仍显示已缓存」/「条目没了字节还在」 |
| 2 | `duplicate_file_paths` 单连接查两表 | 表不在本库 → **直接 Err**（非降级） | 启动对账 / BUG-100 检测面崩溃 |
| 3 | `app_setting` 被两域共同拥有，且库侧走**裸 SQL** 绕过访问器 | 分流错边 → 迁移**重复跑** | `media_episode` 的 `title` **与** `description` **被再次清空** |
| 4 | `library_root()` / `download_dir()` 归属 | 分流错边 → 解析出**错误目录** | 清缓存**静默跳过一切**（什么都不删） |
| 5 | `first_caption()` 每次缓存任务都读 TG 库 | 跨库只读失效 → 静默降级 | 剧集名持续退化，且**每次缓存任务都犯** |

## 根因

### 主因：`media.rs` 在共库假设下写成了「单连接跨域」，从未声明过域边界

`store.rs:297-364 Store::open` 打开**一个** `libsql::Connection`，`media.rs` 的全部
`impl Store` 方法（`:1052` 起）复用**同一个** `self.conn`。两域共库时这不是问题；
拆库后同一个 `self.conn` 无法同时看到两张分属不同文件的表。

关键：**没有任何一处代码声明过「这个字段属于哪个域」**。归属知识只存在于施工图的人工分析里，
不在类型系统、不在常量、不在测试断言里——所以拆库时无法靠编译器或门禁发现漏网。

### 逐条证据

**#1｜`purge_item` 跨两域无事务（最高危）**

`download-engine/crates/orig-tg/src/cache.rs:414-477`，单函数内依序：

- `:441` `std::fs::remove_file` —— 回收字节（文件系统域）
- `:442` `set_item_file_path(it.id, None)` —— **写库域** `media_item`
- `:460` `reset_tg_flag(st, &it.source, &it.ref_key)` —— **写 TG 域** `media_message`（经 `:876-898 reset_tg_flag` → `:888 clear_downloaded`）
- `:463-470` 任一失败仅计入 `failed`，**不中止、不回滚**

共库时两条语句共享一个隐式事务边界；拆库后它们分属两个文件，**没有跨库事务可加**
（libsql 的 `ATTACH` + 事务在跨文件时语义受限）。BUG-029 / BUG-109 的注释证明此处曾被专门修过
（注释原文指向「清字节却仍显示已缓存」这一最难查的不一致），说明该处对顺序/原子性极度敏感。

**#2｜`duplicate_file_paths` 单连接查两表**

`store.rs:756-792`，`:772`：

```rust
for table in ["media_item", "media_message"] {
```

`:770-771` 注释原文：「两张表都要查：`media_item` 决定『条目能不能播』，
`media_message` 决定『TG 流水能不能重新取字节』——只查一张会漏掉另一侧的死链。」

拆库后 `media_item` 不在 TG 库，该 `for` 的第一次迭代即返回 Err。这不是「漏查」而是**整个功能不可用**。
对应单测 `store.rs:1718 duplicate_file_paths_reports_shared_paths_in_both_tables`
（`:1755` 断言 `shared.len() == 2`，两表各一条）将连带失效——且失效原因是**测试自身跨库**，不是被测逻辑错。

**#3｜`app_setting` 是唯一一张被两域共同拥有的表，且库侧绕过访问器**

**第一层：两域共同拥有**

- 库域侧建表/读写：`media.rs:78` / `:161`（`CREATE TABLE IF NOT EXISTS`）、
  `:82` / `:165`（读）、`:139` / `:213`（写 `mig.*` 标记）
- TG 域侧建表/读写：`store.rs:335`（建表）、`:663` / `:674`（`get_setting` / `set_setting`）
- 使用方：`cache.rs:62`（`download_dir`）、`routes.rs:732/788/803/844`

危害不在于「表分了读不到」，而在于**迁移标记（`mig.item_text_split_v1`、`mig.episode_text_to_item_v1`）
落错边 → 下次启动视为未迁移 → `backfill_item_text` / `collapse_episode_text` 重跑**。
而重跑的动作是 `media.rs:208-209`：

```rust
conn.execute("UPDATE media_episode SET title = NULL, description = NULL", ()).await?;
```

**清空的是 `title` 与 `description` 两个字段**（不只是简介）——即：分流错误 =
**用户的剧集标题与简介被二次清空**，且这是幂等标记失效导致的**重复伤害**（每次启动重犯）。

上游已实测：本机 `app_setting` 实有 **2 行**，恰为上述两个 `mig.*` 键；
`library_dir` / `download_dir` **都不在表中**（库根正走 `library_root()` 第 4 档默认值）。

**第二层（更关键）：库侧读写 `app_setting` 用的是裸 SQL，完全绕过访问器**

`media.rs` 对 `app_setting` 的全部访问均为裸 SQL，**不经过 `get_setting`/`set_setting`**：

| `media.rs` 行 | 语句 | 性质 |
|---|---|---|
| `:78` / `:161` | `CREATE TABLE IF NOT EXISTS app_setting (key TEXT PRIMARY KEY, value TEXT NOT NULL)` | **自己建表，两处各写一遍** |
| `:82` / `:165` | `SELECT 1 FROM app_setting WHERE key = ?1` | 读迁移标记 |
| `:139` / `:213` | `INSERT OR REPLACE INTO app_setting (key, value) VALUES (?1, '1')` | 写迁移标记 |

读写点：`media.rs:84` / `:140` / `:167` / `:214`，实参为常量 `ITEM_TEXT_SPLIT_MIG`（`:30`）/
`EPISODE_TEXT_MIG`（`:33`），**非字符串字面量**。

**这一层使「在 `set_setting` 内部分流」的方案失效**：分流的判定逻辑若写在访问器里，
这两个键不走访问器 → 判定逻辑够不着它们 → 它们照旧写入**当前连接**（拆库后 = TG 连接）→
触发重跑 → 上述二次清空。**即：任何只在 `get_setting`/`set_setting` 层做的归属拦截，
都保不住这两个后果最重的键。**

根因在签名：`media::migrate(&conn)`（由 `store.rs:362` 调用）接收的是**裸 `libsql::Connection`**，
不是 `Store` —— 这既是它用裸 SQL 的原因，也是归属判定够不着它的原因。

**判定口径（本档 A3 的依据）**：`app_setting` 存在**两条访问路径**——
① 访问器（`get_setting`/`set_setting`，2 个 key：`library_dir` / `download_dir`）；
② 裸 SQL（`media.rs` 6 处，2 个 key：两个 `mig.*`，其中 2 处还自己建表）。
**归属机制必须在两条路径上同时成立，否则机制本身是假绿。**

**#4｜`library_root()` 与 `download_dir()` 的域归属未被裁定**

调用点实测（`library_root()` 共 **15 处**）：
`store.rs:682-707`（定义）、`cache.rs:141 / 631 / 675 / 719 / 782 / 1059`、
`media.rs:1069 / 1151 / 1540 / 1672 / 1930`、
`routes.rs:717 / 754 / 867 / 2158 / 2675 / 3012`。

`download_dir()`：`cache.rs:55-69`（定义，注释「缓存字节的**唯一可删区**」）、
`routes.rs:753 effective_download_dir`、`routes.rs:817 / 1064 / 1654 resolve_cache_dir`。

对 `media.rs` 侧（`:1069/1151/1540/1672/1930`）它读的是**库根**，属库域；
对 `routes.rs:3012 item_raw` 与 `cache.rs:141 house_downloaded_bytes` 它同时要判「是否在可删区内」。
**归属分错 = 解析出一个不存在的目录**，而下游 `inside_dir` 判定为 false 时的行为是**跳过**
（`cache.rs:424-437`），于是「清理缓存」表现为**静默什么都不删**——无错误、无日志、无提示。

**#5｜`first_caption()` 是持续性的跨域读（非一次性）**

`media.rs:3485` 注释自述：「读的是 `media_message.caption`（**真实 caption**），
而不是 `media_item.title`」；实现 `:3524` / `:3532`；调用方 `ensure_series`。

施工图 §4 设计的跨域只读入口 `LibraryStore::tg_caption`（只读、`Option`、**失败降级**）
本身是对的，但**降级策略把故障变成了静默**：`tg_ro` 不可用时剧集名退化为
「频道名·日期」而非报错。危害是**每次缓存任务都触发一次**（不同于 `caption_of_ref` 的一次性），
用户会观察到剧集名逐渐失真且无法定位。

### 次因：约 35 处单测的语义前提随拆库失效

`store.rs` / `media.rs` / `cache.rs` 中通过 `set_setting("library_dir")` 或
直接断言两表结果来构造前提的单测（如 `store.rs:1399 library_root_resolution_chain`、
`:1718 duplicate_file_paths_…`、`media.rs:6334/6445/6517`、`cache.rs:1349/1389`）
在拆库后需要**显式建立两库**才能运行。若不改造，失败原因会是「夹具不全」而非被测逻辑错，
属于本仓已登记的判据质量问题（BUG-156：断言打在错误的层级上）。

## 复现

**前置**：按施工图 T01–T05 完成拆库（构造「两文件 + 单连接」的中间态即可，无需完整实现）。

1. **#2 直接可复现**：拆库后启动 → `duplicate_file_paths` 首次调用即返回 Err；
   跑 `store.rs:1718` 单测必 FAIL。
2. **#4 静默复现**：把 `library_root` 的 `app_setting` 读侧指向 TG 库（或库库，取错的一边），
   制造一个已缓存条目 → 执行「清理缓存」→ 观察 `Purged{removed:0, skipped:N}`：
   **无错误、无异常、UI 正常**，但字节与条目都还在。
3. **#3 伤害复现**：把两个 `mig.*` 标记写进 TG 库（或让库侧读不到标记）→ 重启 → 观察
   `media_episode` 的 `title` 与 `description` 被 `media.rs:208-209` 二次清空；
   此时 `app_setting` 里标记仍在（存在错边），故**每次启动都会重犯**。
   注意：#3 的实现路径是**裸 SQL**（`media.rs:82/139/165/213`），**不经访问器** ——
   因此「在 `set_setting` 里做归属判定」这类修法对它无效，复现不会因此消失。
4. **#1 不可靠复现但可推演**：在 `:442` 与 `:460` 之间注入失败（如令 TG 库只读），
   观察结果是 `failed` 计数 +1，而**库域改动已落盘、TG 域改动未落盘**——两域不一致且无补偿路径。

## 修复

> 本条为**前置阻塞档（pre-fix）**：不新增产品行为，只声明「拆库动工前必须先成立」的改造项。
> 修复方式属工程自决，但**验收判据（下述 A1–A6）必须先成立**。

### 硬约束

- **H1**：拆库动工前，`media.rs` / `cache.rs` / `store.rs` 中**不得存在任何单连接跨域读写**。
  每一处跨域访问必须在代码上可识别（独立的连接对象或独立函数），且其失败路径**不得静默**。
- **H2**：`app_setting` 的归域机制必须**同时覆盖两条访问路径**——
  ① 访问器（`get_setting` / `set_setting`）；
  ② **裸 SQL**（`media.rs:78/82/139/161/165/213`）。
  只覆盖 ① 的机制**保不住两个 `mig.*` 键**（`media.rs:84/140/167/214` 走裸 SQL，
  实参为常量 `media.rs:30/33`），因而等于没做。落地形态见 A3。
  同时：**「未登记 key 静默兜底到某一侧」的兜底策略不安全** ——
  `app_setting` 是封闭 key 集（实测全仓仅 4 个 key），兜底方向若指向后果最重的一侧
  （`mig.*` 落错 = 数据清空），则每一次漏登记都变成静默的数据损伤。
  正解是**未登记 key 显式失败**（非静默落任一侧）。
- **H3**：`library_root()` / `download_dir()` 的求解**不得依赖运行时归属推断**：
  库根只由库库自身的路径推导（施工图 §2.2 已论证无真环，本次确认该结论成立）。

### 归属定案（原「待拍板」项，已按实测判据收敛）

`library_dir` / `download_dir` 的归属曾是分歧点（架构师 v1 判「均归库库」、
QA 判「均归 TG 库」）。**双方都把两个 key 绑在一起判。**

> **⚠️ 二次修正（用户质疑触发，2026-09-28）**：上一版本档把 `download_dir` 判给「TG 库」，
> **该判定错误，已废止**。错因：用「当前谁在读它」当归属依据，忽略了
> 「这个概念本身属于哪个能力」。用户指出「**工具本身是下载工具，有一个下载功能，和 TG 没关系**」——
> 核实后用户正确，证据见下。

#### 真实架构：`download_dir` 属**下载引擎域**，不属 TG 域也不属库域

决定性证据（全部实测）：

| 证据 | 位置 | 含义 |
|---|---|---|
| **「铁律 5」** | `orig-daemon/src/activity.rs:435` 测试 `tg_unavailable_still_returns_downloads`，注释原文「**9877 挂掉时普通下载任务必须照常返回**」 | 项目已确立：**普通下载（`TaskKind::Download`）与 TG 缓存（`TaskKind::Cache`）是两个任务类别**，且下载必须独立于 TG 存活 |
| daemon 侧有完整下载目录语义 | `orig-daemon/src/config.rs:81`（字段）、`:446`（三级解析 `request → config → platform default`）、`:475`（API 暴露）、`:219-222`（配置文件读取） | 下载目录是**下载引擎的一等配置** |
| daemon 侧用正确的 OS API | `orig-daemon/src/config.rs:439-443` 委托 `orig_core::paths::default_download_dir()`（注释「never a literal `~/Downloads`, see BUG-071」） | 主域实现 |
| **orig-tg 侧是复制品** | `orig-tg/src/config.rs:52-63` **自己实现一遍**手工拼 `HOME`/`USERPROFILE` + `Downloads`，注释自述「**对齐 orig-daemon：~/Downloads**」 | 副消费者，且该实现**恰是 BUG-071 要修的手工拼接形态**（与 daemon 侧未真正对齐） |
| orig-tg 侧唯一用途是**可删区判定** | `cache.rs:291/619/769/1058` 全部是 `inside_dir(&dir, &path)` 检查与清理范围 | 它不是「下载目录」的所有者，只是用它判定「哪个文件可以删」 |

⇒ **`download_dir` 的域归属 = 下载引擎（daemon / `orig-core`）**。
`orig-tg` 中的同名 key 是**跨域消费副本**（为缓存字节判定可删区），不是它的家。

#### 修正后的归属表

| key | 归属 | 判据 |
|---|---|---|
| `library_dir` | **`library.db`** | 域 = 库域；唯一实体读在 `Store::library_root()` 内（`store.rs:698`），随 `library_root()` 迁 `LibraryStore` |
| `download_dir` | **下载引擎域**（不属任一新库） | 域 = 下载引擎（铁律 5 + daemon 侧完整语义 + orig-tg 侧为复制品）。**落进 TG 库会破坏「TG 挂掉时下载照常」** |
| `mig.item_text_split_v1` / `mig.episode_text_to_item_v1` | **`library.db`** | 域 = 库域；由库域 `media::migrate` 读写，动作作用于 `media_episode` |
| `mig.store_split_v1`（新增） | TG 库（临时标记） | 拆库进度标记，随原库保留 |

**`download_dir` 的落地形态（三种，须先裁定）**：

- **(a) 留 TG 库**：零改动，但**语义错误**——把下载引擎的配置寄存在 TG 域，
  且「TG 库」在 D1-A（独立 orig-media 进程）形态下会被媒体服务持有，造成「下载配置被内容域挟持」。
- **(b) 留库库**：架师 v1 判定，**更错**（把下载引擎配置寄存在内容域）。
- **(c) 归下载引擎自有配置**：correct-by-domain。但下载引擎当前**没有自己的库**
  （`orig-daemon` 零 SQLite 连接，见 F8），故需先回答「下载引擎的配置存哪」——
  可能是 `download-engine.toml`（`daemon/config.rs:446` 已是三级解析的一环）或 daemon 新建自有配置。
  **此项与 D1（部署形态）耦合，须与 D1 一并裁定。**

**判据维度差异（定案的关键）**：三个 key 的归属依据是**域**（谁的能力），
不是「当前哪个连接在读它」。**用调用点判归属会把「寄宿现状」当成「设计归属」**——
这正是本档前版对 `download_dir` 判错的根因，也是架构师 v1/QA 判错的同一类错误。

**若把 `library_root()` 留在 TG 侧 Store（QA 原方案）会怎样**：库侧 5 处调用
（`media.rs:1069/1151/1540/1672/1930`）都要跨连接回 TG 库读库根，
违反 `MEDIA-DESIGN.md §0` 的 M3 禁区（「不依赖 TG 会话」）。⇒ 该方案不闭合。

## 验收证据

> 状态为 `open`，按规范**不得伪造验收证据**。以下为**拆库动工前必须成立的可证伪判据
> （预先声明）**，用于判定 T01–T05 是否可以开工。

**A1（跨域访问可识别）**：拆库后，`purge_item` / `duplicate_file_paths` / `first_caption`
三条路径上的跨域访问必须在**代码层面可静态识别**（独立连接对象或独立函数签名）。
反向证伪：若 `purge_item` 仍以单个 `self.conn` 同时写 `media_item` 与 `media_message`，A1 必须 FAIL。

**A2（删除联动不许静默）**：制造「TG 库不可写」后执行清缓存，
`Purged` 必须如实反映**字节未回收**（`removed` 不含该条），且**必须产生可见错误**
（非仅计数 +1）。反向证伪：若 UI 与日志均无异常而字节实际未删，A2 必须 FAIL。

**A3（`app_setting` 归属机制必须覆盖两条访问路径）**

归属必须以常量表落码（施工图 §2.1.2 的 `LIBRARY_DB_KEYS` / `TG_DB_KEYS` 形态可用），
且**未登记 key 必须显式失败，不得静默兜底到任一侧**（兜底方向指向后果最重侧 = 每次漏登记
都变成静默数据损伤；`app_setting` 实测为封闭 key 集，穷举可行）。

检测须**三层齐备**，缺一层即 FAIL：

1. **静态扫描**：扫**裸 SQL** `app_setting` 出现次数（`conn.execute` / `prepare` / `CREATE TABLE`），
   **白名单为 0** —— 现有 6 处（`media.rs:78/82/139/161/165/213`）中，建表 2 处与读写 4 处
   均须在改造后落入「经归属判定」的路径。⚠️ **仅扫 `get_setting`/`set_setting` 的实参不够**：
   两个 `mig.*` 走裸 SQL，实参还是常量（`media.rs:30/33`），扫字面量会**漏掉后果最重的两个键**。
2. **归属断言**：对每个 key 断言其**实体读写点所在连接**与归属一致 —— 但**注意判据方向**：
   归属由**域**决定（谁的能力），断言的是「实体读写点是否落在其**域应有**的连接上」，
   **不是**「该 key 当前被哪个连接读 ⇒ 就归哪个库」（后者 = 用寄宿现状推设计归属，正是本档
   对 `download_dir` 前版判错的根因）。按修正后归属：
   - `library_dir`（域=库域）→ 实体读 `store.rs:698` 必须落在**库连接**；
   - `download_dir`（域=**下载引擎**）→ 其 orig-tg 侧 4 处读点（`cache.rs:62` / `routes.rs:732/788/844`）
     均为**跨域消费副本**，断言的是「它是副本而非所有者」；若拆库后被误判为「归 TG 库或库库」
     而由该库持有真源 → **FAIL**（违反铁律 5：TG 库被媒体服务持有后，下载配置被内容域挟持）。
   反向：某 key 的实体读点落在与其**域归属**相反的连接上 → FAIL。
3. **未知 key 拒绝**：构造一个未登记 key 调 `set_setting` → **必须返回 Err**（或 debug 断言 panic），
   **不得静默写入任一库**。

反向证伪：在**拆库前的现库（共库态）**下，第 1 层与第 3 层**必然 FAIL**
（现库裸 SQL 6 处、无归属常量表）；若在共库态下 A3 全绿，则说明门禁是假绿。

**A4（库根求解不依赖 TG 库）**：断开 TG 库（改名为不可打开）后，`library_root()`
必须仍返回正确库根（施工图 §2.2 的无真环论证成立）。反向证伪：若库根解析在 TG 库缺失时
退化为 `Path::new(".").join("library")`，A4 必须 FAIL（该退化路径见 BUG-172 既有隐患条目）。

**A5（迁移不重复伤害）**：在 `mig.*` 标记已存在的前提下重跑启动流程，
`media_episode` 的 **`title` 与 `description` 均必须保持不变**（`media.rs:208-209`
清的是这两列，非仅 `description`）。反向证伪：迁移二次执行导致任一列被再次清空，A5 必须 FAIL。

**A5b（签名级切断，A1/A5 的落地手段）**：迁移逻辑必须改走「已声明归属的连接」，
不得接触裸 `Connection`—— 即 `media::migrate(&conn)`（`store.rs:362` 调用）的签名改造完成后，
`mig.*` 的读写不得再出现裸 SQL。反向证伪：若改造后仍能构造出「`mig.*` 写入非其归属库」的路径，
A5b 必须 FAIL。

> 说明（对 QA 方案的采纳与反驳折中）：**不建议给 `Connection` 层做一套分流**——
> 那等于把 `Store` 已封闭的抽象打开，且会同时适用于库域与 TG 域连接，
> 是「重新发明一个更弱的 `Store`」。正解是**把迁移逻辑改走 `Store` / `LibraryStore` 方法**，
> 由签名切断裸 `Connection` 的可得性。此为 A5b 的依据。

**A6（剧集名跨域读失真必须可见）**：`tg_caption` 不可用时，`ensure_series` 的剧集名降级
**必须可观测**（日志或诊断端点计数）。反向证伪：剧集名静默退化为「频道名·日期」
而 `/api/tg/diag` 与日志均无痕迹，A6 必须 FAIL。

**证据落盘要求**：证据须引用被 git 跟踪的入库路径（迁移单测入
`download-engine/crates/orig-tg/src/` 的 `#[cfg(test)]` 或
`download-engine/verify/`）或真实提交短 hash；仅 `verify_shots/` 引用不构成跨机器可核验证据。

**反向证伪要求**：A1/A3/A5 的断言必须能在**拆库前的现库（共库态）**上
**必然 FAIL**（对齐 `MEMORY.md` 的「反向证伪是验收的验收」）——
即在共库态下这三个判据本就不成立，才能证明它们真的在为拆库把关，而非事后追认。
