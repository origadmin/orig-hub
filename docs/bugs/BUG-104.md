# BUG-104: 落盘文件名不含 chat/message 标识 → 两个 media_item 共享同一 file_path，清一条即打掉另一条的字节

- 状态: fixed
- 发现日期: 2026-09-21
- 模块: engine
- 严重程度: high

> 立项方式：所有者对「入库流水线」做完整流程评估后点名要修的两条 P0 之一。
> 评估档：`docs/design/ingest-pipeline-assessment.md` 第 1 条（P0）。
> 编号说明：098/099/100/101/102/103 在我动手前已被他条占用（媒体库生命周期、标签高亮、
> 监控搜索位置、监控列表折叠、同步单飞、合并剧集丢备用源），故顺延至 104。

## 现象

两个不同频道各发一个同名文件（例如都叫 `video_2024.mp4`），落盘后得到**完全相同**的
`file_path`。两个 `media_item` 于是指向同一个磁盘文件：

- 清掉其中一条时，`cache.rs::purge_item` 会 unlink 该文件；
- 另一条的 `file_path` 仍在、状态字段（`media_message.downloaded`）**不会复位**；
- 结果：UI 仍显示「已缓存」，点开 404，且因为状态是「已缓存」，**不会出现「重新缓存」入口**
  —— 用户卡死在这里，只能自己去数据库里改标志位。

## 根因

落盘文件名由原始名直接 `sanitize_filename` 得到，不含任何来源标识：

- `download-engine/crates/orig-tg/src/grammers.rs` 的 `download()` 中，
  `Media::Document` 分支原先是 `sanitize_filename(&name)`；
- 只有「无名文档」与「图片」两条分支（`doc-<chat>_<msg>.<ext>` / `photo-<chat>_<msg>.jpg`）
  天然带 chat/message，所以**有名字的文档**是唯一漏网的一类，而它恰恰是最常见的一类。

同名即同路径，同路径即共享字节 —— 没有任何一层会拒绝这种共享。

## 修法（止损修补，**不是最终方案**）

新落盘文件名改为 `<sanitized_name>-<chat_id>-<message_id>.<ext>`：

- 新增 `grammers::cache_filename(name, chat_id, message_id)`，
  先 `sanitize_filename` 清洗原始名，再在扩展名**之前**插入 `-<chat>-<msg>` 唯一后缀；
- 长度受 `MAX_CACHE_FILENAME_CHARS = 180` 约束（Windows `MAX_PATH` 260，扣掉目录前缀与
  BUG-024 的 `.part` 临时后缀）。**超长只截名字部分**：预算先扣掉唯一后缀与扩展名再截，
  唯一性不会因为截断被破坏；按**字符**而非字节截断，避免中文名被切成非法 UTF-8；
- 极端输入（扩展名长到把名字预算吃光）兜底为 `media-<chat>-<msg>.<ext>`，不产出空名。

**重要边界（必须守住，否则制造新事故）：**

1. **只影响新建，存量一律不动。** 存量行的 `file_path` 已写进数据库，改命名规则会让新代码
   找不到旧文件，制造数据错位。撞名只暴露、不自动修复（见下）。
2. **这是过渡方案。** 后续 hash blob 存储改造
   （`docs/design/blob-store-design.md`：`<download_dir>/blobs/ab/cd/<sha256hex>`）
   落地后由它的迁移任务统一搬运存量文件，届时 `cache_filename` 即可退役 ——
   代码注释里已写明，避免后人误以为是最终方案。
3. 图片与无名文档两条分支**保持原样**：它们本来就唯一，改了只会让存量路径对不上，无收益。

## 存量撞名检测（只报不修）

判据就是「按 `file_path` 分组，count > 1」。两种触发方式：

1. **启动对账（自动）**：`main.rs` 在 `Store::open` 之后跑一次
   `Store::duplicate_file_paths(20)`，非空则同时打 `stderr` 与环形日志
   （前端 `/api/tg/logs`、设置页日志面板可直接看到，不必翻进程输出）。
2. **按需（手动）**：`GET /api/tg/diag` 新增 `file_path_collisions` 字段。
   该端点是**手动**触发的诊断快照（`AccountsPanel.tsx` 按钮），不在任何轮询路径上，
   故这里的 DB 读不构成轮询压力，也不新增端点。

两张表都查：`media_item`（决定「条目能不能播」）与 `media_message`（决定「TG 流水能不能
重新取字节」）—— 只查一张会漏掉另一侧的死链。

**不自动修复**：自动修复意味着替用户决定删哪个文件/哪条记录，可能造成不可逆的数据丢失。
存量会自然收敛（清掉重下即不再撞名），不需要迁移。

## 验收证据

- 唯一性：`download-engine/crates/orig-tg/src/grammers.rs`
  `grammers::tests::cache_filename_is_unique_across_chats_and_messages` ——
  同名 + 不同频道 / 同频道不同消息，产出文件名互不相同，且后缀保留在扩展名之前。
- 清洗与兜底：同文件 `cache_filename_sanitizes_illegal_chars` ——
  `a:b|c?d*e.mp4` → `a_b_c_d_e--1001-7.mp4`（频道 id 为负，`--` 是预期形态）；
  空名 → `download--1001-7.bin`；无扩展名 → `README--1001-7`。
- 截断不破唯一性：同文件 `cache_filename_truncates_stem_but_keeps_unique_suffix` ——
  400 字的名字被截到总长 ≤ 180 后，`-<chat>-<msg>.mkv` 完整存活；预算耗尽走 `media` 兜底。
- 检测面：`download-engine/crates/orig-tg/src/store.rs`
  `store::tests::duplicate_file_paths_reports_shared_paths_in_both_tables` ——
  两个频道共享同一 `file_path` 时 `media_item` 与 `media_message` **各**报一条且 `count = 2`；
  唯一路径不被误报。
- 门禁：`cargo build` / `cargo test -p orig-tg`（58→59 项全绿）/ `scripts/check-bugs.py`
  / `scripts/sync-sidecars.sh --check` / `scripts/check-pollution.sh`。

## 备注

- 本次修复与 BUG-105（判定「能不能播」看数据库字段不看磁盘）是同一份评估里的两条 P0，
  现象互相放大：撞名让「清一条」变成「打掉两条」，而 BUG-105 的修复保证受害者会被复位成
  「未缓存」而不是永久假死。
- 未修（本条不覆盖）：`cache.rs::inside_dir` 在 canonicalize 失败时静默返回 false，
  把「判断不出来」与「确实不在目录内」混为一谈 —— 那是 BUG-105 的处理范围（三态判定），
  本条不改动它，因为改错会让「只删自己产出的字节」这条铁律失效。
