# BUG-458: 文件管理主操作「导入目录」语义错——应为「目录管理」（受管根集合的登记与管理），目录下媒体直接进文件管理

- 状态: open
- 发现日期: 2026-10-27
- 模块: shell
- 严重程度: mid
- 排期: 2026-11-26

> 来源：用户报告「**导入目录 不对，应该是添加目录，然后目录下的媒体文件进入文件管理。**」

## 现象

1. 文件管理主区右上角**主操作**（`page-primary-action`）是「＋ 导入目录」
   （`tauri-shell/src/shell/ContextBarFilesActions.tsx:33-44`，`t('media.importDir')`）。
2. 空态提示复用同一个词：`MediaLibraryPanel.tsx:1390` 渲染「导入目录」，
   `i18n/locales/zh-CN.json:214` 的 `media.emptyHint` 写「也可以点「导入目录」把本地
   视频/图片目录登记进来（原文件保留在原位，不会被复制或移动）」。
3. 实际行为是「**扫描 → 勾选文件 → 写库**」（`ImportDialog.tsx:22-81`）：
   目录本身**不成为纳管对象**。关闭对话框后往该目录新增一个视频，文件管理里
   不会出现，必须再走一遍「导入目录」并重新勾选。
4. 用户期望的语义是「**目录管理**」（2026-10-28 术语更正）：入口不是一次性的
   「添加目录」按钮，而是**受管根集合的管理**——登记 / 移除 / 设为主目录 / 手动对账
   都在同一处；目录登记进来后，其下的媒体归文件管理，内容变化能被看到，
   而不是一次性挑文件。

## 根因

1. **主操作接的是「导入文件」链路，不是「登记目录」链路。**
   `filesActions.import` → `ImportDialog`（`MediaLibraryPanel.tsx` 注册）→
   `scanDirectory` + `importMediaItems`（`ImportDialog.tsx:51 / 66-73`）。
   这条链路的产出是 **N 条 media_item**，目录只是扫描的输入参数，用完即弃。
2. **「受管根」能力已存在但没接进文件管理。**
   引擎侧 `GET/POST/DELETE /api/fs/roots`、`POST /api/fs/roots/primary`
   （`api/tg.ts:836-866`）；前端唯一调用点是设置面板
   （`SettingsPanel.tsx:819` 移除根、`:848` 新增根）。
   `grep -rn "listManagedRoots|addManagedRoot" --include=*.tsx` 在文件管理侧
   **0 命中** ⇒ 「目录管理 = 登记受管根」这条路径在文件管理里根本没有入口。
3. **文案把两种语义压成一个词。** 「导入」既像「复制进来」（实际不复制，见
   `ImportDialog.tsx:20` 注释），又不表达「持续纳管」，用户据此理解为
   「把目录加进来」，与实现不符 —— 名称承诺的行为与代码行为不一致。

## 复现

1. 文件管理 → 右上角「导入目录」→ 填目录 → 扫描 → 勾选若干文件 → 导入 N 个。
2. 往同一个目录拷入一个新视频。
3. 回到文件管理 ⇒ 新视频不出现；必须再次「导入目录」并手动勾选它。

## 启动时后台对账（2026-10-27 用户追加裁定）

用户追加：「**启动时后台验证数据 3 种情况：库有文件没有、库没有文件有、都有。
没有的入视频，不入剧集库。这样就没问题了吧？**」

按「目的已定 ⇒ 结论已定」落定如下（三种情况的行为表，即对账的唯一真源）：

| # | 库 | 磁盘（受管根下） | 判定 | 行为 |
|---|---|---|---|---|
| 1 | 有条目 | 无文件 | 条目**悬空**（文件被移走/盘未挂载/根被换） | 标为「文件缺失」并**在条目与本集两级可见**；**不删条目、不删剧集**；有来源可重取则给「重新缓存」入口 |
| 2 | 无条目 | 有文件 | 目录新增内容 | **按路径幂等登记为条目**（video / photo / audio / file），**只入条目、不入剧集**（不自动成剧、不自动归集） |
| 3 | 都有 | 都有 | 一致 | 不动（对账结果 = 0 变更，不产生 UI 噪音） |

**结论（不再反问）**：

- 第 2 支（库没有文件有）**只建条目、不进剧集库** —— 由「受管根 = 纳管字节，
  成剧是另一条独立链路（组键/归并/人工合并）」唯一确定，故这一支不涉及剧集。
- **但第 1 支必然涉及剧集**：`media_episode` 通过条目挂到剧集，条目悬空会让该集在
  剧集里表现为「无字节」⇒ 剧集页出现「缓存缺失 N 集」（`SeriesDetail.tsx:854`
  `series-recache-missing`）与缺集灰条（`:875` `series-gap-bar`）。
  ⇒ 「不涉剧集」只对第 2 支成立；第 1 支必须在剧集层有可见表达，
  否则用户看到的是「文件还在列表里，点播放却失败」。
- **切换主目录 ≠ 条目失去字节**（2026-10-28 更正，见裁定 C）：旧根只要仍在受管根集合内，
  其下条目的字节依然可达 ⇒ **不该判缺失**。本段初版写的「主根切换 = 旧根下条目全部落入
  第 1 支」是**判据错**——把「主目录是谁」当成了缺失判定的依据，
  而缺失只在「该位置不再被任何受管根覆盖」时才成立。

## 修复方向（未实施；≥2 实质选项 + 1 个「不做」）

### 选项 A（推荐）：主操作改「目录管理」，落到受管根集合的登记与管理

> 术语按 2026-10-28 更正：不是单次的「添加目录」按钮，而是**目录管理**
> （登记 / 移除 / 设主目录 / 手动对账同一处）。

- 文案 `media.importDir` → 「目录管理」（zh/en 同步）；主操作点击后打开目录管理面板：
  列出 `listManagedRoots`（`api/tg.ts:836`）、新增走 `addManagedRoot`（`:843`）、
  移除走删除端点、设主目录走 `/roots/primary`（`:861`）、底部「完成 / 重新对账」
  按钮按裁定 B 触发一次对账。
- `涉及:` `ContextBarFilesActions.tsx`（1 处文案 + handler）、`MediaLibraryPanel.tsx`
  （`filesActions.import` 实现改为打开目录管理 + 刷新）、新增目录管理面板组件、
  `zh-CN.json` / `en-US.json`。
- `量化:` 主操作 1 个、受管根列表 1 处、对账按钮 1 个；现有「扫描并登记勾选文件」
  降级为次级入口。
- `回归风险:` 中 —— 与下载根「唯一字节出口」判据（下载单根 / 管理多根，越界 403）
  相邻，需确认登记后不产生重复条目（按路径幂等）。
- `后果:` 目录被记住且可管理；新增文件在启动时或用户点「完成」时被看到；
  「导入」与「目录管理」两种能力各自名实相符。

### 选项 B：保留「导入目录」为文件级导入，另设「目录管理」为受管根

- 两个入口并存：主操作「目录管理」（受管根集合），次级「导入文件」（现有 ImportDialog）。
- `涉及:` 同上 + 动作组多一颗按钮（宽度回到 BUG-451 的 358px 量级，需重测重叠）。
- `量化:` 动作组 4 → 5。
- `回归风险:` 中 —— 上下文栏窄窗重叠（BUG-451）需重跑
  `verify/verify_bug451_ctxbar_no_overlap.cjs`。
- `后果:` 能力最全，但同一屏两个「把东西弄进来」的入口，需靠文案强区分。

### 选项 C：只改文案，不动链路

- 仅把「导入目录」改名「目录管理」，行为仍是扫描 + 勾选导入。
- `涉及:` 2 个 i18n 键。`量化:` 0 逻辑改动。`回归风险:` 低。
- `后果:` **名字与行为仍然不一致** —— 改名后用户点进去发现目录没被记住，
  等于把 BUG 从「名字错」换成「名字骗人」。不推荐。

### 选项 D：不做

- `涉及:` 无。`量化:` 0。`回归风险:` 无。
- `后果:` 文件管理永远只能靠反复手工导入来吸收本地目录内容。

## 裁定 A：入库时机（2026-10-27 用户拍板）

用户原话：「**入库时机是什么？TG 点击缓存 → 数据入库 → 文件加入下载，图片开始缓存 →
完成。数据入库后就可以查看整个数据了。**」

⇒ **入库 = 数据产生那一刻（元数据先行，字节后到），不存在独立的「扫描入库」阶段。**
原 ① ② ③ 三选项均不采用，按下列时序真源落地：

| 来源 | 入库时点 | 入库内容 | 可查看性 |
|---|---|---|---|
| TG（点击缓存） | **点击那一刻**即登记条目 | 条目元数据（标题 / 来源 / 分组） | 入库即可在文件管理看到整条数据；字节随下载/图片缓存完成后补齐（asset 级：图完成 → 图出现） |
| 本地（目录管理 → 登记/确认） | **用户显式点击「完成 / 对账」时**跑一次对账（见裁定 B），命中第 2 支（库没有文件有）⇒ 建条目、不入剧集 | 按路径幂等登记 | 对账完成即可见，无需再走 ImportDialog |
| 后续变化（新增/删除/换根/移动） | **只对账时点上跑**，见裁定 B | 第 1/2/3 支各自行为 | —— |

**判据（写死）**：

1. **「可见」只依赖条目，不依赖字节** —— 条目一入库就该出现在列表里；字节缺失用
   缺失态表达（BUG-468 裁定「单向对账 + 缺失可见」），不得用「看不见」表达。
2. **不新增独立的扫描入库任务/端点** —— 目录侧复用对账第 2 支的登记逻辑，
   TG 侧沿用现有点缓存即登记；`importMediaItems` 保留为「导入文件（勾选）」的次级入口。
3. **入库与成剧是两条独立链路**（第 2 支只建条目、不入剧集），成剧仍走组键/归并/人工合并。

## 裁定 B：对账时机与性能红线（2026-10-28 用户拍板）

用户原话：「**时间点之前不是确定过了吗？启动的时候，然后点击完成的时候也扫一次？
这个没必要主动频繁处理。整体核心都是性能为主要目标。**」

⇒ 对账**只有两个时点**，其余一律不跑（性能红线）：

| # | 时点 | 触发方式 | 范围 |
|---|---|---|---|
| 1 | **启动** | 系统自动（每次启动一次） | 全部受管根 |
| 2 | **用户显式点击** | 目录管理面板里的「完成 / 重新对账」按钮 | 当前操作的根（或全量，由用户在该面板选择） |

**判据（写死）**：

1. **系统不做任何自动的额外对账** —— 下载完成、缓存完成、切换视图/主目录、
   定时轮询、文件系统监听（watch）**均不触发**对账。对账成本随条目与目录规模线性增长，
   而上述事件的触发频率不可控 ⇒ 一律禁止。
2. **「添加完却看不到」由时点 2 解决，不由自动扫描解决** —— 用户登记目录后点「完成」
   即跑一次；不点则等到下次启动。这比「登记即后台全量扫」省一次不可预期的大规模 IO，
   且行为对用户可预测。
3. **对账必须可中断 / 不阻塞交互**：后台跑、进度走状态栏；同一时刻只允许一个对账任务
   （单飞，与下载单飞模型一致）。
4. **没有文件监听** —— 不引入 `notify`/inotify 类实时监听（性能与跨平台风险的双重成本），
   目录内容变化只在时点 1 / 2 被看到。

## 裁定 C：主目录切换与缺失判定（2026-10-28 定稿：采纳 ②）

**结论：切主目录只改「新字节往哪落」，不动条目归属、不触发对账；缺失判定只挂
「该位置是否仍被某个受管根覆盖」，不挂「主目录是谁」。**

1. **主目录 ≠ 归属。** 主目录（`/api/fs/roots/primary`，`api/tg.ts:861`）只决定
   **新增字节的落点**（下载出口）与库根派生；条目的身份与归属由 `source + ref`
   与受管根覆盖决定（BUG-468 裁定：真源 = 条目 + 来源坐标，路径只是可失效属性）
   ⇒ 换主目录后旧条目照旧有效、照旧可达。
2. **缺失判定的唯一依据**：文件所在位置**是否仍被任一受管根覆盖**。
   - 旧根仍在受管集合（哪怕不再是主目录）⇒ **不判缺失、不进第 1 支**；
   - 旧根被**移除**出受管集合 ⇒ 该根下条目进入第 1 支（标「文件缺失」、
     条目与本集两级可见；有来源给「重新缓存」，无来源明说「无法取回」）。
3. **对账时机服从裁定 B**：切主目录**不触发**对账（性能红线：系统不自动对账）；
   「移除根」是用户显式点击 ⇒ 按裁定 B 时点 2 跑一次对账并给结果摘要
   （N 条失去字节 / 其中 M 条可重取）。
4. **UI 表达分离**：设主目录的提示只说「新内容将落到 X」，不得暗示旧内容失效；
   **移除根**才是破坏性动作 ⇒ 需二次确认 + 结果摘要（「该根下 N 条将失去字节」）。
5. **排除项**：①（切根即全量对账）不采纳 —— 与裁定 B 冲突，且会制造
   「切个主目录把库搞坏」这个本不该存在的错误状态；③ 的「按根分组显示」
   可作为呈现增强另议，但**缺失判定一律按本裁定第 2 条**，不因分组而豁免。
