# BUG-161: 验收/诊断脚本默认直连生产 orig-tg(9877) 写入用户真实库且无守卫、不清理 —— 媒体库留下 `DiagCard_<ms>` 孤儿剧集残留

- 状态: fixed
- 发现日期: 2026-09-23
- 模块: build
- 严重程度: high
- 档位: standard

## 现象

用户在媒体库看到「没有正确标题/内容」的条目，原话：

> 「还有入库数据怎么没有正确的标题和内容是 `DiagCard_<ts>` 这种?」

取证确认 `DiagCard_<ts>` 是**剧集墙上的一张 0 分集孤儿剧集卡**
（`media_series` 第 `<series_id>` 行：`kind='series'`、`episode_count=0`、`source_key=NULL`、
无标签、`description=NULL`），它出现在媒体库剧集墙，用户可见。

**全仓 grep `DiagCard` 零命中** —— 它**不是产品代码生成的**，没有任何代码路径会产出该标题。

## 根因

### 0. 先纠正「真实库在哪」——否则取证会看错库

运行中的生产实例是 `download-engine/target/release/orig-tg.exe`（监听 `127.0.0.1:9877`，
本机 PID 40836），它背后是 **Tauri 壳 `app_data_dir()` 下的库**：

```
<用户目录>\AppData\Roaming\com.origadmin.orighub\tg\store.db   ← 本例真库（含 DiagCard）
```

而 `%LocalAppData%\OrigHub\tg\store.db` 是 **daemon（download-engine）侧**的数据目录
（`download-engine/crates/orig-daemon/src/state.rs:313 tg_data_dir()` → `%LocalAppData%\OrigHub`），
本例它的 `media_item` / `media_series` **为空**。两者是不同的库，**只按 Brief 里写的
`%LocalAppData%` 取证会一无所获**。定位真库的可靠办法：`Get-NetTCPConnection … LocalPort 9877`
拿 PID → 该进程所属组件 → 其数据目录；或按标题串在磁盘上全文检索 `*.db`（本例由
「在 `%APPDATA%` 与仓库内逐字节搜 `DiagCard_<ts>`」精确定位）。

### 1. 残留由一个「建了不删」的验收/诊断脚本产生

`tauri-shell/verify/*.cjs` 默认把后端地址指向**生产实例** 9877：

- `shot_clear_center.cjs:56` / `shot_item_cache.cjs:44` / `shot_media_delete.cjs:49` /
  `shot_media_tags.cjs:49`：`const API = 'http://127.0.0.1:9877'`（硬编码生产）。
- `shot_series_text_edit.cjs:49`：`process.env.API_BASE || 'http://127.0.0.1:9877'`。
- `verify_merge_frontend.cjs:45`、`verify_series_not_found.cjs:43`：
  `process.env.ORIG_MEDIA_API || 'http://127.0.0.1:9877'`。

这些脚本会向生产实例 `POST /api/media/series` 建**真实**剧集（例如
`verify_series_not_found.cjs:187` 建 `VerifySeriesNF_${Date.now()}`）。清理只写在 `finally`
里（如 `verify_series_not_found.cjs:273-281`）—— 脚本被 kill / 崩溃未走 `finally`、
或某次临时诊断脚本**根本不清理**时，残留即落地。`DiagCard_<ms>` 属后者：一个
`DiagCard_${Date.now()}` 形态的临时诊断，建完未删。

旁证：用户看到的 `<ts>`（= `DiagCard` 的 ms 戳，落库为
`created_at=<ts>`（秒）→ **2026-09-23 23:35:10 本机**）与 `VerifySeriesNF_` 的实跑值
`<ts>`（约 +9.4 分钟）同批，均指向同一段时间窗内的本机验收/诊断脚本。

### 2. 全链条缺守卫

没有任何机制阻止脚本对生产实例写入；`finally` 清理对被 kill / 崩溃 / 未走 finally 的路径无效。
「删除/写任何东西要显式授权」这条项目硬规则在 verify 脚本层**没有落到代码**。

## 复现

只读取证（不删任何数据）——列出疑似测试残留的剧集：

```sh
# 读真实库（复制到临时文件后只读打开，保证零写入）
python - <<'PY'
import sqlite3, os, shutil, tempfile
src = os.path.join(os.environ['APPDATA'], 'com.origadmin.orighub', 'tg', 'store.db')
tmp = os.path.join(tempfile.gettempdir(), 'orighub_live_ro.db'); shutil.copy2(src, tmp)
cur = sqlite3.connect(f'file:{tmp}?mode=ro', uri=True).cursor()
for r in cur.execute("select id,title,created_at from media_series order by id"):
    print(r)
PY
```

或经运行中实例（只读 GET）：

```sh
curl -s http://127.0.0.1:9877/api/media/series | python -c "import sys,json; print([s['title'] for s in json.load(sys.stdin)['items']])"
# -> ['Big Buck Bunny · 码率阶梯', 'Sintel · 码率阶梯', 'Jellyfish · 码率阶梯', '自然风光合集', '城市与科技合集',
#     '<一条剧名 caption> …', 'DiagCard_<ts>']   ← 末项即残留
```

修复后新增的守卫可直接复现拦截：

```sh
node -e "require('./verify/lib/sandbox.cjs').guardWrites('x','http://127.0.0.1:9877')"; echo "exit=$?"
# -> 打印隔离实例指引，exit=2（拒绝写生产实例）
```

## 修复

新增 `tauri-shell/verify/lib/sandbox.cjs`（三道防线）并把**所有会写后端的** verify 脚本接入：

1. **`guardWrites(scriptName, base)`**：目标为生产实例（回环地址 + 9877）时**默认拒绝执行**
   （`exit 2`）并打印隔离实例的拉起用法；确需在生产上写验证必须显式
   `ORIG_VERIFY_ALLOW_PROD_WRITES=1`（对应项目规则「删除/写任何东西要显式授权」）。
   接入脚本（7 个）：`shot_clear_center` / `shot_item_cache` / `shot_media_delete` /
   `shot_media_tags` / `shot_series_text_edit` / `verify_merge_frontend` / `verify_series_not_found`。
2. **`trackCleanup(fn)` + `installCleanup()`**：进程钩子覆盖**所有**退出路径
   （`beforeExit` 可跑异步 / `SIGINT` / `SIGTERM` / `uncaughtException` / `unhandledRejection`），
   不再依赖脚本作者手写 `finally`。
3. **`createTempSeries(base, prefix)`**：建临时剧集的**同时**自动登记删除，
   「建了不删」在 API 上不可表达。
4. 另附只读残留清点 `listResidue(base)` 与 `sweepResidue(base,{apply})`
   （`apply` 亦需 `ORIG_VERIFY_ALLOW_PROD_WRITES=1` 才真删）。

文档：`tauri-shell/verify/README.md` 新增 **§4 污染防线**（含隔离实例拉起示例）。

> 未采纳「服务端按标题前缀拦写」方案：那会把判据写死进产品，且对任意临时脚本无效；
> 治本是「脚本**默认不写生产实例**」+「无法跳过清理」。

## 关联

- **BUG-154**（条目 title 为空或原始文件名）：`routes.rs:911-922` 已把「无 caption 时不再
  用落盘文件名当标题」。**运行中的 `target/release/orig-tg.exe` 构建于 2026-09-23 03:22，
  早于该修复（BUG-154.md 落于 22:30）—— 即部署的 9877 二进制是旧的**，故本机仍能在
  2026-09-23 22:39 之后入库出 `<hash>--…` 形态标题。建议重建/重启生产二进制后复核。
- **BUG-157 / BUG-158**（污染门禁 / git 钩子）：同属「流程防线」类，但门禁只管**提交内容**，
  管不到「脚本往用户真实库写数据」——本 BUG 补上后者。
- **BUG-023 / BUG-135 教训**：会真删/真写的验证必须「独立端口 + 唯一库名 + mock 构建」
  （`download-engine/verify/verify_bug_135_136.py` 头部的拉起示例）。

### 备注：为何「标题退化」不是新的产品缺陷

用户「没有正确标题/内容」的另一半观感来自一票 `photo--…` / `doc--…` / `TG 图片 #…`
条目。逐条核对真实库后排除其为独立缺陷：

- 这些条目的 `media_message.caption` 实测为 **NULL**（消息本身没有 caption）→ 落盘名/占位
  兜底**属预期**，不是「有 caption 却被丢掉」。
- 其中 `<hash>--<chat>-<id>` 形态是 **BUG-154 修复前的历史行**（且因
  `upsert` 用 `COALESCE(NULLIF(excluded.title,''), title)`，空标题不会覆盖旧值，重缓存也
  不会自动洗白）——属**历史数据**，非当前代码缺陷；根治需一次性 backfill（另行评估）。
