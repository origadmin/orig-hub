# BUG-085: TG 全量缓存任务端点被轮询时读 SQLite，且每次多算一条无用 count

- 状态: open
- 发现日期: 2026-09-20
- 模块: engine
- 严重程度: low

## 现象

BUG-077 引入的只读聚合端点 `/api/activity`（前端 5s 轮询）在 `tg_enabled` 时会打到
`/api/tg/cache/tasks/all`。该端点**每次调用两次 SQLite**：`list_cache_tasks(500)` +
`count_cache_tasks()`（`orig-tg/src/routes.rs:986-1005`）。

其中 `count_cache_tasks()` 的结果**没人用** —— daemon 侧的 `TgTasksPayload`
（`download-engine/crates/orig-daemon/src/activity.rs:157-161`）根本不消费 `counts` 字段。
等于每次轮询白跑一条全表 count。

## 根因

同一文件里存在两条技术路线，对比可见这不是疏忽而是缺口：

- `/api/tg/cache/tasks`（`routes.rs:972-982`）明写「读路径 O(1)：服务内存快照，不碰 SQLite」
  「这是前端 1s 轮询的高频端点」—— AGENTS.md §5 第 52 行「被轮询的读端点不许碰 DB」在这里
  是被认真执行过的；
- `/api/tg/cache/tasks/all`（`routes.rs:986-1005`）则直接查库。

BUG-077 用不了内存端点，是因为两者契约不同：内存端点的设计裁定是**只返回一条**
（`routes.rs:965-967`，单飞契约），而聚合视图的 `is_in_transit`
（`activity.rs:375-376`）明确要把 `failed|interrupted` 一并显示——「必须让用户看见才能推进」，
一条不够。`/tasks/:id` 又要先有 id。

**根因是 TG 侧缺一个「内存快照版全量端点」，不是 daemon 侧调用错了。**

## 复现

1. 启动 daemon（9876）与 orig-tg（9877），`[tg] enabled=true`；
2. `curl "http://127.0.0.1:9876/api/activity?scope=active"`；
3. 每次请求都会在 TG 侧产生 2 次 SQLite 查询，其中 1 次（count）结果被丢弃。

代码审读即可确认：`routes.rs:996-1003` 计算 `counts`，`activity.rs:157-161` 不定义该字段。

## 修复

**未修（follow-up，不阻塞 BUG-077 交付）**。已在 `activity.rs:305` 上方留豁免注释，
标明这是对 AGENTS.md §5 第 52 行的已知偏离及理由，避免后人误判为疏忽。

现有缓解（因此定级 low）：轮询周期 5s 而非 1s；仅 `tg_enabled` 时才调用；前端「有活才轮」，
静默期 0 次请求；`no_proxy()` + 2s connect / 4s 超时，不会挂死。
