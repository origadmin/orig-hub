# BUG-229: 非 1x 倍速无条件切 FRC 转码流 ⇒ 浏览器对 fMP4 代理发起乱序 range 风暴 + 全片转码缓存，用户报「同时几十个 request、缓存差不多整部、不是前面优先」

- 状态: fixed
- 发现日期: 2026-10-09
- 模块: engine+shell
- 严重程度: high

## 现象（用户报，实测复现）

2x 播放 6.7 分钟条目（item 673）：30s 内 98 个媒体请求打到 `/api/media/items/673/stream?speed=2`
（**每秒峰值 69**），Range 起点乱序（0 → 1MB → 64KB → 2.6MB …），缓冲达 **133.7s / 201.6s = 66% 全片**；
转码缓存把整片 persist 落盘。用户原话：「同时请求几十个 request，前面的没回来后面的又卡住，
缓存了差不多整部片子——严重逻辑问题」。

## 根因（CDP Network domain 实测，`tauri-shell/verify/_probe_reqstorm.cjs`）

两级叠加：

1. **shell**：`VideoPlayer.tsx` 倍速换档 effect 中
   `rateSrc = playbackRate === 1 ? null : streamUrlAtRate(compat, playbackRate)`
   —— 只要倍速 ≠1 就**无条件**切 FRC 服务端转码流，与源是否可直解无关。item 673（HEVC，
   本机 Edge 直解流畅，BUG-224 已证）在 2x 下也被迫走转码。
2. **engine**：FRC persist 产物是 fMP4（`empty_moov+frag_keyframe`）。Chromium 对带
   `accept-ranges` 的 fMP4 做 moof 边界探测式 range 请求（69 req/s 乱序），且 FRC 产物
   没有内容时长索引 ⇒ 浏览器预读 66% 全片才能稳定播放。

对照组（同条目 1x 直解 `/raw`，普通 mp4 moov 在尾）：20s 仅 70 请求（双读头：顺序数据头
+ 尾部 moov 索引头），Range 到 36MB / 523MB = **7%**，顺序推进。

## 修复

`tauri-shell/src/components/media/VideoPlayer.tsx`：

1. 倍速换档只发生在**已在兼容流上**的源（真不可解、走 FRC）：
   `onCompat = usingCompat || baseCompatRef.current || activeSrc.includes('/stream')`，
   可直解源保持原 src，倍速交给 `<video>.playbackRate`（浏览器原生行为）；
2. `applyPrefs` 播放速率条件同步改为 `usingCompat && hasVideoTrack`（原先「存在 compatSrc
   即钳 1」会让直解倍速失效）；
3. unsupported 切兼容流时 `activeContentSpeedRef`/`contentOffsetRef` 显式归位（兼容流
   播放速率恒 1，直解高倍速中切流时 contentTime 换算不得带旧速率）。

engine 侧此前已落地（同轮）：磁盘预算 LRU（`ORIG_TG_PROXY_MAX_BYTES`，默认 2GiB，按 mtime
淘汰 `.mp4` 不碰 `.part`）、4x 降编码成本（ultrafast + 降采样）、单飞卡死超时、冷启动兼容流
`Accept-Ranges` 广播。本修复后非 1x 可直解源**完全不产生转码缓存**，engine 缓存只服务真不可解源。

## 验收证据

探针 `tauri-shell/verify/_probe_reqstorm.cjs`（真实 viewer 组件 + 真实倍速菜单，CDP Network
domain 全量抓取），修复前 → 修复后（同条目 673、同 30s 窗口）：

| 指标 | 修复前（2x→FRC） | 修复后（2x→直解） |
| --- | --- | --- |
| /stream 请求 | 95/98 | **0** |
| 瞬时请求峰值 | 69 req/s | 14 req/s |
| 缓冲推进 | 133.7s/201.6s = 66% 全片 | 47.5s/403.1s = 12% |
| 媒体时长 | 201.6s（FRC 压缩） | 403.1s（原生） |
| 数据流量 | ≈转码全片 | 471×128KB ≈ 60MB/30s = 2MB/s（= 2x 消耗速率，守恒） |

修复后 2x 直解的 471 请求/30s 是 Chromium 对 `playbackRate>1` 的多 reader 预读（128KB 粒度、
数据量守恒、每请求纯本地文件 IO 无服务端状态），与修复前「乱序风暴 + 66% 全片堆积 + 转码
单飞槽占用」有本质区别。

流畅度（`tauri-shell/verify/_probe_app_realrate.cjs`，真实组件）：673 @2x effRate=0.995、
drop 7.8%、srcChanged=false（0 次换源重载）、longtasks=0、bufAhead 38.8s。

类型检查 `tsc --noEmit` 通过。
