# BUG-166: 「解码吃力」把数据晚到型丢帧误判为解码吞吐不足 —— 无可见卡顿却常驻误导提示

- 状态: fixed
- 发现日期: 2026-09-24
- 模块: shell
- 严重程度: low
- 档位: standard

## 现象

用户报「播放时还会出现『解码吃力：画面在丢帧，调低播放速度会明显更流畅』，出现原因不明，
因为暂时没看到卡顿」。

`droppedVideoFrames` 这个指标**分不清两种成因**：

| 成因 | 机制 | 可见性 | 「调低速度」是否对症 |
|---|---|---|---|
| 解码吞吐不足 | 解码器跟不上帧率（真吃力） | 明显卡顿 | 对症 |
| **数据晚到** | 供给被抢（同管道其他流量/在线节流），帧到得晚被整批弃掉 | **几乎不可见** | **不对症** |

数据晚到型丢帧可以在视觉无感知的速率下持续超过判据阈值（>3 帧/秒 持续 2s），
于是提示在「没看到卡顿」时出现，且建议的动作（调低倍速）根本治不了晚到。

BUG-053 的迟滞改造解决了「闩锁不恢复」，但**没有处理成因混淆**：`waiting`/`stalled`
不在基线重置事件里（stall 恢复后的补帧爆发全被算成新丢帧），且判定不关心缓冲健康——
供给不足期与供给充足期一视同仁。

## 修复

`tauri-shell/src/lib/decodeHealth.ts` 两条守卫：

1. `REBASE_EVENTS` 追加 `waiting` / `stalled`：stall 恢复瞬间重置基线，
   补帧爆发的旧账不计入新丢帧；
2. 判定前置「数据供给健康」：缓冲领先播放位置 `aheadSec < DATA_AHEAD_MIN(=2s)` 时
   **只跟基线、清空连击、绝不置位**——此刻的丢帧是晚到，不是解码慢；
   供给充足（≥2s 领先）仍持续丢帧才允许判「解码吃力」（此时文案才是对症的）。

## 验收证据

三阶段行为测试（真实应用内 CDP 驱动，合成 `getVideoPlaybackQuality` 计数 +
`Network.emulateNetworkConditions` 真实节流，判据**可判绿也可判红**）：

```
P1_tooth(供给充足+丢帧应出现):   toast=true   ahead=15.79 dropped=180   —— 验牙：真吃力仍能报
P2_recover(撤丢帧应消失):        toast=false  ahead=13.24 dropped=0     —— 迟滞恢复不回归
P3_starve(断供+丢帧不应出现):    toast=false  ahead=-0.63 dropped=1025  —— 晚到型误报被抑制
SELF-TEST PASS（可判绿也可判红）
```

P3 即用户的误报场景：缓冲已断供（ahead<0）而丢帧计数爆涨 1025，旧实现必然置位，
修复后正确保持沉默。另：健康播放回归实测全程 `dropped=0`（ahead 峰值 18s），
提示不再无中生有。

跨机器可核引用（入库路径）：`tauri-shell/src/lib/decodeHealth.ts`
（`REBASE_EVENTS` + `DATA_AHEAD_MIN` 守卫）、`tauri-shell/verify/lib/cdp.cjs` 复现脚本。
