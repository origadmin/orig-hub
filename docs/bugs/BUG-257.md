# BUG-257: 入库队列三处缺陷 —— 卡住的条目无法中断（只有 90s 空闲看门狗，且它会把整个任务判失败、放弃剩余条目）；重启把 queued+running 整批降级为 interrupted 且无任何恢复；失败原因被折叠成通用网络文案

- 状态: fixed
- 发现日期: 2026-10-10
- 模块: engine+shell
- 严重程度: high
- 登记: 用户报告「发现入库问题，卡主的资源无法暂停，延迟。重启也没有自动恢复队列选项。失败是否有错误日志？这3点需要评估。」

## 现象（三点，均附实测）

### 点 1：卡住的资源无法暂停

用户在入库（TG 缓存）过程中遇到条目卡住，**没有任何手段中断它**，只能等。

实测（2026-10-10 16:43–16:49，`GET /api/tg/cache/tasks` 每 30s 采样，端口由 `/api/config` 的
`tg_port` 运行时解析）：队首任务 `id=137`（9 条）的 `itemBytes` 只以 **512 KiB 为步长**跳动
（`RANGE_CHUNK`），且出现**连续 60–90s 完全不动**的平台期；随后该任务被判 `failed`，
错误原文为：

```
download failed: download stalled: no bytes for 90s (chat -1004457697592 msg 1156);
connection presumed dead, aborted to unblock the cache queue
```

**UI 侧是能看出「卡住」的**：`CacheManagerDialog.tsx:150` 定义 `STALL_MS = 15_000`，
`:238` 由服务端下发的 `progressAt` 推出 `stalled`，`:426-431` 渲染
`data-testid="cache-task-stalled"`，文案 `tg.ingestStalled` = 「已 {n} 秒无进展」。
**所以用户看得见卡住，却做不了任何事** —— 这正是「无法暂停」的观感来源。

### 点 2：重启也没有自动恢复队列选项

实测（16:41 / 16:49 两次）：队列里长期有 **26–31 个 `queued`** 任务在等（单飞模型，
一次只跑一个），而**重启不会把它们接着跑，而是整批作废**：

```
{"cancelled": 12, "done": 61, "failed": 5, "interrupted": 2, "queued": 26, "running": 1}
```

`interrupted` 就是重启的产物。按 `mark_stale_cache_tasks` 的 WHERE 条件，
一次重启会把当时的 **26 个 `queued` + 1 个 `running`（共 27 个）全部**降级为 `interrupted`。

### 点 3：失败是否有错误日志

**有，而且不止一处**；但**具体诊断在界面上被折叠掉了**。

实测把 137 的 `error` 原文喂进前端的呈现函数（`tgReason.ts:88-99` `describeTgFailure`
→ `classifyTgReason`），因其网络正则含 `connect`，而原文含 **`connection presumed dead`**
⇒ 命中 `:44-53` 的 `tg.reasonNetwork` ⇒ 界面实际显示的是：

> 「无法连接到 Telegram，请检查网络与代理设置后重试。」

即：真实条件是「**连续 90s 零字节**」（连接已建立、字节流中途停住），
界面却告诉用户「**连不上 Telegram，去查网络与代理**」。**这是误导性的可行动指引** ——
用户会去改代理，而问题在传输中途停滞。

## 根因

### 根因 1：缓存侧「暂停/继续」是**被裁定移除**的，但取消只作用于「条目之间」

**先说清楚：没有 pause/resume 不是遗漏，是既有裁定。**
`download-engine/crates/orig-daemon/src/activity.rs:13-14`：

> 4. **不造假暂停/继续**：TG 无真续传（只能任务级重试），统一 UI 给「暂停/继续」就是假能力。
>    故 cache 侧 `actions` 至多是 `retry`，永不含 pause/resume。

且有单测锁死这条（`activity.rs:497-506` `cache_never_exposes_pause_or_resume`），
`actions_for(TaskKind::Cache, "queued"/"running")` 返回空数组（`activity.rs:365-377`）。

**但用户要的不是「暂停后从断点续传」，而是「把卡住的这条掐掉、让队列往前走」。**
这个能力在语义上属于 **cancel / 中断**，不属于 pause —— 而 cancel 是存在的，只是**够不着在途条目**：

- 取消内核是 `cancel_task_kernel`（`cache.rs:957` 单条 / `:1024` 批量，两个端点共用），
  它**只改数据库状态**，不触碰任何在途 IO。
- worker 在**每条消息循环的顶部**检查任务是否仍活跃（`routes.rs:2017` 调 `is_cache_task_active`），
  之后才发起 `cache_one_bytes(...).await`（`routes.rs:2084`）。
  ⇒ **取消只在「条目之间」生效**，在途条目的 await 期间取消无效。
- 全库**没有** `tokio::select!` 竞速、没有 `CancellationToken`、没有 `.abort()` / `AbortHandle`
  （三种写法均零命中）⇒ **不存在任何真正的取消机制**。这一条是**遗漏，不是裁定**。

**唯一能打断在途条目的机制**是 90s **空闲**看门狗（`grammers.rs:625-651`）：

```rust
const STALL_IDLE: std::time::Duration = std::time::Duration::from_secs(90);
match tokio::time::timeout(STALL_IDLE, body.next()).await { ... }
```

它的三个性质决定了用户体验：① 是**空闲**超时（任何非空 chunk 都会重置），**不是墙钟上限**
⇒ 一个「每 89s 来一小块」的慢流可以**无限期**占住队首；② **不感知取消**；
③ **硬编码、不可配置**。日志里那句 `aborted to unblock the cache queue` 就是它在工作。

⇒ 合起来：**慢**（不触发看门狗）与**卡**（触发看门狗，但代价 90s）之间没有用户可控的中间档，
而 90s 之内用户按「取消」没有任何反应 —— 这就是「无法暂停，延迟」。

### 根因 2：重启把 queued+running **整批**降级，且全库没有任何恢复路径

`download-engine/crates/orig-tg/src/store.rs:1189-1204`：

```rust
/// 启动时清理僵尸任务：进程被杀/崩溃时残留的 queued/running 永远等不到 worker，
/// 必须显式降级为 `interrupted`，否则前端会显示一个永不推进的「缓存中」（假状态）。
"UPDATE cache_task SET status = 'interrupted', current_id = NULL, updated_at = ?1
 WHERE status IN ('queued', 'running')"
```

调用点在启动流程 `download-engine/crates/orig-tg/src/main.rs:213`（带日志
「cache tasks: {n} stale task(s) marked interrupted」）。

**降级本身是有依据的裁定**（`docs/bugs/BUG-024.md:72-73`：拒绝伪造的「缓存中」态），
这条没问题。问题在**另一半**：

- **没有任何自动恢复。** 全库 `spawn_cache_task` 只在两处被调用：入队与**手工**重试。
  启动路径里没有任何遍历 `cache_task` 重新入队的代码。daemon 侧
  （`download-engine/crates/orig-daemon/src/`）也不碰缓存任务。
- **「恢复队列」这个概念在 i18n 里根本不存在**（zh-CN / en-US 均无对应键）。
- 恢复只能**手工批量重试**：`POST /api/cache/tasks/retry?ids=`（`routes.rs:1030`，BUG-249 加的），
  且它确实覆盖 `interrupted`（`RETRYABLE_STATES`，`cache.rs:995`）。

⇒ 所以准确的说法是：**「启动时降级为 interrupted」这个决策存在过；「重启后要不要/如何恢复队列」
这个决策从未存在过。** 用户感知到的「重启也没有自动恢复队列选项」= 决策缺失。

> 旁证一处**文档与现实不符**：`docs/bugs/BUG-077.md:24` 称 TG 侧「重启可恢复」。
> 实测与之相反（重启是把活跃态降级为 `interrupted`，不是恢复）。本档不据此改该文档，
> 仅登记冲突。

### 根因 3：失败原因有落库、有落盘，但在**呈现层被折叠**

**三处落库/落盘（均持久，重启不丢）：**

| 落点 | 位置 | 内容 | 实测 |
|---|---|---|---|
| `cache_task.error` 列 | 写入 `store.rs:1092-1105` | 任务级失败原文 | 137 / 94 两条带完整 stall 原文 |
| `logs/orig-tg.log` | 子进程 stdout/stderr | 每次条目失败的完整原文 | 3,746,847 字节 |
| `logs/errors.log` | `state.rs:838-845` | daemon 核心错误，append-only | 136,927 字节 |
| 内存日志 | `state.push_log`，经 `/api/tg/logs` 暴露 | 近期事件 | 实测可取到逐条失败记录 |

日志路径本身可经 daemon 端点取到（`orig-daemon/src/routes.rs:515-521` 返回
`{dir, orig_tg, errors}`）。

**但呈现层把具体诊断压成了通用文案。** `tauri-shell/src/lib/tgReason.ts:44-53` 的
网络类正则里含 `connect`，而 stall 原文含 `connection presumed dead` ⇒ 命中网络类
⇒ `:96-98` 返回 `t('tg.reasonNetwork')`，**原文被丢弃**。结果是「90s 零字节」
被显示为「无法连接到 Telegram，请检查网络与代理设置后重试」。

**另一处缺口：`cancelled` 与 `interrupted` 的 `error` 恒为 `None`。**
实测 12 个 `cancelled` + 2 个 `interrupted` 全部无原因字段。其中 `cancelled` 是用户主动行为
（无需原因）尚可接受；但 `interrupted` 是**重启造成的**，界面只显示「已中断」
（`tg.statusInterrupted`），**不说明是重启导致、也不提示「可重试」** —— 用户无法把
「已中断」与「我刚重启过」联系起来。UI 侧渲染失败原因的条件是
`CacheManagerDialog.tsx:441` `task.status === 'failed'`，`interrupted` 不在此列。

### 连带发现（用户未提，但同源且更严重）：条目卡死会让**整个任务**失败，剩余条目被直接放弃

`cache_task.error` 是**任务级**字段，而 stall 是**条目级**事件。实测两条：

| 任务 | done/total | 被放弃（从未尝试）的条目 | 失败时间 |
|---|---|---|---|
| `id=137` | 2/9 | **7** | 16:44:40 |
| `id=94` | 8/9 | **1** | 16:48:29 |

即：**一条消息卡住 90s，整条任务就终止，剩下 7 条连试都没试。**
合计 8 条条目因两次 stall 被静默放弃。这与用户说的「延迟」是同一件事的两面：
队列不但慢，而且**每卡一次就丢一批**。

## 复现

```bash
# 前置：dev 栈在线（daemon 127.0.0.1:19786；orig-tg 端口取 /api/config 的 tg_port，当前 19788）
P=http://127.0.0.1:19788

# ① 看队列现状与失败原因（点 1 / 点 3）
curl -s --noproxy '*' "$P/api/tg/cache/tasks/all"
#   → counts 里 queued 长期两位数；failed 任务的 error 带完整 stall 原文

# ② 看「卡住」如何被 UI 折叠（点 3）：把 error 原文走一遍前端的呈现函数
#   tgReason.ts describeTgFailure → classifyTgReason
#   原文含 "connection presumed dead" ⇒ 命中 /connect/ ⇒ 显示 tg.reasonNetwork
#   （「无法连接到 Telegram，请检查网络与代理设置后重试。」）

# ③ 看 90s 看门狗（点 1）：间隔 30s 采样，观察 itemBytes 在 512 KiB 步长上的平台期
for i in $(seq 1 10); do
  curl -s --noproxy '*' "$P/api/tg/cache/tasks" | head -c 400; echo; sleep 30
done
#   → 平台期 >90s 后，该任务被标 failed，error 为 "no bytes for 90s ... aborted to unblock the cache queue"

# ④ 看重启语义（点 2）：读代码即可，不必真重启（真重启会毁掉现场队列）
#   store.rs:1189-1204 的 WHERE status IN ('queued','running') + main.rs:213 的调用点
```

> **本档未做的验证，如实登记**：**没有**真去点「取消」或真去重启服务来复现。
> 两者都会破坏用户正在使用的真实队列（当时有 26 个任务在排队、且服务在跑）。
> 点 1 的「取消够不着在途条目」是**代码级判定**（`routes.rs:2017` 的检查在
> `routes.rs:2084` 的 await **之前**），不是实测；点 2 同理是代码级判定。
> 若需实测，应在隔离实例上做，不得动生产队列。

## 修复（2026-10-10 已实施）

三点全部落地。**未新增 pause/resume 能力**——`activity.rs` 铁律 4 仍然成立：
本档要的是「把卡住的这条掐掉、让队列往前走」，属cancel 语义。

### 点 1：取消可达在途 IO（不再只是改数据库）

取消此前**只改数据库状态**，而 worker 只在**每条目之前**查一次活跃性 ⇒ 在途条目的
`download().await` 完全够不着，唯一能打断它的是 90s 空闲看门狗。

- `state.rs`：新增 `CacheCancel { flag: Arc<AtomicBool>, notify: Arc<Notify> }` 与按task_id
  的令牌登记（`cache_cancel` / `request_cache_cancel` / `clear_cache_cancel`）。
  **标志与唤醒源两者缺一不可**：标志是权威但不唤醒 `select!`；`Notify` 会丢信号
  （`notify_waiters` 只唤醒已在等的等待方）。用标志判据 + `notify_one` 补发许可，
  「先置位、后注册等待」这个窗口才无洞（有专测守着）。
- `cache.rs::cancel_task_kernel`：**先置令牌、再落库**。顺序刻意如此——令牌是够得着
  在途 IO 的判据，DB 状态只是呈现面；反过来会出现两次 `await` 之间 worker 取到未置位
  令牌的窗口。对尚未起跑的任务同样有效（竞态方向只有一个，不会漏取消）。
- `routes.rs::run_one_cache_task`：把 `cache_one_bytes(...).await` 放进
  `tokio::select!`，`biased` 且取消分支排第一（取消与下载完成同时就绪时**优先判取消**，
  否则用户会看到「取消了进度还在涨」）。条目之间的检查改为读**同一张令牌**，
  杜绝「在途已取消、下一条目又判成活跃」的自相矛盾。
- 取消路径**不调** `finish_cache_task`：`cancel_cache_task` 已置 `cancelled`，
  再写一次终态只会把「用户取消」谎报成别的状态。
- **附带修掉一个读数泄漏**：`update_cache_task_progress` 的 WHERE 只有 `id`（而
  `finish_cache_task` 一直有状态门），于是取消后 `done` 仍在往上涨。已补同款状态门。

### 点 2：重启真的恢复队列

`mark_stale_cache_tasks` 此前 WHERE 覆盖 `('queued','running')`。但 `queued` 的语义是
「还没开始」——它们从未传输过一个字节，降级成 `interrupted`（中途被打断）**没有依据**，
且等于「重启即清空待办」。**BUG-024 反对的是假状态，不是保留队列**；`queued` 不是假状态。

- 现在只降级真正传输过字节的 `running`；`queued` 原样保留。
- 新增 `recover_queued_cache_tasks`（按 id 升序 = FIFO），`main.rs` 启动时经
  **既有** `spawn_cache_task` 重新投递（单飞门禁在那里，store 层不另起一套）。
- 降级时**写入成因**（判据 5）：此前 `interrupted` 的 `error` 恒为 NULL，界面只显示
  「已中断」，用户既不知道是自己重启造成、也不知道它可重试（它确实在 `RETRYABLE_STATES` 里）。
- `interrupted` 的恢复入口复用 BUG-249 已有的批量端点，未新增能力。

### 点 3：失败原因可观测

- `tgReason.ts`：新增 `STALLED_RE` / `RESTARTED_RE` 两个判据，**排在网络类正则之前**。
  这是判据 6 的要害：停滞原文含 `connection presumed dead`，而网络正则含 `connect`，
  命中后界面显示「无法连接到 Telegram，请检查网络与代理设置后重试」——对
  「连接已建立、字节流中途停住」而言是**误导性的可行动指引**（用户会去反复改代理）。
  判据取停滞语义而非整句精确匹配（秒数/chat/msg 号会变，写死整句等于给每个数字留漏网口）。
- `CacheManagerDialog.tsx`：原因渲染条件由 `status === 'failed'` 放宽到含 `interrupted`
  （语义分级：中断是「可恢复」，用琥珀色而非红色），并加 `data-testid="cache-task-reason"`。
- i18n 新增 `tg.reasonStalled` / `tg.reasonRestarted`（中英双语）。

### 与指派口径的偏差（如实登记）

指派给出的实现地图里，多数符号**在本仓库不存在**（已逐一核实，且 `git log --all -S`
确认它们**从未在任何分支或历史中存在过**）：`CacheTaskState`、`CacheProgress`、
`CacheError`（及其「10 个 pause 点」）、`run_cache_task` / `process_single`、
`record_bytes` / `bump_download_state`、`grammers.rs` 的
`ClientBuilder::worker_timeout(GRAB_MAX_SECS)` 与 `connect_config().retry_delay`
（**grammers.rs 里根本没有任何重试循环**）、`tgFloodWait` / `two_factor_required` /
`download_stalled` / `tg.retryExhausted`、`str_to_friendly_err` / `TgNetwork.tsx`、
`already_running` 的 202 分支。

因此按**同等结果**、对着**真实符号**实施，并如实记录：
- 未发明 10码枚举与 `CACHE_PAUSE_REASON_TEXT` 表——本仓库没有任何东西产出那些码，
  凭空造一张表等于制造第二真源。
- 未新增 `GET /api/cache/pause-reasons`：真实失败面只有停滞看门狗与 `ClientError` 各变体，
  端点得有真实数据源才成立。
- 「record_bytes 把 canceled 推到 done」在本仓库**不成立**：`finish_cache_task` 早有
  `status IN {CACHE_TASK_ACTIVE_STATES}` 状态门。真实的泄漏更窄（进度写无门），已修。

## 原始修复方向（研究阶段提出，保留供对照）

以下 6 条是登记时的分析结论，**保留原文**以便与上节「实际怎么修的」对照。
其中 1 / 4① / 5 / 6 已实施；2 / 3 **未实施**（见上节与下节「仍未覆盖」）。

1. **给在途条目一个真正的中断手段**（点 1 的核心）。不是加 pause/resume
   （那会违反 `activity.rs` 铁律 4 且确实是假能力），而是让**取消可达在途 IO**：
   把 `cache_one_bytes(...).await` 放进 `tokio::select!`，与一个取消信号竞速，
   或在字节流循环里检查取消标志。**这需要一份新裁定**：现行裁定只否定了
   pause/resume，从未评估过「取消是否应打断在途条目」。
2. **让 90s 看门狗可配置，并区分「慢」与「死」**（点 1 的「延迟」）。
   现行是**空闲**超时：一个每 89s 来一块的流可以无限期占住队首。至少应补一个
   **墙钟上限**（单条目最长耗时）并在 UI 上区分「正在慢慢传」与「已停滞」。
3. **条目卡死不应终止整个任务**（连带发现）。stall 是条目级事件，应记为该条目失败、
   **继续处理该任务的其余条目**，最后汇总；而不是让 `done=2/9` 的任务整条判 `failed`
   并放弃剩余 7 条。若确有「一条失败即整批失败」的理由，需在文档层说明。
4. **重启恢复队列**（点 2）。两个层次，需产品决策：
