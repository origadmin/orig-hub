# BUG-470: 单条 / 整组数据缺「加入筛选 + 入库（缓存）」合并快捷入口——核心逻辑不变，只加一个入口

- 状态: fixed
- 发现日期: 2026-10-27
- 模块: shell
- 严重程度: mid
- 排期: 2026-11-26

> 来源：用户报告「**比如某个数据组，是否要提供筛选功能？点击添加到筛选 + 入库
> 两个一起做了？**」
> 澄清（2026-10-28）：「**添加的时候编辑筛选标题啊**」；
> 定稿（2026-10-28）：「**加入筛选逻辑为主，筛选就是标题，就是剧集名，这是核心逻辑**」；
> 范围收窄（2026-10-28）：「**我说的是单条/组数据，是否添加筛选 + 入库（缓存）功能合并。
> 编辑能力就是上面说的，什么核心逻辑都不变，改的仅仅是快捷入口和功能。**」

**本档范围（写死）**：只在**单条数据 / 整组数据**上加一个快捷入口，
把「加入筛选（含编辑筛选名）」与「缓存入库」合成一次操作。
**核心逻辑一律不动** —— 不新增模型、不改归档轴、不改归并、不改谓词语义。

## 一、核心逻辑（本档定稿，不再列候选方案）

> **入库这个动作的主语是「加入筛选」。筛选名 = 这批内容的标题 = 剧集名。三者同一个字符串，
> 不存在「给条目还是给剧」的分支。**

1. **一次动作，一件事**：选（或新建）一个筛选 → 入库。不拆成「先建筛选规则、再进面板勾选、
   再入库」三步，也不拆成「入库 + 事后改名」两步。
2. **三者同一**：筛选的名字 = 入库后这批内容的标题 = 归属剧集的名字。
   实现上就是同一个值同时下发给 `titleHint`（条目显示名）与 `seriesHint`（剧名），
   并配 `seriesKey`（筛选身份，幂等轴）。
3. **筛选是归类轴，不是过滤器**：「筛选」在这条链路里的语义是**这批内容归到哪一部/哪一类**，
   不是「按关键词把消息过滤出来」。过滤（谓词）只是「自动投进这个筛选」的一种来源，
   不是筛选本身。
4. **没有筛选名 = 没入库**：不给名字就入库 ⇒ 库里多一批无名内容，用户无从认领
   （这正是现状）。故入口必须提供筛选名（可预填 caption 兜底，可现场编辑）。

## 二、我前两版错在哪（误解复盘，避免第三次偏离）

| # | 我的错误决策 | 错在哪一步 | 后果 |
|---|---|---|---|
| 1 | 把「筛选」读成**仓库里既有的「文字筛选规则」**（keyword 谓词，`api/tg.ts:298`） | 拿既有概念去套用户的话：仓库里 `monitor/filters` 确实是谓词，于是我把「加入筛选」理解成「把一个组塞进某条谓词的命中集合」 | 造出「谓词要不要扩显式成员集」这个**伪问题**，整档围着规则模型打转 |
| 2 | 把「添加到筛选 + 入库」拆成**两个能力**再讨论合并 | 用户说的是**一个动作的两个面**：加入筛选就是入库那一刻的事，不存在先有筛选、后入库的顺序 | 造出「合并成一步 vs 两步」的**伪选项** |
| 3 | 把「编辑筛选标题」降级为**补参数**（补 `titleHint` / `seriesHint` 的技术选择题） | 标题不是参数，是筛选的**名字**——筛选名就是标题就是剧集名，三者同一，没有可选项 | 造出「A（给剧名）/ B（只给显示名）」的**伪二选一**，把定稿问题做成待拍板 |
| 4 | 把「某个数据组」锁死成技术上的 **media group（`groupId`）** 并据此评估「组内过滤」 | 用户说的「某个数据组」= **一批要入库的内容**（可以是一个相册组，也可以是一批命中） | 造出「组内过滤要不要做」这个**用户根本没提**的议题，偏离中心 |
| 5 | 把「加快捷入口」升级成**数据模型改造**（筛选实体扩 `members[]`、谓词降级、计数口径改写） | 用户明说「**改的仅仅是快捷入口和功能**」——范围外 | 把一个小入口改造成跨引擎的模型变更，工作量与回归面都被我放大 |

⇒ 五次偏离同源：**用仓库里既有的技术概念去套用户的产品语义**，
而不是先问「用户这句话在描述哪个动作」；以及**把入口级诉求升级成架构级改造**。
本档此后以第一节的核心逻辑 + 本档范围为准。

## 三、现象（现状与核心逻辑的差距）

1. **TG 面板入库完全没有筛选/命名入口。** 整组缓存 `downloadAlbum`
   （`TgPanel.tsx:1845-1859`）只传 `chatId / messageIds / groupId`；单条 `doDownload`
   （`:1826`）只传一条 —— **都不传 `titleHint` / `seriesHint` / `seriesKey`**
   ⇒ 从 TG 面板入库的内容，名字由后端按 caption 决定（无 caption 时落 BUG-436 兜底），
   归属由后端自行归并 ⇒ **「加入筛选」这个动作在 TG 面板根本不存在**。
2. **筛选/命名只存在于「筛选面板」这一条链路上。** `TgFilterPanel.tsx:368-380` 的入库传
   `titleHint: filter.keyword || filter.label`、`seriesHint: filter.label || filter.keyword`、
   `seriesKey: tg:filter:{id}`（BUG-436 兜底 / BUG-438 归档轴）。
3. **筛选目前被焊死在「文字谓词」上。** `addTgMonitorFilter({keyword, label})`
   （`api/tg.ts:298`）—— 筛选 = 一条 keyword 规则，没有「显式归入」的概念，
   也没有独立身份 ⇒ 从 TG 面板入库的内容无法「加入某个筛选」，
   因为筛选在这里只回答「匹配哪些消息」，不回答「这批内容归到哪」。

## 四、根因

1. **入口只做「取字节」，不做「归属」。** 单条 `doDownload`（`TgPanel.tsx:1826`）与整组
   `downloadAlbum`（`:1845-1859`）的语义是「把字节取回来」，既没有「归到哪个筛选」的选择，
   也没有名字输入 ⇒ 归属与命名被完全遗漏，库里因此产生无名批次。
2. **命名参数可选，且只有筛选面板填**（`api/tg.ts:541-560` 的 `titleHint` / `seriesHint` /
   `seriesKey` 全为可选；唯一填的地方是 `TgFilterPanel.tsx:368-380`）
   ⇒ 命名成了「走哪条链路」的副作用，而不是「入库」动作的固有组成。
3. **两条链路不对等**：同一件事（入库）走筛选面板有名有归属，走 TG 面板无名无归属 ——
   差的就是**入口上有没有那一下「加入筛选」**。

> 注：筛选的谓词模型（`addTgMonitorFilter`，`api/tg.ts:298`）**不是本档的障碍**——
> 快捷入口上的「新建筛选」就是建一条筛选（名字即标题即剧名），
> 「选已有筛选」就是复用其 `id` 作 `seriesKey`；不需要模型新增任何字段。

## 五、定稿设计（入口层落地判据，不改核心逻辑）

1. **入口位置：单条 + 整组两处。** TG 面板的单条缓存（`doDownload`，`:1826`）与整组缓存
   （`downloadAlbum`，`:1845`）各提供一个「**加入筛选并缓存**」入口
   （与既有「缓存」入口并列，不替换 —— 不缓存只想归类时仍走原入口）。
2. **一次操作，一件事**：点入口 → 选已有筛选 **或** 新建并命名（预填 caption 兜底值、
   现场可编辑）→ 提交 ⇒ **一次 `enqueueCacheTask`**，
   带 `titleHint` = `seriesHint` = 筛选名、`seriesKey = tg:filter:{筛选 id}`，
   同时完成归属与缓存入队。这就是「添加到筛选 + 入库两个一起做了」。
3. **筛选名是必填语义**：留空须显式提示「没有名字的内容在库里认不出来」，
   不允许像现状这样静默入库。
4. **落点清单（全部在壳层）**：`TgPanel.tsx:1826 / 1845`（入口 + 提交逻辑）、
   一个选择/新建筛选的轻量控件（可复用筛选面板已有选择逻辑）、i18n 约 2 键。
   **引擎零改动**：不新增端点、不改 `enqueueCacheTask` 契约、不改筛选表结构。

## 六、明确不做（排除项，防止再次偏离）

1. **不改核心逻辑**：不加 `members[]`、不改筛选实体、不改谓词语义、不改 `tg:filter:{id}`
   归档轴、不做数据迁移、不改命中计数口径（因此不涉及 BUG-125/133）。
2. **不做组内过滤**（只挑组内部分成员入库）—— 相册组本就同类；「排除已缓存」省不下成本
   （worker 幂等跳过，BUG-308）；且与「性能为主要目标」冲突。用户未提此诉求，
   是本档第 4 条误解衍生出来的伪议题。
3. **不做文件监听 / 事件自动对账**（BUG-458 裁定 B）—— 筛选归属只在用户显式点击时发生。
