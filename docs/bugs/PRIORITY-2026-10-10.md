# 缺陷优先级总表（2026-10-10 快照）

> **性质**：本表是**建议排序**，供产品侧裁定；不是门禁、不改任何缺陷档的状态。
> **真值来源**：标题 / 状态 / 严重程度 / 模块均从 `docs/bugs/BUG-*.md` 与 `docs/bugs/README.md` 现读，未手工转录。
> **覆盖**：全库 71 条未关闭登记（`open` 67 / `in_progress` 2 / `partial` 2），**逐条入档、无遗漏、无重复**。

## 分档判据（先立规则，再排表）

| 档 | 判据 |
|---|---|
| **P0** | 本轮用户直接报告 / 点名（用户**此刻就能感知**） |
| **P1** | 生产已触发，**阻塞主流程或数据完整性**（`critical` / `high`，用户迟早必遇） |
| **P2** | 生产已触发，**影响体验但非阻塞**（条件性 / 次要路径；`high` 或 `mid`） |
| **P3** | **潜伏 / 未在生产触发**，或一致性 / i18n / 可维护性（`low` / `mid`） |
| **P4** | **新能力 / 架构 program**（需立项或长期推进，不属缺陷修复节奏） |

> **排序原则**：① 用户**已感知**优先于「我判断重要」；② 阻塞 / 数据损伤优先于体验；
> ③ 已生产触发优先于潜伏；④ 新能力不与缺陷抢修复档位（单列 P4）。
> **与严重程度的关系**：`严重程度` 是单档内的属性，**不等于**优先级 ——
> 例：BUG-122 是 `mid` 但影响面 27.6%（提档至 P1）；BUG-261 是 `mid` 但实测受害面 0（降至 P3）。
