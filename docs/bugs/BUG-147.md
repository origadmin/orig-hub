# BUG-147：来源可用性探活用了「进程存活」判据——TG 不可用仍给可用的重新缓存按钮

- 状态: fixed
- 发现日期: 2026-09-23
- 模块: shell
- 严重程度: major
- 档位: standard

## 现象

`lib/mediaSources.ts` 里 TG 适配器的 `health()` 调的是 `tgHealth()`（即 `GET /health`）。

该端点只反映 **orig-tg 进程是否在跑**：进程在就返回 200。于是当 TG 实际上是
「在跑但不可用」（未登录 / 离线调试模式 / MTProto 连接失败）时，探活给出 `true`，
媒体库据此认为来源可用，给出**可点的「重新缓存」按钮**——用户点下去才吃到 503。

这正是 BUG-145 要消灭的「点了必然失败的活按钮」，只是判定口径错了：判据问的是
「进程活着吗」，而按钮的可用性取决于「能不能真的从来源取回字节」。

## 根因

`health()` 复用 HTTP 服务的存活端点当作来源可用性判据。两者语义不同：

- `GET /health`：进程存活（HTTP 服务在监听）；
- `GET /api/tg/diag` 的 `available`：TG 客户端真实可用（凭证齐备且 MTProto 已连接），
  并附带 `unavailable_reason` 说明为什么不可用。

离线调试模式下二者结论相反：前者 `200 / {"status":"ok"}`，后者 `available:false`、
`mode:"unavailable"`。用前者判来源可用性，等于把「没连上」报成「连上了」。

## 复现

1. 以 `ORIG_TG_OFFLINE=1` 启动 `orig-tg`（模拟 TG 未连接；媒体库 API 仍正常）。
2. `curl http://127.0.0.1:9877/health` → `{"status":"ok"}`；
   `curl http://127.0.0.1:9877/api/tg/diag` → `"available":false,"mode":"unavailable"`。
3. 打开媒体库：来源离线横幅**不出现**，「重新缓存」按钮不置灰 —— 但此时点它必然失败。

## 修复

`tgAdapter.health()` 改为调 `tgDiag()` 并取 `available` 布尔值（请求失败一律判 false，
覆盖「进程都没起」这种情况）。媒体库其余逻辑不变：`probeRecacheBackends()` 拿到 false
后，横幅提示 + 「重新连接」入口出现，`recacheBlockedReason` 驱动按钮置灰并给出原因。

## 验收证据

**已执行**（真实渲染，非仅类型检查）。

- 环境：`orig-tg` 以 `ORIG_TG_OFFLINE=1` 启动（9877，`mode=unavailable`），`orig-daemon`
  在 9876，前端 dev server 在 5180；headless Edge 经 CDP 取渲染后 DOM。
- 修复前（探活用 `/health`）：媒体库内无 `media-source-offline-banner`。
- 修复后（探活用 `/api/tg/diag` 的 `available`）：
  - `[data-testid="media-source-offline-banner"]` 文本 =
    「来源服务未连接（TG）：库内内容照常可播可管理，仅「重新缓存」暂不可用。」+「重新连接」按钮；
  - 同时 `[data-testid="media-panel-title"]` = 「🎬 媒体库」，媒体卡片正常渲染
    （`[data-testid="item-source"]` = 「本地」）—— 证明**来源不可用不影响库的浏览**。
- 类型检查：`cd tauri-shell && node node_modules/typescript/bin/tsc --noEmit -p tsconfig.json` → 无输出（rc=0）。
- 反向证伪：`/api/tg/diag` 的 `available` 为 false 是横幅出现的**唯一**触发条件；
  若把探活改回 `tgHealth()`（`/health` 恒 200），横幅即消失——判据的可证伪性由此成立。
