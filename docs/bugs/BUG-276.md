# BUG-276: 单条目墙钟是**进程内 per-attempt 计时**，orig-tg 重启即清零 ⇒ 慢条目永不判失败、队首被无限占住（实测同一任务占队首 21 小时）

- 状态: open
- 发现日期: 2026-10-10
- 模块: engine
- 严重程度: high

> 来源：BUG-274 的 E4 实验顺带发现，用户 2026-10-10 裁定「**按推荐处理**」（= 该漏洞落档；卡死队列不动）。
>
> **本档为任务文档**（用户 2026-10-10 定：后续一律纯文档任务，代码由别的组负责）。
>
> **与 BUG-271 的关系**：BUG-271 立项要「给每条目加**总时长**死线（如 30min）」，
> 实现确实落了（`14e6257`），但落地形态是 **`tokio::time::timeout` 包住「一次尝试」**，
> 计时**只活在进程内**。**本条是该修复的覆盖缺口**——不是复报（BUG-271 治的「慢流不触发空闲看门狗」
> 已成立），而是**新发现的、它没有覆盖的路径**。故另立编号并互相关联。

## 现象

一个缓存任务在**队首同一条消息上停留 21 小时**，既不完成、也不被判失败：

登记当时实测（`GET /api/tg/cache/tasks` + 只读 `store.db`）：

| 字段 | 值 |
|---|---|
| `cache_task.id` | **134**（chat `-1004457697592`，`total=9`） |
| `status` | `running` |
| `done` | **0** |
| `current_id` | **1181**（**始终是第一条**，21 小时未推进） |
| `itemBytes / itemBytesTotal` | 23,592,960 / 194,116,505（**12.2%**，185 MB 条目） |
| `created_at` | **1791562886**（距今 **21.0 小时**） |
| `error` | **None** |

其后还有 **20 个排队任务** ⇒ 队列长期不空闲。

**连带后果（这才是危害所在）**：该条目在下载期间**独占整条 MTProto 连接** ⇒
远程播放（`/api/tg/file`）实测 **0 B/s**、`/api/tg/thumb` 与 `/api/tg/dialogs` 双双挂起
（详见 **BUG-274** 的 E4 对照表）。**不是「卡一下」，是「长时间不可用」。**

## 根因

### 事实 1（代码）：墙钟的寿命 = **一次尝试**，不是**一个条目**

```rust
// download-engine/crates/orig-tg/src/routes.rs:983-1004
let limits  = download_limits(st).await;          // 每次调用重新解析
let started = std::time::Instant::now();
let download = st.client.download_limited(chat_id, message_id, dir, Some(&st.cache_dl), &limits);
let outcome = match tokio::time::timeout(limits.wall, download).await { ... }
```

- 计时器是 **`tokio::time::timeout`**，包住**这一次** `download_limited` 调用 ⇒
  **只活在当前进程的当前这次尝试里**（`started` 是进程内 `Instant`）。
- 默认值 `wall = 30min`（`download-engine/crates/orig-tg/src/login.rs:237`；
  取值链 `app_setting > env > 默认`，实测生产库 `app_setting` **无任何阈值键** ⇒ **走默认 30min**）。

### 事实 2（代码）：重启会把尝试**重新开始**，于是计时归零

```rust
// download-engine/crates/orig-tg/src/main.rs:213-235
//   stale running → interrupted；queued → recover_queued_cache_tasks()
//   首个任务直接起 worker，其余留在 queued 由它 FIFO 接续
state.push_log(format!("cache task {}: re-queued after restart", t.id));
```

⇒ 每次进程重启，任务被**重新入队**并**重新起一次下载尝试** ⇒ **`started` 重新计时**。
**只要重启间隔 < `wall`，墙钟永远不触发。**

### 事实 3（运行时实测）：重启间隔 **远小于** 30min

`%APPDATA%\com.origadmin.orighub\logs\orig-tg.log` 实测：

| 量 | 值 |
|---|---|
| 日志时间跨度 | `2026-10-10T09:30:57Z` → `13:07:05Z` = **约 3.6 小时** |
| 进程启动次数（`listening on` 计数） | **16 次** |
| 重启间隔样例 | `10:06:22` 起，`10:07:46` 又 `bound` ⇒ **约 1.5 分钟** |
| 日志中 `too slow` / `wall-clock` 字样 | **0 命中** |

⇒ **16 次启动 / 3.6 小时** ⇒ 单次尝试远短于 30min ⇒ **墙钟从未到期**。

### 事实 4（推论）：`current_id` 未推进，反证墙钟从未触发

墙钟超时的处置路径是「**记录该条失败 + `continue` 下一条**」（`routes.rs:2260-2274`，
BUG-257 方向 3 的既有语义：条目级失败**不**终止任务）。
⇒ 若墙钟对 1181 触发过哪怕一次，**`current_id` 必已推进到 1182**、且日志必有 `too slow`。
**两者都没发生** ⇒ 墙钟从未触发 —— 与事实 3 互相印证。

### 小结（一句话）

**墙钟的语义写的是「每条目 30 分钟」，实现的是「每次尝试 30 分钟」；
而本环境下进程重启比 30 分钟频繁得多 ⇒ 这条死线在实践上不存在。**

> **诚实边界**：我**未能**从行为上确证「正在运行的二进制包含 `14e6257`」
> （`GET /api/tg/config` 只回 `downloadDir`/`libraryDir`，不暴露阈值；PID 归属查询在本会话被沙箱挡住）。
> 但：① release 二进制 mtime `21:06:13` 晚于提交时间 `19:41:57`；② 日志里
> `cache queue resumed after restart: 22 task(s) re-queued` 证明**启动恢复逻辑在场**。
> ⇒ 事实 1/2 是**代码级确定**；事实 3/4 是**运行时可复现的观测**。

## 复现

**判据（最小、零代码）**：

1. 取一个**慢条目**（`itemBytesTotal` 大、实测速率远低于「总量 / 30min」）。
2. 在**不重启**的前提下观察 ≥ 35 分钟：**必须**在 30min 处出现
   `cache_one(...): too slow -> download too slow: ...` 日志，且 `current_id` 推进。
3. **反向证伪（本条的靶心）**：在第 2 步的窗口内**重启一次 orig-tg**（或用 `POST /api/tg/restart`），
   然后继续观察 ⇒ **计时被重置、30min 死线不再到期**。这与不重启的情形必须**可观测地不同**。

**必须采集**：`logs/orig-tg.log` 里 `listening on` 的**次数与时间戳**（重启频率）、
`too slow` 是否出现、`cache_task.current_id` 是否推进。

## 修复（方向；**本档不改代码**）

**核心要求：把「墙钟」从「一次尝试」提升为「一个条目」——即计时的**载体必须跨进程存活**。**

1. **持久化条目级累计耗时**（推荐）：在 `cache_task` / 条目级记录里存**该条目已累计尝试的墙钟**
   （或首次开始时间 `first_attempt_at`），每次重启后**接着算**而不是从零算。
   超限即按 BUG-271 的既有通道判该条失败（不弃单、可重试）。
   - 需注意与 **BUG-257「重启把 running 降级为 interrupted」**的语义一致：重启**不应**清空累计。
2. **改用「尝试次数 / 累计字节停滞」上限**：例如「同一 `(task, message)` 重启重试超过 N 次」
   或「累计尝试时长超过 wall」即判失败。对「重启频繁」这一环境形态更鲁棒。
3. **（治本，但超出本条）先查重启频率本身是否正常**：实测 **3.6h / 16 次**、部分间隔 ~1.5 分钟。
   若这是 daemon 巡检自愈对「链路抖动」的过度反应（BUG-178 的 `POST /api/tg/restart` + 巡检），
   那它是**另一个缺陷**（应单独建档），本条只保证「即使重启频繁，条目级死线依然成立」。

**不可推翻的既有裁定**：缓存 worker **全局单飞**（`routes.rs:1425-1430`）、
条目级失败不终止任务（BUG-257 方向 3）、空闲看门狗 90s 治「死」（`grammers.rs:651`）——
本条**不触碰**，只补「慢」这一档在**重启路径**上的缺口。

## 后续观测（2026-10-10 自然实验：墙钟**确实触发**，但只在**最后一次重启后**重新计时 30min）

> 本节为**追加记录**（不改写上文）。原「事实 4」用「`current_id` 未推进」**反证**墙钟从未触发；
> 本节补上**正向现场** —— 墙钟最终触发了，且触发时刻**恰好**是「最后一次重启 + 1800s」。

登记 BUG-277 时（2026-10-10）从 `GET /api/tg/logs`（内存环形日志）取到：

```
[1791637627] cache task 134: re-queued after restart
[1791637627] cache task 134: start 9 item(s) chat=-1004457697592
[1791639427] cache task 134: item 1181 failed: download too slow: 1800.0s for chat -1004457697592 msg 1181; wall-clock limit 1800s exceeded, aborted to keep the cache queue moving (continuing with remaining items)
[1791641227] cache task 134: item 1182 failed: download too slow: 1800.0s for chat -1004457697592 msg 1182; wall-clock limit 1800s exceeded, aborted to keep the cache queue moving (continuing with remaining items)
```

**读数**：

| 事件 | 时刻 | 与前一事件间隔 |
|---|---|---|
| 重启重新入队 `re-queued after restart` | 1791637627 | — |
| `item 1181 failed: 1800.0s` | 1791639427 | **1800s**（= 1791637627 + 1800） |
| `item 1182 failed: 1800.0s` | 1791641227 | **1800s** |

**结论（对本条的印证与修正）**：

1. **印证「计时载体 = 进程内、重启归零」**：`too slow` 报数是 **1800.0s**（= 默认 `wall`），
   且**恰好在重启后 1800s 出现** ⇒ 计时**确实从重启时刻重新起算**（否则 21 小时早该触发）。
2. **修正「墙钟从未触发」的措辞**：墙钟**会**触发 —— 只要**两次重启之间**能连续跑满 30min。
   原「事实 4」的反证成立条件是「期间无 30min 无重启窗口」；本次观测说明
   **触发与否取决于重启间隔**，而非「永不触发」。**机制结论（进程内计时 + 重启归零）不变**，
   只是「危害」从「永不判失败」精确化为「**每次重启都要重烧一遍 30min**」——
   对 `total=9` 的任务，光烧超时就要 **9 × 30min ≈ 4.5h**，且期间队首**始终被占**。
3. **`currentId` 已推进**：登记 BUG-277 时实测 `currentId=1183`（`1181/1182` 即上述两次失败的结果）
   ⇒ 与「失败分支 `continue` 下一条」（`routes.rs:2260-2274`）一致。

**对本条判据的影响**：判据 1「跨重启（窗口内主动重启 ≥3 次）条目仍在**累计** wall 处判失败」
依然成立且更必要 —— 修复后应做到「重启**不**重置累计」，即上述两条 `1800.0s` 应变成
**累计**到 1800s 即失败，而非每次重启后再烧 1800s。
