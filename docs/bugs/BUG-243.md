# BUG-243: 无「可查的调试日志」—— 引擎把子进程输出丢进 DEVNULL，出错只剩一句「未能启动」

- 状态: fixed
- 发现日期: 2026-10-09
- 模块: engine+shell
- 严重程度: high
- 报告轮次: 用户第 4 轮评审（新需求）

## 现象（用户原话）

> 「关于里面能不能添加调试日志,添加核心错误跟踪日志? 日志也放一个路径记录,到时候错误可以直接从调试路径检查,
> 优化检查流程,但是不能影响整体下载,播放性能.」

## 根因

- daemon 拉起 orig-tg 时**继承 daemon 自己的 stdio**，而 daemon 由 `scripts/dev_services.py`
  与桌面壳以 `stdout=DEVNULL / stderr=DEVNULL` 启动 ⇒ **orig-tg 的启动失败原因当场就丢了**，
  只剩 daemon 内存里一句 `tg_last_error`。而那句还会被「下一次成功拉起」清空、进程重启后更是毫无痕迹
  —— 偏偏偶发故障只在事后才有人来查。
- 实测（2026-10-09）：daemon 报 `orig-tg exited without listening on 127.0.0.1:19788` 时，
  磁盘上**找不到任何** orig-tg 的输出，无法区分「端口被占」「会话失效」「进程自己崩了」，
  只能靠人工复现。**「无法检查」本身就是故障不可解的一半**。
- 用户要的不是更多日志，而是**一条可定位的路径**。

## 修法

- 单一日志根目录：`<数据目录>/logs`（`orig-daemon/src/state.rs::log_dir()`，与 `tg_data_dir()` 同源
  ⇒ 调试 / 生产 / 桌面壳三方看到同一个目录）：
  - `logs/orig-tg.log`：orig-tg 子进程**完整** stdout/stderr（`tg_start_on` 拉起时重定向写入）；
  - `logs/errors.log`：daemon 记录的**核心错误**（`set_tg_last_error` 每次追加，`YYYY-MM-DDTHH:MM:SSZ` 时间戳）。
- 单文件 8 MiB 滚动一代（`.1`）：诊断价值集中在最近一段，且无限增长会持续吃用户磁盘。
- **性能约束（用户明确要求）**：只在**启动 / 失败路径**写盘，**不**逐请求落盘（逐请求写会把日志变成 IO 热点）；
  打开失败一律返回 `None`，日志永远不能让主流程失败（磁盘满 / 目录只读都不能阻断下载与播放）。
- `GET /api/config` 下发 `logs.{dir,orig_tg,errors}` **绝对路径**；设置-关于页新增「调试日志」区块
  展示路径 + 「打开日志目录」。**前端不拼路径** —— 路径真源在引擎，两端各拼一套必然漂移。

## 验收证据

- 隔离实例（临时数据目录 + 独立端口 29886 + `ORIG_TG_PATH` 指向不存在）：
  `PUT /api/config/tg {enabled:true}` 触发失败 → `logs/errors.log` 落盘
  （`2026-10-09T15:42:52Z orig-tg binary not found at ...`），`GET /api/config` 三项 `logs` 齐全。
- 真实 UI 探针 `tauri-shell/verify/verify_bug243_debug_logs.cjs`
  （截图 `tauri-shell/verify/evidence/BUG-243/1_about_logs.png`，2026-10-09 实测 **PASS**）：
  - 关于页 `about-logs-dir` 文本 === 引擎 `logs.dir`（**逐字符**，不是近似）；
  - Node 侧核对磁盘：目录存在、`errors.log` 非空（2540 B）；
  - 「打开日志目录」在拿到路径后可用（未拿不到上下文时禁用）。
- `npx tsc --noEmit` 通过；`cargo build --release -p orig-daemon` 通过。
