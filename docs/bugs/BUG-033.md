# BUG-033：倍速播放触发投递请求风暴 —— 同一块数据被反复重取，页面卡死

- **状态**：fixed
- **日期**：2026-09-18
- **模块**：engine（本地文件投递 / `serve_local_file`）

## 现象

用户主诉（原文）：

> 「播放卡死问题没解决，**倍速播放的时候同一块数据好像请求了无数遍，一瞬间刷了好几百条**，
> 这是最严重的问题，页面卡死。」

复现后的线上字节账（2x 播放 202s / 262 MB 的 `9月16日(10).mp4`，10 秒窗口）：

| playbackRate | 请求数 | 传输量 | 冗余倍数 | 终态 |
|---|---|---|---|---|
| 1x | 2–3 | 6–25 MiB | ~1.9x | 正常 |
| **2x** | **137** | **792 MiB** | **63x** | 136/137 被 abort |

即：**1x 完全正常，一旦倍速就爆炸**；白传比例 70%+，10 秒内近 800 MiB 灌进来。
在 WebView2（Tauri 壳）里就表现为界面卡死。

## 根因

**服务端喂数据的速度远超解码器的消费速度。**

- 解码器消费速率 ≈ 码率 × playbackRate（本例 1.24 MiB/s × 2 ≈ 2.5 MiB/s）
- 而本地千兆下服务端能以 **数百 MiB/s** 把字节灌进去
- Chromium 的媒体加载器读满当前 buffer 后即 **abort 连接**，稍后另起请求；
  由于上一响应被中途掐断、已收字节未被有效利用，它会在**同一区域附近反复重取**
  （实测重复 Range 起点密集挤在 19–25 MB 区间，间隔仅几十 KB）
- 倍速使消费加速 → abort 频率随之激增 → 雪崩

## 候选根因排除（对照实验，勿重复劳动）

每一项都做了 A/B，全部**不是**杠杆：

| 候选 | 实验 | 结果 |
|---|---|---|
| 我们的投递实现有缺陷 | 用**标准 Python Range 实现**（60 行，RFC 7233 一致）投同一文件、同一播法 | **130 请求 / 51x 冗余** —— 一样炸，故与实现无关 |
| 回包块大小 | `OPEN_CHUNK` = 1 / 4 / 8 / 32 MiB / EOF 五档 | 123–137 请求，全在同一量级 |
| 前端 `preload` | `auto` / `metadata` / `none` | 73 / 69 / 65，无杠杆 |
| 浏览器缓存 | `setCacheDisabled` 开 / 关 | 137 / 136，无杠杆 |
| Range 形态可分流 | 对比 seek 期与顺序播放期的 `Range` 头 | 两者**同为 open-ended `bytes=S-`**，无法按形态区分 |
| 前端重建元素 | `loadstart` / `emptied` 计数 | `+0 / +0` —— 元素从未重建，与前端无关 |

> 结论：这不是"某个参数调错了"，而是**投递速率与消费速率失配**这一结构性问题。

## 修复

`crates/orig-tg/src/routes.rs` 的 `serve_local_file` 增加**投递背压**：

```rust
/// 目标速率 = 文件码率 × DELIVERY_BUDGET_FACTOR(6.0)
/// duration 不可得时回落到 DELIVERY_FALLBACK_BPS(16 MiB/s)
/// 可用 ORIG_TG_DELIVERY_BPS 覆盖（0 = 关闭，便于 A/B，无需重编）
fn delivery_bps(total: u64, duration_secs: Option<i64>) -> f64
```

流式发送循环里按「已发送字节数应有的耗时 − 真实耗时」补 `sleep`，使发送速率贴合消费速率；
客户端断开时整个 stream 被 drop，`sleep` 随之中断，不泄漏。

两条投递路径（`/api/media/items/:id/raw` 与 `/api/tg/local/:chat/:msg`）共用该实现，
`duration` 分别取自 `media_item.duration` 与 `media_message.duration`。

**为什么是「码率 × 6」**：2x 播放需要 2×码率，留 3 倍余量给起播/seek 的突发预读。
实测该档位把冗余压到 3x 量级，同时不牺牲播放推进。

## 附带修复：倍速入口按钮小到点不到

几何取证（`verify_shots/shot_speed_menu.cjs`）发现两处播放器的倍速入口按钮
**低于 24×24 的最小可点击目标**，且贴在窗口最右上角：

| 位置 | 修复前 | 修复后 |
|---|---|---|
| `MediaViewer`（媒体库全屏播放器） | **27×23 px** | **40×32 px** |
| `TgPanel`（TG 面板行内播放器） | ~22×18 px | 40×32 px |

菜单项同步从 52×29 提到 64×32。

**这正是「倍速播放还是没有拉出来」的直接来源** —— 功能一直是好的（点击后
`playbackRate` 确实变 2，此前多轮验收都能证），但入口又小又贴边，用户找不到、点不准。
修复方式：`h-8 min-w-[2.5rem]` + `ring-1 ring-white/30`（提升与黑底的对比度）+ `aria-label`
（无障碍与可测性），菜单项 `min-h-[32px] min-w-[64px]`。

新增门禁 `4d. shot_speed_menu.cjs`：断言入口 ≥24×24 且在视口内、菜单四项可见可点、
点击 2x 后 `playbackRate === 2`，并落盘三张截图（初始态/菜单展开态/2x 生效态）。

## 已知取舍

速率余量（`DELIVERY_BUDGET_FACTOR`）是 seek 首帧与传输冗余之间的权衡：

| 目标速率 | seek | 2x 冗余 |
|---|---|---|
| 7.8 MB/s（×6，当前默认） | 3.0 s | 3.03x |
| 15.6 MB/s（×12） | 3.4 s | 5.27x |
| 26 MB/s（×20） | 1.4 s | 6.99x |
| 不限速 | 2.1 s | 63x |

seek 数值波动较大（另一支探针直测跳转起播仅 456 ms），故保留 ×6；
若实际使用中 seek 体感偏慢，用 `ORIG_TG_DELIVERY_BPS` 上调即可，无需改代码。

## 未采纳的方案及原因

- **换投递通道**：实测 `file://` → 16 请求、`blob:` → 0 网络请求，均优于 HTTP；
  但已缓存文件在 Tauri 侧要经 `asset` 协议、且未缓存流无本地路径，改造面大于收益。
  若后续仍见风暴，这是下一个候选方向（`convertFileSrc`）。
- **调整块大小 / preload / 缓存开关**：已实测全部无效（见上表），故**不再保留**这些旋钮。
- **按 Range 形态对 seek 免限速**：实测 seek 与播放同形，不可分流。
