# BUG-138：media:list 无读缓存——cacheKey 未覆盖条目列表，与既有列表缓存策略不一致

- 状态: fixed
- 发现日期: 2026-09-22
- 修复日期: 2026-10-13
- 模块: shell
- 严重程度: low

## 现象

媒体库条目列表每次进入 items 视图都发真请求（无在途合并、无结果缓存）；而同面板的剧集列表/剧集详情走 `fetchCache` 有缓存。同一面板两种数据策略，且条目列表是最高频消费的那一个。

## 根因

`tauri-shell/src/lib/fetchCache.ts:62-67` `cacheKey` 只有 `seriesList(tagId)` / `seriesDetail(id)` 两个键；`MediaLibraryPanel.loadItems`（`:168-187`）直接请求 `/api/media/items`。

## 复现

进出 items 视图（或切 tab）抓包：每次都有新的 `/api/media/items` 请求；对比切剧集视图（命中缓存零请求）。

## 修复

- 列表读走 `cached(cacheKey.mediaList(序列化查询参数), ...)`；增删改/导入/重缓存等变更路径必须 `invalidateCache`（`refreshAll` 已有全清调用点，核对其覆盖新键）。
- 注意与搜索防抖（250ms）协同；不做时间过期（fetchCache 既有裁定：随机过期会让「刚改完又看到旧值」）。

**已知残留风险（诚实记录）**：A / D1 读的是「缓存此刻是否仍在」，而 `onPosterReady`
在卡片补完封面后会作废整族 `media:list`；共享活栈上若别人正在导入数据，封面补写随时可能落进
测量窗口，导致这两条判据间歇性红（修复验证初期实测到过一次 16/17）。脚本已用
「等 raw / PATCH 计数静止 → 窗口内污染检测 → 整轮重来（最多 3 轮）」处理，并把每轮的
`cycleLog` 原样写进 `result.json` —— 不把「重试到绿」藏起来。
