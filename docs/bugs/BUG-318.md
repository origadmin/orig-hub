# BUG-318: 下载域数据丢失——orig-tg 不可用时静默空列表 + daemon 引擎下载纯内存重启全丢 + 聚合层活跃任务被掩蔽 + 聚合拉取用常量端口

- 状态: fixed（①③④ 已修；② 引擎下载持久化单列 **BUG-319** 待拍板）
- 发现日期: 2026-10-15
- 模块: engine+shell
- 严重程度: high

## 现象（用户原话，2026-10-15 20:5x）

> 「全部下载 好像有点问题,数据经常丢失,里面的实现好像也有问题,特别是"子"的控制.」

「全部下载」= 侧栏下载域页面（`nav.download`）。两类观感：

1. **数据经常丢失**：入库行整批消失，页面显示「暂无传输任务」，没有任何提示；
   过一会儿（或重进页面）又出现。
2. **里面的实现有问题**：展开后的「子」（条目明细）没有控制、没有状态、没有信息
   —— 与 BUG-315 复报同款，已在该条跟踪，本条不重复展开。

## 根因（三个独立缺陷，均已实证）

### ① 前端把「取不到」渲染成「没有」——`sources` 健康通道完全没接（主因）

BUG-077 设计的 `GET /api/activity` 响应含 `sources: [{kind, available, error, count}]`，
daemon 侧契约完备（orig-tg 不可达 ⇒ 恒 200 + `sources[1].available=false` + cache 条数 0，
`activity.rs::merge` 铁律 5，单测 `tg_unavailable_still_returns_downloads` 覆盖）。

但前端 `useIngestGroups.ts:122-131` **只读 `data.tasks`**：

```ts
const data = await fetchActivity('all')
const next = (Array.isArray(data?.tasks) ? data.tasks : [])
  .filter((t) => t.kind === 'cache')   // ← 从不看 data.sources
```

orig-tg 不可用时（监督重启实测约每 10-15 分钟一次，日志无 panic）：

- daemon 返 200，cache 任务 0 条 ⇒ `next = []` ⇒ `setTasks([])` ⇒ **全部入库行消失**；
- `error` 仍是 `null`（请求没失败）⇒ 「TG 服务未连接」banner **不出现**；
- `total === 0` 且无 error ⇒ 渲染「暂无传输任务」空态——与「真的没有任务」**完全同形**；
- 更糟：`hasWork.current = groups.some(活跃|停滞)` 此时为 `false` ⇒ **轮询停摆**，
  orig-tg 恢复后也不会自动回血，用户必须手动刷新或切走再切回。

即 BUG-176（媒体库「没有内容/取不到内容」不可区分）在下载域的**同款复发**——
那条已修，这条一直没修。

### ② daemon 引擎下载任务纯内存，进程死亡即全丢（架构缺口，BUG-077 已记未修）

`orig-daemon/src/state.rs:198`：`pub tasks: Mutex<HashMap<String, DownloadTask>>`——
全仓无任何任务表持久化（grep `fs::write|persist` 只命中 config 与测试）。

**2026-10-15 20:58 实证**：daemon（PID 48568，用户侧 elevated 启动）与 orig-tg 双双死亡，
`netstat` 19786/19787 无监听、`Get-Process` 无进程，活栈只剩 vite（5180）。
⇒ 引擎下载行全部消失且**不可恢复**（orig-tg 侧 cache_task 有 SQLite，不受影响）。

> 本子项需产品裁定（落盘/快照/明示），已单列 **BUG-319**，不随本条关闭。

### ③ 聚合层代表任务掩蔽活跃入库（控制丢失）

`ingestGroups.ts::groupIngestTasks` 按 `updatedAt` 取**最新**一条作 `latest`（行状态/
按钮/进度全以它为准）。但同 `itemKey` 下非最新任务若是活跃态，它就被藏进 `history`：

- 「下载中」档看不到它（组状态 = 终态）；
- 行上没有「取消」按钮（动作按 `latest.status` 分派）；
- 概览「在传」计数不含它。

可达路径：终态行被「取消优先」时 `set_cache_task_priority` 会 bump `updated_at`
（`store.rs:1706`）⇒ 一条更早的 queued 任务瞬间不再是「最新」。

### ④ daemon 聚合拉取用编译期常量端口，顺延后把健康的 orig-tg 误报成不可用（本轮新发现）

`activity.rs::fetch_cache_views` 的 URL 用编译期常量 `TG_PORT`（19787），而 orig-tg
绑不上起点（Windows 保留区/被占）时 daemon 会**顺延重选**并落进 `st.tg_port`
（`/api/config` 的 `tg_port`、前端 base 校准都以它为真源）。顺延后聚合永远打到一个
没有服务的端口 ⇒ `/api/activity` 恒 200 但 `sources.cache.available=false`、cache
零条 —— 与 ① 同款用户观感（入库行整批不可用），但根因在引擎侧。

**实证（2026-10-15 21:3x）**：实验脚本占放 19787 导致 orig-tg 顺延到 19788 后，
daemon（19:19 构建的二进制）`/api/activity` cache 条数从 137 变 **0**，而 orig-tg
`/all` 直连正常 137 条；同二进制上 `state.rs:566` 的 session URL 用的却是
`tg_port_state()`（正确）—— 全仓仅此一处生产用法漏改。

## 复现

| # | 步骤 | 预期（正确） | 实测（缺陷） |
|---|---|---|---|
| 1 | orig-tg 死亡期间打开下载页 | 「TG 服务未连接」banner + last-known 行 | 「暂无传输任务」空态，零提示 |
| 2 | orig-tg 恢复后停留在下载页 | 行自动回来 | 行不回来（轮询已停），须手动刷新 |
| 3 | daemon 死亡后重启 | 引擎下载行可恢复 | 行全丢（纯内存） |
| 4 | 同 key：queued 旧行 + done 新行（done 行被取消优先 bump 时间） | 组显示排队中 + 可取消 | 组显示已完成，活跃任务不可见不可控 |

## 修复方案

1. **①前端（本轮修）**：`useIngestGroups` 读 `data.sources`，cache 条
   `available === false` ⇒ 置「取不到」态——**保留 last-known 行不清空** + banner
   直出 `error` 原因（复用既有 `dl-tg-unavailable` 通道）；`hasWork` 门禁增加
   「未知态续轮」（取不到时必须继续轮，否则恢复不自动）。
2. **③聚合（本轮修）**：`groupIngestTasks` 代表任务改「**有活跃取最新活跃，
   否则取最新**」——组状态/动作/进度与「最需要关注的那次入库」一致。
3. **④引擎（本轮修）**：`activity.rs::fetch_cache_views` 的 URL 从编译期常量
   `TG_PORT` 改为 `st.tg_port_state()`（运行时真源，与 `/api/config`、session URL
   同源）；新增单测 `cache_views_use_runtime_tg_port_not_the_const`（假 orig-tg 起在
   非常量端口 ⇒ 聚合必须 available=true；旧实现必败）。
4. **②引擎持久化（待拍板，不本轮动）**：见「待拍板」。
