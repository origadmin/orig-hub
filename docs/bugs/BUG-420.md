# BUG-420: 内容 hash 只覆盖 12% 的条目——`hash_file` 是死代码，「存量懒纳入」从未实现，归并判据对老条目恒失效

- 状态: fixed
- 发现日期: 2026-10-23
- 模块: engine
- 严重程度: high

## 现象

用户实测真实库（`%APPDATA%/com.origadmin.orighub/tg/store.db`）：

```
video 377 条，有 content_hash 19 条
photo 213 条，有 content_hash 28 条
file    6 条，有 content_hash  0 条
```

即 **596 条里 47 条有 hash（7.9%），video 只有 19/377（5%）**。于是 BUG-407/408 刚落地的
「同 hash ⇒ 同一集」判据对这些条目**恒不成立**——合并两个来源时，本该认成「同一份文件」
的两条会被判成「两个不同视频」，各自续编。

用户质问：「是不是 hash 的算法来源不对？」

## 根因（实测定位，非猜测）

**算法没错，是覆盖没铺开。** 三条并存的原因：

1. **只有 blob 路径写 hash。** `routes.rs:3067` 是唯一生产写入点，且被
   `if let Some(hash) = outcome.content_hash` 包着；`content_hash` 由
   `grammers::PartFile::finish_into_blob` 在**流式落盘到 `.blobs/ab/cd/<hash>`** 时产出。
   走平铺降级分支（`house_downloaded_bytes` → `backfill_item_bytes`）的条目**不写 hash**。
   D24-A（BUG-309）2026-10-12 才落地 ⇒ 之前下载的全部条目没有、之后走降级分支的也没有。
   库内实证：**47 条有 hash 的条目，`file_path` 100% 在 `.blobs` 下；不在 `.blobs` 下的 0 条有 hash。**

2. **存量回填从未实现。** `blob.rs:87` 的 `hash_file` 文档写着
   「用于**存量懒纳入**（`content_hash IS NULL` 的行在触及时补 hash）与测试」——
   实测 `grep "hash_file("` 全仓只有**定义 + 3 处测试**，零生产调用点。
   **文档承诺的能力不存在**，这比没写更糟：它让「hash 覆盖率」在评审时看起来是有方案的。

3. **`orig-core` 算的 sha256 从未落库。** 下载引擎 `crates/orig-core/src/engine.rs` 在完成时
   算 `hash_sha256`（`Completed { hash_sha256 }`），但 `grep hash_sha256` 在 `orig-core`
   之外**零命中** ⇒ 算完就丢，daemon 侧没有任何消费者把它写进 `media_item.content_hash`。

另需分清两类「没有 hash」，它们**不是**同一件事（用户的判据是「没有 hash 说明没有文件」，
在库内成立，但要区分「文件从来没有」与「文件曾经有、现在路径悬空」）：

| 情形 | 条数 | 判定 |
|---|---|---|
| `file_path IS NULL` | 214 | 从未下载 ⇒ 无文件 ⇒ 无 hash，**正确** |
| `file_path` 指向的文件已不存在 | 84 | 路径悬空（旧平铺布局/临时夹具），hash 无从算 |
| 文件存在但无 hash | 251 | **本条缺陷的主体**，读盘即可算（合计 20.06 GB） |
| 文件存在且有 hash | 47 | 正常 |

（合计 596。注意相对路径必须按**库根** `D:/OrigDown/.orighub/library` 解析 ——
按下载根解析会把 131 个真实存在的文件误判成「不存在」，第一次统计就是这么错的。）

## 影响

- BUG-407/408 的归并正确性只对 7.9% 的条目生效 —— 用户看到的现象是「合并了两个来源，
  明明同一集却变成两集」，与「归并逻辑没修」无法区分。
- 内容去重（同一文件多源）在存量数据上整片失效。
- `media_blob.refcount` 的口径被隐式绑死为「hash ⇒ 字节在 blob 里」，使得「给平铺条目补 hash」
  不能简单复用 `backfill_item_bytes_with_blob`（会给不存在的 blob 路径记引用计数）。

## 复现

```sh
# 真实库口径（只读）
python -c "
import sqlite3,os
p=os.path.expandvars(r'%APPDATA%\com.origadmin.orighub\tg\store.db')
c=sqlite3.connect(f'file:{p}?mode=ro',uri=True)
print(c.execute(\"select kind,count(*),sum(trim(coalesce(content_hash,''))<>'') from media_item group by kind\").fetchall())
"
# 死代码证据
grep -rn "hash_file(" download-engine/crates/
```

## 修复

1. **补 hash 不碰引用计数**：新增 `Store::set_item_content_hash`（只写 `content_hash` 一列）。
   平铺条目的字节不在 `.blobs` 下，给它记 refcount 会让「归零即 unlink blob 路径」指向
   一个不存在的文件 ⇒ 回收语义失真。**hash 是内容身份，与「字节存在哪」解耦。**
2. **`recount_blobs` 加口径闸**：只统计 `file_path` 落在 `.blobs` 下的条目。
   否则启动对账会把 251 条平铺 hash 造成 251 行「字节不存在的 blob」。
3. **存量回填**（`hash_backfill::backfill_content_hashes`）：扫 `content_hash IS NULL
   AND file_path IS NOT NULL`，`resolve_item_path` 解析绝对路径，文件不存在则跳过并计数，
   存在则 `spawn_blocking` 读盘算 SHA-256 写回。**幂等**（已补的不再进扫描集），
   **不阻断启动**（后台任务，失败只记日志）。
4. **平铺降级分支也写 hash**：`routes.rs` 的 `else` 分支归仓后读一次文件补 hash，
   使「走降级的下载」不再产出无 hash 条目（否则下次启动又要回填一遍）。
5. 启动钩子：`main.rs` 在 legacy-root 迁移之后、服务监听之前起一个后台任务（延迟 8s，
   让启动先完成），跑一次全量回填。

**明确不做**：不把存量平铺文件搬进 `.blobs`（那是 D24-A 的「纳入」动作，会改 120 条
`file_path` 并在内容重复时留下两份字节，属破坏性迁移，须单独拍板）。

## 验收证据

- **单测**（`cargo test -p orig-tg --lib hash_backfill` → 4 passed）：
  - `backfill_hashes_only_real_files_and_is_idempotent_bug420`：真文件 2 / 缺文件 1 ⇒
    `hashed=2 missing_file=1 failed=0`，hash 等于 `blob::hash_file` 的值，缺文件保持 NULL，
    同内容两文件 hash 相等；重跑 `scanned=1 hashed=0`。
  - `backfill_resolves_relative_paths_against_library_root_bug420`：库根相对路径
    （`chat-1/1-media.mp4`）必须解析到真文件；根换成不存在目录 ⇒ `hashed 0 / missing 1`
    （这是最容易静默失效的一环：库根算错 = 251 个文件全判「不存在」，报表却像「文件本来就没有」）。
  - `hash_only_rows_never_create_blob_rows_bug420`：平铺 hash ⇒ `recount_blobs` 返回 0；
    受管 blob 仍计 1。
  - `clear_bytes_on_hash_only_row_reports_reclaimable_bug420`：平铺 hash 条目清字节返回
    `None`（可回收），`content_hash` 与 `file_path` 一并置空。
- **隔离端到端**：`download-engine/verify/verify_bug420_hash_backfill.py` →
  **12 PASS / 0 FAIL，exit 0**。隔离实例（临时 DB + 独立端口），并用
  `ORIG_TG_HASH_BACKFILL_DELAY_SECS=3600` 关掉启动自动回填 —— 否则后台任务会与
  手动端点抢同一批条目，断言必抖。在最终产物 `c407849d…` 上复跑。
- **反向证伪 2 次**（都当场 FAIL，改回后复跑 4 passed / 12 PASS）：
  1. 去掉「文件不存在就跳过」⇒ `missing_file 0 ≠ 1`（exit 101）；
  2. 去掉 `recount_blobs` 的 `.blobs` 闸 ⇒ `media_blob 1 ≠ 0`（exit 101）。
- **全量回归**：`cargo test -p orig-tg --lib` → **336 passed / 2 failed**，两红为既有缺陷
  BUG-418 / BUG-419（与本次改动无关，`git stash` 后同样红）。
- **产物**：`c407849d…`（12 位产物指纹，非提交）17,852,416B（`dev_stack.py build-tg`，四处副本指纹一致）。

## 真实库预期（下次启动自动生效）

回填在 `main.rs` 里 8 s 后后台跑一次，故**用户下次启动应用即自动补齐**；
可用 `GET /api/media/hashes` 观察：

| 指标 | 修复前 | 修复后（预期） |
|---|---|---|
| `hashed` | 47 | **370**（47 + 251 个真实文件 + BUG-421 修回的 72 条） |
| `missing` | 335 | **12**（11 条下载根顶层 + 1 条 C: 临时夹具，真的没有字节） |
| `noFilePath` | 214 | 214（从未下载，无文件即无 hash） |

（`hashed` 不是 298 而是 370：其中 72 条要先靠 **BUG-421** 把旧库根路径改写回来，
否则它们会被判成「文件不存在」而跳过 —— 两条缺陷是同一条链路上的前后段。）

首跑要顺序读 20.06 GB，SSD 上约 1–3 分钟；期间不阻塞任何请求。
