# BUG-172：媒体库被错误部署在 TG 进程内——一个来源插件的生死决定了一等公民功能的可用性

- 状态: open
- 发现日期: 2026-09-28
- 模块: engine
- 严重程度: critical
- 档位: standard
- 类型: epic
- 延期至: 2026-12-15（理由：设计级工程，需独立里程碑；详见关联设计文档）

## 现象

媒体库面板在用户并未遭遇任何真实故障时，整页显示「媒体服务未运行」（i18n `media.offline`），
资料库列表、播放、剧集/标签管理全部不可用。

**触发条件（全部为常态，非故障）**：

1. 用户从未绑定 Telegram（`npm run dev` 只起前端；或全新安装未配置 TG）；
2. 用户绑定过 TG，但当前未登录 / 断网 / 凭证失效；
3. 用户主动关闭 TG 插件（`tg.toggleHint`「关闭即终止并隐藏 TG 模块」）；
4. 用户只想播放一个**本地导入**的视频——这条路径与 Telegram 毫无关系。

用户感知是「我的资料库没了」，而事实是**库完整地躺在磁盘上，只是没人能读它**。

## 根因

### 主因：媒体库 API 与 TG 服务被合并部署在同一进程

- 媒体库全部 HTTP 端点（`/api/media/*`：stats/items/series/episodes/tags/scan/export…）
  注册在 `download-engine/crates/orig-tg/src/routes.rs:82` 起；
- 前端硬编码 `MEDIA_BASE = TG_BASE`（`tauri-shell/src/api/media.ts:11`），即 9877；
- `orig-daemon`（9876）**无任何 media 端点**——`grep -rn "media" orig-daemon/src/` 零命中；
- 于是「媒体库可用」被等价为「`orig-tg` 进程在跑」。

### 关键事实：媒体库代码对 TG 的依赖为 **0**

这一点决定了本条不是「解耦」，而是「**错误合并部署**」：

- `media.rs`（6576 行，媒体库全部实现）中 `st.client` / `self.client` / `state.client`
  的引用次数为 **0**；
- 媒体库路由**不做 `ensure_authorized`**：`routes.rs:82` 的 stats 注册点无鉴权，
  而 `:348 / :450 / :577 / :612 / :651 / :816 / :1060` 等 TG 端点均有；
- `media.rs:1-8` 的模块文档自述职责为「用户可管理的内容目录层」，与
  `media_message`（TG 同步流水）**职责分离**；
- `orig-tg/src/main.rs` 文件头明写：「只要本地媒体库（`/api/media/*`，**与 TG 客户端无关**）
  就能驱动整页 UI 联调」；不可用时挂 `unavailable.rs::UnavailableClient`，
  TG 能力全部诚实 503，**media 端点照常服务**。

即：**媒体库在代码层已完全脱离 TG，只是被装在了 TG 的进程壳里。**

### 次因 A：外壳启动顺序把 TG 凭证当作 orig-tg 的启动前置

`tauri-shell/src-tauri/src/lib.rs:407 spawn_tg()`：

```rust
let cfg = read_tg_config(app)?.ok_or("not-configured")?;
if cfg.api_id.trim().is_empty() || cfg.api_hash.trim().is_empty() {
    return Err("not-configured".into());
}
```

无凭证直接拒绝拉起；`setup`（约 L599-606）捕获后仅打印 `ensure_tg skipped`。
**后果：9877 无进程 → 媒体库永久不可达**（在纯 Tauri 外壳路径下）。

> 注：`read_tg_config` 缺文件返回 `Ok(None)`（L390-392），不 panic；`ok_or` 先于
> L409 返回，故空 cfg 走不到空串判断。

### 次因 B：自愈目标与探活目标错位

- 探活：`mediaSources.ts:117 probeLibraryBackend()` → `getLibraryStats()` → **9877**
  （精确判据是「`/api/media/stats` 可达」，非笼统的「9877 在跑」）；
- 自愈：`MediaLibraryPanel.tsx:94-113 probeLibrary` 首探失败后调
  `ensureLibraryBackend()` → `mediaSources.ts:127` → `ensureDaemon()` → **9876**。

**拉起 9876 不解决 9877 的问题**——daemon 起来了，9877 仍无进程，再探依旧 false。
「重试」按钮指向的修复动作无法修复它所报的问题（J2 判据的直接命中）。

同文件下方明明已有正确的 `ensureTg`（`api/tauri.ts:10` 的 `ensureTg` 封装），未被使用。

### 次因 C：第三条拉起路径不校验 TG 凭证（潜在不一致）

`orig-daemon` 的 `PUT /api/config/tg {enabled:true}` → `st.tg_start()`
（`orig-daemon/src/routes.rs:663-694`）。该路径是 daemon 进程内的拉起逻辑，
**不校验 Tauri 侧的 `config.json`**，与次因 A 构成两套不一致的启动前置条件。

## 复现

1. 不配置 TG 凭证（或删除 `<appDataDir>/tg/config.json`），以常规方式启动桌面应用；
2. 打开侧栏「媒体库」；
3. 观察：整页显示「媒体服务未运行」+ 一个「重试」按钮；点击后仍为该状态；
4. 对照：`ls` 库根（默认 `<TG数据目录>/library`）可见条目文件完好——
   **数据没丢，是服务没人提供**。

**开发态最小复现**：仅 `npm run dev`（`tauri-shell/package.json:7` = `"dev": "vite"`，
只起前端 5180，不拉任何后端）→ 必然命中。

## 修复

> 本条为**前置设计档（pre-fix）**：先固化判定与目标形态，修复方案以决策项定案后再落实现。

### 硬约束（修复的前提，需用户拍板）

**H1**：媒体库的可用性**不得依赖任何 Telegram 配置 / 登录 / 进程状态**。
「媒体服务」与「TG 服务」必须是两个独立可寻址、独立可启动的服务。

### 目标形态

| | 媒体服务（内容域 / 资产） | TG 服务（来源域 / 传输通道） |
|---|---|---|
| 生命周期 | 随应用启动，**无前置条件** | 可插拔，由 TG 配置决定启停 |
| 依赖 | 无 | 依赖媒体服务的库根与存储 |
| 可用性 | 只取决于「本地库 + 本服务」 | 失效仅影响「从 TG 取回字节」 |
| 端点 | `/api/media/*` | `/api/tg/*` |

### 候选方案（详见 `docs/design/media-service-deployment-decision-2026-09-28.md` D1）

- **A｜独立进程（真插件式）**：新建 `orig-media` sidecar，`/api/media/*` 迁入。
  可用性最强（无前置条件启动），但需先解决 `store.db` 写权仲裁与
  `serve_local_file` 跨进程共用（`AGENTS.md` §5 要求两路必须共用，BUG-031/033）。
- **B｜归入 `orig-daemon`（hub 内置服务）**：`/api/media/*` 挂 9876。
  `orig-daemon` 是现状**唯一无需凭据前置即可启动**的后端，媒体库随应用必然可用；
  不新增进程/二进制，前端一行改向（`api/media.ts:11`）。**回归面最小。**
- **C｜壳内嵌（子线程/同进程 API）**：**可行但被否**——媒体库核心消费方式是
  `<video>` 以 URL 拉流（`api/media.ts:214` → `/api/media/items/{id}/raw`），
  `invoke` 无法服务 `<video src>`；且会摧毁现有 HTTP 验收链（headless Edge + CDP）。
- **D｜维持现状**：不做。**注意：这不是稳定中间态**——每新增一个来源
  （抽象已支持 oss/s3/netdisk）都会再叠一层同类问题。
- **演进选项**：将 `media.rs` 与媒体路由从 `orig-tg` crate 中物理迁出，
  从代码归属上消灭寄宿关系（可与 A/B 叠加）。

### 本次评估的关键量化（支撑上述取舍）

- `media.rs`（6576 行）外部依赖仅 6 项：`std` / `libsql` / `serde` /
  `crate::cache` / `crate::store`（`media.rs:10-18`），**无任何 TG 类型**；
  `cache.rs`、`store.rs` 对 TG 客户端引用同为 **0**。
- 二进制体积：`orig-tg.exe` **12.23 MiB** vs `orig-daemon.exe` **7.23 MiB**，
  差 **5.00 MiB**（即 grammers/MTProto/crypto 栈）——媒体库几乎不需要这部分，
  是「为媒体库单开进程」的主要成本项。
- 前端以 **HTTP `fetch`** 访问媒体库（`api/media.ts:195` / `:359`），非 Tauri `invoke`。

### 待一并处理的既有隐患（本次核查发现，不属本 BUG 主因）

- **存量绝对路径条目**：`media_item.file_path` 自 P2 起存库根相对路径，存量条目仍是
  绝对路径（`cache.rs:75-86 resolve_item_path()` 兼容两态）。迁移时须保持两态可读。
- **假空库风险**：库根解析链（`store.rs:692-717`）失败时**不 panic**，退化到
  `Path::new(".").join("library")`，可能读到 CWD 下的另一个空库，
  用户看到「空库」假象。需在服务启动期显式校验并给出可诊断错误。
- **归仓降级**：`house_into()` rename 失败时文件留在 TG 暂存区、`file_path` 回填绝对路径
  （`cache.rs:173-181`）。此类文件的物理位置仍在「唯一可删区」内，是「所有权已转移、
  物理位置未转移」的不一致态，迁移方案须覆盖。

## 验收证据

> 状态为 `open`，按规范**不得伪造验收证据**。以下为**修复后必须满足的可证伪判据
> （预先声明）**，用于将来判定本条是否真正闭环。

**P1（无 TG 凭证下媒体库可用）**：清空 `/tg/config.json` 后启动应用，
`curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:<media-port>/api/media/stats` = **200**；
媒体库面板渲染出真实条目，**DOM 中不出现** `media.offline` 文案。

**P2（TG 失效不影响库）**：`orig-tg` 以不可用态运行（`/api/tg/diag` → `available:false`）时，
媒体库列表、已缓存内容播放、剧集/标签管理**全部可用**；仅「重新缓存」入口按来源置灰
（沿用 BUG-147 已确立的口径）。

**P3（自愈目标一致）**：制造「媒体服务已停」状态后点击「重试」，
**必须恢复媒体库**（而非拉起一个无关服务后仍然报错）。
反向证伪：若 ensure 目标与实际探活目标不一致（如 ensure 9876 / probe 9877），
本判据必须 FAIL。

**P4（真故障才阻断）**：只有当承载 `/api/media/*` 的服务确实不可达**且自愈失败**时，
才允许出现整页阻断态；文案须归因正确（区分「库不可用」与「服务不可用」）
并给出可执行的下一步。

**证据落盘要求**：证据须引用被 git 跟踪的入库路径（验收脚本入
`download-engine/verify/` 或 `tauri-shell/verify/`）或真实提交短 hash；
仅 `verify_shots/` 引用不构成跨机器可核验证据。

**反向证伪要求**：P1/P2 的断言必须能在「仅前端 dev server 起、无任何后端」时
**必然 FAIL**（对齐 `MEMORY.md` 的「反向证伪是验收的验收」）。
