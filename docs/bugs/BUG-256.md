# BUG-256: 临时文件回收页签信息架构失衡 —— 列表上方堆叠 9 个构件（含与本页签无关的「入库统计条」），明细行直接渲染内部标识 `doc--…` 导致不可辨识

- 状态: open
- 发现日期: 2026-10-10
- 模块: engine+shell
- 严重程度: mid
- 登记: 用户报告「静态页浏览: 入库流水线 -> 临时文件回收 需要重新设计。上半部分无用内容占据弹窗一半，下面内容选择显示的东西混乱 `doc--1004493170102_6896` 这种完全不明觉厉。」

## 现象

「入库流水线」弹窗（`tauri-shell/src/components/CacheManagerDialog.tsx`）切到**「临时文件回收」页签**后，
弹窗上半被一串构件占满，真正要看的**条目清单被压到下半**；而清单每一行只显示
「勾选框 + 标题 + 字节数」，标题大量是 `doc--1004493170102_6896` 这类**内部标识**，
用户无法判断「要删的是哪一条」。

## 根因

**1. 明细行直接渲染 `media_item.title`，未过仓库里既有的「原始文件名」守卫**
`tauri-shell/src/components/CacheBytesPanel.tsx:431-432`：

```tsx
<span className="min-w-0 flex-1 truncate text-xs text-fg-strong" title={x.title}>
  {x.title}
</span>
```

而守卫**已经存在**：`tauri-shell/src/lib/tgmedia.ts:60` 的 `isRawFileName()`，
正则 `/^[a-z]+--\d+_\d+/i` —— **能命中 `doc--1004493170102_6896`**；
媒体库也已用它兜底：`tauri-shell/src/components/MediaLibraryPanel.tsx:355`
`title: isRawFileName(e.title) ? '' : (e.title ?? '')`。
**唯独本面板一处没用** ⇒ 同一份数据在媒体库被清洗、在这里被原样展示。

> 这正是 **BUG-154**（「条目 title 为空或原始文件名 —— 分集展示兜底成 `#<itemId>`」）
> 的**未覆盖面**：当年修的是剧集/分集展示，字节回收面板不在改动范围内。

**2. 后端把 title 原样透传，判定责任全压给展示层**
`download-engine/crates/orig-tg/src/cache.rs:827`：`"title": it.title` ——
`clear_preview` 不做任何可读化处理。展示层没接，于是内部标识直达界面。

**3. 存量脏标题「改代码消不掉」（BUG-154 只救新数据）**
`import_cached_file`（`download-engine/crates/orig-tg/src/routes.rs:1024-1066`）现已按 BUG-154
改成「无 caption（或首行为空）⇒ 标题取**空串**，不拿落盘文件名伪装」；
但 `upsert_media_item`（`download-engine/crates/orig-tg/src/media.rs:1226`）写的是

```sql
title = COALESCE(NULLIF(excluded.title, ''), media_item.title),
```

—— **空串不会覆盖已有值**。于是早期（BUG-154 之前）以落盘文件名当标题写库的行，
**重新缓存也不会被修正**。上表 7 条 `doc--…` 即属此类**存量**：
必须靠一次性回填/迁移，或由展示层兜底；**继续改写入逻辑对它们无效**。

**4. `via Mr.Yan` 表明 title 里混进了非标题内容（未定因，如实登记）**
按现行口径 title 应取 caption 首行。`via Mr.Yan` 是**发送者名**，与口径不符。
本档**不猜成因**：需单独取证该行的 `media_message.caption` 与写入路径。

**5. 上半部分的构件与页签语义不匹配（信息层级）**
第 3 项（入库统计条）在第 1 条里已证明是**跨页签常驻**。
依据本仓既有裁定 `docs/bugs/BUG-148.md`：「能力限制/实现信息不得做成常驻核心元素」——
一个回答「入库进度」的读数，出现在「回收字节」页签上，回答的**不是用户此刻的问题**，
却持续占位。第 4 项（分区卡片）与页签同义重复，同样属纯占位。

## 修复方向（未实施）

1. **明细行改「可辨识标识」**：行内给出**频道名**（宿主已传入 `chatTitleOf`，见
   `CacheManagerDialog.tsx:1238`）+ **消息号** + **类型** + **时间**；
   `title` 仅在**非原始文件名**时才显示 —— 认得出「删的是哪几条」才谈得上判断该不该删。
2. **接入既有守卫**：本面板复用 `isRawFileName()`（与媒体库同源，不新写第二套判定）。
3. **上半部分收敛**：`cache-ingest-summary` 只在「入库流水线」页签渲染；
   删掉与页签同义的分区卡片；影响面读数与四档按钮合并为一行。
4. **存量处置（必须如实登记条数）**：为 `doc--…` 形态的 title 提供一次性回填
   （源取 `media_message.caption`），或在文档里明确判为「不可恢复」并列出受影响 id。
   **不得**只改写入逻辑就当存量已修。
5. **`via Mr.Yan` 单独取证**（见根因 4），不并入本条修复。

> 收敛时**不得撤掉任何能力**：四档（全部/孤儿/陈旧/失败）、按频道选定、勾选回收、
> 确认条都必须保留（`docs/bugs/BUG-149.md`：重构不是删能力的授权）。

## 修复后必须满足（可证伪判据，预先声明）

1. 「临时文件回收」页签下，入库统计条（`data-testid="cache-ingest-summary"`）在 DOM 中**不存在**；
2. 明细行内**不出现**任何匹配 `^[a-z]+--\d+_\d+` 的字符串（含 `title` 悬浮属性）；
3. 每行至少给出「频道 + 消息号 + 类型」三项可辨识信息，空标题行也必须可辨识；
4. 四档按钮、按频道选定、勾选回收、确认条**全部仍在**且可用（防「重构顺手删能力」）；
5. **反向证伪**：把 `isRawFileName` 守卫去掉，判据 2 必须重新 FAIL。

- **BUG-136**：cache 接口 `external` 字段双形状双口径 —— 影响面条读数的既有约束。
