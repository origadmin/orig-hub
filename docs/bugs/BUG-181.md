# BUG-181 缓存队列「任务1添加，任务2就完全无法添加」——排队任务零呈现 + 条目内进度冻结

- **状态**: fixed
- **发现日期**: 2026-09-29
- **模块**: engine+shell
- **严重程度**: critical

关联 BUG-180（队列饿死）——本单是其兄弟缺陷：队列活着，但**活着这件事对用户不可见**。

## 症状

用户：「任务1添加,任务2就完全无法添加! 一点逻辑都没有吗?」——任务 1 入队后，任务 2 入队无任何反馈；任务 1 自身长时间无进度变化。

## 根因（两层叠加，BUG-180 修复后依然存在）

1. **排队任务对前端零呈现（契约缺口）**：`GET /api/tg/cache/tasks` 按单飞呈现契约只返回**一个**任务（running 优先）。任务 2 入队成功（DB `queued` 行在、worker 会接续），但该端点对它只字不提——前端 `entryStateFor` 在下一次轮询（5s）立即把任务 2 的条目打回「未缓存」。用户视角：添加动作被静默吞掉。单飞呈现（AGENTS §5 D2）禁的是「多个进度」，不覆盖「排队状态集合」，把两者混为一谈是本缺陷的认知根因。
2. **条目内进度冻结（观测缺口）**：缓存任务进度只在**条目边界**更新（`update_cache_task_progress` 仅在条目完成时调用）。实测频道内单条视频 200–345MB、代理链路 ≈0.7MB/s（任务 79 的 8543=203MB 耗时 294s、任务 80 的 8533=184MB 耗时 284s），这 5 分钟窗口内 `done` 计数纹丝不动——BUG-180 的 90s 无字节看门狗**不触发是合法的**（字节一直在来，判据是间隔非总时长）。对用户，「活着」与「死了」在 UI 上不可区分。

## 修复

### 后端（download-engine/crates/orig-tg）

1. **排队覆盖摘要**（`routes.rs`）：`GET /api/tg/cache/tasks` 响应增加 `queued: [{id, chatId, groupId, messageIds, total}]`（快照内存读，O(1)，上限 20）。仍是**一个进度**（`task` 字段不变），排队任务不带进度、只带覆盖集合——单飞呈现不被破坏，且不新增派生轮询。
2. **条目内字节进度**：
   - `login.rs`：`Client::download` 增加第 4 参 `progress: Option<&DownloadProgress>`（`Arc<AtomicU64>` × 2）；5 个实现同步（GrammersClient 实报，mock/unavailable/测试夹具忽略）。
   - `grammers.rs`：开流前 `set_total`（总量在 media 元数据可知），每非空 chunk 写盘成功后 `add_bytes`。
   - `state.rs`：`AppState.cache_dl` + `cache_dl_task`（归属任务 id，防错配）；`cache_dl_begin/end`。
   - `routes.rs`：`cache_one_bytes` 增加 `task_id: Option<i64>`（worker 传 Some，单条下载端点传 None）；序列化时对 `running` 任务注入 `itemBytes`/`itemBytesTotal`（`total==0` 不注入，防 `0/0` 空洞分母），三个任务端点（list/by_id/all）统一走 `task_with_progress`。

### 前端（tauri-shell/src）

3. **`lib/entryState.ts`**：`EntryState` 增加 `queued`（排队中）；派生规则 3 拆分——`taskStatus==='queued'` → `queued`，`running` → `caching`，同属活跃、同样压过旧态。
4. **`components/TgPanel.tsx`**：
   - `queuedTasks` 状态与 `cacheTask` 同源同请求；`entryStateFor` 对不在当前任务里的条目查排队覆盖 → 入队下一拍即点亮「排队中」。
   - `albumProgress` 扩展 `queued/itemBytes/itemBytesTotal`；排队组渲染「排队中 + 取消」（`data-testid="album-queued"`），运行组渲染「缓存中 n/N · 60.0 MB/202 MB」（`data-testid="album-progress"`）；单条任务渲染 `bubble-item-bytes`。
   - `cancelAlbum` 支持取消排队任务（直接出队）。
   - 轮询签名加入 `itemBytes` 与 queued ids（等值短路不被破坏——内容没变仍零重渲染）。
5. **`components/CacheManagerDialog.tsx`**：任务行标签表补 `queued` 键（排队行从「缓存中」纠正为「排队中」）。

## 防再发

- **往「单结果」端点加状态时，先问「这个状态集合是否本来就存在」**：单飞契约管的是进度呈现数量，不管状态覆盖范围——用「返回一个任务」推导「排队不可见」是过度推理。
- **进度类 UI 的判据必须是「值在变」**：任何只在边界更新的计数（n/N），在边界间隔可达分钟级时，必须补边界内的连续量（字节/时间），否则一律视为「冻结态」缺陷。
