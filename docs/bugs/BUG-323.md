# BUG-323 下载设置「目录路径」无逻辑：默认根=库根（内部 AppData 隐藏路径），WEB 下无法挑目录

- 状态: fixed
- 发现日期: 2026-10-16
- 模块: engine+shell
- 严重程度: high

## 现象（用户原话）

> 先修复 下载设置 的目录路径问题:
> 1. 无法修改目录,不论WEB和APP哪种方式都应该可以修改路径吧?
> 2. 默认和库根完全脱离,甚至错误,毫无逻辑性. 目录应该默认下载,可以切换用户设置目录.

## 根因（活栈实测，2026-10-16）

四条独立缺陷叠加（①②③ 为首次定位，④ 为本次验收中新增断言查出）：

### ① 默认下载目录错误：被绑到「库根/下载」，而库根默认是内部 AppData 隐藏路径

首次定位时活栈 `GET /api/config` 实测：

| 字段 | 值 |
|---|---|
| `default_download_dir` | `C:\Users\godcong\Downloads`（平台默认，正确） |
| `download_dir` | `null`（未配置） |
| `library_dir` | `C:/Users/godcong/AppData/Roaming/com.origadmin.orighub/tg/library`（**内部隐藏路径**） |
| `manual_download_root` | `…AppData/Roaming/com.origadmin.orighub/tg/library\下载` |

根因链：
- `orig-daemon/src/config.rs::manual_download_root()`（D23-A①）在 `download_dir` 未配置时返回 `<library_dir>/下载`；
- 而 `library_dir` 的默认由 `orig-tg/src/store.rs::library_root()` 解析链末端给出 = `<TG 数据目录>/library`（内部 AppData）；
- 二者相乘 ⇒ 「默认下载目录」= `…AppData/…/tg/library/下载` —— 用户永远找不到，且与系统 `Downloads` 完全脱离。

设计文档 `docs/design/cache-root-unification-2026-09-28.md` R2/C1 早已定案：**`download_dir` 默认值唯一真源 = `orig_core::paths::default_download_dir()`（平台 Downloads）**。D23-A① 的 `<库根>/下载` 覆盖了它。

### ② 前端把内部 AppData 库根回填进 daemon（耦合固化）

`SettingsPanel.tsx`（load effect）在「daemon 的 `library_dir` 为空且 TG 有值」时 `saveLibraryConfig({ dir: tgLib })` —— 把 TG 的内部 AppData 库根写进 `download-engine.toml` 的 `library_dir`。实测该文件即含：
`library_dir = "C:/Users/godcong/AppData/Roaming/com.origadmin.orighub/tg/library"`。
回填的唯一目的是让 D23-A① 的 `<库根>/下载` 生效；默认根改正后它反而固化了内部路径。

### ③ WEB（网页调试模式）下「浏览…」按钮被禁用 ⇒ 没有挑目录的入口

`DirectoryPicker.tsx` 原为 `disabled={disabled || !inTauri}`，且 `pick()` 在非 Tauri 时只做
「软失败 + 提示」。CDP 实测：

- `download-dir` 输入框：`disabled:false / readOnly:false`，输入被接受，保存后值落库；
- **「浏览…」按钮 `disabled: true`**（title：网页调试模式不支持系统原生目录对话框）。

即：WEB 下唯一「改目录」的直觉入口（选择器）是死的，手输虽可用但非显性。
违背 BUG-179「调试与生产同一产品，禁第二套可用性语义」。
**而桌面壳早已能遍历整个文件系统**（`capabilities/default.json` 的 `dialog:allow-open`），
所以「WEB 不能挑目录」并非能力缺失，而是通路缺失。

### ④ 界面与引擎真源漂移：引擎「未配置」时界面沿用本地旧值（本次验收断言查出）

`SettingsPanel.tsx` load effect 原为：

```ts
if (c.download_dir) { setDir(c.download_dir); updateSettings({ downloadDirectory: c.download_dir }) }
```

有值才同步、**为空不管** ⇒ 本地镜像（localStorage `orig-hub:settings.downloadDirectory`）里的
旧值被沿用，界面显示一个引擎根本不会使用的目录：同一屏里「当前生效」写平台 Downloads、
输入框却写着别的路径。用户侧的观感就是「改了像没改 / 改不动」。
判据（本次新增）：把镜像污染成 `D:\stale-not-the-engine-dir`、引擎置空后重载 ——
旧实现下界面**照旧显示该脏值**（实测 `input="D:\stale-not-the-engine-dir"`）。

## 复报注记（2026-10-16 第二次，规则层）：单一根 —— 库根跟下载走

用户原话：

> 严重逻辑问题毫无修复. 库根跟下载走,所有文件不允许脱离下载路径,下载路径是所有权限的限制路径.

### 我上一轮的逻辑错误（必须记录）

上一轮我把「默认下载根」与库根**解耦**（`manual_download_root()` 恒返回平台 Downloads），
并把「撤销两者耦合」当成修复 —— 这与用户要的方向**正好相反**。

解耦之后系统里仍存在**两个互相独立的根**：下载路径（平台 Downloads）与库根
（`…AppData/…/tg/library`）。归仓字节照旧落在 AppData —— 即**文件仍然脱离下载路径**。
用户的原话「默认和库根完全脱离,甚至错误」批评的正是这种「两个根各走各的」，
而我把它读成了「解耦」并据此加固。方向性错误，非表述问题。

### 用户裁定后的规则（本缺陷的真正判据）—— **已作废，见下方第三次裁定**

<details><summary>作废内容（保留作历史）</summary>

| 规则 | 内容 |
|---|---|
| **R1 单一根** | 下载路径是全部用户内容字节（下载成品、归仓媒体、转码代理）的**唯一容器**。 |
| **R2 库根从属** | 库根 = `<下载路径>/library`，**派生值**，不可独立配置。 |
| **R3 权限边界** | 任何按路径的读/删/列举，解析后必须落在下载路径之内，越界一律拒（403）；库根不可配，故「脱离」在接口层与结构上均**不可表达**。 |

> 作废原因（用户 2026-10-16 裁定）：R1/R2 把「管理」坍缩到「下载」之下，与项目实际模块结构
> （`files` 管理 / `download` 下载 / `tg` 插件 / `share` 共享 为平行一级域）冲突。管理不应受
> 下载路径约束。下载根只是「默认受管根 + 新下载落点」，其余受管根由用户添加。

</details>

### 三条缺陷与修法

| # | 缺陷 | 修法 |
|---|---|---|
| ⑤ | 库根解析链四级（env → `app_setting.library_dir` → `config.json.libraryDir` → `<TG 数据目录>/library`），后三级都能把库根指到下载路径之外 | `orig-tg/src/store.rs`：`library_root()` 改为 `download_root().join("library")`；新增 `download_root()`（env `ORIG_TG_DOWNLOAD_DIR` → `app_setting.download_dir` → 平台默认）；**删除**后两级配置来源 |
| ⑥ | 库根有两个可写入口（daemon `PUT /api/config/library`、TG `PUT /api/tg/config {libraryDir}`），前端两边都写 | 两个端点**恒 422** 并直出正确做法；前端 `api/tg.ts` 整段配置读写通道删除；`SettingsPanel` 库根改**只读展示**（`data-testid="lib-root-readonly"`，无输入框） |
| ⑦ | 权限边界只在删除路径上，字节**出口**（缓存流 / raw / 转码源）不校验，历史绝对路径可直接服务到界外 | 新增 `cache::resolve_managed_path()`（词法归一化 + 边界判定）与 `path_within`/`lexical_normalize`；`local_file`、媒体 `/raw`、转码源三处字节出口一律 403 |
| ⑧ | 转码代理 <br>`<TG 数据目录>/proxies` 在下载路径之外（同为媒体字节） | `proxy_dir()` → `<下载路径>/.orighub/proxies`（`.` 前缀保证不进成品扫描）；`config.rs::default_download_dir()` 改为委托 `orig_core`（消除第三份实现） |

### 存量迁移（规则落地的保命线）

库根改为派生后，旧根下的存量字节会**整片失联**（库根相对路径解析到新根为空；绝对路径被新的
403 闸门挡住）。实测存量：`…AppData/…/tg/library` **204 个文件 / 24.3 GB**；
`media_item.file_path` 337 条有值（132 相对 / 205 绝对，其中 65 条前缀为旧库根）。

- `Store::migrate_legacy_managed_roots()`（orig-tg 启动时执行一次，失败不阻断启动）：
  递归**移动**旧落点内容到下载路径内（同卷 `rename` 优先，跨卷 copy + 校验大小 + 删源），
  **绝不覆盖**同名项（跳过并计数），并把 DB 里 `media_item.file_path` /
  `media_message.file_path` / `cache_task.dir` 的前缀逐行改写（大小写不敏感、
  只认分隔符边界；同值多行按一次改写计）。
- **旧落点是两处，不止库根**（同日复报补测）：`<TG 数据目录>/library`（旧库根）与
  `<TG 数据目录>/downloads`（BUG-323 之前 `Config::default().download_dir` 的值）。
  后者实测压着 **33 个文件 / 3.5 GB 真实媒资**（`11f018a2…--1004457697592-1013.mp4` 等
  90–160 MB 的成片），三张表分别有 26 / 32 / 18 条记录指向它 —— 只搬库根等于把这些片子
  整片变成「取不到」。
- 幂等：旧落点不存在/为空/与新落点互含 ⇒ 无事可做；有跳过项时保留历史 setting 以便下次
  重试（静默丢弃冲突项等于替用户做减法）。
- 回执落 `data_dir/legacy-roots-migration.json`（`{roots:[{name,from,to,moved,skipped,rewritten}]}`）。
- **不搬什么**：用户外部导入的引用（`source=local`、路径由 `POST /api/media/items` 显式给出）
  不在此列 —— 那是用户自己的文件，引擎不搬别人的东西（其可读性见下方「待拍板」）。

### 配置真源收敛（daemon 唯一入口）

- `PUT /api/config/download` 保存后**立即**把生效路径推给 orig-tg
  （`state::push_tg_download_root`，失败不静默、`tg_error` 直出界面）；
- `tg_supervise` 巡检每轮比对「上次成功同步值」，变了就补推 ⇒ 用户改完目录**无需重启**，
  TG 掉线恢复后也会自动对齐；
- `GET /api/config` 契约变更：新增 `library_root`（派生）与 `effective_download_root`，
  **移除** `library_dir`（可配语义已废）；`files.rs::walk` 排除根层 `library` / `.orighub`，
  避免媒体库文件混进「下载成品」。


## 复报注记（2026-10-16 第三次，用户裁定推翻刚性单根）：下载单根 / 管理多根

### 用户原话（两处裁定）

> 管理是管理,下载是下载. 下载单根,管理多根(下载根为默认主不可删除,可以设置切换主) 大致是这个思路.

> 「主根」不是路径吗?

### 逻辑错误（必须记录）

第二次裁定（R1/R2/R3 刚性单根）把「库根从属下载路径」当成不可动摇的边界，于是
`resolve_managed_path` 的闸门只认**下载根**。但项目实际模块结构是平行的五个一级域
（`files` 管理 / `download` 下载 / `tg` 插件 / `share` 共享），管理域**不该**被下载路径约束。
把「管理多根」硬塞进「下载单根」之下，是架构层面的错误归并。

用户纠正后结论：
- **下载模块 = 单根**（引擎生产者，单一输出目录）—— 刚性单根对**下载**是对的，保留。
- **管理模块 = 多根**（受管根之并集）；下载根是其中一员，且**默认主 + 不可删除 + 可切换主**。
- **「主根」就是一个被标记 `is_primary` 的受管根路径**；「切换主」只是把那面旗移到另一条
  路径上，**只改管理视图默认选中，不动下载落点、不重定向写入**。
- 安全模型从「单一根」改为「受管根之并集」：删除安全 / 越界 403 覆盖**并集**，不再只认下载根。

### 新规则

| 规则 | 内容 |
|---|---|
| **R1′ 下载单根** | 下载模块守单根：`resolve_managed_path(download_root, …)` 原签名不动，下载永远落 `download_dir`（引擎生产者输出目录），不受管理模块「主」影响。 |
| **R2′ 管理多根** | 管理模块守**受管根之并集**。受管根集合含：下载根（恒 `locked`、由 `download_dir` 派生、不入用户数组以免与 daemon 下发双真源）+ 用户增删的根。 |
| **R3′ 主根语义** | 主根 = 一条被标 `is_primary` 的受管根**路径**；切换主仅改管理视图默认选中，**不决定下载落点、不重定向写入**。 |
| **R4′ 并集边界** | 管理域的读/删/列举经 `resolve_managed_path_union(roots, …)`（含 `path_within_any`），解析后须落在任一受管根之内，越界一律拒（403）。下载域仍用自己的单根闸门。 |

### 分层落地范围

- **Stage 1（引擎层，已实现，未走验收）**：
  - `orig-tg/src/store.rs`：`ManagedRoot{path,primary,locked}`（模块级结构）+ `managed_roots()` /
    `add_managed_root` / `remove_managed_root`（locked/下载根 显式 422，不吞成幂等）/
    `set_primary_root`；用户根持久化于 app_setting `managed_roots`，下载根由 `download_dir` 派生。
  - `orig-tg/src/cache.rs`：新增并集闸门 `resolve_managed_path_union` / `path_within_any`（与下载单根
    闸门 `resolve_managed_path(download_root,…)` **平行**，互不替换）。
  - `orig-tg/src/routes.rs`：`GET/POST/DELETE /api/fs/roots`、`POST /api/fs/roots/primary`、

|---|---|---|

### 2. 根因

`orig_core::paths::default_download_dir()` 解析 OS 已知文件夹（`~/Downloads`），
而它就是**内容默认根** ⇒ 装机未显式配置时，库根/缓存/blob/代理全部落进系统盘。
前四轮复报都在修「路径语义」，没有一条规则说「内容不得落系统盘」。

### 3. 修法（按用户对默认值的说明分两层）

| 层 | 落点 | 行为 |
|---|---|---|
| 名义默认 | `paths::default_download_dir()` | **保持** `~/Downloads`（用户：「~/Downloads是默认设置」），只作「未配置」的占位概念 |
| 禁用盘判定 | `paths::is_forbidden_content_drive` + `FORBIDDEN_CONTENT_DRIVE = "C:"` | 解析结果在禁用盘 ⇒ 判为「不得采用」 |
| 实际内容根 | `paths::CONTENT_ROOT` / `content_root()` = `D:/OrigDown` | 禁止盘的解析结果一律改取它，并 `tracing::warn!` 留痕 |
| daemon 侧 | `config::effective_download_root` / `manual_download_root` | 同一规则（未配置、显式填 C:、env 注入 C: 全改道） |
| orig-tg 侧 | `Store::download_root`（env / setting / 默认三级） | 同一规则；`ORIG_TG_LIBRARY_DIR` 是运维覆盖，不改道 |
| 存量来源识别 | `paths::os_download_dir()` | **只**给启动迁移指名「字节原来在 `~/Downloads`」，绝不作写点 |

### 4. 搬迁（已执行，非夹具）

副本落 `D:/OrigDown`：`library`（211 文件 / 23.71 GB）、`legacy-downloads`（33 / 3.45 GB）、
