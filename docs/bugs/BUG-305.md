# BUG-305: 媒体库「在 TG 中查看」仅落 t.me 外链，缺应用内跳转（插件→对应频道→对应内容）

- 状态: fixed
- 发现日期: 2026-10-14
- 模块: shell
- 严重程度: high

> 来源：用户 2026-10-14 追问「在 TG 中查看 的逻辑没有修复,是不能修复还是没有记录? 插件->对应频道对应内容.」
>
> **本档为任务文档**（用户定：纯文档任务，代码由别的组负责；本组只负责登记与判据）。
> **登记规范**：遵循「内容数据不入库」原则（见 BUG-232）：**不含真实频道名 / 消息文案**；
> 实测标识一律以占位符表示（`<chat_id>` / `<msg_id>`）。
>
> **与 BUG-285 的边界（不可混淆）**：
> BUG-285 的 `fixed` 仅对「**存在**一条指向 TG 源消息的入口」成立——其落地形态是
> `SeriesDetail.tsx` 剧集详情「来源」块里的一个 `<a target="_blank" href="https://t.me/c/<chat>/<msg>">`
> 外链（open-in-browser）。**本档跟踪的是 BUG-285「修复方向 §2（复用反向跳转同构机制，P0）」
> 从未落地的部分**：应用内不离开页面、切到 TG 插件面板、定位对应频道与消息。

## 现象

用户在媒体库看到一条 TG 来源的内容，想「回到它来自 TG 的哪条消息、在哪个频道」时：

1. **应用内没有这条路径**。从媒体库卡片 / 列表行点不出任何「跳到 TG 面板并定位」的动作——
   唯一存在的「在 TG 中查看」只在**剧集详情页的「来源」块**（必须点进某集详情、再翻到来源行），
   且点开是**离开应用去 t.me 网页**，不是「在应用内切到 TG 插件、选频道、定位消息」。
2. 用户从媒体库网格/列表的视角看，**根本不存在**「在 TG 中查看」入口（入口埋在两级之下）。
3. 即便找到那个入口、点开 t.me，也只是跳到 Telegram 网页版，**与「插件→对应频道→对应内容」
   这条应用内链路无关**——用户要的是在 OrigHub 内从媒体库钻到 TG 面板的正确频道、正确消息。

⇒ 用户感知「逻辑没有修复」成立：**对「应用内跳转」这一语义，确实没有修复**；
BUG-285 的 `fixed` 是对「有外链入口」这一弱子集的标记，不覆盖本档范围。

## 根因

**数据层坐标齐全，但前端没有「正向 TG 焦点」的接收与消费机制。**

### 事实 1：坐标一直都在（可修，非不能修）

- 条目：`media_item.source/ref`，`ref='<chat_id>:<msg_id>'`（`routes.rs:1793` 构造）。
- 剧集：`media_series.source_key='tg:msgs:<chat>:<first>'`（`routes.rs:2295`），反查 `find_series_by_source_key`（`media.rs:3687`）。
- 前端 `MediaEpisode.ref` / `EpisodeSourceRef.ref` 已是 TG `<chat>:<msg>`（`api/media.ts`）。

⇒ 任意条目用 `ref`、任意剧集用 `source_key` 都能解析出 `(chat_id, msg_id)`。**缺的不是数据，是链路。**

### 事实 2：应用内无正向跳转接收器

- **grep `setPendingTgFocus / focusMessage / goToChannel / pendingTgFocus` 全仓 0 命中**。
- 唯一的跨视图焦点是**反向**的 `pendingMediaFocus`（`useStore.ts:185-192`，注释「入库流水线 → 媒体库」，形如 `<chatId>:<msgId>`）——把「流水线 → 媒体库」打通；
  **没有**「媒体库 → TG 面板」的对应 store 契约。
- `TgPanel` 的 `selectedChannel` 是**组件内部 state**（`TgPanel.tsx:655` 的 `useMemo`/本地），
  没有「外部点一下就切到某频道、滚动到某消息」的 API；频道选择 / 消息定位完全由面板自身驱动。

⇒ 要打通「插件→对应频道→对应内容」，必须新增：①store 正向焦点 + setter；②TgPanel 消费它选频道+定位消息；③媒体库入口把动作从「开 t.me」改为「设焦点 + 切 TG 面板」。

## 复现

1. 打开媒体库，找到一条 `source==='tg'` 的条目/剧集（其 `ref` 形如 `<chat_id>:<msg_id>`）。
2. 在媒体库**网格/列表卡片**上找「在 TG 中查看」入口 —— **不存在**（入口只在剧集详情源块）。
3. 点进剧集详情 → 来源块 → 点「在 TG 中查看」—— 行为 = **新标签打开 t.me 网页**，
   应用仍停在媒体库/详情，**TG 面板未被激活、频道未切换、消息未定位**。
4. 想「在 OrigHub 内从这条内容钻到 TG 对应频道对应消息」—— **做不到**。

## 修复方向（本档不改代码；由别的组实施）

1. **store 新增正向焦点（P0）**：与 `pendingMediaFocus` 同构反向——
   `pendingTgFocus: { chatId: number; messageId: number } | null` + `setPendingTgFocus`。
   约定：媒体库侧入口消费坐标后 `setPendingTgFocus({chatId, messageId})` 并 `navigate('tg')`。
2. **TgPanel 消费焦点（P0）**：监听 `pendingTgFocus`——
   切到 `channelId===chatId` 的频道（必要时先 `addTgMonitoredChannel` 或按已监控列表定位）、
   在消息流中定位 `key=\`s-${chatId}-${messageId}\`` 并滚动进可视区 + 高亮，随后 `setPendingTgFocus(null)`。
3. **入口扩面 + 改动作（P0）**：
   - 媒体库**卡片**（`MediaCard`）、**列表行**、**剧集详情来源块**均渲染「在 TG 中查看」；
   - 动作改为「设 store 正向焦点 + 切 TG 面板」（应用内），**不再**只开 `t.me` 外链
     （外链可保留为次要出口，但必须另有应用内主入口，否则判据 FAIL）。
4. **坐标口径（同 BUG-285 §修复方向 ①）**：条目用 `ref`、剧集用 `source_key` 反查；
   `source==='local'` 或坐标缺失/为空 ⇒ **不渲染**入口（无 TG 消息可跳）。
5. **不回退反向跳转**：`pendingMediaFocus`（流水线 → 媒体库）不得被改/删（BUG-285 判据 ⑤）。

## 修订（2026-10-14 落地时）：实施边界与四个决定

> 历史锚定（BUG-082 先例：追节不改写正文）：本修订**不**改写上方任何叙述，
> 只在文末追加，标明落地后的真实边界与依据。

### 1. 实施主体

上方「本档为任务文档（代码由别的组负责；本组只负责登记与判据）」是登记时的分工口径；
本档最终由**本组**实施并验收。

### 2. 剧集级坐标经「聚焦分集」解析（API 不暴露 series.source_key）

`/api/media/series` 列表与详情均不下发 `source_key`，剧集级坐标改由 SeriesDetail
**当前聚焦分集**的 `source` / `ref` 解析（与 BUG-285 `sourceMessageUrl` 同一口径），
不新增后端字段。系列墙 → 详情默认聚焦第一集，入口即取该集坐标。

### 3. 未监控频道先入监控再定位

跳转目标频道若未监控，先 `addTgMonitoredChannel`（幂等）并刷新监控列表，再选中 ——
监控频道的消息流是本地真列表（键 `s-<chat>-<msg>`），可定位；未监控的在线流键
`l-<chat>-<msg>` 仅作防御性兜底。

### 4. 定位循环有界翻页（目标消息常不在第一页）

实测目标消息在第 4 页（每页 30 条）。定位循环每 300ms 探一次 DOM，未命中且
`hasMore` 时有界翻页（上限 20 页），翻完仍没有 ⇒ 停表、清状态并给
`tg.locateFailed` 如实反馈 —— 不无限轮询、不静默假装成功。

### 5. BUG-285 外链 testid 原样保留

`episode-source-view-tg`（`<a target="_blank">`）**不改名**（BUG-285 判据①a 依赖它），
应用内主入口启用新 testid `episode-source-jump-tg`；两者同在来源块主版本行，
主入口在前、外链降为次要出口。
