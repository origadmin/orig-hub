# BUG-113：单集多视频 —— 多源结构已有，但缺「质量」与「主版本」语义

- 状态: open
- 严重程度: high
- 模块: engine+shell
- 发现日期: 2026-09-22

**用户诉求（2026-09-22 原话）**：

> 「单集多视频」这是需求，必须实现。加入或者合并剧集后，如果遇到多个视频源，总有高质量和
> 低质量的，总有一个为主的。

即三点：**一集可有多源**、**多源之间有质量高低**、**有且仅有一个主版本**。

## 现状（实地取证，非推测）

多源结构**已经存在**（BUG-039 引入），不是从零开始：

```sql
-- media.rs:366-375
CREATE TABLE IF NOT EXISTS media_episode_source (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    episode_id INTEGER NOT NULL,
    item_id    INTEGER NOT NULL UNIQUE,   -- 全表唯一
    created_at INTEGER NOT NULL,
    UNIQUE(episode_id, item_id)
);
```

配套的读写接口也齐了：

| 能力 | 位置 |
|---|---|
| `POST /api/media/episodes/:id/sources` 挂备用源（幂等） | `routes.rs:2853` |
| `POST /api/media/episodes/:id/sources/primary` 主备切换 | `routes.rs:2867` |
| `DELETE /api/media/episodes/:id/sources/:item_id` 摘除 | `routes.rs:2880` |
| 读路径一次性补全各集 `sources`（避免 N+1） | `media.rs:1259-1286` |
| 前端三个同名函数 | `api/media.ts:374-392` |

## 真正的缺口

| # | 缺口 | 证据 |
|---|---|---|
| 1 | **无质量维度**：没有 `quality` / `bitrate` 字段，无法表达「这个源更清晰」 | 建表只有 `created_at`；`media_item` 只有 `size/duration/width/height`，无码率 |
| 2 | **主版本是隐式的**：主源 = `media_episode.item_id` 那一行，没有 `is_primary` 列 | `media.rs:249-257`；生产建表（366-375）无 `is_primary` |
| 3 | **排序与质量无关**：备用源按 `created_at ASC` 排 → **先来的是主** | `media.rs:1268` `ORDER BY s.created_at ASC, s.id ASC` |
| 4 | **UI 盲目切主**：只有一个「N 源」按钮，点击把 `sources[0]` 提为主，用户看不到质量、无法选择 | `SeriesDetail.tsx:692-709` `switchEpisodeSource(ep.id, ep.sources![0])` |
| 5 | **挂载 / 摘除备用源在 UI 上根本不存在**：`attachEpisodeSource` / `detachEpisodeSource` 只在 `api/media.ts:375` 与 `:391` **定义**，**全前端零调用**（grep `tauri-shell/src` 只命中定义处）—— 用户只能「切主」，**既不能挂、也不能摘** | 产品经理取证，主理人复核 |

于是「有一个为主的」这条在**数据层无法表达、在 UI 层无法呈现**：谁是主取决于**谁先被
缓存**，而这恰恰与质量无关。

## 更正一条此前写错的结论

`docs/review/media-tg-review-2026-09-22.md` 第 20、67-69、204-209 行曾断言
「**单集多视频在数据模型上就不可能实现**」。**该结论错误**：它只看了
`media_episode.item_id` 是 1:1（这本身没错），**却忽略了已存在的 `media_episode_source`**。

教训（已同步进项目记忆）：**「主入口 1:1」不等于「整模型 1:1」**；评审里写「不可能」这种
断言之前，必须把**该实体相关的所有表**列一遍再下结论。评审文档相应段落已随本条更正。

## 硬约束（改造时不得违反）

- `trg_media_episode_source_video_only_ins/upd`（`media.rs:485-498`）：`media_episode_source`
  **只接受 `kind='video'`**，图片永远不能成为播放源。这是 BUG-044 定的规则级不变量，
  由**数据层触发器**表达，不要退化成应用层校验。
- `media_episode_source.item_id` **全表 UNIQUE**：同一内容只能是一集的源。
- 建表批（`execute_batch`）里**只允许出现新旧库都存在的列**，否则旧库升级会整批失败、
  `Store::open` 回落空库，表现为「用户数据全没了」（BUG-032）。新增列必须走
  `pragma_table_info` 探测 + `ALTER TABLE ADD COLUMN`，照 `migrate()` 现有写法。

## 修复方向

见架构师增量设计：`docs/design/episode-multi-source-design-2026-09-22.md`。

要点（待设计确认后回填到本条）：质量字段的表达方式（离散等级 vs 连续量排序）、主版本
是否改为显式 `is_primary`、自动选主与手动指定的**防覆盖**设计、多视频聚成同一集的判据。

### 必须回答的两个设计问题

1. **自动选主会不会覆盖用户的手动选择** —— 若每次新增源都重算主版本，用户手动指定的
   结果会被悄悄改掉。必须有「手动指定优先」的标记与规则。
2. **什么情况算「同一集的多个源」而不是「两集」** —— 加入剧集 / 合并剧集时按什么判据
   聚合（标题？集号？TG 分组？）。判据不确定时宁可列待拍板，不要拍脑袋。
