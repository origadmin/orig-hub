# BUG-135：删除媒体条目时文件删除与 clear_downloaded 失败被静默吞——接口假成功

- 状态: fixed
- 发现日期: 2026-09-22
- 模块: engine
- 严重程度: mid

## 现象

删除媒体条目时，若磁盘文件删除失败（文件被占用、只读等）或 `clear_downloaded` 失败，接口照常返回成功，界面无任何提示——用户以为删干净了，实际字节还占着磁盘；下次按 `source+ref` 幂等 upsert 还会把条目「复活」（BUG-029 时代实测过的「删不掉」表象）。

## 根因

`routes.rs:2107-2140` `delete_media_item` 中两处吞错：

```rust
let _ = std::fs::remove_file(p);
let _ = st.store.clear_downloaded(chat, msg).await;
```

这与同文件 `reset_tg_flag` 的既有判定（BUG-109：「失败必须如实报错」）**自相矛盾**——同一个文件里两种纪律。

## 复现

Windows 下用播放器打开条目文件（占用锁）→ 在媒体库删除该条目 → 返回 200 成功，文件仍在磁盘。

## 修复

已修（`download-engine/crates/orig-tg/src/routes.rs` `delete_media_item`，提交 `4c6f07f`）：两条路径的 `let _ =` 全部拆掉，判定与同仓 `cache::reset_tg_flag`（BUG-109 那条规则）**并轨**，且**复用它而不是另写一份**（`reset_tg_flag` 因此改为 `pub(crate)`，清字节与删条目共用同一条「复位失败即如实报错」规则）：

| 失败 | 处置 | 理由 |
|---|---|---|
| 清 TG `downloaded` 失败 | **中止**删除，500 + 明确原因，条目一行都不删 | 标记没清掉 → 下次按 `source+ref` 幂等 upsert 会把条目「复活」，删除等于没删。「删了又回来」这个状态不允许存在 |
| `remove_file` 失败 | **不中止**（用户意图优先），warn 留痕（路径 + io::Error + 回收通道），响应 `bytesRemoved:false` + `bytesError` | 残留字节有兜底回收通道 `POST /api/cache/clear?scope=orphan`；但**不许说成成功** |

响应体在既有 `{ok, removed}`（幂等删除语义）之上**只新增**字段：成功带 `bytesRemoved: true` 且不带 `bytesError`；失败带 `bytesRemoved: false` + `bytesError: "<原因>"`。

前端对「条目已删但字节未回收」的可行动提示不在本次范围内（判据 1/2 只约束接口如实性），如需请另开单。

真实报文摘录（隔离实例 port 9879）：

1. 判据 1（不可删 → 必须报错，不得吞）：令文件被进程占用后再删该条目 ——

   ```text
   DELETE /api/media/items/3
   → 200 {"bytesError": "另一个程序正在使用此文件，进程无法访问。 (os error 32)",
          "bytesRemoved": false, "ok": true, "removed": 1}
   ```

   字节失败**不中止**删除（按处置表）：条目已删（随后 `GET /api/media/items/3` → **404**）、
   字节仍在磁盘上；失败**没有被说成成功**（`bytesRemoved:false` + 非空 `bytesError`）。

2. 判据 2（错误带可行动信息）：服务端日志实到 WARN ——

   ```text
   2026-09-22T19:34:28.967282Z  WARN orig_tg::routes: delete_media_item:
   remove_file failed for .../downloads/locked.mp4 (item 3): 另一个程序正在使用此文件，
   进程无法访问。 (os error 32); entry deleted anyway, bytes left behind
   (reclaim via POST /api/cache/clear?scope=orphan)
   ```

   （文件路径 + io::Error + 回收通道三项齐全；同一条也进 `/api/tg/logs`，脚本按此断言。）

3. **反向证伪**（清 TG 标记失败 → 中止并真报错，不是恒 200）：导入 `source=tg` 且
   ref 不可解析的条目后删除 ——

   ```text
   DELETE /api/media/items/4
   → 500 {"error": "cannot delete media item 4: the tg downloaded flag could not be
           cleared (see server log), so the entry would reappear on the next sync;
           nothing was deleted"}
   GET /api/media/items/4 → 200（条目仍在，中止生效，没被偷偷删掉）
   日志：reset_tg_flag: cannot parse tg ref "not-a-tg-ref"; downloaded flag left set
   ```

4. 正向对照（证明第 3 条的 500 由失败触发，不是「tg 条目一律拒删」）：
   可解析 ref（`-1001234567890:1`）的 tg 条目 → `200 {"bytesRemoved": true, "ok": true, "removed": 1}`。
   另：正常删除 → `200 {"bytesRemoved": true, "ok": true, "removed": 1}` + 文件从磁盘消失 + GET 404；
   幂等重删 → `200 {"bytesRemoved": true, "ok": true, "removed": 0}`（原有幂等语义未动）。
