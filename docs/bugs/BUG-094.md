# BUG-094: daemon 拉起 orig-tg 时用错数据目录且拿不到凭据，冷启动必然掉登录态

- 状态: fixed
- 发现日期: 2026-09-21
- 模块: engine
- 严重程度: high

## 现象

从桌面壳（Tauri）正常启动、不走 `verify_shots/restart_tg.py` 旁路时，daemon 拉起的
orig-tg 读不到已授权会话、也拿不到 API 凭据 → `/api/tg/session` 不会是 `Authorized`
→ 侧栏 Telegram 导航项（BUG-093 的门控）被过滤。

BUG-093 修的是「跑着的那个实例是离线的」，本条修的是「正常拉起来的那个也连不上」。
前者是环境残留，后者是真缺陷。

## 根因

两处叠加，任何一处单独存在都会导致失败。

### 1. 数据目录约定分裂

`download-engine/crates/orig-daemon/src/state.rs:186-215` 的 `tg_data_dir()`
（`ORIG_TG_DATA` 未设时）返回 ** `%LOCALAPPDATA%\OrigHub` **，于是
`tg_start_on()` 注入：

```
ORIG_TG_SESSION = %LOCALAPPDATA%\OrigHub\tg\session.session
ORIG_TG_DB      = %LOCALAPPDATA%\OrigHub\tg\store.db
```

而真实已登录的会话与凭据其实在 ** `%APPDATA%\com.origadmin.orighub\tg\` **：

```
session.session   65536 字节   2026-09-19 07:12:37
store.db        2818048 字节   2026-09-20 16:47:00
config.json         115 字节   含 api_id / api_hash / proxy
```

`%LOCALAPPDATA%\OrigHub\tg\` 下另有一份 `session.session`（57344 字节，2026-09-17），
是早期残留，**不是**当前登录态。两份并存本身就是目录约定分裂的产物。

### 2. 凭据从不落盘

`download-engine/crates/orig-daemon/src/config.rs:94-96` 定义 `tg_api_id` /
`tg_api_hash`（`Option<String>`，默认 `None`，见 `:109-110`）；
`state.rs:163-172` 只在二者非空时才注入 `ORIG_TG_API_ID` / `ORIG_TG_API_HASH`。

而实测仓库根 `download-engine.toml`（以及
`download-engine/download-engine.toml`、
`download-engine/crates/orig-daemon/download-engine.toml`）**都没有 `[tg]` 段**
（全文只有 `[classify]`）。`git log -p --all -- download-engine.toml` 也从未出现过
`api_id` / `api_hash`。

即：凭据只存在于 `%APPDATA%\com.origadmin.orighub\tg\config.json`，daemon 侧无处可得。

## 修法方向（待拍板）

架构师评估意见：**以 Tauri 侧注入为主，daemon 侧近乎零改动。**

- `tg_data_dir()` 已支持 `ORIG_TG_DATA` 覆盖（`state.rs:199-203`），
  桌面壳拉起 sidecar 时把 `app_data_dir()` 指进去即可；
- 凭据同理，由 Tauri 侧读 `config.json` 后注入 `ORIG_TG_API_ID` / `ORIG_TG_API_HASH`；
- **不应让 daemon 继续自猜目录**——每多一个「猜」的路径就多一份分裂的会话。

## 追加：存在自救死循环，用户无法自行恢复

QA 独立复核（2026-09-21）在评估「能否自愈」时挖出第三层——**不止连不上，而且坏了就修不回来**：

1. 唯一能正确拉起 orig-tg 的路径是 Tauri 壳的 `tauri-shell/src-tauri/src/lib.rs:382`
   `spawn_tg`：它用 `app_data_dir()` = `%APPDATA%\com.origadmin.orighub\tg`
   拿真实 session，并从同目录 `config.json` 读 api_id / api_hash / proxy。
2. 但 `spawn_tg` **只在 `ensure_tg`（`lib.rs:466`）与 `tg_save_config`（`lib.rs:501`）被调用**，
   而 Tauri 启动的 `setup` 阶段**不主动调用**它。
3. 前端唯一的自救入口是 `tgHealth()` 失败 → `ensureTg()`，两个调用点在
   `TgPanel.tsx:281` 与 `MediaLibraryPanel.tsx:62`。
4. 而 daemon 拉起的那个「无凭据实例」`/health` **恒返回 200** → `tgHealth()` 永不失败
   → `ensure_tg` 永不触发。`lib.rs:483` 那段「alive but unavailable → kill + respawn」
   也救不了，因为它同样挂在 `ensure_tg` 路径上。
5. 与此同时 `nav-tg` 已被 `Sidebar.tsx:316` 过滤掉 → **用户根本进不去 TgPanel**，
   连手动触发的机会都没有。

结论：**「UI 里配置一次 TG，下次冷启动又坏，且无法再进入 TG 面板重配」是必然复现的回退**，
不是偶发。QA 判定：从桌面壳正常启动**大概率无法**变成 `Authorized`。

实测运行时佐证：`GET /api/tg/diag` → `mode:"ready"`, `mock:false`,
`proxy:"socks5://127.0.0.1:7897"`（走旁路时）；而 daemon 侧 spawn 的实例不会有这些。

## 与 BUG-093 的关系

BUG-093 的旁路脚本之所以能连上，正是因为它绕过了这三处：它自己指向
`%APPDATA%\com.origadmin.orighub\tg`、自己从 `config.json` 注入凭据、且不依赖
`ensure_tg` 的自救链路。**这条旁路一直在掩盖本条缺陷。**

## 实施记录（2026-09-21，待端到端验收）

三处改动，均已通过 `cargo test` / `cargo build --release` / `cargo check`（shell）：

1. **目录（治本）** `tauri-shell/src-tauri/src/lib.rs` `spawn_daemon()`：拉起 daemon
   sidecar 时注入 `ORIG_TG_DATA = app_data_dir()`。**注意是父目录**——
   `download-engine/crates/orig-daemon/src/state.rs` 的 `tg_data_dir()` 内部还会
   `join("tg/session.session")`，传 `.../tg` 会拼出 `.../tg/tg/...`（第三份分裂会话）。
2. **凭据（治本）** `state.rs::tg_start_on()` 新增 `resolve_tg_env()`：
   `[tg]` 段为空时回退读 `<数据目录>/tg/config.json` 的 `api_id` / `api_hash`
   （数字与字符串两种形态都收）；`proxy` 仅在非 custom 代理模式下用 config.json 的值。
   文件缺失 / JSON 非法 / 字段缺失一律按「无凭据」继续，不 panic、不阻断启动，
   且不打印任何字段值。单测：`state::tests::tg_credentials_fall_back_to_config_json`、
   `tg_credentials_missing_or_invalid_is_empty`、`explicit_config_wins_over_config_json`。
3. **保命阀** `lib.rs` `setup`：后台线程调一次 `ensure_tg()`。原逻辑已自带
   「`tg_alive() && tg_service_real()` → 跳过」，故不会 kill 掉已健康的实例；
   未配置时返回 `Err("not-configured")`，只记日志、不影响出窗。

## 第三层修复：门控改为「进程可达即显示」（2026-09-21）

上面两段解决的是「为什么连不上」。这一段解决的是「连不上时用户为什么什么都看不到、也无从下手」。

`Sidebar.tsx:316` 原来的门控是 `tgBound && tgReady`，`tgBound` 取自 `phase === 'Authorized'`
—— 于是**只要连不上，整个 TG 入口就凭空消失**，失败原因无处展示，用户也进不去重配。

改动（分两个提交）：

- `7248204`（`fix(shell): keep TG nav visible when service is up but account unbound`）
  - `Sidebar.tsx:304` 门控改为只用 `tgReady`，`tgBound` 这一 prop 因只服务于该门控而移除；
  - `MainLayout.tsx` 删掉「未绑定 → 退回 all」那段（与新门控语义冲突：门控放行、它又弹回）；
    保留「服务摘除才弹回」，且语义从 `status === 'ok'` 放宽为**只有 `unreachable` 才隐藏**
    —— 即「进程可达即算服务在」，这是用户裁定「TG 服务在跑就显示入口」的本意；
  - `TgPanel.tsx` 新增未授权引导区（`data-testid="tg-unbound-guide"`）：状态说明 + 分类后的
    失败原因 + 去绑定入口，原文只进日志，**不新增任何轮询**。
- `22a3f59`（`fix(shell): make the TG binding entry reachable and share reason mapping`）
  - 修掉「出口不通」：引导区指向「设置 → 账号」，而 `AccountsPanel.tsx:45` 仍是旧门控
    `status === 'ok'`，绑定卡与登录按钮在当前状态下仍隐藏 → 用户点了出口却扑空。
    统一为同一语义（`unreachable` 才隐藏）；
  - `reason → i18n 键` 的分类映射抽成唯一真源 `tauri-shell/src/lib/tgReason.ts`
    （`classifyTgReason` / `logTgReason`），五个调用点统一走它，
    **不再有任何一处直出后端原文**（BUG-087 教训：同一语义多处各写各的会一起显示错值）。

实测（当前环境正是「服务活着但未授权」）：`nav-tg` **可见**；点击不弹回且渲染引导区；
UI 文案中 `MTProto` / `read 0 bytes` / `api_id/api_hash not configured` 等原文串**命中 0**；
`pageErrors` 为空；`tsc --noEmit` 0 错；`verify_ui_render.cjs` 19/19 PASS。

**保留不动的两处（有意为之）**：
1. 登录发码按钮在连不上时仍 `disabled` —— BUG-023 定下：连不上 Telegram 时发码必然失败，
   放进流程是误导。规则合理，未推翻。
2. 「连接诊断 → 最近日志」的 `<pre>` 块**保留原文** —— 那是日志查看器本身，
   是唯一排障依据；BUG-088 约束的是「喂给用户的错误文案」，不是排障日志。

## 端到端验收（2026-09-22 完成，环境阻断已解除）

此前卡在环境：socks5 代理（`127.0.0.1:7897`）上游到 Telegram 被切断 —— SOCKS5 握手与
CONNECT 均成功（`reply=0`），但经代理做真实 TLS 握手得到
`SSLEOFError: UNEXPECTED_EOF_WHILE_READING`，**只测 TCP 端口会误判成代理正常**。
当时对照组（改动前的旁路 `restart_tg.py`）同样失败，证明与改动无关。

代理恢复后，以 **daemon 冷启动**（非旁路脚本）复验，一次通过。详见下方「验收证据」。
