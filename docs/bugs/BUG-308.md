# BUG-308: 入库去重窗口只覆盖活跃任务——任务结束后同一 TG 消息可重复入队（重复下载字节 + 重复入库索引）

- 状态: open
- 发现日期: 2026-10-14
- 模块: engine
- 严重程度: mid
- 排期: 2026-11-26

## 现象

用户原则（2026-10-14 原话）：「一组数据只能入一次缓存吧?」

实际：一个组/单条缓存任务**结束之后**（终态 done/interrupted/failed），再次对同一批消息发起缓存，
系统不会拦截：
1. 字节被重新下载一遍（即使磁盘上原文件还在）；
2. `cache_task` 产生第二条入库记录——「入库 = TG 插件下载的索引」（用户 2026-10-14 定义）
   因此出现重复索引行，下载页同一内容出现多条历史。

注：`media_item` 因 `UNIQUE(source, ref)` upsert 不产生重复条目——重复只发生在**字节下载**与
**任务索引**两层。

## 根因

- `download-engine/crates/orig-tg/src/store.rs:1155` `active_cache_task_covering` 仅在
  **活跃任务**（queued/running）集合内用 `json_each(cache_task.items)` 查重；终态任务不参与覆盖判断。
- `enqueue_cache_task`（store.rs:1077-1124）入队路径没有「该 message 是否已被历史任务认领
  （media_item source+ref 存在）」的检查。
- 「字节已在盘」也无前置判断；重新下载后归仓命名带 msg_id（同一目标路径），表现为覆盖式重下。

## 复现

1. 对 TG 频道某视频发起缓存，任务 done，文件在盘；
2. 不删缓存，再次对同一消息发起缓存；
3. 预期：拦截并提示「已入库」（或只提供「重新下载」显式动作）；
   实际：产生新 cache_task 行并重新走完整下载。

## 修复

按 **D22=A②**（docs/design/module-restructure-2026-10-13/09...§14）：

- 入队前查**历史认领**：media_item `source+ref` 已存在 →
  - 字节在盘：拦截，标「已入库」，零字节下载、零新 cache_task 行；
  - 字节已失：走条目上的显式「重新下载/补字节」，复用原入库记录而非新建索引。
- 验收夹具：同一 (chat,msg) 连续入队两次 → cache_task 增量 0；字节删除后走「补字节」→
  cache_task 行数不变、item 行不变、file_path 重新点亮。
