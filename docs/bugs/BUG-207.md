# BUG-207 播放「还是不流畅」的定位与止损：重量级条目为 HEVC，Chromium 0 帧可解却无限风暴拉流

- 状态: fixed
- 发现日期: 2026-09-30
- 模块: shell
- 严重程度: high

## 现象

用户反馈：「还是播放器流畅问题…解码吃力：画面在丢帧，调低播放速度会明显更流畅。
有没有更好的算法? 不可能播放器可以,浏览器不行吧?」

## 实测定位（全部仪表化测量，非推理）

**投递层已排除**：BUG-199 环回不限速已在运行二进制中（target/release/orig-tg.exe
03:49 构建 > 修复提交 03:29；运行进程 04:13 启动）。实测 32MiB Range 响应
0.19s ≈ **174 MB/s**；可解码条目 598（720p AVC 1.9Mbps）仪表化播放 30s
**0 丢帧**、缓冲领先均值 14s、无长任务、`mediaCapabilities` smooth=true。

**解码层实锤**：库内重量级条目整类为 **HEVC（hvc1）**——

| 条目 | 规格 | 实测 |
|---|---|---|
| 472 | 1.78GB / 12.0Mbps / 1241s | videoWidth=0、**0 帧解码**、20s **137 请求** |
| 357 | 308MiB / 10.4Mbps / 249s | videoWidth=0、**0 帧解码**、20s **97 请求** |
| 598 | 72MiB / 1.9Mbps / 720×1280 | 620 帧正常呈现、0 丢帧、共 3 请求 |

（全库 167 条视频：码率中位 2.1Mbps、p95 8.2Mbps、max 12.0Mbps；>8Mbps 共 9 条。）

**机理**：本机 Chromium（WebView2/Edge）无硬件 HEVC → 0 帧可解，但音频轨能解、
时长正常、`currentTime` 照走。`preload="auto"` 的 `<video>` 永远等不到「可播」状态，
进入「缓冲 → abort → 重取」循环（BUG-033 的风暴形态在**不可解码**场景复活；
BUG-199 撤掉环回节流后无人压制它）——20 秒 97–137 个请求、GB 级无效 IO，把整页拖卡。

**回答用户之问**：「播放器可以，浏览器不行」对这一类文件是**事实**——本地播放器
（VLC/PotPlayer）自带软件 HEVC 解码；Chromium 只有硬件 HEVC（本机无）。
**没有任何投递/节流算法能变出解码能力**；结构性出路只有服务端转码
（H.264 8-bit，orig-hub 无 ffmpeg，属 orig-studio-ee transcode 域）。

## 修复（前端止损，BUG-207 本体）

`VideoPlayer`：`useDecodeHealth` 判定 `unsupported`（且条目应有视频轨，
新增 `hasVideoTrack` prop 防音频误伤）→ **立即停载**：`pause() +
removeAttribute('src') + load()`，中止在途请求；整屏 `role="alert"` 遮罩给出
可行动文案（`tg.decodeUnsupported` 已改为「已停止加载以避免无效流量；请用系统
播放器打开原文件」）。把无限风暴换成一次诚实的失败。

## 关联

- BUG-034：decodeHealth 探测（unsupported/strained 两态）的延续——此前「检出不作为」，本条补上「检出即止损」。
- BUG-199：环回不限速（投递层根因，已修并实测）；本条证明「解不动」场景会复活请求风暴，节流不是万能前置。
- BUG-122：27.6% MPEG-TS 误名 .mp4——同类「容器/编码与扩展名不符」家族。
