# BUG-438: 入库不随筛选标题归馆——同一批筛选内容散落成「每个相册一部剧」

- 状态: fixed
- 修复提交: 34d605a
- 发现日期: 2026-10-27
- 模块: engine+shell
- 严重程度: mid

## 现象

用户 2026-10-27 原话：

> 入库应该随筛选标题入库对应标题剧集

现状：一条文字筛选规则命中多个相册，勾选入库后在媒体库里落成**多部剧**，每部按
**该相册自己的 caption** 起名；没有一部以用户打的那段筛选词为名。于是「我刚才入库
的那一批」在库里不是一个整体，找不到。

## 根因（代码层逐行核对）

**筛选词只走到条目标题，从来不参与归集。两条链完全分离：**

1. 壳：`TgFilterPanel#ingest` 传 `titleHint: filter.keyword || filter.label`
   → `EnqueueCacheReq.title_hint`（`routes.rs:1536`）→ 落 `cache_task.title_hint`
   （`:1623`）→ 只在条目**自己没有 caption** 时用来补标题
   （`:2345` / `:2437`，BUG-436）。它**不在归档链上**。
2. 引擎归集另走一把键：`Store::file_items_into_series`（`media.rs:5490`）按
   `episodic_group_key(chat, normalized_name, group, first)`（`routes.rs:4757`）落：
   - 命中在任务里且有 group ⇒ name = **组内 caption**（`tg_group_facts`，BUG-378
     定为权威源；为空则回落 `first_caption`；再空則 `tg:group:{chat}:{gid}`）；
   - 不在任何任务里 ⇒ name = 归一化的**条目自己标题**；
   - 两者都空 ⇒ `tg:group:` / `tg:msgs:{chat}:{first}`。
   新建剧集的名字再取 `fallback_series_title(&title, &kind, item_id)`
   （`media.rs:1947`，调用点 `:5586`）＝ 条目自己的标题。

   ⇒ 无论走哪条支路，键与剧名的原料都是 **caption 或条目标题**；`title_hint`
   不在这条链上，故**筛选规则在引擎侧没有任何归档含义**。

这与面板自己的定位互相矛盾 —— `TgFilterPanel` 头部注释明写：「一条筛选规则 =
一条虚拟监控频道」。既是虚拟频道，就该有归档面。

## 合理性评估（差异在哪、哪一边该动）

| 维度 | 用户口径 | 现状口径 | 判定 |
|---|---|---|---|
| 筛选规则是什么 | 一条虚拟监控频道 ⇒ 天然归档轴 | 只是查询条件，出库即丢 | **需求与注释一致，现状自相矛盾** |
| 条目显示名叫什么 | 未涉及 | caption ＞ 筛选词 ＞ 组内 caption（BUG-436） | **保留不动**：展示层要真名（BUG-154 / BUG-310） |
| 归到哪部剧 | 应为筛选标题 | 每个相册各自的 caption 名 | **这是真差异**，且用户不可见既成事实 |
| 性能 | —— | 现状零额外查询 | 推荐方案同样是零额外查询 |

结论：**需求成立，但不能用「改标题」的方式实现。**把筛选词同时当标题会连条目真名
一起盖掉（与 BUG-154「不拿别的字段伪装标题」相悖，`xxx EP01` 这种真名会消失）。
正确切法是**两条轴分开**：显示名照旧走 BUG-436，归档面新增一条只在筛选入库时下发的
可选 hint。

## 修复（已实施：方案 A）

用户 2026-10-27 补的约束：**标题一般是剧集标题，标题可改且不该影响后续入库** —— 这条约束
直接决定了实现必须「键与剧名分离」，否则改名 = 拆剧。

1. `EnqueueCacheReq` 增可选 `series_key` / `series_hint`（camelCase：`seriesKey`/`seriesHint`）。
   只有 `TgFilterPanel#ingest` 传：`seriesKey = tg:filter:{filter.id}`、
   `seriesHint = filter.label || filter.keyword`。
2. `cache_task` 增两列（可空 TEXT，幂等 migrate `migrate_cache_task_series_filing`）；
   写入沿用 `set_cache_task_title_hint` 的同样拆法（不动 `enqueue_cache_task` 签名，
   避免牵连几十处调用点），且**只在新建任务时写**：复用活跃任务时这批消息并入的是
   原来那条任务的家，不该被第二个筛选词抢走。
3. `cache_task_msg_index` 的第 4 项带上 `(series_key, series_hint)`（按任务 `Arc` 共享，
   不给每条消息克隆字符串；那个 SELECT 本来就在加载全部 `cache_task` 行 ⇒ **0 额外查询**）。
4. `file_items_into_series`：任务行有 `series_key` ⇒ **优先用它作键**；
   剧名只在 `create_series` 那一刻取 `series_hint`（miss 时），其余分支逐字保持原样
   （组内 caption / 条目标题 / `tg:group:` / `tg:msgs:`，BUG-292 / BUG-378 不受影响）。

**KEY 与 NAME 分离就是「改名安全」的机制**：`find_series_by_source_key` 命中既有剧集时根本
不用剧名，`create_series` 也只在 miss 时调用 ⇒ 用户改过的名字既不拆剧也不回滚。

## 验收证据

单测：`download-engine/crates/orig-tg/src/media.rs`
`filter_ingest_files_into_its_own_series_and_survives_rename_bug438`，三条判据 ——

1. 两个不同相册（caption 分别为「相册甲」「相册乙」）带同一个 `series_key`
   ⇒ `created == 1`（一部剧），且键是 `tg:filter:7`、**不是** `tg:named:600:相册甲`；
   新建剧集的剧名 = `series_hint`（「我的筛选」）；
2. **改名后**（直接 `UPDATE media_series SET title='我改过的名字'`）同 key 的新条目
   ⇒ `(created, attached) == (0, 1)`，`COUNT(*) FROM media_series == 1`，
   且名字仍是用户改过的 ⇒ 改名既不拆剧、也不被回滚；
3. 条目自己的标题仍是它的 caption（归档轴不渗透显示名，BUG-154）。

**判据验牙（反向变异）**：把 `explicit_filing` 置空（等价于回到「只看组内 caption」的旧实现）
跑同一用例 ⇒ `created = 2`（两个相册两部剧，正是 BUG-438 的现象）⇒ FAIL；复原 ⇒ PASS。

全回归：`cargo test -p orig-tg --lib` ⇒ **341 passed / 1 failed**；
唯一红灯 `cache::tests::priority_endpoint_rejects_malformed_requests_bug277` 是**既有缺陷**
（BUG-419：已置顶任务无法取消置顶），此前已用 A/B 证明在本轮改动前同样失败，与本条无关。
壳侧 `tsc --noEmit` 通过。

## 不做什么（刻意）

- **不**给存量任务回溯归档：`series_key` 为空时保持现状 —— 与「删规则不动已入库
  消息」的既有口径一致。
- **不**改 `normalized_series_name` / `episodic_group_key` 现有分支：频道视图、
  客户端直传、自动自愈三条路径的键必须与原口味一致，否则会重现 BUG-292 的裂剧。

## 复现（老旧现象）

建一条命中多相册的规则 → 面板入库 → 断言媒体库里出现 **1 部**以筛选词为名的剧集
（修复前：N 部、以各相册 caption 为名）。
