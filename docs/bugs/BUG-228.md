# BUG-228: 外部实例占用端口 + link 断 ⇒ tg_reselect_port 每次重启把端口迁走，形成端口漂移风暴、前端跟着配置来回跳

- 状态: open
- 发现日期: 2026-10-09
- 模块: engine
- 严重程度: mid
- 排期: 2026-11-26

## 现象

daemon 的 `/api/config` 下发 `tg_port` 在 19787/19788 之间来回跳（实测每 1-2.5 分钟一次），
`tg_running` 随之抖动；前端 `tgService.port` 跟着校准，已打开的播放器流 URL（绝对地址指向旧端口）
在漂移后落到死端口。

## 根因（2026-10-09 实测）

`tg_supervise` 巡检（state.rs:425）在「进程在但链路断」时走 `tg_restart()`（state.rs:414）：
`tg_stop()` 只杀托管子进程（杀不到外部实例）→ `tg_start()` → `tg_reselect_port()`（state.rs:246）
发现当前端口**不可绑定**（被外部实例占着）→ 顺延选下一个端口 → spawn 新子进程。叠加 BUG-227
（5s 窗口不够，新子进程也被杀），循环变成：

```
外部实例占 P1 → daemon 迁到 P2 → spawn 失败（5s 被杀）→ 巡检发现 P2 无监听
→ spawn 又失败 → 迁到 P3 …（每 60s 一次）
```

端口漂移本身不是缺陷，缺陷是**把「端口被别人占着且别人在正常服务」当成「本机端口不可用」**
而迁移：BUG-091 的探测语义（「端口连得上 = 已有实例在服务」）在 `tg_is_running` 里存在，
但 restart 路径的 reselect 没有先问「占端口的实例是不是活的、能不能用」。

## 结构性修法方向（本轮不实现）

1. 迁移前先探测占用者健康度：端口有监听者时优先复用（对齐 BUG-091「别的发起方拉起也算在服务」
   的语义），仅当监听者不响应/不健康才迁移，并把「占用者是谁、为什么迁」写进 `tg_last_error`；
2. 或：占用端口不迁移，daemon 保持 `tg_running=true`（端口连通即算在服务）静默等待，
   与「待配置=健康」分支同构；
3. 迁移后必须确保新端口 spawn 成功再改 `tg_port`（当前是先改 state 后 spawn，失败也不回滚），
   避免「config 指向一个从未成功监听过的端口」。

## 验收证据

- 2026-10-09 观测 `/api/config` `tg_port` 序列：19788 → 19787 → 19788 → 19787 → 19788（约 1-2.5 分钟
  一次翻转），每次伴随 `tg_last_error` 在两个端口间交替刷新；
- 同期手工实例在被迁走的端口上健康服务（health ok、`/api/media/*` 正常），daemon 仍坚持迁移并 spawn。

## 关联

- BUG-227（启动窗口 5s 不足使每次 spawn 必败，把「迁移」从偶发变成风暴）。
- BUG-091（外部实例也算「在服务」的原始语义，restart 路径未对齐）。
- BUG-178（restart 是唯一执行者入口，本缺陷在其 reselect 子步骤）。
