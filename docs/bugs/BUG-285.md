# BUG-285: 媒体库条目/剧集无「跳回 TG 源消息」入口 —— 数据层已存 `(source, ref)` / `source_key` 可精确定位，前端零入口，无标条目无法人工识别与纠正

- 状态: fixed
- 发现日期: 2026-10-12
- 修复日期: 2026-10-13
- 模块: shell
- 严重程度: high

> 来源：用户 2026-10-12 报障「之前的大量错误文件如何解决从入库开始的错误和问题？
> **大量的无标入库这些完全无法知道到底是什么了，也无法跳转到对应的正确信息**，所以怎么修复？怎么处理？」
> **本档为任务文档**（用户定：纯文档任务，代码由别的组负责）。
>
> **登记规范**：遵循「内容数据不入库」原则（见 BUG-232）：**不含真实频道名 / 消息文案**；
> 实测标识一律以占位符表示（`<chat_id>` / `<msg_id>` / 剧集 A 等）。

## 现象

媒体库里**没有可辨识信息的条目/剧集**（标题为占位名 `TG <chat_id> · <日期>`、或分集标题/介绍为空）出现时，
用户**无法知道它对应 TG 上的哪条消息**，也**没有任何入口跳回去看源头** ⇒ 只能干瞪眼，无法人工识别与纠正。

用户原话对应两点：
- 「**无法知道到底是什么**」= 条目/剧集自身无信息（源头缺标，见 BUG-281/283）。
- 「**无法跳转到对应的正确信息**」= **没有「跳回 TG 源消息」的入口**（本档核心）。

## 根因

**数据层已经完整记录了「这条内容来自 TG 的哪条消息」，但前端零入口把它暴露给用户。**

### 事实 1：条目层已存 `(source, ref)`，`ref` 就是 `<chat_id>:<msg_id>`

`media_item` 建表（`download-engine/crates/orig-tg/src/media.rs:543-557`）：
```sql
CREATE TABLE IF NOT EXISTS media_item (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    source TEXT NOT NULL,      -- 如 'tg'
    ref    TEXT NOT NULL,      -- ← 就是 TG 消息定位键
    ...
    UNIQUE(source, ref)
);
```
`ref` 的构造：`routes.rs:1793` `let ref_key = format!("{}:{}", chat_id, msg_id);`

⇒ 任意媒体条目都能**精确定位**到 `(chat_id, msg_id)`。

### 事实 2：剧集层已存 `source_key`，且已有反查

`media_series.source_key`（`media.rs:565`），构造：`routes.rs:2295` `format!("tg:msgs:{}:{}", self.chat_id, first)`。
反查函数：`find_series_by_source_key`（`media.rs:3648`，`SELECT id FROM media_series WHERE source_key = ?1`）。

⇒ 任意 TG 自动成剧的剧集也能**精确定位**到 `(chat_id, msg_id)`。

### 事实 3：前端零入口 —— 没有任何「媒体库 → TG」的跳转

- 全前端 **无 `source_key` / `sourceKey` 消费**（grep 命中 0 文件）。
- 全前端 **无「在 TG 中查看」类入口**（grep `openInTg` / `jumpTo` / `gotoMessage` / `revealInTg` / `viewInTg` / `jumpToTg` 命中 0）。
- 唯一的跳转是**反向**的：`pendingMediaFocus`（`tauri-shell/src/store/useStore.ts:185-192`，注释「入库流水线 → 媒体库的跳转焦点，形如 `<chatId>:<msgId>`」）
  把「**入库流水线 → 媒体库**」；**没有**「媒体库 → TG」的对应机制。

⇒ 用户说的「无法跳转到对应的正确信息」= **数据在、入口缺**，非数据缺失。

### 事实 4：这正是「无标入库」无法收敛的最后一环

无标数据的源头成因在别处（分集不共享组级 caption ⇒ BUG-281；剧集标题回退占位名且不重算 ⇒ BUG-283；
同内容多版本被编成连续多集 ⇒ BUG-284）。但**即便源头已产生无标数据，只要用户能一键跳回 TG 源消息**，
就能人工识别「这到底是什么」并手工纠正。缺了这一环，无标数据只能**永久沉积**。

## 复现

1. 入库一个「首条消息无 caption、靠后消息才有」的相册组（或任意无 caption 的视频）。
2. 媒体库打开该条目/剧集：标题为空或 `TG <chat_id> · <日期>`。
3. 尝试找「这条来自 TG 哪条消息 / 跳过去看看」的入口 —— **不存在**。
4. 只读 SQL 佐证（数据其实在）：
```sql
SELECT id, source, ref FROM media_item WHERE source = 'tg' LIMIT 5;   -- ref 形如 '<chat_id>:<msg_id>'
SELECT id, title, source_key FROM media_series WHERE source_key LIKE 'tg:msgs:%' LIMIT 5;
```

## 修复（方向；**本档不改代码**）

1. **加「在 TG 中查看」入口（P0）—— 位置设计：跟着「来源」显示走（基础逻辑：入口贴着它解释的那条来源）**
   - **原则**：「来源」在哪里显示，入口就放在哪里，且**必须与被解释的那条来源同一行**——
     用户看到那行写着「TG」，入口就贴在那行的「TG」旁；**不许**放进独立区块、弹窗或别处。
   - **「来源」当前显示在 3 处**：
     (a) **剧集内页右栏「来源」块**（`tauri-shell/src/components/media/SeriesDetail.tsx:980-1024`，
         `data-testid="episode-source-info"`）——**主版本行**（`:986-995`，行尾显示 `TG`/`本地`）
         + **备用源列表**每行（`:998-1021`，含「切换 / 摘除」）；
     (b) **媒体卡片**（`MediaCard.tsx:465`，来源作为 tooltip「来源：TG」）；
     (c) **分集展开态**（`EpisodeExpanded.tsx:321`，显示「来源：TG」）。
   - **落地**：
     - 主版本行行尾 → 加「在 TG 中查看」（用 `cur.ref`）；
     - 每个备用源行「切换 / 摘除」旁 → 加「在 TG 中查看」（用 `s.ref`）；
     - `MediaCard` / `EpisodeExpanded` 的「来源：TG」文案 → **该文案本身可点**（次要入口）。
   - **显示条件（同一条基础逻辑）**：仅当该行 `source === 'tg'` **且 `ref` 非空**时出现——
     **入口只对「能跳的来源」出现**；本地来源（`source === 'local'`）没有 TG 消息可跳，**不显示**。
   - **坐标已齐，无需新增后端字段**：`MediaEpisode.ref`（`tauri-shell/src/api/media.ts:191`）与
     `EpisodeSourceRef.ref`（`:221`）**本身已是 TG ref**（`<chat_id>:<msg_id>`），
     源码注释原文：「TG `chat:msg` ref / 本地路径 —— 按来源下发缓存任务的坐标」。
2. **复用反向跳转的同构机制（P0）**：`pendingMediaFocus`（流水线 → 媒体库）已证明「按 `chatId:msgId` 跨视图定位」可行；
   本档是其**反向**，应复用同一套 store 契约与消费点，避免另造一套。
3. **剧集级与条目级都要能跳**：剧集用 `source_key`、条目用 `ref`；对**无 caption** 的消息也能跳
   （跳过去至少能看到原始消息本身，哪怕它自己也没标题）。
4. **与存量收敛的分工（P1）**：本档只解决「**能跳回去看**」；「存量无标数据如何批量重算/合并收敛」
   见 BUG-283（标题重算）、BUG-281（分集 caption）、BUG-284（同槽归并）。**本档是它们的人工兜底前提**。

## 关联

- **BUG-283**（open, high）：存量剧集标题退化成占位名、无重算通道 —— 本档给「跳回源头」能力，是其**人工纠正的前提**。
- **BUG-281**（open, high）：分集不共享组级 caption（分集大面积空）—— 同属「无标」族。
- **BUG-284**（open, high）：合并语义缺陷 —— 同属「错误数据」族。
- **BUG-232**（登记规范来源）：「内容数据不入库」原则。
- `pendingMediaFocus`（`useStore.ts:185-192`）：**同构先例**（流水线 → 媒体库的跨视图定位）。

（修复前预先声明的可证伪判据，供对照：）

1. **入口位置正确且可达**：`episode-source-info` 块内，**主版本行**与**每个 `source === 'tg'` 的备用源行**
   各有一个「在 TG 中查看」入口，且**与被解释的来源同一行**（DOM 断言：入口是该来源行的**兄弟节点**，
   非独立区块、非弹窗）；点击后 TG 面板定位到对应 `chat` + `msg`。
   **反向证伪**：入口被放进独立区块 / 与来源行不同位置 ⇒ 判据必 **FAIL**；入口不存在 ⇒ **FAIL**。
2. **无标也能跳**：对**无 caption** 的源消息，入口同样可用，跳过去能看到原始消息本身（不因「无标题」而禁用）。
   **反向证伪**：仅对「有标题」的条目给入口 ⇒ 判据必 **FAIL**。
3. **本地来源不显示入口**：`source === 'local'` 的来源行**没有**「在 TG 中查看」（无 TG 消息可跳）。
   **反向证伪**：本地来源行也显示入口 ⇒ **FAIL**（点了无坐标可跳）。
4. **条目级与剧集级都可跳**：条目用 `ref`、剧集用 `source_key`，两类都能定位。
5. **不推翻反向跳转**：`pendingMediaFocus`（流水线 → 媒体库）不得回退或改名。
6. **真实 UI 可核**：点击入口后 DOM 断言 TG 面板当前定位消息的 `chat_id` / `msg_id` 与来源一致（**不读 className**）。
