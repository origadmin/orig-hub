# BUG-361: `cn()` 是裸 join，尺寸类冲突由**样式表源序**定胜负 ⇒ 同一按钮在不同构建下高/字号不一致

- 状态: fixed
- 发现日期: 2026-10-21
- 模块: shell
- 严重程度: high

## 现象

用户 2026-10-21 复报（原话）：

> 「3. 大量各种这种基础逻辑,基础排版问题,导致项目完全无法推进,变成一个烂项目,无标注,
> 无进度,无法处理了. 什么原因? 为什么?」

实测：`tauri-shell/src` 里 **149 处** `<Button size="sm" className="h-7 …">`
（`size` 给 `h-8`，调用方 `className` 再给 `h-7`）。`cn` 是裸 join：

```ts
export function cn(...classes) { return classes.filter(Boolean).join(' ') }
```

两个高度类同在 class 列表里，**胜负由 Tailwind 生成样式表的源序决定**，与调用方
书写顺序无关。实测 TG 气泡操作行按钮 `<Button size="sm" className="h-6 px-2 text-[10px]">`
渲染出 **32px**（`h-8` 赢了 `h-6`）—— 代码声明 24px、界面给 32px，且无声无息。

同类冲突还有 `text-xs` vs `text-[10px]`、`px-3` vs `px-2`、`w-9` vs `w-4`。
用户看到的「同样的按钮不一样高」「声明了的字号没生效」「排版混乱」即来源于此：
**同一个源文件在不同构建/不同扫描顺序下可以渲染出不同尺寸**。

## 根因

`cn` 只做拼接，不做**同属性互斥**裁决。`Button` 的 `sizeClasses` 与调用方
`className` 在 `cn()` 里平等拼接，把「我想覆盖尺寸」表达成了「我和默认值并列」——
而 CSS 层面并列的同属性类谁赢由源序决定，不是由书写顺序决定。
（BUG-344 已在 `Button` 注释里点名这个坑，但只在 `xs`/`icon-sm` 两个 token 上
打了补丁，没有在 `cn` 这一层根治。）

## 修复

`cn` 增加**同组后者赢**的裁决（`tauri-shell/src/lib/utils.ts`）：

- 只收语义上互斥的属性组：`h-`/`min-h-`/`max-h-`/`w-`/`min-w-`/`max-w-`/`p-`/`px-`/`py-`/`gap-`，
  以及**字体尺寸**（`text-<size token>` 与 `text-[<长度>]`）。
- 刻意**不收** `rounded-*`（`rounded-md` 与 `rounded-tl-lg` 不是互斥）、
  `bg-*`/`border-*`（颜色与宽度混在同前缀下，误合并会静默改配色）、
  `text-center`/`text-white`（`text-` 一符三义，只有尺寸 token 与方括号长度是字号）。
- 变体前缀（`hover:`/`md:`/`disabled:`）进分组键：`hover:h-8` 与 `h-6` 不是互斥，
  合并掉会让悬浮态失效。
- 落选者整类丢掉（合并后每个属性只剩一个类）；中奖者保留在**它自己被写下的位置**。
