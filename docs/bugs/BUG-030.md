# BUG-030：task 轮询过频致页面卡顿

- **状态**：fixed
- **日期**：2026-09-17
- **模块**：shell（前端轮询）

## 现象

用户反馈：task 请求太频繁导致页面卡死。要求降到 5s/15s 或更好的方式。

## 根因

双轮询源叠加 + 无短路：

1. `TgPanel` 主轮询 1s（`/api/tg/cache/tasks`）——BUG-027 时为恢复「缓存中 n/N」实时性设的节拍；
2. BUG-029 新增的 `CacheManagerDialog` 2s（`/api/tg/cache/tasks/all`），打开面板时主轮询**不暂停**——
   两源同时跑 ≈ 1.5 req/s，且 Dialog 每次 `load()` 无条件 `setTasks(新数组)`，
   内容未变也触发全量重渲染（任务行 × 进度条 × 计数徽章），渲染级联在低配 webview 里放大为卡顿。

## 修复

1. **单一数据源**：面板打开时 TgPanel 主轮询暂停（`cacheManagerOpen` 入 effect 依赖），面板自轮接管；关闭恢复。
2. **降频 5s**：TgPanel 1s → 5s；CacheManagerDialog 2s → 5s。进度颗粒度 5s 对分钟级下载任务足够。
3. **等值短路**：Dialog `load()` 比对任务签名（id:status:done:total:currentId:error），内容未变不 setState——零重渲染。
4. **进度平滑补偿**：`Progress` 组件新增 `smoothMs`，面板内进度条过渡拉到 4800ms（≈轮询周期），
   低频节拍下宽度过渡连续、观感近似匀速，不再「跳一下停 4.7s」。

## 验收

- `verify_shots/diag_task_rate.cjs`（mock 9879 + Vite 5182）6/6：
  - 面板关：22s 内主轮询 4 次（旧 1s 节拍为 ~22 次），任务终态后自动归零；
  - 面板开：主轮询 0 次（单源接管），面板轮询 5s 节拍；
  - 观测期 PerformanceObserver longtask(>50ms) 增量 = 0。
- 回归 `run_cache_manager_ui.sh` 9/9（BUG-029 面板/入库断言不破）。
- `npm run build` exit 0。
