# BUG-351: TG 链路瞬时 down 即重启进程 ⇒ 5 分钟一次重启风暴（477 次），而重启事实对外不可见、「关于」页两项恒绿

- 状态: fixed
- 发现日期: 2026-10-21
- 模块: engine+shell
- 严重程度: high

## 现象

用户报障（2026-10-21）：「tg 莫名挂了，另一个（下载引擎）好的。但是关于中两个状态
都是好的。」

实测取证（真实 dev 栈 19786/19787，`%TEMP%/orighub-dev-daemon.log`）：

- `[tg] supervise: telegram link is down, restarting orig-tg` 出现 **477 次**、
  `orig-tg restarted` 472 次 —— 不是偶发，是**长期重启循环**；
- 巡检 15s、链路重启冷却 300s（`state.rs:59` / `:70`）⇒ 每 **5 分钟**重启一次
  orig-tg；每次重启 orig-tg 日志都出现
  `[tg] cache queue resumed after restart: N task(s) re-queued` —— 在传缓存任务
  被打断后重新排队，用户侧就是「TG 莫名挂了」；
- 而同刻 `/api/config` 回 `tg_running=true`、`/api/tg/session` 回
  `available=true` ⇒ 关于页「下载引擎 · 运行中」与「TG 插件 · 运行中」**两个绿点**
  同时亮着，与「挂了」直接矛盾。

## 根因

1. **链路健康一次判定就触发最重的处置**：`state.rs:719` 巡检每轮只取一次
   `/api/tg/session` 的 `available`，false 且已配凭证就 `tg_restart()`（杀进程 +
   重 spawn）。MTProto 断连是常态（代理抖动 / bad salt / 重连窗口），一次瞬时
   false 不该重启进程 —— 代价是会话重建 + 缓存队列 re-queue + 用户可见中断；
   冷却只限制频率（5 分钟一次），不改变「一次 down 必重启」的判据 ⇒ 抖动期
   就是持续的重启风暴。
2. **重启事实不下发**：`tg_last_error` 只记 **spawn 失败**（`state.rs:774` 注释），
   链路重启不写它；`/api/config` 只回瞬时 `tg_running`（进程在当前这一刻在不在，
   重启窗口只有几百 ms）⇒ 界面永远只能看到「运行中」。
3. 前端关于页（`SettingsPanel.tsx:1462-1505`）只读这两个快照 ⇒ 状态显示与真实
   健康度脱节：**系统每 5 分钟自杀重启一次，界面一无所知**。

## 修复（已实施）

1. **连续确认才重启**（`download-engine/crates/orig-daemon/src/state.rs`）：
   链路 down 需连续 `TG_LINK_DOWN_CONFIRMS = 3` 轮（覆盖约 45s）才重启；任一
   轮健康即清零。抖动期不再重启；真断（持续 45s 不可用）才重启（原自愈能力保留）。
2. **链路健康对外可见**：daemon 新增 `tg_link_status()` ——
   `link_down` / `down_streak` / `restarts`（累计重启次数）/ `last_restart_at`
   （epoch 秒）/ `reason`（最近一次 down 的原因，取自 `unavailable_reason`，
   HTTP 失败记为 `session probe failed`）；`/api/config` 新增 `tg_link` 字段下发。
3. **前端如实呈现**（`SettingsPanel.tsx` 关于页 TG 卡 + `api/daemon.ts` 类型 +
   `store/useStore.ts` 的 `tgService.link`）：
   - 绿点判据改为 `tgEnabled && tgRunning && !link.link_down`；
   - 链路 down 或 **近期重启过**（默认 15 分钟窗口内）⇒ 转琥珀色并直出
     「最近重启 N 次 · 时间」，不再恒绿 —— 「关于」页第一次能反映「TG 被重启过」。

## 验收证据

- **引擎单测**（`cargo test -p orig-daemon --release`，67 passed / 0 failed）：
  - `link_down_requires_consecutive_confirmations`：第 1 轮 / 阈值前-1 轮不重启，
    达到 `TG_LINK_DOWN_CONFIRMS=3`（约 45s 持续不可用）才确认；
  - `link_status_exposes_restart_history`：`link_down` 在**未达阈值时也如实下发**
    （不是等重启了才说）、重启次数累计、`last_restart_at` 墙钟下发、重启后重新累积；
  - **反向验牙**：把 `link_down_confirmed` 变异回「一次 down 即重启」（`streak>=1`）
    ⇒ `link_down_requires_consecutive_confirmations` 实测 FAIL，恢复后复绿 ——
    判据对旧实现必败，非恒绿；
- **真栈下发**（19786，新二进制）：`/api/config` 实测返回
  `tg_link={link_down:false, down_streak:0, confirms_required:3, restarts:0, last_restart_at:null, reason:null}`；
- **前端探针** `tauri-shell/verify/_probe_bug351_link_restarts.cjs` **5/5 PASS**：
  - L1 `tg_link` 下发齐全；L2 健康态状态点 `bg-success` 且**无**重启条（没有事实
    不报警 —— 对「凭空报警」的验牙）；L3 注入 7 次重启 ⇒ `about-tg-restarts` 直出
    「链路断导致重启 7 次 · 最近 <时间> · 原因」且状态点转 `bg-warning`；
    L4 注入 `link_down` ⇒ 状态点非绿 + 状态文案「运行中 · 链路不可用」；
    L5 无页面错误；
  - 截图 `verify_shots/bug351-about-tg-restarts.png`（眼验：琥珀点 + 琥珀重启条；
    注入值仅探针演示，真实环境 restarts 从 0 起算）；
  - 实施中抓修一个真缺陷：状态点判据顺序（先判 `running` ⇒ 绿）会把「近期重启过」
    短路掉 —— 修正为 down/近期重启优先于绿，正是 L3 首跑 FAIL 抓到的；
- 前端改动 `tauri-shell/src/components/SettingsPanel.tsx` /
  `tauri-shell/src/store/useStore.ts` / `tauri-shell/src/types.ts` /
  `tauri-shell/src/api/daemon.ts`；引擎改动
  `download-engine/crates/orig-daemon/src/state.rs` /
  `download-engine/crates/orig-daemon/src/routes.rs`；
- `tsc --noEmit` 0 错。
- **注**：477 次重启的历史计数在旧 daemon 进程内存里，新二进制从 0 起算；后续
  真实链路中断发生时，关于页将自然出现琥珀提示条（无需再取证）。
