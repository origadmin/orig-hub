# BUG-208 HEVC 条目浏览器永远播不了（0 帧解码）——兼容流：按需实时转码 H.264 自动切换

- **状态**: fixed
- **发现日期**: 2026-09-30
- **模块**: engine
- **严重程度**: high

## 现象

用户反馈（2026-09-30）：「还是播放器流畅问题…解码吃力…不可能播放器可以,浏览器不行吧?」；
后续拍板采纳转码兼容流方案并裁定目标编码 H.264（「如果没有差别选哪个并不重,兼容性更好的」）。

库内重量级条目（>8Mbps 共 9 条，472=1.78GB/12Mbps、357=308MiB/10.4Mbps 等）在浏览器里黑屏有声、
提示「解码吃力」，播放体验卡顿；同文件在本地播放器（VLC/PotPlayer）正常。BUG-207 的停载遮罩
止损了流量但不解决「能看」。

## 根因（BUG-207 仪表化证据链）

- 投递层已排除：BUG-199 环回不限速生效（实测 174 MB/s）；可解码条目（598，720p AVC）
  30s 播放 **0 丢帧**、缓冲领先均值 14s——普通条目是流畅的。
- 解码层：重量级条目整类 **HEVC（hvc1，mp4 盒扫描实锤）**。Chromium 只认硬件 HEVC，
  本机没有 → `videoWidth=0`、`totalVideoFrames=0`、0 帧解码，但音频能解、时长正常。
  `preload="auto"` 陷入「缓冲 → abort → 重取」风暴（20s 97–137 请求）拖卡整页。
- **本地播放器能播是因为自带软件解码；任何投递/节流算法都变不出解码能力**。
  结构性出路只有转码。编码选型裁定：H.264（解码开销更低 + 全平台硬解兼容性碾压；
  HEVC 唯一优势省 30–40% 空间，与「随时能看」冲突）。

## 修复

### 引擎（`download-engine/crates/orig-tg`）

- **新端点 `GET /api/media/items/:id/stream`（`routes.rs`）**，三态：
  1. **代理命中**：`<TG 数据目录>/proxies/<id>.mp4` 存在 → `serve_local_file`
     （Range/ETag/MIME/背压一处定义），头 `x-orig-stream: proxy`；
  2. **转码在途**：单飞（`TRANSCODE_INFLIGHT` watch 表）——同一条目绝不并起两个
     ffmpeg，后到者等完成再吃代理；
  3. **冷启动**：spawn ffmpeg（`-c:v libx264 -preset veryfast -crf 23 -pix_fmt yuv420p
     -c:a aac -movflags frag_keyframe+empty_moov` `-f mp4 pipe:1`）实时转 **fMP4**，
     stdout 一边泵给响应（转码即播，无需等整片）一边 tee 落 `.part`，exit 0 后原子改名
     正式代理；客户端断开 → `kill_on_drop` 杀 ffmpeg + 清 `.part` 不留垃圾。
     头 `x-orig-stream: live`。
- **ffmpeg 解析链**（`resolve_ffmpeg_from`，纯函数 + 单测）：`ORIG_FFMPEG_PATH` →
  sidecar 同目录 → `<TG 数据目录>/bin` → `%LocalAppData%\OrigHub\bin`（dev/生产通吃
  的安装位）→ `<TG 数据目录>/../bin` → `PATH`；落空返回 **501**（前端停载遮罩兜底，
  绝不静默降级）。
- **`Store::proxy_dir`（`store.rs`）**：`<TG 数据目录>/proxies`——与库根同级但**刻意
  不进库**（代理是可再生派生物，混进唯一内容仓会破坏「1 份存档」计数语义）。
- ffmpeg 运行时落地：`ffmpeg 9.0.2 essentials`（gyan.dev 静态构建）安装于
  `%LocalAppData%\OrigHub\bin\ffmpeg.exe`（本机原先无任何 ffmpeg）。

### 壳（`tauri-shell/`）

- **`VideoPlayer.tsx`**：`unsupported` 判定后不再直接停载——有 `compatSrc` 先换源重试
  （横幅 `player.compatStream` 告知），兼容流也失败/缺省才回退 BUG-207 停载遮罩；
  原始源记入 `localStorage`（`orighub.compatSrcs`，有界 200 条），已知解不动的条目
  **下次直开兼容流**，免走「3s 无帧弯路」+ 少付一次 abort-re-request 代价。
- **`MediaViewer.tsx`**：视频条目传 `compatSrc = mediaItemStreamUrl(id)`。
- **`api/media.ts`**：`mediaItemStreamUrl(id)`。

## 验收证据

- **单测**：`cargo test -p orig-tg resolve_ffmpeg_prefers_explicit_then_data_dir_bins`
  PASS（解析链优先级/落空语义 5 断言）；`cargo check -p orig-tg` EXIT 0。
- **真实浏览器（入库脚本 `tauri-shell/verify/verify_compat_stream.cjs`，10/10 PASS、EXIT 0）**：
  1. HEVC 条目 472 打开 → 兼容流横幅 20s 内出现（自动切换）；
  2. 切换后真实出帧：`videoWidth=1280`，totalVideoFrames 505 → 745（4s，持续增长=真在播）；
  3. 切换后 10s 窗口 `/raw` 请求 4→4（旧源弃用即停，风暴终止）；
  4. 重开同一条目直接从 `/stream` 起步（localStorage 记忆生效）+ 横幅即现；
  5. 回归：可解码条目 598 在 `/raw` 正常出帧（720×1280、180 帧），不误切兼容流；
  6. 全程无页面错误。
- **代理命中（curl 全链路实测）**：472 全片转码 7m09s（20min 内容 ≈ 2.8x 实时），
  产物 224,202,558 B（源 1.78GB 的 12%）；`.part` 原子改名后二次请求
  `x-orig-stream: proxy` + `206 Partial Content`（`content-range: bytes 0-1023/224202558`）
  + TTFB **19ms**——直播态（转码即播）→ 代理态（秒开 + 可拖进度）闭环。
- 截图：`verify_shots/compat_stream/A-compat-stream-playing.png`（真实画面 + 兼容流横幅）、
  `C-decodable-no-compat.png`（回归）。
- `tsc --noEmit` EXIT 0；`sh scripts/sync-sidecars.sh` OK（四处副本一致）。

## 防再发

- 「浏览器能不能播」由**解码能力**决定，与投递算法无关——新编码条目进库后若再遇
  「黑屏有声」，兼容流路径已是自动兜底，无需逐条修。
- 派生物（转码代理）永不进媒体库目录；`x-orig-stream` 响应头可区分 live/proxy 供诊断。
