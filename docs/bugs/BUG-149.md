# BUG-149：入库流水线记录只增不减——已验收的批量清理入口被无编号重构撤掉，且全库无保留策略

- 状态: fixed
- 发现日期: 2026-09-22
- 模块: shell（入库流水线面板）+ engine（cache_task 生命周期）
- 严重程度: major
- 档位: standard

## 现象

用户质疑：「入库流水线 记录为什么完全没有清理? 只能往里面加? 这设计当初怎么通过的?」

实测 `C:\Users\godcong\AppData\Roaming\com.origadmin.orighub\tg\store.db`：
`cache_task` 共 **20** 行，状态分布 `[('done', 20)]`，`updated_at` 跨度
1789758600 → 1790081134，**没有任何一行曾经被清理**。

三处同时成立，构成「只能往里加」：

1. **后端无保留策略**：全库检索 `prune|retention|purge|vacuum|olderThanDays|DELETE FROM cache_task`
   与启动期/定时清理（`spawn|interval|tick|startup`）后确认，`cache_task` **没有任何自动 GC
   或保留期**。唯一的清理动词是字节清理 `POST /api/cache/clear`，其文档注释
   （`cache.rs`）明确写的是「清理**缓存字节**的唯一端点」——它不动任务记录。
2. **前端只剩单条删除**：`CacheManagerDialog.tsx` 只 import 了 `deleteCacheTask`（单条），
   「全选 / 删除所选」被撤掉。20 条记录要清 20 次点击 + 20 次确认。
3. **重复入库会继续增生**：`docs/design/ingest-pipeline-assessment.md` 3.10 已点名——
   部分唯一索引只覆盖 `queued/running`（`store.rs:335-337`），终态后再次入队是 `INSERT` 新行
   （`store.rs:691-728`）。同一条消息每「重新缓存」一次就多一行，`done` 行单调增长。

## 根因

### 1. 直接原因：一次无编号的自主重构推翻了三天前刚验收的用户诉求

`9bee7b8`（2026-09-21 17:58，godcong，标题 `refactor(shell): present the cache dialog as
the library ingest pipeline`）在重排呈现口径时，顺手把批量删除整个撤掉：

- 被删代码：`await deleteCacheTasksByIds(ids)` 与
  `{/* 选择工具条：全选（当前筛选内）+ 删除所选 */}`，连同 import 一并移除。
- 撤掉的理由写在文件头注释里（第 38-48 行）：「清记录本身就是个假需求 —— 记录是流水线的
  历史，一条条删它不释放任何字节……批量删除整个撤掉。」
- `git log -S "假需求"` 全库仅此一处，`git blame -L 38,48` 指回 `9bee7b8`；前一代版本
  `9a28947`（2026-09-20）的注释标题恰恰是相反的「## 为什么删除要能「全选 / 部分选择」」。
- `git show --stat 9bee7b8`：8 个文件、+626/-458，全是前端，**未碰后端**；提交信息
  **未引用任何 BUG 编号**——属于绕过缺陷档案的自主重构。

### 2. 被推翻的那条诉求是用户明确提过、且已验收的

`docs/bugs/BUG-054.md`（状态 fixed，**2026-09-18 已验收**）记录了用户原文三问之三：

> 「缓存管理 的删除至少有个弹窗确认吧？还有清理需要有全选，部分选择这些吧？一个一个删？」

其修复表（`:88`）把验收形态写得很具体：`CacheManagerDialog` 需具备「逐行勾选 + 表头全选 +
已选计数 + 「删除所选」；**任何删除（含单条）都先出确认条**，并如实报出其中活跃任务数」。
验收项 `:116` ③k 还要求「批量删除点取消后记录数逐字未变」。

即：用户 09-18 要求 → 09-18 验收 → 09-21 被 `9bee7b8` 撤掉。

### 3. 同日写成的评估文档给出的是相反结论

`docs/design/ingest-pipeline-redesign-assessment.md` §1.4「清理/删除功能分级」（与 `9bee7b8`
同日写成，commit `ad9f92e`）：

| 级别 | 做什么 |
|---|---|
| L0（现状） | 单条完全删除、`cache_task` 终态清理、清字节保留条目 |
| **L1（推荐目标档）** | **多选删除 + 按筛选删除** + 删除前影响面预览 |

设计侧把「多选删除」列为推荐目标档，实现侧同日把它删了。且 L0 现状栏还把「`cache_task`
终态清理」当作**已有能力**——实现把它删成「只有单条」后，连 L0 都不再成立。

### 4. 保留策略从来没有被定义过

检索 `AGENTS.md`、`docs/rules/{bug-registry,code-constraints}.md`、`docs/ACCEPTANCE.md`、
`docs/bugs/BUG-*`、`docs/design/*`：**没有任何一处**定义 `cache_task` 的保留期、
上限或生命周期。唯一沾边的是 `docs/design/ingest-pipeline-assessment.md:84` 3.10
「任务去重只在活跃态 … → **记录增生**」——只描述现象，未定策略。

也就是说：**不是「评审通过了一个只增不减的设计」，而是根本没做过这个决策。**
`9bee7b8` 用一句「清记录是假需求」同时扮演了设计结论与实现动作。

性质归类（与 BUG-148 同源）：**实现者自己发明产品判断，绕开缺陷档案直接改产品语义。**

## 复现

打开「入库流水线」面板（TG 视图 → 入库流水线）：列表里 20 条 `done` 记录，每行只有一个
「删除」按钮，没有全选、没有勾选框、没有「删除所选」，也没有任何按时间/按状态的清理入口。

## 修复

补齐 L1 档的**手动清理**能力，后端能力现成，只动前端接线：

- `CacheManagerDialog.tsx`
  - 恢复逐行勾选（`cache-select-row`）+ 表头「全选（当前筛选内）」（`cache-select-all`）
    + 「已选 N 条」计数 + 「删除所选（N）」（`cache-delete-selected`）。
  - 批量删除走原子端点 `DELETE /api/cache/tasks?ids=1,2,3`（`deleteCacheTasksByIds`，
    `cache.rs:765`、`store.rs:913`），不循环调单条——BUG-054 时代前端循环调单条的形态
    无原子性、无影响面，正是不再重演的旧形态。
  - 确认条按 BUG-054 验收形态：批量与单条**都要确认**，且如实报出所选中的活跃任务数
    （删活跃记录等于停掉正在跑的入库，不说清楚就是偷偷改状态）。
  - 取消/逃逸后选中态与记录数都不变（对应 BUG-054 ③k）。
  - 文件头注释改写：原「清记录是假需求」的论断删除，换成「记录可清，但清的是历史不是字节，
    所以必须显式确认 + 如实报影响面」。
- i18n：补回 `tg.cacheDeleteSelected`、`tg.cacheDeleteConfirmBatch`（zh-CN / en-US）。
  注：`tg.cacheSelectAll` / `tg.cacheSelectRow` / `tg.cacheSelectedCount` 三个键当时只删了
  UI 没删键，至今残留在两份 locale 里——这正是拆一半留一半的痕迹。

**不在本次范围内（需另行拍板）**：

- **自动保留策略（retention/GC）**：设计文档 §1.4 把「生命周期自动化」列为 L3 并写明
  「本期不做」。本次只恢复手动清理，不引入定时清理。
- **增生本身（3.10）**：终态后再次入队 `INSERT` 新行。修法是改为复用/覆写旧行，
  会动到 `enqueue_cache_task` 的语义与 BUG-078 的重试语义，风险高于本次，单列。

**已执行**（真实渲染，非仅类型检查）。判据全部写成具体数值，不写「看起来正常」。

- 环境：`orig-daemon` 9876 / `orig-tg` 9877（正常模式，`mode:"ready"`、`available:true`、
  `session_phase:"Authorized"`）/ 前端 dev server 5180；headless Edge 经 CDP 取渲染后 DOM。
  入口路径：侧栏 `nav-tg` → 上下文栏 `tg-cache-manager-entry` → 面板 `cache-manager`。
- **初始态**：`cache-task-row` = 20；`cache-select-row` = 20；`cache-select-all` 存在；
  `cache-selected-count` = 「已选 0 条」；`cache-delete-selected` 文案「删除所选（0）」
  且 **disabled=true**（空集没有删除路径）。
- **全选**：勾中 20，`cache-selected-count` = 「已选 20 条」，
  `cache-delete-selected` 文案「删除所选（20）」、disabled=false。
- **取消证伪**（BUG-054 ③k）：点「删除所选」→ 确认条文案「确定删除所选 20 条记录？」→
  点「取消」→ 确认条消失，`cache-task-row` **仍为 20**，选中数仍「已选 20 条」——
  记录数与选中数逐字未变（不是「看起来差不多」）。
- **生效证伪**：取消全选 → 只勾前 2 条 → 「已选 2 条」/「删除所选（2）」→ 确认 →
  `cache-task-row` 由 **20 降为 18**（正好减 2），选中数回到「已选 0 条」。
- **后端复查**（证明不是只改前端状态）：`GET /api/tg/cache/tasks/all` 的
  `counts.done` 与 `tasks.length` 同步由 **20 → 18**。
- **反向证伪 4/4 通过**（`falsify_bug_149.mjs`）：F1 未勾选时按钮 disabled=true →
  F1b 禁用态点击不产生确认条（`cache-confirm-batch` 不存在）→ F2 取消后
  `rows 18 → 18` → F3 单条删除的行内确认条仍工作（`cache-confirm-inline` 出现）。
  这些断言在改动前必然失败（那时无勾选框、无批量按钮），故不是恒真断言。
- **happy path 未被改坏**（动了必经渲染路径必须同时验成功路径）：改动前记录的 20 行里
  `cache-task-golibrary` = 20、`cache-task-delete` = 20，改动后两轮删除过程里这两个按钮
  始终可用且行为不变；「重试」按钮按状态出现（本次基线全为 done，故为 0，非被改坏）。
- 类型检查：`cd tauri-shell && node node_modules/typescript/bin/tsc --noEmit -p tsconfig.json`
  → 无输出（rc=0）。
- 反向证伪（文案层面）：`grep -rn "清记录本身就是个假需求\|批量删除整个撤掉" tauri-shell/src`
  → 无命中；若命中说明倒退复发。
- 账目说明：验收过程真实删掉了 2 条 `done` 记录（20 → 18）。这是本面板第一条修复，记录
  本身即历史，删除行为是被测对象，故不还原；`cache_task` 记录不影响字节，无副作用。
