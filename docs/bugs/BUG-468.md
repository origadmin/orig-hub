# BUG-468: 文件位置变更是否需要与库关联——下载 → 管理路径 → 库存储 → 位置移动，整链路评估

- 状态: in_progress
- 发现日期: 2026-10-27
- 模块: engine+shell
- 严重程度: mid
- 排期: 2026-11-26

> 来源：用户报告「**说的位置，这里就有个问题，文件位置变更，如何关联，是否需要关联？
> 需要评估考虑下。从下载、文件的管理路径、库的存储方式，到文件位置移动，
> 这几点关联起来考虑整个流程。**」

## 现象（待评估的问题，不是已定位的缺陷）

整条链路上「文件在哪」这件事有**四个不同的落点**，彼此的关系从未被一次性裁定：

| 环节 | 位置由谁决定 | 现状事实 |
|---|---|---|
| ① 下载落盘 | `download_root`（引擎配置的唯一字节出口） | 下载单根；管理侧多根（ManagedRoot 并集，越界 403）；库根 = `<下载路径>/library` 派生 |
| ② 文件管理路径 | 条目登记时记录的 `file_path`（本地导入来源） | `ImportDialog` 按路径幂等登记；`scanDirectory` 读的是目录当前内容 |
| ③ 库的存储方式 | blob + 条目元数据（播放走 blob） | `OrganizeWizard` 头部红线：整理**绝不修改 blob 或 `media_item.file_path`**；产物（link/copy）**不是唯一字节来源** |
| ④ 文件位置移动 | 用户在磁盘上移动 / 删除 / 换盘 / 换主根 | 库侧**无感知**：条目仍指向旧路径，播放走 blob 时无碍，走路径时失败 |

⇒ 用户的问题精确化为：**④ 发生后，库要不要跟着改（关联），还是只做「发现 + 表达」？**

## 根因（评估层面的根因）

1. **位置是外部可变事实，却被视为条目属性。** 磁盘路径由用户/系统随意改变，
   若把它当真源，就必然要维护一条「外部变化 → 库更新」的反向链路，
   而这条链路在离线期间不可观测（期间的变化只能靠事后对账发现）。
2. **现有能力已经隐含选择了「不关联」**：整理产物不改 `media_item.file_path`、
   产物不是唯一字节源 —— 说明「副本可以有多个位置，库不认位置」已是既定设计；
   但这条原则没有写成跨环节的裁定，也没有覆盖「原始文件被移走」的情形。
3. **缺一次全链路的对账定义**：哪一侧是权威（库 vs 磁盘）、变化时谁赢、
   不可判定时如何表达 —— 三项皆未定（BUG-458 已定「三种对账情况」的行为表，
   但那是**条目↔受管根**的对账，未覆盖**下载根 ↔ 库根 ↔ 整理产物**三者的关系）。

## 复现（评估用场景）

1. 下载完成 ⇒ 字节在 `download_root`，条目在库，库根派生路径下可见。
2. 用户在磁盘上把该文件移到别处（或在外部删除）。
3. 观察：库中条目不变；播放走 blob 成功；按路径的入口（打开目录 / 整理 / 重新缓存）
   行为不一致 —— 有的失败、有的静默。
4. 切换主目录（`/api/fs/roots/primary`）⇒ 旧根下条目整体进入「库有文件没有」。

## 评估结论（本档给出的专业意见，待拍板确认后落地）

**结论：不建立双向绑定，采用「单向对账 + 缺失可见」。**

- **真源 = 条目 + 来源坐标**（`source` + `ref`，可据此重取字节），**不是磁盘路径**。
  路径只是「当前已知位置」这一可失效属性。
- **关联方向固定为单向**：磁盘 → 库（对账发现差异并表达），**不做** 库 → 磁盘
  （库不主动搬动/重建用户文件）。
- **变化的表达优先于静默修复**：文件不在原处 ⇒ 条目标「文件缺失」并在条目与本集两级可见
  （见 BUG-458 第 1 支），有来源则给「重新缓存」，无来源则明确说「无法取回」——
  而不是自动把路径改成一个猜测出来的新位置。
- **下载根 / 库根 / 整理产物三者关系**：下载根 = 唯一字节出口；库根 = 派生视图；
  整理产物 = 派生副本（非唯一）。⇒ 位置移动只对「下载根内的文件」有意义，
  对整理产物无意义（产物被删不影响播放，这是既有红线，本档不改）。

## 裁定（2026-10-27 用户拍板）

**采纳 ①：单向对账 + 缺失可见（不做双向关联）。** 用户原话「**单项够了吧？
后期有问题再改**」⇒ 本档结论即为落地结论，不再保留 ② ③ 作为候选。

落地判据（写死，供实现与验收直接引用）：

1. **真源 = 条目 + 来源坐标**（`source` + `ref`），磁盘路径只是可失效属性，
   库**永不**主动搬动 / 重建 / 猜测用户文件的位置（红线：库不写用户磁盘）。
2. **关联方向只有一条：磁盘 → 库。** 对账（启动 + 换根 + 手动触发）负责发现差异，
   差异一律**表达**（条目标「文件缺失」，条目与本集两级可见），不做静默改写。
3. **缺失态必须可见**：有来源 ⇒ 给「重新缓存」；无来源 ⇒ 明说「无法取回」——
   不得呈现为「正常条目但点开失败」。
4. **整理产物不参与关联**：产物非唯一字节源（既有红线），产物被移动/删除不影响播放，
   库侧不登记、不判缺失。
5. **延后项（本次不做，出问题再开档）**：内容哈希识别移动、库写用户磁盘的红线例外。
   二者一旦需要，按新 BUG 走，不在本档内预留接口。

## 交付物（本档的完成判据）

一份链路评估文档（进 `docs/`），必须回答四个问题并给出裁定表：

1. 下载落盘位置变更（换 `download_root`）后既有条目如何关联；
2. 用户外部移动 / 删除文件后库如何表达（与 BUG-458 对账表对齐）；
3. 整理产物被移动 / 删除后是否要与库断开关联（现状已解耦，是否反向登记）；
4. 库存储（blob + `file_path` 镜像）在位置变更时**谁是唯一真源**（本档答：条目 + 来源坐标）。
