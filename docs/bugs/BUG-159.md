# BUG-159：删除/合并剧集后客户端陈旧 series 引用未失效 + 404 无语义化展示（series not found）

- 状态: fixed
- 发现日期: 2026-09-23
- 模块: shell
- 严重程度: high
- 档位: standard

## 现象

用户在媒体库里打开某剧集详情（`view==='seriesDetail'`、`activeSeriesId=该 id`、`detail` 已缓存）后，
若该剧集被删除（BUG-126 的路径）或被合并（BUG-037 删源剧集），前端仍持有死 id 并再次导航到它时，
`openSeries(deadId)` 请求 `GET /api/media/series/:id` 拿到后端 404，文案 `"series not found"`
（`download-engine/crates/orig-tg/src/routes.rs:2849`）。

旧代码的 `openSeries` 只做 `setError(e.message)` 后**直接返回**，于是：

- `view` 仍停在 `seriesDetail`，但 `detail` 仍是删除/合并前那份陈旧数据（缓存没清）；
- 屏幕中央/顶部出现裸的 `series not found` 报错，没有「该系列已不存在」的语义化提示，也没有回到剧集墙的出口；
- 通过 `refreshAll`（`MediaLibraryPanel.tsx:497`：当 `view==='seriesDetail'` 时 `await openSeries(activeSeriesId)`）
  周期性或手动刷新时会**反复 404**，用户被卡死在报错态。

播放器侧栏（`MediaViewer` → `useSeriesDetail`）同理：剧集被删后侧栏 `error` 直接显示裸 `series not found`，
没有语义化降级。

## 根因

1. **后端逻辑正确**：`get_series`（`media.rs:1374`）先在 `media_series` 全量表里 `find(|s| s.id == id)`，
   查不到才抛 404 —— 只有「客户端传了一个已不存在的 series id」才会 404。这不是后端 bug。
2. **前端缺失效 + 缺语义化**，两处：
   - `MediaLibraryPanel.openSeries`（`MediaLibraryPanel.tsx:252`）对 404 无任何特殊处理，
     既不清理死缓存、也不回退视图、也不给出可行动提示，只把裸文案塞进 `error`。
   - `useSeriesDetail`（`useSeriesDetail.ts:29`）把 404 文案原样作为 `error` 返回，
     消费方（`EpisodeList`）直接把 `error` 当失败文案渲染，没有「剧集已不存在」分支。
3. **缓存层本就支持精确失效**：`fetchCache.invalidateCache(cacheKey.seriesDetail(id))`
   （`fetchCache.ts:52`）按前缀删键，删源/删目标剧集后只要调用它即可让死引用失效 —— 旧代码没用上。

> 注：`media_item.series_id` 不是存储列（`media.ts:900` 由 `media_episode` 实时算出），
> 合并后条目归属会自动校正，**不存在「条目指向已删剧集的悬空引用」**，故无需在条目层做处理。
> 问题纯粹在「客户端持有一个已不存在的 series id 并再次导航」。

## 复现

确定性复现路径（已在验收脚本里实跑验证）：**剧集墙仍含一张陈旧死卡时，用户点击该卡**。

```sh
# 1) 建一个剧集（记录封面会出现在剧集墙）
curl -s -X POST http://127.0.0.1:9877/api/media/series \
  -H 'Content-Type: application/json' -d '{"title":"复现系列"}'   # -> {"id": N}

# 2) 打开媒体库，剧集墙经 loadSeries 拉到这张新卡（view==='series'）

# 3) 不进详情，直接在后端把它删掉
curl -s -X DELETE http://127.0.0.1:9877/api/media/series/N        # -> {"ok":true}
#    此时前端剧集墙仍是删除前的旧列表（cached(seriesList) 未失效），死卡还在墙上

# 4) 用户点击墙上那张死卡 -> onOpen={() => void openSeries(N)}
#    openSeries(N) 请求 GET /api/media/series/N 拿到 404 "series not found"
#    旧代码：只 setError(裸文案) 后直接返回，view 卡死、墙残留死卡、裸文案上屏。
```

> ⚠️ **「返回」路径不会触发守卫**：详情视图的「返回」走 `onBack → loadSeries()`，并**不调用**
> `openSeries(deadId)`，故守卫永远不会在「返回」时被命中。真正的触发点是「剧集墙仍含陈旧死卡时点击该卡」。
> 首版验收脚本误用「进详情→删→返回」流程，实测守卫从未执行（8/9 但语义提示断言空过），修正为上述点死卡流程后
> 守卫才真正被触发、修复才被真实验证。

真实用户路径：某剧集被合并（`MergeSeriesDialog` 把源剧集删除）或被删除后，同一份 `loadSeries` 列表缓存
尚未刷新，用户再次点击剧集墙上的那张死卡即命中；或 `refreshAll`（`:497`）在 `view==='seriesDetail'` 时
`await openSeries(activeSeriesId)` 周期性重开死 id 而反复 404。

## 修复

只改前端，后端零改动。三处外科手术式定点修复：

1. **`tauri-shell/src/hooks/useSeriesDetail.ts`**
   - 新增 `isSeriesNotFound(err)`：识别两类 404 文案 —— 后端 `body.error="series not found"`
     （`request()` 直接把它当 message）与 body 解析失败时的裸状态码 `404 Not Found`。
   - `useSeriesDetail` 新增 `notFound` 状态：404 时置 `true`，让消费方给出语义化提示而非裸文案。

2. **`tauri-shell/src/components/MediaLibraryPanel.tsx`**（`openSeries`，`MediaLibraryPanel.tsx:252`）
   - 捕获到 `isSeriesNotFound` 时：
     - **清掉死 detail 缓存**：`invalidateCache(cacheKey.seriesDetail(id))`；
     - **同时作废「剧集列表」缓存**（关键修复点，见下）：`invalidateCache(cacheKey.seriesList(activeTagId))`
       与 `invalidateCache(cacheKey.seriesList(null))`；
     - **回退剧集墙**：`setDetail(null)` / `setActiveSeriesId(null)` / `setView('series')` / `void loadSeries()`；
     - **语义化提示**：`setError(t('media.seriesGone'))`「该系列已被删除或合并，已返回剧集列表」。
   - `[activeTagId, setError, t, loadSeries]` 为 deps（含 `activeTagId`，因为守卫内读取了它来作废列表缓存）。
   - 为什么必须清列表缓存：`loadSeries`（`:223`）走 `cached(cacheKey.seriesList(activeTagId), ...)`，
     `listSeries` 是「按标签拉全部剧集」的只读调用。若只清 detail 缓存，回退后 `loadSeries()` 会命中
     **被删除前的旧列表**，剧集墙仍渲染那张死卡 —— 用户再次点击即再次 404。实测 v3 仅清 detail 时
     断言「回退后墙不再列出死卡」即 FAIL，补上列表失效后 9/9 全绿，印证了这一点。
   - 这同时修掉了 `refreshAll`（`:497`，`view==='seriesDetail'` 时 `await openSeries(activeSeriesId)`）
     反复 404 卡死的问题（回退后 `view!=='seriesDetail'`，不再重开死 id）。

3. **`tauri-shell/src/components/media/EpisodeList.tsx`** + **`MediaViewer.tsx`**
   - `EpisodeList` 新增 `notFound` prop：为真时渲染 `t('media.seriesGone')` 而非裸 `error`。
   - `MediaViewer` 透传 `notFound={notFound}`。

4. **i18n**：`tauri-shell/src/i18n/locales/{zh-CN,en-US}.json` 新增 `media.seriesGone`。

修复后契约：**任何路径拿到「剧集已不存在」都不再裸抛 `series not found`**，而是语义化提示并自动回到可继续操作的视图。

## 关联

- **BUG-126**（从剧集移除分集会被重新编回 / 删剧集后条目重组）：删除剧集的主路径之一，直接触发本缺陷。
- **BUG-037**（合并剧集删除源剧集）：合并把源剧集删除，若源曾是 activeSeriesId 即触发。
- **BUG-070**（fetchCache 共享缓存、写操作后显式失效）：本修复复用其 `invalidateCache` 精确失效能力。
- 后端判据：`download-engine/crates/orig-tg/src/routes.rs:2849`（`"series not found"`）。

## 验收证据

真实渲染验收脚本（零依赖 CDP，复用 `verify/lib/cdp.cjs`，与 BUG-123/153/155 同款通道）：

- **脚本**：`tauri-shell/verify/verify_series_not_found.cjs`
- **门禁 1（非恒绿）**：`APP_URL` 指向死端口 → `RESULT: UNREACHABLE (exit 2)`，证明脚本不是恒绿。
- **门禁 2（证伪）**：`ORIG_VERIFY_REVERT=1` 时脚本向守卫回退路径注入「该缺陷会裸抛的 `series not found`」
  并期望它出现，修复后该文案**不应**出现 → 断言翻转、`exit 1`（证明脚本有牙、能抓住回归）。
- **主断言**（修复后实跑 `exit 0`，9/9 PASS）：
  1. 点击 `nav-media` 进入媒体库，断言剧集墙已挂载；
  2. 经 API `POST /api/media/series` 建剧集 → 刷新并再进媒体库，断言墙经 `loadSeries` 渲染出该新卡；
  3. **不进详情**，直接经 API `DELETE /api/media/series/:id`（200）删掉它；
  4. `clickSeriesCardByText(page, title)` 点墙上那张**死卡** → 触发 `openSeries(deadId)` 守卫；
  5. 断言语义化提示「该系列已被删除或合并」上屏（非裸 `series not found`）；
  6. 断言回退后**剧集墙不再列出该死卡**（只数墙内 `series-card` root 含标题的数量 === 0，避开侧栏「最近」等独立列表）；
  7. 断言**全程 `document.body.innerText` 不含裸 `series not found`**；
  8. 断言无未捕获 JS 异常 / `pageerror`。
- 跑法：`cd tauri-shell && npm run dev`（端口 5180，CORS 仅放行该 origin）+ 后端 9877，
  再 `node verify/verify_series_not_found.cjs`。（`httpJson` 走 server-to-server 直连 9877，不受浏览器 CORS 约束；
  证据 `result.json` 落 `os.tmpdir()/orighub-verify-series-not-found`，仓外，符合 AGENTS.md §6 污染防线。）
