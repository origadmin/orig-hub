# BUG-281: 相册组的分集内容**不共享组级 caption** —— 每个分集只取「该消息自己的 caption」，组内只有带 caption 的那一条分集有标题/介绍（实测 149 个分集仅 31 个有介绍）

- 状态: open
- 发现日期: 2026-10-12
- 模块: engine+shell
- 严重程度: high

> 来源：用户 2026-10-12 报障「多集入库时，**大部分集是没有内容的**，但是**某一集是有介绍的**（媒体库显示），
> 但是入库队列的时候是什么都没有的（只有默认标题）」。
> 本档是其中**媒体库侧**的一半；**队列侧**另立 **BUG-280**（同一批调查，**不同根因**）。
> **本档为任务文档**（用户定：纯文档任务，代码由别的组负责）。

## 现象

一个相册组（N 条视频消息）入库后成为「**1 个剧集 + N 个分集**」，但**只有 1 条分集有标题与介绍**，
其余 N-1 条**标题、介绍全空**。

实测（生产库 `%APPDATA%\com.origadmin.orighub\tg\store.db`，只读）：

| 剧集 | 分集数 | 有标题的分集 | 有介绍的分集 | 有内容的是第几集 |
|---|---|---|---|---|
| 315 《温柔的妈妈被我弄哭了》 | 8 | 1 | 1 | **第 6 集**（消息 3378） |
| 260 《温柔的妈妈被我弄哭了》 | 8 | 1 | 1 | **第 5 集**（消息 1207） |
| 319 《我的温柔妈妈》 | 5 | 0 | 0 | **一集都没有** |

**全库合计**（`source_key LIKE 'tg:group:%'`）：

| 口径 | 数值 |
|---|---|
| 分集总数 | **149** |
| 其中 `media_item.title` 非空 | **32** |
| 其中 `media_item.description` 非空 | **31** |
| 其中 `file_path` 非空（有字节） | 111 |
| **剧集级** `media_series.description` 非空 | **49 / 50** |

⇒ **约 79%（118/149）的分集没有标题与介绍**，而**剧集级介绍几乎总是有**。

## 根因

**入库时每个分集的 `media_item.title/description` 只取「该消息自己的 caption」，没有任何组级分发。**

### 事实 1：分集内容 = 该消息自己的 caption（无兜底、无分发）

`register_media_item_t0`（`routes.rs:1760-1815`，取 caption 在 `:1782-1793`）：

```rust
let (title, desc) = row.as_ref()
    .and_then(|m| m.caption.as_deref())
    .map(crate::media::split_caption)
    .unwrap_or((None, None));
// BUG-049 照片条目的可读兜底标题；非照片维持空串（BUG-154：不拿内部文件名伪装标题）。
let title = match title {
    Some(t) => t,
    None if photo_rule => format!("TG 图片 #{msg_id}"),
    None => String::new(),
};
```

`caption` 为空 ⇒ `title = ""`、`desc = None`。**它不查同组其他消息、也不回退 `file_name`** ——
`row` 来自 `st.store.get_message(chat_id, msg_id)`（`routes.rs:1767`），**只取这一条消息**。

### 事实 2：剧集级**有**分发（用的正是那条 caption）

`ensure_series`（`routes.rs:2154`）在 `:2161-2170` 用 **`first_caption`** 切剧集标题与介绍：

```rust
// 剧集标题与介绍来自**组内 caption**：首行标题、其余介绍（split_caption）。
let (title, desc) = match st.store.first_caption(self.chat_id, &self.task_msgs).await { ... };
```

`first_caption`（`media.rs:4215-4233`）遍历 `message_ids`，**返回第一条非空 caption**。

⇒ **同一条 caption 只被用了两次**：**剧集级** + **那条消息自己的分集**。
**其余分集完全拿不到**，因为分集侧没有对应的「回填」逻辑。

### 事实 3：caption 在 TG 上本来就只挂在一条消息上

相册组由上传者一次性发多条视频，**说明文字（caption）通常只写在其中一条**（不一定是第一条）。
实测组 3373-3380：**只有 3378 有 caption**，3373-3377/3379/3380 全空（但它们**有 `file_name`**）。

### 事实 4：`split_caption` 的形状放大了后果

`split_caption`（`media.rs:4572-4602`）：**首行 = 标题**，其余非空行 = 介绍。
⇒ **单行 caption 只会产出标题、介绍为空**；多行才有介绍。

### 事实 5（**决定修复形态**）：分集介绍有一道「与剧集介绍逐字相同就隐藏」的门控

`shouldRenderEpisodeDescription`（`tauri-shell/src/lib/episodePresentation.ts:45-51`）：

```ts
export function shouldRenderEpisodeDescription(ep, series): boolean {
  const epDesc = (ep.description ?? '').trim()
  return epDesc.length > 0 && epDesc !== (series.description ?? '').trim()
}
```

注释写明理由：TG 抓取的剧集会**把整段剧集简介逐字复制进每一集**（实测 series 101），
而剧集简介已在全剧层常驻 ⇒ 单集层再渲染就是**同一段文案出现两遍**，故**逐字相同才隐藏**。

`SeriesDetail.tsx:946-954` 消费该门控：为真渲染 `data-testid="episode-focus-desc"`，
为假渲染空态 `media.descEmptyEp`（即用户看到的「没有内容」）。

> **⚠ 这条对修复方案是硬约束**：任何「让分集 `description` = 组级介绍」的修法，
> **都会被这道门控判为「重复」而隐藏** ⇒ 数据修好了、**界面上仍然什么都看不到**。
> 修 **BUG-281** 必须**同时**处理这道门控（或改介绍的组织形态），否则等于没修。

## 回答用户的两个问题

**问题 1：「这应该是没有获取到正确的标题内容，因为不在第一个吗？」**

**不是**（至少不是这个原因）。代码**不要求** caption 在第一条：
- 剧集级用 `first_caption` 会**主动找**「第一条非空」，实测剧集 315 的 caption 在**第 6 条**（消息 3378）也被正确找到；
- 队列标题 `cache_task_title` 也是「找第一条**有**标题的」。

真正的机制是：**caption 在 TG 上确实只挂在一条消息**（事实 3），
而**分集侧没有任何分发或回填**（事实 1）⇒ 只有那一条的分集有内容。
（**队列侧**另有「被文件名遮蔽」的问题，见 **BUG-280**，那是另一回事。）

**问题 2：「那显示为什么是正常的？」**

因为媒体库**顶部**渲染的是**剧集级**介绍，而剧集级**几乎总有值**：
- 剧集级：`SeriesDetail.tsx:528-536`（`detail.description`，`data-testid="series-description"`）
  与 `SeriesHero.tsx:205-213` —— 数据来自 `media_series.description`（49/50 有值）。
- 分集级：`SeriesDetail.tsx:949` 渲染 `cur.description`；
  且 `:524` 注释明写「非空恒渲染（**绝不用首集介绍 `cur.description` 兜底**）」——
  即**有意不做**「用剧集介绍冒充分集介绍」，所以分集空就是空。

⇒ **剧集页整体看起来正常，逐集看就大面积空。**

## 复现

1. 找一个相册组（≥2 条视频消息，仅其中一条带 caption）。
2. 入库后在媒体库打开该剧：**顶部有介绍**；**逐集查看** ⇒ 只有 1 集有标题/介绍，其余空。
3. 只读 SQL 佐证：
```sql
SELECT e.episode_no, i.title, substr(COALESCE(i.description,''),1,40) AS desc
  FROM media_series s
  JOIN media_episode e ON e.series_id = s.id
  LEFT JOIN media_item i ON i.id = e.item_id
 WHERE s.id = 315 ORDER BY e.episode_no;
```

## 修复（方向；**本档不改代码**）

**先要一个产品裁定**（这是本条的关键，**不许实现者自决**）：

> **相册组的组级 caption（描述整组/整剧）应当如何作用于各分集？**
>
> - **选项 1（推荐）分集继承组级介绍**：分集**没有自己 caption** 时，`description` 继承剧集级
>   （即 `first_caption` 的正文）；**标题仍保持「不伪造」**（沿用 BUG-154）。
>   **必须同时处理事实 5 的门控**：否则继承来的介绍**与剧集介绍逐字相同 ⇒ 被隐藏**，
>   等于没修。可选处置：(a) 门控增加「分集自己的介绍为空、当前显示的是继承值」这一维度，
>   改为「按**来源**去重」而非「按**文本**去重」；(b) 分集介绍**组织成非逐字相同的形态**
>   （如前置一行 `《剧名》· 第 N 集` 再跟正文），使门控自然放行；
>   (c) 继承值走**独立的呈现位**（不复用 `episode-focus-desc`），不与剧集介绍互斥。
> - **选项 2 分集回退到 `file_name`**：仅在文件名**看起来是真名**（如
>   `2048原创短剧_温柔的妈妈被我弄哭了_第7集_AI短剧.mp4`）时用作标题。
>   与 **BUG-154「不拿内部文件名伪装标题」有张力**，须一并裁定「放宽到什么形态」。
> - **选项 3 分集标题用「剧名 + 集号」派生**（如 `《X》第7集`），介绍继承组级 ——
>   与选项 1 的 (b) 天然相容（标题/介绍都带上集号 ⇒ 不逐字相同）。
> - **选项 4 不做**：接受 79% 分集无内容，仅在剧集级展示。

**必须一并评估的既有实现**：`shouldRenderEpisodeDescription`（`episodePresentation.ts:45-51`）
是为治「同一段简介在剧集层与单集层各显示一遍」而立的（注释引用 series 101 实测），
**不是缺陷**；本条的修复**不得**简单删掉它（否则回退那个已修的问题），只能改**去重维度**或**介绍形态**。

**不可推翻的既有裁定**：BUG-154（不拿内部文件名伪装标题）、BUG-152（剧集标题取首个批次第一条 caption）、
BUG-054（`media_item.description` 列与三态契约）、BUG-205（自动入库不造合集）。

## 关联

- **BUG-280**（open）：**队列侧**标题被无意义文件名遮蔽 —— 同一批调查、**不同根因**，可分开修。
- **BUG-152**（fixed）：剧集标题取首个批次第一条 caption ⇒ 剧集级**已有**分发；本条治的是**分集级缺失**。
- **BUG-154**（fixed）：不拿内部文件名伪装标题 ⇒ 「分集标题为空」是它的**直接后果之一**，修复须与它协商。
- **BUG-054**（fixed）：`media_item.description` 列与「介绍空值 = 显式清空」的三态契约。
- **BUG-049**（fixed）：照片条目有可读兜底标题（`TG 图片 #<id>`）—— **视频没有**，这正是分集空的对照物。

## 验收证据

（状态 `open`，尚无验收证据。修复后必须满足的**可证伪判据（预先声明）**：）

1. **分集不再大面积空**：构造相册组（≥3 条视频，仅 1 条带多行 caption）入库后，

2. **剧集级不回退**：`media_series.description` 仍来自 `first_caption`，不回退 BUG-152。
3. **不伪造标题**：分集标题**不得**出现 `manifest.mp4` / `manifest (2).mp4` 这类**内部**文件名（不回退 BUG-154）；
   若采用选项 2，判据必须写明「真名」的判定规则（否则等于放宽 BUG-154 而未留痕）。
4. **真实 UI 验（必须断言「可见」而非「非空」）**：`SeriesDetail` 分集介绍位置出现
   `data-testid="episode-focus-desc"` 且**不是**空态 `media.descEmptyEp`
   —— 即必须通过 `shouldRenderEpisodeDescription`（事实 5）。**反向证伪**：
   只写库不改门控/形态 ⇒ DB 里 `media_item.description` 非空、UI 仍渲染 `media.descEmptyEp`
   ⇒ 判据必 FAIL。同时 `SeriesDetail` 剧集页**顶部**介绍不变、不出现一段简介显示两遍
   （series 101 的回退面）。
5. **存量数据可复核**：若做回填，须登记**回填条数 + 每条追得到的来源**（消息号 → caption），
   **禁止**凭空编造或按标题正则硬猜。
