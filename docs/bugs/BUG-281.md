- 模块: engine+shell

## 现象

一个相册组（N 条视频消息）入库后成为「**1 个剧集 + N 个分集**」，但**只有 1 条分集有标题与介绍**，
其余 N-1 条**标题、介绍全空**。

实测（生产库 `%APPDATA%\com.origadmin.orighub\tg\store.db`，只读；真实标识已占位化）：

| 剧集 | 分集数 | 有标题的分集 | 有介绍的分集 | 有内容的是第几集 |
|---|---|---|---|---|
| 剧集 A | 8 | 1 | 1 | **靠后某一集**（带 caption 的那条） |
| 剧集 B | 8 | 1 | 1 | **靠中某一集**（带 caption 的那条） |
| 剧集 C | 5 | 0 | 0 | **一集都没有** |

**全库合计**（`source_key LIKE 'tg:group:%'`）：

| 口径 | 数值 |
|---|---|
| 分集总数 | **149** |
| 其中 `media_item.title` 非空 | **32** |
| 其中 `media_item.description` 非空 | **31** |
| 其中 `file_path` 非空（有字节） | 111 |
| **剧集级** `media_series.description` 非空 | **49 / 50** |

⇒ **约 79%（118/149）的分集没有标题与介绍**，而**剧集级介绍几乎总是有**。

## 根因

**入库时每个分集的 `media_item.title/description` 只取「该消息自己的 caption」，没有任何组级分发。**

### 事实 1：分集内容 = 该消息自己的 caption（无兜底、无分发）

`register_media_item_t0`（`routes.rs:1760-1815`，取 caption 在 `:1782-1793`）：

```rust
let (title, desc) = row.as_ref()
    .and_then(|m| m.caption.as_deref())
    .map(crate::media::split_caption)
    .unwrap_or((None, None));
// BUG-049 照片条目的可读兜底标题；非照片维持空串（BUG-154：不拿内部文件名伪装标题）。
let title = match title {
    Some(t) => t,
    None if photo_rule => format!("TG 图片 #{msg_id}"),
    None => String::new(),
};
```

`caption` 为空 ⇒ `title = ""`、`desc = None`。**它不查同组其他消息、也不回退 `file_name`** ——
`row` 来自 `st.store.get_message(chat_id, msg_id)`（`routes.rs:1767`），**只取这一条消息**。

### 事实 2：剧集级**有**分发（用的正是那条 caption）

`ensure_series`（`routes.rs:2154`）在 `:2161-2170` 用 **`first_caption`** 切剧集标题与介绍：

```rust
// 剧集标题与介绍来自**组内 caption**：首行标题、其余介绍（split_caption）。
let (title, desc) = match st.store.first_caption(self.chat_id, &self.task_msgs).await { ... };
```

`first_caption`（`media.rs:4215-4233`）遍历 `message_ids`，**返回第一条非空 caption**。

⇒ **同一条 caption 只被用了两次**：**剧集级** + **那条消息自己的分集**。
**其余分集完全拿不到**，因为分集侧没有对应的「回填」逻辑。

### 事实 3：caption 在 TG 上本来就只挂在一条消息上

相册组由上传者一次性发多条视频，**说明文字（caption）通常只写在其中一条**（不一定是第一条）。
实测某 8 条组：**只有其中一条有 caption**，其余全空（但它们**有 `file_name`**）。

### 事实 4：`split_caption` 的形状放大了后果

`split_caption`（`media.rs:4572-4602`）：**首行 = 标题**，其余非空行 = 介绍。
⇒ **单行 caption 只会产出标题、介绍为空**；多行才有介绍。

### 事实 5（**决定修复形态**）：分集介绍有一道「与剧集介绍逐字相同就隐藏」的门控

`shouldRenderEpisodeDescription`（`tauri-shell/src/lib/episodePresentation.ts:45-51`）：

```ts
export function shouldRenderEpisodeDescription(ep, series): boolean {
  const epDesc = (ep.description ?? '').trim()
  return epDesc.length > 0 && epDesc !== (series.description ?? '').trim()
}
```

注释写明理由：TG 抓取的剧集会**把整段剧集简介逐字复制进每一集**（实测某剧集），
而剧集简介已在全剧层常驻 ⇒ 单集层再渲染就是**同一段文案出现两遍**，故**逐字相同才隐藏**。

`SeriesDetail.tsx:946-954` 消费该门控：为真渲染 `data-testid="episode-focus-desc"`，
为假渲染空态 `media.descEmptyEp`（即用户看到的「没有内容」）。

> **⚠ 这条对修复方案是硬约束**：任何「让分集 `description` = 组级介绍」的修法，
> **都会被这道门控判为「重复」而隐藏** ⇒ 数据修好了、**界面上仍然什么都看不到**。
> 修 **BUG-281** 必须**同时**处理这道门控（或改介绍的组织形态），否则等于没修。

## 回答用户的两个问题

**问题 1：「这应该是没有获取到正确的标题内容，因为不在第一个吗？」**

**不是**（至少不是这个原因）。代码**不要求** caption 在第一条：
- 剧集级用 `first_caption` 会**主动找**「第一条非空」，实测剧集 A 的 caption 在**靠后某条**也被正确找到；
- 队列标题 `cache_task_title` 也是「找第一条**有**标题的」。

真正的机制是：**caption 在 TG 上确实只挂在一条消息**（事实 3），
而**分集侧没有任何分发或回填**（事实 1）⇒ 只有那一条的分集有内容。
（**队列侧**另有「被文件名遮蔽」的问题，见 **BUG-280**，那是另一回事。）

**问题 2：「那显示为什么是正常的？」（更正 2026-10-12：用户指的是 TG 中的内容展示，不是媒体库）**

- **用户说的「显示正常」= TG 侧**：相册组在 Telegram（以及 OrigHub 的 TG 面板）里，每条消息**各自**显示自己的 caption；那条**带 caption 的消息**自然就把介绍显示出来了。TG 本就是「一消息一 caption」，不存在「把一条 caption 分发给同组其他消息」的预期 ⇒ 源头内容看着正常，不矛盾。
- **媒体库是错的（非「正常」）**：这正是 BUG-281 本身 —— 入库后 149 个分集仅 31 个有介绍（约 79% 空），与用户原话「媒体库里面也是错误的」一致。上一版我把「剧集页顶部有剧集级 `media_series.description`（49/50 有值，`SeriesDetail.tsx:528-536` / `SeriesHero.tsx:205-213`）」误当成「媒体库看起来正常」的解释 —— 这是误读：剧集级介绍有值**不等于**分集内容不缺失，**分集大面积空是确凿缺陷，不是正常表现**；媒体库顶部有介绍、但逐集空，用户看到的就是「错的」。

⇒ 三个面的正确结论：**TG 源内容正常显示** / **入库队列只剩默认标题（BUG-280）** / **媒体库分集大面积空（BUG-281）** —— 三者读不同的真源列，所以表现不一致。

## 复现

1. 找一个相册组（≥2 条视频消息，仅其中一条带 caption）。
2. 入库后在媒体库打开该剧：**顶部有介绍**；**逐集查看** ⇒ 只有 1 集有标题/介绍，其余空。
3. 只读 SQL 佐证（`<series_id>` 为占位）：
```sql
SELECT e.episode_no, i.title, substr(COALESCE(i.description,''),1,40) AS desc
  FROM media_series s
  JOIN media_episode e ON e.series_id = s.id
  LEFT JOIN media_item i ON i.id = e.item_id
 WHERE s.id = <series_id> ORDER BY e.episode_no;
```

## 修复（**已裁定**，2026-10-12 team-lead 按「按你的推导定」拍定；原选项留痕在下方引用块）

**裁定：选项 1（分集继承组级介绍）+ 门控由「按文本隐藏」改为「按来源标注」。**

### 推导（为什么不是其他选项）

- **实测先把题面修正了**：44 个有介绍的分集里 **36 个与剧集介绍逐字相同**（被门控隐藏），
  只有 8 个不同。题干「只有某一集有介绍」在现行门控下的真实形态是「**几乎每一集都看不到介绍**」——
  带 caption 的那一集（剧集 A 的靠后那一集）的介绍与剧集介绍**逐字相同**（逐字全等，
  只读 SQL 实测），同样被隐藏。⇒ 「组级介绍只惠及一条分集」这个前提不完整，
  **门控本身就把那条分集的介绍也藏掉了**。
- **选项 2/3** 要放宽 BUG-154 或派生标题，超出「修空」的最小面；**选项 4** 不接受。
- **门控删不得**（BUG-171 的「某剧集」场景：分集把剧集简介抄进自己 caption），
  但「**隐藏**」这个处置被实测证伪：它把 36/44 分集的介绍藏掉，**直接产出本条缺陷**。
  改为「**标注**」：与剧集介绍相同的文本显式挂「剧集介绍」标签，不同的挂「本集介绍」——
  重复被写明，不靠隐藏。

### 裁定内容（实现照此执行，不许自决）

1. **引擎侧**：分集无自己的 caption 正文时，`media_item.description` **继承组级 caption 正文**
   （`first_caption` → `split_caption().1`，与 `ensure_series` 同源）。**标题不动**
   （BUG-154：不拿内部文件名/剧集名伪造分集标题；照片沿用 `TG 图片 #<id>` 兜底）。
   存量数据**一次性回填**（`app_setting` 标记键，只补空位；回填条数 + 按剧集分解必须可追索）。
2. **界面侧**：`shouldRenderEpisodeDescription` 改为「**有正文即渲染**」；新增
   `episodeDescriptionIsSeriesLevel` 按与剧集介绍的逐字相同性切换区块标签
   （「剧集介绍」/「本集介绍」）。空态 `media.descEmptyEp` 仅在两层都没有正文时出现。

**不可推翻项维持**：BUG-154（不拿内部文件名伪装标题）、BUG-152（剧集标题取组内 caption）、
BUG-054（介绍空值三态契约）、BUG-232 v2（1s 端点不查 DB）、BUG-205（自动入库不造合集）。

### 原选项留痕（2026-10-12 裁定前）

> **相册组的组级 caption（描述整组/整剧）应当如何作用于各分集？**
>
