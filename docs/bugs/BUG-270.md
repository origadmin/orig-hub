# BUG-270: 本集图组**无条件堆叠** —— 用户原裁定是「超出显示才用跑马灯」，实现把前提条件整个漏掉；且堆叠态**没有跑马**（只有逐次点击翻页）

- 状态: open
- 发现日期: 2026-10-10
- 模块: shell
- 严重程度: mid
- 排期: 2026-11-26

> 来源：用户报告「**本集图组的展示有点问题，当前是默认堆叠的，应该展开，只有宽度不够的情况下才应该堆叠，  
> 且堆叠时应该支持跑马。**」
>
> **本档为任务文档**（用户 2026-10-10 定：后续一律纯文档任务，代码由别的组负责）。

## 现象

### 现象 1：本集图组**无条件**渲染层叠形态 —— 与可用宽度、与帧数**都无关**

`tauri-shell/src/components/media/SeriesDetail.tsx:675-693`（右栏「本集图组」位）：

```tsx
{!editingEpisode ? (
  <div className="flex flex-col gap-1.5 border-t border-border-subtle/60 pt-2.5">
    <h4 ...>{t('media.episode.sectionImages')}</h4>
    {focusFrames.length > 0 ? (
      <div className="py-1">
        <Deck frames={focusFrames} w={focusPortrait ? 170 : 300} h={focusPortrait ? 302 : 169}
              maxW={420} peek={26} onOpenFrame={(i) => openFocusLightbox(cur, i)} />
      </div>
    ) : null}
  </div>
) : null}
```

**唯一门控是 `focusFrames.length > 0`** —— 只要有 1 帧就渲染 `Deck`。  
**没有**任何宽度判断、没有**任何**帧数下限。

### 现象 2：`Deck` 的重叠是**恒定的**（写死在样式里），不是「宽度不足才发生」

`tauri-shell/src/components/media/Deck.tsx`：

| 行     | 代码                                                                                             | 含义                                                    |
| ----- | ---------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `:45` | `const vis = Math.min(n, 6)`                                                                   | 可见槽数固定 ≤ 6                                            |
| `:46` | `const cap = maxW > 0 ? maxW : w`                                                              | 总宽上限 = **硬编码 `maxW=420`**（调用点 `SeriesDetail.tsx:686`） |
| `:48` | `step = n > 1 ? Math.max(8, Math.min(peek, Math.round((cap - w) / Math.max(1, vis - 1)))) : 0` | 露边宽由 `cap` 反推                                         |
| `:81` | `left: slot * p`                                                                               | 第 i 张卡 `left = min(rel, vis-1) * p` ⇒ **相对前一张固定偏移**   |
| `:82` | `zIndex: Math.max(1, n - rel)`                                                                 | 层叠顺序                                                  |

⇒ 每张卡的 `left` 只由 **`n` 与常数 `maxW/w/peek`** 决定，**与容器实际可用宽度完全无关**。  
所以：容器再宽，卡片也照样重叠；容器再窄，重叠量也不变（只会被外层裁切）。

### 现象 3：单帧（n = 1）时**仍走 Deck**（只是恰好不重叠）

`n === 1` ⇒ `step = 0` ⇒ `total = w`。视觉上不重叠，但：

- 仍受 `maxW = 420` 与**固定单卡宽**（`w = 170 竖 / 300 横`）约束 ⇒ 容器宽 900px 时图也只有 300px 宽；
- 仍挂载 `episode-deck-count`（显示 `1 / 1`）与 `⤢` 按钮。

⇒ 用户看到的是「**一张图 + 一个 1/1 计数**」，这是**层叠控件用在单帧上**的语义噪声。

### 现象 4：名字叫「跑马灯」，但**没有任何跑马运动**

`Deck` 的**全部交互**：

| 行          | 交互                                                   |
| ---------- | ---------------------------------------------------- |
| `:57-62`   | `onClick`：点**左半** `prev()` / 点**右半** `next()`（一次翻一张） |
| `:54-55`   | `next/prev` = `head ± 1`（环形）                         |
| `:98-103`  | 右上角计数 `head+1 / n`                                   |
| `:104-116` | `⤢` 打开灯箱                                             |

**没有**：自动滚动、无横向 `scroll`、无拖拽、无滚轮。  
`transition: 'left .42s …'`（`:85`）只是**点击翻页的动画**，不是跑马。

而命名却在承诺跑马：`Deck.tsx:4`「stacked deck 跑马灯」、`SeriesDetail.tsx:99`「本集图组 = **stacked deck 折叠跑马灯**」、  
`:670`「本集图组 = **stacked deck 折叠跑马灯**（规范核心…）」。

## 根因

### 根因 1：**用户原裁定本来就写了「超出显示才用跑马灯」，实现把前提条件整个漏掉**

`docs/design/media-episode-image-handover-2026-09-28.md:25`（**用户原话第 1 条**）：

> 「剧集主图和整体图感觉可以合并成跑马灯…主图的横纵显示,现在纵图变成了裁剪,我觉得应该缩放嵌入的.  
> **图的显示应该首推超出显示使用跑马灯模式.**」

⇒ 「**超出显示**」是**前提条件**：只有放不下时才用跑马灯模式。  
**实现从未表达这个条件**（现象 1：唯一门控是 `length > 0`）。

后续裁定只重申了**位置**、丢掉了**条件**：

| 文档   | 行            | 原文                 | 只约束了什么          |
| ---- | ------------ | ------------------ | --------------- |
| 交接文档 | `:29`        | 「主图跑马灯要那种折叠效果的」    | **形态**（折叠 = 堆叠） |
| 交接文档 | `:30` / §6.1 | 「**我要的只是右边的折叠效果**」 | **位置**（只留右栏）    |
| 交接文档 | `:94`        | 「**折叠效果只保留在右栏**」   | **位置**          |

⇒ **没有任何一条把「超出显示」这个条件带下来**。实现者按「右栏 = 一律 deck」落地，  
条件在交接中**静默丢失**。这是**累积类问题的标准形态**：不是「这设计怎么通过的」，  
而是「**这个条件是否存在过**」—— 存在过（用户原话第 1 条），但**没进实现，也没进验收**。

### 根因 2：「宽度不够才堆叠」在当前架构下**无法表达** —— 全仓没有容器宽度测量能力

实测 `grep -rn "ResizeObserver|useMediaQuery|matchMedia|clientWidth|offsetWidth|container-type|@container" tauri-shell/src`：

| 命中                                              | 用途                                                           |
| ----------------------------------------------- | ------------------------------------------------------------ |
| `SettingsPanel.tsx:932` / `useStore.ts:134,149` | 全是 `matchMedia('(prefers-color-scheme: light)')` —— **主题判定** |
| 其余                                              | **0 命中**                                                     |

⇒ **没有任何一处测量元素宽度**。现有唯一的响应式手段是**视口级 Tailwind 断点**：

- `SeriesDetail.tsx:367` `min-[1100px]:grid-cols-[340px_1fr]` —— 断的是**视口**，不是图组容器。
- 右栏可用宽度 = 视口 − 340px（左栏）− 间距 − 内边距，**二者不等价**；
- 且 `< 1100px` 时左栏退化为**上下堆叠**（`SeriesDetail.tsx:363-365` 注释），右栏变成**全宽**  
  ⇒ 同一视口下右栏可用宽度会**跳变**。

⇒ 「只有宽度不够才堆叠」**不是改几行样式**，而是**缺一个前置能力**（容器宽度观测）。  
这与 **BUG-267 D1** 的「类型筛选前置缺失」同类：**先有测量，才谈条件**。

### 根因 3：「跑马」被当成**命名**而不是**行为**

- `reel(frames,…)`（横向跑马）**只存在于 v3 静态原型**（交接文档 `:71` 列出 `reel`、`:85-86` 记 deckBlock 宽度约束），  
  **未移植进生产代码**；移植进生产的是 `deck.js` 的 click-flip（`Deck.tsx:57-62`）。
- 于是「跑马灯」这个**专有名词**被留在了注释与组件名里，而**运动本身没有实现**。
- 后果：用户按字面理解「跑马灯 = 会自动走 / 能滚」，实际点一下才动一张 ⇒ **命名与行为不符**（用户本次直接点出）。

### 现象 5（旁证）：旧形态**有**「平铺 + 横向滚动」的参照实现，但该组件已是**孤儿**

`tauri-shell/src/components/media/EpisodeExpanded.tsx`（旧手风琴形态的展开态）：

- `:126` `<div className="flex items-start gap-2 overflow-x-auto pb-1" data-testid="episode-images">`  
  ⇒ **平铺一行 + 横向滚动**（正是「展开」形态）；
- `:26` `const IMAGE_INLINE = 3`；`:137-151` 超过 3 张给「**还有 N 张 / 收起**」折叠切换。

**但 `EpisodeExpanded` 已是孤儿**：全仓 `grep -rn "EpisodeExpanded"` 只命中  
**注释**（`SeriesDetail.tsx:103`、`episodePresentation.ts:13`），**0 处 JSX 使用**  
（`EpisodeRow` / `SeriesHero` / `EpisodeBoard` 同样只剩注释引用）。

⇒ 「展开形态」不是没有先例，而是**先例被留在了一个不再渲染的组件里**，未随迁移带入新形态。

## 修复方向（未实施；≥2 实质选项 + 1 个「不做」）

### 选项 A（推荐）：补「容器宽度观测」能力，建立**两态**（够宽平铺 / 不够宽堆叠+跑马）

- **前置**：新增容器宽度观测（`ResizeObserver` + `useElementWidth` hook，或 CSS `container-type: inline-size` + `@container`）。
- **平铺态**（默认）：全部帧按行平铺；放不下时**横向滚动**（复用 `EpisodeExpanded.tsx:126` 的 `overflow-x-auto` 先例）。
- **堆叠态**（仅当平铺所需宽度 > 容器可用宽度）：进入层叠，并**补跑马**（横向可滚 / 可拖；是否自动滚动见「待确认 1」）。
- `涉及:` 新增 1 个 hook 或 1 处 CSS 容器查询 + `Deck.tsx`（两态分支）+ `SeriesDetail.tsx:675-693`（传容器引用）。
- `量化:` 新增 1 个能力（宽度观测）、`Deck` 增 1 个状态分支、调用点改 1 处。
- `回归风险:` 中 —— 需保证平铺态与堆叠态**都能开灯箱**（`⤢` / 点瓦片，R6 能力不回退）。
- `后果:` 完全符合用户原话（「首推超出显示使用跑马灯模式」）；多帧图组在宽屏下不再无谓层叠。

### 选项 B：不新增测量能力，用**帧数阈值**近似「宽度不够」

- 例如 `n ≤ 3` 平铺（复用 `EpisodeExpanded.tsx:26` 的 `IMAGE_INLINE = 3` 口径）、`n > 3` 堆叠。
- `涉及:` `SeriesDetail.tsx:680` 加一个 `n` 判断 + `Deck` 增加平铺分支。
- `量化:` 1 处判断 + 1 个分支。
- `回归风险:` 低。
- `后果:` **零新能力**，但**与「宽度不够」这个真条件不符** —— 宽屏下 5 张图仍层叠（用户要的正是「宽度够就展开」），  
  窄屏下 3 张图可能放不下却仍平铺。**只是近似，不是修复。**

### 选项 C：只修「单帧也堆叠」这一处（最小改动）

- `n === 1` 时改为平铺单图（按容器宽自适应），多帧仍一律层叠。
- `涉及:` `SeriesDetail.tsx:680` 加 `n === 1` 分支。
- `量化:` 1 处分支。
- `回归风险:` 低。
- `后果:` 消除现象 3 的荒谬（`1 / 1` 计数），但**现象 1 / 2 / 4 全部保留** ⇒ 用户本次的三点诉求只解一点。

### 选项 D：不做

- `涉及:` 无（0 行改动）。`量化:` 0。`回归风险:` 无。
- `后果:` 用户原裁定第 1 条（「超出显示才用跑马灯」）**永久不被实现**；「跑马灯」这个名字继续承诺不存在的运动。

## 交付后必须满足（可证伪判据，预先声明）

1. **够宽 ⇒ 平铺**（裁定 D2：**一行平铺**）：当容器可用宽度 ≥ 全部帧平铺所需宽度时，**全部帧在同一行可见且不重叠** ——  
   判定用 `getBoundingClientRect`：任意相邻帧的 `left` 差 ≥ 单帧宽（无重叠），且全部帧的 `top` 相同（确为**一行**，非网格）。
2. **不够宽 ⇒ 堆叠**：当容器可用宽度 < 平铺所需宽度时，进入堆叠态（相邻帧 `left` 差 < 单帧宽）。
3. **堆叠态必须有「自动」跑马**（裁定 D1）：堆叠态下**在没有任何用户输入**时，帧的位置**随时间自行位移**。  
   判法：间隔 ≥ 1s 连续采样同一帧的 `getBoundingClientRect().left` 两次（期间不发任何指针 / 键盘 / 滚轮事件）  
   ⇒ 两次值必须**不同**。若只有「可横向滚动 / 可拖动」而**无自动位移** ⇒ **FAIL**  
   （这正是用户本次点出的「跑马是命名不是行为」，现象 4）。悬停暂停为可选增强，不作为判据。
4. **反向证伪（双向）**：
   - 把容器宽度设为极小（如 200px）⇒ 判据 1 必须 **FAIL**（必须转为堆叠）；
   - 把容器宽度设为极大（如 1600px）⇒ 判据 2 的堆叠必须 **消失**。  
     若两向都不变 ⇒ 说明「宽度」根本没参与判定（**当前现状即此**）。
5. **单帧（n = 1）必须「不影响图片整体 + 居中」**（裁定 D5）：
   - **不裁剪**：显示框的 `width / height` 宽高比与图像原始 `naturalWidth / naturalHeight` **一致**（误差 ≤ 1%）；  
     若二者不等 ⇒ 存在裁剪 ⇒ **FAIL**。
   - **居中**：图像显示框在容器内的左右留白相等（`|leftGap − rightGap| ≤ 2px`）。
   - **无层叠语义噪声**：不渲染 `episode-deck-count`（或渲染为无意义值即判 FAIL）。
6. **既有能力不回退**（BUG-149）：开灯箱（`⤢` / 点瓦片，能力 R6）、`episode-deck-count` 的计数语义、  
   本集图组的**帧来源**（`SeriesDetail.tsx:310-320`：集图 poster 为底 + 挂图依次入列）逐项保留。
7. **判据必须在真实 UI 上验**（BUG-156）：宽度与重叠用 `getComputedStyle` / `getBoundingClientRect` 判定，  
   **不读 className**；并须在两个视口（如 900px / 1600px）各跑一遍。
8. **不得用固定像素断点冒充「宽度不足」**（裁定 D4 = **自动**判定，即必须由**容器宽度观测**驱动）：  
   判据 4 的双向证伪必须通过；  
   若实现用 `min-[1100px]` 这类**视口**断点，判据 4 在「视口不变、容器变宽」时必然 FAIL。

### 裁定对「修复方向」的影响

- **D4 = 自动** ⇒ 采纳**选项 A 的前置能力**（容器宽度观测）；**选项 B（帧数阈值近似）被排除**  
  —— 它与「宽度不够」这个真条件不符（见选项 B 的「后果」）。
- **D5 = 单帧整图居中** ⇒ **选项 C（只修单帧）被排除为完整方案**：它只解 D5，  
  D1 / D2 / D4 全部保留（现象 1 / 2 / 4 不动）。
- ⇒ 实际交付形态 = **选项 A**，且须同时满足 D1（自动跑马）+ D2（平铺 + 横向滚动）+ D4（自动判定）+ D5（单帧整图居中）。

### 裁定引出的两条硬约束

1. **「自动跑马」（D1）与「容器宽度观测」（D4）是两个独立能力**：前者要**运动**、后者要**判定**。  
   两者当前都缺（现象 4 / 根因 2）⇒ 交付必须**同时**补上，只补其一不算完成。
2. **D5「不影响图片整体」与 D2「一行平铺」相容**：平铺态的单帧同样按整图、居中呈现。  
   「不影响图片整体」= **不裁剪**，正对应用户在交接文档 `:25` 的原始不满（「现在纵图变成了裁剪，我觉得应该缩放嵌入的」）。

### D6 边界（**未裁定**；D2 与 D4 在同一场景下指向两种行为，如实登记）

D2 给平铺态配了「**溢出横向滚动**」，D4 又说「**放不下就堆叠**」。二者在**同一个溢出场景**（平铺所需宽度 > 容器可用宽度）  
下**指向不同行为**：前者让你滚，后者让图叠起来。按判据 1 / 2 / 4 当前写死读法（「放不下全部 ⇒ 堆叠」），  
**平铺态的横向滚动将永远不可达**（因为一溢出就转堆叠）⇒ D2 那一半裁定会变成死代码。

两种可能口径，**需下一轮指认**（这是本轮 4 条答复未能覆盖的最小边界，不是实现细节）：

- **口径 α**：溢出**一律**转堆叠 ⇒ 「横向滚动」只作为堆叠态内（叠加自动跑马）的补充手段。  
  优点：二态清晰；缺点：D2 的「溢出横向滚动」名义落空。
- **口径 β**：溢出**先**横向滚动；只有窄到「平铺没有意义」（如容器宽 < 单帧宽 × 2）才堆叠。  
  优点：贴合用户「**只有**宽度不够才堆叠」的语感、保留横向滚动；缺点：需要一个「窄到没意义」的第二阈值。

**在 D6 拍板前**，判据 1 / 2 / 4 按**口径 α** 执行（二态：够宽平铺 / 不够宽堆叠），  
即当前文本；若改判为 β，判据 2 的门槛须同步改写并重新取证。
