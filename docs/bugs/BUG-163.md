# BUG-163: 本地投递节流配额每请求从 0 起算 —— body 首块被扣住 440–725 ms，播放与浏览双重卡顿

- 状态: fixed
- 发现日期: 2026-09-24
- 模块: engine
- 严重程度: high
- 档位: standard

## 现象

用户报「播放浏览卡顿异常严重」，而同一批内容在 `orig-studio-ee` 上正常。

量化后现象是**两个时刻的错位**：媒体条目的本地投递里，

- **响应头 3–28 ms 秒回**（206 的 `Content-Range` 也在这一刻就到达）；
- 但 **`<video>` 在 440–725 ms 内拿不到任何 body 字节**。

且这笔空等**每发一次新 Range 请求就重付一次**，命中路径包括：

| 触发 | 前端位置 |
|---|---|
| 起播 | `serve_local_file`（`media_item_raw` 与 `/api/tg/local/:chat/:msg` 共用） |
| 拖动进度条 | 同上，新 Range 请求 |
| Chromium 断线重取 | BUG-033 记录的 abort-and-re-request |
| 媒体库每张视频卡片进视口抽帧 | `MediaCard.tsx:172` → `generateVideoPoster`（`poster.ts:81`，`preload='metadata'` + seek 到 1 s） |

浏览侧被放大：抽帧并发上限 `MAX_CONCURRENT = 2`（`poster.ts:11`），而每个视频卡片至少发两次
Range 请求（metadata 一次、seek 一次），每次都先付这笔空等；一屏数十张卡片就串行数十秒，
且全程与正在播放的视频抢同一条被节流的通道。

## 根因

`download-engine/crates/orig-tg/src/routes.rs` 的 `serve_local_file`（修复前 `:2607` 起）。

节流的「允许已发字节数」配额**每个请求都从 0 重新起算**：

```rust
let bps = delivery_bps(total, duration_secs);      // :2669（修复前行号）
let started = std::time::Instant::now();           // :2670
...
let due = sent_next as f64 / bps;                  // :2686
let lag = due - started.elapsed().as_secs_f64();
if lag > 0.0 { tokio::time::sleep(...).await; }    // :2689
```

`due` 是**从 0 开始的线性曲线**，而块大小 `CHUNK = 1 MiB`（`:2667`）。于是第一个 1 MiB 块被
推迟到 `1 MiB ÷ bps` 才发出。代入 `bps = max(6 × 码率, 1 MiB/s)`（`delivery_bps`，`:2580`），
用户真实库里 29 条视频的 bps 落在 [1.45, 7.43] MiB/s ⇒ **空等 135–1000 ms，p50 = 492 ms**。

也就是说：BUG-033 为了抑风暴加的限速，**把「Chromium 反复重取」转化成了「每次重取都被扣住
半秒以上」** —— 风暴的字节量被压下去了，代价是每次请求都要重付一次起步延迟。二者本可正交。

### 对照：`orig-studio-ee` 为什么没有这个问题

ee 前端走 `useHls` + `hlsSrc`（`orig-studio-web/src/hooks/useHls.ts:126`、
`components/common/VideoPlayer.tsx:112`），由服务端出 HLS 分片与封面，**不存在这条
「每请求从零起算」的投递节流链**。hub 明确剥掉 HLS、改客户端抽帧，于是把这笔代价完整暴露。

## 复现

```sh
# 库用副本、实例跑非生产端口，绝不触碰 9877 与 %APPDATA%
# item 394 = 206798323 B / 527 s ⇒ bps = max(6×码率, 1MiB/s) = 2.25 MiB/s
curl -s -o /dev/null \
  -w 'header_ttfb=%{time_starttransfer}s\n' \
  -H 'Range: bytes=0-' \
  --max-time 1 \
  http://127.0.0.1:19881/api/media/items/394/raw
```

在一段 `Content-Range: bytes 0-33554431/206798323` 已到达之后，body 仍要等约 0.49 s 才有第一个字节。
正式复现脚本见「验收证据」的入库脚本。

## 修复

给每个响应加一个**以秒计**的初始突发信用，把速率曲线整体右移，而不是改稳态速率：

```rust
/// 初始突发信用（秒）：每个响应开头允许「不计入节流」的时间额度。
const DELIVERY_BURST_SECS: f64 = 4.0;                       // :2570

fn delivery_due_secs(sent_bytes: u64, bps: f64, burst_secs: f64) -> f64 {   // :2577
    (sent_bytes as f64 / bps - burst_secs).max(0.0)
}
```

`serve_local_file` 内把 `due` 从 `sent_next / bps` 改为 `delivery_due_secs(sent_next, bps, burst_secs)`（`:2716`），
`burst_secs` 读 `ORIG_TG_DELIVERY_BURST_SECS`（`:2693`，与 `ORIG_TG_DELIVERY_BPS` 同款覆盖写法），未设则用常量。

用**秒**而非字节，是为了让信用随码率自动缩放：任何码率下都先给「`burst_secs` 秒的播放内容」，
恰好够一次填满可播缓冲，而 4 s 之后的稳态仍严格是 `bps` —— BUG-033 的抑风暴结论不变。

  - 常量 `DELIVERY_BURST_SECS`（`:2570`）、纯函数 `delivery_due_secs`（`:2577`）。
  - `serve_local_file` 的 env 覆盖（`:2693`）与 `due` 计算（`:2716`）。
  - 新增单测 `routes::tests::delivery_due_secs_matches_burst_then_ramps`（`:3515`）、
    `routes::tests::serve_local_file_first_byte_is_immediate`（`:3529`）、
    `routes::tests::serve_local_file_still_throttles`（`:3565`）；
    后两者共用 `static DELIVERY_ENV_LOCK`（`:3511`）串行化（env 为进程级）。

**执行命令与结果（本机实跑）**：

```sh
cd download-engine
cargo test -p orig-tg --lib
# -> test result: ok. 94 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 4.84s
```

**判据（跨机器可核，逐字）**：

- 纯函数：`delivery_due_secs(1024*1024, 1048576.0, 4.0) == 0.0`（首块不等待）、
  `delivery_due_secs(8*1024*1024, 1048576.0, 4.0) == 4.0`（4 s 后按 bps 线性）。
- 端到端：4 MiB 临时文件 + `duration=500`（即 bps 被 1 MiB/s 下限钉住）+ `Range: bytes=0-` ⇒
  **第一个 body 块耗时 < 150 ms**。
- 反向（回归）：同文件、`ORIG_TG_DELIVERY_BURST_SECS=0`、读完全部 body ⇒
  **耗时 >= 3.0 s**（证明稳态节流没被关掉，不是「把限速删了」）。

**验牙（反向证伪，证明断言非恒绿）**：

把 `DELIVERY_BURST_SECS` 临时置 `0.0`（即还原缺陷态）重跑 `serve_local_file_first_byte_is_immediate`
→ **FAILED**，panic 于 `routes.rs:3554`：

```
首块必须立即到达（burst 信用生效）；实际耗时 1.0086859s
test result: FAILED. 0 passed; 1 failed; 0 ignored; 0 measured; 93 filtered out
```

实测 1.0087 s 与诊断预测的 `1 MiB ÷ 1 MiB/s = 1000 ms` 吻合；恢复到 4.0 后同用例 PASS。

**wire 级 A/B（改动前 vs 改动后，隔离实例 + 生产库副本，非 9877）**：

| 394 | 206798323 / 527 | 2.25 MiB/s | 28 → 26 ms | **489 → 27 ms** |
| 408 | 161541698 / 388 | 2.38 MiB/s | 18 → 16 ms | **440 → 17 ms** |
| 359 | 112980880 / 381 | 1.70 MiB/s | 3 → 17 ms | **617 → 26 ms** |

首块改善 −94.5% … −99.3%。

**浏览器层 A/B（真实 `<video>`，用户可见指标）**：

批次：4 条目 × 2 轮 × 3 档（A = 改动前 / B = 修后 / B1 = 修后 + `ORIG_TG_DELIVERY_BURST_SECS=1`）。
口径：headless Edge（与 WebView2 同 Chromium 内核）；未在真实 WebView2 内复测，量级应一致。

| 指标 | A（改动前） | B（修后） | 变化 |
|---|---|---|---|
| 起播（元素挂载 → 首个 `playing`） | 849.3 ms（621–1068） | **95.0 ms**（53–262） | −89% |
| `seek@60s` | 626.3 ms（479–886） | **79.3 ms**（25–178） | −87% |
| 连续 5 次 seek 累计 | 3978.2 ms（3104–6172） | **432.5 ms**（109–1178） | −89% |
| 首个 Range 请求的 body 首块 | 549.1 ms（428–708） | **6.5 ms**（5–11） | −99% |
| 请求数 / `net::ERR_ABORTED` | 10–18 / 7–13 | 10–12 / 7–9 | 下降 |
| **冗余倍率**（20 s 窗口累计字节 ÷ 实播字节） | 1.41–1.87 | **1.27–1.80** | **无回归** |

- 稳态播放三档全程 `waiting 0–1 / stalled 0 / currentTime 最大停顿 0` —— 本缺陷**不落在稳态**，
  用户感知的「卡顿」全部集中在**起播与每一次 seek**（这正是它被报成「播放浏览卡顿」的原因）。
- **定值对照**：`BURST_SECS=1` 与 `4` 无可测差异（seek 76.2 vs 79.3 ms、起播 92.4 vs 95.0 ms、
  冗余 1.41–1.87 vs 1.27–1.80，均在同一噪声带）⇒ 只要 > 0 即足够，`4.0` 安全，无需调小。
- 冗余判据基准（BUG-033）：不限速 63x / 限速后 1.97x；B 稳在 1.x ⇒ 抑风暴结论保持。
