# BUG-223: 非 1x 倍速卡顿 —— 服务端 30fps FRC 降低浏览器解码负载

- 状态: fixed
- 发现日期: 2026-10-09
- 模块: engine+shell
- 严重程度: mid

## 现象

用户确认 1x 正常、2x 略卡、4x 非常卡，且较大视频更容易卡。用户要求高速档不要依赖浏览器以高 `playbackRate` 解码原流，而是由服务端产生固定 30fps 的快进/慢放流，播放器仍以 1x 播放。

## 根因与假设边界

- 「30fps 源 × 4 = 120fps，高于 60Hz，所以必然 judder」不是有效根因：30fps 源的 4x 是 2 帧/vsync 的整数比，呈现 cadence 本身可均匀；2x 也是整数比。非整数帧/vsync 比才会产生 cadence 抖动（见 `.workbuddy-ai/memory/2026-10-08.md` §二十七）。
- 用户已确认卡顿及「越大越卡」；这说明不能再把任务设成重复证明卡顿。较高像素/码率与倍速更可能放大浏览器解码/投递负载，但本机尚无用户真实播放链路的可比量化结果，故不把「解码已被证明是唯一根因」写成事实。
- 本修复通过强制浏览器只解码 H.264 30fps 派生流，直接降低客户端单位时间解码负担；它**不会减少服务端读取/解码源文件的成本**。若服务端实时转码供给不足，仍可能 stall，届时应停止在此方案上迭代并转查吞吐链。

## 方案

所有**非 1x**倍速（0.5x、0.75x、1.25x、1.5x、2x、3x、4x）通过 `/api/media/items/:id/stream?speed=S` 请求服务端 FRC；1x 保持原始 `/raw`（已知不兼容源仍可走原有 H.264 兼容流）。播放器在 FRC 流上设 `playbackRate=1`。

视频滤镜：`setpts=(PTS-STARTPTS)/S,fps=30`。它先按 S 压缩/拉伸源时间戳，再以 `fps=30` 统一采样为 CFR 30fps；适用于任意源帧率、分数倍速及 VFR 输入，不用假设「抽帧步长 K=S」。音频同步使用 `atempo`（大于 2 时级联），仍编码 AAC，不静音。

FRC 输出媒体时间轴被压缩为原时长/S，因此前端按 S 把时间文案和无障碍时间值换算回源内容时间；切换倍速时保存并恢复源内容时间与暂停/播放状态，seek、跳转和进度比例继续对应同一内容位置。

速度代理按条目+倍速分文件、按同一键单飞，禁止不同速度误命中同一代理。

## 用户可见权衡

- 非 1x 切速要切换/启动对应速度代理，首次加载会有转码启动开销；已生成代理后可复用。
- 输出最多 30 个独立画面/秒。2x/4x 时会主动少取源帧，降低浏览器解码负载；如果当前设备本来能轻松解码，运动时间分辨率可能低于原生 `playbackRate`。本修复优先消除「越大越卡」的高负载路径，不承诺创造源中不存在的帧。
- 服务端仍须实时解码源并转码；若源材料/机器导致 ffmpeg 跟不上，FRC 不能掩盖供给 stall。

### 判据②③④ 验收中发现的实现缺陷（已修）

`routes.rs` 的 FRC 分支同时传了 `-r 30` 与 `-fpsmax 30`，ffmpeg 直接拒绝打开输出：

```
[libx264 @ ...] Only one of -fpsmax and -r can be set for a stream.
Error opening output file ...: Invalid argument
```

后果是**所有非 1x 档的流都是 0 字节**（响应头仍带 `decimate=<speed>`，极易被只看响应头的检查判成通过），切速后浏览器再也出不了画面。`fps=30` 滤镜本身已把输出重采样为 CFR 30，`-r 30` 纯属冗余，故删除 `-r 30`、保留 `-fpsmax 30`（实测三档均 `avg_frame_rate=30/1`）。

判据①的脚本 `verify_bug_223_frc_frames.py` 只传 `-r 30`、不传 `-fpsmax`，因此它**测不到这个冲突** —— 判据①与判据②③④此前从未在同一条 ffmpeg 命令行上交叉验证过。

## 评估：`select=not(mod(n\,K))` 抽帧提案（2026-10-09，已否决）

提案原文：「gte 用浮点阈值卡帧时间边界，浮点误差让抽帧变成每 3 帧抽 1（输出 98 帧而非 150）；
整数帧号取模 `mod(n,K)` 才精确，改用 `select=not(mod(n\,K)),setpts=N/30/TB`，`K=round(源fps×S/30)`」。

**结论：方向（整数帧号比浮点时间阈值稳）成立，处方不成立，不予采纳。** 两条硬事实：

1. **诊断对象不在本仓库**：全仓（含 docs）检索 `gte(` 零命中。本仓 FRC 是
   `routes.rs:3170 speed_video_filter` = `setpts=(PTS-STARTPTS)/S,fps=30`，命令行见
   `routes.rs:3459-3468`。「98 帧而非 150」不是这条链路的产物。
2. **处方会让 7 档里的 4 档报废**（`download-engine/verify/verify_bug_223_frc_frames.py --falsify`，
   30fps/300 帧与 25fps/200 帧两个合成源，ffmpeg 自身 `ffprobe -count_frames` 统计）：
   - 30fps 源 1.5x：`K=round(1.5)=2` ⇒ 输出 150 帧 / 5.000s，应为 200 帧 / 6.667s（**时长少 25%，实际变成 2x**）；
   - 30fps 源 0.5x / 0.75x：`K=1` ⇒ 输出 300 帧 / 10.000s，慢放**完全不生效**（`select` 只能丢帧，慢放需要复制帧）；
   - 25fps 源 2x：`K=round(1.67)=2` ⇒ 3.333s，应为 4.000s；25fps 源 4x：`K=3` ⇒ 2.233s，应为 2.000s。
   - 合计 **11/14 档**不满足判据①（仅 30fps 源的 2x/3x/4x 恰好命中整数 K）。

根因是 `K = round(源fps × S / 30)` 只在 `源fps × S / 30` 恰为整数时精确；而 `fps=30`
按时间戳等间隔重采样，**天然表达 2/3 这类分数比**（1.5x 实测 200 帧 = 300×2/3，即 2-1-2-1 均匀抽帧），
且不需要先探测源帧率，VFR 源也有定义（VFR 没有单一 `源fps`，`K` 无定义）。

**采纳的部分**：「用 ffmpeg 自身统计帧数验证」——原单测（`routes.rs:4563`）只断言滤镜**字符串**，
没有一次真实编码，「串写错一个字符」与「真的产出 30fps」在 CI 里长得一样。已补
`download-engine/verify/verify_bug_223_frc_frames.py`：正向 14/14 PASS（30fps 与 25fps 源 ×
0.5/0.75/1.25/1.5/2/3/4 档，断言 `avg_frame_rate=30/1`、时长 = 源/S ±1 帧、帧数 = round(源时长/S×30) ±1），
`--falsify` 反向证伪 11/14 档失败（判据有牙）。这就是判据①的可执行形态。
