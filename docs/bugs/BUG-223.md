# BUG-223: 高倍速（≥3x）卡顿 —— 改用服务端均匀抽帧替代 playbackRate 强制高帧率（帧率转换 FRC）

- 状态: open（方案已定，待实现确认）
- 发现日期: 2026-10-09
- 模块: engine + shell
- 严重程度: mid

## 现象

`no-store` 回退（BUG-219）后播放大幅好转，但用户实测 **2x 仍略微卡顿、4x 非常卡顿**。
用户命题：4x 不要靠「快速刷新（120fps 呈现）」，而是「以 1x 正常播放一个已被均匀抽帧成 30fps 的流」——
即 1 秒墙钟显示 4 秒内容、但**显示节拍恒为均匀 30fps**。

## 根因（已读源码 + 实测核实）

- 本机合成器实测 **精确 60.0Hz**（7 窗口位置 rAF 均 16.67ms；`Win32_VideoController` 报 165Hz 但浏览器拿不到 >60Hz 合成面，§二十七）。
- 库内主力内容是 **30fps**（472=720p60 HEVC 已代理、673=1080p30 HEVC、511=1080p30 H.264）。
- 4x 播放 30fps 源 ⇒ 浏览器须以 **120fps** 呈现；60Hz 显示器只能显示 60 帧 ⇒ 浏览器被迫不均匀丢帧 ⇒ **judder（卡顿观感）**。
  这是物理/管线必然，不是解码或投递不足（`decodeHealth` 有效倍速 ≈0.993、缓冲全程领先、`waiting`/`stalled` 全 0）。
- `<video playbackRate>` **不给呈现调度口子**：它只让解码/呈现提速，超刷新率的部分只能靠合成器丢帧，且 Chromium 对超频的丢帧不均匀 ⇒ 高倍速必然抖。
- 2x of 30fps = 60fps 呈现，**贴着 60Hz**，同轮对照实测 app 与裸 `<video>` 节拍差在噪声内（§二十六 NO-RESIDUAL）⇒ 2x 本身本已平滑；
  用户感知的「略微卡顿」更可能来自**应用控件层在可见期/重渲染的余波**（BUG-217/218 已收敛大部分，非本档范围），或 60fps→60Hz 相位抖动，非本算法能解。

## 算法（用户命题 = 帧率转换 / 均匀抽帧 FRC）

**uniform frame decimation**：输出恒定 30fps 的 H.264 流，每输出帧 = 源的第 0、S、2S… 帧；客户端以 `playbackRate=1` 播放。
- 60Hz 上 30fps 均匀（每帧占 2 个 vsync）⇒ **无 judder**，只是内容快进。
- 这正是 mpv `--fps`/帧步进、主流高倍速快进的底层原理。

## 修复方案（落地于现有 /stream 转码管线，零重构播放器）

1. **服务端 `routes.rs:3407` 的 ffmpeg 参数**：`/stream` 增加 `speed`/`decimate` 查询参数。
   - `S==1`（默认）：保持现管线（`-fpsmax 30` 等，BUG-209）。
   - `S>=3`：追加视频滤镜 `-vf "select='not(mod(n\,S))',setpts=PTS/S/TB"` + 输出 `-r 30`，丢音频（`-an`，快进静音；`atempo` 提速为可选 refinement）。
     `select` 取源第 0/S/2S… 帧，`setpts=PTS/S/TB` 把每帧原时序除以 S ⇒ 输出时长 = 源时长/S、帧间隔恒 1/30s ⇒ S 倍速、均匀 30fps。
     （注意：`setpts` 必须用原 `PTS`/S 而非 `N/30`，否则 `N` 是抽帧前原帧号会让帧间隔仍是 S/30、未归一化。）
2. **客户端 `VideoPlayer.tsx`**：倍速档（`RATES` 在 `:81`）中 **≥3x 路由到 `/stream?speed=S`** 并以 `playbackRate=1` 播放；<3x 保留自然 `playbackRate`（≤60fps 上本已均匀）。
   高倍速一律走 /stream（本就转 H.264，任意源可用，BUG-208）。
3. **取舍 / 已知限制**：
   - 切倍速 / seek 需重启转码（冷启动从 0，BUG-208 既有行为；`no-store` 已回退 ⇒ 6× 冗余被缓存吸收，重启开销可接受）。
   - 分数倍速（1.25/1.5/0.75/0.5）需**插值**而非抽帧，本轮不覆盖（它们 ≤60fps 上本已平滑）。
   - 纯客户端 WebCodecs 自绘可达任意倍速**瞬时**切换，但等于重写播放器，本轮不做。

## 修复后必须满足（可证伪判据）

1. 4x 下：app 与裸 `<video>` 同轮对照 `ΔgapP95 ≤ 5ms`、`|Δpresented| ≤ 1.5`（即 4x 不再有应用侧 judder）。
2. `x-orig-stream` 响应头标记抽帧档（如 `decimate=4`）以便诊断。
3. 用户主观：4x 流畅（快进观感，无卡顿）；2x 不低于现状。
