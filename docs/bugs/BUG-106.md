# BUG-106: orig-tg 的 sender runner 静默死亡后，所有实时 RPC 恒失败且健康态谎报 ok

- 状态: fixed
- 修复 commit: `fe2b7e4`
- 发现日期: 2026-09-22
- 模块: engine
- 严重程度: critical

## 现象

用户报「TG 功能显示 400 Bad Request：`{"error":"request error: dropped (cancelled)"}`」。

实测（2026-09-22 02:0x，orig-tg pid 20240 已运行多时）：

- `GET /api/tg/folders` → **400** `{"error":"request error: dropped (cancelled)"}`;
- `/api/tg/logs` 里**每一条**实时 RPC 都在失败：
  - `monitor tick failed: request error: dropped (cancelled)`（每 30s 一条，连续数十条）
  - `cache task 65: failed on 2476: request error: dropped (cancelled)`
- 但「健康态」三个口径**全部说正常**：
  - `GET /api/tg/session` → `{"available":true,"phase":"Authorized","user_id":523058983}`
  - `GET /api/tg/diag` → `{"available":true,"health":"ok","mode":"ready"}`
  - `GET /api/tg/dialogs` → **200**（走缓存/本地库，不触网）

即：**TG 实际已完全不可用，但所有健康检查都报绿**，用户只会在点了某个真发请求的功能时才撞见一个裸露的 400。

## 根因

`request error: dropped (cancelled)` 是 grammers 的 `InvocationError::Dropped`
（`grammers-mtsender-0.10.0/src/errors.rs:253`）。该变体语义明写（同文件 `:228-232`）：

> The request was cancelled or dropped, and the results won't arrive.
> **This may mean that the `SenderPoolRunner` is no longer running.**

四个独立缺陷叠加：

1. **runner 句柄被丢弃，死亡不可观测**（主要）
   `download-engine/crates/orig-tg/src/grammers.rs:126`
   ```rust
   let _runner = tokio::spawn(pool.runner.run());
   ```
   `JoinHandle` 绑到 `_runner` 后随 `connect()` 返回即被 drop（detach）。runner 任务
   **panic 或退出后无人知晓、也无人恢复** —— 之后每一次 `invoke()` 都返回 `Dropped`，
   进程却继续存活并对外报 200。这是本条「静默死亡」的直接原因。

2. **`/api/tg/folders` 把传输层错误裸抛成 400**
   `crates/orig-tg/src/routes.rs:546-549`
   ```rust
   async fn folders(...) -> Result<impl IntoResponse, ApiError> {
       let folders = st.client.folders().await?;   // ← 失败即 400，原文直出
       Ok(Json(folders))
   }
   ```
   **同一处失败在 dialogs handler 里是被容忍的**：`routes.rs:350`
   `if let Ok(folders) = st.client.folders().await { ... }`。
   同一依赖、两种容错策略 —— 不一致本身就是缺陷。

3. **健康态不看活性，只读本地状态**
   - `session.phase` 读的是会话文件里的授权态（`Authorized` 只说明「曾经登录过」）；
   - `diag.health` 同理；
   - 两者都**不做任何一次真实 RPC 探活**。
   于是「sender 已死」在健康接口上完全不可见。

4. **`daemon` 的 `tg_start` 存在「端口被将死进程占住 → 误判已运行」的竞态**（次要，本轮另记）
   `crates/orig-daemon/src/state.rs:137-140`
   ```rust
   if self.tg_is_running_on(port).await { return Ok(true); }   // 不 spawn
   ```
   `tg_stop()` 只 `kill()` 不等退出；紧接着 `tg_start()` 时若将死进程仍持有 9877，
   `tg_port_has_listener` 返回 true → **提前返回 true 且不拉起**，于是 TG 永久下线。
   实测：连续 `PUT /api/config/tg {enabled:false}` → `{enabled:true}` 后，
   接口回 `tg_running:true` 但**进程列表中根本没有 orig-tg**。

## 复现

1. 让 orig-tg 长时间运行（本例约数小时）直至 sender runner 死亡（触发条件待查，见「待确认」）；
2. `curl http://127.0.0.1:9877/api/tg/folders` → 400 `request error: dropped (cancelled)`；
3. `curl http://127.0.0.1:9877/api/tg/session` → 仍 `phase:Authorized`；
4. `curl http://127.0.0.1:9877/api/tg/diag` → 仍 `health:ok`。

**反向验证（证明是客户端状态而非网络）**：
用同一份会话与凭据新起一个 orig-tg（端口 9899，避免干扰），`GetDialogFilters` **完全正常**：

```
[tg] GetDialogFilters raw count=3 variants=[default,chatlist,chatlist]
[tg] folder id=2 title="‼️全网分组中心A‼️" include=84 mapped=84
[tg] folder id=3 title="MyTop"        include=18 mapped=18
```

**同时排除网络因素**（BUG-094 教训：只测 TCP 端口会误判）：
经 `socks5://127.0.0.1:7897` 对 `149.154.167.51:443` / `149.154.167.50:443` /
`91.108.56.130:443` 做真实 SOCKS5 CONNECT + TLS 握手：
- SOCKS 握手三处全部成功（0.02–0.04s）；
- TLS 报 `WRONG_VERSION_NUMBER` —— 这是**可达**的证据（Telegram 的 443 跑 MTProto 而非 TLS，
  服务端回了非 TLS 字节）。若上游真断，表现会是 `UNEXPECTED_EOF`（BUG-094 当时即如此）。

结论：**网络、代理、DC 均通；故障在 orig-tg 进程内的 sender runner**。

## 修复

### 已实施（2026-09-22）

1. **保留 `JoinHandle` 并暴露活性**（根治「静默」）
   - `crates/orig-tg/src/grammers.rs`：`GrammersClient` 新增 `sender: Option<JoinHandle<()>>`；
     `connect()` 里 `let _runner = tokio::spawn(...)` → `let runner = ...` 并存入结构体。
   - 新增 `Client::link_alive()`（trait 默认 `true`，`GrammersClient` 用
     `!handle.is_finished()` 实现，`UnavailableClient` 覆写为 `false`）。
2. **健康接口如实反映链路**
   `crates/orig-tg/src/routes.rs` 的 `diag`：新增 `link_alive` 字段；
   `health` 由恒为 `"ok"` 改为链路断时报 `"degraded"`。
3. **`/api/tg/folders` 与 dialogs 容错一致**
   失败时返回 `[]` 并 `push_log` 留痕（含「链路已断 → 重启 orig-tg 恢复」的可行动提示），
   **不再把传输层原文裸抛成 400**。
   **响应体仍是数组**（前端 `listTgFolders(): Promise<TgFolder[]>`，改形状会直接破坏解析），
   活性另由 `diag.link_alive` 暴露 —— 不靠响应体塞状态位。
4. **daemon 重启竞态修复**（恢复通道本身）
   `crates/orig-daemon/src/state.rs`：`tg_stop()` 在 `kill()` 之后
   `timeout(TG_STOP_WAIT_TIMEOUT, c.wait())` 等子进程真正退出，让 OS 释放 9877。
   新增常量 `TG_STOP_WAIT_TIMEOUT = 5s`（超时也不阻塞调用方）。

### 未实施（有意留白）

- **runner 死亡后进程内自愈**（重建 `SenderPool` + runner）：
  **尚未拿到 runner 的退出原因**（panic payload）。不知道病因就重连，
  等于把崩溃变成崩溃循环 —— 先把 `link_alive` 的观测面铺开，
  等下一次复现时从日志/句柄拿到退出原因再定自愈策略。
- 因此当前恢复路径仍是**重启 orig-tg**（daemon 托管），但这条路径现在：
  (a) 不再被端口竞态卡死（第 4 项已修）；(b) 链路断了会被 `diag` 如实报出来。

## 验收证据

### 1. 恢复后的实测端点（daemon 正规托管，非手动旁路）

```
$ netstat -ano | grep LISTENING | grep -E "9876|9877"
  TCP    127.0.0.1:9876   LISTENING   46536    ← orig-daemon
  TCP    127.0.0.1:9877   LISTENING   46516    ← orig-tg（daemon 自动拉起）
```

```
GET /api/tg/session  200  {"available":true,"phase":"Authorized","user_id":523058983,...}
GET /api/tg/diag     200  {"health":"ok","link_alive":true,"api_configured":true,
                           "mode":"ready","session_phase":"Authorized",
                           "proxy":"socks5://127.0.0.1:7897",...}
GET /api/tg/folders  200  [{"id":2,"title":"‼️全网分组中心A‼️","channelIds":[…84 个…]},
                           {"id":3,"title":"MyTop","channelIds":[…18 个…]}]
```

分组数据与故障前一致（84 + 18 个频道），**不再出现 400**。

### 2. 健康态不再谎报（反向证伪）

故意用**错误数据目录**启动 daemon（不带 `ORIG_TG_DATA`，落到默认的
`%LOCALAPPDATA%/OrigHub`，那里没有凭据），新的 `diag` 如实报出降级：

```
GET /api/tg/diag     200  {"health":"degraded","link_alive":false,
                           "api_configured":false,"mode":"unavailable",
                           "unavailable_reason":"api_id/api_hash not configured",...}
GET /api/tg/folders  503  {"error":"api_id/api_hash not configured; bind a Telegram account first"}
```

**反向证伪成立**：修复前同一个接口在链路已死时照样回 `health:"ok"`；
现在 `health` 会随链路状态变化，且 `folders` 不再把传输层原文裸抛成 400
（凭据缺失走 `503` + 可行动文案，链路断开走降级 `[]` + `push_log` 留痕）。

### 3. daemon 重启竞态已修（第 4 项）

```
$ curl -X PUT .../api/config/tg -d '{"enabled":false}'
  {"ok":true,"tg_enabled":false,"tg_running":false}
  → orig-tg 进程消失，9877 释放

$ curl -X PUT .../api/config/tg -d '{"enabled":true}'
  {"ok":true,"tg_enabled":true,"tg_running":true}
  t=2s  9877 UP                      ← 修复前：30s 内始终 not yet，且谎报 running:true
$ curl .../api/tg/folders  → 200 + 真实分组
```

```

```

## 待确认

- runner 退出的**触发条件**尚未定位：是 panic、是连接断开后 runner 主动 quit、
  还是某种超时。需要在 `grammers.rs:126` 处捕获 handle 的退出原因（panic payload）
  才能定性。**在拿到退出原因前，第 4 项（自愈）不宜贸然实现** —— 不知道病因就重连，
  可能只是把崩溃变成崩溃循环。
