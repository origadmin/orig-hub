# BUG-348: 入库流水线用「下载进度」的语言表达「入库状态」——语义错配 + 排版错乱

- 状态: fixed
- 发现日期: 2026-10-21
- 模块: shell
- 严重程度: high

## 现象

用户夜报第 3 条（用户同时给出**正确的语义裁定**）：

> 入库流水线表示形式严重逻辑问题，正确的逻辑是**只管自己，只管完成、非完成等
> 简易内容，不管进度等等**；这部分所有逻辑全不对，排版也不对，按钮位置都是错乱
> 排版，错误进度条，完全不可用。

当前每一行（`CacheManagerDialog.tsx` 的 TaskRow，第 358-620 行）承载了四层内容：

1. 第 500-505 行：`<Progress>` **进度条**；
2. 第 510-521 行：百分比 `pct%` + `done/total` + 更新时间戳；
3. 第 525-551 行：字节读数 / **下载速度** / **剩余时间 ETA** / 停滞秒数；
4. 第 552-556 行：正在处理的消息 id；此外还有失败原因、未入库说明、删除确认条，
   以及行尾多个动作按钮（去下载查看 / 优先下载 / 取消优先 / 去媒体库 / 重试 /
   取消 / 删除）挤在同一行尾。

## 根因

把两个不同业务的词汇表混用了：

- **入库**问的是「这份内容进没进来」——答案是**二元的**（已入库 / 未入库），
  未入库时只需说清「为什么」（失败 / 中断 / 取消）；
- **下载**才问「传了多少、多快、还要多久」。

进度条 + 速度 + ETA 是后者的词汇，搬到前者身上得到的是**不可证伪的噪声**：
用户看到一条 73% 的行，无法据此判断「这条算不算进来了」。

排版侧是同一个根因的一体两面：一行同时塞「进度条 + 若干个参数 + 若干颗按钮」，
排版只能靠 `flex-wrap` 自由落体 ⇒ 用户观察到的「按钮位置错乱」不是对齐失误，
是**承载过量**之后的必然结果。

## 修复（已实施）——按用户裁定重写语义与排版

1. **删进度类读数**：进度条、`pct%`、字节、速度、ETA、停滞秒数、`done/total`、
   「准备中」、正在处理的消息 id、宿主时钟 `nowMs` —— 全部撤出流水线行
   （`STALL_MS`/`RATE_FRESH_MS`/`fmtEta`/`formatSpeed`/`Progress` 随之删除）；
2. **行只表达状态档**：状态徽标 + 标题 + 条数 + 更新时间（一行）；异常行第二行
   只放**成因**（`describeTgFailure` + `isItemFailureSummary` 例外保留）；
3. **动作区定槽**：行尾单一右侧槽——时间 + 优先/取消优先（`icon-sm` 图标钮 ★/☆）
   + **一颗主操作**（三态互斥：已入库→去媒体库查看 / 可重试→重试 / 进行中→取消）
   + 删除（`icon-sm` ✕，危险确认条保留）；
4. **跨界出口撤出**：「去下载查看」连同 `onGoDownload`/`onOpenDownload` 全链删除
   （TgPanel/MainLayout 接线一并清），条目级明细的家本来就在下载域；
5. 行级勾选保留（BUG-346 负责让它的状态可见）。
