# BUG-375：`/api/tg/cache/tasks/all` 读路径打库等锁（用户：「获取现在进度这是毫秒级的需求」）

- 状态：fixed
- 发现日期：2026-10-22
- 模块：engine
- 严重程度：high
- 域：engine
- 用户原话（2026-10-22）：
  - 「TG 入库任务暂时无法读取：request orig-tg: error sending request for url (http://127.0.0.1:19787/api/tg/cache/tasks/all)」
  - 「为什么有一条数据? 这不是统一获取的吗? 下载应该就一个接口吧? 前端只负责展示,不然功能全乱了.」
  - 「逻辑有问题,获取现在进度这是毫秒级的需求,当前实现完全不对, 单请求->毫秒响应. 内部实现逻辑肯定有严重问题.」

## 根因（实测，不是推测）

用户报错时 `GET /api/tg/session` 正常返回 Authorized —— orig-tg 活着、探针绿、不重启，但 daemon 聚合层仍报 cache 源不可用。对同一端点连测三次：

| 次数 | 耗时 | daemon 4s 超时下的结果 |
|---|---|---|
| 1 | 3.18s | 勉强过 |
| 2 | 0.03s | 过 |
| 3 | **13.70s** | **超时 ⇒ `error sending request for url`** |

reqwest 对**超时**的显示正是 `error sending request for url`，看着像"连不上"，其实是"太慢了"。

**为什么慢**：`list_all_cache_tasks` 每次请求打三条 SQL（`list_cache_tasks(500)` + 逐频道标题 + 清单摘要聚合），而 `st.store` 与下载 worker **共用同一条 libsql 连接** —— worker 一持写事务，读只能排在后面等锁。实测无写竞争时三条合计仅 **36ms**（标题查询占 33ms：10 个频道拉回 3768 行，只为取其中几百条标题）⇒ 观测到的 3.18s/13.70s 与 36ms 之间 100～400 倍的差距**全部是等锁**。

**内部实现的严重问题（用户说对了）**：同文件的 `/api/tg/cache/tasks`（单任务端点）**早已**改读内存快照，`state.rs:111` 注释白纸黑字写着「每次都打 SQLite 既浪费又与下载 worker 的写争用同一连接……读走内存是流畅度的底线」。而 `/tasks/all` 同在轮询路径上（daemon 每 5s 拉一次），却还在直接打库 —— **快的那条的成果没有辐射到慢的那条**。这不是不知道，是没做全。

原两候选结论：① 本机企业代理 —— **排除**（`build_http_client` 已 `no_proxy()`，`state.rs:180`）；② 「orig-tg 运行时 stall」—— **表述不准**，进程不假死，是重端点等锁。

## 修法

1. **读路径零 DB**：`list_all_cache_tasks` 抽内核 `all_cache_tasks_payload`，改读三个内存快照（tasks / 标题来源 / 清单摘要），全部由「唯一写者」在每次 DB 变更后经 `refresh_cache_tasks` 同步重建（25 个写点全覆盖，读方 clone `Arc` 即返回）。
2. **快照上限对齐契约**：`refresh_cache_tasks` 的 limit 50 → `CACHE_TASK_SNAPSHOT_LIMIT = 500`（否则"读改走快照"会顺带把条数砍到 50，界面无故少显示 450 条）。
3. **写点开销从 34ms 降到亚毫秒**：新增 `store::message_captions_for_refs`，标题查询只取任务**实际涉及**的 message_id（`channel_id = ? AND message_id IN (...)`，每批 400 防变量数上限）。旧查询把每个频道所有有标题的消息全拉回（实测 10 频道 / 3768 行 / 33ms）。
   - 为什么必须省：这 34ms 移到写点后，实测把墙钟用例 `wall_clock_accumulates_across_restarts…` 的重启次数从 3 压到 2（`assert!(restarts >= 3)` 红）—— **修读路径不能变成拖慢写路径**。

## 验收证据

修复提交 `c206939`；测试（`cargo test -p orig-tg --lib`）：

- **BUG-375 判据 1（有牙）** `all_cache_tasks_payload_reads_snapshot_not_store_bug375`：入队后**故意不刷快照** ⇒ 此刻 DB 有 1 条而快照空，payload 必须返回 0 条（走库就会返回 1 条）；刷完后必须一次拿到任务 + 标题 + 清单摘要。
  - **反向证伪**：把实现改回 `st.store.list_cache_tasks(500)` ⇒ 断言立刻红，报「未刷新快照时必须返回 0 条 —— 走库就会返回 DB 里那 1 条（旧行为）」，`left: Some(1)` vs `right: Some(0)`。还原后复测绿。
- **BUG-375 判据 2** `snapshot_limit_matches_the_endpoint_contract_bug375`：快照上限 == 500（端点契约）。
- **回归**：`list_all_cache_tasks_omits_discarded_counts_bug085` 补一行 `refresh_cache_tasks` 后绿（该端点已改读快照，测试须按新契约刷）。
- **全量对齐**：`cargo test -p orig-tg --lib` 改动后 318 passed / 2 failed；**HEAD 基线全量同样 2 failed**（`cache_task_rerun_is_idempotent` 既有失败、`wall_clock_accumulates…` 全量并行假红——单跑绿、并行红）⇒ 同断言同数据，与本批无因果。passed 316 → 318（新增 2 个）。
- **测试编译坑（记档）**：`routes.rs` 的 `mod tests` 用**显式 `use super::xxx;` 白名单**（非 `use super::*`）⇒ 新加的被测函数必须同时加进白名单，否则 E0425「cannot find function」，而函数明明定义在同文件顶层——症状与病因相距极远。
