# BUG-375：`/api/tg/cache/tasks/all` 读路径打库等锁（用户：「获取现在进度这是毫秒级的需求」）

- 状态：fixed
- 发现日期：2026-10-22
- 模块：engine
- 严重程度：high
- 域：engine
- 用户原话（2026-10-22）：
  - 「TG 入库任务暂时无法读取：request orig-tg: error sending request for url (http://127.0.0.1:19787/api/tg/cache/tasks/all)」
  - 「为什么有一条数据? 这不是统一获取的吗? 下载应该就一个接口吧? 前端只负责展示,不然功能全乱了.」
  - 「逻辑有问题,获取现在进度这是毫秒级的需求,当前实现完全不对, 单请求->毫秒响应. 内部实现逻辑肯定有严重问题.」

## 根因（实测，不是推测）

用户报错时 `GET /api/tg/session` 正常返回 Authorized —— orig-tg 活着、探针绿、不重启，但 daemon 聚合层仍报 cache 源不可用。对同一端点连测三次：

| 次数 | 耗时 | daemon 4s 超时下的结果 |
|---|---|---|
| 1 | 3.18s | 勉强过 |
| 2 | 0.03s | 过 |
| 3 | **13.70s** | **超时 ⇒ `error sending request for url`** |

reqwest 对**超时**的显示正是 `error sending request for url`，看着像"连不上"，其实是"太慢了"。

**为什么慢**：`list_all_cache_tasks` 每次请求打三条 SQL（`list_cache_tasks(500)` + 逐频道标题 + 清单摘要聚合），而 `st.store` 与下载 worker **共用同一条 libsql 连接** —— worker 一持写事务，读只能排在后面等锁。实测无写竞争时三条合计仅 **36ms**（标题查询占 33ms：10 个频道拉回 3768 行，只为取其中几百条标题）⇒ 观测到的 3.18s/13.70s 与 36ms 之间 100～400 倍的差距**全部是等锁**。

**内部实现的严重问题（用户说对了）**：同文件的 `/api/tg/cache/tasks`（单任务端点）**早已**改读内存快照，`state.rs:111` 注释白纸黑字写着「每次都打 SQLite 既浪费又与下载 worker 的写争用同一连接……读走内存是流畅度的底线」。而 `/tasks/all` 同在轮询路径上（daemon 每 5s 拉一次），却还在直接打库 —— **快的那条的成果没有辐射到慢的那条**。这不是不知道，是没做全。

原两候选结论：① 本机企业代理 —— **排除**（`build_http_client` 已 `no_proxy()`，`state.rs:180`）；② 「orig-tg 运行时 stall」—— **表述不准**，进程不假死，是重端点等锁。

## 修法

1. **读路径零 DB**：`list_all_cache_tasks` 抽内核 `all_cache_tasks_payload`，改读三个内存快照（tasks / 标题来源 / 清单摘要），全部由「唯一写者」在每次 DB 变更后经 `refresh_cache_tasks` 同步重建（25 个写点全覆盖，读方 clone `Arc` 即返回）。
2. **快照上限对齐契约**：`refresh_cache_tasks` 的 limit 50 → `CACHE_TASK_SNAPSHOT_LIMIT = 500`（否则"读改走快照"会顺带把条数砍到 50，界面无故少显示 450 条）。
3. **写点开销从 34ms 降到亚毫秒**：新增 `store::message_captions_for_refs`，标题查询只取任务**实际涉及**的 message_id（`channel_id = ? AND message_id IN (...)`，每批 400 防变量数上限）。旧查询把每个频道所有有标题的消息全拉回（实测 10 频道 / 3768 行 / 33ms）。
   - 为什么必须省：这 34ms 移到写点后，实测把墙钟用例 `wall_clock_accumulates_across_restarts…` 的重启次数从 3 压到 2（`assert!(restarts >= 3)` 红）—— **修读路径不能变成拖慢写路径**。

## 过程发现：本修复自身引入的一处回归（已修）

第一版修完后补规模化实测，暴露了**自己引进来的问题**——原修法只盯着读路径，没查「写点到底新增了多少」：

| 测量项（400 任务 / 4000 引用） | 第一版（debug） | 增量合并后（debug） | 增量合并后（**release**） |
|---|---|---|---|
| `list_cache_tasks(500)` | 5.44 ms | 5.44 ms | 1.45 ms |
| `message_captions_for_refs` | 43.40 ms | 43.40 ms（仅首刷） | 12.84 ms（仅首刷） |
| `task_manifest_summaries` | 6.82 ms | 6.82 ms | 3.17 ms |
| `refresh_cache_tasks`（**首刷**） | 54.77 ms | 54.77 ms | 23.33 ms |
| `refresh_cache_tasks`（**稳态**，下载循环内每条目一次） | 54.77 ms | **11.80 ms** | **6.96 ms** |
| `all_cache_tasks_payload`（**读路径**） | 23.60 ms | 19.68 ms | **6.75 ms** |

**release 读路径 6.75ms**（400 任务 / 4000 消息量级）就是用户「单请求 → 毫秒响应」的答案；对照第一版 3.18s 是 **470 倍**差距，且那 3.18s 里绝大部分是等锁而非真在干活（无写竞争时三条 SQL 仅 36ms）。

根因：`run_one_cache_task` 的下载循环里**每下载完一条目就调一次** `refresh_cache_tasks`（`routes.rs` 两处 `done += 1` 之后，HEAD 本来就有这两个调用点）。HEAD 版刷新只做一次 `list_cache_tasks(50)`（约 1ms），第一版把它变成「任务 + 全量标题 + 清单摘要」三条 SQL ⇒ 单任务 10 条目多花 550ms，且**全程占着那条唯一的 libsql 连接**——等于把 BUG-375 的等锁从读路径原样搬进了下载循环。墙钟用例条目少，所以没抓到它。

**修法（增量合并）**：标题来源是 Telegram caption，一条消息解析过一次就不会变（唯一例外是自愈补写）。所以 `refresh_cache_tasks` 改为**只查快照里还没解析过的引用**，并把值类型改成 `Option<MsgTitleSources>`：

- 键不存在 = 还没解析过 ⇒ 这次查；
- `Some(s)` = 解析过、有标题；
- `None` = 解析过、确实没有标题 ⇒ **不再重查**（否则无标题消息会被每次刷新反复查）。

稳态下新增引用为 0，标题一条 SQL 都不打 ⇒ 稳态刷新 54.77 → 11.80ms。

**配套的失效机制（漏了就等于自愈白做）**：`backfill_message_titles` 从 Telegram 补回 caption 写库后，必须显式 `invalidate_cache_task_titles` 把这些引用打回「未解析」——否则快照里它们早已是 `None`，补回来的标题被永久挡在快照外：界面看不到，且 `spawn_title_selfheal` 也不会再触发（它只扫无标题任务，而那时标题已经在库里了）。这条路由**走真实生产路径**的测试守着（见判据 4）。

**而「只打回未解析」本身也是一个 bug（本档第二条自查）**：`invalidate` 只移除键、不查库，于是 `/tasks/all` 再读快照时这些引用不见了 ⇒ 标题消失；下一轮自愈看到「无标题」去补，`message_has_title` 却已经为真 ⇒ 直接跳过、不写库、也就不再触发任何解析 ⇒ **标题要等到下一次写点才可见**。而写点可能几个小时都不来（全部任务终态时没有任何 DB 写入）。所以最终形态是 `resolve_cache_task_titles`：**当场查库并把结果写回快照**，标题立即可见，不依赖任何后续刷新。两个方法的分工写在了 `state.rs` 的文档注释里（`invalidate` = 下次刷新时重查，调用方必须能等；`resolve` = 现在就查写回）。

## 验收证据

修复提交 `c206939`（第一版）+ 本轮增量合并；测试（`cargo test -p orig-tg --lib`）：

- **BUG-375 判据 1（有牙）** `all_cache_tasks_payload_reads_snapshot_not_store_bug375`：入队后**故意不刷快照** ⇒ 此刻 DB 有 1 条而快照空，payload 必须返回 0 条（走库就会返回 1 条）；刷完后必须一次拿到任务 + 标题 + 清单摘要。
  - **反向证伪**：把实现改回 `st.store.list_cache_tasks(500)` ⇒ 断言立刻红，报「未刷新快照时必须返回 0 条 —— 走库就会返回 DB 里那 1 条（旧行为）」，`left: Some(1)` vs `right: Some(0)`。还原后复测绿。
- **BUG-375 判据 2** `snapshot_limit_matches_the_endpoint_contract_bug375`：快照上限 == 500（端点契约）。
- **BUG-375 判据 3（规模实测）** `all_cache_tasks_payload_is_millisecond_scale_bug375`：400 任务 / 4000 引用量级上逐条 SQL 计时 + 读路径计时，数字直接打进测试输出。
  - 实测（**release**，出厂真值）：首刷 23.33ms、**稳态 6.96ms**、对照 29.86ms、**读路径 6.75ms**。debug 下同批为 95.18 / 19.72 / 91.18 / 30.75ms——未优化构建慢约 3 倍，所以判据绝不能按 debug 的贴线值设。
  - **判据用比值不用绝对值**：322 个用例并行跑时机器负载能让任何耗时涨 2～3 倍（实测读 19.7→52.3ms、稳态 11.8→32.6ms），拿贴线绝对阈值当判据，红的是 CI 抖动而不是功能缺陷。所以主判据是 `对照 > 稳态 × 1.5`（两者只差标题查询，机器快慢同比例放大两边、不动比值），绝对上界只取 250ms 这种「数量级没崩」的宽值。
  - **反向证伪**：把 `.filter(|r| !titles.contains_key(r))` 改回 `.filter(|_r| true)`（全量重查）⇒ 稳态 63.34ms vs 对照 65.05ms（比值 1.03）⇒ 立刻红。还原后复测绿。
- **BUG-375 判据 4（有牙）** `selfhealed_title_reaches_the_snapshot_bug375`：首刷后引用被标记为「解析过、无标题」；经**真实自愈路径**（直接调 `backfill_message_titles`，夹具客户端 `message_meta` 返回预置 caption）补回标题后，payload 必须拿到它。
  - **刻意不调 `refresh_cache_tasks`**：生产里 `/tasks/all` 之后同样没人会刷（写点可能几小时不来）⇒「补回的标题要可见」不能依赖刷新。补一次 refresh 就会把「生产代码漏了这一步」放过去。
  - **反向证伪 ①**：删掉 `backfill_message_titles` 末尾的失效调用 ⇒ `left: None` vs `right: Some("自愈补回的标题")`，红。
  - **反向证伪 ②**：把 `resolve_cache_task_titles` 改回「只 remove 键」（第一版正是如此）⇒ 同样红，报「必须**不依赖刷新**就进入快照」。还原后复测绿。
  - 为什么必须走真实路径：在测试里手动调失效接口的话，「生产代码漏了挂钩」这件事测试照样绿，牙齿就没了。
- **回归**：`list_all_cache_tasks_omits_discarded_counts_bug085` 补一行 `refresh_cache_tasks` 后绿（该端点已改读快照，测试须按新契约刷）。
- **全量对齐**：`cargo test -p orig-tg --lib` 本轮 **321 passed / 1 failed**；HEAD 基线（`git stash` 只暂存本批两个文件）**单独跑同一用例同样红** ⇒ `cache_task_rerun_is_idempotent` 是既有失败，同断言同数据，与本批无因果。passed 319 → 321（新增判据 3、判据 4 两个测试）。
  - 注：第一版全量时 `wall_clock_accumulates_across_restarts…` 在全量下红（重启 3→2），单跑绿 ⇒ 并行假红；增量合并把稳态写点开销降下来后，该用例在全量下**转绿**。
  - release 模式下 4 个 BUG-375 用例同样全绿（`cargo test --release -p orig-tg bug375`）。
- **测试编译坑（记档）**：`routes.rs` 的 `mod tests` 用**显式 `use super::xxx;` 白名单**（非 `use super::*`）⇒ 新加的被测函数必须同时加进白名单，否则 E0425「cannot find function」，而函数明明定义在同文件顶层——症状与病因相距极远。
