# BUG-255: 媒体库剧集集数统计错误 —— 大量多集内容显示为 1 集

- 状态: fixed
- 发现日期: 2026-10-10
- 模块: engine（shell 无需改动）
- 严重程度: mid
- 修复提交: BUG-255 引擎侧修复（见文末）

## 现象

用户原话：「3. 媒体库卡片集数统计问题不正确，大量包含多集的显示 1 集。」

## 取证结论（2026-10-10，引擎侧，只读副本 + 引擎单测复现）

> 取证副本路径（生产库只读拷贝，未触碰生产库）：
> - 生产库本体：`download-engine/tg_store.db` 与根 `tg_store.db`（引擎 `config.rs:46` 默认 `./tg_store.db`）
>   经 `copy` 到临时目录后实测 **0 行**（fresh skeleton，本机从未以真实数据跑过引擎）。
> - 唯一真实世界样本：`verify_shots/bug126-live/store.db`（**旧 schema**，无 `media_episode_image` 表）
>   已拷贝到 `/d/tmp/bug255/dbs/` 只读分析。
> - 当前 schema（含 `media_episode_image`）的生产库不在仓库内（随部署应用走），故真值分布无法在仓库内直接取；
>   根因与修复由引擎自身 `Store` API 的确定性单测复现并验证（见验收证据）。

### 1. `episodeCount` 的产生函数 / 口径

- 函数：`Store::list_series_filtered`（`download-engine/crates/orig-tg/src/media.rs:1469`）。
- 映射点：`media.rs:1533` 读取 SELECT 第 8 列 `r.get(8)?` → `SeriesView.episode_count`。
- 产生 SQL（第 1475 行）：
  ```sql
  (SELECT COUNT(*) FROM media_episode e WHERE e.series_id = s.id)
  ```
  —— 统计 `media_episode` 表里**本剧集的分集行数**。
- 同一次 `SeriesView` 扩展里 BUG-250 新增的口径（第 1496 / 1498 行）：
  ```sql
  -- videoCount（第 13 列）
  (SELECT COUNT(*) FROM media_episode e JOIN media_item i ON i.id = e.item_id
     WHERE e.series_id = s.id AND i.kind = 'video')
  -- photoCount（第 14 列）
  (SELECT COUNT(*) FROM media_episode e JOIN media_item i ON i.id = e.item_id
     WHERE e.series_id = s.id AND i.kind = 'photo')
  ```
- **口径差异**：`episodeCount` 数的是 `media_episode` 的**全部行**（不论 kind：视频分集、photo-only 组的照片分集、file/audio 分集）；`videoCount`/`photoCount` 是**同一张表**按 `JOIN media_item.kind` 切出来的两个分区。三者**都不数** `media_episode_image`（集级挂图）与 `media_episode_source`（备用源）。这正是 bug 所在（见第 4 点）。

### 2. 真值分布

- 仓库内生产库（root `tg_store.db`、 `download-engine/tg_store.db`）：**0 行**，无法提供真值。
- 旧 schema 真实样本 `verify_shots/bug126-live/store.db`：
  - `media_series = 6`，`media_episode = 43`，`media_item = 115`（video 85 / photo 30）。
  - `media_item` 中 `file_path IS NULL` = 4（均为 photo；video 全部已落盘）。
  - 每 series 的 episodes 分布：`{1:1, 5:2, 9:2, 14:1}`（即 1 部 1 集、2 部 5 集、2 部 9 集、1 部 14 集）。
  - 纯视频相册归组正确（series 1..5 的 `ep_count == distinct_ep_items`），证明**归组逻辑本身没错**，缺陷在「集数计数」而非「归组」。
- 结论：当前 schema 的真实用户库不在仓库；根因与修复改由引擎单测确定性复现。

### 3. 三个「明明多集却显示 1 集」的反例

由于生产库不在仓库，以下反例基于引擎 `Store` API 的确定性复现（即真实引擎行为），并用旧样本佐证机制一致性：

- 反例 A（确定性复现，核心）：一个**混编组**——1 个视频 + 3 张照片（照片按 BUG-168 作为集级挂图挂在视频那一集，而非独立分集）。
  - 实际媒体数 = 1 视频 + 3 照片 = **4**；
  - 修复前引擎 `episodeCount = 1`、`photoCount = 0` → 卡片显示「1 集 / 1 视频 / 0 图片」；
  - 即「1 预告片 + N 海报/截图」这类最常见的相册，全部被压成「1 集」。
- 反例 B（同机制，N=2）：1 视频 + 2 照片 → 显示「1 集」，应为 **3**。
- 反例 C（同机制，N=5）：1 视频 + 5 照片 → 显示「1 集」，应为 **6**。
- 佐证（旧样本，证明不是归组虚高）：`bug126-live` 的 series 1「Big Buck Bunny · 码率阶梯」`ep_count=14 == distinct_ep_items=14`——纯视频相册归组无误；一旦混入照片走挂图路径，「14」就会塌成「1」。 defect 对所有混编组**统一成立**，与用户「大量」的描述一致。

### 4. 根因判定

**真实根因：计数查询漏算 `media_episode_image`（集级挂图）。**

- 在**混编组**（组内含视频）里，照片不建 `media_episode` 行，而是作为集级挂图写到 `media_episode_image`
  （`routes.rs` `register_photo_slot` → `attach_photo` → `add_episode_image`；`media.rs` 触发器
  `trg_media_episode_image_photo_only_ins` 仅放行 photo 入 `media_episode_image`）。
  于是这些照片既不进 `media_episode`，也不进 `media_episode_source` → 对 `episodeCount`/`videoCount`/`photoCount`
  **三个计数器全部隐形**。一个「1 视频 + N 照片」的相册于是显示 `episodeCount = 1`。
- **候选 ①（BUG-248 入队未带 `register_slot`）**：属实但**非根因**。代码注释（`routes.rs:1618`）明确入队只登记
  `media_item`、集槽由 worker 建——这是设计（worker 的 `IngestCtx::register_slot` 负责成剧分集）。无论槽位何时建立，
  计数查询都漏算挂图，故 ① 不是造成「显示 1 集」的原因。
- **候选 ②（归组按消息各建 series ⇒ `media_series` 虚高）**：**不成立**。`ensure_series`（`routes.rs:1872`）
  以 TG 相册 `group_id` 作为幂等 `source_key`（`tg:group:{chat}:{group}`），同相册消息正确归并为一部剧；
  旧样本 series 1..5 也证实纯视频相册归组准确。故 ② 非根因。

### 5. 影响面

- **卡片读数（`list_series_filtered` → `SeriesView.episodeCount`/`videoCount`/`photoCount`）**：**受影响**——这是 bug 本体。混编组集数/图片数被严重低估（甚至归零）。
- **剧集详情分集列表（`list_episodes` + `list_episode_bindings`）**：照片作为集级挂图**数据仍在**、详情内能看到，但凡引用 `episodeCount` 的「集数」标签同样错标；属**部分受影响**（数据不丢，计数标签错）。
- **EE 导出 manifest（`export_bundle`，`media.rs:1967`）**：**不受影响**——导出 SQL 同时 `JOIN media_episode` 与 `media_episode_image`，把分集及其挂图一并复制，文件不漏。故导出内容完整，仅卡片读数错。

## 修复

- 文件：`download-engine/crates/orig-tg/src/media.rs` 的 `list_series_filtered`。
- `episodeCount` 改为对本剧集**全部媒体条目**去重计数：
  `media_episode`（分集主条目）**∪** `media_episode_image`（集级挂图），备用源 `media_episode_source`（同内容另一缓存副本）**不计入**。
- `photoCount` 改为（分集主条目里的 photo）**∪**（集级挂图里的 photo）去重计数；`videoCount` 维持只数 `media_episode` 视频分集
  （挂图表仅含 photo，不影响）。
- 列序号未变（`episode_count`=第 8 列、`photo_count`=第 14 列），`SeriesView` 映射无需改动。
- 纯照片组（photo-only）每张照片本身即是独立分集，修正后计数不变（仍 = 照片数），无回归。
