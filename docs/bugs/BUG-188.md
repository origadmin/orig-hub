# BUG-188 纯图组的「加入媒体库」排在传输队列里：不需要字节的编目动作被落盘队列延迟

- **状态**: fixed
- **发现日期**: 2026-09-29
- **模块**: shell
- **严重程度**: low

关联 BUG-049（TG 图片不落盘、按需代理）、BUG-181（单飞队列与排队态呈现）、BUG-184 / BUG-185（同一操作行的另两面）、产品语义「编目与落盘是两个正交模块」。

## 现象

在 TG 相册上，**同一个文案「加入媒体库」在不同粒度下走两条完全不同的路径**：

| 粒度 | 路径 | 用户感受 |
|---|---|---|
| **单张**图片（`MessageBubble`） | `importPhoto` → `importMediaItems`（**同步**） | 点完即入库 |
| **相册组**（`AlbumBubble`，含纯图组） | `downloadAlbum` → `enqueueCacheTask`（**入单飞队列**） | 点完先显示「排队中」+「取消」 |

对**纯图组**（组内全是 photo、没有任何视频）来说，整组**一个字节都不需要落盘**（BUG-049：图片由 raw 端点现场代理），
却仍要排进**传输队列**：worker 忙时（正在下载别的视频）该组长时间停在「排队中」，
而「排队中」这一支会**遮蔽操作行**（见下），用户看到的既不是「加入媒体库」也不是完成态 ——
正是 BUG-185 那种「这个页面到底能不能缓存」的认知错误，只是触发条件不同。

## 根因

### 前端：相册的按钮只有一条出口

| 位置 | 事实 |
|---|---|
| `tauri-shell/src/components/TgPanel.tsx:1207-1219` | `downloadAlbum(items)` → `enqueueCacheTask({chatId, messageIds, groupId})` |
| `tauri-shell/src/components/TgPanel.tsx:1252-1268` | `importPhoto(item)` → `importMediaItems([{source:'tg', ref, kind:'photo', …}])`（同步、批量端点） |
| `tauri-shell/src/components/TgPanel.tsx:1279` | `onAlbumDownload` = `downloadAlbum` —— 相册按钮**唯一**出口 |
| `tauri-shell/src/components/TgPanel.tsx:1276` | `onBubbleImportPhoto` = `importPhoto` —— 单张图片才有同步出口 |
| `tauri-shell/src/components/TgPanel.tsx:2243` 起 | 相册操作行调用 `onDownload(items)`（无论组构成） |

### 呈现：排队态是三分支里的第一支，会顶掉其余两支

| 位置 | 事实 |
|---|---|
| `tauri-shell/src/components/TgPanel.tsx:2216` | `{progress ? (` —— 只要有任务覆盖该组，就走这一支 |
| `tauri-shell/src/components/TgPanel.tsx:2218-2222` | `progress.queued` → 渲染 `[data-testid="album-queued"]`（「排队中」）+ `:2232` 「取消」 |
| `tauri-shell/src/components/TgPanel.tsx:2243` | `) : !allDone ? (` —— **只有 `progress` 为空才可能看到按钮** |
| `tauri-shell/src/components/TgPanel.tsx:2262` 起 | `) : (` 完成态分支 —— 同样被排队态遮蔽 |

### 后端：worker 对 photo **会登记**（所以不是死按钮，只是排队）

| 位置 | 事实 |
|---|---|
| `download-engine/crates/orig-tg/src/routes.rs:1793` | `let photo_rule = media_type.as_deref() == Some("photo")` |
| `download-engine/crates/orig-tg/src/routes.rs:1814-1828` | BUG-049 分支：`ing.register_item(…, photo_rule)` + `register_slot` → `push_log("photo {msg_id} registered to library (no cache by rule)")` → `done += 1` → `continue`（**不取字节**） |
| `download-engine/crates/orig-tg/src/routes.rs:1753-1759` | 注释明确「登记从『任务终态一次性 append』前移到『逐消息取字节之前』」⇒ 登记是 T0 的、必然发生的 |

⇒ 纯图组走 worker **最终会入库**，本条**不是**「按钮无效」，而是「**不需要字节的动作被排在字节队列后面**」。
与产品语义（编目与落盘是两个正交模块，编排层按序驱动）不符：编目不该等落盘队列。

## 复现

**已完成：静态证据链（决定性）**

```sh
# ① 两条路径不同源
sed -n '1207,1219p;1252,1268p;1276,1279p' tauri-shell/src/components/TgPanel.tsx

# ② 排队态遮蔽操作行（三分支第一支）
sed -n '2216,2245p' tauri-shell/src/components/TgPanel.tsx

# ③ worker 对 photo 只登记不取字节
sed -n '1793p;1814,1828p' download-engine/crates/orig-tg/src/routes.rs
```

**部分完成：运行时观测（只有一次，且非我复现）**

验收时观察到：纯图组点「加入媒体库」后**入队一个 cache task（id=96）**，
**121 秒**内未产生任何 `media_item` 行，最终取消该任务、改直接调 API 才完成入库。

> **诚实边界**：这一次观测发生在「worker 正忙」的条件下（当时队列里有其他组的视频任务）。
> 「延迟多久」因此**不是稳定判据** —— 本档只主张**路径错位**（不需要字节的动作排进了字节队列），
> 不主张某个具体延迟数字。修复动工前应补一次可控复现（造一个占住 worker 的任务 → 观察纯图组是否停在「排队中」）。

## 修复

方向：**按组构成分流**（与 BUG-184/185 的分叉判据同源，都用「需落盘条目数」）。

1. `cacheTargets === 0` 的组（纯图组）：点「加入媒体库」直接走**批量** `importMediaItems`
   （一次调用带上该组全部 ref —— 原子端点，**禁止**前端循环调单条），
   并像 `importPhoto` 那样把 refs 加入 `photoLibRefs`（`TgPanel.tsx:1264`），使该组**立刻**进入完成态。
2. `cacheTargets > 0` 的组（含视频）：保持走 worker（视频必须落盘），**不得**改动这条路径。
3. 不得为了本档把「排队中」这一支删掉 —— BUG-181 裁定「排队不可见」是缺陷，排队态必须如实呈现；
   本档要消除的是**不该出现的排队**，不是排队的呈现。

> 端点已核实（本档发现时）：`tauri-shell/src/api/media.ts:259-261`
> `importMediaItems(items: ImportEntry[])` → **一次** `POST /api/media/items`（body `{items}`）⇒
> 批量原子端点**已存在**，无需新增；修复只需把纯图组的出口指过去。

## 关联

- BUG-049：TG 图片不落盘、raw 端点现场代理 —— 本档的「不需要字节」依据。
- BUG-181：单飞队列与排队态呈现（「排队不可见」是缺陷）—— 本档**不否定**排队态，只否定错误的排队来源。
- BUG-184 / BUG-185：同一操作行的另两面（假分数 / 完成态落空）。三条应共用「需落盘条目数」这一判据。
- 产品语义（AGENTS.md §5 / 落地文档）：编目（内容域）与落盘（传输域）**正交**，编排层按序驱动 ——
  本档是该原则在「相册按钮出口」上的具体违反。
