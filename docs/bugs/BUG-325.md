# BUG-325: 单测把用户真实媒体搬出 `~/Downloads`（27.5 GB 落进 %TEMP% 夹具）

- 状态: fixed
- 发现日期: 2026-10-19
- 模块: engine
- 严重程度: critical

## 现象（本次改动的自查发现，非用户报告）

BUG-323 复报（下载路径选择无效）修到一半时跑 `cargo test -p orig-tg store::`，
4 条测试失败；排查失败原因时发现**两条失败测试已经把真实用户数据搬走了**：

- `~/Downloads/library`（211 文件 / 24 GB）→ `%TEMP%\orig_tg_store_<pid>_\bug323_migrate\Downloads\library`
  （一部分）与 `%TEMP%\...\bug323_downloads\Downloads\library`（另一部分）
- `~/Downloads/legacy-downloads`（33 文件 / 3.5 GB）→ `%TEMP%\...\bug323_downloads\Downloads\legacy-downloads`

原始报错本身已经指明动了真实目录，只是一眼看不出来：

```text
thread 'store::tests::migrate_legacy_library_root_bug323' panicked at store.rs:2810:
called `Result::unwrap()` on an `Err` value:
"read C:\Users\godcong\Downloads\library\每日沙雕墙--1001341930464: 系统找不到指定的路径。 (os error 3)"
```

## 根因

为修「改下载路径后存量失联」，在 `Store::legacy_managed_roots()` 里加了平台默认
下载目录（`~/Downloads`）下的两处引擎旧落点。问题是这两处的来源是
`orig_core::paths::default_download_dir()` —— 它在**测试进程里同样解析到真实家目录**，
而测试的 `download_dir` 指向 %TEMP% 夹具，于是「真实 `~/Downloads/library` →
夹具目录」成了一条合法迁移：

1. **可由单测触达 ≠ 只应由启动路径触达**：迁移源一旦来自全局真源（真实家目录），
   任何调用 `migrate_legacy_managed_roots()` 的单测都会把它当合法来源搬走。
2. **并行测试放大**：`cargo test` 默认多线程，两条测试同时搬同一个真实目录 ⇒
   `每日沙雕墙--1001341930464` 被一条测试 rename 走、另一条随即可读不到
   （os error 3），内容**分裂**到两个夹具里（一边空目录、一边 7 个文件）。
3. **只搬不覆盖挡不住「搬错地方」**：`move_dir_contents` 的不覆盖纪律保证不毁数据，
   但没有任何机制阻止「把真实目录整体搬进临时目录」这种越界搬动。

## 修复

1. **拆出独立的启动路径迁移**：平台默认落点从 `legacy_managed_roots()` 移出，
   改为纯函数 `Store::platform_default_legacy_roots(default_dir, dl, library_root)`
   （默认目录由参数注入）+ `migrate_platform_default_legacy_roots()`，
   **只由 `main.rs` 启动路径调用**，任何单测都触达不到真实家目录。
2. **纯函数单测覆盖逻辑**（`platform_default_legacy_roots_lists_only_engine_subdirs_bug325`）：
   ① 只列 `library` 与 `legacy-downloads` 两项引擎子目录（不列默认目录整体）；
   ② 默认目录 == 下载路径时一项都不列；③ 大小写/分隔符差异也算相同。
   回归判据：把纯函数改回直接调 `default_download_dir()` ⇒ 该测试编译不过（参数没了）。
3. **既有两条 BUG-323 测试恢复原断言**（`["downloads"]` / `["library"]`），
   因为它们本就只应看到一个夹具内落点。

## 验收证据

- 数据已完整还原（同卷 rename，字节未损）：`~/Downloads/library` 211 文件 / 14 个
  chat 目录 / 24 GB；`~/Downloads/legacy-downloads` 33 文件 / 3.5 GB。
  夹具生成文件（`chat--1/*`、`abc--1-2.mp4`、`photo--1_3.jpg`）已排除，未混回用户数据。
- 可核验引用（入库路径 / 命令，跨机器可复核）：
  - `download-engine/crates/orig-tg/src/store.rs` 的
    `platform_default_legacy_roots`（纯函数，默认目录由参数注入）与
    `migrate_platform_default_legacy_roots`（`pub`，启动路径专用）；
  - `download-engine/crates/orig-tg/src/main.rs` 启动段
    "platform-default legacy root migrated" 日志块；
  - 复跑命令：`cargo test -p orig-tg store::` —— 必须全绿，且
    `platform_default_legacy_roots_lists_only_engine_subdirs_bug325` 在列；
  - 反向证伪：把纯函数改回直接调 `orig_core::paths::default_download_dir()`
    ⇒ 该测试失去注入参数、编译即失败（参数没了），
    `grep -n "default_download_dir" download-engine/crates/orig-tg/src/store.rs`
    在**非 main 侧**应零命中。

## 沉淀的规则

**迁移/清理类代码的「源」不得来自进程级全局真源（家目录、当前用户目录），
除非调用方只能在生产路径上。** 判据：写这类函数时先问「单测能不能用它碰到真实
用户目录」——能，就把真源改成注入参数，并由启动路径单独包一层。
