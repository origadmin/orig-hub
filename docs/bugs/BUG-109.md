# BUG-109: 清缓存无论成败都报 `removed`，删除失败被静默吞掉

- 状态: fixed
- 严重程度: mid
- 模块: engine
- 发现日期: 2026-09-22

## 现象

`/api/cache/clear`（含 `ids` / `orphan` / `all` / `stale` / `failed` 各档）无论删除是否真的成功，
一律返回 `removed: N`。若 `remove_file` 失败（文件被占用 / 权限）或 `set_item_file_path`
失败（DB 锁），用户看到的是「已清理 N 项、释放 X 字节」，而**文件还在磁盘上**，
条目也可能仍显示「已缓存」。

## 根因

`crates/orig-tg/src/cache.rs` 的 `purge_item()`：

```rust
let _ = std::fs::remove_file(&it.file_path);        // 失败被吞
let _ = st.store.set_item_file_path(it.id, None).await;  // 失败被吞
Purged { removed: 1, skipped: 0, bytes }            // ← 无论成败都算 removed
```

两个失败都被 `let _ =` 吞掉，返回值**无条件**计为 `removed: 1`。

讽刺的是，该函数的文档注释恰恰写着：

> 集合档与分档共用同一实现，避免「某条路忘了复位 TG 标记」这类分支漂移
> （**清字节却仍显示「已缓存」是最难查的一类不一致**）。

也就是说，这段代码的**意图**正是防止这类不一致，而它的实现自己在制造这种不一致。

与 BUG-106 同源：错误在源头被销毁，只剩一个「看起来成功」的表象供下游猜。

## 修复

- `Purged` 增加 `failed` 字段，`add()` 一并累加。
- `purge_item()` 分两步判定：任一步失败即计 `failed`（**不计 `removed`、不计 `bytes`**），
  并各留一条 `push_log` 说明失败原因；两步都成功才计 `removed: 1`。
- 三处响应（`ids` / `orphan` / 其余档）与 `push_log` 均带上 `failed`。
- 响应新增 `"failed"` 字段是**向后兼容**的（前端忽略不认识的字段），
  `removed` 的含义从「尝试清理的条数」收敛为「真正清掉的条数」。

保留「尽力而为」语义：单条失败不中断其余条目，但结束时如实报失败数。

## 验收证据

- 编译：`CARGO_TARGET_DIR=/d/tmp/cargo-106 cargo check -p orig-tg` → **0 error / 0 warning**
  （0 warning 说明 4 个 `Purged` 构造点都已被完整覆盖，没有遗漏字段）。
- 改动文件：`download-engine/crates/orig-tg/src/cache.rs`。

**未做端到端实测**：需要构造「文件被占用导致 `remove_file` 失败」的场景，
Windows 上造占用容易但会牵动正在运行的播放器进程，且缓存工作集当前为空
（`removed=0` 的路径走不到）。失败分支的**留痕与计数逻辑**为静态确认；
下次清缓存时若出现 `failed > 0`，日志会直接给出原因，可据此补验。
