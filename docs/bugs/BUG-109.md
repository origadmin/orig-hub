# BUG-109: 清缓存无论成败都报 `removed`，删除失败被静默吞掉

- 状态: fixed
- 严重程度: mid
- 模块: engine
- 发现日期: 2026-09-22

## 现象

`/api/cache/clear`（含 `ids` / `orphan` / `all` / `stale` / `failed` 各档）无论删除是否真的成功，
一律返回 `removed: N`。若 `remove_file` 失败（文件被占用 / 权限）或 `set_item_file_path`
失败（DB 锁），用户看到的是「已清理 N 项、释放 X 字节」，而**文件还在磁盘上**，
条目也可能仍显示「已缓存」。

## 根因

清缓存链路上有**三处**吞错，分布在两个入口：

**入口一 `purge_item()`（批量清理）**

```rust
let _ = std::fs::remove_file(&it.file_path);        // 失败被吞
let _ = st.store.set_item_file_path(it.id, None).await;  // 失败被吞
reset_tg_flag(st, &it.source, &it.ref_key).await;   // 内部也吞（见下）
Purged { removed: 1, skipped: 0, bytes }            // ← 无论成败都算 removed
```

**入口二 `clear_item()`（单条清理）**

```rust
let _ = std::fs::remove_file(&path);                // 失败被吞
...
Ok(Json(json!({"ok": true, "cleared": true})))      // ← 照样报成功
```

**第三处最隐蔽 —— `reset_tg_flag()`**

```rust
let _ = st.store.clear_downloaded(chat, msg).await;  // 失败被吞
```

这条是 BUG-029 点名症状的**直接成因**：清了字节但 `downloaded` 没复位，
**下次缓存 upsert 会让条目「复活」**，用户看到的就是「删不掉」。
它比「文件没删掉」更隐蔽 —— 磁盘上确实没了，界面却仍显示已缓存。

讽刺的是，该函数的文档注释恰恰写着：

> 集合档与分档共用同一实现，避免「某条路忘了复位 TG 标记」这类分支漂移
> （**清字节却仍显示「已缓存」是最难查的一类不一致**）。

也就是说，这段代码的**意图**正是防止这类不一致，而它的实现自己在制造这种不一致。

与 BUG-106 同源：错误在源头被销毁，只剩一个「看起来成功」的表象供下游猜。

## 修复

- **`reset_tg_flag()` 改为返回 `bool`**：`clear_downloaded` 失败、或 `source=="tg"`
  却解析不出 `(chat, msg)`，都留痕并如实返回 `false`。
- **`purge_item()`（批量）**：`Purged` 增加 `failed` 字段；删文件 / 清 `file_path` /
  复位 `downloaded` **任一步失败即计 `failed`**（不计 `removed`、不计 `bytes`），
  并各留一条 `push_log` 说明原因。
- **`clear_item()`（单条）**：`remove_file` 失败不再被吞 —— 直接 500 并说明原因；
  `reset_tg_flag` 失败同样 500，文案点明「条目可能在下次同步后复活」。
- 三处响应（`ids` / `orphan` / 其余档）与 `push_log` 均带上 `failed`。
- 响应新增 `"failed"` 字段是**向后兼容**的（前端忽略不认识的字段），
  `removed` 的含义从「尝试清理的条数」收敛为「真正清掉的条数」。

保留「尽力而为」语义（批量）：单条失败不中断其余条目，但结束时如实报失败数。
单条入口则相反 —— 它只有一个目标，失败就该如实失败。

## 验收证据

- 编译：`CARGO_TARGET_DIR=/d/tmp/cargo-106 cargo check -p orig-tg` → **0 error / 0 warning**
  （0 warning 说明 4 个 `Purged` 构造点都已被完整覆盖，没有遗漏字段）。
- 改动文件：`download-engine/crates/orig-tg/src/cache.rs`。

**已实测（单测，`cache::tests`）** —— 两条覆盖成功与失败两条分支：

```
purge_reports_failed_when_the_file_cannot_be_removed ... ok
purge_reports_removed_when_the_file_is_gone          ... ok
```

- 失败分支的构造技巧：`inside_dir` 对**不存在的文件**会退到父目录判定，
  所以「路径在缓存目录内、但文件本身不存在」能通过目录校验，
  却必然让 `remove_file` 失败 —— 无需真的去占用一个文件（那会牵动正在运行的播放器）。
  断言：`failed == 1`、`removed == 0`、`bytes == 0`，且日志里有 `purge_item` 留痕。
- 成功分支（反向约束）：真写一个 512 字节的文件再清，断言
  `removed == 1`、`failed == 0`、`bytes == 512`，且文件确实不在了。
  没有这条，就无法排除「把 failed 写反、连成功也计失败」这种反向错误。

未覆盖：`reset_tg_flag` 中 `clear_downloaded` **真的返回 Err** 的那条路径
（内存库上它不会失败）—— 该分支同样是静态确认。
