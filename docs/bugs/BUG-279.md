# BUG-279: 媒体库「未缓存」条目与入库队列任务**无关系联动** —— 看不到它到底在不在队列、是不是失败、还是压根没状态

- 状态: open
- 发现日期: 2026-10-11
- 模块: engine+shell
- 严重程度: high
- 排期: 2026-11-10

> 来源：用户 2026-10-11 指令：「添加媒体库未缓存有品可能在入库队列中的任务关系联动，知道视频实际是失败，还是根本没有状态等等，评估下具体逻辑和方案，添加 BUG」。
>
> **本档为任务文档**（与 BUG-277 同例：纯文档，代码由别的组负责）。
>
> **与 BUG-261 / BUG-170 / BUG-277 的关系**：BUG-261 已把「未缓存可点缓存 / 有更好版本可切换」做完，但**只解决「能不能发起」，没有解决「发起之后这条到底什么状态」**；BUG-170/248 把**元数据先于字节登记**（条目先存在、字节后到），于是媒体库里天然存在大量「有信息、无字节」的条目。这两点叠加 ⇒ 用户面对一个未缓存条目，**完全无法判断它是「排队中 / 正在下 / 上次下失败（为什么）/ 被取消 / 还是压根没入过队」**。这正是用户要的「关系联动」。

## 现象

用户在媒体库（尤指剧集内页 `SeriesDetail`）看到一个**未缓存**的视频（有标题、有来源、`hasBytes=false`），但：

1. **不知道它现在在不在入库队列** —— 只能去「缓存管理」弹窗里一条条翻，且弹窗是**全局单飞视图**（`GET /api/tg/cache/tasks` 只回当前唯一 running 任务 + queued 摘要），**没有按条目定位的查询**。
2. **不知道它有没有失败过、失败原因是什么** —— 比如某条大文件被墙钟判失败（`BUG-276`），或源被踢、Token 过期、磁盘满，失败原因写在 `cache_task.error`，但**前端没有任何入口把这条 error 透出来**。
3. **不知道它是「失败 / 取消」还是「根本没状态」** —— 也就是用户原话的「实际是失败，还是根本没有状态」。两条语义天差地别：前者需要「重试 / 重新缓存」，后者只是「去点一下缓存」。当前 UI 不区分，统一显示成「可缓存」灰字，用户无从判断。

**危害**：未缓存条目 ≠ 未发起缓存。当队列不健康（见 BUG-274/276，队首可能被一条慢流占 21 小时）时，用户以为「点了没反应 / 没下下来」，其实是**卡在队列里或上次已失败**，但界面给不出任何线索，只能去翻全局弹窗撞运气。这是「未缓存」状态的**信息黑洞**。

## 根因

联动在**三层都缺**，每一层都有确切的落点：

### 1. 引擎层：没有「按条目查任务」的查询，且现有查询只覆盖活跃态

- `cache_task` 表**已经**存了全部所需字段：`status`（字符串，`download-engine/crates/orig-tg/src/store.rs:167`）、`error`（`Option<String>`，`store.rs:172`，失败原因就在这里）、`done`/`total`（进度，`store.rs:160-170`）。
- 但 `store.rs:963` 唯一的按 key 查询 `active_cache_task(item_key)` **只查 `status IN ('queued','running')`**（常量 `CACHE_TASK_ACTIVE_STATES`，`store.rs:186`）。
- **没有任何查询返回终态任务**（failed / cancelled / interrupted / done）给一个 `item_key`。所以「这条是不是上次失败了」在引擎层**根本查不出来**。
- 状态机全集（来自 `BUG-277` 档案与 `routes.rs`）：`queued → running → done|failed|cancelled|interrupted`，还有 BUG-257 的 `RETRYABLE_STATES=["failed","cancelled","interrupted"]`。终态一清二楚，但**没有按条目回看终态的通道**。

### 2. 接口层：没有任何「按条目」的查询端点

`routes.rs:55-73` 的缓存端点全集是：
`GET /api/tg/cache/tasks`（当前唯一 running + queued 摘要）、`GET /api/tg/cache/tasks/all`、`GET/DELETE /:id`、`POST /:id/priority`、`POST /api/cache/tasks/:id/retry`、`DELETE /api/cache/tasks?ids=`。
**全部是「全局视图」或「按任务 id」**，**没有任何「按 item_key / 按 chat:msg」定位的端点**。壳层 `api/tg.ts:390 getCacheTask()` 只拿全局唯一任务，**无法问『这条视频的缓存任务是什么状态』**。

### 3. 壳层：判据看得到来源，看不到任务

- `lib/mediaSources.ts:118 canRecacheEpisode()` / `episodeRecacheCandidates()`（BUG-261）只用 `source/ref`（chatId:messageId）判「**能不能**缓存」，**完全不碰 `cache_task` 状态**。
- `SeriesDetail` 据此渲染「可缓存」动作，但**不显示任务进度 / 失败 / 取消** —— 用户点到缓存之后，这条就「消失在全局队列的某个角落」。

### 4. 关键约束：条目 ↔ 任务的 key 不只是 `m:` 一种

- 入队时 `item_key` 单条 = `m:{chat_id}:{message_id}`、整组（相册）= `g:{chat_id}:{group_id}`（`routes.rs:1214-1216`）。
- 一个任务覆盖多条消息：`CacheTask.message_ids: Vec<i64>`，**组任务把整本相册打包成一条 `g:` 任务**（`routes.rs:1216` 的 `g:` 分支 + `message_ids`）。
- ⇒ **按条目联动必须同时覆盖两种 key**：某集的视频若是相册里的一条消息，它的任务 `item_key` 是 `g:chat:group`，而条目侧能拿到的定位符是 `m:chat:msg`。只查 `item_key='m:chat:msg'` 会**漏掉组任务** ⇒ 设计时必须「精确 `m:` 匹配 + 组任务 `message_ids` 包含该 msg 的匹配」两者取最新。

## 方案（待拍板前的建议实现，纯文档）

> 以下为建议落点，**三条红线**先声明，改动前需用户拍板：
> ① **只新增查询与端点，不改既有状态机**（BUG-257 取消/恢复、BUG-277 优先级、`active_cache_task` 现有调用方一律不动）；
> ② **字节态（hasBytes）是「到没到」的事实真源，任务态是「在不在转 / 为什么没到」的意图态**，两者必须**分别呈现再合并显示**，不能互相覆盖（避免 BUG-176「没有内容 vs 取不到内容」同款歧义）；
> ③ 新增端点必须**只读**、必须进真实队列索引，不得为这条联动新建一张表。

### 1. 引擎（`download-engine/crates/orig-tg/src/store.rs`）

新增 `cache_task_for_item(chat_id: i64, message_id: i64) -> Option<CacheTask>`：
- 先按精确 key 查：`item_key = 'm:{chat}:{msg}'` 任意状态取 `id DESC` 第一条；
- 再按组任务查：`item_key LIKE 'g:{chat}:%'` 且 `message_ids` **JSON 包含** `msg`，取 `id DESC` 第一条；
- 两路取 `id` 最大者返回（语义：最新一次尝试，覆盖「先失败→又重试→又 running」）。
- 与 `active_cache_task` 共存，不删不改后者。

### 2. 接口（`routes.rs` + `api/tg.ts`）

- 新增 `GET /api/tg/cache/tasks/by-item?chatId=&messageId=` → `{ task: {id,status,error,done,total} | null }`；`null` = **根本没有状态**（从未入队或记录已删，正是用户要区分的语义）。
- `api/tg.ts` 加 `getCacheTaskForItem(chatId, messageId)`。

### 3. 壳层（`lib/mediaSources.ts` + `SeriesDetail`）

- `mediaSources.ts` 加 `episodeCacheStatus(ep)`：由 episode 的 `source/ref`（`ref` 形如 `chat:msg`，解析见 `routes.rs:4921 parse_tg_ref_coords` / `routes.rs:7709`）→ `chatId+messageId` → 调 `getCacheTaskForItem`；与 `hasBytes` 合并成判别态：
  `no-task | queued | running(progress) | failed(reason) | cancelled | done(no-bytes 异常)`。
- `SeriesDetail` 未缓存区按判别态渲染：
  - `no-task` → 「未缓存 · 可缓存」（保留现有 recache 动作）；
  - `queued`/`running` → 「缓存中 N%」+ 进度；
  - `failed` → 「缓存失败：<error> · 重试」（重试走现有 `retryCacheTask`）；
  - `cancelled` → 「缓存已取消 · 重新缓存」。
  - `done` 但 `hasBytes=false` → 单独标「已入队完成但字节缺失（异常）」，不掩盖。

## 判据（可证伪，预先声明）

1. **引擎单测**：对一条 `failed` 任务的 `m:` key，`cache_task_for_item` 返回该任务且 `error` 非空；对不存在的 key 返回 `None`；对同一 key「先 done 再 failed」两条任务返回最新（failed）。
2. **反向证验**：把实现换回 `active_cache_task` 同款 `status IN active` 查询 ⇒ 对 `failed` 任务必返回 `None`（FAIL）。
3. **端点**：对一条 `failed` 任务 `GET by-item` 回 `status=failed` + `error` 非空；对不存在回 `200 + null`。
4. **UI（CDP 真实截图，禁读 className、用 `data-testid`）**：未缓存且 `failed` 的条目在 `SeriesDetail` 显示失败原因 + 重试；未缓存且 `no-task` 显示可缓存；未缓存且 `running` 显示进度。三种状态各一张截图。
5. **不回退**：`active_cache_task` 现有调用方、`BUG-257`/`BUG-277` 既有的取消/恢复/优先级逻辑、全局 `GET /api/tg/cache/tasks` 视图**一条都不改**；新增查询/端点带来的回归 = 本 BUG 自身。
