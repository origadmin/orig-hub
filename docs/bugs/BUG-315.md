# BUG-315: 条目明细层无控制、无状态、无信息——组清单展开后每行只有「S1E29 / 已登记未编入 / 有字节」

- 状态: fixed（透传 + 渲染 + 单测 + 活栈验收；详见验收证据）
- 发现日期: 2026-10-15
- 模块: engine+shell
- 严重程度: high

## 现象

用户 2026-10-15 原话：「2. 条目明细的逻辑问题没有任何修复,无控制,无状态,无信息.」

下载页 TG 入库组行展开「条目明细」（`IngestGroupRow.tsx:290-317`，数据源
`GET /api/tg/cache/tasks/:id/items`），每一行只有三样：

```
S1E29        已登记未编入        有字节
```

逐项对照用户三个「无」：

1. **无信息**：无标题/文件名（`media_message.caption` / `file_name` 在库中从未透传）、
   无大小（`media_message.size` 在库中，前端只拿到布尔 `has_bytes` ⇒ 「有字节」之外
   不知道多少字节）、无时间（`msg_date` 未透传）、无失败原因（任务级 `latest.error`
   有，条目级无）。
2. **无状态**：明细行唯一的「状态」是**编入态**（slotted / registered_unslotted /
   missing，BUG-296 的审计语义），**没有传输态** —— 哪条正在传、哪条在排队、哪条
   失败过几次、单条已烧多久，一律看不到（`cache_task_item_wall.started_at` /
   `accum_ms` 已在库、未透传）。
3. **无控制**：明细行零按钮。组行级动作（取消/重试/优先下载/去媒体库查看/删除）在
   BUG-300 复报③ 补齐过，但**条目级没有任何干预手段** —— 一批 10 条里 1 条失败，
   用户只能整组重跑（TG 无真续传，整任务重跑 = 已完成的 9 条再传一遍）。

## 根因

- BUG-296 的组清单（manifest）设计目标是**缺口审计**（序号全集 + 三态 + 布尔字节），
  `ManifestEntry`（`media.rs:1584`）只回 6 个审计字段：`message_id` / `state` /
  `has_bytes` / `episode_id` / `season` / `episode_no`。前端 `IngestGroupRow`
  就照这 6 个字段渲染，没有任何一层按「明细面板」补齐过。
- 明细层从未被当作**任务监控界面**设计：BUG-300 复报③ 的补齐全部落在组行层
  （按钮常驻、优先徽标、去媒体库查看），明细层原样未动 —— 所以用户看到的是
  「组行修了、点开还是老样子」。
- 数据层不缺：标题/大小/时间/时长/类型在 `media_message`（`store.rs:431-446`），
  逐条在途与累计时长在 `cache_task_item_wall`（`store.rs:488-499`）—— 是**透传与
  渲染缺失**，不是采集缺失。

## 复现

1. dev :5180 → 下载 → 任一带多条的 TG 入库组行 → 展开；
2. 看「条目明细」每行：仅 `S<n>E<n>`/`#<msgid>` + 后端状态词 + 「有/无字节」；
3. 对照 `media_message` 同行（只读库）：`caption`/`size`/`msg_date` 有值而未显示。

## 修复

1. **透传**（engine）：`manifest_entries`（`media.rs:3200`）为每条补
   `media_message` 的 `caption`/`file_name`/`size`/`msg_date`/`media_type`/`duration`
   与 `cache_task_item_wall` 的 `started_at`/`accum_ms`（⇒ 逐条传输态：在途/排队/
   累计时长）；不新建表、不改状态机、不改 BUG-296 的三态语义（审计口径保持）。
2. **渲染**（shell）：明细行补四列信息 —— 标题（caption→file_name→`#msgid` 兜底）、
   大小（`formatBytes`，无字节显示「—」）、时间（`msg_date`）、传输态徽标
   （在途/待传/失败原因）。
3. **控制**（shell，最小集）：条目级先上「单条重试」（后端需配套单条入队能力，
   没有则该按钮不上线——**命名不得超出行为**）与 slotted 条目的「去媒体库查看」；
   其它控制待本条验收后评估，不一次铺开。
4. 判据（可证伪）：一条有 caption+size 的消息，明细行必须显示标题与具体字节数
   （反向：只回布尔 ⇒ 断言 FAIL）；一条在途消息必须显示「在途」（反向：不透传
   `started_at` ⇒ FAIL）。
5. 懒加载纪律保持（`IngestGroupRow.tsx:98-116`）：明细不跟随 3s 轮询刷新，
   展开时拉一次；新字段不得把一次展开变成 N 次请求。

## 关联

- BUG-296（组清单设计点，本条是其「审计口径」到「明细面板」的补齐）、
  BUG-294（逐条台账，同一数据族，实施时合并取舍）、BUG-300（复报③ 只修到组行层，
  明细层未动是本条的发现现场）

## 验收证据

### 1. 后端单测（跨机器可核，入库 `media.rs`）
- 测试：`manifest_entries_transmits_info_and_transfer_state_bug315`（`media.rs:11879`）。
- 结果：`1 passed; 0 failed`（2026-10-15，D:/tmp/orig-tg-test 靶机外构建跑通）。
- 断言覆盖：任务级清单（`task_id=Some`）透传 `caption/file_name/size/msg_date/media_type/
  duration/started_at/accum_ms` 全部新字段；反向证伪——`series` 级清单（`task_id=None`）
  不透传 `started_at`（恒 `None`）。

### 2. 活栈后端实测（部署引擎，:19787）
- `GET /api/tg/cache/tasks/163/items`（已授权 TG 会话、真实任务）返回的条目已含
  `fileName/size/mediaType/msgDate/duration/caption`，例如：
  - `messageId:3450` → `duration:840, fileName:"proxy.mp4", mediaType:"video", msgDate:1791614681, size:659104995`
  - `messageId:3458` → `caption:"🌟🔥…《妈妈陪儿子高考》EP10…"`（长标题透传成功）。
- 「无信息」全字段端到端打通；「无状态」（`started_at/accum_ms`）的单测证伪路径已闭环，
  已终态任务正确不附带在途态。

### 3. 前端渲染（shell，tsc 通过）
- `ManifestEntry` 类型补 8 字段（`types.ts:392`）；i18n 补 `tg.manifestInFlight`/`tg.manifestAccum`（zh/en）。
- **主修复点 = `IngestGroupRow.tsx`（下载页 TG 入库组行展开「条目明细」，即用户原话的现场）**：
  每条渲染 标题（caption→fileName→`#msgid` 兜底，`min-w-0 flex-1 truncate`）、大小
  （`formatBytes`，无则 `—`）、时间（MM/DD）、传输态徽标（在途=`default` Badge / 已传 Ns=`secondary` Badge）。
- 次修复点 = `CacheManagerDialog.tsx`（缓存管理弹窗的同一份组清单），同步渲染同款字段。
- 教训（已记入本档）：首轮把渲染改到 `CacheManagerDialog` 而非用户可见的 `IngestGroupRow`，
  活栈 UI 验收脚本**先 FAIL**（展开后仍只有 `S1E1 已入库 有字节` 旧格式），据此定位到
  「改端点 ≠ 用户能用，必 grep 前端调用方」—— 两处清单消费点都要改。
- `npx tsc --noEmit` 通过（2026-10-15）。

## 复报注记（2026-10-15 23:2x，第三次）

用户原话：「展开/收缩根本看不到,样式有问题. 展开内容下载,停止,控制是否对策?」
——「展开内容下载、停止、控制」= 本条**「无控制」子项**的第三次复报（复报不新开号）；
「展开/收缩根本看不到」（入口不可见）此前未登记，已**当场补登 BUG-320**。

本轮已落地的部分（「无控制」的下载半边）：

- 条目级「下载」：明细行缺字节的条目给下载按钮 ⇒ `POST /api/tg/cache/tasks
  {chatId, messageIds:[id]}`（前端不做去重，幂等由后端 BUG-308 保证：已入库拦下、
  活跃任务复用、缺字节复位重跑）；整批在传时按钮禁用并直出原因。
- 条目级「停止」**刻意不提供**：传输的最小单位是任务不是消息（TG 无真续传、队列不可抢占），
  假按钮会「点了却取消整批」—— 改为在展开区直说「条目级停止不存在，要停请用本行的『取消』」。

仍 open 的部分：**无信息**（caption/size/msg_date 透传）与**无状态**（逐条传输态
`cache_task_item_wall.started_at/accum_ms` 透传）—— 数据在库、manifest 只回 6 个审计字段，
按本节「修复」第 1、2 条继续做。

验收证据（本轮部分）：`tauri-shell/verify/verify_bug320_expand_toggle.cjs` B1–B4 四条
（缺字节 6 条条条有下载按钮、有字节 0 个按钮、展开区直说停止缺席）；
主验收脚本新增「条目级下载接线」源码锚点。完整证据见 BUG-320.md。

## 复报注记（2026-10-16，第四次：排版 + 图片标签）

用户原话：「明细右边的按钮和状态的排版为什么是乱的? 还有 S1E1这些,如果是视频还好,混入的图片呢? 逻辑有问题.」

- **排版乱**：条目 `<li>` 用 `flex flex-wrap` 却只在「下载」按钮挂 `ml-auto`，其余元信息不成簇
  ⇒ 换行时按钮被单推右侧、状态散落。修=右侧元信息 + 操作聚成**一个右对齐簇**
  （`ml-auto flex shrink-0 items-center gap-2`，内部不拆行）—— `IngestGroupRow.tsx`。
- **图片标签逻辑错**：引擎 `manifest_entries`（`media.rs:3313`）只 `JOIN media_episode`
  （`trg_media_episode_video_only_*` 触发器保证分集只能是 video）⇒ **图片永远拿不到
  season/episode**，前端兜底成 `#messageId`（对用户无意义的 TG 内部号，与视频 `S1E1` 混排）。
  修=首列按 `mediaType` 给可读标签（视频分集=`S{n}E{m}`；图片=`图片`；视频非分集=`视频`；兜底
  `#id`）—— `IngestGroupRow.tsx` + `CacheManagerDialog.tsx`（两处清单消费点同步）。
- 验收：`tauri-shell/verify/bug315_photo_label.cjs` 展开含图片的真实任务 163 ⇒
  **9 条图片行首列全为「图片」、`#messageId` 裸号行数 = 0 → PASS**；
  `bug315_live_ui.cjs` 下载页组行 ⇒ 右侧 `113.8 MB 10/11 已入库 有字节 已传 118s / 在途`
  已成右对齐簇 → PASS。`npx tsc --noEmit` 0 错。
- **仍 open（未擅自改）**：图片是否应继承**所属集**的 `S1E1`（引擎未把 `media_episode_image`
  接入 manifest）—— 属引擎语义扩展，待拍板。
