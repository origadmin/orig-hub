# BUG-345: 相册 group_id 过 JSON 边界被 JS 精度损失污染（item_key/去重键与真值差 1）

- 状态: fixed
- 发现日期: 2026-10-20
- 模块: engine+shell
- 严重程度: high

## 现象

BUG-341 验收探针（`tauri-shell/verify/_probe_bug341_filter_groups.cjs`）验牙运行时
抓到：前端入库请求里的 `groupId` 是 14315949991671396，而活库真值是
14315949991671397——**差 1**。

活库实证（`%APPDATA%/com.origadmin.orighub/tg/store.db`，2026-10-20）：

- `cache_task` 共 70 个组键（`item_key LIKE 'g:%'`）任务，其中 **62 个**的
  `item_key`/`group_id` 比该组首条消息在 `media_message` 里的真 group_id 差 1
  （如 task 193：键尾号 94316，真值 94317；task 192：39588 vs 39589）。

## 根因

TG 的 `group_id` 量级 ~1.4e16，**超过 JS `Number.MAX_SAFE_INTEGER`**（2^53-1
≈ 9.007e15）。以 JSON **number** 过边界时，前端 `JSON.parse` 把它舍入到相邻的
可表示双精度浮点 ⇒ 同一相册在系统里分裂成两个身份（键差 1）。

污染面（都是前端 number 收/发的路径）：

1. `TgPanel.downloadAlbum`（v0.4.2 相册整组缓存，存量路径）—— `groupId` 原样
   回传 ⇒ 活库 62/70 个组键任务被污染；
2. `TgFilterPanel` 整组入库（BUG-341 新路径）—— 探针验牙时同款污染。

不是显示问题：`item_key` 是去重键与相册身份，`cache_task_active_uniq`、前端
「相册气泡 ↔ 任务」比对、`active_cache_task_covering` 之外的键口径全建立在它
恒等于真 group_id 上。

## 修复（让错误状态不可表达）

1. **串界**：`group_id` 过 JSON 一律走**字符串**（GitHub node_id 同款先例）——
   四个序列化点（`TgMedia` / `MonitorFilterHit` / `StoredMessage` / `CacheTask`）
   共用 `store::serialize_group_id_opt`；`cache_tasks_payload` 的手写 `json!`
   同步改字符串；`EnqueueCacheReq.group_id` 用
   `store::deserialize_group_id_opt` **宽容反序列化**（string/number 都收），
   陈旧标签页不被击；
2. **存量修复**：`repair_group_key_precision` 启动迁移——按任务首条消息在
   `media_message` 里的真 `group_id` 重写 `item_key` 与 `group_id` 两列；
   真值取不到的行不动（消息可能已清理，不按猜测写身份）；单行失败跳过不阻断
   启动；幂等（修过再跑 no-op）；
3. **前端类型**：`groupId` 全处 `number → string`（types.ts ×5、api/tg.ts、
   TgPanel FeedItem、TgFilterPanel HitUnit），键构造与判空语义不变。

## 验收证据

- 引擎测试（`download-engine/crates/orig-tg/src/store.rs`）：
  `group_id_crosses_json_as_string`（序列化必须是字符串）、
  `repairs_group_keys_corrupted_by_js_precision`（污染键按真值重写 + 孤儿行
  不动 + 幂等）；反序列化两形态测试
  `enqueue_group_id_accepts_string_and_number`（`download-engine/crates/orig-tg/src/routes.rs`）；
- 探针 `tauri-shell/verify/_probe_bug341_filter_groups.cjs` 判据 U5a：入库 wire 的
  `groupId` 必须等于活库真值 14315949991671397（验牙：重部署前的旧二进制必败——
  旧二进制连组内成员都只回 1 条）；
- 活库对账（重部署后 orig-tg 启动日志 `[store] BUG-345: repaired N cache_task key(s)`）：
  `cache_task` 组键与 `media_message` 真值 100% 一致。
- 2026-10-20 重部署后实测（`%APPDATA%/com.origadmin.orighub/tg/store.db` 只读对账）：
  70 个 `g:` 组键 `cache_task` 与 `media_message` 真值 **0 不一致**（修复前同一
  口径 62/70 被舍坏 1；task 193 键 `…94316` ⇒ 真值 `…94317`，`group_id` 列同步
  修复）；wire 实测 `GET :19787/api/tg/monitor/filters/{id}/messages` 的
  `groupId` 为字符串真值 `"14315949991671397"`（旧二进制为 number，JS 侧舍成
  `…396`——探针 U5a 在旧二进制上的失败明细 `g:14315949991671396` 即活证词）。

## 关联

- BUG-341：整组入库的 payload 形状（groupId 原样回传）——本 BUG 是它的上游
  精度缺陷；
- BUG-329/330：相册分组键（`g:{chat}:{group}`）的引入处。
