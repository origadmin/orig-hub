# BUG-274: 每次新的缓存写入时卡顿一下 —— 缓存记账与播放读**共用一条 SQLite 连接**，且库处于 rollback journal 模式（每次提交都独占 + fsync）

- 状态: open
- 发现日期: 2026-10-10
- 模块: engine
- 严重程度: high

> 来源：用户报告「**现在发现新的状况，缓存效果好像可以了但是每次新的缓存写入时好像会卡顿一下。**」
>
> **本档为任务文档**（用户 2026-10-10 定：后续一律纯文档任务，代码由别的组负责）。
>
> **与 BUG-273 的关系（不是重复登记）**：BUG-273 治的是**播放侧**的段级停顿
> （`/stream` 冷缓存转码泵背压 + 增长 `.part` 的 Range 直读），触发条件是**播放行为本身**；
> 本条治的是**后台缓存写入**触发的卡顿，触发条件是**缓存 worker 的写入**——
> **即使播放的是已完全落盘的本地文件也会卡**，两者触发面不相交。
> 故**另立编号**并在两档互相关联；若后续证实二者同源，应合并回 BUG-273 并撤下本号。

## 现象

- 缓存功能本身已可用（用户：「缓存效果好像可以了」）。
- 但**每次有新的缓存写入发生时**（新条目开始取字节／进度推进／条目完成归仓），
  正在进行的播放或界面**卡一下**，随后恢复。
- 关键特征：**触发源是缓存写入，不是播放动作**——与 BUG-273 的「段交界卡」是**不同的触发面**。

## 已排除的路径（先否定，避免重复排查）

| 候选 | 实测 | 判定 |
|---|---|---|
| **前端轮询**（播放时后台有轮询风暴） | 三处定时器全部**有活才轮**且周期 5s：`TgPanel.tsx:790-800`（`tgBroken`／`!hasActiveTask`／`cacheManagerOpen` 任一即 return，5s）、`MainLayout.tsx:74`（仅 SSE `connected=false` 才拉）、`CacheManagerDialog.tsx:706`（仅面板打开且 `hasActive`）；`useStore.ts:665-690` 的 `probeTg` 有界（≤5 次、就绪即停） | **不成立**（前端只能解释「每 5s 一次」的节拍，**无法解释「每次写入都卡」**） |
| **归仓是跨卷拷贝** | `cache.rs:196-212` `house_into` = `create_dir_all` + 两次 `rename`；跨卷 rename 会**整体失败**→ 调用方降级（留原位、回填绝对路径、warn），**绝不静默拷贝**（`cache.rs:120-186`）。实测库根 `…\com.origadmin.orighub\tg\library`、缓存目录 `…\tg\downloads`、`proxies` **全在 C:** | **不成立**（同卷 rename = O(1)，不存在「完成时整文件拷贝」） |
| **运行时单线程被阻塞** | `main.rs:149` `#[tokio::main]`（无参数）= **多线程**运行时（worker = CPU 数） | **不成立**（单次阻塞不会卡死全部） |
| **缓存写入有节流导致排队** | `cache.rs`／`grammers.rs` 内**无任何** `throttle`／`rate_limit`／`sleep` 命中；`ORIG_TG_DELIVERY_BPS` 只作用于**投递**（BUG-199），与缓存写入无关 | **不成立**（写入是**全速无节流**的） |
| **每 chunk 写库** | 下载进度是**内存态**（`grammers.rs:635-668` `p.add_bytes`／`p.set_total`，`login::DownloadProgress` 原子读），DB 记账是**条目级**（`routes.rs:2124` 循环内每条目一次） | **不成立**（DB 写入频次 = 每条目十几次，非每 chunk） |

## 根因（排名 + 证据；**量级尚未实测，见「复现」**）

**共同结构**：`AppState` 持有**单条** `Store`（`state.rs:99` `pub store: Store`），
`Store` 只有**一条** libsql 连接（`store.rs:100-108` `pub(crate) conn: Connection`，
由 `store.rs:299` `Builder::new_local(path).build().await?.connect()` 建）
⇒ **进程内所有 SQL 都排在同一条连接上**。

作者**已知**这一点并在注释里写明（`state.rs:114-118`）：
> 「`GET /api/tg/cache/tasks` 是前端 1s 轮询的高频读，每次都打 SQLite（ORDER BY 排序）
> 既浪费又与下载 worker 的写争用**同一连接**。」

**当年的缓解只覆盖了前端轮询那条读路径**（改成内存快照 `cache_tasks`），
**播放路径仍在每请求打 DB**——这就是本条的缺口。

### 排名 1：播放路径**每请求**一次 SQL，与缓存记账争用同一连接

| 事实 | 位置 |
|---|---|
| `library_root()` 解析链第 2 级读 `app_setting` | `store.rs:723-738`（`:724-727` 环境变量短路；否则 `get_setting("library_dir")` → `store.rs:691-699` 一次 `SELECT`） |
| 播放**三个**端点**每请求**各调一次 `library_root()` | `routes.rs:771`（`/tg/local`）、`:3527`（`/raw`）、`:3778`（`/stream`） |
| 实测生产库 `app_setting.library_dir` = **NULL** ⇒ 每次都走到 `get_setting`（**环境变量未设，短路不生效**） | 只读查询 `app_setting` |

⇒ 播放期间的**每一个** HTTP 请求（含 Range 重取）都要在这条连接上排一次读；
缓存 worker 的写突发**插在中间**时，该读等待。

### 排名 2：库处于 **rollback journal 模式**（非 WAL）——每次提交独占 + fsync + 日志文件增删

| 事实 | 证据 |
|---|---|
| `store.db` 头部 `write_version = 1`、`read_version = 1` | 直接读文件头偏移 18/19 字节（`SQLite format 3\0` 之后） |
| 目录下**没有** `store.db-wal`／`store.db-shm` | `ls store.db*` 只有 `store.db` |

rollback journal 模式下**每次写事务**要：建 `-journal` 文件 → 写页 → **fsync** → 写头 → **fsync** → **删 journal**。
libsql 本地模式默认 `synchronous=FULL` ⇒ **每次提交都落盘**。
库文件位于 `%APPDATA%`（`…\com.origadmin.orighub\tg\store.db`）——该目录是**安全软件实时扫描**的典型目标，
**每次 journal 文件创建/删除都可能触发扫描** ⇒ 单次提交的真实代价远高于纯内存估算。
**WAL 模式不会有这个每提交的文件增删与独占语义**，这正是它通常被用于「读写并发」的原因。

### 排名 3：缓存记账的**写频次**放大了排名 1/2

缓存 worker `run_one_cache_task`（`routes.rs:2093` 起）**每条目**的 DB 动作：

| 时机 | 动作 |
|---|---|
| 任务开始 | `get_cache_task` + `mark_cache_task_running` + `refresh_cache_tasks`（`routes.rs:2094-2096`） |
| 每条目开头 | `update_cache_task_progress` + `refresh_cache_tasks`（`routes.rs:2135-2138`） |
| 已缓存分支 | `register_item`／`register_slot`／`backfill_item_bytes` + `update_cache_task_progress` + `refresh_cache_tasks`（`routes.rs:2151-2172`） |
| 取字节后 | `house_downloaded_bytes`（含 `library_root()` + `list_channels()`）+ `backfill_item_bytes`（`routes.rs:2195-2240`） |
| 完成/失败 | 再次 `update_cache_task_progress` + `refresh_cache_tasks`（`routes.rs:2260`／`:2293`／`:2353`） |

其中 `refresh_cache_tasks()`（`state.rs:302-305`）= `list_cache_tasks(50)`（**全表 SELECT**）
+ `*cache_tasks.write().await = …`（tokio **写锁**）。
而 `list_cache_tasks` 的 `ORDER BY CASE WHEN status IN (…) THEN 0 ELSE 1 END, id DESC LIMIT ?1`
（`store.rs:936-952`）**无索引支撑**——实测 `cache_task` 表 **107 行**、**唯一索引**
`cache_task_active_uniq`（部分唯一索引，**不含 status**）⇒ 每次都要**临时排序**。

⇒ 每条目在**同一条连接**上产生 **十几次写 + 4~6 次全表 SELECT**；
播放的读请求落在这个窗口内就要等。

### 量级诚实说明（**未实测，不许当结论用**）

排名 1/2/3 的**机制**有直接代码/文件头证据；但**「十几次串行 SQL 是否足以产生肉眼可见的卡顿」尚未实测**。
`cache_task` 仅 107 行，纯内存估算在**亚毫秒**量级，与「肉眼可见」有差距；
真正可能把量级抬上来的是 **rollback journal 的每提交 fsync + `%APPDATA%` 安全软件扫描**（排名 2）。
**故本条以「机制成立 + 量级待测」登记，不得在实测前宣称已定因。**

### 附：另一条**未排除**的通道（需在复现时一并观察）

缓存下载与**远程播放**共用同一个 MTProto 客户端（`state.rs:93` `pub client: Arc<dyn Client>`）。
若播放的是**未落盘的远程**条目，其拉流与缓存下载会争用**同一条 MTProto 连接**（同型问题见 BUG-028）。
⇒ 复现时必须先确认播放源是 **Local（已落盘）** 还是 **Remote**，否则会把 MTProto 争用误判成本条。

## 复现

### 判别实验（零代码、可逆；**需用户决定是否执行**）

| 实验 | 做法 | 若卡顿消失 ⇒ 坐实 |
|---|---|---|
| **E1 短路库根解析** | 给 orig-tg 进程设 `ORIG_TG_LIBRARY_DIR`（指向当前库根 `…\com.origadmin.orighub\tg\library`）后重启。`library_root()` 命中环境变量即**直接返回、不碰 DB**（`store.rs:724-727`） | **排名 1**（播放读与缓存写争用同一连接）。E1 是**唯一**能单独切掉「播放路径每请求一次 SQL」的开关 |
| **E2 暂停缓存 worker** | 播放中**暂停/停止**缓存任务，观察卡顿是否消失 | 卡顿确实来自缓存侧（与前端无关） |
| **E3 换 WAL** | 把 `store.db` 切到 WAL（`PRAGMA journal_mode=WAL`）后重启，重复 E2 的播放 | **排名 2**（rollback journal 的每提交 fsync/独占）。WAL 下读不再被写阻塞 |
| **E4 区分 Local/Remote** | 记录卡顿发生时的播放源（Local 还是 Remote） | 区分本条与 MTProto 争用（附通道） |

**建议顺序**：E4（纯观察，零成本）→ E1（单个环境变量，可逆）→ E2 → E3。
E1 若无效，再验 E2/E3；E1 若生效，即可直接定因排名 1。

### 需要一并采集的量

- 卡顿时刻与**缓存条目边界**（任务开始／进度跳变／归仓完成）的时间相关性——**必须对齐时间戳**，
  不能凭「感觉同时」。
- 卡顿期间播放端点的**请求延迟**（`/tg/local`／`/raw`／`/stream` 的 `%{time_total}`）。
- 卡顿期间 `store.db-journal` 文件**是否存在/被增删**（rollback journal 模式的直接指纹）。

## 修复（方向；**本档不改代码**）

1. **`library_root()` 结果进程内缓存**（设置变更时失效）⇒ 播放路径**零 SQL**。
   这是最小、最低风险的改动，且与「库根是低频变更的设置」语义相符。
2. **切 WAL**（`journal_mode=WAL` + `busy_timeout`）⇒ 读写不再互相独占，消除每提交的 journal 增删。
3. **合并 `refresh_cache_tasks` 的调用**（每条目 4~6 次 → 收敛为条目边界 1~2 次），
   或改为**去抖**（写后延迟合并刷新），并给 `list_cache_tasks` 的排序**补索引**。
4. **播放路径与缓存写入分连接**（只读连接 / 连接池）——根治「单连接串行」，
   但回归面最大，须在 1~3 之后按需再做。

**不可推翻的既有裁定**：缓存 worker **全局单飞**（`routes.rs:1425-1430`「**设计裁定（用户）**」）
与条目级失败不终止任务（BUG-257）——本条**不触碰**。
