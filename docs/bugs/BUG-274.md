# BUG-274: 每次新的缓存写入时卡顿一下 —— 缓存记账与播放读**共用一条 SQLite 连接**，且库处于 rollback journal 模式（每次提交都独占 + fsync）

- 状态: open
- 发现日期: 2026-10-10
- 模块: engine
- 严重程度: high

> 来源：用户报告「**现在发现新的状况，缓存效果好像可以了但是每次新的缓存写入时好像会卡顿一下。**」
>
> **本档为任务文档**（用户 2026-10-10 定：后续一律纯文档任务，代码由别的组负责）。
>
> **与 BUG-273 的关系（不是重复登记）**：BUG-273 治的是**播放侧**的段级停顿
> （`/stream` 冷缓存转码泵背压 + 增长 `.part` 的 Range 直读），触发条件是**播放行为本身**；
> 本条治的是**后台缓存写入**触发的卡顿，触发条件是**缓存 worker 的写入**——
> **即使播放的是已完全落盘的本地文件也会卡**，两者触发面不相交。
> 故**另立编号**并在两档互相关联；若后续证实二者同源，应合并回 BUG-273 并撤下本号。

## 现象

- 缓存功能本身已可用（用户：「缓存效果好像可以了」）。
- 但**每次有新的缓存写入发生时**（新条目开始取字节／进度推进／条目完成归仓），
  正在进行的播放或界面**卡一下**，随后恢复。
- 关键特征：**触发源是缓存写入，不是播放动作**——与 BUG-273 的「段交界卡」是**不同的触发面**。

## 根因（**已实测坐实**，2026-10-10 E4 实验）

### 结论：**远程播放被缓存下载饿死** —— 单条 MTProto 连接上的队头阻塞

同一次会话、**同一个缓存运行窗口内**的对照（脚本 `tauri-shell/verify/bug274_e4_mtproto.cjs`
→ 产物 `tauri-shell/verify_shots/bug274_e4/result.json`）：

| 侧 | 端点 | 实测 |
|---|---|---|
| **Local**（媒体库／已落盘） | `/api/media/items/607/raw`（Range 0-8MiB） | **215 / 150 / 145 MB/s**，8 MiB 全量、**完全不受影响** |
| **Remote**（TG 面板／未缓存） | `/api/tg/file/-1001341930464/208253` | **0 B**（3/3 次；status=206 但 body 0 字节）；手测 60s = 1,572,864 B / 60.01s ≈ **26 KB/s** 且未下完 |
| 非媒体、**同一条 client** | `/api/tg/thumb`、`/api/tg/dialogs` | **双双挂起**（5s 上限、`http=000`） |

**排除「链路断」**：同期 `/api/tg/diag` = `link_alive:true, mode:"ready", session_phase:"Authorized"`（代理 `socks5://127.0.0.1:7897`）
⇒ 0 字节是**争用**，不是断链。

**机制**：缓存 worker 的下载与远程播放共用**同一条** MTProto 连接（`state.rs:93`）
⇒ 大文件下载在单连接上产生**队头阻塞**，其余请求（远程播放／缩略图／dialogs）**全部排队等待**
（同型见 BUG-028：单连接串行拉流）。**不是带宽打满，而是连接被占住**——实测该下载自身只有 ~12–40 KB/s
（远低于 BUG-028 记录的单流正常值 0.33–0.5 MB/s），却足以让远程播放归零。

⇒ **与用户描述完全吻合**：「每次新的缓存写入时卡一下」= 每开始下载一个新条目，该连接即被该条目占住；
**条目越大、占得越久**。

### 同时观测到的放大器：一个 21 小时未完成的队首条目

登记当时实测（`GET /api/tg/cache/tasks`）：

- 运行中任务 **id=134**（chat `-1004457697592`，9 条消息，`done=0`），**卡在第 1 条** `currentId=1181`；
- 该条目 **194,116,505 字节只到 23,592,960 字节（12.2%）**；`createdAt` 距今 **21.0 小时**；
- 其后 **20 个排队任务**（`queued`）⇒ **队列长时间不会空闲**。

⇒ 单飞队列（`routes.rs:1425-1430` 用户裁定）**+** 单连接队头阻塞 = **只要队首是大条目且慢，
远程播放就长期不可用**（不是「卡一下」，是「一直卡」）。**这是本条最严重的实际后果。**

### 原排名 1/2/3（SQLite 单连接 / rollback journal / 记账写频次）—— **降级为「未证实」**

E4 的对照直接削弱了它们：**媒体库（Local）播放实测 215 MB/s，完全不受缓存写入影响**。
若「单连接 SQLite 串行 + rollback journal 每提交 fsync」真的能造成肉眼可见的卡顿，
它应当同样打击 Local 投递（`/raw` 也要 `library_root()` 打一次 DB）—— **实测没有**。
⇒ 排名 1/2/3 **保留在档内备查，但不再作为本条的解释**；除非后续出现「Local 也卡」的证据，否则不投入排查。

### 原「根因（排名 + 证据）」小节（**已被上面取代，保留备查**）

**共同结构**：`AppState` 持有**单条** `Store`（`state.rs:99` `pub store: Store`），
`Store` 只有**一条** libsql 连接（`store.rs:100-108` `pub(crate) conn: Connection`，
由 `store.rs:299` `Builder::new_local(path).build().await?.connect()` 建）
⇒ **进程内所有 SQL 都排在同一条连接上**。

作者**已知**这一点并在注释里写明（`state.rs:114-118`）：
> 「`GET /api/tg/cache/tasks` 是前端 1s 轮询的高频读，每次都打 SQLite（ORDER BY 排序）
> 既浪费又与下载 worker 的写争用**同一连接**。」

**当年的缓解只覆盖了前端轮询那条读路径**（改成内存快照 `cache_tasks`），
**播放路径仍在每请求打 DB**——这就是本条的缺口。

### 排名 1：播放路径**每请求**一次 SQL，与缓存记账争用同一连接

| 事实 | 位置 |
|---|---|
| `library_root()` 解析链第 2 级读 `app_setting` | `store.rs:723-738`（`:724-727` 环境变量短路；否则 `get_setting("library_dir")` → `store.rs:691-699` 一次 `SELECT`） |
| 播放**三个**端点**每请求**各调一次 `library_root()` | `routes.rs:771`（`/tg/local`）、`:3527`（`/raw`）、`:3778`（`/stream`） |
| 实测生产库 `app_setting.library_dir` = **NULL** ⇒ 每次都走到 `get_setting`（**环境变量未设，短路不生效**） | 只读查询 `app_setting` |

⇒ 播放期间的**每一个** HTTP 请求（含 Range 重取）都要在这条连接上排一次读；
缓存 worker 的写突发**插在中间**时，该读等待。

### 排名 2：库处于 **rollback journal 模式**（非 WAL）——每次提交独占 + fsync + 日志文件增删

| 事实 | 证据 |
|---|---|
| `store.db` 头部 `write_version = 1`、`read_version = 1` | 直接读文件头偏移 18/19 字节（`SQLite format 3\0` 之后） |
| 目录下**没有** `store.db-wal`／`store.db-shm` | `ls store.db*` 只有 `store.db` |

rollback journal 模式下**每次写事务**要：建 `-journal` 文件 → 写页 → **fsync** → 写头 → **fsync** → **删 journal**。
libsql 本地模式默认 `synchronous=FULL` ⇒ **每次提交都落盘**。
库文件位于 `%APPDATA%`（`…\com.origadmin.orighub\tg\store.db`）——该目录是**安全软件实时扫描**的典型目标，
**每次 journal 文件创建/删除都可能触发扫描** ⇒ 单次提交的真实代价远高于纯内存估算。
**WAL 模式不会有这个每提交的文件增删与独占语义**，这正是它通常被用于「读写并发」的原因。

### 排名 3：缓存记账的**写频次**放大了排名 1/2

缓存 worker `run_one_cache_task`（`routes.rs:2093` 起）**每条目**的 DB 动作：

| 时机 | 动作 |
|---|---|
| 任务开始 | `get_cache_task` + `mark_cache_task_running` + `refresh_cache_tasks`（`routes.rs:2094-2096`） |
| 每条目开头 | `update_cache_task_progress` + `refresh_cache_tasks`（`routes.rs:2135-2138`） |
| 已缓存分支 | `register_item`／`register_slot`／`backfill_item_bytes` + `update_cache_task_progress` + `refresh_cache_tasks`（`routes.rs:2151-2172`） |
| 取字节后 | `house_downloaded_bytes`（含 `library_root()` + `list_channels()`）+ `backfill_item_bytes`（`routes.rs:2195-2240`） |
| 完成/失败 | 再次 `update_cache_task_progress` + `refresh_cache_tasks`（`routes.rs:2260`／`:2293`／`:2353`） |

其中 `refresh_cache_tasks()`（`state.rs:302-305`）= `list_cache_tasks(50)`（**全表 SELECT**）
+ `*cache_tasks.write().await = …`（tokio **写锁**）。
而 `list_cache_tasks` 的 `ORDER BY CASE WHEN status IN (…) THEN 0 ELSE 1 END, id DESC LIMIT ?1`
（`store.rs:936-952`）**无索引支撑**——实测 `cache_task` 表 **107 行**、**唯一索引**
`cache_task_active_uniq`（部分唯一索引，**不含 status**）⇒ 每次都要**临时排序**。

⇒ 每条目在**同一条连接**上产生 **十几次写 + 4~6 次全表 SELECT**；
播放的读请求落在这个窗口内就要等。

### 量级诚实说明（**未实测，不许当结论用**）

排名 1/2/3 的**机制**有直接代码/文件头证据；但**「十几次串行 SQL 是否足以产生肉眼可见的卡顿」尚未实测**。
`cache_task` 仅 107 行，纯内存估算在**亚毫秒**量级，与「肉眼可见」有差距；
真正可能把量级抬上来的是 **rollback journal 的每提交 fsync + `%APPDATA%` 安全软件扫描**（排名 2）。
**故本条以「机制成立 + 量级待测」登记，不得在实测前宣称已定因。**

### 排名 0（**已实测坐实，见上「根因」节**；2026-10-10 用户追问「哪里来的远程？」后核实并提升）

**Remote 播放真实存在，且只存在于 TG 面板。** 缓存下载与远程播放**共用同一个 MTProto 客户端**。

| 事实 | 位置 |
|---|---|
| TG 面板点播时按「该消息是否已缓存」二选一：**已缓存 → `/api/tg/local`（本地流）**；**未缓存 → `/api/tg/file`（现场从 TG 拉流）** | `TgPanel.tsx:1170-1171`：`src: local ? tgLocalFileUrl(...) : tgFileUrl(...)`，`fallbackSrc: local ? tgFileUrl(...) : undefined` |
| `/api/tg/file/{chat}/{msg}` = `media_file`：**不预下载**，直接 `st.client.media(chat_id, message_id, range)` 边拉边投 | `routes.rs:483-495`（注释原文：「供 `<img>`/`<video>` 直接引用实现点看/点放，**不预下载**」） |
| 媒体库（`SeriesDetail`／`VideoPlayer`）**只有 Local**：`/raw` 对**无字节的视频**直接 **404**（`routes.rs:3521`），仅**图片**回退 TG 缩略图代理 | `routes.rs:3490-3524` |
| 缓存 worker 的下载与远程播放**共用同一个** `Arc<dyn Client>` | `state.rs:93` `pub client: Arc<dyn Client>` |

⇒ **判别含义（这条直接决定后续所有排查方向）**：

- 若卡顿发生在**媒体库**里 ⇒ 播放源**必然是 Local** ⇒ **排名 0 不成立**，回到排名 1/2/3。
- 若卡顿发生在 **TG 面板**、且点的是**尚未缓存**的消息 ⇒ 播放源是 **Remote** ⇒
  缓存 worker **每开始下载一个新条目**，就与正在播放的在线流分走**同一条 MTProto 带宽与请求队列**
  ⇒ 与「**每次新的缓存写入时**卡一下」的字面触发条件**最吻合**（同型问题见 BUG-028：单连接串行拉流）。

⇒ **本档必须最先坐实/排除这一条**：它与用户描述的字面触发条件吻合度最高，
且**无需任何代码改动**即可用「媒体库 vs TG 面板」两处观察区分。

## 复现

### 判别实验（零代码、可逆；**需用户决定是否执行**）

| 实验 | 做法 | 若卡顿消失 ⇒ 坐实 |
|---|---|---|
| **E1 短路库根解析** | 给 orig-tg 进程设 `ORIG_TG_LIBRARY_DIR`（指向当前库根 `…\com.origadmin.orighub\tg\library`）后重启。`library_root()` 命中环境变量即**直接返回、不碰 DB**（`store.rs:724-727`） | **排名 1**（播放读与缓存写争用同一连接）。E1 是**唯一**能单独切掉「播放路径每请求一次 SQL」的开关 |
| **E2 暂停缓存 worker** | 播放中**暂停/停止**缓存任务，观察卡顿是否消失 | 卡顿确实来自缓存侧（与前端无关） |
| **E3 换 WAL** | 把 `store.db` 切到 WAL（`PRAGMA journal_mode=WAL`）后重启，重复 E2 的播放 | **排名 2**（rollback journal 的每提交 fsync/独占）。WAL 下读不再被写阻塞 |
| **E4 区分 Local/Remote**（**已执行 → 排名 0 成立**） | 同一缓存窗口内对比：①媒体库 `/raw`（Local）②`/api/tg/file`（Remote） | **实测：①215 MB/s 不受影响、②0 B/s** ⇒ **排名 0 成立**（见「根因」节） |

**执行结果（2026-10-10）**：**E4 已跑 → 排名 0 成立** ⇒ **E1/E2/E3 不必做**（它们只服务于排名 1/2/3）。
- E1/E2/E3 保留在档内备查，仅在出现「**Local 也卡**」的新证据时才启用。
- 严格基线（无缓存运行时的 Remote 吞吐）**未取**：登记当时环境里已有一个 **21 小时**的外来缓存任务在跑、
  其后还有 20 个排队（队列不空闲）。**未授权取消他人队列** ⇒ 以 BUG-028 的单流正常值（0.33–0.5 MB/s）作参照。
  因对照是**同一窗口内 Local vs Remote**，结论**不依赖**该基线。

### 需要一并采集的量

- 卡顿时刻与**缓存条目边界**（任务开始／进度跳变／归仓完成）的时间相关性——**必须对齐时间戳**，
  不能凭「感觉同时」。
- 卡顿期间播放端点的**请求延迟**（`/tg/local`／`/raw`／`/stream` 的 `%{time_total}`）。
- 卡顿期间 `store.db-journal` 文件**是否存在/被增删**（rollback journal 模式的直接指纹）。

## 修复（方向；**本档不改代码**）

> **2026-10-10 实测后重写**：原方向 1~4 服务的是**已被降级**的排名 1/2/3，保留在文末备查。
> 下面的方向对应**已坐实的**根因（单连接队头阻塞 + 慢队首放大器）。

1. **远程播放期间让缓存下载让路**（对应根因本体）。可选形态：
   - **有远程播放在进行时暂停/降速缓存下载**（需要一个「远程播放活跃」信号，可从 `/api/tg/file` 的
     在途计数取得）；
   - 或**给缓存下载设带宽/分片节流**，使其不占满单连接（但实测瓶颈是**队头阻塞而非带宽**，
     单靠限速未必有效，须先验证）。
2. **优先让用户看到的东西先落地**：用户正在看的那条消息，若未缓存 ⇒ **立刻转成缓存任务并前置到队首**，
   使「正在看的」尽快从 Remote 变 Local（Local 实测 215 MB/s 完全不受影响）。这与产品既有的
   「Local 优先、Remote 只作过渡兜底」一致。
3. **修掉「慢队首」放大器**（**这是本条最严重的实际后果**）：登记时实测队首条目已跑 **21 小时**、
   只完成 12.2%，其后 20 个任务排队 ⇒ 远程播放**长期不可用**。
   BUG-271（`fixed`）已加墙钟上限，但**未覆盖「任务重启后被重新入队、墙钟重置」**这一路径 ——
   需确认该路径下墙钟是否真的生效；若未生效，应另立缺陷。
4. **连接级并行**：MTProto 侧多连接/多 DC 分片，使缓存下载与远程播放**不共用同一条连接**。
   根治但回归面最大（牵动 BUG-028 的 4 路并行裁定），**最后做**。

**不可推翻的既有裁定**：缓存 worker **全局单飞**（`routes.rs:1425-1430`「**设计裁定（用户）**」）
与条目级失败不终止任务（BUG-257）——本条**不触碰**（但方向 1 的「让路」需在此裁定内实现，
例如**挂起**而非**并发**）。

### 备查：原方向 1~4（服务已降级的排名 1/2/3）

1. `library_root()` 结果进程内缓存（播放路径零 SQL）。
2. 切 WAL（`journal_mode=WAL` + `busy_timeout`）。
3. 合并/去抖 `refresh_cache_tasks`，并给 `list_cache_tasks` 的排序补索引。
4. 播放路径与缓存写入分连接。
