# BUG-175: 设置页「默认下载目录」显示 Unix 风格路径（`~/Downloads`），Windows 上完全不可用

- 状态: fixed
- 发现日期: 2026-09-29
- 模块: shell
- 严重程度: mid

## 现象

设置页「下载 → 默认下载目录」与「新建下载 → 输出目录」的输入框，在用户**未显式设置**时
显示的占位符是 `~/Downloads` —— 一条 Unix 路径。Windows 用户看到它无法判断真实落盘位置，
也无法照抄输入（`~` 在 Windows 不被展开）。用户多次反馈「显示为 Linux，完全不是 Windows 的方式」。

## 根因

两处叠加，缺一不可：

1. **后端从未下发系统默认目录。** `GET /api/config`（`download-engine/crates/orig-daemon/src/routes.rs:464`）
   只回 `download_dir`（用户显式配置值，未设置时为 `null`），前端拿不到「系统默认」这一档。
2. **前端只能用写死的 i18n 占位符兜底。** `SettingsPanel.tsx:460/477` 与
   `AddDownloadDialog.tsx` 的 `DirectoryPicker` 占位符回退到 `t('downloads.dirPlaceholder')`，
   而该键此前是 `"~/Downloads"`（`i18n/locales/zh-CN.json:49`）—— 把「后端没给」表现成了「Unix 路径」。

> 平台默认目录本身早已正确：`orig_core::paths::default_download_dir()` 走 OS known-folder API
> （Windows = `SHGetKnownFolderPath(FOLDERID_Downloads)`），即 `C:\Users\<user>\Downloads`。
> 缺陷只在于「正确值从未到达用户眼前」。

## 复现

1. 启动 daemon + `npm run dev`（5180），打开设置页 → 下载。
2. 观察「默认下载目录」输入框：显示 `~/Downloads`（修前）。
3. 对照 `curl http://127.0.0.1:<daemon>/api/config`：修前响应里根本没有默认目录字段。

自动化：`tauri-shell/verify/verify_default_download_dir.cjs`（断言 UI 占位符 **逐字等于**
daemon 的 `default_download_dir`，并反向断言无任何占位符含 `~`）。修前该脚本在
「placeholder equals daemon default_download_dir」一项必然 FAIL。

## 修复

- `download-engine/crates/orig-daemon/src/routes.rs`：`GET /api/config` 新增
  `default_download_dir` 字段（`orig_core::paths::default_download_dir()`）。
- `tauri-shell/src/api/daemon.ts`：`DaemonConfig` 新增 `default_download_dir: string`。
- `tauri-shell/src/components/SettingsPanel.tsx`：新增 `defaultDir` 状态，
  挂载时 `getConfig()` 拉取；两处 `DirectoryPicker` 占位符改为
  `dir || defaultDir || t('downloads.dirPlaceholder')`。
- `tauri-shell/src/components/AddDownloadDialog.tsx`：同上，打开对话框时拉取并作占位。
- `tauri-shell/src/i18n/locales/{zh-CN,en-US}.json`：`downloads.dirPlaceholder`
  由 `~/Downloads` 改为中性文案（`系统默认下载目录` / `System default download folder`），
  仅当 daemon 不可达时才回退到它 —— 不再把「拿不到」伪装成 Unix 路径。

## 关联

- 对照 BUG-071（`~` 展开 / 平台默认目录），本缺陷是其**展示侧**的遗留。
- 与 BUG-176 同批验收（均为「daemon 不可达 ⇒ 用户看到假象」类）。
