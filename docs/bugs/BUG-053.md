# BUG-053 解码提示是「只会置位的闩锁」：不论是否卡顿都常驻「解码吃力」

- **严重级**: major / misleading-ui
- **状态**: fixed（2026-09-19 已验收）
- **报告轮次**: 2026-09-19（用户原文：「为什么会卡顿播放还有提升空间吗? 还有不论是否卡顿都会出现:
  解码吃力：画面在丢帧，调低播放速度会明显更流畅 提示」）
- **模块**: shell（`src/lib/decodeHealth.ts`、`MediaViewer`、`TgPanel.VideoBlock`）

## 现象

提示**一旦出现就不再消失** —— 用户 1x 流畅播放时也一直看到它。而实测同一素材 1x 播放
丢帧为 **0 / 486 帧**，即提示内容与实际状态不符。

## 根因（四条叠加，主因是第 1 条）

`decodeHealth.ts` 的 `strained` 判定写成了一次性置位：

```ts
severeStreak = severe ? severeStreak + 1 : 0
if (severeStreak >= STREAK) setState('strained')   // ← 只有置位，没有复位
```

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | **只会置位、永不撤销**：`setState('strained')` 之后没有任何路径回到 `'ok'` | 任何一次瞬时抖动都把提示**永久**钉在画面上，直到切集/关播放器 —— 这正是「不论是否卡顿都出现」 |
| 2 | `resetKey` 不含倍速（VideoPlayer 甚至没有 key） | 提示文案建议「调低播放速度」，而**降低倍速恰恰不会清掉它** —— 建议与触发条件自相矛盾，用户只会得出「这提示没用」 |
| 3 | `paused` / `seeking` 早退时既不重设基线也不重置 streak | 暂停/跳转期间累积的计数会在恢复时被当成新丢帧结算 |
| 4 | 无预热静默期 | 起播预热、首帧填充、拖动进度的瞬时抖动即可满足「连续 4 个采样点（2s）」 |

## 修复

改为**带迟滞的实时状态**（`src/lib/decodeHealth.ts`）：

1. **可恢复**：连续 `CALM_STREAK = 4`（≈2s）不再丢帧 → 撤销提示（迟滞避免闪烁）。
2. **预热静默期** `WARMUP_MS = 1500`：起播/跳转/改速后只跟基线、不判定。
3. **事件重设基线**（`loadedmetadata` / `loadeddata` / `seeking` / `seeked` / `ratechange` / `play`）：
   计数跳变的点上把旧账清零。
4. **样本量下限** `MIN_SAMPLED_FRAMES = 4`：采样窗内几乎没解出帧（卡缓冲/刚起播）时不判定。
5. 画面尺寸出现后同样撤销 `unsupported`（元数据晚到、换源后不再误报）。

调用点把倍速并入 `resetKey`，使「调低速度」这个建议**真的会重设判定基线**：

- `VideoPlayer.tsx`：`useDecodeHealth(videoRef, \`${src}|${playbackRate}\`)`
- `TgPanel.tsx`：`useDecodeHealth(videoRef, \`${playing}-${item.messageId}-${rate}\`)`

## 验收

新增 `verify_shots/verify_decode_notice_recovery.cjs`：用**脚本化丢帧序列**驱动真实检测器
（patch `getVideoPlaybackQuality`），因此不依赖本机解码吞吐、结果确定性可复现。

| Phase | 条件 | 期望 | 修复版 |
|---|---|---|---|
| 0 | 真实播放 1x（不 patch）6s | 无提示 | PASS（全程无提示） |
| A | 干净样本（丢帧恒 0）5s | 无提示（误报即失败） | PASS |
| B | 持续丢帧（+10 帧/500ms = 20 帧/s）4s | 必须出现提示 | PASS（文案正确、视口内可见） |
| C | 丢帧停止 4s | **提示必须消失** | PASS（**2110ms 内撤销**） |

**验牙（断言真的会失败）**：把旧实现装回去重跑同一脚本 —— Phase 0/A/B 全 PASS，
**Phase C FAIL「仍停留『解码吃力…』」**，精确复刻用户现象。修复后复跑 ALL PASSED。

`tsc --noEmit` exit 0。证据：`verify_shots/decode_notice_recovery/`
（`phase0-real.png` / `phaseA-clean.png` / `phaseB-burst.png` / `phaseC-recovered.png` / `result.json`）。

## 关于「为什么会卡顿、还有提升空间吗」的实测

同一素材（H.264 1280×720 @30fps，id=380，297s）落地测量：

| 场景 | 需要上屏 | 实际上屏 | 丢帧 | 结论 |
|---|---|---|---|---|
| 裸 `<video>` 1x（Chromium） | 30 fps | **29.86 fps** | **0 / 486（0%）** | 1x 完全达标，无卡顿 |
| 裸 `<video>` 2x（Chromium） | 60 fps | 43.69 fps | 158 / 847（18.65%） | 2x 确实跳帧 |
| 裸 `<video>` 2x（Edge） | 60 fps | 43.25 fps | 47 / 722（6.51%） | 同上，非 Chromium 特例 |
| 空闲页 rAF（对照） | — | 60.11 fps | — | 呈现循环本身是 60Hz |

即 **2x 的卡顿 = 视频路径吞吐不足（~43fps 上限），而非页面呈现上限**。

但 **该数值不可外推到用户体感**：BUG-034 已用「同素材、同引擎、唯一变量」对照证明
**app 播放器不弱于裸 `<video>`**（2x 达成率 app 77.4% vs 裸 72.6%），且强制切到
RTX 3060 独显后 2x 仍为 40.1fps（Iris Xe 为 39.1fps，**无改善**）。
该 ~43fps 上限是本测量环境（Playwright 合成器时钟 55.5Hz）的既有特性 —— 见 BUG-034
「测量局限」。硬解能力本身正常：`mediaCapabilities` 对 HEVC/H.264 1080p@60fps
返回 `smooth=true, powerEfficient=true`（Iris Xe 硬解），`canPlayType` 全部 `probably`。

**结论**：播放器代码层面没有可提升空间（已被上面的对照证明不弱于裸 video）；
真正错的是提示本身 —— 它把一次瞬时抖动说成了持续状态。本 BUG 修的正是这个。

## 教训

1. **状态类提示必须可恢复**（带迟滞的实时状态，而非一次性闩锁）：不可恢复的告警一旦误触发
   就永久占据界面，用户会连同正确告警一起忽略它。
2. **「建议」必须与「触发条件」一致**：提示让用户降速，而 `resetKey` 不含倍速 ——
   照做也清不掉，等于自证无效。
3. **断言必须验牙**：新增的恢复类断言要先把旧实现装回去跑一遍，确认它**必然失败**，
   否则无法区分「修好了」与「断言根本不生效」。
