# BUG-024: 缓存状态完全丢失 —— 下载任务只活在浏览器内存里，刷新即归零且无法续传

- 状态: fixed
- 发现日期: 2026-09-17
- 模块: engine+shell
- 严重程度: critical

## 现象

用户报告：「TG 中点击『缓存』，切换/刷新页面，显示『继续』，点击『继续』继续缓存。
核心问题，缓存状态完全丢失。」

即：点击缓存 → 刷新/切页 → 进度与「缓存中」标识全部消失，界面退回到一个
看似「什么都没发生」的状态，用户无法判断缓存是否在跑、跑到哪、是否成功。
（页面上的「继续 n/N」是由**数据库快照**推导的，只能反映**已经成功落盘**的条目；
刷新时正在传输、尚未返回的那一条服务端完全不知情，于是呈现为「停滞/需重来」。）

## 根因

三层结构性缺陷叠加，缺一层都不至于「完全丢失」：

### 1. 任务状态存在浏览器内存，不在服务端

`tauri-shell/src/components/TgPanel.tsx`：

- `const [downloading, setDownloading] = useState<Set<number>>(new Set())` —— 单条「缓存中」
- `const [albumProgress, setAlbumProgress] = useState<Map<string, { done: number; total: number }>>(new Map())` —— 整组进度
- `downloadAlbum()` 用 `for` 循环在**浏览器里**逐条 `await downloadTgMessage(...)`

刷新页面 = 组件卸载 = Set/Map 归零，且循环被浏览器直接终止。
**下载的编排权在浏览器手里**，这是本缺陷的总根因。

### 2. 服务端下载是同步阻塞调用，没有任务实体

`crates/orig-tg/src/routes.rs` 的 `download` 处理器把整条下载**跑完才返回**；
`store.rs` 的 `mark_downloaded` 只在单条**成功返回之后**才写入。
客户端断开（刷新）后该请求被丢弃，服务端**没有任何任务记录**——
既无法报告进度，也无法在重连后告诉前端「刚才那条其实下完了」。

### 3. 落盘非原子：半截文件写在最终路径上

`crates/orig-tg/src/grammers.rs` 的 `download` 直接 `File::create(最终路径)` 边下边写。
中断会在**最终路径**留下半截文件；而「已缓存」判定依赖 DB 标记，
一旦标记与磁盘状态不一致，就会出现「标记已缓存但文件残缺」或「重新下载」的错乱。

### 次要发现：CORS 来源白名单写死开发端口（放大排查难度）

`main.rs` 的 `CorsLayer::allow_origin` 仅列 `localhost:5180 / 127.0.0.1:5180 / tauri://localhost`。
而前端 `api/tg.ts` 的 `request()` 对**所有**请求（含 GET）都带 `Content-Type: application/json`，
使 GET **不是**简单请求、必然先发 OPTIONS 预检。于是任何**非 5180 端口**的前端都拿不到
`GET /api/tg/session` → 前端按「服务不可达」判为未绑定 → **Telegram 侧栏入口整个消失**
（不是「未登录」提示，而是入口不见了），极易被误判为登录态丢失。
实测：隔离端口 5182 上该请求有 `REQ` 无 `RES`，`localStorage` 被改写成 `{bound:false}`。

## 复现

1. 打开 TG 面板，对含多条的相册点击「缓存」。
2. 在进度推进过程中**刷新页面**（或切到别的视图再切回）。
3. 修复前：进度与「缓存中」标识全部消失，无法确认缓存是否继续。

验收脚本即按此步骤断言（见下）。

## 修复

**原则：把缓存任务的生命周期从「一次 HTTP 请求」里搬出来，服务端成为唯一真相源。**

1. **新增 `cache_task` 表（服务端任务实体）**：`chat_id / group_id / item_key / items /
   total / done / status / dir / current_id / error / created_at / updated_at`，
   并以 **partial unique index** 约束「同一 item_key 只允许一个活跃任务」。
2. **入队即返回，worker 在服务端跑**：`POST /api/tg/cache/tasks` 入队后立刻返回任务快照，
   真正下载由 orig-tg 内的 detach worker 承担；刷新只是重新 `GET /api/tg/cache/tasks`。
3. **拒绝假「缓存中」**：进程启动时把遗留的 `queued/running` 任务降级为 `interrupted`
   （崩溃后不会留下永远转圈的僵尸任务）。
4. **幂等续跑**：worker 逐条先判定「已缓存」= **DB 标记 + 文件真实存在** 双条件，
   命中即跳过 → 重新入队天然表现为「继续」，而不是重下。
5. **可取消**：`DELETE /api/tg/cache/tasks/:id` 置 `cancelled`，worker 在条目间隙自停，
   进度冻结且不再写入已缓存清单。
6. **原子落盘**：先写 `.part` 再 `rename` 到最终路径，杜绝半截文件冒充完整缓存。
7. **前端改为读服务端任务**：删除浏览器侧下载循环与 `downloading`/`albumProgress` 内存态，
   改为 1s 轮询服务端任务（orig-tg 无 SSE 基础设施，轮询是当前最小实现）。
8. **CORS 来源可追加**：`ORIG_TG_EXTRA_ORIGINS`（逗号分隔）追加白名单，
   隔离端口验收/自定义前端部署无需改代码。

## 防再发

1. **长任务状态禁止只存前端内存**：凡「刷新/切换后应保持」的状态，一律落服务端，
   前端只做投影与轮询。判据：刷新一次，状态是否还在且已推进。
2. **验收必须包含「刷新」这一步**，且**服务端任务态与 UI 文本交叉断言**——
   单看 UI 文本会被「已缓存 1/3」提前判过（本次实测踩到），必须等服务端终态。
3. **CORS 来源不得写死开发端口**；隔离端口验收用 `ORIG_TG_EXTRA_ORIGINS` 追加，
   不改码、不碰生产实例。
4. **夹具必须"诚实"**：`ORIG_TG_DUMMY_DOWNLOAD=1` 才产出占位下载与缩略图，
   默认关闭——回退 dummy 时绝不允许产生**假缓存文件**，否则验收本身会骗人。
