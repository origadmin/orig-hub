# BUG-322: 引擎下载「来源无关重试」契约未履约 + 双面对齐缺失（下载页栈重启空白）+ 重排队身份错乱（重试后状态回退成 cancelled）

- 状态: fixed
- 发现日期: 2026-10-16
- 模块: engine+shell
- 严重程度: high

## 现象（用户原话，2026-10-16）

> BUG-319 验收后：「我不确定哪个方案好. TG只是其中一个插件功能,要考虑后续的100个插件,不同来源.」

由此引出三条必须同时成立的事实：

1. **下载页在栈重启后空白**：用户看到「数据经常丢失」。根上是 `GET /api/downloads`（原生面）只读内存任务表，没有合并 `engine_task` 库；而 `GET /api/activity`（聚合面）合并了库。两处各自实现合并 ⇒ 漂移：栈重启后下载页空、活动页有行。这不是数据真的丢，是**下载页这一面没把持久化记录呈现出来**。
2. **引擎下载任务取消/失败后没有「重试」入口**：但 TG 侧早已存在通用的 `Action::Retry` 契约，前端只认契约（`item.actions`）不认 `kind`。引擎侧没履约 ⇒ 用户只能删掉重加。用户明确指出不能把重试做成 download 特例（后续 100 个插件/不同来源都要能复用同一套）。
3. **点「重试」后状态回退成 cancelled**：UI 验收序列实测 `cancelled>downloading?` 不成立，重试后接口状态仍 `cancelled`，看起来「重试没生效」。

## 根因

### 1. 单一真源缺失（直接机制，对应现象①）
同一批引擎任务有两个呈现面（`/api/downloads` 原生面带分块/连接明细；`/api/activity` 聚合面与 TG 同列）。两处各自去「合并内存与库」，必有一处漏合并。聚合面在 `download_views` 里调了 `engine_rows` 的雏形，原生面 `list()` 只读 `st.tasks` 内存 ⇒ 重启后原生面空白。

### 2. 引擎侧动作枚举未覆盖 Retry（对应现象②）
`activity.rs::actions_for(Download, status)` 只给 `pause/cancel/resume`，终态返回空；而 `Action::Retry` 早已为 `Cache` 终态（`failed`）提供，前端 `DownloadItem` 只渲染 `item.actions` 里的动作，故引擎终态行永远没按钮。

### 3. spawn 收尾闭包按 id 认领状态而非按任务身份（对应现象③）
`requeue`（重试）复用同一 task id 重建新 `Task`；旧任务的 `spawn_task` 收尾闭包按 `id_run` 把终态写库。旧任务若仍在临终跑（cancel 后 `run()` 还要收尾几秒），它的写库会覆盖刚重建的新任务状态 ⇒ 重试后状态被旧任务的 `cancelled` 覆盖。这是**身份错乱**：状态写入必须认「这个 Arc<Task> 是不是还活着」，不是认 id。

## 处置（改动）

### 后端（orig-daemon）
- 新增 `engine_rows(st: &AppState) -> Vec<EngineRow>`：**内存优先、库补齐**的单一真源。`/api/downloads` 的 `list()` 与 `/api/activity` 的 `download_views()` 都改走它，消除双面对齐漂移。
- `actions_for(Download, status)` 终态补 `Action::Retry`（与 `Cache` 同契约）：`cancelled/error/interrupted → [Retry]`，`completed` 仍空；`TaskKind` 层不再特判 download。
- 新增 `POST /api/downloads/:id/retry`：取库记录按原 url/output 走与新建**同一段** `probe_url`/`build_task` 重建，不新造路径；复用既有 `requeue` 的 Registry 按 scheme 分派（来源无关）。
- `spawn_task` 收尾闭包捕获 `Arc<Task>`，**不在内存表即跳过写库**（`st.tasks` 里没有该 `Arc` 句柄 ⇒ 这是别人的活体/已死的旧任务，不写），从根上消除旧任务覆盖新任务。
- `EngineTaskRecord` 新增 `interrupted` 状态（进程被杀留下的未完成行），恢复时标 `interrupted` 再按 url 重建；暂停行恢复后仍是 `paused`（用户意图不被重启改写）。

### 前端（tauri-shell）
- `types.ts`：`DownloadStatus` 加 `actions?: string[]`；联合类型补 `'interrupted'`（类型不承认的状态前端永远不会正确处理）。
- `status.rs`/`status.ts`：`DownloadStatus` 序列化带 `actions`；`statusMeta` 补 `interrupted: { label:'已中断', variant:'destructive' }`（否则持久化引入的新状态被渲染成「空闲」）。
- `useStore.ts`：新增 `retry(id)`，调 `POST /api/downloads/:id/retry` 后 `refresh()`。
- `DownloadItem.tsx`：**按契约渲染**（`can = actions.includes`），不按 `status` 硬编码；终态行（`stalled` = 无 pause/resume 可点）的「重试」按钮**常驻可见**（不藏 hover）；在途行保持 hover-only。
- `DownloadPanel.tsx`：全部档过滤补 `interrupted`（否则恢复行被直接滤掉看不见）。

- 源于 BUG-319 待拍板的「interrupted 行如何重试」；本 BUG 把重试做成来源无关契约而非 download 特例（呼应 2026-10-16 用户「100 个插件/不同来源」要求）。
- 持久化本体在 BUG-319（fixed）。双面对齐是 BUG-319 修后暴露的次生缺口。
- 与 BUG-318/BUG-176 同源：聚合面恒 200、但来源不可用/记录缺失时不能把「取不到」渲染成「没有」。
