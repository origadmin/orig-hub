# BUG-246: 入库流水线「排队中」行标题退回频道名——消息行只在任务**启动时**才落 `media_message`，排队阶段查不到

- 状态: open
- 发现日期: 2026-10-10
- 模块: engine
- 严重程度: mid

## 现象

- 用户把内容加进入库流水线后，行标题仍显示**频道名/裸频道 ID** 而不是内容标题；
  其余状态（已完成 / 运行中 / 失败）在 BUG-232 v2 之后都已正确。
- 用户原话：「入库流水线添加后就应该能获取到完整数据了，但是实际排队中显示的数据还是不正确」。

## 根因

**消息元数据落库发生在任务启动时，不在入队时。**

- 标题来源（BUG-232 v2）：`download-engine/crates/orig-tg/src/routes.rs:1166-1191`
  `cache_task_titles()` / `cache_task_title()` 从 `media_message` 取
  `channel_id + message_id` 对应的**首个非空 caption**。
- 而 `media_message` 行的写入点是 `IngestCtx::prepare()`
  （`download-engine/crates/orig-tg/src/routes.rs:1425-1446`）：遍历任务消息，
  缺行才调 `st.client.message_meta()` 补写 `upsert_message`。
  该函数在 **worker 启动任务时**才跑 —— 排队任务尚未启动 ⇒ 行整条缺失。
- `POST /api/tg/cache/tasks`（`routes.rs:1126-1157`）只写 `cache_task` 一行，
  不碰 `media_message`。
- 于是 `cache_task_title()` 对排队任务恒返回 `None`，前端标题链
  `task.title → 频道名 → 裸 chatId` 必然退到第二档。

**实测（本机 live 库，2026-10-10）**：

- `GET /api/tg/cache/tasks/all` 共 83 条任务，按状态统计「无 title」：
  - `queued` **12/12 全无 title**
  - `done` 3/51 无（这 3 条是 caption 本就为空，属如实为空）
  - `running` 1/1 有、`failed` 4/4 有、`interrupted` 4/4 有
- 库核对（`%APPDATA%/com.origadmin.orighub/tg/store.db`）：13 条排队任务
  逐条消息查 `media_message`，结果**全部「缺行=全部」**（既非空 caption，也非 ID 不匹配）：
  ```
  task 125 chat -1003704645341 n=2 有caption=0 空caption=0 缺行=2
  task 128 chat -1003704645341 n=3 有caption=0 空caption=0 缺行=3
  task 136 chat -1004457697592 n=5 有caption=0 空caption=0 缺行=5
  （13 条同形）
  ```
  反证 ID 形态没问题：同库 `media_message` 的 `channel_id` 就是 `-100…` 形态，
  且同频道其它状态的任务标题能取到。

## 复现

在 TG 频道里对若干组内容点「加入媒体库」（让其排在已有任务之后），打开入库流水线面板：
这些排队行标题显示频道名，不显示内容标题。

## 修复

**把元数据登记前移到入队时刻**（与 BUG-170 已裁定方向一致：元数据登记瞬间完成，
耗时的只有字节）：`POST /api/tg/cache/tasks` 落 `cache_task` 之后，立即为该任务缺失的
消息补 `media_message` 行（复用现有 `st.client.message_meta()` + `store.upsert_message()`，
后台 `tokio::spawn` 异步执行，不阻塞入队响应）。

实现落地时对原方案做了一处收口（单一真源）：补写逻辑抽成
`async fn ensure_message_rows(st: &Arc<AppState>, chat_id: i64, msg_ids: &[i64])`，
入队处理器与 `IngestCtx::prepare()` **共用同一个函数**，而不是两处各写一份。
`prepare()` 的预扫语义不变（仍只补缺失行、单行失败跳过），只是改为调用该函数——
`upsert_message` 幂等，它继续充当「入队时补写失败 / 升级前入队的历史任务」的安全网。
