# BUG-114：在线流零背压 —— `media_file()` 直透下载流，未缓存内容播放卡顿

- 状态: open
- 严重程度: high
- 模块: engine
- 发现日期: 2026-09-22

## 现象

未缓存内容在线播放卡顿甚至卡死界面。

## 根因

`media_file()`（`GET /api/tg/file/:chat/:msg`）用 `Body::from_stream` **直接透传** grammers
下载流，**没有任何节流**。而 BUG-033 加的背压只做在本地文件投递上：

```
grep DELIVERY_BUDGET_FACTOR
→ routes.rs:2324  仅 serve_local_file 使用一次
```

即 **BUG-033 只修了本地路径，在线路径漏了**。

后果与 BUG-033 实测一致：本地千兆下服务端灌数据速率（数百 MB/s）远超解码器消费速率
（码率 × playbackRate），Chromium 读满 buffer 即 abort，并在**同一区域反复重取** ——
实测 2x 播放 10s 内 **137 请求 / 792 MiB / 冗余 63x**，在 WebView2 里就是界面卡死。

## 定位（离线优先拍板后的调整）

用户 2026-09-22 拍板「离线优先，入库即落盘」后，**播放默认走 Local**（唯一有背压的那条），
`Remote` 降级为**过渡态兜底**。因此本条：

- **仍然必须修**（缓存未完成时、在线预览时仍会走这条路）；
- **但不再是最紧急的一条** —— 主流路径已经是本地投递。优先级排在 BUG-115 / BUG-116
  （入库即落盘与存量脏数据）之后。

## 修复方向

统一投递契约（评审文档专题二）：

```
DeliverySource::Local{path} | Remote{chat,msg}
        ↓ 单一入口 deliver(source, range) -> (stream, size, mime)
        ↓ 两条路都过同一个 throttle(reader, budget)
```

- 背压：`budget = bitrate × DELIVERY_BUDGET_FACTOR`（6.0），无码率回落
  `DELIVERY_FALLBACK_BPS`（16MiB/s），支持 `ORIG_TG_DELIVERY_BPS` 覆盖以便 A/B；
- Remote 额外加**有界预读缓冲**（约 32MiB）反压 grammers；
- 判据：**倍速下的冗余倍数应在个位数**（当前基线 3-4x 为合格参考）。

## 验收要求（不得只做冒烟）

- 用 `diag_rate_storm.cjs` **分别在 1x 与倍速下各记一段** —— 1x 完全正常的通路在 2x 下
  可能放大数十倍（BUG-033 教训）。
- 新增/修改任何投递端点都必须纳入该脚本回归。
- 判「卡顿」必须用真实上屏帧（`requestVideoFrameCallback` + `getVideoPlaybackQuality`），
  禁用 `timeupdate` / `rAF`（BUG-034）。

## 关联

- BUG-033（背压，只修了本地）、BUG-034（卡顿判据）、BUG-028（Remote 应走
  `parallel_range_stream`）。
