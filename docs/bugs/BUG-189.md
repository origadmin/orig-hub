# BUG-189: 并发下取新行 id 的竞态（**三处**）—— 连接级 `last_insert_rowid()` 被别的请求抢走

- 状态: in_progress
- 发现日期: 2026-09-29
- 模块: engine
- 严重程度: critical

## 现象

**真实数据已被删除**：真实剧集 108 消失。

- 日志：`[1790687418] /api/media/series/112/merge: ...（源 108 已删除）`
- `GET /api/media/series/108` → 404

报因不在合并逻辑本身，而在**它拿到的 id 是错的**。

> 证据来源：现象由 `merge-verifier` 在并发写验证中实测报告（team-lead 已在处理）；
> 「16 路并发有 6 路拿到重复 id」由修复者在代码注释中实测记录（`media.rs:2152`）。
> 本条的**代码事实（根因表、三处位置、修复现状）**由 engineer 独立只读复核。

## 根因

两步取 id，而两步之间**没有事务**：

| 位置 | 事实 |
|---|---|
| `download-engine/crates/orig-tg/src/store.rs:100-108` | `pub struct Store { pub(crate) conn: Connection, ... }` —— **整个 Store 只有一条共享连接**（注释：「`pub(crate)` 供 `media` 模块复用同一连接」） |

`last_insert_rowid()` 是 **SQLite 的连接级状态，且不区分表**。在单条共享连接上，
「INSERT」与「取 id」之间存在 `.await` 让出点，并发请求交错时该值可能已被**另一个请求**
（甚至**另一张表**的 INSERT）改写 ⇒ 返回的 id 与刚插入的行**不对应**。凡「按回包 id 记录、
随后 `DELETE /:id` 或拿它当合并源/目标」的调用方，都会操作到**错误的真实数据**。

### 三处生产点（**必须全部覆盖，只修一两处等于未修复**）

| # | 位置 | 函数 | 修复前 | 现状 |
|---|---|---|---|---|
| 1 | `media.rs:2148`（doc `:2150-2155`） | `create_series` | `INSERT INTO media_series` 后**单独** `SELECT last_insert_rowid()` | **已修**：改 `INSERT ... RETURNING id`（同一条语句） |
| 2 | `media.rs:3568`（doc `:3568-3571`） | `create_tag`（旧名 `upsert_tag`） | `INSERT INTO media_tag` 后**单独** `SELECT last_insert_rowid()` | **已修**：改 `INSERT ... VALUES (...) RETURNING id` |
| 3 | `store.rs:806`（旧写法 `:840`） | `enqueue_cache_task` | `INSERT INTO cache_task` 后 `self.conn.last_insert_rowid()` | **未修**：`:820` 现为**临时旧写法**（注释原文：「仅用于证明新测试能真红，验证后立即改回 RETURNING 版」） |

**排除项（避免把测试代码误当第四处）**：`media.rs:5825` 与 `media.rs:5876` 也出现
`conn.last_insert_rowid()`，但二者均在 `#[cfg(test)] mod tests`（起始 `media.rs:4278`）内，
是测试夹具用裸 `conn` 造数据后取 id，**非生产点**。

## 复现

三个并发单测（每个生产点一个，均已入库）：

| 测试 | 位置 |
|---|---|
| `create_series_ids_are_unique_under_concurrency` | `media.rs:6712` |
| `create_tag_ids_are_unique_under_concurrency` | `media.rs:6759` |
| `enqueue_cache_task_concurrent_ids_are_isolated` | `store.rs:1779` |

做法：N 路任务在 `tokio::sync::Barrier` 对齐后**同时**发起，最大化「INSERT 与取 id 之间」的
交错概率；断言各路拿到的 id **互不相同**，且各自 `get_*` 到的内容与自己的请求一致。

**验牙**：把任一处改回「先 INSERT、再单独取 id」，对应测试必须**红**。
（`store.rs:820` 的临时旧写法正是为此存在，验证后须改回 `RETURNING`。）

**端到端补充判据**：并发两路 `POST /api/media/series` 必须回**不同** id，且各自
`GET /api/media/series/:id` 的标题与请求一致。单线程下 `last_insert_rowid()` 恰好总是对的
—— **这正是该缺陷至今未被发现的原因**，故单线程断言不足以作数。

## 修复

统一方向：**`INSERT ... RETURNING id`**（一次往返取本行 id），或 `BEGIN IMMEDIATE`
事务包住「INSERT + 取 id」。禁止再出现「INSERT 之后另起一句取连接级 id」。

- 点 1 `create_series`：**已完成**。
- 点 2 `create_tag`：**已完成**。
- 点 3 `enqueue_cache_task`（`store.rs`）：**进行中**（owner: store-fix，见任务 #12）。
  完成判据：`:820-840` 的临时旧写法被 `RETURNING` 版取代，且
  `enqueue_cache_task_concurrent_ids_are_isolated` 在**旧写法下红、新写法下绿**。
