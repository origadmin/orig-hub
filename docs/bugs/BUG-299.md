# BUG-299: 文件域只认媒体库——HTTP 下载完成、导入完成与 TG 缓存完成三类成品不自动进入文件域，且成品浏览器不含非媒体文件与无字节「在线」条目（模块重整 M2）

- 状态: open
- 发现日期: 2026-10-13
- 模块: engine+shell
- 严重程度: critical
- 档位: standard

> **来源**：用户 2026-10-13 规划包 `docs/design/module-restructure-2026-10-13/tasks.md` §M2（D13/D16=A）。
> 产品口径（用户原话）：「缓存后应该进入文件管理，这是需求」。

## 现象

1. **HTTP 下载完成的文件不进文件域**：引擎下载完成后只在下载列表里可见，
   文件域（M0 后的分类墙/资料库）不会出现该成品，用户必须手动「加入媒体库」类操作。
2. **成品浏览器只覆盖媒体**：视频/音乐/图片之外的成品（pdf / zip / srt / 文档）在文件域**无位置**，
   只能去系统目录翻。
3. **无字节 TG 图片条目**：`media_item` 存在但字节未落盘（`hasMediaBytes=false`）时，
   条目要么不显示、要么显示为「缺失」，与「在线可重缓存」混淆（BUG-147 要求库浏览不被来源失效阻断）。
4. **未归档靠前端全量过滤**：`MediaLibraryPanel` 在客户端按 `series_id == null` 过滤，
   千条级库下既慢又与后端参数化查询语义重复。
5. **存量文件无补录**：升级前已完成下载的历史文件不在文件域，无一次性扫描通道。

## 根因

- **ingest 只有一条路径**：现状只有 TG 缓存完成会 upsert `media_item`
  （`source='tg'`, `ref=<chat>:<msg>`，`routes.rs` 的 `register_media_item_*` 家族），
  **引擎完成事件没有接线到 ingest**（`orig-core` 下载完成 → 无人消费）。
- 文件事实无装配层：`03-data-model-and-migration.md` 的 `FileFact` 目标态是
  「受管下载根 × 任务记录 × `media_item` 投影」的**只读内存快照**（§D1 端点不碰 DB、不现场扫盘），现状不存在该层。
- `source` 与 `ref` 的唯一约束（BUG-292 的同源键）已存在但只被 TG 路径使用，
  HTTP/local 两条来源没有复用同一幂等入口。

## 复现

1. 用「新建下载」完成一个 HTTP 文件 → 文件域不出现该文件（只有下载列表可见）；
2. 库内放入一个 pdf 成品 → 文件域无位置显示；
3. TG 图片条目（有行无字节）→ 显示为缺失/不可点，而非「在线 · 点击缓存」；
4. 构造千条级 `media_item` → 未归档视图首屏卡顿（前端全量过滤）。

### 出口判据

1. 端到端「HTTP 下载完成 → 文件域立即可见 → 可播放」，且**断 TG 进程重复下载**不重复建条目（幂等）；
2. 视频 + pdf + zip + srt + 在线图片混合夹具下六分类计数与磁盘一致，同一成品不双计；
3. 删除联动回归（BUG-051/096：清缓存不删条目 / 删 TG 条目连字节）；
4. 千条级未归档查询不卡 UI；归集后各 pane 计数一致；
5. 轮询三律证据（无新增轮询）；`cargo test` + 双端 verify；
6. **反向证伪**：ingest 入口去掉 `source+ref` 幂等判重 → 重复完成事件必产生重复条目（必须 FAIL）。

## 设计基础违反定性（2026-10-15 用户裁定，追加不改写上文）

**用户原话（裁定级）**：「『文件管理』= 已登记媒体的全量墙，逻辑有严重的问题。既然全量，那就是**共通 + 兼容性**；当前的实现逻辑 ZIP、exe、pdf、其他全不兼容，**设计基础违反**；大量这种问题被认为是正确的，这有严重问题。」

**定性（本节取代一切「M0 过渡 / M2 待补 / 已知欠账」式叙述）**：

1. **数据模型倒置**：共识（D1=A 文件管理为纲、D13 事实轴、README §FileFact「受管字节的**通用记录**：路径/大小/时间/类型/来源」、spec §3「浏览全部文件，含非媒体文件」、09-revision §9.3「范围扩到含非媒体文件行」）要求文件域对**全部类型共通兼容**；现状把 `media_item`（媒体登记表）当唯一事实源 ⇒ 「全量」实为「已登记媒体」，非媒体成品（zip/exe/pdf/…）一律不可达。这是**违反**，不是分期。
2. **伪依赖拆除**：原任务表以 BUG-172（媒体迁 daemon，M1）为 M2-T01 前置。2026-10-15 实证：**读通路不需要它** —— `orig-daemon` 现存 `GET /api/downloads`（`status.rs::DownloadStatus.dest_path`）+ `/api/config.default_download_dir`（受管下载根），枚举成品所需的路径/状态/根目录**今天就在 daemon 手里**，前端下载域也已在消费（`listDownloads()`）。BUG-172 只挡 ingest **写入**路径（daemon 完成事件 → upsert media_item）。「必须等 M1」是把违反合理化的第二层叙事，一并废止。
3. **合法化叙事清除**（用户指控「大量这种问题被认为是正确的」的载体）：`FilesPanel.tsx` 旧「过渡口径」、`MediaLibraryPanel.tsx` 旧「有损映射 M0 期」、BUG-298 残余③1 的「真正区分在 M2」叙述**已改写为违反标记**（指明共识原文 + BUG-299 + 「不得读作既定正确态」）。tasks.md M0-T03 原文不动（规划包历史），但其「M0 分类墙暂不含」条款自此**只许作为违反记录引用，不许作为口径引用**。
4. **修复验收口径**：文件域父行必须对 zip/exe/pdf/任意扩展名与媒体一视同仁地可见、可定位（打开目录）、可删除（含字节，AGENTS §5 联动）；「已登记媒体墙」降为文件域内的一个视图，不再是域本身。
