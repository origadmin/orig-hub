- 模块: shell
- 严重程度: mid

> 来源：用户 2026-10-12「播放依然卡顿，为什么 TG Web 不卡、本地反而卡？」的诊断取证。
> **本档为任务文档**（用户定：纯文档任务，代码由别的组负责）。

> 而用户主诉包含「2x 卡」⇒ 用户的 2x 观感**可能另有来源**（起播 / 缓冲延迟），本档只记录**已证部分**，不替用户结论背书。

## 现象

应用内播放器（`VideoPlayer` → `/stream` FRC 路径）在**部分倍速**下**稳态**即出现上屏节拍抖动（一顿一顿），且**与倍速非单调**：

- **最差 = 3x**（两源 `jitterShare` ≈ 0.27），**次差 = 4x**（472 = 0.266 / 673 = 0.145）。
- **1.25x / 2x 几乎为零**（472 = 0 / 0；673 = 0.056 / 0.078）。
- 同轮 **裸 `<video>` + 原生 `playbackRate`** 对照在 4x 反而最稳（0.003）。

### 事实 1：不是供数、不是解码 —— 是**呈现层**节拍
全部 18 采样 `waiting = 0`、`stallGaps = 0`、`readyState = 4` ⇒ **不存在供数中断**；抖动来自上屏节奏。

### 事实 2：抖动与倍速**非单调**
落在**整数 vsync 倍数**上的档位几乎零抖（472@1.25x、472@2x 直方图纯 `2×`、`jitterShare = 0`）；
没落上的档位退化成 `1×` / `3×` vsync **交替**（直方图成对出现 `1×:N … 3×:N`）⇒ 一顿一顿。**最差是 3x**。

### 事实 3：FRC 把上屏帧率压到 ~24–30 fps
app 路径每档只有 ~30 fps（高倍速降到 24 fps）上屏；而**裸 video + 原生 playbackRate** 对照能到 50–60 fps。
FRC 转码命令带 `-fpsmax`（`download-engine/crates/orig-tg/src/routes.rs` 转码段），高倍速用更低 fps。

### 事实 4（★ 关键反例）：**裸对照在 2x 也抖（0.197）** ⇒ **不能**简单归因于「FRC 压缩帧率」
`bare@2x jitterShare = 0.197` **大于** `app@2x = 0` ⇒ 「FRC 30fps 撞 60.9Hz」**不足以解释全部**。
⇒ **机制未定论**：可能与「源帧率 × 倍速 与刷新率的关系」「合成器节拍」等多因素相关，须继续定位。

### 事实 5：**必须 headful**
headless 会把低倍速数字**灌水**：472@1x `0.235`（headless）→ `0.033`（headful）；472@2x `0.145` → `0.000`。
（`verify/lib/cdp.cjs` 的 BUG-213 警告成立：headless 下 rVFC 被钉在假 ~60 Hz。）

## 修复（方向；**机制未定论前不指定实现**）

1. **先定位**（P0）：把「源帧率 × 倍速 ÷ 刷新率」与 `jitterShare` 的相关性做定量核对（含裸对照臂），
   判定究竟是「FRC 输出 fps 与刷新率拍频」还是「合成器节拍」或二者叠加。
2. **若确为拍频**：FRC 输出 fps 应选**能整除刷新率**的值（60 Hz 下 30 fps = 2×vsync、20 fps = 3×vsync），
   避免落在非整数倍（如 24 fps：24 / 60.9 ≈ 0.394）。
3. **不得据此回退 stream-first**（BUG-230 已实测 `raw` 更卡）。
4. **不推翻** BUG-217 / 218（控件层合成）与 BUG-273 / 274（投递链路）的既有结论 —— 本档已用 `waiting/stallGaps = 0` 与它们划清界限。
