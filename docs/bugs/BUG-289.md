## 现象

应用内播放器（`VideoPlayer` → `/stream` FRC 路径）在**部分倍速**下**稳态**即出现上屏节拍抖动（一顿一顿），且**与倍速非单调**：

- **最差 = 3x**（两源 `jitterShare` ≈ 0.27），**次差 = 4x**（472 = 0.266 / 673 = 0.145）。
- **1.25x / 2x 几乎为零**（472 = 0 / 0；673 = 0.056 / 0.078）。
- 同轮 **裸 `<video>` + 原生 `playbackRate`** 对照在 4x 反而最稳（0.003）。

### 事实 1：不是供数、不是解码 —— 是**呈现层**节拍
全部 18 采样 `waiting = 0`、`stallGaps = 0`、`readyState = 4` ⇒ **不存在供数中断**；抖动来自上屏节奏。

### 事实 2：抖动与倍速**非单调**
落在**整数 vsync 倍数**上的档位几乎零抖（472@1.25x、472@2x 直方图纯 `2×`、`jitterShare = 0`）；
没落上的档位退化成 `1×` / `3×` vsync **交替**（直方图成对出现 `1×:N … 3×:N`）⇒ 一顿一顿。**最差是 3x**。

### 事实 3：FRC 把上屏帧率压到 ~24–30 fps
app 路径每档只有 ~30 fps（高倍速降到 24 fps）上屏；而**裸 video + 原生 playbackRate** 对照能到 50–60 fps。
FRC 转码命令带 `-fpsmax`（`download-engine/crates/orig-tg/src/routes.rs` 转码段），高倍速用更低 fps。

### 事实 4（★ 关键反例）：**裸对照在 2x 也抖（0.197）** ⇒ **不能**简单归因于「FRC 压缩帧率」
`bare@2x jitterShare = 0.197` **大于** `app@2x = 0` ⇒ 「FRC 30fps 撞 60.9Hz」**不足以解释全部**。
⇒ **机制未定论**：可能与「源帧率 × 倍速 与刷新率的关系」「合成器节拍」等多因素相关，须继续定位。

### 事实 5：**必须 headful**
headless 会把低倍速数字**灌水**：472@1x `0.235`（headless）→ `0.033`（headful）；472@2x `0.145` → `0.000`。
（`verify/lib/cdp.cjs` 的 BUG-213 警告成立：headless 下 rVFC 被钉在假 ~60 Hz。）

## 修复（方向；**机制未定论前不指定实现**）

1. **先定位**（P0）：把「源帧率 × 倍速 ÷ 刷新率」与 `jitterShare` 的相关性做定量核对（含裸对照臂），
   判定究竟是「FRC 输出 fps 与刷新率拍频」还是「合成器节拍」或二者叠加。
2. **若确为拍频**：FRC 输出 fps 应选**能整除刷新率**的值（60 Hz 下 30 fps = 2×vsync、20 fps = 3×vsync），
   避免落在非整数倍（如 24 fps：24 / 60.9 ≈ 0.394）。
3. **不得据此回退 stream-first**（BUG-230 已实测 `raw` 更卡）。
4. **不推翻** BUG-217 / 218（控件层合成）与 BUG-273 / 274（投递链路）的既有结论 —— 本档已用 `waiting/stallGaps = 0` 与它们划清界限。

## 机制闭合（2026-10-12，定量核对 —— **本档初稿的预测子是错的，已更正**）

对 18 采样做「投递节奏 vs 刷新率」的定量核对（headful，refresh ≈ 60.9 Hz）。**结果推翻了本档初稿的假设**：

- **初稿假设（错）**：「源帧率 × 倍速 ÷ 刷新率」的拍频。实测 **Pearson r = 0.103**（剔除 0.5x/0.75x 供数噪声后 0.098）⇒ **几乎无解释力**。
- **正确预测子**：**「投递帧率 ÷ 刷新率」** —— 令 `dist(x, ℤ)` = x 到最近整数的距离（≈ 需被补到下一个 vsync 倍数的帧占比），实测 **Pearson r = 0.842**（剔噪后 **0.912**）⇒ 解释 ~71–83% 方差。

### 根因（源码）：**≥3x 档把投递 fps 从 30 降到 24**

`download-engine/crates/orig-tg/src/routes.rs:4076-4082`：
```rust
fn encode_profile(speed_hundredths: u16) -> EncodeProfile {
    if speed_hundredths >= 300 { EncodeProfile { preset: "ultrafast", crf: 28, fps: 24 } }  // ≥3x
    else                        { EncodeProfile { preset: "veryfast",  crf: 23, fps: 30 } }  // <3x
}
```
`fps` 直接进滤镜 `setpts=(PTS-STARTPTS)/{speed},fps={N}`（`speed_video_filter`，`:4084-4086`）
⇒ **<3x 投递 30 fps、≥3x 投递 24 fps**。ffprobe 实测缓存代理坐实（`<item_id>.mp4` / `-speed-50/75/200` = 30 fps；`-speed-300/400` = **24 fps**）。

### 判读

| 投递 fps | 在 60.9 Hz 上的 vsync/帧 | 观感 |
|---|---|---|
| **30** | 2.03（≈ 整数 2） | **近乎完美**（`jitterShare` ≈ 0） |
| **24** | **2.54**（半整数 ⇒ 最差） | **一顿一顿**（`jitterShare` ≈ 0.27） |

⇒ 「3x/4x 抖」**不是倍速本身**，而是**该档选的 `fps = 24` 恰好撞在 60 Hz 面板的最坏节奏上**。

### 反例 `bare@2x = 0.197 > app@2x = 0` 的解释（本档初稿的疑点，现已闭合）

- `app@2x`：走 FRC 代理（fps=30 档）⇒ 投递 30 fps ⇒ r = 2.03（近整数）⇒ 平滑 **0**。
- `bare@2x`：放**基础代理**（30 fps、无 FRC）+ 原生 `playbackRate=2` ⇒ 浏览器上屏 **50.2 fps** ⇒ r = 1.213（离整数远）⇒ 抖 **0.197**。
- ⇒ **帧更多 ≠ 更匀**；2x 处 FRC 反而**帮忙**（把投递锁到 30 fps ≈ 2×vsync）。`bare@4x` 投递 59.8 fps ≈ 刷新率 ⇒ r = 1.018 ⇒ 又平滑。

### 重要推论：这是**显示器相关**的

在 **120 Hz** 面板上：24 fps ⇒ 5.075（近整数 ⇒ 平滑）、30 fps ⇒ 4.0（完美）⇒ **3x/4x 抖动会消失**。
⇒ 本档不是「所有机器都抖」，**取决于刷新率**（修复判据须注明目标刷新率）。

### 诚实标注（两处异常）

1. **`673@4x` 的缓存代理实测是 30 fps**（违反「≥3x ⇒ 24」）⇒ 该采样实测 0.145 偏平滑。成因 = **代理文件名无编码版本键**（`<item_id>-speed-<n>.mp4`）且命中会刷新 mtime（`:4296-4299`）⇒ **旧编码设置下生成的陈旧代理被永久沿用** ⇒ **另立 BUG-291**。
2. `0.5x / 0.75x` 实测 jitter（0.12–0.17）高于模型预测（0.03）：其 `aheadMin` 仅 2.34 s（起播未稳）⇒ 判为**供数/预热噪声**，故剔噪后相关系数更高。
