# BUG-061: 引擎产物在仓库里有四处副本，构建不刷新「壳自己的那份」也无陈旧检测

- 状态: fixed
- 发现日期: 2026-09-19
- 模块: build
- 严重程度: critical

## 现象

同一个引擎二进制在仓库里存在**四处**副本，而 `cargo build --release` 只更新其中一处：

| # | 路径 | 谁在用 | 实测状态 |
|---|---|---|---|
| 1 | `download-engine/target/release/orig-tg.exe` | 验收脚本直接拉它 | 新（11952640 B） |
| 2 | `download-engine/target/release/orig-tg-x86_64-pc-windows-msvc.exe` | Tauri `externalBin` 读取源 | BUG-055 已同步 |
| 3 | `tauri-shell/src-tauri/target/debug/orig-tg.exe` | **`tauri dev` 启动的 app 实际跑它** | **9400832 B，冻结在 2026-09-16 21:30** |
| 4 | `tauri-shell/src-tauri/target/release/orig-tg.exe` | **打包壳实际跑它** | **同上，冻结** |

`tauri.conf.json` 的 `bundle.externalBin` 写的是不含目标三元组的
`../../download-engine/target/release/orig-tg`，Tauri 按平台追加三元组读取源码副本，
再**复制进壳自己的 target 目录**。该复制发生在**构建时**：只要用户直接启动已构建好的壳，
3)/4) 就是历史快照，`cargo build` 再多次也不影响它们。

后果是「开发者全绿 / 用户体感不变」被两份文件隔开。本轮用户报告的两个现象正是它的直接表现：

- **「内容没有正确进入视频内容介绍，剧集是正确的」** —— 用户进程里的引擎是 09-16 版，
  该版本的 `media_item` 表**没有 `description` 列**（BUG-054 才加的），条目介绍写不进去；
  而剧集侧 `media_series.description` 一直存在，所以「剧集是对的」。
- 相关的标题编辑/介绍编辑在用户侧表现为「改了没反应」，而验收脚本读到的是新二进制，
  于是全部通过 —— 两边用的根本不是同一个程序。

BUG-055 只处置了副本 2)，未覆盖 3)/4)，也没有把「陈旧」变成可见失败。

## 根因

侧车二进制的**权威来源**没有被声明，副本一旦生成就没有任何机制保证它与源码同步：

- 同步动作隐式依赖「Tauri 会在构建时复制」，而复制是**构建期一次性行为**；
- 没有任何地方比较「产物 mtime vs 引擎源码 mtime」，陈旧与否不可观测；
- 产物路径（含三元组后缀、壳 target 目录）分散在配置与构建系统里，人工难以穷举 ——
  这正是 BUG-055 只修了 1/3 的原因。

## 复现

1. 改任意 `.rs` 并 `cargo build --release -p orig-tg`；
2. `ls -la tauri-shell/src-tauri/target/debug/orig-tg.exe tauri-shell/src-tauri/target/release/orig-tg.exe`
   —— mtime 与体积**不变**；
3. 启动壳（dev 或已打包），它 spawn 的就是这两个旧文件；
4. 对新二进制跑的验收脚本全绿，对旧引擎的界面行为不变。

## 修复

已实施（工具层）：

- 新增 `scripts/sync-sidecars.sh`：把 cargo 产物同步到 2)3)4) 三处，并在
  **产物比引擎源码旧**时直接失败（陈旧必须响，不能静默）；`--check` 只校验不写盘；
  同步后内置 `cmp -s` 对账，2) 与 1) 不一致即 FAIL；
- 构建路径接入（两条入口都覆盖，无论怎么起都不会漏）：
  - `tauri-shell/src-tauri/tauri.conf.json` 的 `beforeDevCommand` / `beforeBuildCommand`
    改为 `npm run sidecars && ...`；
  - `tauri-shell/package.json` 增加 `npm run sidecars` / `tauri:dev` / `tauri:build`。

## 验收证据

- 同步后 `md5sum` 三处逐一对齐（脚本内置 `cmp -s` 对账，不一致即 FAIL）；
- 陈旧注入验证：`touch` 任一 `.rs` 后跑 `sh scripts/sync-sidecars.sh --check`，必须 FAIL
  并指名「产物比源码旧」的文件；
- 端到端：重启壳后 `GET /api/tg/diag` 的 `available:true 且 mock:false`，
  且条目编辑能写入 `description`（真实库读回非空）。
