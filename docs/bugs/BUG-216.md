# BUG-216 播放器 `timeupdate` 触发整棵控件树重渲染 —— 进度条/缓冲段/时间文案状态下沉到叶子组件

- 状态: fixed
- 发现日期: 2026-10-08
- 模块: shell
- 严重程度: mid

## 现象

应用内播放器（`VideoPlayer`）在 2x / 4x 倍速下上屏节拍弱于同页面的裸 `<video>`：同一素材
（媒体库条目 472 = HEVC 1280×720 **60fps** 11.8Mbps）、同渲染尺寸（1440×807）、都破缓存、
同一浏览器会话，`_probe_render_churn.cjs` 实测：

| 模式 | 倍速 | 上屏 fps | rVFC 间隔 p95 | 间隔 >25ms 的帧 | `timeupdate`/s | DOM 变更/s |
|---|---|---|---|---|---|---|
| 应用播放器 | 2x | 55.9 | 33.1ms | 42 | 3.8 | **24.5** |
| 裸 `<video>` | 2x | 59.2 | 17.1ms | 5 | 3.7 | 0 |
| 应用播放器 | 4x | 55.7 | 33.1ms | 38 | 3.8 | **32.6** |
| 裸 `<video>` | 4x | 58.8 | 17.1ms | 11 | 3.7 | 0 |

两侧 `timeupdate` 频率一致（3.7–3.8/s）⇒ 不是事件频率问题；差异在应用侧每秒多出 24.5–32.6 次
DOM 变更，代价约 4fps 上屏、约 8% 的帧多占一个垂直同步。

## 根因

进度条、已缓冲条、时间文案的状态是 `VideoPlayer` **顶层**的 state
（`tauri-shell/src/components/media/VideoPlayer.tsx` 原 `:144-146` / `:160`）：

- `onTimeUpdate`（原 `:416-421`）每个事件都 `setCurrentTime(v.currentTime)` 并 `readBuffered()`
  （原 `:409-414` → `setBuffered(...)`）；`progress` 同样写 `buffered`。
- 消费点在顶层渲染：`shownSec/playedPct/bufferedPct`（原 `:525-527`）、进度条与已缓冲条
  （原 `:759` / `:773`）、时间文案（原 `:879`）。

于是**每次 `timeupdate` 都重渲染整个 `VideoPlayer`**，而它带着一棵很大的子树（控制行、
8 项倍速菜单、音量、全屏 / PiP 等）。实测该重渲染在 DOM 上表现为每事件约 6 次属性写入
（2x：226 属性 + 19 文本 / 38 事件）。

## 复现

```sh
cd tauri-shell
node verify/_probe_render_churn.cjs
```

脚本用 `verify/lib/cdp.cjs` 起**一个** headful 浏览器，在同一 page 上先后测量
`[data-testid="media-viewer"] video`（应用播放器）与注入的裸 `<video>`，各跑 2x / 4x，
每次破缓存（`?rc=<ts>`）、`Page.bringToFront` 保活、启动参数关掉后台节流；
输出 `presented / gapP50/p95/max / gt25 / timeupdate/s / mutations/s / mutKinds / longtasks`。

## 修复

把「随媒体时间推进」的 UI 从顶层拆出去，父组件不再因时间推进而重渲染：

1. **时间文案** 抽成叶子组件 `PlayerTimeText`（`VideoPlayer.tsx`），只持有 `currentTime` /
   `duration`。文案每秒才变一次，与 React 的 characterData 写入本就等频，无需再降到 DOM 层。
2. **进度条 + 已缓冲条** 抽成叶子组件 `PlayerProgressBar`，时间推进**完全不经 React state**：
   `timeupdate` / `progress` / `seeked` 触发的是「墙钟节流 + 变化才写」的 DOM 直写
   （`playedRef.style.width` / `bufferedRef.style.width` / `setAttribute('aria-valuenow')`）。
   节流常量：播放段 `BAR_WRITE_MS=700`、aria `ARIA_WRITE_MS=5000`、
   已缓冲段 `BUFFERED_WRITE_MS=1500` 且变化 ≥ `BUFFERED_DELTA_PCT=2%`。
3. **拖拽语义（BUG-165）逐字保留**：按下 / 移动只更新 `dragRatioRef`（视觉位置，条面即时
   跟手，**不写 `currentTime`**），只有 `pointerup` 才提交唯一一次 `seekToRatio`。
   `skip()` 写 `currentTime` 后由 `seeked` 事件即时刷新条面（父组件只保留一个
   `durationRef` 作兜底，不再持有时间 state）。
4. **不删任何能力（BUG-149）**：倍速菜单、音量、静音、全屏、PiP、快进 / 快退、进度条
   aria（`role=slider` + `aria-valuemin/valuemax/valuenow` + `aria-label`）全部保留；
   `useDecodeHealth` 的调用方式与判据未改（BUG-034 / 207 / 208 / 212 不受影响）。

**被否决的写法（如实登记）**：先把 DOM 直写合并进 `requestAnimationFrame`（每帧最多写一次）
再降频。实测**反而打坏上屏节拍** —— 同条件下 app@2x 从 presented 55.7 掉到 51.5、
`gt25` 从 42 涨到 84（3 次复测一致）。原因是 rAF 回调与视频呈现同帧竞争，回调里的样式写入
会推迟该帧合成。故改为在事件回调里**同步写、靠墙钟节流降频**（见 `write()` 上方注释）。

## 关联

- BUG-149：播放器能力不可删（倍速 / 音量 / 全屏 / PiP / 快进退 / aria）。

**如实声明未达标项**：本档只消除了「整树重渲染」这一项，**上屏节拍三项判据未达标**——
`presented` 55.7 / 54.6（要求 ≥58）、`gapP95` 33.2ms（要求 ≤20ms）、`gt25` 37 / 45（要求 ≤15）。
且**修复前的基线同样不达标**（55.9 / 55.7、33.1、42 / 38）⇒ 该节拍缺口**不是** `timeupdate`
重渲染造成的。已做的定位（见下「二次观察」）显示缺口主要不在控件层。

**反向证伪（同条件 A/B）**：用 `git stash` 回到修改前、在同一时段重跑一次基线
（app 2x 55.7 / gt25 42 / mutations 25.2；app 4x 54.6 / gt25 42 / mutations 31.8），
再 `git stash pop` 还原；前后 `sha256` 一致、`git status` 一致 —— 证明「改前 mutations 高、
改后低」，而非只看改后数字。

**回归验证（真实 UI 交互）**：`tauri-shell/verify/verify_bug216_timeline.cjs`，9/9 PASS、exit 0：
拖拽期间 `currentTime` 停在原位（0.00，未提交 seek，BUG-165）、松手后跳到 744.96s
（= 60% × 1241.6s）、拖拽中条面跟手（played 宽度 35%、`aria-valuenow=434`）、倍速菜单 8 档且
点 4x 后 `playbackRate=4`、播放/暂停按钮翻转 `paused`、时间文案随播放推进、无未捕获异常。

**二次观察（已定位部分，未修）**：把控件层 `[role="toolbar"]` 临时 `display:none` 后，
app@2x 的 `gt25` 仅从 37 降到 26、presented 从 55.4 升到 55.9，离裸 `<video>` 的 5–6 / 59 仍远
⇒ 应用播放器与裸 `<video>` 的节拍差主要**不在**控件层，也不在重渲染，而更可能在两者不同的
合成上下文（`<video>` 所处的容器 / 叠加层决定是否走视频直通路径）。该差异使
`app vs bare` 作为节拍对照本身带系统性偏差，需要单独立项，不在本档范围。
