# BUG-023: TG 连接失败静默退化为 dummy —— 登录态/发码/client id 全体「消失」，且端口冲突直接 panic

- 状态: fixed
- 发现日期: 2026-09-17
- 修复日期: 2026-09-17
- 模块: engine+shell
- 严重程度: critical

## 现象

用户报告「大量核心回退错误（流程规则侧）」：

1. 登录丢失（面板显示未登录，`/api/tg/session` 为 Anonymous）
2. 验证码发送无效（`/api/tg/start` 无有效响应）
3. TG client id 丢失（`/api/tg/diag` 显示 `api_configured=true` 但实际不可用）

三者在同一时间点同时出现，且**界面上没有任何错误提示**。

## 根因

`crates/orig-tg/src/main.rs:18-28` 的 `build_client`：只要配置了 `api_id/api_hash`，
但 `GrammersClient::connect` 返回任何 `Err`，就**静默回退到内存 DummyClient**，并把
`api_mode` 写成 `"dummy"`：

```rust
match GrammersClient::connect(config).await {
    Ok(c) => return (Arc::new(c), "real"),
    Err(e) => eprintln!("[warn] grammers connect failed ({e}); falling back to dummy client"),
}
...
(Arc::new(dummy::DummyClient::default()), "dummy")   // <- 仍然照常 bind 并对外服务
```

回退后的 dummy 实例**照常监听 9877 并对外提供服务**，于是前端拿到的是一个
「能连上、但没登录、也发不出验证码」的服务——三个症状全部由此产生。

叠加两个放大因素：

1. **错误无处可见**：`main.rs:1` 声明 `#![windows_subsystem = "windows"]`，进程无控制台，
   `eprintln!` 全部丢弃（实测 stderr 日志为空）。前端与服务端都不暴露降级状态。
2. **端口冲突直接 panic**：`main.rs:94` `TcpListener::bind(addr).await.unwrap()`，
   端口被占（AddrInUse 10048）时 panic 退出，同样静默。
   且 `main.rs:92` 的 "orig-tg listening on ..." 打印在 bind **之前**，极具误导性。

### 结构性成因（比单点 bug 更重要）

`api_mode: &'static str` 是个**纯展示标签**：全仓检索确认它只被两处消费——
`routes.rs` 回显进 diag JSON、`AccountsPanel.tsx` 渲染一行文字，
**没有任何代码据它分支**。也就是说系统"知道"自己已经降级，行为上却不因此改变。
再叠加前端 `useStore.ts` 的

```ts
catch {
  // 服务不可达时无法确认登录，视为未绑定
  if (get().accounts.tg.bound) get().setTgAccount({ bound: false, phone: null })
}
```

把「够不到服务」直接坍缩成「未绑定」，形成三段静默坍缩链：
**后端降级 → 标签不可见 → 前端读成未登录**，用户看到的只有「登录没了」。

### 实测证据（2026-09-17）

```
INFO grammers_mtproto::mtp::encrypted: got bad salt; salts have been reset down to a single one
INFO grammers_mtsender::sender: incorrect server salt; re-sending request MsgId(...)
[warn] grammers connect failed (session error); falling back to dummy client
orig-tg listening on http://127.0.0.1:9877
thread 'main' panicked at crates\orig-tg\src\main.rs:94:62:
called `Result::unwrap()` on an `Err` value: Os { code: 10048, kind: AddrInUse, ... }
[warn] grammers connect failed (network: SQLite failure: `database is locked`); falling back to dummy client
```

`git log` 追溯：dummy 起始于 `9aac588 feat(engine): scaffold orig-tg sidecar service`
（"in-memory dummy client with unit tests. Reserved for grammers MTProto real implementation"），
即**骨架期尚无真实实现时的合法测试替身**。它本身没有问题，
问题在于真实实现落地后它**没有退役**，反而留在了生产决策路径上。

## 复现

**A. 症状复现（dummy 混淆）**：让 9877 上跑一个 dummy 实例（无凭证），
`/api/tg/session` → Anonymous、`/api/tg/diag` → `api_mode:"dummy"`，
前端表现与用户报告完全一致（登录丢失 / 发码无效 / client id 缺失）。

**B. 静默降级复现**：在 TG 网络不可达（代理抖动）时启动带凭证的实例，
进程不报错、照常监听，仅 `/api/tg/diag` 的 `api_mode` 悄悄变成 `dummy`。

```bash
curl -s http://127.0.0.1:9877/api/tg/diag   # api_mode=dummy 即为降级
curl -s http://127.0.0.1:9877/api/tg/session # phase=Anonymous
```

## 修复

**原则：让「连接失败却对外服务」这个状态不可表达。** TG 只有**可用 / 不可用**两态，
不存在「假装可用」的第三态；合成数据只允许存在于测试构建。

1. **类型层面消除第三态**（`state.rs`）：删除 `api_mode: &'static str`，
   改为 `enum Availability { Ready, Unavailable(String) }` —— 不可用必须携带原因，
   且以类型而非字符串约定表达，无法被"忘记检查"。
2. **生产禁止静默回退 + 无假数据**（`main.rs`）：`build_client` 只有两种结局——
   真实客户端就绪，或挂载新增的 `unavailable.rs::UnavailableClient`。
   后者是**说真话的空对象**：每个能力都返回 `ClientError::Unavailable(原因)`
   （映射 503），与旧 `DummyClient`（返回合成数据「说谎」）形成明确对照。
3. **不再 panic 且日志不再误导**（`main.rs`）：`bind` 显式处理失败，
   非零退出码 `3`；`"listening on ..."` 移到 bind **成功之后**。
4. **故障外显**（`routes.rs`）：`ensure_available/ensure_authorized` **先判可用性再判登录阶段**
   ——顺序反了会把「服务故障」伪装成「401 未登录」。
   `/api/tg/diag` 与 `/api/tg/session` 下发 `available` + 原因，
   `api_mode` 字段移除（避免继续用展示标签代替行为约束）。
4b. **桌面壳同步改造**（`tauri-shell/src-tauri/src/lib.rs`）：壳的 `tg_service_real()`
   用**裸 HTTP 字符串匹配** `"api_mode":"real"` 判断 sidecar 是否可用 ——
   字段移除后该函数会永久返回 `false`，导致壳把健康的真实实例判为「无效」
   反复杀掉重拉、且 spawn 8s 超时（比原缺陷更严重）。
   已改为读新契约：`available == true` **且 `mock != true`** 才视为有效实例。
   —— 教训：移除一个字段前，必须扫**所有消费方**；跨语言（Rust 壳 + HTTP 字符串匹配）
   的消费方不会被 `grep <字段名>` 在业务代码里找到，必须连同 **HTTP 响应解析点**一起搜。
5. **mock 逐出生产**（`Cargo.toml` + `mock.rs`）：`dummy.rs` 更名 `mock.rs`，
   用 `#[cfg(feature = "mock")]` 编译排除，生产二进制**物理上不含合成实现**；
   启用还需 `ORIG_TG_MOCK=1` 且**必须显式 `ORIG_TG_DB`**（否则退出码 `4`），
   杜绝合成频道/消息污染真实 `tg_store.db`。
   验收用独立 target 目录构建（`CARGO_TARGET_DIR=target-mock`），
   绝不覆盖生产 sidecar 路径上的二进制。
6. **前端不再把故障读成未登录**（`types.ts` / `useStore.ts` / `AccountsPanel` / `TgPanel`）：
   新增三态 `TgAvailability`（`ok` / `unavailable(原因)` / `unreachable`）。
   `unavailable`/`unreachable` 时**保留**上次绑定态（「不知道」≠「没登录」），
   TG 面板与账号页显式展示「Telegram 不可用 + 原因」，并禁用登录入口。
   故障时不再发起必然 503 的拉取，避免刷无谓错误。

## 验证

`verify_shots/run_availability_verify.sh`（隔离端口 9881-9883，不碰 9877）：

| 场景 | 断言 |
|---|---|
| S1 生产二进制 + 无凭证 | 23/23：diag/session `available=false` + 原因；**6 个 TG 端点全部 503 且原因可读，且不是「not authorized」伪装**；媒体资料库不受影响 |
| S2 生产二进制 + 有凭证但连不上 | 23/23：原因 `MTProto connect failed: ...`，**仍然 503 而非静默可用的假服务**（核心回归点） |
| S3 mock 构建 + 显式开关/隔离库 | 11/11：`available=true` 且 **`mock=true` 自报家门**；登录/监控/缓存链路夹具完好 |
| S4 mock 构建 + 未指定隔离库 | 退出码 4，拒启动 |

单元测试：`unavailable::tests::every_capability_fails_honestly`（10 个能力逐一断言必须失败，
不允许任何一个悄悄返回 `Ok`）、`view_is_anonymous_sentinel`。

生产二进制内容取证：`grep -a` 检索 `Mock Channel`/`ORIG_TG_MOCK`/`SYNTHETIC` 均为 **0** 次，
而 `telegram unavailable` 等诚实错误串存在 —— 合成实现确实不在生产构建里。

UI 证据：`verify_shots/run_unavailable_ui.sh` 11/11，截图见
`verify_shots/tg_unavailable/`（TG 面板「Telegram 不可用 + 原因」、账号页故障横幅、
登录入口禁用、诊断显示「不可用」而非「占位」）。

同时修复了本次暴露的**测试可靠性**问题：`run_cache_task_verify.sh` 原先依赖
`rm -rf $TMP` 清库，而本机 safe-delete 守卫会拦截目录删除（FAIL_CLOSED），
导致上一轮的「无 groupId 任务」残留、污染计数断言——**该套件此前只在手工清过的目录上通过**。
改为每轮唯一库名 + `t.get("groupId")`，现已可重复运行（33/33 连续通过）。

## 关联

- BUG-012（显示已登录但实际会话失效）—— 同一类「对外状态与真实状态不一致」缺陷
- BUG-016（api_id/api_hash 丢失，凭证仅存活于进程内存）
- BUG-024（缓存状态丢失）—— 二者共同点：状态放在了不该在的地方（前者在假客户端里说谎，后者在浏览器内存里）
- BUG-025（`/api/tg/code` 在未登录时回「已授权」）—— 同类「静默说谎」缺陷，由本次验收发现
- **防再发（流程侧）**：验证 TG 相关功能时**严禁在生产端口 9877 上启动 mock 实例**
  （会真实顶掉用户登录态，制造出与本文档一模一样的症状）。
  前端已支持 `VITE_TG_PORT` 覆写，合成验证必须跑在独立端口 + 独立库，
  再让 Vite 指向该端口，与生产实例物理隔离。
- **防再发（结构侧）**：任何「失败后换个对象继续跑」的兜底都必须自问：
  换上的对象**会不会说谎**？会的话就不是兜底，而是把故障藏起来。
  诚实做法是空对象 + 显式错误，或直接失败。

### 门控层级修正（2026-09-17 用户裁定，二轮评审）

面板级故障卡只是**保底回退**；常规探测应该在**入口层**就把 TG 摘掉：

- `MainLayout` 统一计算 `tgFeatureReady = tgEnabled && (探测 ok 或未返回)`，
  挂载与开关变化时探测（开启侧最多重试 5 次，等 daemon 拉起 orig-tg）；
- `Sidebar`：TG 导航 = `tgBound && tgReady`——开关关或不可用时**即使已绑定也不显示**；
- `AccountsPanel`：TG 绑定卡同门控整体不渲染，仅保留「连接诊断」面板（唯一能看原因的地方）；
- TG 视图被摘除时用户自动送回下载页；`TgPanel` 故障卡保留为兜底（正常路径不可达）。
- 验收：`verify_shots/run_unavailable_ui.sh`（入口摘除 10/10，截图肉眼复核）+
  `run_cache_ui_verify.sh`（mock 可用时导航正常出现 11/11，证明不过度摘除）。
