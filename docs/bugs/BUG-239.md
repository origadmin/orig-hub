# BUG-239: 进入媒体库请求成倍放大 —— `stats`/`diag` 各发 4 次、`tags`/`series` 各 2 次，且封面抽帧按缺封面条目数线性发 `items/{id}/raw`；切走再回必重发

- 状态: fixed
- 发现日期: 2026-10-09
- 模块: shell
- 严重程度: mid
- 登记: 用户报告「**请求爆炸问题**：进入媒体库请求了 **42 个**，而且大量重复问题数据」
  （后半句另行建档，见 BUG-240）

## 现象

进入媒体库（媒体域）后，浏览器 Network 面板出现远超必要的请求，且**同一份数据被重复拉取**。
实测（首次进入，8 秒窗口，`tauri-shell/verify/_probe_libstorm.cjs`）：

| 端点 | 实测次数 | 应有次数 |
|---|---|---|
| `/api/media/stats` | **4** | 1 |
| `/api/tg/diag` | **4** | 1 |
| `/api/media/tags` | **2** | 1 |
| `/api/media/series` | **2** | 1 |
| `/api/media/items/{id}/raw` | 随「缺封面条目数」线性增长 | 0（或 1 次批量） |

对照：reload 后再进入 = 28 张剧集卡、媒体域 11 个请求；**切走再回（`nav-tg` → `nav-media`）
必重发同一套**（实测 4×`stats` + 4×`diag`）—— 不是「首屏一次性」，而是**每次进入都重发**。

## 根因（五条，均为代码事实）

**1. 同一个探活函数在一处 effect 里被调用两次**
`tauri-shell/src/components/MediaLibraryPanel.tsx:95` 的 `probeLibrary` 内部，`:97` 与 `:108`
各调一次 `probeLibraryBackend()`；后者定义在
`tauri-shell/src/lib/mediaSources.ts:124`，其函数体 `:126` 直接 `await getLibraryStats()`
⇒ 单次 `probeLibrary` 就发 **2 次** `/api/media/stats`。

**2. `fetchCache` 只覆盖了 4 个消费者里的 1 个**
`tauri-shell/src/components/MediaLibraryPanel.tsx:200-206` 的 `Promise.all`：

```ts
const [s, tg, sr] = await Promise.all([
  getLibraryStats(),                                          // :202 ← 未包 cached()
  listTags(),                                                 // :203 ← 未包 cached()
  cached(cacheKey.seriesList(null), () => listSeries()),      // :204 ← 唯一走了缓存
])
```

`tauri-shell/src/lib/fetchCache.ts:2-16` 的模块注释写明了它要解决的**正是本现象**
（「同一部剧集的详情由三个消费者各拉一遍……含 React 严格模式下 effect 双调用的 2 次」，
规则 1 = **在途合并**：同 key 并发调用共享同一个 Promise）。
但 `getLibraryStats()` / `listTags()` **绕过 `cached()` 直接调用**，规则 1、2 对它们完全失效。

**3. `React.StrictMode` 在 dev 下双调 effect**
`tauri-shell/src/main.tsx:14` 的 `<React.StrictMode>` 使所有 effect 在开发模式执行两次。
**这一条本身不是缺陷**（生产构建不双调），但它把第 1、2 条的放大**再翻一倍**，
也解释了「已走 `cached()` 的 `series` 仍实测 2 次」。

**4. `probeRecacheBackends` 的 effect 依赖 `alive`，会重跑**
`MediaLibraryPanel.tsx:124-132`：`useEffect(..., [alive])` ⇒ `alive` 变化即重跑
`probeRecacheBackends()`（`lib/mediaSources.ts:167`），其内部 `:69` 又发一次 `tgDiag()`。

**5. 封面抽帧是「按条目」的 N+1**
视频条目无封面时，卡片各自抽帧取封面：
- `tauri-shell/src/components/media/SeriesCard.tsx:44`（剧集墙；实测 28 部剧里 4 部 `poster=null`）
- `tauri-shell/src/components/media/MediaCard.tsx:160`（「全部内容」网格，**最多 120 张卡各发一次**）
- 抽帧实现 `tauri-shell/src/lib/poster.ts:81` `generateVideoPoster`，内部 seek 再发一次
  ⇒ 每个缺封面条目 **2 个** `items/{id}/raw`

> 规则依据（本仓既有约定）：`docs/bugs/BUG-232.md:30`「**不在渲染期发起请求**（请求风暴规则）」。
> 第 5 条正是渲染期按条目发请求；第 1~4 条是同一份数据被当成多份。

## 复现

```bash
# 前置：dev 栈在线（daemon 127.0.0.1:19786 / orig-tg 127.0.0.1:19787 / vite 127.0.0.1:5180）
node tauri-shell/verify/_probe_libstorm.cjs        # 请求总数 + 按端点分组
node tauri-shell/verify/_probe_libstorm_p1.cjs     # 首次进入（8s 窗口）
node tauri-shell/verify/_probe_libstorm_p3.cjs     # 切走再回（对照「每次进入都重发」）
```

脚本用 CDP Network domain 全量抓取；上表的数字即脚本一次运行的输出（可复跑复现）。

## 修复方向（已实施）

1. `MediaLibraryPanel.tsx:202/:203` 的两个调用改走 `cached(...)`（与 `:204` 一致），
   复用既有 `fetchCache` 的在途合并与结果缓存；
2. `probeLibrary` 内的两次 `probeLibraryBackend()` 收敛为一次（或让 `probeLibraryBackend`
   自身走 `cached()`）；
3. `MediaCard` / `SeriesCard` 的封面抽帧改为**受控并发**：**可见性门控**（进入视口才抽、
   离开即撤销未启动的排队）+ **队列上限**（超出丢弃并计数）+ **播放让路**（播放器挂载期间
   暂停启动）+ **按条目去重**（在途合并 + 会话内结果复用）。抽帧预算集中在
   `tauri-shell/src/lib/poster.ts` 一处，调用方只声明「我要这条的封面」；
4. `probeRecacheBackends` 的 effect 依赖收敛（`alive` 变化不应重发 `tgDiag`）。

> 判据 3 原文「改批量后应为 O(1) 批次数」是修复前预设的**实现方向**；实际采用
> 「可见性门控 + 预算队列」，故达成的**实质**是「首屏 raw 去重条目数 ≤ 可见候选数」，
> 而非严格 O(1) 批次数。判据的实质（不随缺封面条目数线性增长）由下方验收证据 A1/A2 承担。

## 修复后必须满足（可证伪判据，预先声明）

1. 首次进入媒体库：`/api/media/stats`、`/api/tg/diag`、`/api/media/tags`、`/api/media/series`
   各**恰好 1 次**（dev 构建下也成立 —— 即 `cached()` 的在途合并生效，而不是靠关掉 StrictMode）；
2. 切走再回媒体库：上述 4 个端点**总请求数为 0**（结果缓存命中）；
3. 首屏 `/api/media/items/{id}/raw` 请求数**不随缺封面条目数线性增长**（改批量后应为 O(1) 批次数）；
4. 反向证伪：把判据 1 对应的改动还原为直接调用 `getLibraryStats()`，判据 1 必须重新 FAIL。

## 验收证据

环境：dev 栈（daemon 127.0.0.1:19786 / orig-tg 端口取 `tg_port` 真源 / vite 127.0.0.1:5180）。

**A. 请求放大（判据 1、2）**——`tauri-shell/verify/_probe_libstorm.cjs`（CDP 全量抓包）：

- 首次进入媒体库 P1：`all=4 TG=4`，即 `/api/media/stats` **1×**、`/api/tg/diag` **1×**、
  `/api/media/tags` **1×**、`/api/media/series` **1×**（各**恰好 1 次**，判据 1 满足）；
- `nav-tg` → `nav-media` 切走再回 P3：`all=0 TG=0`（上述 4 端点**总请求数 0**，判据 2 满足）。

**B. 封面抽帧预算（判据 3）**——`tauri-shell/verify/verify_bug_239_cover_frame_budget.cjs`
（自造 80 条「有字节、无封面」夹具，跑完按标题前缀精确扫除，绝不碰用户既有条目）：

- 正常态 **8/8 PASS**（退出码 0）：首屏「挂载候选 81 / 可见候选 42，落差 39」，被请求 raw 的
  条目**全部落在可见集合内**（A1）、去重 raw 条目数 **30 < 挂载候选 81**（A2）、无字节候选
  **从未被请求**（D1）、抽帧预算读数 `stats.pending ≤ 10` 且 `stats.dropped=27`
  （队列上限确实咬合，E）、滚动后新增 raw 全在「曾可见」集合内（B1）、播放器 5s 窗口
  raw 增量 0（C1）；
- **反向验牙**`BUG239_TEETH=1`：注入「永远报 intersecting」的 IntersectionObserver 替身
  ＝关掉可见性门控 ⇒ **A1 FAIL**（屏外条目被请求）与 **B1 FAIL**（越界条目被请求），
  退出码 2 —— 证明判据确实在测可见性门控，而非恒真。
  替身只注入浏览器页面，**未改任何源码**（`tauri-shell/src` 无相关改动即还原）。

**C. 播放卡顿（用户复报）**：网格仍挂载（40 条无封面候选在队列）并打开播放器后
（播放让路门置位，读数 `paused=true, active=0`），10s 窗口 `currentTime` 推进
**9.98s / 10.0s = 0.998×**（修复前实测 **0.72×**），`presentedFps 29.8`、
`decodedFps 29.9`、丢帧 0%、longtask 0、`srcChanged=false`。

**未独立复跑**：判据 4（把 stats 改动还原 → 判据 1 FAIL）本轮只做了正测（P1/P3），
未做该反向证伪，如实登记（不阻塞本条 `fixed`——缺陷本体已由 A/B/C 正测覆盖）。
