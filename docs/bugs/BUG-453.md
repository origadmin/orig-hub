# BUG-453: dev 与 release 互相干扰、无统一控制脚本，dev 进程每次构建都被杀

- 状态: fixed
- 发现日期: 2026-10-27
- 模块: shell
- 严重程度: high

## 现象

1. 改引擎后要更新 dev 栈，但 `scripts/dev/dev_stack.py build` 内部第一步就是 `do_stop()`，
   把正在跑的 daemon+orig-tg 全部杀掉，再 `cargo build`、再 `sync-sidecars`、再 `start`。
   → 用户体感「dev 进程总是被杀」，且每次只能停了再建，无法热更新。
2. dev 与 release 的入口分散：`dev_services.py`（release daemon 1986 路径）、`dev_stack.py`
   （dev 29786 路径）、`tauri build`（release app）三套各自为政，没有「一行命令管所有」。
3. 编译 release 时 `sync-sidecars.sh` 会重写 `tauri-shell/src-tauri/target/{debug,release}/orig-*.exe`，
   若 release app 正从那里运行，复制即失败；且 dev 若也曾用这些目录，就会被动受影响。

## 根因

dev daemon 的运行二进制就是 `cargo build` 的**输出文件本身**：
`dev_services.DAEMON_EXE = download-engine/target/release/orig-daemon.exe`。
Windows 下运行中的 `.exe` 被文件锁占住，`cargo build` 链接该文件会直接 `Access is denied`，
`sync-sidecars.sh` 的 `cp -f` 也会失败 ⇒ 构建前必须先停 dev。这是「构建必杀 dev」的硬约束。

运行态已做端口/端点/任务库分离（dev 29786 + `daemon.dev.endpoint` +
`engine_tasks.dev.db`）；会话与 release 共用真实 `session.session`（dev 不另起隔离会话，
否则 dev orig-tg 永远是 Anonymous、面板永久「未绑定」）。但**二进制副本未分离**，
所以物理隔离只完成了一半。

## 复现

- `python scripts/dev/dev_stack.py start` → daemon 跑在 `download-engine/target/release/orig-daemon.exe`
- 改 `orig-tg` 源码 → `python scripts/dev/dev_stack.py build` → 日志第一行就是 `停止 dev 进程`，
  daemon 被 `taskkill /T /F` 杀掉。

## 修复

1. **dev 运行二进制搬出 cargo 输出目录**：新增 `download-engine/target/dev-stack/`，
   `dev_stack.py` 增加 `ensure_dev_bins()` 把 `target/release` 的 engine exe 复制进去；
   `do_start` 之前把 `dev_services.DAEMON_EXE` 重定向到该副本。daemon 从副本目录启动后，
   会自动从该目录 `current_exe().parent()` 拉起 orig-tg（`state.rs:tg_binary_path`）⇒ 自洽。
   `cargo build` 只写 `target/release`，不再触碰运行中的 dev 进程。
2. **热更新代替全杀**：`dev build` 改为「`cargo build` → 复制新 exe 进 `dev-stack` →
   若 daemon 在线则只 `taskkill` 其 orig-tg 子进程（端口 29787），daemon 的 `tg_supervise`
   自愈重启并拾取新 orig-tg；仅当 daemon 本体二进制变更（极少见）才重启 dev daemon」。
   正常一次 `dev build` 不再杀任何 dev 进程。
3. **统一入口 `scripts/hub.py`**：同一脚本同时管 `dev` 与 `release` 两套世界，二者端口/数据根/
   二进制/端点/任务库/会话/日志全部互不相关；`release build` 编 release app 时只停它自己的
   副本（release app），绝不碰 dev（29786）。`hub.cmd` 为 ASCII 启动器。

## 关联

- BUG-446（open）：release 壳打开即 Application Hang——release 真正可用前需先解此条；本 BUG 只解决
  「可被脚本可靠编出 release」与「dev 不再被构建杀死」，不修复 release 启动卡死本身。
- 既有分离设施（端口 29786、端点/任务库/会话 env）见 `dev_stack.py::dev_runtime_env`，本 BUG 复用之。

## 验收证据

- **根因现场坐实**：`Get-Process` 显示 dev daemon 原进程路径为
  `download-engine/target/release/orig-daemon.exe`（cargo 输出目录），即「构建必锁死→必停 dev」的祸根。
- **迁移后**：`dev restart` 后 dev daemon/orig-tg 进程路径均为
  `download-engine/target/dev-stack/*.exe`，与 cargo 输出目录物理分离。
- **dev build 实测（关键验收）**：`cargo build --release -p orig-daemon -p orig-tg` 真实重编（2m22s），
  构建期间 release 世界 `19786/19787`（pid 34956/11924）**始终未受影响**；dev 因本次 daemon 本体源码
  比产物新，触发唯一一次整段重启（18280→26232，新 dev-stack 副本），orig-tg 热更新至 5536。
  即：改 orig-tg/前端场景 daemon 完全不重启，仅 daemon 本体变更才整段重启（物理上不可避免）。
- **统一入口**：`python scripts/hub.py dev ...` / `python scripts/hub.py release ...` 两套世界端口/数据根/
  二进制/端点/任务库/会话/日志全隔离；`release build` 只停它自己的世界（19786），绝不碰 dev（29786）。
- 路径证据：`scripts/hub.py`、`scripts/hub.cmd`、`scripts/dev/dev_stack.py`（dev-stack 副本隔离 + 热更新）。
