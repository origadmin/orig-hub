# BUG-273: 播放卡顿（再报）：段级「读写入」串行只存在于**转码代理的增长 `.part`** —— 响应止于请求当刻的 EOF（`total = meta.len()`），且转码泵与响应之间只有 **32 槽**管道（`resp_tx.send().await`）⇒ 产出被播放消费节流，每个分片边界都要等下一片

- 状态: open
- 发现日期: 2026-10-10
- 模块: engine
- 严重程度: high

> 来源：用户报告「**卡顿问题依然没有很好解决，当前播放有缓存读取写入问题，当前缓存播放完才会进行下一段缓存，
> 这就造成了每个缓存点会卡顿。**」
>
> **本档为任务文档**（用户 2026-10-10 定：后续一律纯文档任务，代码由别的组负责）。

## 现象（用户原话拆解）

| 用户措辞 | 拆出的可验证命题 |
|---|---|
| 「当前播放有**缓存读取写入**问题」 | 播放的**读**与缓存的**写**之间存在串行/争用 |
| 「当前缓存**播放完**才会进行**下一段缓存**」 | 取下一段的动作，被「当前段被消费完」**门控** |
| 「**每个缓存点**会卡顿」 | 停顿发生在**分段边界**，且**每个边界都发生** |

⇒ 这是一个**段级串行化**指控。本档的任务是：**它在代码里成立在哪一条路径上**。

**结论：唯一同时贴合「当前段播完才产出下一段」的结构是 D2 + D3（`/stream` 冷缓存路径）。**
A / B / C / D1 四条**全部不成立**。

## 根因 1（段级）：转码产出被播放消费**节流** + 响应止于**写入前沿**

### 1.1 产出被消费节流（`resp_tx.send().await` 的 32 槽背压）

`download-engine/crates/orig-tg/src/routes.rs`：

```rust
:3922  let (resp_tx, resp_rx) =
:3923      tokio::sync::mpsc::channel::<Result<axum::body::Bytes, std::io::Error>>(32);
:3924  tokio::spawn(transcode_pump(ffmpeg, src, part_p, final_p, key, …));
...
:4109      let mut buf = vec![0u8; 256 * 1024];
...
:4139      if !client_gone
:4140          && resp_tx
:4141              .send(Ok(axum::body::Bytes::copy_from_slice(&buf[..n])))
:4142              .await            // ← 32 槽满即阻塞
```

`transcode_pump` 把 ffmpeg stdout **双写**（一份进响应通道、一份落 `.part`），
但**两者共用同一个循环**：一旦响应通道满（客户端没在消费），`send().await` **阻塞整个泵**
⇒ **转码与落盘一起停**。

⇒ 这不是「限速」，而是**结构性正反馈**：
**播放等生产**（前沿不够就读不到），**生产等播放**（通道满就写不动）。
只要**转码速率 ≤ 播放消费速率**，前沿就**永远贴在播放头上**，于是**每个分片边界都必须等下一片**。

`routes.rs:4005` 的 ffmpeg 参数里**没有 `-re`**（不是人为限速到实时）⇒ 转码快于实时时不会 stall；
**慢于实时时（高码率 / 倍速 / 慢 CPU）必然在每个产出边界 stall**。倍速是重灾区：
倍速变体 `-speed-<百分之一倍速>.mp4`（`routes.rs:3796-3799`）要求 ffmpeg 产出**更快的时间轴**，成本更高。

### 1.2 响应止于「请求那一刻」的 EOF

`serve_local_file` 对增长中的 `.part` 服务时：

```rust
:4368  let total = meta.len();                              // ← 请求当刻的长度
:4390  let e = if open {
:4391      (s + OPEN_CHUNK - 1).min(total - 1)              // ← 封顶在当下 EOF
...
:4473      format!("bytes {start}-{end}/{total}")            // ← Content-Range 如实报当下长度
```

⇒ **响应在当下 EOF 处结束**，客户端**必须再发一次 Range** 才能拿到后面的字节。
`routes.rs:3896-3898` 的注释自述了这个设计（「浏览器缺多少再要多少」），
它的**初衷**是对的（4x 暂停后再播不必等整片转完），但**代价**就是：**每追平一次写入前沿 = 一处「缓存点」停顿**。

⇒ 1.1 与 1.2 **叠加**：1.1 让前沿永远贴着播放头，1.2 让每次追平均为一次新的请求往返。
**这正是用户描述的「每个缓存点会卡顿」。**

## 根因 2（条目级）：缓存 worker **全局单飞** —— 但这是**已裁定的设计**，本档不推翻

`routes.rs:2124` 任务内**逐条**串行：

```rust
:2124  for msg_id in task.message_ids.iter().copied() {
```

且 `spawn_cache_task`（`routes.rs:1425`）的注释明写：

```
/// 启动后台缓存 worker：**全局单飞**——同一时刻至多一个 worker 协程在跑，
/// 跑完当前任务后按 FIFO 接续最老的 `queued` 任务，直到队列清空。
///
/// 设计裁定（用户）：不论多少缓存在排队，`task` 端点只呈现**一个**当前任务；
/// 与之配套，执行侧也必须是单飞——否则多 worker 并发写进度会把「1s 一次」
/// 的节拍打碎成「1s 多次状态变化」。
```

⇒ **这是用户已拍板的设计**（与 BUG-027 的「后端（单飞 + 顺序队列 + 单结果契约）」一致，
`BUG-027.md:26-27`、`:58`；`BUG-028.md:84-85` 明确「单飞/队列语义不变」）。

**本档不主张推翻它**，只如实登记它的**可感知后果**：
「下一条缓存必须等上一条缓存完成」——若用户看的是**剧集连续多集**，
那么「播放完当前集才轮到缓存下一集」在**队列语义**上确实成立（条目级，非段级）。
**是否要为此引入「正在播放的下一集优先」是产品问题，见「待确认 3」。**

## 明确否定（这些**不是**原因，避免下一轮重复排查）

1. **「播放读一个正在被下载的 TG 文件」不成立**：TG 缓存的落盘临时文件（`grammers.rs:1053-1072` 的
   `<name>.part`）**不被任何播放端点服务** —— `/raw` 与 `/tg/local` 只服务 `file_path` 非空的**完整文件**
   （未完成返回 `None`，`routes.rs:914-923`）。未缓存时播放走的是**另一条**独立直播流（`media_file`，`routes.rs:483`）。
2. **已落盘的完整文件（A / B / D1）不存在段级串行**：`total` = 全量，客户端连续取。
3. **前端不做任何分段缓存/预读**：`MediaSource` / `SourceBuffer` / `ReadableStream` / `Range` 头
   在 `tauri-shell/src` **0 命中**；只有 `<video preload="auto">`（`VideoPlayer.tsx:1192`），缓冲全交浏览器。
   且**稳态播放中 `<video src>` 不变**（`VideoPlayer.tsx:714` 的 `sameStreamTarget` 早退）——
   换源只发生在**改倍速 / seek 超覆盖 / 解码判死 / onError**（`:732`、`:907`、`:781`、`:1068`）。
   缓冲条只画 `buffered.end(last)` **连续一条**（`:380-390`）⇒ 用户看到的「一段一段」**不是前端画的**。
4. **无「播放让路 / 暂停下载」逻辑**：全仓搜 `pause|yield|priority` 无播放让路命中；
   `BytesPresence`（`cache.rs:249-257`）只有 `Present/Missing/Unknown` 三态、**仅供展示**，不是调度信号。
5. **无绕过页缓存的手段**：`madvise` / `posix_fadvise` / `O_DIRECT` / `mmap` **0 命中**；
   读走 OS 页缓存。**BUG-219 已证伪「卷级磁盘 I/O 争用」**（同盘写使 `/raw` 读降 36% 但**未复现 stall**），本档不重复列为主因。

## 修复方向（未实施；≥2 实质选项 + 1 个「不做」）

### 选项 A（推荐）：**解耦「产出」与「投递」** —— 让 `.part` 落盘不再被响应通道节流

- `transcode_pump` 改为：**无条件**把 ffmpeg stdout 写 `.part`（独立于响应通道）；
  响应通道降级为**尽力投递**（`try_send`，满则丢弃并由客户端下次 Range 追平）。
- 效果：转码与落盘**全速跑完**，播放只消费**已完成前缀**；前沿不再贴着播放头。
- `涉及:` `routes.rs` 的 `transcode_pump`（约 `:4090-4160`）与 `resp_tx` 的类型/用法（`:3922-3923`、`:4139-4142`）。
- `量化:` 1 个泵的写入策略 + 1 个通道语义；**不动**端点契约、不动前端。
- `回归风险:` 中 —— 必须保证「live 流」仍能连续投递（不能因丢包让播放断流）；
  需验：冷缓存首播可正常开播、拖拽仍可追平。
- `后果:` 直接消除「每个缓存点等下一片」；**首播延迟不变**（仍是边转边播）。

### 选项 B：只**放大管道**（最小改动）

- `mpsc::channel(32)` → 显著更大（如 256 槽 ≈ 64MiB），或把 256KiB 缓冲调大。
- `涉及:` `routes.rs:3923`（槽数）+ `:4109`（缓冲大小）。
- `量化:` 2 个常数。
- `回归风险:` 低。
- `后果:` **缓解不根治** —— 缓冲填满后仍然是「生产等消费」；
  转码慢于实时时（倍速场景）前沿依旧贴住播放头。**只是把停顿推后，不是消除。**

### 选项 C：**先转后播**（牺牲首播延迟换稳定）

- 冷缓存时先转完（或转到足够大，如 60s 内容）再开播；UI 给「转码中 x%」进度与自动开播。
- `涉及:` `/stream` 冷启动分支 + 前端等待态。
- `量化:` 1 个门控 + 1 个进度呈现。
- `回归风险:` 中 —— 与 BUG-226 的「锚点起转免等待」设计**取向相反**，须一并复核。
- `后果:` 播放期不再停顿，但**首播要等**（用户此前明确抱怨过等待 ⇒ 需产品拍板）。

### 选项 D：不做

- `涉及:` 无（0 行改动）。`量化:` 0。`回归风险:` 无。
- `后果:` 冷缓存播放继续在每个分片边界停顿；用户第 N 次报告可预期。

## 修复后必须满足（可证伪判据，预先声明）

1. **产出不再被消费节流**：冷缓存播放中**暂停播放**（不消费）30s，
   `<proxy_dir>/<id>.mp4.part` 的长度**必须持续增长**（≥ 暂停前速率的 50%）；
   若停滞 ⇒ **FAIL**（现状即此）。
2. **段边界无 stall**：冷缓存播放全程，用 **`waiting` 事件**与 **`currentTime` 推进速率**判 stall
   （**禁用** `timeupdate` / `rAF`，BUG-034）；1x 与 2x 各测一遍（BUG-033 教训：1x 正常的通路在 2x 可能放大数十倍）。
3. **反向证伪（双向）**：
   - 选 A 时，把泵改回「`send().await` 与 `.part` 写共用同一循环」⇒ 判据 1 **必须 FAIL**；
   - 把通道槽数改回 32（选 B 场景）⇒ 判据 1 的增益必须**可测地回退**。
4. **既有能力不回退**（BUG-149）：冷缓存**首播可开播**（不要求先转完）、**拖拽/seek 仍可追平**（BUG-253/226）、
   `/stream` 的三种 `x-orig-stream` 模式头（`proxy` / `part` / `live`）语义不变。
5. **不回退既有裁定**：BUG-028 的 4 路并行、BUG-199 的**环回不限速**、
   BUG-219 的 `ETag`/`Last-Modified` 复用机制、BUG-027 的**缓存单飞**（本档不推翻）。
6. **判据必须在真实 UI / 真实播放上验**（BUG-156），`getComputedStyle` / 事件 / 响应头判定，**不读 className**。
