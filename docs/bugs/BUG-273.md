# BUG-273: 播放卡顿（再报）：段级「读写入」串行只存在于**转码代理的增长 `.part`** —— 响应止于请求当刻的 EOF（`total = meta.len()`），且转码泵与响应之间只有 **32 槽**管道（`resp_tx.send().await`）⇒ 产出被播放消费节流，每个分片边界都要等下一片

- 状态: open
- 发现日期: 2026-10-10
- 模块: engine
- 严重程度: high

> 来源：用户报告「**卡顿问题依然没有很好解决，当前播放有缓存读取写入问题，当前缓存播放完才会进行下一段缓存，
> 这就造成了每个缓存点会卡顿。**」
>
> **本档为任务文档**（用户 2026-10-10 定：后续一律纯文档任务，代码由别的组负责）。

## 现象（用户原话拆解）

| 用户措辞 | 拆出的可验证命题 |
|---|---|
| 「当前播放有**缓存读取写入**问题」 | 播放的**读**与缓存的**写**之间存在串行/争用 |

## 根因 1（段级）：转码产出被播放消费**节流** + 响应止于**写入前沿**

### 1.1 产出被消费节流（`resp_tx.send().await` 的 32 槽背压）

`download-engine/crates/orig-tg/src/routes.rs`：

```rust
:3922  let (resp_tx, resp_rx) =
:3923      tokio::sync::mpsc::channel::<Result<axum::body::Bytes, std::io::Error>>(32);
:3924  tokio::spawn(transcode_pump(ffmpeg, src, part_p, final_p, key, …));
...
:4109      let mut buf = vec![0u8; 256 * 1024];
...
:4139      if !client_gone
:4140          && resp_tx
:4141              .send(Ok(axum::body::Bytes::copy_from_slice(&buf[..n])))
:4142              .await            // ← 32 槽满即阻塞
```

`transcode_pump` 把 ffmpeg stdout **双写**（一份进响应通道、一份落 `.part`），
但**两者共用同一个循环**：一旦响应通道满（客户端没在消费），`send().await` **阻塞整个泵**
⇒ **转码与落盘一起停**。

⇒ 这不是「限速」，而是**结构性正反馈**：
**播放等生产**（前沿不够就读不到），**生产等播放**（通道满就写不动）。
只要**转码速率 ≤ 播放消费速率**，前沿就**永远贴在播放头上**，于是**每个分片边界都必须等下一片**。

`routes.rs:4005` 的 ffmpeg 参数里**没有 `-re`**（不是人为限速到实时）⇒ 转码快于实时时不会 stall；
**慢于实时时（高码率 / 倍速 / 慢 CPU）必然在每个产出边界 stall**。倍速是重灾区：
倍速变体 `-speed-<百分之一倍速>.mp4`（`routes.rs:3796-3799`）要求 ffmpeg 产出**更快的时间轴**，成本更高。

### 1.2 响应止于「请求那一刻」的 EOF

`serve_local_file` 对增长中的 `.part` 服务时：

```rust
:4368  let total = meta.len();                              // ← 请求当刻的长度
:4390  let e = if open {
:4391      (s + OPEN_CHUNK - 1).min(total - 1)              // ← 封顶在当下 EOF
...
:4473      format!("bytes {start}-{end}/{total}")            // ← Content-Range 如实报当下长度
```

⇒ **响应在当下 EOF 处结束**，客户端**必须再发一次 Range** 才能拿到后面的字节。
`routes.rs:3896-3898` 的注释自述了这个设计（「浏览器缺多少再要多少」），
它的**初衷**是对的（4x 暂停后再播不必等整片转完），但**代价**就是：**每追平一次写入前沿 = 一处「缓存点」停顿**。

⇒ 1.1 与 1.2 **叠加**：1.1 让前沿永远贴着播放头，1.2 让每次追平均为一次新的请求往返。
**这正是用户描述的「每个缓存点会卡顿」。**

## 明确否定（这些**不是**原因，避免下一轮重复排查）

1. **「播放读一个正在被下载的 TG 文件」不成立**：TG 缓存的落盘临时文件（`grammers.rs:1053-1072` 的

## 修复方向（未实施；≥2 实质选项 + 1 个「不做」）

### 选项 A′（推荐，**取代原选项 A**）：把「生产停止判据」从**响应通道满**改为**距播放点 > N 秒**（有界滑动窗口）

**先纠正一个前提**（这决定 A′ 与「只把窗口调大」的区别）：
现状的停判据是「响应通道 32 槽满」（`routes.rs:4140-4142`），
而**通道语义是「响应投递队列」，不是「磁盘预读窗口」**。后果：窗口永远停在**满/空边缘**，
一空就 stall ⇒ **在现状下把 N 调大是无效的**（满 = 生产停，N 名存实亡）。

⇒ A′ 的实质是**换掉停判据**：

- **生产侧**：把 `.part` 推进到「**播放点 + N 秒**」对应的字节位置，**到此为止**（不整片转完）；
- **播放侧**：从 `.part` 读，读到写入前沿就**等下一次推进**（而不是重新发一次 Range 往返）；
- 播放点前进 ⇒ 生产继续推进 ⇒ **磁盘 / CPU 占用有界**（最多领先 N 秒的字节）。

#### 关于 N 的口径（回答用户「你认为呢？」）—— 必须写成不等式，并承认它的边界

设 `r_c` = 消费速率（字节/秒 = 码率 × 倍速）、`r_p` = 生产速率（转码输出字节/秒）、
`T_w` = **一次写入批次的墙钟耗时**（含 TG RPC ~1.2s、转码一个分片的耗时）、`W` = 窗口秒数。

- **窗口从满到空的时间** = `W / (r_c − r_p)`（仅当 `r_p < r_c` 时为正）；
- 用户的判据「下一次缓存更新写入前不被消耗完」即 `W / (r_c − r_p) ≥ T_w`
  ⇒ **`W ≥ T_w × (r_c − r_p)`**；
- **★ 关键边界（不许含糊）**：当 `r_p < r_c` 时，**任何有限的 W 都只能把 stall 推迟 `W/(r_c−r_p)` 秒，不能消除**。
  只有 **`r_p ≥ r_c`** 才真正消除 stall；此时 **W 只是余量**（防抖动），可以取得很小。
- ⇒ **N 不是「一个固定秒数」，而是一条「先让 `r_p ≥ r_c` 成立、再留余量」的组合口径**：
  1. 先测 `r_p` —— **解耦后** ffmpeg 的真实产出速率（不再被消费节流）；
  2. 若 `r_p ≥ r_c` ⇒ `W` 取小（如 10–30s）即可，**这就是根治**；
  3. 若 `r_p < r_c` ⇒ **必须降需求**（倍速已有 FRC 变体 `-speed-<百分之一倍速>.mp4` 降帧率省码率，
     `routes.rs:3796-3799`），否则只能退回**选项 C（先转后播）**。
- **★ 倍速必须单独定 W**：2x 时 `r_c` 翻倍、4x 时 ×4，而 `r_p` 基本不变
  ⇒ **倍速下 `r_p < r_c` 是常态**（与此前「2x / 4x 卡」同一根因）。
  ⇒ `W` **必须按倍速缩放**，不能一个常数走天下。

- `涉及:` `routes.rs` 的 `transcode_pump`（约 `:4090-4160`）+ `resp_tx` 语义（`:3922-3923`、`:4139-4142`）
  + 「播放点」的取得（由前端上报 `currentTime`，或由泵从 Range 请求头推断）。
- `量化:` 1 个停判据 + 1 个播放点来源 + 1 组按倍速缩放的 W。
- `回归风险:` 中 —— ① live 流仍须连续投递；② 冷缓存**首播可开播**（不得退化成「先转后播」）；
  ③ 拖拽 / seek 仍可追平（BUG-253 / BUG-226）；④ 前端若需上报播放点，**不得引入高频轮询**。
- `后果:` 在 `r_p ≥ r_c` 时**消除段边界 stall**，且**资源占用有界**（不整片爆转）；
  在 `r_p < r_c` 时**如实承认只是推迟**，并走降需求或选项 C。

> **原选项 A（`try_send` + 全速跑完 `.part`）不采用** —— 用户指出它会「爆炸性一次缓存整部片」。
> 但 A 与 A′ 的**共同点才是根治所在**：**两者都必须先把「生产被消费节流」解掉**；
> 差别只在**停判据** —— A 是「跑到 EOF」，A′ 是「跑到播放点 + N」。**A′ 严格优于 A。**

### 选项 B：只**放大管道**（最小改动）

- `mpsc::channel(32)` → 显著更大（如 256 槽 ≈ 64MiB），或把 256KiB 缓冲调大。
- `涉及:` `routes.rs:3923`（槽数）+ `:4109`（缓冲大小）。
- `量化:` 2 个常数。
- `回归风险:` 低。
- `后果:` **缓解不根治** —— 缓冲填满后仍然是「生产等消费」；
  转码慢于实时时（倍速场景）前沿依旧贴住播放头。**只是把停顿推后，不是消除。**

### 选项 C：**先转后播**（牺牲首播延迟换稳定）

- 冷缓存时先转完（或转到足够大，如 60s 内容）再开播；UI 给「转码中 x%」进度与自动开播。
- `涉及:` `/stream` 冷启动分支 + 前端等待态。
- `量化:` 1 个门控 + 1 个进度呈现。
- `回归风险:` 中 —— 与 BUG-226 的「锚点起转免等待」设计**取向相反**，须一并复核。
- `后果:` 播放期不再停顿，但**首播要等**（用户此前明确抱怨过等待 ⇒ 需产品拍板）。

### 选项 D：不做

- `涉及:` 无（0 行改动）。`量化:` 0。`回归风险:` 无。
- `后果:` 冷缓存播放继续在每个分片边界停顿；用户第 N 次报告可预期。

## 修复后必须满足（可证伪判据，预先声明）

1. **产出不再被消费节流，且窗口有界**（选项 A′，**双向都判**）：
   冷缓存播放中**暂停播放**（不消费）30s，观察 `<proxy_dir>/<id>.mp4.part` 的长度：
   - 若**停滞不动** ⇒ **FAIL**（现状即此：`send().await` 把整个泵卡住）；
   - 若**一路涨到整片 EOF** ⇒ **也 FAIL**（= 用户否决的「爆炸性一次缓存整部片」）；
   - **必须**：继续增长，并**停在**「播放点 + N 秒」对应的字节位置附近。
2. **窗口不空**：冷缓存播放全程，`buffered.end(last) − currentTime ≥ W_min` 恒成立；
   **1x / 2x / 4x 分别取值**（W 必须按倍速缩放，不得用同一常数）。
3. **段边界无 stall**：冷缓存播放全程，用 **`waiting` 事件**与 **`currentTime` 推进速率**判 stall
   （**禁用** `timeupdate` / `rAF`，BUG-034）；1x 与 2x 各测一遍（BUG-033 教训：1x 正常的通路在 2x 可能放大数十倍）。
4. **必须实测并记录 `r_p` 与 `r_c`**：给出解耦后 ffmpeg 的**真实产出速率** `r_p` 与各倍速下的 `r_c`。
   - 若 `r_p ≥ r_c` ⇒ 判据 1–3 全部可达 ⇒ 本档为**根治**；
   - 若 `r_p < r_c` ⇒ **必须如实写明「本档只推迟、不消除」**，并给出降需求（FRC 降帧率省码率）或选项 C 的结论。
     **禁止**把「只推迟」报成「已解决」。
5. **反向证伪（双向）**：
   - 把泵改回「`send().await` 与 `.part` 写共用同一循环」⇒ 判据 1 的「停滞」必须**复现**（即修复前 FAIL）；
   - 把 `W` 设为 0（或把停判据改回「通道满」）⇒ 判据 2 **必须 FAIL**；
   - 把 `W` 设成「整片」（不设上限）⇒ 判据 1 的「涨到 EOF」分支**必须 FAIL**。
6. **既有能力不回退**（BUG-149）：冷缓存**首播可开播**（不要求先转完）、**拖拽 / seek 仍可追平**（BUG-253 / BUG-226）、
   `/stream` 的三种 `x-orig-stream` 模式头（`proxy` / `part` / `live`）语义不变。
7. **不回退既有裁定**：BUG-028 的 4 路并行、BUG-199 的**环回不限速**、
   BUG-219 的 `ETag` / `Last-Modified` 复用机制、BUG-027 的**缓存单飞**（本档不推翻）。
8. **判据必须在真实 UI / 真实播放上验**（BUG-156），用事件 / 响应头 / `stat` 判定，**不读 className**。
