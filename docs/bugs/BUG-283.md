# BUG-283: 存量剧集标题退化成占位名 `TG <chat_id> · <日期>` 且无「按 source_key 重算」通道 —— 同频道多个剧集不可分辨，破坏剧集管理与文件管理

- 状态: open
- 发现日期: 2026-10-12
- 模块: engine
- 严重程度: high

> 来源：用户 2026-10-12 报障「之前的入库标题问题好像导致了更严重的媒体库资料数据混乱问题了：
> TG -1003969766003 · 2026-10-10 这是媒体库的数据，和入库标题一样，但是这个必定是属于某个剧集的，
> 现在这样完全不知道是哪个剧集的，这种混乱完全破坏了剧集的管理和媒体库的文件管理。」
> **本档为任务文档**（用户定：纯文档任务，代码由别的组负责）。

## 现象

媒体库里出现**标题为占位名** `TG <chat_id> · <日期>` 的剧集（用户示例 = `TG -1003969766003 · 2026-10-10`）。
该形态与**入库兜底标题**同源（`routes.rs:2233-2250` 的「频道名 · 日期」回退）。

实测（生产库 `%APPDATA%\com.origadmin.orighub\tg\store.db`，只读）：

| 剧集 | 标题 | source_key | 分集数 |
|---|---|---|---|
| 281 | `TG -1004457697592 · 2026-10-10` | `tg:msgs:-1004457697592:1199` | 1 |
| **329** | `TG -1003969766003 · 2026-10-10` | `tg:msgs:-1003969766003:3266` | 1 |
| 334 | `TG -1003969766003 · 2026-10-11` | `tg:msgs:-1003969766003:3320` | 1 |
| **335** | `TG -1003969766003 · 2026-10-11` | `tg:msgs:-1003969766003:3373` | 8 |
| 337 | `TG -1003969766003 · 2026-10-12` | `tg:msgs:-1003969766003:3450` | 1 |

- **全库 72 个剧集中 5 个**是占位名（约 7%）。
- 同一频道 `-1003969766003` 下 **4 个（329 / 334 / 335 / 337）只差日期** ⇒ **列表里不可分辨**，合并时也极易选错目标。
- **关键反例**：剧集 **335**（组 3373-3380，8 集）的**第 6 集（msg 3378）有完整真 caption**
  `🌟🔥🔥《温柔的妈妈被我弄哭了》EP1-8 频道连载中 ⭐⭐⭐`，但**剧集标题仍是占位名**
  ⇒ 说明标题在**创建时回退成占位名后，之后再也不会更新**。

**破坏面（用户原话对应）**：
- **剧集管理**：看到 `TG -1003969766003 · 2026-10-10` 无法判断是哪部剧、与哪些剧集是同一部 ⇒ 无法正确整理 / 合并。
- **文件管理**：文件挂在**不可辨识**的剧集下，后续按剧集归档 / 导出全部失去依据。

## 根因

**剧集标题在 `first_caption` 拿不到时回退成「频道名 · 日期」占位名，且没有任何「后续重算 / 回填」通道 ⇒ 占位名被永久钉死。**

### 事实 1：占位名的生成点
`download-engine/crates/orig-tg/src/routes.rs:2215-2250`（`ensure_series`）：
```rust
let (title, desc) = match st.store.first_caption(self.chat_id, &self.task_msgs).await.unwrap_or(None) {
    Some(cap) => crate::media::split_caption(&cap),
    None => (None, None),
};
let title = match title {
    Some(t) => normalized_series_name(&t),
    None => {
        let base = channel_title(st, self.chat_id).await
            .unwrap_or_else(|| format!("TG {}", self.chat_id));
        format!("{base} · {}", ymd_str(self.created_at as u64))
    }
};
```
`channel_title` 拿不到频道名时退到 `TG {chat_id}` ⇒ 生产库出现的正是 `TG -1003969766003 · <日期>` 形态。

### 事实 2：没有更新通道（幂等复用 + 追加不写 title）
- 同一任务内：`ensure_series` 开头 `if let Some(sid) = self.series { return Some(sid); }`（`routes.rs:2216-2218`）直接复用，不重算。
- 跨任务追加：既有剧集按 `source_key` 复用，**追加路径刻意不写 title**（BUG-152 明示）。

### 事实 3：这正是 **BUG-152 显式推迟、且从未实施**的缺口
`docs/bugs/BUG-152.md:149-153`（「六、已知边界（如实标注，未修）」）原文：
> **存量剧集 title 不回溯**：已存在的剧集（含被首条 caption 钉死的旧 title）**不会**被本次修复改名
> —— 追加路径刻意不写 title。纠正存量需另立显式的「按 source_key 重算标题」迁移，**未实施**
> （属用户裁定范畴）。

⇒ 用户本轮报的**正是**这条被推迟的「存量重算」缺口；BUG-152 只修了「追加路径不再改 title」，**没有**修「已钉死的占位名如何纠正」。

### 事实 4：触发占位的原因有多种，但后果同一（永久占位）
- caption 在创建时**尚未到达**（相册组逐条入库，首条无 caption，如剧集 335）；
- 首行为空 / 剥完标签为空（`routes.rs:2243-2250`）；
- **BUG-156**（fixed）治过的「首行整行 `#` 词被 `split_caption` 弹空」。
三者**共同后果**都是落到占位名；BUG-156 只修了 `split_caption` 那一侧，**占位名的后续纠正仍缺**。

## 复现

1. 入库一个「**首条消息无 caption、靠后消息才有**」的相册组（或单条无 caption 的视频）。
2. 媒体库打开该剧：标题为 `TG <chat_id> · <日期>`，无法辨识归属。
3. 只读 SQL 佐证：
```sql
SELECT id, title, source_key FROM media_series WHERE title LIKE 'TG %' ORDER BY id;
```

## 修复（方向；**本档不改代码**）

1. **显式「按 source_key 重算标题」迁移（P0）** —— BUG-152 已预告、本档落地：
   对存量剧集，用 `first_caption(chat_id, task_msgs)` 重新规范化标题；能算出真名则替换占位名。
   对剧集 335，应能由 msg 3378 的 caption 算出 `《温柔的妈妈被我弄哭了》`。
2. **增量回填（P0）**：新 caption 到达时，**仅当既有剧集标题是占位名**（可识别形态）且新 caption 能算出真名 ⇒ 更新标题。
   **不得覆盖用户已手工编辑的标题**（与「追加不写 title」的既有裁定协商，不能一刀切放开）。
3. **占位名可辨识化（P1）**：确实算不出真名时，占位名至少含**首条消息号**（如 `TG <chat_id> · <日期> · #<first_msg>`），
   避免同频道多剧集同名不可分辨；频道名可用时优先用频道名。
4. **合并入口可达（P1）**：确认占位剧集可被 BUG-186 的「多选剧集 → 合并」选中（否则无法人工收敛）。

## 关联

- **BUG-152**（fixed）：剧集标题批次相关、**存量不回溯** —— **本档是其显式推迟缺口的落地**（同源，不同范围）。
- **BUG-156**（fixed）：首行全 `#` 词被弹空 → 退化成「频道名 · 日期」占位名（**触发原因之一**；只修了 `split_caption` 侧）。
- **BUG-037**（fixed）：分批内容裂成多个剧集 + 合并能力 —— 解释了「同频道多个剧集」的由来。
- **BUG-280**（open）：**队列**标题被无意义文件名遮蔽（同源形态，不同面）。
- **BUG-281**（open）：**分集**不共享组级 caption（本档是**剧集级标题**，不同面）。
- **BUG-186**（系列合并）：占位剧集必须能被选中合并，否则人工无法收敛。

## 验收证据

（状态 `open`，尚无验收证据。修复后必须满足的**可证伪判据（预先声明）**：）

1. **存量重算生效**：跑「按 source_key 重算标题」后，剧集 **335** 的 `title` 必须由 `TG -1003969766003 · 2026-10-11`
   变为 **`《温柔的妈妈被我弄哭了》`**（由 msg 3378 的 caption 规范化得出）；全库占位剧集数由 **5 → 0**
   （对确实无 caption 的剧集给出**可辨识**占位，见判据 3）。
   **反向证伪**：不重算 ⇒ 335 仍为占位名 ⇒ 判据必 **FAIL**。
2. **增量回填且不覆盖用户编辑**：构造「首条无 caption、靠后有 caption」的组，入库后剧集标题必须等于靠后 caption 的规范化名；
   若该剧集标题已被用户**手工编辑**，回填**不得覆盖**。**反向证伪**：无条件覆盖用户标题 ⇒ 判据必 **FAIL**。
3. **占位可辨识**：确实算不出真名时，同一频道下的多个占位剧集**标题必须互不相同**（含首条消息号等判别位）。
   **反向证伪**：仍产出 `TG <chat_id> · <同一日期>` 两条 ⇒ **FAIL**。
4. **不推翻既有裁定**：BUG-152（批次无关性）、BUG-156（`split_caption`）、BUG-037（合并能力）不得回退。
5. **真实 UI 可核**：媒体库剧集墙不再出现**无法分辨的同名占位剧集**（DOM 断言标题唯一、**不读 className**）。
