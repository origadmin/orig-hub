# BUG-227: daemon 拉 orig-tg 用 5s 全程连通窗口，代理链路慢时把本可成功的启动系统性否决（"exited without listening" 假象）

- 状态: fixed
- 发现日期: 2026-10-09
- 模块: engine
- 严重程度: high

## 现象

daemon（`TG_START_WAIT_TIMEOUT=5s`，`download-engine/crates/orig-daemon/src/state.rs:45`）反复报
`orig-tg exited without listening on 127.0.0.1:19787/19788`、`tg_running=false`，而同一个二进制
带 daemon 同款 env 手工拉起可正常服务（health ok、缓存媒体可播）。用户表现为 TG 服务反复
「开了但不可用」，设置页停留上次失败原因。

## 根因（2026-10-09 实测）

orig-tg 的启动顺序是**先连 MTProto、后绑 HTTP**。已配置凭证 + 代理链路慢/挂起时（实测
socks5://127.0.0.1:7897 端口活但上游断，MTProto connect 失败返回耗时 ~11.7s），HTTP bind 要等
MTProto 尝试结束才发生：

- 实测 bind 耗时 11.2s / 11.7s（连续 3 次手工拉起一致）；
- daemon 等待窗口 5s：bind 未发生 → 到点 `c.kill()`（state.rs:383）→ 判定
  `exited without listening`（state.rs:391）——**把「连得慢」误判成「起不来」并杀掉本可成功的进程**；
- 此后 daemon 每 60s（`TG_SPAWN_COOLDOWN`）重试一次，每次同样在 5s 被杀 → 系统性失败风暴。

## 结构性修法（本轮已实现，2026-10-09 深夜）

真正的问题是**就绪判据被登录耗时绑架**：daemon 用「TCP 能否连上端口」判定起没起来，
而 orig-tg 把 bind 放在 MTProto 之后 ⇒ 端口何时可连 = 网络多快登录。两处一起改：

1. **orig-tg 先占端口、再连 Telegram**（`orig-tg/src/main.rs`）：`TcpListener::bind` 移到
   `build_client` **之前**，`axum::serve` 仍在其后。端口与登录解耦：端口先归我们所有，
   登录慢只影响 `/api/tg/*` 的可用性（`Availability::Unavailable` → 503），
   不再反过来把服务本身判成「起不来」。先 bind 期间到达的连接排在 backlog 里，不丢请求。
2. **daemon 等待窗口 5s → 30s**（`TG_START_WAIT_TIMEOUT`，`orig-daemon/src/state.rs`）：
   给慢链路足余量；真正的失败仍然快速失败（子进程退出即刻中止，见拉起循环）。

顺带纠正 message 语义（原「结构性修法方向」第 3 条）：现在三条失败原因分别是
「二进制缺失」「进程退出（带退出码）」「窗口内未监听 / 端口不可绑」，不再混成一句。

原「本轮不实现」的方向 1（就绪即只认 bind）正是本轮采用的做法。

## 验收证据

- 代码位置（入库，可跨机器复核）：`download-engine/crates/orig-tg/src/main.rs`（`TcpListener::bind`
  移到 `build_client` 之前）、`download-engine/crates/orig-daemon/src/state.rs`
  （`TG_START_WAIT_TIMEOUT` 5s→30s + 拉起初期的端口占用日志）。
- 实测冷启动耗时（同款 env、同二进制，走 socks5 代理）：**5.10 s / 6.96 s** —— 抖动全在网络侧
  （MTProto 协商盐与 future salts），而窗口原值 5 s 恰好落在区间内。
- 修复后（2026-10-09 23:45，`orig-tg` 早绑定版本已部署到位）：
  `PUT /api/config/tg {enabled:true}` **2.59 s** 返回 `{"tg_running":true,"tg_port":19788,"tg_last_error":null}`；
  `GET /api/tg/diag` → `{"health":"ok","available":true,"link_alive":true,"mode":"ready","session_phase":"Authorized"}`；
  媒体库 `GET /api/media/items` 正常返回。用户侧「TG 服务未能启动，模块已隐藏」消失。
- 手工同款 env 拉起：bind 11.7s → health ok（2026-10-09 07:38 / 07:50 / 08:0x 三次）；
- **2026-10-09 深夜复现（BUG-232 v2 部署时）**：同款 env 手工启动新构建 orig-tg，
  轮询探测得 **listen 5.10s**（临界刚过 5s）⇒ daemon 连续 3 次 `PUT /api/config/tg`
  均在窗口内否决，`tg_running=false`，并把端口从 19787 顺延到 19788（BUG-228 的漂移现场）。
- ⚠️ 用户当时看到的那一句 `orig-tg exited without listening on 127.0.0.1:19788` 属**分支 1（进程真的退出）**：
  当时 19788 被「临时绕行的手工实例」占着（绕行实例 = 同一端口的第二个 orig-tg），
  daemon 拉起的子进程 bind 失败即退 ⇒ 报分支 1。绕行实例已撤除，不再手工占端口。
- daemon 侧 30s 窗口的二进制已就位（`download-engine/target/release/orig-daemon.exe` + 壳 target 三处），
  但**运行中的 daemon 实例是 2026-09-29 构建**且本会话无权终止（见 BUG-234 部署记录）——
  下次引擎启动即生效。
