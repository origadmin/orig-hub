# BUG-092: /api/interfaces 单次约 1s 阻塞，新建下载弹窗开合卡顿

- 状态: fixed
- 发现日期: 2026-09-21
- 模块: engine
- 严重程度: mid

## 现象

`GET /api/interfaces` 单次约 1 秒（体检时连测 5 次：1.042 / 0.892 / 0.931 / 0.887 / 0.868 秒）。

调用点是 `tauri-shell/src/api/daemon.ts:70`，**新建下载弹窗一打开就拉** —— 于是每次开合弹窗
都要干等近 1 秒才出网卡列表，肉眼可见卡顿。

## 根因

`download-engine/crates/orig-daemon/src/routes.rs:701`（修前）：

```rust
async fn list_interfaces() -> axum::Json<serde_json::Value> {
    let all = orig_net::list_all_adapters().unwrap_or_default();   // 同步阻塞
    let pool = orig_net::InterfacePool::resolve(None)...;          // 又一次同步探测
```

`list_all_adapters()` 走 Windows `GetAdaptersAddresses`（且带 `GAA_FLAG_INCLUDE_PREFIX`），
`InterfacePool::resolve()` 再解析一遍 —— 两次同步系统调用直接跑在 async handler 里，
既占住 worker 线程，也让每次请求都付全量代价。

而网卡清单**几乎不变**（插拔网线/连 VPN 才动），却按「每次打开弹窗全量重算」计费 ——
刷新频率与数据变化频率严重不匹配。

## 复现

```sh
for i in 1 2 3 4 5; do
  curl -s --noproxy '*' -o /dev/null -w "%{time_total}\n" http://127.0.0.1:9876/api/interfaces
done
```

## 修复

**加缓存**（不动前端，不改契约）：

- 内存缓存 + TTL 30s（`INTERFACES_TTL`），命中即返回，第二次起毫秒级；
- 重算走 `tokio::task::spawn_blocking`，不再占住 async worker 线程；
- **手动失效**：`?refresh=1` 强制跳过缓存重算一次；等价的 `invalidate_interfaces_cache()`
  供配置变更 / 网卡增删处调用。

红线遵守情况：这不是轮询端点，缓存只在 TTL 到期后由**命中的那次请求**重算一次 ——
不预刷新、不建后台任务、不加轮询，不会退化成高频刷新端点（AGENTS.md §5）。
响应体结构与字段完全不变（实测缓存命中与首次响应的 JSON 逐字节一致）。

## 验收证据

在同一台机器上另起一份临时 daemon（`PORT=19876`，空配置目录，**未触碰 9876/9877/5180**），
对新二进制连测 5 次：

```
第1次: total=1.536461s     <- 缓存未命中，全量计算
第2次: total=0.005413s
第3次: total=0.004081s
第4次: total=0.004492s
第5次: total=0.004198s
```

复测一轮同形态（1.986 / 0.008 / 0.007 / 0.006 / 0.006 s），第二次起均在 **4–8ms**
（约为原来的 1/200）。`?refresh=1` 实测 1.5206s —— 证明手动失效确实会重算，不是缓存击穿后假命中。

同机对照：线上 9876（旧二进制）同时刻实测 0.878s，与体检基线一致。

  `sh scripts/sync-sidecars.sh --check` PASS；
  `python scripts/check-bugs.py` 与 `sh scripts/check-pollution.sh` 均 EXIT 0
