# BUG-396: 入库流水线「优先」状态可作用于已完成/已取消的任务

- 状态: fixed
- 发现日期: 2026-10-23
- 模块: engine+shell
- 严重程度: high
- 报告: 用户 2026-10-23 16:43「入库流水线 有严重问题,"优先" 居然能针对已完成的进行设置. 完成后应该就没有优先这个状态了. 当前逻辑不对.」

## 现象（实测，非推测）

「全部下载」里已完成（`status=done`）/ 已取消（`status=cancelled`）的入库对象，仍然：
- 显示「优先」徽标（行内 `ingest-group-prioritized`）；
- 带「取消优先」动作按钮（`ingest-group-action-unprefer`）。

即任务已经结束，「优先」这个排序状态却还挂在它身上。用户判定：完成后就**不该再有优先状态**。

## 根因：终态离队不清 priority + 前端判据不看状态

### 引擎侧（状态真源允许脏数据存在）
- `store.rs::finish_cache_task`（`UPDATE cache_task SET status=?, ...`）在任务走到 `done`/`failed` 时**不归零 `priority`**；
- `store.rs::cancel_cache_task` 在置 `cancelled` 时同样**不归零 `priority`**；
- `cache.rs::prioritizable`（`t.status=="queued" || t.priority>0`）**故意**允许「`priority>0` 即使非排队也可取消置顶」——注释明言为防「点了置顶后终态任务按钮还在、点了却 422」。这是与本次裁定的直接冲突点：用户要的是「终态无优先状态」，而不是「终态还保留优先以便撤销」。

### 前端侧（陈旧值照样渲染）
- `ingestGroups.ts::ingestActionsFor`：`if (priority > 0) acts.push('unprefer')` —— 不看 `status`；
- `IngestGroupRow.tsx` 徽标：`(latest.priority ?? 0) > 0 && (...)` —— 不看 `status`；
- `CacheManagerDialog.tsx::prioritizable`：`task.status==='queued' || (task.priority??0)>0` —— 同上。

三层判据与后端 `prioritizable` 逐字同源 ⇒ 终态任务只要残留 `priority>0`，UI 就呈现优先状态。

## 修法（让错误状态不可表达）

1. **引擎归零（真源）**：`finish_cache_task` 与 `cancel_cache_task` 的 `UPDATE` 增加 `priority = 0`（任务离队即清排序状态）。
2. **引擎判据收紧**：`prioritizable` 改为 `t.status=="queued" || (t.priority>0 && t.status!="done" && t.status!="cancelled")`——终态任务永不「可取消置顶」。
3. **前端三轮对齐**：`ingestActionsFor` 的 `unprefer` 分支加 `!isCacheSettled(status)`；`IngestGroupRow` 徽标加 `!isCacheSettled(latest.status)`；`CacheManagerDialog.prioritizable` 加 `task.status!=='done' && task.status!=='cancelled'`。

效果：done/cancelled 任务既无徽标也无「取消优先」按钮；运行中/排队中被置顶的任务仍能正常取消置顶（那才是「可观察效果」所在）。

## 补记（2026-10-27）：同一裁定还有一层没收干 —— 面板判据分裂

修复当时只align了**下载域 ingest 行**（`ingestGroups`/`IngestGroupRow`），`CacheManagerDialog`
（「入库流水线」面板）仍在用自己的 `isPrioritized(task) = priority > 0`（不看状态），
三处消费它：行内徽标、`canCancelPrefer`、批量「取消优先」子集。只要任何终态行残留
`priority > 0`（failure/interrupted 路径），「完成后仍是优先」就在这一面复活 ——
同一份数据，下载域说没有、面板说有。**这是锚点缺失，不是数据脏**。

后端 `prioritizable` 同样有终态集合分裂：只排除 `done`/`cancelled`，而启动迁移的终态
口径是四个（`done,cancelled,failed,interrupted`）⇒ `failed` + pin 的行端点放行 200、
前端同期判它终态（BUG-249 同型的判据分裂）。

收口做法（让「多套读法」不可表达）：
- 前端新增唯一判据 `hasPriorityPin(status, priority) = priority > 0 && isCacheActive(status)`
  （`domains/download/ingestGroups.ts`）：下载域徽标、`ingestActionsFor`、`CacheManagerDialog`
  的徽标/按钮/批量子集**全部**引用它，面板不再自算；
- 后端 `cache.rs::prioritizable` 收敛为 `queued || (priority > 0 && running)`，与迁移的四终态口径同源。
