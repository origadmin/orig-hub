# BUG-291: 转码代理文件名**无编码版本键** —— 改编码档位后**陈旧代理被永久沿用**（实测 4x 代理仍是旧档的 30 fps）

- 状态: fixed
- 发现日期: 2026-10-12
- 修复日期: 2026-10-13
- 模块: engine
- 严重程度: mid

> 来源：BUG-289 的机制闭合过程中**顺带发现**（ffprobe 实测某 4x 代理 `r_frame_rate = 30/1`，而现行编码档位规定 ≥3x 应为 24 fps）。
> **本档为任务文档**（用户定：纯文档任务，代码由别的组负责）。
>
> **严重程度说明**：`mid` —— 不导致崩溃或不可播，但会造成
> ①**改了编码策略对存量代理无效**（用户仍看到旧行为）②**「修复后行为一致」不可证**（新旧代理混用）
> ③**诊断被误导**（实测节拍与现行档位不符，见 BUG-289 的异常标注）。
>
> **数据口径**：条目以 `<item_id>` 占位。

## 现象

修改 FRC 编码档位（如 `encode_profile` 的 `fps`）后，**已经存在的转码代理不会失效重建**：

- ffprobe 实测：`<item_id>-speed-300.mp4` / `-speed-400.mp4` 为 **24 fps**（符合现行「≥3x ⇒ 24」），
  但**另一个** `<item_id>-speed-400.mp4` 实测为 **30 fps** ⇒ **沿用旧档**。
- 后果：同一档位在不同条目上**编码不一致**；改了策略的版本与没改的历史代理混在一起。

## 事实

### 事实 1：代理文件名**不含编码版本键**

`download-engine/crates/orig-tg/src/routes.rs:4271-4275`：
```rust
let variant = speed_hundredths
    .map(|speed| format!("{id}-speed-{speed}.mp4"))
    .unwrap_or_else(|| format!("{id}.mp4"));
```
⇒ 文件名只有 `(item_id, speed)`，**没有**编码参数（`preset` / `crf` / `fps` / 滤镜）的指纹或版本。
编码档位定义在同文件 `encode_profile`（`:4076-4082`）⇒ **档位变了，文件名不变**。

### 事实 2：命中即刷新 mtime ⇒ 陈旧代理更「长寿」

代理命中时会 `set_modified(now)`（`:4296-4299`，注释：「命中即『最近使用』」），
而 LRU 预算 `enforce_proxy_budget` 按 **mtime 升序**淘汰
⇒ **越常看的代理越不会被淘汰** ⇒ 陈旧编码的代理**反而活得更久**。

### 事实 3：缓存语义无「有效性校验」

命中路径只判 `metadata(&final_p).is_ok()`（`:4293`）—— **只判存在、不判内容是否仍符合现行档位**。

## 复现

1. 在旧编码档位下播放某条目的某倍速，令其代理落盘。
2. 修改编码档位（如把 ≥3x 的 `fps` 从 24 改成 30，或反向）。
3. 重新请求同一条目同倍速 ⇒ 仍命中**旧代理**（`x-orig-stream: proxy`），编码仍是旧档。
4. 用 `ffprobe` 核对 `r_frame_rate` ⇒ 与现行档位**不一致**。

## 修复（方向；**本档不改代码**）

**总目标：代理的「有效性」必须能被判定；档位变更后旧代理必须失效重建。**

1. **文件名带版本键（P0，最小）**：把编码档位的指纹并入变体名（如 `<item_id>-speed-<n>-<hash>.mp4`，
   `<hash>` 取自 `EncodeProfile` 的实质参数），档位变更 ⇒ 文件名变 ⇒ 自然重建。
2. **命中时校验（P0，备选）**：命中代理时校验其编码是否与现行档位一致（如 ffprobe 读 `r_frame_rate`），
   不一致则视为未命中、重建。**注意**：此路有 per-hit 成本，须缓存结论或只校验一次。
3. **可运维入口（P1）**：提供「清理转码代理缓存」入口（用户/诊断可用），并让 LRU 预算同时覆盖**陈旧档位**的代理。
4. **不推翻既有设计**：不得取消「断开后继续转码」与 LRU 预算；不得改变 `TranscodeKey`（`(item_id, speed)`）的**单飞语义**。

## 关联

- **BUG-223**（FRC 编码档位 / `-r` 与 `-fpsmax` 互斥）：档位定义处同源（`encode_profile`）。

## 验收证据

### 改动

`download-engine/crates/orig-tg/src/routes.rs`（唯一代码改动文件）：

- 新增 `COMPAT_ENCODE_PROFILE` / `encode_profile_for()`：把 `speed=None`（兼容代理）的档位
  （`veryfast` / `crf 23` / `fps 30`）从 pump 里的字符串魔数抽成常量，使**代理文件名里的指纹**
  与**真正下给 ffmpeg 的 `-preset` / `-crf` / `-fpsmax`** 同源（原两处各写一份，必然漂移）。
- 新增 `encode_profile_fingerprint(EncodeProfile) -> String`：把 `preset`/`crf`/`fps` 折叠成
  **确定性**短标记（如 `ultrafast-crf28-24fps`）。刻意不用 `DefaultHasher`——运行期不稳定的哈希
  会让同档位两次请求算出不同名字，直接毁掉「秒开」。
- 新增 `proxy_variant_for()` / `proxy_variant()`：变体名由 `{id}-speed-{n}.mp4` 变为
  `{id}-speed-{n}-{指纹}.mp4`（1x 兼容代理为 `{id}-{指纹}.mp4`）。
- `media_item_stream` 的 `variant` 改用 `proxy_variant(id, speed_hundredths)`（`final_p` / `part_p`
  与命中判据自然跟随）；`transcode_pump` 改用 `encode_profile_for()` 取档位，逐字等价。
- 未改动：`TranscodeKey`（仍是 `(item_id, speed)`）与单飞语义、LRU 预算（`enforce_proxy_budget`）、
  「断开后继续转码」、BUG-226 锚点流语义。

### 测试（cargo test，非 mock）

- 路径：`download-engine/crates/orig-tg/src/routes.rs` → `routes::tests::bug291_encode_profile_change_invalidates_stale_proxy`
- 命令：`cd download-engine && cargo test -p orig-tg --lib --target-dir /tmp/orig-tg-bug288 bug291_encode_profile_change_invalidates_stale_proxy`
- 结果：**`test result: ok. 1 passed; 0 failed`**（`test routes::tests::bug291_encode_profile_change_invalidates_stale_proxy ... ok`）

断言覆盖：

1. 现行 4x 档位名 **≠** 修复前旧命名 `673-speed-400.mp4` ⇒ 磁盘上任何 pre-fix 陈旧代理都不可能
   再被 `metadata(final_p)` 命中（**判据 1「档位变更即失效」的主断言**）。
2. 现行名 **≠** BUG-291 记录的旧档位（`ultrafast/crf28/**30fps**`）算出的名字 ⇒ 改 `fps` 即失效重建。
3. crf 变 / preset 变 ⇒ 名字也变（指纹覆盖档位全部实质参数，不只是 fps）。
4. 形状断言：`{id}-speed-{n}-{指纹}.mp4`（指纹必须落在倍速之后、扩展名之前）。
5. 确定性（**判据 2「不回归秒开」**）：同参数两次调用同名 ⇒ 档位未变时第二次请求仍命中代理，不会每次重转。
6. **判据 4「不推翻既有设计」**：1x 兼容代理与各倍速仍各自独立成文件（BUG-226 语义保持），
   且兼容代理同样带指纹。
