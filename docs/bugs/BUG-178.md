# BUG-178: TG 进程有两个主人、三套「可用性」—— 同一次会话里「插件运行中」与「Telegram 不可用」并存

- 状态: fixed
- 发现日期: 2026-09-29
- 模块: engine+shell
- 严重程度: critical

## 现象

用户报告（2026-09-29）：**「哪里都显示『Telegram 不可用』，『Telegram 插件』为可用且开启，
全部逻辑都有严重问题，不符合核心设计和规范。」** 并追加裁定：**「daemon 为唯一启动，
服务的重启、kill 都应该是你自己负责，不应该是手动项。」**

同一次会话里两句互相否定的话同时为真：

| 位置 | 说的话 | 它实际在说哪个对象 |
|---|---|---|
| 设置 → 通用 | 「Telegram 插件 **运行中**」（开关开启） | orig-tg **进程**（daemon 托管） |
| 设置 → 账号 / TG 面板 | 「**Telegram 不可用**」 | Telegram **链路**（MTProto） |

而「链路不可用」里还混进了**根本不是故障**的两件事：没配 api_id/api_hash、没登录 ——
那都是**待用户完成的动作**。于是「去填个凭证」被渲染成红色故障，用户判定这整套逻辑自相矛盾。

## 根因

四个独立缺陷叠加，任一单独存在都不会产生这个观感：

| # | 事实 | 位置（修前） |
|---|---|---|
| 1 | **TG 进程有两个主人**：daemon 拉起并巡检，桌面壳另有 `spawn_tg`/`ensure_tg` 且用 `kill_port_owner(9877)` 硬杀，会杀掉 daemon 拉起的实例 | `src-tauri/src/lib.rs`（`spawn_tg` / `ensure_tg_inner` / setup 后台线程） vs `orig-daemon/src/state.rs` |
| 2 | **可用性只有一个词**：`/api/tg/session` 的 `available=false` 同时表示「没配凭证」「没登录」「连不上」，端点里没有 `api_configured`，前端无从区分 | `orig-tg/src/routes.rs::session`；`store/useStore.ts::refreshTgSession` |
| 3 | **门控掺了链路探测**：`resolveTgFeatureReady(tgEnabled, tgAvailability)` 用链路层的 `unreachable` 兜底判服务，而设置页只读 `tg_running` —— 两个真源各说各话 | `store/selectors.ts` |
| 4 | **端口有三份硬编码**：daemon `TG_PORT=9877`、壳 `TG_PORT=9877`、前端 `TG_PORT=9877`；且 9876/9877 落在本机 Windows 动态保留区（`netsh` 排除段 9857–9956），**没有任何监听者但 bind 恒 `WSAEACCES`(10013)** → 服务根本起不来 | `orig-daemon/src/state.rs`、`src-tauri/src/lib.rs`、`src/api/tg.ts` |

第 4 条是物理层：实测 `node -e` 对 9876/9877 直接 bind 返回 `EACCES`；
19786/19787 正常。第 2 条是观感层：它把「待办」翻译成「故障」。

## 修复

### 1. daemon 是 orig-tg 的**唯一所有者**（消除两个主人）

- 删除桌面壳侧全部 TG 进程管理：`spawn_tg` / `tg_alive` / `tg_service_real` /
  `ensure_tg_inner` / `ensure_tg` / `tg_status` / `TgState` / setup 后台拉起线程。
- `tg_save_config` 退化为「写 `tg/config.json` + 请 daemon 重启」，
  不再 `kill_port_owner`、不再自己 spawn。
- daemon 新增 `POST /api/tg/restart`（`tg_restart` = stop + start）；
  前端 `restartTgService()` 只是**请求**执行，不碰进程。
- 删除前端「重试连接」按钮（AccountsPanel / TgPanel）与 `lib/tgRetry.ts`；
  `mediaSources.ts::ensureAvailable` 改走 daemon 重启。

### 2. 可用性分两层（服务层 / 链路层）

- `types.ts`：新增 `TgServiceState`（enabled / running / port / lastError）与
  `TgLinkInfo`（`ready` / `needs_config` / `needs_login` / `link_down` / `unknown`）。
- `/api/tg/session` 补 `api_configured`，让「没配凭证」与「连不上」可分。
- `store.tgService` 唯一真源是 daemon `/api/config`；`store.tgLink` 由
  `resolveTgLink(session)` 推导；**服务不在就不问链路层**（问了只会把「服务没起来」
  报成「Telegram 连不上」）。
- 门控 `resolveTgFeatureReady(tgService)` 只问服务层。
- 文案：只有 `link_down` 用故障色；`needs_config` / `needs_login` 是引导。
  新增 i18n `tg.serviceDown*`、`tg.needsConfig*`、`tg.linkDown*`（zh + en）。

### 3. daemon 自愈覆盖链路断（消除手动项）

`tg_supervise` 两档：进程不在 → 拉起（spawn 冷却 60s）；进程在但**已配凭证却连不上** →
重启（链路重启冷却 300s）。判据 `tg_link_healthy_from` 把「没配凭证」排除在重启之外
（那是待办，重启一百次也修不好，还会顶掉刚填完凭证的实例）。

### 4. 端口单一真源 + 自动避让

- 默认端口迁移出保留区：daemon 9876 → **19786**，orig-tg 9877 → **19787**。
- daemon `bind_with_fallback`：首选端口绑不上就顺延扫最多 64 个，实际端口写入
  `<data_dir>/daemon.endpoint` 并随 `/api/config` 的 `port` 下发。
- `tg_reselect_port`：拉起前若端口不可绑定则顺延，结果记进 `tg_port`，随 `tg_port` 下发。
- 桌面壳读端点文件解析端口（缺失时扫描），`daemon_status` 返回**实际**端口。
- 前端 `api/daemon.ts::setDaemonPort` / `api/tg.ts::setTgPort`，base 改为每次现算；
  媒体库 `media.ts` 基址同步动态化。
