# BUG-347: 入库计数恒 0——后端已砍 `counts` 字段，前端仍在按它会存在的方式读取

- 状态: fixed
- 发现日期: 2026-10-21
- 模块: shell
- 严重程度: high

## 现象

用户夜报第 2 条：「入库流水线 在传 1 待处理 21 已缓存 73 内容显示错误」。

活实测（2026-10-21，真实运行栈 5180/19786/19787）：

- TG 侧入口（`tg-ingest-status`）显示 **在传 1 · 待处理 21 · 已缓存 73**；
- 打开面板，同一份数据的统计条（`cache-ingest-summary`）显示
  **已入库 0 · 入库中 0 · 入库失败 0**；分组页签（`cache-scope-*`）三条也全是
  `全部 · 0 / 已入库 · 0 / 入库失败 · 0`。

同一屏对同一事实给出两套互相否定的读数，且列表本体明明有 139 行。用户判定
「内容显示错误」——不是读数偏差，是读数恒零。

## 根因

后端 BUG-085 把 `GET /api/tg/cache/tasks/all` 的 `counts` 字段砍掉了（daemon 侧
从不读，砍得对），但消费端没跟着改：

1. `api/tg.ts:639-644` 仍把返回类型声明为必含
   `counts: Record<string, number>`——**类型层面谎称字段存在**，编译器因此永远
   不会提示；
2. `CacheManagerDialog.tsx:771` 读 `res.counts ?? {}` ⇒ 恒取空对象；
3. `groupCounts({})`（第 133 行）对空表求和 ⇒ `ingested/ingesting/failed/
   cancelled` 全 0；
4. 统计条与三个页签读数全部由它派生 ⇒ 恒 0。

而入口那三个数（`overview.active/stalled/done`）来自**另一条链**
（`useIngestGroups` ⇐ `/api/activity`）⇒ 两条链各说各话。

这是典型的「假可用」：字段消失以后，界面既不报错也不缺失，只是安静地显示 0。

## 修复（已实施）

1. **单一真源**：面板已拿到全量 `tasks` 列表，计数**本地派生**（`useMemo` 按
   `GROUP_OF` 归并），不再依赖服务端是否给 `counts`；
2. **删类型谎言**：`api/tg.ts` 的 `listAllCacheTasks` 返回类型去掉 `counts`
   （没有的字段就别声明它存在）；`load()` 的等值判据同步删掉
   `JSON.stringify(counts)` 段；
3. 双读数分裂由 BUG-349 的链合一收口。

## 验收证据

- 探针 `tauri-shell/verify/_probe_bug348_pipeline.cjs` 判据 S4：统计条三段
  `{"done":97,"active":0,"failed":26}` 之和 = 123 = 「全部」页签读数 = 列表
  行数（修复前同口径恒 `0/0/0`）——**验牙**：把派生装回 `groupCounts({})`
  空表后 S4(legacy) 实测全 0 FAIL（活库明明有 123 行）；
- 截图 `verify_shots/bug348-pipeline-rows.png`：统计条「已入库 97 · 入库中 0 ·
  入库失败 26」与页签「全部 · 123 / 已入库 · 97 / 入库失败 · 26」一致。

## 关联

- BUG-085：`counts` 字段的移除处（本 BUG 是它的半移除——只砍了生产者）；
- BUG-349：两条链同源双轮询（本 BUG 的读数分裂是它的表现面之一）；
- BUG-340：同 family「取不到 ≠ 没有」——这里变成了「没取到 ⇒ 报 0」。
