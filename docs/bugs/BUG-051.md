# BUG-051 三模块边界失守：展示/缓存/媒体库互相侵入（设计已定稿，P0–P4 实施）

- **严重级**: architecture / critical
- **状态**: partial —— **P0/P1 已实施并验收**（2026-09-19），P2–P4 待实施
- **报告轮次**: 2026-09-19 第一轮（用户裁定：「逻辑很乱，1 展示 / 2 缓存 / 3 媒体库三个模块分开讨论，相互设计实现互不影响」）

## 现象（按模块归属）

**M1 展示**
1. 相册网格写死 `aspect-square` + `object-contain`（`lib/tgmedia.ts:94-104`、`TgPanel.tsx:1696,1708`）→ 竖图左右、横图上下大片留白；7 图 `3+3+1` 瘸腿行空洞。
2. 一条记录只有「内容 + 介绍」两类数据：**无标题、标签完全未解析渲染**。
3. 状态四套真源打架：`downloadedPaths`(445-467) / `photoLibRefs`(749-770) / `cacheTask`(509-537) / `item.downloaded`(143)，写入时机不同。
4. `TgPanel.tsx` 1957 行：取数、状态机、展示同处一组件。

**M2 缓存**
5. `/api/tg/cache/clear` 名不副实——只清 dialog 列表缓存，不动字节、不动 `file_path`（routes.rs:538-546）。
6. `upsert_media_item` 的 `COALESCE(excluded.file_path, 旧值)`（store.rs:616）→ 传 NULL 时旧路径被粘住，清缓存无法置空。
7. 下载成功但入库失败只记日志、`downloaded=1` 保留 → 「已缓存未入库」（routes.rs:846-849）。
8. 两条独立清理链（`clear_stored` 1573-1592 / `delete_media_item` 1884-1902）非事务 → 孤儿文件、悬空 `file_path`（`local_file` 628-630 的 404 兜底即承认）。
9. `cache_task.dir` 建表未读；状态靠字符串约定无 DB 约束；缓存业务横跨 routes/store/state，端点挂 `/api/tg/` → 媒体库要读缓存态必须反依赖 TG。

**M3 媒体库 / 播放**
10. 单集多来源：剧集页有（SeriesDetail:470-487），**侧栏无**（EpisodeList:136-210）。
11. `1-2` 合集区间：仅剧集页渲染（SeriesDetail:407-411），侧栏（EpisodeList:183）与播放页（MediaViewer:120-123,135）取单点。
12. 卡片集号徽标：`MediaCard` 有 `episodeLabel` 但从未被传入（MediaLibraryPanel:723-731）。
13. 图片边界靠 `MediaViewer.modeOf` 兜底而非构造序列时排除（MediaLibraryPanel:205-223）。
14. 播放页无分集导航：`VideoPlayerProps` 仅 9 项、无 `episodes/currentIndex/onPrev`（VideoPlayer.tsx:48-63），切集在 MediaViewer（81-83,170-179）；`useSeriesDetail` 重复拉取（MediaViewer:65）。

## 根因

三个模块没有边界：缓存过程态挂在 TG 端、被媒体库反依赖；展示层自己判缓存态（四套真源）；
播放与剧集组织分离（播放器不知道剧集）。同一事实在多处各存一份 → 必然打架、必然互相破坏。

## 修复（设计定稿，未动代码）

- **边界**：M1 展示（只读+入队）/ M2 缓存（纯后端 `/api/cache/*`，过程态）/ M3 媒体库（唯一事实源）。
  事实态 = `media_item.file_path`，过程态 = `cache_task`，单向写入。
- **逻辑链固定顺序**：入队 → 登记事实 → 取字节（仅 video）→ 回填 → 终态显式；失败只失败字节。
- **唯一清理链**：清缓存 = unlink + 置空；删条目 = unlink + 删行同事务。
- **展示**：`layoutTiles()` justified-rows 动态拼图（上限 9）；四类数据（标题/介绍/内容/标签）；
  状态收敛到 `GET /api/media/state?refs=`；组件拆四层。
- **库/播放**：`episodeLabel()` 三处统一（含区间）；侧栏多源；序列构造排除非视频；
  播放页 = 剧集一等视图（播放器 + 分集侧栏，props 补 `episodes/currentIndex/onSelect/onPrev/onNext`）。

| 项 | 取证（修复前） | 修复 |
|---|---|---|

## 已实施（缓存管理功能集评估与收敛，2026-09-19 第四轮）

用户裁定：「清除记录和清空全部有什么区别？那清空失败、清空成功要不要？你这些不是无限叠加了吗？」

**根因**：把**动词**当成了要枚举的对象（单删 / 全删 / 清除记录 / 清除终态…），
每想到一个场景就长出一个按钮和一个端点 → 必然无限叠加（下一个就是「清空失败」）。

**评估结论——缓存管理只有两类对象，最小完备集为 5 个动词：**

| # | 动词 | 粒度 | 为什么缺一不可 |
|---|---|---|---|
| 1 | 取消 | 行级（活跃） | 停掉正在跑的任务，否则只能杀进程 |
| 2 | 重试 | 行级（失败类） | 失败记录重跑，否则只能回 TG 翻原消息 |
| 3 | 删除 | 行级（终态） | 移除**这一条**记录 |
| 4 | 清除 | 批量，范围 = `all\|success\|failed` | 移除**一批**记录；**动词只有一个，范围可组合** |
| 5 | 清除缓存文件 | 磁盘（全量） | 释放空间；配「占用读数」才有意义 |

三档范围**互斥且并集为全集**（`success` ∪ `failed` ∪ 活跃 = 全部记录），
因此不存在「要不要再加一档」的问题；活跃任务只有 `all` 档会动。
「清除记录」与「清空全部」的区别被消解为**同一动作的不同范围**，不是两个功能。

**改动**：
- `store.rs`：删 `clear_finished_cache_tasks` / `clear_all_cache_tasks`，
  合并为 `clear_cache_tasks(scope: TaskClearScope)` + `TaskClearScope::parse/predicate`。
- `cache.rs`：三档批量端点合并为 `DELETE /api/cache/tasks?scope=`；新增 `GET /api/cache/stats`
  （`files`/`bytes`/`external`——不知道占多少的「清除」是盲操作）；非法 scope 回 422（不静默当全部）；
  删除兼容别名 `/api/tg/cache/finished`。
- 前端：`clearAllCacheTasks`/`clearFinishedCacheTasks` → `clearCacheTasks(scope)` + `getCacheStats`/`clearCacheBytes`；
  `CacheManagerDialog` 顶部改为「磁盘占用读数 + 清除缓存文件」+「三档范围分段 + **唯一**清除记录按钮」，
  分段同时过滤列表（看什么就清什么）；重试改图标按钮；i18n 删 3 个重复键、增 10 个（中英）。

**实测发现（stats 读数）**：本机 `已缓存 1.9 GB · 19 个文件 · 94 个外部文件不纳入清理`
——外部文件计入读数但**永不删除**，避免误删导入/扫描进来的资料。
