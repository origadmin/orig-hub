# BUG-466: 下载主列表误用 /api/downloads/native（引擎单源）而非统一 /api/downloads（全来源）—— BUG-392 回归

- 状态: open
- 发现日期: 2026-10-27
- 模块: engine+shell
- 严重程度: high
- 排期: 2026-10-30

## 现象

用户在运行态实测发现：下载面板周期性发出 `GET /api/downloads/native`（来自 `useStore.refresh()`），
而非统一的 `GET /api/downloads?scope=...`。此前对 #9 的答复称「UI 走统一 `/api/downloads`、native
仅供调试」与实测不符——UI 主列表确实在调 native。

## 根因

下载列表为**双源拼装**，两个端点各说一半，违反 BUG-392「下载只有一个列表接口」的裁定：

1. 引擎段：`DownloadPanel` 的 `items` prop = `store.downloads`，由
   `useStore.refresh()`（`useStore.ts:519`）经 `listDownloads()`（`daemon.ts:61`）
   调用 `GET /api/downloads/native` 填充。该端点（`routes.rs:131` `list()`）只回**引擎行**
   （`engine_rows`，仅原生引擎任务）。
2. 入库段：`DownloadPanel` 的 `ingestRows` 来自 `useIngestGroups`（`useIngestGroups.ts:197`）
   经 `fetchDownloads('all')`（`daemon.ts:521`）调用 `GET /api/downloads?scope=all`，
   回**全来源合并** `ActivitySnapshot`（引擎 + TG + BT）。

由此：同一个下载列表，引擎行走 native、入库行走 unified，等于 BUG-392 当年要灭掉的
「两个 endpoint 各说一半」重现。

### 代码内部注释自相矛盾（根因的元层）
- `routes.rs:766` 明确规定 native 是「**调试/详情投影，非 UI 列表路径**」；统一接口是 `/api/downloads`。
- `daemon.ts:55-59` 反向注释称「速度/分块等引擎原生字段只有 native 才有，store 必须取这一支」——
  **与代码事实相反**：统一端点的 `ActivityTask`（`activity.rs:200-220`）**已含 `speed: Option<f64>`
  与 `progress: f64`**，原生字段并未丢失。该注释是 native 残留调用的错误合理化依据。

## 复现

1. 起 dev 栈，打开下载面板；
2. 网络面板可见周期性 `GET /api/downloads/native`（useStore 轮询）与 `GET /api/downloads?scope=all`
   （useIngestGroups 轮询）并存；
3. 引擎任务数 == native 端点行数，入库任务数 == unified 端点 `tasks` 中 `cache` 类行数。

## 修复

将 `useStore.refresh()` 改用统一端点，消除原生端点对主列表的供给：

1. `useStore.refresh()` 改调 `fetchDownloads('all')` 取 `ActivityTask[]`；
2. `store.downloads` 类型由 `DownloadStatus[]` 改为 `ActivityTask[]`（或做 `ActivityTask -> DownloadStatus`
   映射，保持下游 `DownloadItem` 契约不变）；
3. `MainLayout` 的速度聚合 / `downloadingCount` 等选择器（`selectActiveCount` / `selectActiveSpeedLabel`）
   改为从 `ActivityTask[]` 取数，确认口径与 `useIngestGroups` 完全一致（同一真源）；
4. `listDownloads()`（`/api/downloads/native`）降级为**仅调试用途**（如 `StatusBarDebug` 详情投影），
   或从 UI 调用面移除；
5. 回归：侧栏徽标、状态栏读数、速度聚合、全部下载页在 dev 栈 + CDP 下验证单一端点、无双源。

## 关联

- BUG-392（统一列表/状态变更端点，全来源一个接口）—— 本缺陷是其回归。
- BUG-447 / BUG-455（i18n key 漏补，同类「引入即漏」问题）。

（修复后补：dev 栈网络面板证实下载主列表仅调 `GET /api/downloads?scope=...`，不再有
`GET /api/downloads/native` 作为列表供给；引擎任务与入库任务合并出现在同一端点响应中。）
