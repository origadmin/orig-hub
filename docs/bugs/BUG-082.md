# BUG-082: 左侧 Navi 缺「下载中 / 已完成」状态筛选（被开关整体隐藏，无替代筛选入口）

- 状态: open
- 发现日期: 2026-09-20
- 模块: shell
- 严重程度: mid

## 现象

用户：「最左边的 Navi 栏好像被删掉了几个核心，之前有 全部 / 下载中 / 已完成 这些和
『全部文件』配合的导航筛选，现在没有了，怎么筛选？需要评估下功能，我说的可能有遗漏或者多余。」

现状核对（`tauri-shell/src/components/Sidebar.tsx:30-31`）：

```ts
const DOWNLOAD_MODULE_HIDDEN = true
const HIDDEN_VIEWS: ViewId[] = ['downloading', 'completed']
```

`NAV_ITEMS` 里 downloading / completed 两项**仍然存在**（图标、i18n key `nav.downloading`
/`nav.completed`、计数徽标逻辑全在），只是在第 264-267 行被 filter 掉。所以"被删掉"的
观感来源是**一个开关**，不是代码删除——恢复只需把该常量置 `false`。

## 根因

这不是代码缺陷，而是**一次产品裁定留下的可逆开关与当前诉求脱节**：

- 开关注释记录了当时的裁定：「下载不需要，因为不使用这个下载逻辑——主流程是
  TG 抓取 → 缓存入库 → 媒体库管理/播放，不经过 orig-daemon 的下载任务队列」。
- 但用户现在要筛选下载状态，且同期（BUG-083）又要求顶部下载工具栏常显——
  两者合起来指向"下载仍是可被查看的一等公民"。
- 更关键的是：**隐藏后没有任何替代筛选入口**。`view` 只影响侧栏选中态，
  内容区没有状态筛选控件，"全部文件"下也无法按状态收窄 → 筛选能力真的归零了。

## 复现

1. 启动应用 → 看左侧导航：只有 Orig Hub / 全部文件 / 媒体库 / TG(需绑定) / 设置；
2. 无「下载中」「已完成」两项，也无任何下拉/页签可按下载状态过滤；
3. 把 `DOWNLOAD_MODULE_HIDDEN` 改 false → 两项立即回归（可逆性自证）。

## 修复

**待拍板**（见「设计裁定」）。技术上是可逆的一行开关，但要不要恢复取决于下载模块在
产品里的定位是否与 BUG-077（缓存 vs 下载）的结论一致：

- 若确认"下载仍要可见" → `DOWNLOAD_MODULE_HIDDEN = false`，导航完整恢复，
  计数徽标（`counts.active` / `counts.completed`）自动生效。
- 若确认"下载不再是一等公民" → 则应**同时移除** `NAV_ITEMS` 里这两项与 `HIDDEN_VIEWS`
  死代码，并把下载状态筛选能力挪到它真正该在的地方（否则留着开关就是长期负债）。

无论哪种，都要消除"隐藏了但没替代入口"这一当前状态。

## 设计裁定（产品经理评估，2026-09-20）

**判断：用户想筛的是 TG 缓存任务状态，不是下载队列。** 依据三条：

1. 主流程不经 daemon 下载队列，`listDownloads()` 恒空 → 即便恢复，「下载中/已完成」也是
   两条**永远 0 徽标的空视图**；
2. 真正被等待的状态机是 **TG 缓存任务**（queued/running/done/failed/cancelled/interrupted），
   且筛选**已存在**（`CacheManagerDialog` 三档 all/success/failed），只是埋在
   「TG 面板 → 缓存管理弹窗」两层之下；
3. 用户记的是旧壳子（全部/下载中/已完成 = 同一 downloads 列表的三档）——他要的是
   **"按状态收窄"的能力**，不是这三个词。

补充事实：开关只砍 `downloading/completed`，同源的「全部文件」（`view='all'` → `DownloadList`）
仍硬编码在侧栏 → **半成品**：留了一个空列表入口却没有筛选。

**推荐方案（方案 3：不恢复，把筛选上提到 TG 缓存任务）**

| 优先级 | 动作 |
|---|---|
| P0 | TG 面板内直接提供缓存任务三档筛选（全部/进行中/已完成）+ 计数徽标，不再藏在弹窗里 |
| P0 | 「全部文件」连同下载导航一并纳入 `DOWNLOAD_MODULE_HIDDEN` 下线；开关保留作回滚保险，**不删代码** |
| P1 | 清理 `MainLayout` 的 downloading/completed 分支与 `DownloadList` 依赖 |

理由：把筛选能力放到**有数据的对象**上，而不是恢复两个空视图。
取舍：方案 1（直接改 false）零成本但引入空视图 + 暂停/继续误操作；方案 2（彻底删死代码）
干净但失去回退；方案 3 正确但需动 TG 侧（P1 工作量）。

## 待拍板①：daemon 下载队列是「永久弃用」还是「暂不使用」？

- **因果**：开关隐藏了下载入口但代码与入口残留，用户因此**反复回来问**；根因是当初的裁定
  只写了"不使用"，没写"是否删除"。
- **选项**：(a) 保留开关 + 死代码（可逆，但会继续被问）；(b) 全量删除下载模块。
- **建议**：(a)。并把「全部文件」一并纳管，消除"留一个空列表入口却无筛选"的半成品状态。
