# BUG-082: 左侧 Navi 缺下载队列状态筛选（全部 / 下载中 / 已完成 被开关隐藏，且无替代入口）

- 状态: fixed
- 发现日期: 2026-09-20
- 模块: shell
- 严重程度: mid

## 现象

用户：「最左边的 Navi 栏好像被删掉了几个核心，之前有 全部 / 下载中 / 已完成 这些和
『全部文件』配合的导航筛选，现在没有了，怎么筛选？需要评估下功能，我说的可能有遗漏或者多余。」

现状核对（`tauri-shell/src/components/Sidebar.tsx:30-31`）：

```ts
const DOWNLOAD_MODULE_HIDDEN = true
const HIDDEN_VIEWS: ViewId[] = ['downloading', 'completed']
```

`NAV_ITEMS` 里 downloading / completed 两项**仍然存在**（图标、i18n key `nav.downloading`
/`nav.completed`、计数徽标逻辑全在），只是在第 264-267 行被 filter 掉。所以"被删掉"的
观感来源是**一个开关**，不是代码删除——恢复只需把该常量置 `false`。

## 结论更正（2026-09-21，产品经理）

**先前评估作废。** 先前结论为「用户想筛的是 TG 缓存任务状态，不是下载队列 → 方案 3：不恢复，
把筛选上提到 TG 缓存任务」，已被用户否决，原话：

> 「不对和TG没关系,我说的是下载.APP核心是一个下载工具.」

**正确立场：本应用的核心是一个下载工具，Navi 栏缺的是「下载队列」的状态筛选，与 TG 缓存任务无关。**
下载队列是一等公民，TG 至多是它的一条数据来源（见待拍板③）。本文后续评估一律站在这个立场上。

## 根因

不是代码缺陷，而是**一次过期的产品裁定**：开关把下载降级为"不使用"，但产品定位从未改变——
下载仍是这个应用的主业。裁定与新认知脱节后留下了三个具体后果：

1. **筛选能力归零**：`view` 只影响侧栏选中态，内容区没有任何状态筛选控件，"全部文件"下也
   无法按状态收窄 → 隐藏即等于删除了该能力（无替代入口）。
2. **半成品状态**：开关只砍 `downloading/completed`，同源的「全部文件」（`view='all'` →
   `DownloadList`）仍硬编码在侧栏 → 留了一个全量列表入口，却拿不到任何子集。
3. **口径已经漂移**：`MainLayout.tsx:109-118` 里 `downloading` 视图实际装的是
   `downloading|queued|paused|idle|error` 五个状态，而 `completed` 只装 `completed`
   （`:92`）。七个真实状态里 `cancelled` **两边都不在**，只在「全部文件」里可见。

## 复现

1. 启动应用 → 看左侧导航：只有 Orig Hub / 全部文件 / 媒体库 / TG(需绑定) / 设置；
2. 无「下载中」「已完成」两项，也无任何下拉/页签可按下载状态过滤；
3. 把 `DOWNLOAD_MODULE_HIDDEN` 改 false → 两项立即回归（可逆性自证）。

## 需求评估：三档够不够（站在"这是下载工具"的立场）

引擎真实状态机（`tauri-shell/src/types.ts:2-9`，与 Rust `DownloadStatus` 对齐）共 7 态：
`idle` / `queued` / `downloading` / `paused` / `completed` / `error` / `cancelled`。
用户提的三档只覆盖其中 2 个状态 + 一个全集，**剩下 5 个状态没有归宿**。逐档给结论：

| 档位 | 覆盖状态 | 优先级 | 判断理由 |
|---|---|---|---|
| 全部 | 全集 | **P0** | 基准入口，问题不大 |
| 下载中 | `downloading`（+`queued`+`idle`） | **P0** | 用户明确要，且是"现在正在动"的那一批，最高频 |
| 已完成 | `completed` | **P0** | 用户明确要，是"收尾/找文件"的入口，配「清除已完成」按钮 |
| **已暂停** | `paused` | **P0** | **必须补**。暂停是下载器最典型的"用户介入态"：暂停之后用户一定要能"回到这批任务继续"。现在 `paused` 被塞进「下载中」，而顶部恰好有「继续全部」按钮（`MainLayout.tsx:188-199`）却没有一个能列出被暂停任务的视图 → 按钮有、对象找不到。且 `paused` 不计入 `counts.active`（`:90`），也不计入 `counts.completed` → 暂停的任务**在任何徽标上都不显示**。 |
| **失败 / 错误** | `error` | **P1** | **应补**。`DownloadList` 已带 `onRetry`，失败项需要被"找出来重试"。混在「下载中」里会被误读成"还在跑"，用户干等。失败是终态，不是进行中。 |
| **已取消** | `cancelled` | **P1** | **应补**。取消 ≠ 已完成：文件不完整、不能当成果看。当前它两边都不进，是死角；而 `useStore.ts:304` 的「清除已完成」却又把 `cancelled` 一并清掉 → 清的是看不见的东西。要么给档位，要么明确"取消即删除记录"。 |
| 等待中 | `queued` | **P2** | 暂不独立成档。仅在有并发上限时才有区分价值（排队 ≠ 在跑），现阶段并入「下载中」足够；等有了并发队列上限再拆。 |
| 已做种 / 种子 | — | 不做 | 本引擎无做种能力，无对应数据源，不臆造。 |

**一句话结论：三档不够，最小可用集合是 5 档（全部 / 下载中 / 已暂停 / 已完成 / 失败·已取消）。**
用户那句"可能有遗漏或者多余"的直觉是对的——**遗漏**的是暂停与失败这两类终态/介入态，
**多余**的目前没有（等待中不独立即是对"多余"的克制）。

附带要修的一致性（属 P0 的一部分，不是新需求）：

- 徽标口径：`counts.active` 只算 `downloading|queued`（`:90`），但「下载中」视图还显示
  `paused|idle|error` → **点进去的条数 ≠ 侧栏徽标数**。档位定死后两者必须逐一对齐。
- 「清除已完成」（`:200-210`）清的是 `completed|error|cancelled`（`useStore.ts:304`），
  但它在 `view === 'completed'` 下才显示 → 清掉了不在该视图里的项。要么把 `error/cancelled`
  纳入「已完成」档（语义改名"已结束"），要么让清除只作用于视图内可见项。

## 需求评估：这些筛选与「全部文件」是什么关系

现状是**同级互斥**，不是下钻：

- 「全部文件」是独立渲染的顶层项（`Sidebar.tsx:176-234`，不在 `NAV_ITEMS` 里，不受开关管辖）；
- `downloading` / `completed` 是与它平级的另一个 `ViewId`；
- **分类**（自动分类目录）才是「全部文件」的下钻子项：`Sidebar.tsx:240` 的激活条件是
  `view === 'all' && categoryFilter === cat`，且 `MainLayout.tsx:104-107` 一切换视图就
  `setCategoryFilter(null)`。

也就是说：进「下载中」就丢掉分类，选了分类就回不到状态。**两个维度不能叠加**——
"某分类里正在下载的那几个"这个问法在当前模型下不可表达。这正是用户说"和『全部文件』
配合"时的痛点：他记忆里的配合是这三个词构成一**组**筛选，而不是三个互斥的页面。

**结论：应该是两个正交维度。**

- **状态** = 顶层视图（全部 / 下载中 / 已暂停 / 已完成 / 失败·已取消），决定"看哪一批"；
- **分类** = 当前状态视图下的子筛选，决定"这批里再看哪一分类"。

对应到模型上的改法：`ViewId` 侧保留状态语义，分类从"`all` 的下钻"升级为"任意状态下可用"，
即把 `Sidebar.tsx:240` 的 `view === 'all'` 约束和 `MainLayout.tsx:105` 的清空逻辑一并放开。
`baseVisible → visible` 的两段式过滤（`:109-121`）结构已经是对的，只需让 `categoryFilter`
不再与 `view` 绑定。

优先级：**正交化 P1**（先恢复 P0 的档位，正交化紧随；不做正交化，用户仍会在"分类 + 状态"
上撞墙）。

## 修复

已实施（2026-09-20），档位按待拍板①的 **(b) 五档** 定案：

1. **取消隐藏开关**：删除 `Sidebar.tsx` 的 `DOWNLOAD_MODULE_HIDDEN` / `HIDDEN_VIEWS`
   及那条「下载不需要」的依据注释 —— 该依据已被用户纠正推翻（原话「APP核心是一个下载工具」），
   不做可逆开关，直接删除。
2. **扩档**：`ViewId` 由 6 值扩到 8 值，新增 `paused` / `failed`；`NAV_ITEMS` 顺序
   downloading → paused → completed → failed → media → tg → settings；补两枚内联 SVG
   与 `nav.paused` / `nav.failed` 双语键。
3. **七态归四档**（`MainLayout.tsx` 的 `baseVisible`）：
   downloading ← `downloading|queued|idle`；paused ← `paused`；completed ← `completed`；
   failed ← `error|cancelled`。`idle` 归入下载中档 —— 否则它在四档皆不可见，成为死角。
4. **徽标口径与视图口径统一**：新增 `downloadingBucket`（含 `idle`）同时驱动档位列表、
   侧栏徽标与状态栏计数，使「点进去的条数 == 侧栏徽标数」。跨组件 props 字段由
   `counts.active` 重命名为 `counts.downloading` —— 原命名与 `MainLayout` 内部的
   `active`（不含 idle，驱动速度合计与「全部暂停」可用性）同名不同义，正是本次口径
   漂移的滋生土壤。
5. **消除第二个死按钮**：失败·已取消页同样挂「清空」，其 disabled 判据改用新增的
   `selectHasClearable`（扫 `completed|error|cancelled`，与 `useStore.clearCompleted`
   严格同口径）；原 `selectHasCompleted`（只扫 `completed`）作为误导性死代码一并删除。
6. 默认落地视图 `media` → `all`；TG 未绑定 / 不可用时的兜底同样改为 `all`。
7. 状态栏 `main.status` 追加 `{failed}`；`main.clearHint` 改为「清空已完成与失败记录」
   （原「清空已完成列表」与实际行为不符 —— 它会连带清掉 error/cancelled）。

### 七态归属穷举（源码行级解析驱动，非手填）

口径取自 `tauri-shell/src/components/MainLayout.tsx`：

| 变量 | 状态集合 | 消费方 |
|---|---|---|
| `active`（:102） | `downloading\|queued` | 仅 `totalSpeed` |
| `downloadingBucket`（:109-111） | `downloading\|queued\|idle` | 档位列表 / 侧栏徽标 / 状态栏 |
| `paused`（:112） | `paused` | 已暂停档 |
| `completed`（:113） | `completed` | 已完成档 |
| `failed`（:115） | `error\|cancelled` | 失败·已取消档 |
| `aggregate`（:119-121） | `downloading\|queued\|paused` | 全局进度条（BUG-004，未改动） |

归属结果：`idle` / `queued` / `downloading` → 下载中；`paused` → 已暂停；
`completed` → 已完成；`error` / `cancelled` → 失败·已取消。
**每态恰好落进一档，孤儿态 0**（`idle` 归入下载中档正是为了避免死角）。

徽标（7 态各一条时）：**3 / 1 / 1 / 2，四档之和 = 7 = `counts.total`**；
状态栏四数之和 = 7。对照旧口径（`active` 不含 `idle`）之和 = 6，少算 1 条 ——
即「徽标数 ≠ 点进去的条数」这一 P1 现象已消除。

命门断言（防回归）：`active` 与 `downloadingBucket` **仍然分离**，未被合并。
若被合并，徽标数反而正确，但「全部暂停」会在只有 `idle` 任务时亮起却空转 ——
死按钮以假绿形式回归。二者消费路径已在源码中分别注释锁定。

### 死按钮回归

- 失败·已取消页挂「清空」，其 disabled 判据为新增的 `selectHasClearable`
  （`tauri-shell/src/store/selectors.ts`），扫描口径与 `useStore.clearCompleted`
  （`useStore.ts:302-310`）**逐字一致**，均为 `completed|error|cancelled`；
  原只扫 `completed` 的 `selectHasCompleted` 已作为误导性死代码删除。
- 验收脚本 `tauri-shell/verify/shot_context_bar.cjs` 断言：
  `nav-completed` / `nav-failed` 必须有「清空」，`nav-downloading` / `nav-paused` 必须无。

### 未覆盖（如实记录）

- **未跑真实 UI 冒烟**：`shot_context_bar.cjs` 需要 dev server + 真实 daemon，
  本轮结论均来自源码解析、类型检查与门禁，非浏览器实测。

## 已知语义偏差（非缺陷，待用户裁定文案）

「下载中」档含 `queued`（列表显示「排队」）与 `idle`（显示「空闲」），因此侧栏徽标
「下载中 N」可能包含并非「正在下载」的任务。**数是严格对齐的**（这是 P0 要求），
但标签语义有轻微偏差。改名（如「进行中」）属产品文案决策，本轮不擅改 —— 见待拍板④。

## 待拍板①：恢复下载状态导航，并把档位定在哪一档？

- **因果**：Navi 栏现在没有任何下载状态筛选，而这是下载工具的主导航；根因是
  `DOWNLOAD_MODULE_HIDDEN = true` 这个过期裁定，且隐藏后无替代入口，筛选能力为 0。
  不决定 → 用户每次要找"正在下的/下完的/暂停的"都得在「全部文件」里肉眼翻，
  且「继续全部」「清除已完成」这批按钮找不到作用对象。
- **选项**：
  - **(a) 原样恢复三档**（全部 / 下载中 / 已完成）—— 改 1 行，零风险；但七个状态里
    `paused` / `cancelled` / `error` 仍无归宿（暂停的进不了任何徽标、取消的是死角），
    「下载中」还会装进 `error`，把失败伪装成进行中。**省事但留坑。**
  - **(b) 恢复并定档五档**（全部 / 下载中 / 已暂停 / 已完成 / 失败·已取消）—— 覆盖全部
    7 个状态，徽标与视图可对齐，代价是要新增 2 个 `ViewId` + 2 个 i18n key + 图标，
    并重写 `MainLayout.tsx:109-118` 的划分逻辑。**工作量小（半天内），语义干净。**
  - **(c) 不恢复，改用列表内的状态下拉筛选** —— 保住一个筛选控件，但丢掉"侧栏常驻 +
    带计数徽标"这个下载器的标准形态，且与用户明确要求（"之前有的那几个"）相反。**不推荐。**
- **建议**：**(b)**。理由：下载工具的状态导航是这个应用的主导航，档位划分必须与引擎真实
  状态机（7 态）一一对应，否则就是在 UI 上制造第二个不一致的真源——这正是本项目反复踩的坑
  （BUG-069 分集/条目双真源、BUG-050 规则未成文）。多出的两个档位不是功能膨胀，
  是补齐已有状态；同时保留 `DOWNLOAD_MODULE_HIDDEN` 开关作回滚保险，不删代码。

## 待拍板②：状态筛选与分类筛选是「同级互斥」还是「正交下钻」？

- **因果**：现在切到「下载中」就清空分类、选了分类就回不到状态（`MainLayout.tsx:104-107`
  与 `Sidebar.tsx:240`），两个维度不能叠加；根因是把分类建模成了「全部文件」的私有下钻，
  而状态是与之平级的另一个 `ViewId`。不决定 → "某分类里正在下载的那几个"不可表达，
  用户会在恢复档位后立刻撞上同一堵墙。
- **选项**：
  - **(a) 维持同级互斥** —— 改动量为 0，心智模型简单（一次只按一个维度看）；
    但分类只在「全部」下有效，状态视图里分类被强制清空，能力是残缺的。
  - **(b) 改成正交**（状态 = 顶层视图，分类 = 该视图下的子筛选）—— 放开
    `Sidebar.tsx:240` 的 `view === 'all'` 约束与 `MainLayout.tsx:105` 的清空逻辑，
    `baseVisible → visible`（`:109-121`）两段式结构本就支持；代价是侧栏要能表达
    "分类处于哪个状态下"，且空态文案要说清"该状态下此分类无匹配"（避免重蹈 BUG-042
    把筛选空态显示成"库是空的"）。
- **建议**：**(b)**，且排在 P1（紧跟待拍板①之后做，不与之并行）。理由：用户原话就是这三个词
  「和『全部文件』配合」——配合即叠加，不是三选一。而 (b) 的实现面只有两处约束放开，
  风险低于它带来的语义收益。

## 待拍板③：恢复后下载队列可能为空 —— 队列的数据源要不要扩充？

- **因果**：开关的旧注释称主流程"不经过 orig-daemon 的下载任务队列"，若属实，恢复档位后
  会出现 0 徽标的空视图，等于"修好了入口却没内容"；根因是**数据来源问题**，不是筛选 UI
  问题（这正是上一轮评估把筛选搬去 TG 的诱因，那条路已否决——筛选必须是下载队列的筛选）。
  不决定 → 恢复动作可能交付一组空视图，用户会二次回来问。
- **选项**：
  - **(a) 先恢复 UI，队列内容由「新建下载」自然产生，空就空** —— 改动最小、不牵扯引擎；
    但要给空视图配明确文案（"还没有下载任务"），且短期内主流程确实不产生队列项。
  - **(b) 恢复 UI + 按 BUG-077 的 `activity.rs` 只读聚合，把 TG 缓存任务以「下载任务」
    的身份并入同一队列视图** —— 队列立刻有内容、徽标有数；代价是要动引擎侧聚合端点，
    且必须保住"下载任务"的身份语义（暂停/继续/重试/清除等动作仍各自分流，
    不统一引擎与存储——这是 BUG-077 已定的结论）。
- **建议**：**(b)**，但拆成两步走：先按 (a) 恢复 UI 并配好空态（P0，可立即交付），
  再接 (b) 的聚合（P1，与 BUG-077 同一批）。理由：**入口与内容是两件事，不该互相阻塞**——
  入口缺失是当下的缺陷，内容不足是下一步的演进；而且合并后的队列仍然是"下载队列"，
  TG 缓存只是它的一条数据来源，这与用户「和 TG 没关系，我说的是下载」的口径不冲突。

## 待拍板④：「下载中」档含排队 / 空闲，档名要不要改？

- **因果**：五档定案后「下载中」档覆盖 `downloading|queued|idle` 三态，因此侧栏徽标
  「下载中 N」里可能含有列表显示为「排队」「空闲」的任务；根因是引擎状态机有 7 态而
  档位只有 4 档，中间态必须寄居在某一档，而把它独立成档又会让低频态占据一级导航。
  不决定 → 用户点开「下载中」看到一条写着「空闲」，会怀疑筛选错了。
- **选项**：
  - **(a) 维持「下载中」**（当前状态）—— 成本 0，数是严格对齐的；代价是标签与内容有
    轻微语义偏差。
  - **(b) 档名改「进行中」/「下载队列」** —— 仅改 `nav.downloading` 双语两处，语义更
    包容；代价是偏离用户原话里「下载中」这个说法。
  - **(c) 状态栏单列 `idle` 位** —— 档位徽标只算档位、状态栏再加第 5 个数；需动
    `main.status` 模板 + 双语 + 传参，成本最高，且档位徽标的偏差依然存在。
- **建议**：**(a)**。用户明确列举的档名就是「下载中」，改文案属于产品决策，不应在事故
  修复轮次里顺手替他改；且 `queued` / `idle` 在真实队列里占比很低。若日后中间态变多，
  再按 (b) 改名。
