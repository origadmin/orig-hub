# BUG-282: 后端未启动时前端持续发失败请求 + 资源占用爆炸（无失败退避、无熔断、无请求取消）

- 状态: open
- 发现日期: 2026-10-12
- 模块: shell
- 严重程度: high
- 排期: 2026-11-10

> 来源：用户 2026-10-12 报障「大量错误请求，这应该是后台没有启动。这种情况下依然乱七八糟请求一大堆，而且资源占用爆炸。」
> **本档为任务文档**（用户定：纯文档任务，代码由别的组负责）。

## 现象

当**后端未启动 / 不可达**时（`orig-tg` 默认 `127.0.0.1:19787`、`orig-daemon` `127.0.0.1:19786`），前端：

1. **持续发失败请求** —— 不是停一下或退避，而是按固定节拍**永续**重发（实测稳态约 18 次/分钟，见「根因·事实 5」），且每次切换视图再叠加一批。
2. **资源占用爆炸** —— 后端不可达时**每 5s 整棵组件树重渲染一次**（永不停止）、EventSource 泄漏、无请求取消、会话期集合无界增长（见「根因·事实 6」）。

关键：这不是「后端**在**时请求过多」（那是 BUG-239 / BUG-241 的形态），而是「后端**不在**时**失败请求不退避、无熔断**」的**独立失效模式**。

## 根因

**前端缺少「后端不可达」的失败退避与熔断；`AGENTS.md:82` 明列的「轮询三律」中「失败退避」这一条未实现。**

`AGENTS.md:82`（设计规则原文）：
```
轮询三律（有活才轮／等值短路／失败退避）+ 频率上限 5s + 同一数据单一轮询源
```
实现只对 SSE 落实了退避，其余 5s 轮询类全部缺失。

### 事实 1：常驻 5s 兜底轮询在 SSE 断线时无条件重发（最高优先级）

`tauri-shell/src/components/MainLayout.tsx:73-78`：
```ts
// 定期刷新兜底：仅在 SSE 断线（connected=false）时真正拉取，避免健康连接下每 5s 空轮询
const timer = setInterval(() => {
  if (useStore.getState().connected) return
  refresh().catch(() => {})
}, 5000)
return () => clearInterval(timer)
```
- 触发条件 `connected === false`（SSE 未连通）；后端全关时**恒为 false** ⇒ 每 5s 必发一次失败请求（`refresh()` → `listDownloads()` 打 daemon:19786）。
- **失败后按原间隔继续，永不清定时器、永不退避** ⇒ 12 次/分钟、永久。

### 事实 2：SSE 重连是唯一有退避的地方，但无终止、且 teardown 被丢弃

`tauri-shell/src/api/daemon.ts:280-288`：
```ts
es.onerror = () => {
  es?.close()
  es = null
  if (!closed) {
    onError?.(new Error('SSE connection lost'))
    setTimeout(connect, retryMs)
    retryMs = Math.min(retryMs * 2, 10000)
  }
}
```
- 指数退避 1s→2s→4s→8s→10s 封顶，**全仓唯一退避**；但**永不停止**（10s 封顶后稳态 6 次/分钟）。
- 且 `subscribeEvents`（`api/daemon.ts:249-296`）返回的取消函数在调用处 `tauri-shell/src/store/useStore.ts:291` **被丢弃**（无赋值、无 teardown）⇒ 连接生命周期无人管理。

### 事实 3：两个条件轮询在「后端不在」时守卫失效

- `tauri-shell/src/components/TgPanel.tsx:799-803`：
  ```ts
  useEffect(() => {
    if (tgBroken || !hasActiveTask || cacheManagerOpen) return
    const timer = setInterval(() => void refreshCacheTasks(), 5000)
    return () => clearInterval(timer)
  }, [tgBroken, hasActiveTask, cacheManagerOpen, refreshCacheTasks])
  ```
  守卫用 `tgBroken`（=`tgLink.state === 'link_down'`），但 **orig-tg 进程不在**时 `refreshTgState` 在 `useStore.ts:631-633` 提前 `applyLink({ state: 'unknown' })` ⇒ **`tgBroken` 恒 false，守卫不生效**；`refreshCacheTasks` 的 `catch {}` 静默吞错（`TgPanel.tsx:784-786`，注释写「下次轮询/操作会重试」），`hasActiveTask` 保持旧值 ⇒ 每 5s 继续发失败请求。
- `tauri-shell/src/components/CacheManagerDialog.tsx:779-787`：
  ```ts
  const hasActive = tasks.some((x) => ACTIVE_STATUS.has(x.status))
  useEffect(() => {
    if (!hasActive) return
    const iv = setInterval(() => { setNowMs(Date.now()); void load() }, 5000)
    return () => clearInterval(iv)
  }, [hasActive, load])
  ```
  `load()` 失败只 `setErr`（`CacheManagerDialog.tsx:754-755`），`tasks` 不变 ⇒ `hasActive` 恒 true ⇒ 面板开着就每 5s 发失败请求 + 每 5s 触发重渲染。

### 事实 4：请求层不重试，但也**不携带失败原因**、无人据此停止

- `tauri-shell/src/api/tg.ts:83-103`：`fetch` 抛错 → `throw new Error(tgFailureMessage(0, '', ...))` —— **status=0 就是「连接被拒」的编码**，但只包成 `Error(message)`，**不带 status** ⇒ 调用方无从分支，只能 `setError`。
- `tauri-shell/src/api/daemon.ts:37-51` `request()`：**无 try/catch**，`fetch` 拒绝以 `TypeError` 原样上抛。
- 全仓 `AbortController` **零命中** ⇒ 无请求取消；`tauri-shell/src/lib/fetchCache.ts` 失败不入缓存 ⇒ 后端挂时每个调用点都真发请求，缓存层不提供失败短路。

### 事实 5：失败请求速率估算（后端全关、停留默认视图）

| 来源 | 算式 | 速率 |
|---|---|---|
| 事实 1 daemon 兜底轮询 | 1 req / 5s | **12 / min** |
| 事实 2 SSE 重连（10s 封顶） | 1 req / 10s | **6 / min** |
| **稳态合计** | | **≈ 18 / min，永久持续** |

- 打开缓存管理面板且存在遗留活跃任务：+12/min（事实 3）。
- 每切换一次视图：额外一批一次性失败（TG 面板 ≥3、媒体库 ≥1~3、设置页 ≥6）。

⇒ **不是「每秒几百」的瞬时爆发（那是 BUG-239 / BUG-241），而是「永不停止的周期性失败 + 每次交互叠加一批」**，长时间运行下累积请求数与日志量持续增长。

### 事实 6：资源爆炸来源

1. **整树重渲染节拍**：`MainLayout.tsx:36` 用 `useStore()` **无选择器**订阅整个 store；事实 1 每 5s 调 `set({ loading, error })` 与 `setDaemonAlive(false)`（`useStore.ts:384-391` / `:396-397`，后者经 `daemonWithAlive` **每次生成新对象**）⇒ 后端不在时**每 5s 整棵树重渲染一次，永不停止**。
2. **EventSource 泄漏**：`subscribeEvents` 的 teardown 被丢弃（事实 2）；`tauri-shell/src/main.tsx:14` 的 `<React.StrictMode>` 使 dev 下 `init()` 双调用 ⇒ **两个 EventSource 各跑一套重连**，都永不关闭。
3. **无请求取消**：`AbortController` 零命中；面板卸载时在途 `fetch` 不被 abort，只在 `cancelled` / `alive` 标志处丢弃结果，请求本身继续占连接。
4. **会话期无界集合**：`TgPanel.tsx` 的 `photoCheckedRef` / `reportedFailuresRef` / `entryStateHoldRef` / `albumProgressHoldRef`、`lib/fetchCache.ts` 的 `inflight` / `resolved` Map、`lib/poster.ts` 的 `inflight` / `doneCache` Map 均**无淘汰**。
5. **已排除**：`URL.createObjectURL` 全仓零命中（非泄漏源）。

### 后端侧边界（不是误判来源）

- `orig-tg` 关闭后 19787 **无人监听 → 连接被拒**，`fetch` 直接 reject（`api/tg.ts:93-96`），**不是 404、更不会被 SPA fallback 变成 200**（vite 固定 `strictPort` 5180，未配置 `server.proxy`，前端直连 19787）。
- 故「后端没起」被**正确识别为失败**；真正的问题是识别出失败后**前端不据此停止 / 退避**。
- 薄弱点：daemon **在**、orig-tg **不在** 时 `getConfig()` 仍成功；若 daemon 此时误报 `tg_running=true`，`resolveTgFeatureReady` 会放行 TG 入口，而 `tgBroken` 仍为 false（同事实 3），仅靠一次 `tgHealth` 的 `alive` 兜底。

## 复现

1. 关掉 `orig-tg`（19787）与 `orig-daemon`（19786）（或只关 `orig-tg`）。
2. 打开应用，devtools Network 面板观察：失败请求按 5s / 10s 节拍**持续**出现，长时间不衰减。
3. Performance / React Profiler 观察：后端不可达期间**每 5s 一次整树渲染**。
4. 只读佐证：`netstat -ano | grep -E '19786|19787'` 无监听；前端仍在对该端口发 `fetch`。

## 修复（方向；**本档不改代码**）

1. **失败退避（P0）**：事实 1 / 3 的 5s 轮询在**连续失败**后必须指数退避（如 5s→10s→30s→60s 封顶），**成功后复位**。落实 `AGENTS.md:82` 的「失败退避」。
2. **连接被拒的熔断（P0）**：请求层把「连接被拒」与「HTTP 错误」区分开（`api/tg.ts` 的 status=0 需**作为结构化字段**上抛，而非塞进 message）；连续 N 次连接被拒 ⇒ 全局进入「后端不可达」态，**暂停所有轮询**，仅在用户手动重试 / 检测到恢复时复位。
3. **停止整树重渲染（P1）**：`MainLayout.tsx:36` 的 `useStore()` 改为**按字段选择器**订阅；后端不可达期间不得每 5s 触发全树渲染。
4. **EventSource 生命周期（P1）**：`useStore.ts:291` 保存 `subscribeEvents` 的 teardown 并在卸载时调用；避免 StrictMode 双连接。
5. **请求取消（P2）**：引入 `AbortController`，面板卸载时 abort 在途请求。
6. **无界集合淘汰（P2）**：给上述 Map / Ref 加容量上限或按会话清理。

3. **恢复自动复位**：后端重新启动后，**无需手动操作**即自动恢复轮询与实时连接（不得熔断成永久死）。**反向证伪**：只熔断不复位 ⇒ 后端恢复后仍无请求 ⇒ **FAIL**。

5. **无 EventSource 泄漏**：dev（StrictMode）下不得出现两个并存的 EventSource；卸载后连接必须关闭。
6. **不推翻既有约束**：BUG-239 / BUG-241 的成功请求放大修复不得回退；`AGENTS.md:82` 频率上限 5s 不回退。

### ★ 本次复报对既有正文的三处修正（不改写正文，在此登记）

**① 「事实 5」的稳态估算偏低：实测 24/min，不是 18/min。**

- 实测稳态 = `/api/downloads` 12/min + `/api/events` **12/min** = **24/min**。
- 差量**全部**可由「事实 6.2」解释：dev 下 `<React.StrictMode>`（`main.tsx:14`）使 `init()` 双调用
  ⇒ **两个 EventSource 各跑一套重连**，故 SSE 侧不是 6/min 而是 12/min。
- **直接证据（本次新拿到）**：`/api/events` 的 18 个时间戳**成对出现** ——
  `8324/8330, 9368/9368, 11384/11385, 15389/15396, 23396/23403, 33409/33409, 43415/43422, 53429/53429, 63440/63441`
  = **9 对**，对内间隔 ≤ 7ms。
  ⇒ 「两条连接各自退避」从推断变成**可核验读数**。
- 退避序列实测 `1s→2s→4s→8s→10s→10s→10s…`，与 `api/daemon.ts:286` 的
  `retryMs = Math.min(retryMs * 2, 10000)` **逐项吻合**。

**② `/api/config` 不是「本档清单遗漏的第三个 5s 轮询源」—— 它是有界启动突发。**

- 首次测量只看到「62s 内 12 次」，**极易误判成又一个 5s 轮询源**。
  本次给脚本加了**时间分布**切分（前 10s / 之后），读数立刻分开：
  时间戳 `8320, 8321, 8330, 8337, 8368, 8376, 8380, 8381, 9894, 11400, 12916, 14426`
  —— 前 8 个（`8320…8381`）**挤在 61ms 内**，其后 4 个间隔 `1513, 1506, 1516, 1510` ms，
  **全部落在前 14.4s**，此后 **55s 内 0 次**。
- 拆开归属（不重复计数）：**前 7 个**（`8320…8380`）= StrictMode 双挂载的启动突发；
  `8381` 起**恰好 5 个**（`8381, 9894, 11400, 12916, 14426`）= `probeTg` 的重试链。
- 机制与源码吻合：`useStore.ts:34-35` 的 `TG_PROBE_MAX_ATTEMPTS = 5` / `TG_PROBE_DELAY_MS = 1500`
  ⇒ `probeTg()`（`:671-695`）固定重试 5 次（`:682-683`），每次经 `refreshTgState()` 打一次
  `getConfig()`（`:612`）⇒ 5 次 × 1.5s，**就绪即停、次数有界**（`5 × 1500ms ≈ 7.5s` 的窗口
  与实测 `8381 → 14426` 完全吻合）。
- ⇒ **结论：不得把 `/api/config` 写成「新增的稳态轮询源」。**
  但它确实**无退避** —— `probeTg` 对 `ECONNREFUSED` 与「orig-tg 冷启动还没就绪」一视同仁
  （固定 1.5s × 5），属本档「无失败退避」的一个**有界实例**，
  可作为「事实 3」的补充；**不改变主结论，也不新增 P0 项**。

**③ 判据 D 的判法本次改为「趋势」，不用变异系数。**

首版用 `标准差/均值 < 0.25`，被**首帧 ~1ms 的伪间隔**抬高到 CV = 0.289 而误判 FAIL
（真实间隔是恒定 5000ms）—— 属「断言打在错的量上」。
改为：**丢弃 < 200ms 的间隔后，比「后半段均值 ÷ 前半段均值」**（无退避 ≈ 1.0，有退避应显著 > 1）。
本次得 **1.000**，判据 D PASS（现象复现成功）。
