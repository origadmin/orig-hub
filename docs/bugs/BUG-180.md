# BUG-180: 缓存单飞队列被停滞下载饿死 —— 无字节超时看门狗缺失，「添加一个后,后续无法添加」

- 状态: fixed
- 发现日期: 2026-09-29
- 模块: engine
- 严重程度: critical

## 现象

用户报告（2026-09-29）：**「缓存有严重问题. 添加一个后,后续无法添加.」**

实测（修前，真实运行栈）：

| 观测 | 值 | 含义 |
|---|---|---|
| 任务 75 | `running, done:0/9, currentId:<msg_id>, updatedAt == createdAt` | 相册任务卡在第一条消息，创建后**零进度更新** |
| 任务 76 | `queued`（另一相册 6 条） | 排队中，永远等不到 worker |
| 两次轮询（间隔 8s） | `done/updatedAt/currentId` 完全不变 | worker 卡死在条目下载内部，非慢速 |
| `GET /api/tg/diag` | `link_alive:true, session_phase:Authorized` | 链路层看起来健康，传输层已半死 |

结构性后果：单飞 worker 被永久阻塞 → 后续一切入队只能排队、永不执行
（「后续无法添加」）；且协作式取消只在**条目间隙**检查，卡在条目内时
连「取消任务」也失灵 —— 队列整体死锁，唯一恢复手段是重启进程。

## 根因

`download()` 的消费循环对 range 合并流**没有任何空闲超时**：

| # | 事实 | 位置（修前） |
|---|---|---|
| 1 | `while let Some(chunk) = body.next().await` —— `parallel_range_stream`（K=4）某路 range worker 半死（socks5 代理断流 / DC 停滞）时 `next()` 永不返回；`grammers.rs` 全文无 `timeout`/`Instant` | `orig-tg/src/grammers.rs::download` |
| 2 | 单飞 worker（`spawn_cache_task` → `run_one_cache_task`）同步 `await` 该下载，无看门狗、无进度心跳 ⇒ 一次挂起 = 队列永久饿死 | `orig-tg/src/routes.rs::run_one_cache_task` |
| 3 | 取消语义是「下一条目间隙退出」（`spawn_cache_task` 注释明示）——卡在条目**内部**时取消永远无法生效 | 同上 |

判据勘误：不能用「总时长」做超时（大文件慢速下载是合法的）；
正确的停滞判据是**无字节间隔**——任何非空 chunk 都应重置计时。

## 修复

`orig-tg/src/grammers.rs::download`：消费循环改为
`tokio::time::timeout(STALL_IDLE, body.next())`，`STALL_IDLE = 90s`（无字节间隔，
任何非空 chunk 重置）。超时即返回
`ClientError::Other("download stalled: no bytes for 90s … aborted to unblock the cache queue")`
→ `run_one_cache_task` 既有失败路径把任务置 `failed`（事实不回滚）→ worker
接续队列最老 `queued` ⇒ 队列自愈，取消恢复有效（循环必然终止）。
单条下载端点 `/api/tg/download` 与在线播放同函数，一并受保护。

## 验收证据

修复落位（入库路径）：`download-engine/crates/orig-tg/src/grammers.rs`（`download()`
消费循环改为 `tokio::time::timeout(STALL_IDLE, body.next())`）。

真实运行栈（修正二进制部署后，2026-09-29）：

1. **僵尸降级**：重启后 `counts = {interrupted:2}`（卡死任务 75/76 被正确降级，
   不再显示假「缓存中」）。
2. **连续入队端到端**（修复前的致命场景）：
   - 入队 #1 `POST /api/tg/cache/tasks {chatId:<chat_id>, messageIds:[<msg_id_1>]}`
     → 任务 77，1 次轮询内 `done 1/1`（≈3s）。
   - 入队 #2 `messageIds:[<msg_id_2>]` → 任务 78，1 次轮询内 `done 1/1`（≈3s）。
   - 终态 `counts = {done:24, queued:0, running:0, failed:0}` —— 第二条正常执行，
     「后续无法添加」消除。
3. **单测**：`cargo test -p orig-tg` → 105 passed, 0 failed。
