# BUG-354: Telegram「采集未启用」逻辑不自恰 —— 服务未启动被误判为用户禁用，且「启用」按钮启动不了服务

- 状态: fixed
- 发现日期: 2026-10-21
- 模块: shell
- 严重程度: high

## 现象

用户报障（2026-10-21）：「异常，显示：Telegram 采集未启用。逻辑不自恰：服务未启动为什么显示这个？点击也是无法开启，和核心设计完全偏离。」

具体矛盾：

- **逻辑不自恰**：面板显示「Telegram 采集未启用」（文案暗示是**用户把插件关了**），
  但真实情况是**服务没起来**（daemon 还没拉起 orig-tg / daemon 不可达 / 配置尚未加载）。
  「服务未启动」与「用户禁用」是两种根因完全不同的状态，却被渲染成同一句提示。
- **「启用」按钮启动不了服务**：该按钮只调 `onOpenAccounts` 跳到设置页；而按核心设计
  （BUG-178 / types.ts），**orig-tg 的生命周期由 daemon 独占**，前端从不手动拉起。
  设置页的开关也要经 `saveTgConfig` 打 daemon 才能生效 —— 在「服务未启动 / daemon 不可达」
  这一真实场景下，点击「启用」天然无法把服务拉起来，等于一个**死按钮**。

## 根因

`tgService` 状态缺一个「是否已从 daemon 取得确定性结论」的维度：

- 初始值 `useStore.ts` 为 `{ known:false, enabled:false, running:false }`；
- `refreshTgState` 仅在 `getConfig()` **成功**时落盘 `tgService`；daemon 不可达 / 配置未加载
  时 `getConfig` 抛错、提前 return，`tgService` 保留初始 `enabled:false`；
- TgPanel 的判定顺序是 `!tgEnabled`（→「采集未启用」卡 + 启用按钮）排在 `!tgReady`
  （→「正在启动」卡）**之前**（`TgPanel.tsx` 旧 `!tgEnabled`）。

于是「配置未确认 / 服务未启动」这一 `enabled:false` 被错误地当作「用户禁用」处理：
渲染「采集未启用」并给出只能跳设置页、按设计启动不了服务的死按钮。这正是用户指出的
「逻辑不自恰、与核心设计偏离」。

> 核心设计原则（types.ts `resolveTgFeatureReady` 注释 / BUG-178）：daemon 是 orig-tg 的
> 唯一托管者，前端**不**保留任何手动启停入口；服务层没起来时，正确姿态是「正在启动 /
> 正在连接」这类**由 daemon 负责、无需用户动作**的提示，而非「用户去启用」。

## 修复

**裁定**：`enabled:false` 同时覆盖「用户禁用」与「配置未确认 / 服务未启动」两种语义，
必须用一个 `known` 维度区分。只有 `known && !enabled`（已确认用户主动关掉）才渲染
「采集未启用」卡 + 启用按钮；其余一切「未就绪」归 daemon 职责，落到「正在启动」提示。

- **`types.ts`**：`TgServiceState` 新增 `known: boolean`（含注释说明 BUG-354 语义）。
- **`store/useStore.ts`**：
  - 初始 `tgService` 补 `known:false`；
  - `tgServiceKey` 纳入 `known`（初始 `known:false` 与后来 `known:true` 必须能区分，
    否则「配置未确认」会被短路成「已确认禁用」）；
  - 所有成功写入点（`init` 的 `getConfig`、`refreshTgState`、`setTgEnabled`、`restartTg`）
    补 `known:true` —— 只有真正从 daemon 拿到答案才置真。
- **`components/TgPanel.tsx`**：判定从 `!tgEnabled` 改为
  `tgDisabled = tgService.known && !tgService.enabled`，仅此谓词走「采集未启用」分支；
  注释同步更新（`!known` 的「服务未启动 / daemon 不可达」不算禁用，归「正在启动」）。
