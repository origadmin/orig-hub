# BUG-224: 浏览器报「无法解码该格式」——本机明明能放 / 服务端明明能救，两条救生索都没被拉

- 状态: fixed
- 发现日期: 2026-10-09
- 模块: shell
- 严重程度: high

## 现象

用户报：播放时出现提示「浏览器无法解码该格式（如 .mov/QuickTime），请在 APP 内用系统播放器打开」，
原本能放的文件现在放不了。APP 内并不存在「用系统播放器打开」这个入口。

## 结论先说

**不是格式不支持。** 实测（引擎 = msedge，与 WebView2 同款）：

| 事实 | 数值 |
|---|---|
| 媒体库视频总数 | 138（已排除 `test_videos` 夹具） |
| 其中 HEVC/hvc1 | 30（全部 `.mov`）；H.264 108 |
| 容器为 **MPEG-TS 却命名 `.mp4`** | **14**（id 395–402、488–493），Edge 无渐进式 TS 解复用器 ⇒ 真解不了 |
| 本机 Edge 解 HEVC | **能**：`items/415/raw` 首帧 **0.63s**、`items/673/raw` 首帧 **0.92s**，videoWidth 720 / 1920，帧持续上屏 |

即：`.mov` 那些**本来就该能放**；真正放不了的是 14 条 MPEG-TS，而服务端 ffmpeg 转一下就能放。

## 根因（两条独立缺陷，均实测复现）

### 根因 1：最该被救的那一类，恰好是判据唯一看不见的那一类（这条让 14 条 MPEG-TS 直接判死刑）

兼容流（BUG-208，服务端实时转 H.264）的切换条件是 `decodeHealth` 判出 `unsupported`
（`lib/decodeHealth.ts`，旧判据 `readyState >= 2 && videoWidth === 0` 持续 3000ms）。

而浏览器**明确拒绝**的源（`HTMLMediaElement.error.code === 4` = `MEDIA_ERR_SRC_NOT_SUPPORTED`）
`readyState` **永远是 0**，永远到不了那条判据；`VideoPlayer` 的 `onError` 又只认 `fallbackSrc`
（媒体库场景根本没传），于是直接 `setFatal(true)`。

实测复现（条目 395，ffprobe `format_name=mpegts`）：Edge 挂载后 **1.5s 内**报 `error.code=4`，
`currentSrc` 全程停在 `/raw`，**服务端兼容流一次都没被请求过**，直接弹终态遮罩。
⇒ 服务端那条明明能救的路（`x-orig-stream: live`，转码后 720p/30fps 正常出画面）形同虚设。

### 根因 2：零帧判定与「服务端转码启动」赛跑，输了就判死，还会永久记住（这条伤害本机本来能放的 HEVC）

`NO_FRAME_MS = 3000` 是拍脑袋值。实测本机：

| 源 | 首帧 |
|---|---|
| `items/415/raw`（720p HEVC，原生可放） | 0.63s |
| `items/673/raw`（1080p HEVC，原生可放） | 0.92s |
| `items/415/stream`（兼容流，冷启动实时转码） | **2.67s** |
| `items/673/stream`（兼容流，冷启动实时转码） | **2.89s** |

预算与兼容流首帧之间只剩 **0.11–0.33s** 余量。机器稍忙、或代理未命中需冷启动转码，就必然越界；
越界后果不是「提示一下」，而是切流 → 再判 → 停载。

配套的 BUG-208 记忆把伤害放大成永久：`rememberCompatSrc()` 把被判定过的 src 写进
`localStorage['orighub.compatSrcs']`（上限 200 条，**无清除入口**），下次打开**直开兼容流**；
而兼容流每次冷启动实时转码（实测首字节 2.44s、1.05 MB/s，143MB 源要转 136s），
且是 live fMP4 不支持 Range，暂停 / seek / 切速都会断流报错。
⇒ **一次误判 = 该文件此后永久变慢、且用户无法自愈。**

## 修复

1. `lib/decodeHealth.ts`
   - 抽出并导出唯一裁决点 `zeroFrameVerdict()`：**「还没解出第一帧」≠「解不了」**。
     只有两种情况判死 —— 媒体元素**明确**报 `MEDIA_ERR_SRC_NOT_SUPPORTED`，
     或元数据已就绪且零帧**超过预算**。
   - `NO_FRAME_MS` 3000 → **12000**（依据上表：兼容流实测最差 2.89s，留 4 倍余量）。
   - 真解不了的兜底**没有被取消**，只是从「3 秒后误杀」推迟到「12 秒后判定」。
2. `components/media/VideoPlayer.tsx` — `onError` 亲自接手 `MEDIA_ERR_SRC_NOT_SUPPORTED`：
   有兼容流且未试过 → **先切服务端兼容流**，兼容流也失败才进终态。
   （零帧判定与浏览器明说是同一个事实的两个来源，现在汇到同一条处置。）
3. `components/media/VideoPlayer.tsx` — **停用 BUG-208 的 localStorage 记忆**：
   `readCompatSet()` 恒返回空并顺手清 key，`rememberCompatSrc()` 不再写入。
   理由已写在代码注释里：它的前提（「本机解不动、只有转码能救」）经实测不成立。
