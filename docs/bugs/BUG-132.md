# BUG-132：条目「有无字节」判据分叉——MediaItem 无 has_bytes 恒走 file_path 判定，三态探测未接线

- 状态: fixed
- 发现日期: 2026-09-22
- 模块: engine+shell
- 严重程度: high

## 现象

同一条内容在**条目视图**与**分集视图**对「有没有字节」可能给出不同答案；文件被外部删除或 0 字节时，条目视图仍显示可播/可清，点开播放才 404。

## 根因

前端判据三级优先级（`tauri-shell/src/lib/tgmedia.ts:133-139`）：
① `source==='tg' && kind==='photo'` → true；② `item.hasBytes != null` → 用它；③ `Boolean(item.filePath)`。

但两级后端数据不一致：

- Rust `MediaItem` **没有** `has_bytes` 字段（`media.rs` `media_item_from_row` 只读 14 列，`ITEM_SELECT` 不含）→ 前端 `MediaItem.hasBytes` 恒 `undefined` → **条目视图永远走第③级 `Boolean(filePath)`**。
- `EpisodeView` **有** `pub has_bytes: bool`（`media.rs:690-734`，`get_series` 分集 SQL 末列 `i.file_path IS NOT NULL`）→ 分集视图走第②级。

而 `file_path IS NOT NULL` 已被 BUG-105 判定为**不可靠判据**（文件被外部删除 / 0 字节都谎报「有字节」）。库里已有正确的三态探测 `probe_cached_bytes`（`cache.rs:94-121`，返回 `Present/Missing/Unknown`），**但没有任何媒体端点调用它**（grep 已核实，仅 `/api/tg/downloaded` 在用）。

同病：`media/ItemEditDialog.tsx:34` `canClear = Boolean(item.filePath)` —— 「清除缓存文件」按钮可用性同样基于错误判据。

## 复现

构造 `file_path` 非空但磁盘文件已删的条目 → 条目视图仍标「可播」/编辑弹窗「清除缓存文件」可用；同一内容入剧后在分集视图与实际播放（404）矛盾。

## 修复

统一接后端三态探测（评估文档 Q5 方案 A，推荐）：

- `/api/media/items`（列表）与 `/api/media/items/:id` 下发字节存在性；列表 60 条/页逐条 stat 的性能需评估（可惰性/批量）。
- 前端 `hasMediaBytes` 改为只信后端下发；`canClear` 同源。
- **保持三态（有/无/未知），不压成布尔**——压平会重演 BUG-104/105 的错判。

**判据（每条都必须能 FAIL）**：

1. 构造一条 `file_path` 非空但磁盘文件已删除的条目：条目列表（`/api/media/items`）与
   剧集分集（`/api/media/series/:id`）对该条目必须给出**相同**的「有无字节」结论（均为无字节）。
2. 接口响应中条目对象必须**带** `hasBytes` 字段（当前 Rust `MediaItem` 无此字段，恒为 `undefined`）。
3. 前端 `hasMediaBytes()` 不得再落到 `Boolean(item.filePath)` 兜底分支 —— 用「文件被外部删除」用例断言。

**反向证伪**：用例必须同时跑「文件存在」与「文件已删」两种状态；只跑前者时
`Boolean(filePath)` 也能通过，会假绿。

**取证位置**：`tauri-shell/src/lib/tgmedia.ts`（前端判据）、`download-engine/crates/orig-tg/src/media.rs`
（`MediaItem` 与 `EpisodeView` 的字段差异）、`download-engine/crates/orig-tg/src/cache.rs`
（`probe_cached_bytes` 三态，现成但未接线）。
