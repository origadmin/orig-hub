# BUG-442: 清/删条目不回收平铺布局存量字节——清缓存后文件残留磁盘

- 状态: open
- 发现日期: 2026-10-23
- 模块: engine
- 严重程度: mid

## 现象

清缓存 / 删条目后，DB 侧 `file_path` 已置空、占用统计下降，但库根平铺目录里对应的视频/图片文件仍在，
磁盘空间不回收。用户「占用空间」与真实磁盘长期对不上（与 BUG-133/125 同类症状）。

## 根因

`clear_item_bytes`（`download-engine/crates/orig-tg/src/media.rs:2397`）只维护 **blob 引用计数**
并返回「是否归零」信号；真正的 `unlink` 由调用方在归零后执行，且契约只覆盖 `.blobs` 路径——
`media.rs:2431` 注释明示「归零时调用方会去 unlink **blob 路径**。存量条目的字节还在平铺目录里」。
存量条目（BUG-420/421 涉及的平铺布局、非 hash、非 `.blobs`）的字节既不走 refcount、也不在
`.blobs` 下，清/删路径对其 `file_path` 不触发 unlink ⇒ 字节孤儿化、永久残留。
与 BUG-421 的关系：BUG-421 只改写 72 条 `file_path` 的 DB 行指向新库根，并未顺带回收旧路径字节，
旧文件因此继续泄漏。

## 复现

1. 取一条平铺布局存量条目（有 `file_path`、字节在库根平铺目录、不在 `.blobs`）；
2. `DELETE /api/media/items/:id` 或清缓存；
3. 查 DB `file_path` 已空，但磁盘上该文件仍存在。

## 修复

清/删的字节回收路径须按 `file_path` 实际落点分派：`.blobs` 走 refcount 归零 unlink；平铺布局走直接
`remove_file(file_path)`（与 `routes.rs:4549` `delete_media_item` 的 `absolute` 解析纪律一致）。
回收前须确认该 `file_path` 在库根解析下 `is_file()`（BUG-421 教训：只在新目标存在时才动，否则把
「文件没了」伪装成「路径对了」）。建议补一条回归测试覆盖平铺条目清/删。

## 关联

- BUG-420（content_hash 死代码，存量懒纳入从未实现）、BUG-421（72 条路径改写未触发字节回收）
- BUG-133/125（占用展示与磁盘真值不符）
- `download-engine/crates/orig-tg/src/media.rs:2397`、`routes.rs:4549`、`cache.rs:557`
