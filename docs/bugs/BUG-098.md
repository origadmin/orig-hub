## 现象

所有者提出的 5 点诉求，逐条与代码核对后的结果（**三条真缺口、两条属「以为没有其实已有」**）：

| # | 诉求 | 现状（已核到行号） | 判定 |
|---|---|---|---|
| 1 | 「TG 加入是 TG 的动作，信息过去但字节没过去」 | **方向相反**：字节先落盘，条目才建立。`routes.rs:732` `cache_one` → `download()` → `:763` `mark_downloaded` → `:765` `import_cached_file` → `:829` `upsert_media_item(…, file_path=Some(path))`。TG 消息扫描只写 `media_message`，**不产生 `media_item`** → 未缓存内容在媒体库不可见 | **真缺口**（P0），且方向与描述相反 |

## 根因

**两域之间只有「一个契约」，没有「一个状态」。**

- 唯一契约是 `(source="tg", ref="{chat}:{msg}")`（`media.rs:236` + `AGENTS.md:99`），在此基础上长出 5 条跨界调用：正写 2 条（`import_cached_file` `routes.rs:765`、`import_photo_item` `:854`）、反写 2 条（`clear_downloaded` `:1970`、`reset_tg_flag` `cache.rs:224/575`）、读 2 条（`first_caption` `:1852`、photo 代理 `:2106`）。
- 但**资产域没有自己的生命周期状态**：`media_item` 的行存在被绑死在 `file_path` 上，于是「登记」与「就绪」被压成同一个动作（`import_cached_file`），两域之间**没有「未就绪」这个状态可表达**。诉求 1/2/3 是同一个根因的三个面。
- 诉求 4/5 的根因不同：是**「来源」没有结构化承载**与**「清理」没有分层**，属于能力缺口而非状态缺失。

## 评估结论

**不需要推倒重来，做四处增量。** 域边界其实已经存在（`cache.rs:12` 注释明写「缓存模块不得认剧集」），契约没散，改造可收口。真正需要拍板的是**一项策略选择**（入库时机 + 可见性）；其余三项（状态、来源、事件）是补缺。

### 建议的目标结构

1. **状态机**：`media_item` 增列 `asset_state`（`pending` 已登记无字节 / `ready` 字节在本地且磁盘存在 / `missing` 可重取 / `remote` 按需取〔photo 常态，BUG-049〕）。**不设 `deleted` 终态**——删除即删行，软删会污染所有查询。
   - 归属：`asset_state` = **权威**（只有资产域写）；`media_message.downloaded` 与 `cache_task.status` = **镜像**（上游事实，仅作通知源）。
   - 关键约束：`asset_state` 必须能由「`file_path` + 磁盘 stat」重算（`reconcile_asset_state`），即**权威但可自愈**——这是事件丢失不永久错乱的唯一保障。现有派生的 `has_bytes` 保留为只读，语义改为 `asset_state='ready'` 且**以 stat 为准**。
2. **来源模型**：**不推倒 `source`/`ref`，加一层** `media_origin(item_id, kind, locator, channel_id, message_id, account, url, captured_at)`，`kind` 枚举 `tg|local|s3|oss|webdav|netdisk`。存量按 `source='tg'` + `ref LIKE '%:%'` 回填。
   - **跳转是来源的能力，不是条目的字段**。只有 TG 具备「稳定、可构造、可直达单条」的跳转（`https://t.me/{username}/{message_id}`；私有频道 username 为空 → 退化为应用内定位，**按钮不渲染而非渲染坏链**）。网盘只能到目录、OSS/S3 Console 需登录态、预签名有时效不能存库——这些一律降级为「定位提示」（显示路径/链接文本 + 复制按钮）。
   - 频道名**不复制进 `media_item`**（会过期），前端按 `channel_id` 查 `monitored_channel.title/username`（`store.rs:283-288`）；仅 `url` 入库时快照。
3. **通知**：进程内 `broadcast` 总线 + 新增 `GET /api/tg/events`（SSE）。**事件是加速信号，不是唯一真相**——不缩短轮询（保持 ≤5s，BUG-030 不变），SSE 断线回落轮询，每次（重）连成功触发全量对账。
4. **清理三层**：L1 `cache_task` 台账（已有）/ L1′ `media_message` 已入库行（新增）/ L2 字节（已有）/ L3 `media_item` 条目（单条已有，**批量新增**）。**L2 永不写 L3，L3 可写 L2**——与 BUG-096 单向不变量不冲突。

### 已确认的冲突点（对应「和下载内容、分类有冲突」）

| 冲突 | 现状 | 建议默认 |
|---|---|---|
| 删光分集后剧集空壳 | `prune_empty_series`（`media.rs:1088`）**无条件** prune，不区分自动成剧/手工剧集 | 自动成剧（`source_key` 非空）可 prune；**手工剧集保留空壳** |
| 外部导入文件删不删 | `inside_dir(下载目录, path)` 为真才删（`routes.rs:1962-1967`） | **沿用**：只删自己产出的字节 |
| 在途任务关联的条目被删 | 任务完成后 `upsert_media_item` 会让条目「复活」 | 删条目先取消在途 `cache_task` |
| 清字节后能否重取 | TG 可（ref 在）；本地扫描来源**不可** | 「清字节」仅对可重取来源开放 |
| 图片（`file_path=NULL`）的完全删除 | 无字节可删，只删行 | 文案区分「删除字节」与「移除条目」 |

## 待拍板（团队内**存在分歧**的已显式标出，需所有者裁定）

> PM 与架构师各出了一份评估，多数结论一致，以下 3 条**两方推荐相反或不同**，须由所有者拍板后才能开工。

**① 字节未就绪的条目，在媒体库里默认可见吗？**（**分歧，且决定整个 UI 与状态机**）
- **PM 推荐 A**：可见，与已就绪混排，仅角标区分（对齐 BUG-049 现有图片条目体验；B 方案「收进未就绪页」会让刚登记的内容像丢了）。
- **架构师推荐 A（不同含义）**：**默认不进媒体库网格**，走独立「待获取」视图。理由：`monitor.rs:18` 每频道每轮 100 条，先行入库会灌满空条目；且自动成剧的门是**只卡 kind 不卡字节**的触发器（`media.rs:472-495`），空条目会被编进剧集 → 出现「有集数、无内容」。
- 影响：不决定则状态机（T01）与前端呈现（T05）均无法动手。

**② `media_message`（TG 索引）允许清空吗？**
- **PM 推荐 B**：可清，但清空前把「频道名/username/消息号/消息时间」**快照写入条目**（同时满足诉求 3 与诉求 4）。
- **架构师推荐**：只允许清「已入库」的行，且**必须保留 `downloaded=1` 的行**，提供 `scope=ingested|all`（`all` 需二次确认）。理由：它是重新缓存的坐标（`cached_path` `routes.rs:718-729`）与元数据回填源（`:1852`），无条件清空 → 已入库内容失联。

**③ 本期是否上事件（SSE）？**
- **PM 推荐 B（本期不做）**：诉求 2 的痛点是「没有状态」而非「更新慢」，先补状态。
- **架构师方案**：给出完整 SSE 方案并列入 P1，但明确「事件只通知、状态仍由写路径落库 + `reconcile` 兜底，**不缩短轮询**」。
- 两方对「事件不能成为唯一真相」无分歧，分歧只在**排期**。

**其余已一致、可直接采纳的建议**（无需逐条拍，如无异议即按此实施）：
- 状态用**显式列**而非继续派生（派生已有 1 个例外分支，未来每加一个来源多一个例外）
- 来源模型**现在就做通用抽象**，跳转只实现 TG（等接网盘再改 = 第二次重构）
- 批量删除范围 = **多选 + 按筛选条件**（来源/kind/无字节/时间区间），不做全量清空
- 删条目的字节处置沿用 `inside_dir` 边界（**不删用户外部导入文件**）
- 多来源 `ref` = **源内稳定定位符**，endpoint/bucket 等易变部分进 `media_origin.account`，不进 `ref`

## 主理人仲裁（补充取证后收口，2026-09-21）

分歧不应原样抛回给所有者。补充取证两项后，主理人裁定如下（**如无异议即按此开工**）：

**新增证据 1 —— 清空 `media_message` 的真实代价比「失联」轻。**
`routes.rs:1849-1861` 的 `first_caption`（`:1852`）是**唯一**从 `media_message` 反查 caption 的读路径，
且它只在**导入/重新入库**时被调用，用于切分标题与介绍；已有 `derived.unwrap_or(title)` 兜底。
而已入库条目的 `title`/`description` **已落进 `media_item`，清空流水不影响**。
故清空的后果是「**再次导入时拿不到真实 caption，退化为调用方传入的 title**」，不是「内容失联」。

**新增证据 2 —— 三处轮询确为 5s，已逐处核实。**
`CacheManagerDialog.tsx:451`、`MainLayout.tsx:64-67`、`TgPanel.tsx:582` 均为 `setInterval(…, 5000)`。
即 BUG-030 的 5s 上限现状成立，SSE 的收益是「瞬时刷新 + 无事降频」，不是「修一个已坏的东西」。

### 裁定

**① 可见性 → 采纳架构师方案（默认不进主网格），但必须留可发现入口。**
- 做「元数据先行入库」（满足诉求 1），`pending` 条目**默认不进媒体库主网格**，走独立「待获取」视图；
- **但媒体库顶部常驻「待获取 N 条」入口**——采纳 PM 的顾虑「默认隐藏会让刚登记的内容像丢了」，
  用「可发现」而非「混排」解决。
- 决定性理由（已核）：`monitor.rs:18` 每频道每轮 100 条且整窗口幂等 upsert；自动成剧的门禁是
  触发器 `trg_media_episode_*`（`media.rs:472-495`）**只卡 `kind` 不卡字节** → 空条目会被编进剧集，
  产生「有集数、无内容」。满屏空条目 + 空剧集是不可接受的回归。

**② `media_message` 清空 → 两方方案合并，且由 T02 顺带解决（零额外成本）。**
- 采纳架构师的约束：只清「已入库」行，**保留 `downloaded=1` 的行**（它是重缓存坐标 `routes.rs:718`）；
- 采纳 PM 的快照：清空前把 `channel_id`/`message_id`/频道名/username/消息时间 写入 **`media_origin`**——
  该表 T02 本来就要建，**快照因此不产生额外表**；
- 结合证据 1，快照的最小集合即 `media_origin` 的既有列，无需给 `media_item` 加列（避免踩坑 3）。

**③ SSE → 本期不做，先补状态（采纳 PM）。**
- 理由：诉求 2 的痛点是「没有状态」而非「更新慢」；三处 5s 轮询现状可用（证据 2）；
  SSE 引入后要处理断线重连与重连对账，是独立一块工作量。
- **前提**：T01 的 `asset_state` 必须实现为「权威但可自愈」（`reconcile_asset_state`），
  这样将来上 SSE 只是加速通道，不是状态正确性的依赖。

## 所有者补充澄清（2026-09-21，优先级高于上述评估）

所有者对仲裁的两条回应，实质修正了评估中的两处判断，并追加了一条新诉求：

**澄清 1 —— 来源模型要统一，跳转能力不是区分点。**
> 「网盘/OSS/S3 跳转」和 TG 一样都是「来源 → 入库」。

据此**推翻**「只有 TG 具备可跳转能力、其余降级为定位提示」的分级判断（原见「建议的目标结构」第 2 条）：
四类来源在入库模型上**完全同构**，差异只在各自携带的定位字段不同。目标流程统一为
`来源 → 登记（media_item + media_origin）→ 取字节 → 就绪 → 呈现`。
`media_origin` 的价值因此从「承载跳转」回归为「**承载非 TG 来源的定位信息 + 存量 ref 回填**」。

**澄清 2 —— `remote`（无本地字节、按需从源站取）本期不做，后期再讨论。**
状态机取值**收缩为三个**：`pending` / `ready` / `missing`。`remote` 不进本期状态机，
也不为 photo 特设（photo 无字节继续沿用现有 `file_path=NULL` + BUG-049 的代理链路）。

**追加诉求 —— 同一内容多来源、多版本，剧集一集可对应多个视频且要有主次。**
> 一部视频可能来自不同频道，也可能有不同码率/压片版本；剧集里第 1 集可能对应多个视频，要有主次。

**核查结论：该能力已完整实现（BUG-039），属第三处「以为没有其实已有」的错位。**

- 主版本 = `media_episode.item_id`；备用来源 = `media_episode_source(episode_id, item_id)`
  （`media.rs:366-376` 建表，注释即「同一 (season, episode_no) 槽位的主条目之外的备用来源」；
  `item_id` **全表 UNIQUE**，同一内容只会是某一集的来源）。
- 主备切换 `switch_episode_source`（`media.rs:1719`）用 `BEGIN IMMEDIATE` 事务包住
  「删备用行 + 原主降级为备用 + 主位换新」三步，注释明确不出现「两个主」或「主条目两边都不在」。
- 前端已暴露：`SeriesDetail.tsx:695-708` 渲染同槽备用来源，点击即切主；`media.ts:375/383`
  提供 `attachEpisodeSource` / `switchEpisodeSource`。
- 已知边界：备用源**只接受 video**（触发器 `media.rs:485-495`，BUG-044 不变量）。

**由此收窄的范围**：多版本/主次不需要新建能力，只需在 T02 落地后确认
「不同来源的同一内容如何被挂成备用源」这一步是否顺畅（挂载入口的可发现性待确认，见下）。

## 验收口径

判据写「**值正确**」，不写「值一致」或「数量对得上」：

| 诉求 | 判据 |
|---|---|
| 1 | 对未缓存的 TG 视频消息执行登记：`media_item` 存在且 `source='tg'`、`ref='{chat_id}:{message_id}'`、`file_path=''`、`asset_state='pending'`；**且磁盘上无对应文件** |
| 2 | 字节到达后：同一 `id` 行 `file_path` **等于实际落盘绝对路径**、`size` **等于 `media_message.size`**、`asset_state='ready'`；前端在未手动刷新的情况下完成一次状态翻转 |
| 3 | 执行清空后：`cache_task` 计数 **= 0**、指定范围 `media_message` 计数 **= 0**；**同时**已入库 `media_item` 计数 **= 清空前条目数**（证明只清流水、没连带删条目） |
| 4 | 任一条目可读出：频道名 **= `monitored_channel.title`**（username 为空时回退 `#{chat_id}`）、消息号 **= `message_id`**；TG 跳转 URL **= `https://t.me/{username}/{message_id}`**；username 为空时**跳转按钮不渲染** |
| 5 | 批量删 N 条：响应 `removed` **= N**；这 N 个 id 在 `media_item` 中计数 **= 0**；`media_item_tag`/`media_episode` 关联计数 **= 0**；下载目录内对应文件 `exists=false`；TG 来源条目 `media_message.downloaded` **= 0** |
| 回归 | 手工剧集在分集被删光后**仍存在**（`source_key` 为空）；下载目录外文件在删条目后 `exists=true` |

## 踩坑预警（实施时逐条避让）

1. 加 `asset_state` 列但**只在新链路写** → `import_photo_item`（`routes.rs:854`）、`import_media_items`（`:1803`）、扫描三条老链路不写 → 状态说谎。必须收口到唯一写入函数。
2. 把 `has_bytes` 换成列并删掉派生 → 派生值天然自愈；换成列就引入「磁盘被手工删但状态没更新」的永久谎言。**保留派生**。
3. 为「来源」给 `media_item` 加 `channel_id`/`message_id` 列 → 把 TG 概念灌进资产域，将来每加一种来源多一列 → 列爆炸且稀释 `UNIQUE(source, ref)`。走独立 `media_origin` 表。
4. `monitor.rs` 里直接 `upsert_media_item` 做元数据先行 → 满屏空条目 + 空条目进剧集（见待拍板①）。
5. 直接 `DELETE FROM media_message` 无条件清空 → `cached_path`（`routes.rs:718`）失去幂等坐标。
6. 给 `POST /api/cache/clear` 加 `deleteItems=true` 复用端点 → 「清字节」与「删条目」混成一端点，突破 BUG-096 单向边界。**必须独立端点**。
7. 把引用新列的 `CREATE INDEX`/`UPDATE` 放进 `execute_batch` → BUG-032，整批失败 → `Store::open` 失败 → 表现像「用户数据全没了」（`media.rs:301-310` 有同型前车之鉴）。
8. 上了 SSE 就删掉轮询 → SSE 静默断线时 UI 永久冻结。
9. 为「删除」新增正向级联（删 `cache_task` → 删 `media_item`）→ 直接违反 `AGENTS.md` §5 的 BUG-096 铁律，**禁止**。
