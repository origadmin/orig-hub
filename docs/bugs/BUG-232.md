# BUG-232：入库流水线行标题是频道名/裸频道 ID，没有入库内容的标题

- 状态: fixed（v2：标题改由引擎从 `media_message` 带出，全状态覆盖；实测任务标题 41→66 条、UI 行 36→57 条）
- 发现日期: 2026-10-09
- 模块: shell
- 严重程度: high
- 登记: 用户报告「入库仍然有问题，标题显示：频道 \<chatId\> · 单条 · 1 条，仍然没有内容标题。
  之前 100% 确定修复过能显示入库内容的，当前回退，且修复多次无效」

## 现象

入库流水线（`CacheManagerDialog`）的每条记录行标题显示
`频道 \<裸 chatId\> · 单条 · N 条`，用户无法分辨每条入库记录装的是什么内容。
预期：行标题 = **入库内容的标题**（媒体库条目标题）；频道只是元数据。

## 根因（两层）

1. **结构性缺陷**：该对话框自入库流水线重构（`9bee7b8`，2026-09-21）起，行标题唯一来源是
   `titleOf(chatId) ?? \`频道 ${chatId}\`` —— **只有频道维度，从来没有内容标题路径**。
   全 git 历史核查（`git log -S`），本仓库不存在任何「行显示内容标题」的版本；
   仓库有过 `9a28947`（git ref/object 丢失后重建）记录，用户记忆中的旧修复很可能随
   历史丢失事件湮灭。与 BUG-231 同一原则：**分组维度 ≠ 内容标题**。
2. **退化放大**：dialogs 列表为空（订阅扫描问题，独立登记）时 `titleOf` 解析不到频道名，
   连频道名都不剩，直接露出裸 chatId。

## 修复（v1，已被 v2 取代，保留作沿革）

- v1：行标题链改为三级，内容标题按 by-ref 查**媒体库条目**（每 ref 只问一次）。
  只覆盖 `done`/`interrupted`；用户裁定该获取层错误（数据早在 `media_message`），
  由下面的 v2 取代 —— v1 的 by-ref 查询代码已从壳中删除。

## v2 修复（2026-10-09 深夜，按用户裁定重做获取层）

引擎侧一次 JOIN，壳侧删掉整套客户端补查：

- `orig-tg/src/store.rs` 新增 `message_captions_for_channels`：按频道一次取回
  `media_message` 的非空 caption（任务只跨个位数频道，逐频道一查，不做行级 N 次查询）。
- `orig-tg/src/routes.rs`：`/api/tg/cache/tasks/all` 与 `/tasks/:id` 随任务下发
  `title` = **任务覆盖消息里第一条有 caption 的**。之所以不是「第一条消息的 caption」：
  实测相册/合集首条常为空（某任务 10 条消息里第 3 条才有文案），只认首条会让大量任务
  退化成裸频道 ID——正是用户看到的形态。改取首个非空后任务标题覆盖 41 → 66 条。
  1s 轮询端点 `/api/tg/cache/tasks` **不加**（读路径契约是内存快照不碰 SQLite）。
- 壳 `CacheManagerDialog.tsx`：删 `ingestTitleRef`/`ingestTitles`/by-ref 查询 effect，
  行标题 = `task.title → 频道名 → 裸 chatId`；`types.ts` 补 `title?: string`。

## 部署形态（真实环境约束，非缺陷）

本次部署时发现既有已登记缺陷 **BUG-227**（daemon 5s 启动窗口）实测复现：
新构建 orig-tg 从启动到监听实测 **5.10s > 5s** ⇒ daemon 每次 `spawn` 都在窗口内否决子进程
（报 `exited without listening`）并顺延端口（19787 → 19788，即 BUG-228 的端口漂移）。
本次验收用「daemon 报告端口上直接拉起同源实例」绕行（同数据目录/凭据/端口，daemon 按端口探活
仍视为运行中），已写入 BUG-227 证据。BUG-227/228 修复后该绕行即撤。
