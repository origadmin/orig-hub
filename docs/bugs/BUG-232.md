# BUG-232：入库流水线行标题是频道名/裸频道 ID，没有入库内容的标题

- 状态: open（v1 的 by-ref 客户端查询被裁定**获取层错误**，v2 修订见下；重新打开）
- 发现日期: 2026-10-09
- 模块: shell
- 严重程度: high
- 登记: 用户报告「入库仍然有问题，标题显示：频道 \<chatId\> · 单条 · 1 条，仍然没有内容标题。
  之前 100% 确定修复过能显示入库内容的，当前回退，且修复多次无效」

## 现象

入库流水线（`CacheManagerDialog`）的每条记录行标题显示
`频道 \<裸 chatId\> · 单条 · N 条`，用户无法分辨每条入库记录装的是什么内容。
预期：行标题 = **入库内容的标题**（媒体库条目标题）；频道只是元数据。

## 根因（两层）

1. **结构性缺陷**：该对话框自入库流水线重构（`9bee7b8`，2026-09-21）起，行标题唯一来源是
   `titleOf(chatId) ?? \`频道 ${chatId}\`` —— **只有频道维度，从来没有内容标题路径**。
   全 git 历史核查（`git log -S`），本仓库不存在任何「行显示内容标题」的版本；
   仓库有过 `9a28947`（git ref/object 丢失后重建）记录，用户记忆中的旧修复很可能随
   历史丢失事件湮灭。与 BUG-231 同一原则：**分组维度 ≠ 内容标题**。
2. **退化放大**：dialogs 列表为空（订阅扫描问题，独立登记）时 `titleOf` 解析不到频道名，
   连频道名都不剩，直接露出裸 chatId。

## 修复

- 行标题链改为三级：**入库内容标题 → 频道名 → 裸 chatId**。
  内容标题按 by-ref（`source="tg"`、`ref="{chat}:{msg}"`）查媒体库条目取得，
  每 ref 只问一次（含「查过但无」缓存），不在渲染期发起请求（请求风暴规则）。
- 覆盖 `done` 与 `interrupted`（部分入库）；failed/cancelled/queued 行无库条目，
  如实退回频道链 —— 它们的内容标题需引擎在 `cache_task` 落 caption 字段（见剩余范围）。

## v2 修订（2026-10-09 深夜，用户裁定 v1 获取逻辑错误）

用户指出：**入库后这条消息的基础数据早已保存**，查看不应获取不到。实测证实：

- `media_message`（消息同步时落库）现库 **3665 行、caption 齐全**，覆盖全部状态的任务来源消息
  （含 failed——失败任务的消息 caption 就在本地）。
- v1 修复让 shell 按 by-ref 查**媒体库条目**：只有入库成品才命中 ⇒ 获取层选错。
  数据在 `media_message`，却去 `media_item` 找；查不到再在客户端逐行渲染期补救——
  「后期渲染没问题，获取有严重问题」，正是用户裁定。
- `cache_task` 表无标题列，任务列表 API 也不带 caption ⇒ 任务行天然拿不到已有数据。

**正确修法（v2，引擎侧）**：任务列表服务端一次 JOIN `media_message`（channel_id+message_id）
带出 caption，所有状态（done/failed/cancelled/interrupted/queued）统一有标题；
shell 删除 by-ref 逐行查询（`ingestTitleRef` 整套），行标题 = `task.caption → 频道名 → 裸 ID`。
一次 SQL、零新增请求、覆盖全状态，替代 v1 的「done 行客户端补查」。
需重建部署 orig-tg（重启影响在用会话，时机待用户定）。

v1 的「剩余范围 1」作废并入本修订；v2 落地后 v1 验收口径改为回归项。
