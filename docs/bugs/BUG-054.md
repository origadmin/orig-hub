# BUG-054 条目没有「介绍位」→ 正文被塞进标题；且标题/介绍无编辑入口、缓存删除无确认无选择

- **严重级**: major / data-model + discoverability
- **状态**: fixed（2026-09-18 已验收）
- **发现日期**: 2026-09-18
- **报告轮次**: 2026-09-18（用户原文三问：
  1「剧集为什么正确提取内容了，但是视频内容错误。视频内容应该和剧集一样啊。而且剧集和视频的
  标题不能编辑这是最大问题。」
  2「清除缓存文件 这个功能应该在设置页面的对应功能块下面吧？」
  3「缓存管理 的删除至少有个弹窗确认吧？还有清理需要有全选，部分选择这些吧？一个一个删？」）
- **模块**: engine（`orig-tg`）+ shell（媒体库 / 播放页 / 缓存管理 / 设置页）

## 现象

1. 同一条 TG 消息，**剧集详情页**的标题是干净的一行、介绍完整；**点开视频**（条目侧）
   却是一整坨原文 —— 标题里带着换行和整段正文。两侧「正确/错误」不一致。
2. 剧集和视频**都没有修改标题的入口**（用户原话：这是最大问题）。
3. 「清除缓存文件」只藏在缓存管理对话框里，设置页的 TG 模块下没有。
4. 缓存管理只能**一条一条删**，删之前**没有确认**。

## 根因

### 1. 条目侧根本没有「介绍」这一列（主因）

```sql
-- media_series 有 description，media_item 没有
media_series(..., description, ...)
media_item  (..., title, ...)        -- ← 正文无处可去
```

剧集侧的写入路径调用 `split_caption(caption)` 取「首行 = 标题、余 = 介绍」，所以是对的；
条目侧没有可落库的字段，于是整段 caption 被当成 `title` 写进去。**这不是历史脏数据**：
修复前实测当天（02:25）新写入的 item 380 依然含换行，证明是**当时代码**的行为。

### 2. 两处「功能存在但入口不可发现」

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | `MediaCard` 的编辑按钮是 `opacity-0 group-hover:opacity-100`，且只有一个铅笔图标 | 必须把鼠标悬停到封面正中央才显形 —— 用户找不到，等于没有 |
| 2 | `SeriesDetail` 只实现了 `editingDesc`，**没有** `editingTitle` | 剧集标题**完全没有**修改路径，不是「藏得深」而是「不存在」 |

### 3. 「清除缓存文件」的动作与它所属的模块被拆开

释放磁盘的动作挂在「缓存管理」对话框里（一个**记录级**的运维面板），而它属于
「设置 → 通用 → TG 模块」（**配置级**）。入口错位导致用户找不到，且与设置页其它
TG 动作分离。

### 4. 删除没有「选择」这一层

后端只有 `DELETE /api/cache/tasks?scope={all|failed}` —— 枚举**档位**，不是**集合**；
前端只能逐行删，且不弹确认。用户诉求是「清理」——「清理」天然是选择行为，
挡位枚举表达不了。

## 修复

### engine（`crates/orig-tg`）

1. `media_item` 增加 `description TEXT` 列，`MediaItem` / `ITEM_SELECT` /
   `media_item_from_row` 同步；`upsert_media_item` 增加 `description` 参数，
   INSERT 与 DO-UPDATE 均写。
2. **一次性回填迁移** `backfill_item_text()`：把历史「整段 caption 当标题」的行
   用 `split_caption` 重切成标题 + 介绍。保守规则 —— 标题只重切含换行的整段行、
   介绍只补空位、已有值不动；用 `app_setting` 键 `mig.item_text_split_v1` 收口，
   避免每次启动覆盖用户主动清空的介绍。
3. `ItemPatch` 增加 `description: Option<Option<String>>`（沿用 BUG-041 的 nullable
   契约：字段缺省 = 不改，显式 `null` = 清空）。
4. **标题空值语义 = 不可表达**：`update_media_item` / `update_series` 对空/纯空白
   标题一律保留旧值；路由层对显式空标题返回 422。理由 —— 标题是条目的主标识
   （NOT NULL + 列表/搜索/播放器全依赖），空标题没有合法呈现；而介绍空值是
   **显式清空**，是合法意图。两者语义相反，不能共用一条「照写」路径。
5. `EpisodeView` 增加 `item_description`（分集投影带 `i.description`），
   使播放页与条目侧取到**同一段正文**。
6. `Store::delete_cache_tasks_by_ids(&[i64])`：活跃任务先置 `cancelled` 再删行；
   空集合返回 0。`DELETE /api/cache/tasks` 支持 `?ids=1,2,3`（与 `scope=` 互斥）；
   `parse_ids` 对非法/0/负数/空选择一律 422 —— **不能静默成功**（否则用户以为删了、
   实际没删，或反之误清空）。

### shell

| 位置 | 改动 |
|---|---|
| `MediaCard` | 编辑入口改**常驻可见**（铅笔 + 「编辑」文字，`absolute bottom-1 right-1`） |
| `ItemEditDialog` | 新增「介绍」多行 `textarea`（与标题并列）+ `data-testid`；保存时标题留空则不改、介绍空则发 `null`（清空） |
| `SeriesDetail` | 标题旁新增「改名」入口（`editingTitle` / `titleDraft` / `saveTitle`），前端先拦空标题 |
| `MediaViewer` | 返回行新增「编辑」按钮；底部文案行改显示 `description`（此前显示 `caption`，标题会重复两遍）；补 `whitespace-pre-wrap` —— 介绍是多段文本，`SeriesDetail` 一直有、这里漏了，同一段正文在剧集页有分段、播放页被折成一坨，是「剧集对、视频错」的又一种形态 |
| `MediaLibraryPanel` | 消费 `editItemId` → 拉条目 → 弹同一个编辑框 |
| `useStore` | 新增 `editItemId` / `requestEditItem(id)` / `clearEditedItem()` |
| `CacheManagerDialog` | 逐行勾选 + 表头全选 + 已选计数 + 「删除所选」；**任何删除（含单条）都先出确认条**，并如实报出其中活跃任务数；移除「清除缓存文件」，改为指路设置页 |
| `SettingsPanel` | TG 模块下新增「清除缓存文件」+ **实时占用读数**（进页读一次）；先读占用再确认（确认文案带数字），占用为 0 时禁用 |

**播放器不反向依赖资料库**：播放器挂在布局层、不认识 `MediaItem`，所以它只
`requestEditItem(id)` 把意图发到 store，由媒体库面板接管弹窗。播放器不需要知道
任何资料库细节，编辑逻辑只有一个家。

### UI 断言要点（`shot_round8_edit_cache.cjs`）

- ①b/①c **常驻可发现性用运行期几何判定**，不是看类名：未 hover 时计算 `opacity === '1'`，
  且按钮中心点 `elementFromPoint` 命中自身（旧实现 `opacity-0 group-hover:opacity-100`
  两条都会失败）。①d 断言按钮**带「编辑」文字**，不只一个图标。
- ①h 编辑框里「介绍」的预填值与后端 `description` **逐字相等**（条目与剧集同源同切法）。
- ①m 播放页正文以条目介绍开头；①n0 断言正文 ≠ 标题（不再把整段 caption 显示成标题）。
- ①o 播放页点编辑能拉起同一个编辑框（跨层联动）。
- ②d/②e 点「清除缓存文件」先弹确认，**取消后缓存占用 files/bytes 逐字未变**（未盲执行）。
- ③k 批量删除点**取消**后记录数逐字未变；③i 确认文案含所选条数；③n 单条确认措辞与批量区分；
  ③p 断言缓存管理内**不存在**「清除缓存文件」按钮（动作只有一个家）。

**安全性**：该脚本在真实库上跑，写入类探针一律改完即还原并断言还原成功；
删除只走到确认条为止并点取消。真正的删除语义由 `?ids=` 端点半径（e2e）+ 单测
`delete_cache_tasks_by_ids_removes_only_selected`（应删的删、不该删的一个不动）覆盖。

## 修复过程中暴露的次生缺陷（已一并修）

`update_media_item` 原来写的是 `patch.title.unwrap_or(existing.title)` ——
`{"title": ""}` 会把标题**写成空串**。这不是理论风险：e2e 第一次运行时该子断言实测
`title=''`，并且**把真实库 item 380 的标题写空了**。已从 `media_message.caption`
原文字段还原。修法即上面的「空标题不可表达」归一化 —— 让错误状态不可表达，
而不是在调用点各自记得校验。

## 教训

1. **两个平级实体的文案字段必须同构**。剧集有 `description`、条目没有，于是同一份
   caption 在两侧被切成了不同形状 —— 「一边对一边错」的根因往往是**数据模型不对称**，
   不是切分算法有 bug。
2. **功能存在 ≠ 入口存在**。`opacity-0 group-hover:opacity-100` 在代码里是「有」，
   在用户那里是「没有」。可发现性要用运行期几何断言（`elementFromPoint`）去验，
   不能看类名或看 DOM 里有没有这个节点。
3. **「档位」不等于「集合」**。批量操作的作用范围应当由**用户勾选的 id 集合**决定；
   枚举 `scope=all|failed` 只是把开发者的分类强加给用户，且表达不了「就这几条」。
4. **动作要放在它所属的层级**。记录级运维面板里放配置级动作（清磁盘）会把入口藏掉，
   同一后端动作只保留一个入口 + 一处指路文案。
5. **探针脚本必须自带还原**。写入型 e2e 若只断言「写进去了」，一次断言失败就会把
   真实库留在脏状态（本次已发生一次）；还原步骤 + 「还原成功」断言是脚本的一部分。
