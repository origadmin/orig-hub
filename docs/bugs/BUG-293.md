## 现象

用户播某条目的某倍速时**播放卡死**；此后**该倍速再也播不出来**（请求一直挂、无任何响应字节），
而**同条目其他倍速正常**、**其他条目正常**。重启 `orig-tg` 后恢复，但**再触发一次又会重新卡死**。

## 事实

### 事实 1：守卫挂在循环顶部，而泵阻塞在循环**体内**

`download-engine/crates/orig-tg/src/routes.rs` 转码泵主循环：

```rust
let stall_limit = std::time::Duration::from_secs(30);          // :4817
let mut last_progress = std::time::Instant::now();             // :4818
let mut ever_read = false;                                     // :4819
loop {
    if ever_read && last_progress.elapsed() > stall_limit {    // :4821   ← 守卫只在循环顶部
        // 杀 ffmpeg + finish(false) + return
    }
    match stdout.read(&mut buf).await {                        // :4831
        Ok(0) => break,
        Ok(n) => {
            last_progress = std::time::Instant::now();
            ...
            if file.write_all(&buf[..n]).await.is_err() { ... }        // :4838  ① 写 .part
            if !client_gone
                && resp_tx.send(Ok(...)).await.is_err() { ... }        // :4843-4847  ② 发给客户端
        }
    }
}
```

`resp_tx` 是**容量 32 的有界通道**（`tokio::sync::mpsc::channel(32)`，`:4617`）。
客户端**停止读取**（TCP 窗口关闭 / 响应体不再被 poll）⇒ ② 处 `send().await` **满即阻塞**，
且**不报错**（接收端仍在）⇒ `client_gone` 仍为 `false`。
泵停在这里 ⇒ ① 不再执行 ⇒ `.part` 冻结；**也不再回到循环顶部** ⇒ **守卫永远轮不到执行**。

### 事实 2：ffmpeg 被反压顶住（0% CPU）

泵不再读 `stdout` ⇒ ffmpeg 的 `pipe:1` 写满 ⇒ ffmpeg **阻塞在写**：
实测 **0.0% CPU**，而正常转码期同进程为 **266%**（同一 pid 前后对照）。

### 事实 3：请求侧最长挂 600 s

`wait_for_transcode`（同文件 `:4135`）以 `tokio::time::timeout(Duration::from_secs(600), ...)` 等 watch。
泵**活着但卡住** ⇒ 发送端未关闭 ⇒ 既不 `ready` 也不 `orphan`
⇒ 请求**阻塞到 600 s 超时**，之后才返回 503「transcode in flight but proxy not ready; retry later」。

## 复现（因果，已执行 2026-10-13 04:30 前后）

1. 对**冷**变体 `<item_id>@4x` 建连，读到 ~4 MiB 后**停止读取**（socket 保持打开）。
2. 观察该变体的 ffmpeg 与 `.part`：

| 时刻 | ffmpeg CPU（% 单核） | `.part` 字节 |
|---|---|---|
| 停止读取时 | — | 8 713 623 |
| +10 s | **266.4** | 8 713 623 |
| +20 s | **0.0** | 8 713 623 |
| +30 / +40 / +50 / +60 s | **0.0** | **8 713 623（冻结）** |

⇒ **30 s 的守卫在 50 s 零输出期间一次都没触发**（与事实 1 的结构一致）。

3. **现场旁证**（同机另一变体，用户当时正在播）：`<item_id>@2x` 的 `.part` 自 **04:24:10** 起冻结
   （>4 分钟），其 ffmpeg **0.0% CPU**、`orig-tg` **3%**（空转），`netstat` 显示一条
   **来自 `msedge.exe` 的 ESTABLISHED** 连接挂在 `19787` 上；同一 URL 复测 **`code=000` / 0 字节 / 20 s**，
   而同条目 `speed=1`、`speed=3` 均 200（28.7 MB / 39.5 MB）⇒ **只有这一格死**。

## 修复实施（2026-10-13，代码已改）

改在 `download-engine/crates/orig-tg/src/routes.rs`（唯一代码文件）：

1. **`acquire_transcode_role`：毒化不再 panic。** `.expect("transcode map poisoned")`
   → `.unwrap_or_else(|e| e.into_inner())`。`std::sync::Mutex` 在持锁线程 panic 后**永久毒化**，
   原写法会把**一次** panic 放大成此后**每一次** `/stream` 请求都在这里 panic（全站播放永久失败）。
   与本文件既有 `TITLE_BACKFILL_ATTEMPTS` 同策略：取回内部值继续用。
2. **转码泵主循环：给两处阻塞点各自加时限**（原「无进展」守卫挂在循环顶部、循环体却会阻塞
   ⇒ 守卫**不可达**，本档事实 1）。删除 `last_progress` / `ever_read` 顶部守卫，改为：
   - `tokio::time::timeout(30s, stdout.read(&mut buf))` 超时 ⇒ 判 ffmpeg 僵死 ⇒ 杀进程 + 清 `.part`
     + `finish(false)` 出表返回。**不再依赖 `ever_read`**：从未产出任何字节的僵死同样清。
   - `tokio::time::timeout(30s, resp_tx.send(...))` 超时或失败 ⇒ 判 `client_gone`：
     FRC 变体（`speed_hundredths.is_some() && persist`）**继续**把 `.part` 写完并改名成正式代理；
     live-only（1x / `?t=` 锚点）立即取消（杀 ffmpeg + 清 `.part`）。
3. **未改动**：`TranscodeKey` 单飞语义、`slot` RAII 出表（BUG-288）、「断开后继续转码」、
   LRU 预算、BUG-226 锚点流语义、stream-first（BUG-230）。
