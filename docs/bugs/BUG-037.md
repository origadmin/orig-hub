# BUG-037：分批加入的内容裂成两个剧集，且没有合并能力

- **状态**：fixed
- **日期**：2026-09-18
- **模块**：engine（`media.rs` / `routes.rs`）+ shell（`api/media.ts` / `media/SeriesDialog` / `media/SeriesDetail` / `media/EpisodeList` / `MediaLibraryPanel`）

## 现象

用户主诉（原文）：

> 「剧集可能还需要一个合并功能，比如第一次 1,2 加入了，第二次 3,4 加入了，这会变成 2 个剧集，
> 这时候需要合并功能将内容合并到一起。」

即：**同一部内容被拆成两个剧集，而系统没有把它们合到一起的手段。**

## 事实取证（先复现，再定性）

用户库里**已经真实发生**（真库 `%APPDATA%\com.origadmin.orighub\tg\store.db`）：

```
id=26  1 集   AI成人短剧 【蜜桃TV】 · 2026-09-18
id=27  3 集   AI成人短剧 【蜜桃TV】 · 2026-09-18      ← 标题完全相同

26  source_key = tg:group:-1004418016251:14316412002085836
27  source_key = tg:group:-1004418016251:14316388967223316
                 ↑ 同一频道，两个不同的 group_id
```

自动成剧（BUG-031 路径）按「每个 TG 相册 = 一个剧集」建了两部；两次分批缓存各自产生一个相册，
于是同一个频道、同一部内容被建成两部**同名剧集**。

## 根因

**跨相册的归并无法自动判定。** 系统判断「这批内容和那批是同一部剧」的唯一可靠信号就是
TG 相册的 `group_id`；用户分批选择/转发必然产生不同的 `group_id`，系统无从知道它们该是一部剧。

排除掉的两条「自动归并」路线：

- **按标题相同自动合并** —— 同日同频道缓存两部不同的剧是常见操作，自动合并会误伤且不可逆。
- **把自动成剧改成「每频道一剧集」** —— 反向出错：会把用户有意分开的内容强行并掉。

⇒ **跨批次归并必须由用户表达意图，因此「合并」不是补救功能，而是唯一正解。**

**加剧因素**：自动成剧标题为 `{频道} · {日期}`（只到**日**粒度），同日同频道的两批必然重名 ——
列表里两个同名剧集无法分辨，合并时也容易选错目标。

## 语义边界：合并**不做任何内容级去重**

用户进一步给出四条现实约束，它们分别击穿了三种可能的去重依据：

| 约束 | 被击穿的依据 |
|---|---|
| 文件名可能重复而实际内容不同（分散保存导致） | 文件名 / 标题不可作键 |
| 同一内容可能从多个源进来（tg 缓存 + 本地导入） | 「一条记录」也不够 |
| 序列里会同时有 `1, 2, 1-2, 3, 4`（`1-2` 是并成单文件的版本） | **重叠 ≠ 重复**，范围重叠不可作键 |
| 每批都可能附带同一个预告 | 真重复（预告）也不该被系统吞掉 |

因此定稿语义：**合并只做「搬移 + 保序」，成员集合一律不动。**

- 唯一允许的跳过：`item_id` 在目标**同季**已存在 —— 那是「同一条数据库记录」，属事实而非启发式。
- 跳过**必须如实回报**（`MergeReport.skipped`），不让「少搬了东西」被静默掩盖。
- **集号是「位置」，不是「身份」**：目标各季从 `MAX(episode_no)` 续编，源剧集的原始集号写入
  `media_episode.origin_episode_no`、来源剧集标题写入 `origin_series_title`（**快照**，因为源剧集
  会被删除，存 id 会立刻悬空）。重编后用户仍能分辨「这条原来属于哪部剧、是第几集」。

## 修复

**engine**

- `media_episode` 新增 `origin_series_title` / `origin_episode_no`（旧库兼容按列探测补列）。
- `EpisodeView` 追加 `origin_series_title` / `origin_episode_no` / `source` / `ref` —— 后两者是
  「同一内容多源导入」时用户分辨该删哪条的唯一依据（标题与文件名都不可靠）。
- 新增 `Store::merge_series(target, source)`：`BEGIN IMMEDIATE` 事务内搬移全部 episode →
  标签并集 → 目标元数据仅在缺失时继承 → 删除源剧集 → `COMMIT`；任何一步失败即 `ROLLBACK`。
  - 搬移用**纯 INSERT**（刻意不用 `add_episode` 的 `ON CONFLICT DO UPDATE`）：集号若算错，
    宁可撞唯一约束让事务回滚，也绝不能静默覆盖目标已有分集。
  - `kind` **不重算**：新建对话框允许用户显式选择 kind，静默改写会覆盖用户意图。
- 新增 `POST /api/media/series/:id/merge`（body `{sourceId}`）：`sourceId == id` → 400，
  目标/源不存在 → 404。

**shell**

- `api/media.ts`：`mergeSeries()` + `MediaEpisode` 补溯源与来源字段。
- 新增 `MergeSeriesDialog`：「下一步 → 确认合并」两段式（源剧集会被删除，必须显式确认）。
- `SeriesDetail`：「合并到…」入口；分集副行显示「合并自《X》原 E<n>」与条目来源。
- `EpisodeList`：侧栏分集同样标出合并溯源。

## 验收

门禁 `verify_shots/verify_series_merge.cjs`（并入 `run_all.sh`），断言覆盖：

1. 集号续编（目标各季从现有 max 续编，源顺序保持）；
2. 跳过项**如实回报**且数量正确；
3. **同名不同内容不被吞**（两条都保留）；
4. **`1-2` 与 `1,2` 并存**（重叠不触发去重）；
5. 溯源字段（`originSeriesTitle` / `originEpisodeNo`）随详情下发；
6. 源剧集已删除、源剧集的分集不再挂在源 id 下；
7. 边界：`sourceId == id` → 400、源不存在 → 404；
8. 重复调用（源已删）不产生副作用（目标内容不变）。

## 防再发

- **禁止**给合并加任何「按文件名/标题/时长/内容重叠」的过滤 —— 需要新判据时先证明它是
  「数据库记录身份」级别的事实，而非启发式。
- 合并类操作一律：**单事务 + 失败即回滚 + 不允许静默跳过**。
- 追溯性字段存**快照**而非外键：被追溯的对象会在同一操作里消失。
