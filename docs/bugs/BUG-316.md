# BUG-316: 所有页面访问卡顿——前端侧卡顿，根因未定（请求设计/渲染逻辑/dev 未打包三嫌疑并列）

- 状态: open（分段：①请求重复·配置风暴已修复并验证；②长任务/渲染段已修复并验证；③dev 首屏段待续）
- 发现日期: 2026-10-15
- 模块: shell
- 严重程度: high

## 现象

用户 2026-10-15 原话：「3. 所有页面访问卡顿,接口设计有严重问题(猜测),或者页面设计有严重问题.」
随后补充定位与边界：「"卡顿在前端侧",但是问题可能前后端,接口设计不合理,请求频繁,
渲染逻辑不合理,都可能造成页面卡顿.」

用户明示**卡顿发生在前端侧**，且根因保持开放：不预设是后端接口慢。

## 取证（真实 Edge + dev :5180 活栈，2026-10-15）

| 场景 | 耗时 | 切换引发 API 请求 | longtask >50ms |
|---|---|---|---|

两点已实测排除/收敛：

- **后端响应本身不慢**：接口 TTFB ~20-25ms（BROWSER 侧实测）⇒ 「daemon/orig-tg 慢」
  不是根因；问题在**请求的数量/重复/时机**或**主线程被渲染占住**。
- **dev 模式代价实锤**：首屏 103 个未打包 script（单项 160-190ms 量级），这是
  dev 专属放大项；但用户报的是「所有页面访问卡顿」而不只是首屏 —— 且用户环境
  也跑 dev —— 不能以此搪塞。

## 根因（未定，三嫌疑并列，按嫌疑强度排序）

1. **请求设计（最强嫌疑）**：切到 Telegram 一次 **16** 个请求且 `/api/config`、
   `/health`、`/api/tg/cache/tasks` **成对重复** —— React StrictMode 双挂载与
   「多个组件各自拉同一份数据」两因至少居其一（或并存）；设置 19 次同理。
   切换即请求风暴，而每个请求都带 React 状态更新 ⇒ 主线程被回调切片打碎。
2. **渲染逻辑**：下载视图切回即 183/122ms longtask，文件视图 113ms —— 长列表
   同步渲染（无虚拟化/无分片）直接把主线程占住百毫秒级，期间**任何交互无响应**。
3. **dev 未打包模块**：103 个 script 的首屏代价（单项 160-190ms）。仅 dev 成立，
   发布包不复现；但它是「首屏 2.2s」的主因，与①独立。

## 复现

1. dev :5180，开 devtools Performance；
2. 逐一点击侧栏 nav-download / nav-tg / nav-settings / nav-files，记录每次切换的

3. 复现探针读数：→TG 16 请求含三端点成对重复；下载/文件视图 longtask >100ms。

## 修复

分段定位、逐段可证伪，**禁止「优化一轮再看」式的无判据改动**：

1. **先定位请求重复来源**：量 StrictMode 双挂载 vs 多组件各拉（给数据源加请求
   计数锚点或网络面板按 initiator 归组）；若是前者评估关 StrictMode 双跑（仅 dev）
   或迁移到不会双发的数据层；若是后者按「单一数据源、组件订阅」收敛。
2. **再定位长任务来源**：下载/文件视图长列表定位到具体渲染组件（行数、单行成本），
   按需上虚拟化/分片；判据 = 同数据量下 longtask 阈值下降且有具体读数。
3. dev 首屏：评估路由级懒加载是否已覆盖、103 个 script 能否收敛（不牺牲
   BUG-298 的模块化目标）。
4. 每段落地配反向证伪：把重复请求加回/把虚拟化拆掉，断言必须 FAIL。
5. 不动后端接口语义（TTFB 实测无病）；若定位中发现后端真问题，另开档不并本条。

## 验收证据

### 段① 请求重复·配置风暴（已修复 + 活栈验证，2026-10-15）

**根因定位**：`getConfig()`（`api/daemon.ts`）与 `getTgConfig()`（`api/tg.ts`）是裸 `request()`，
零缓存 ⇒ 设置页单次挂载并发/重复拉取 `/api/config` 达 **8 次**（StrictMode 双挂 + `loadClassify`/
`loadProxy`/`Promise.all` + `useStore` 初始化 + `refreshTgState`），每次都是真实网络请求。

**修复**：两 getter 改为「在途去重 + 短 TTL（4s）」；五个 daemon 写配置端点与两个 TG 写配置端点
成功后 `invalidateConfig()` / `invalidateTgConfig()`，保证回读最新。

**反向证伪（修复前基线）**：修复前探针实测 `nav-settings` 的 `/api/config` = 8×。
**修复后活栈探针**（`tauri-shell/verify/bug316_locate_lag.cjs`，阈值 ≤2×）：
- nav-download `/api/config=0`
- nav-tg `/api/config=1`
- nav-settings `/api/config=0` ← 8× → 0×
- nav-files `/api/config=0`
- 四页 `RESULT: PASS`。

**剩余（段②/③，待续，非本次改动）**：其它端点（dialogs/health/cache/tasks/session）仍各 2×，属
StrictMode 双挂载使每个 mount effect 跑两次，需「单一数据源 + 组件订阅」或收敛 effect 才能彻底消除；
下载/文件视图 longtask（百毫秒级，无虚拟化）属渲染段②。本次**只动配置 getter**，不碰后端语义、
不动这些端点，符合「分段、可证伪、禁止无判据改动」。

### 段② 长任务/渲染段（已修复 + 活栈验证，2026-10-16，提交 1fbe6cd）

**根因定位**：两个重视图的全量同步渲染。cat-all 文件视图 671 行 × FileRow（实测
每节点渲染成本 ~0.26ms）、下载域入库组 104 行 × IngestGroupRow（重行组件
~0.52ms/节点）——切视图时一次性渲染全部行，把主线程占住百毫秒级。

**归因探针**（`verify/bug316_first_download_probe.cjs`，首访 nav-download 全程
profile + TaskAttribution）：229ms 中 JS 执行 ~49ms，其余为布局/绘制——即
438 节点 × 重行组件 × StrictMode 冷启动的固有成本，热路径 76ms。

**修复**：新增通用动态行高窗口化组件 `components/ui/virtual-list.tsx`
（measure-and-cache：ResizeObserver 逐行盯高 + 布局效应同步量 offsetHeight +
offsets 前缀和 + 二分查找窗口 + 上下 spacer + rAF 节流滚动），接入两视图：

| 视图 | 容器 | estimate | overscan | 依据 |
|---|---|---|---|---|
| FileListView（cat-all） | file-list-scroll | 34px | 10 | 行高实测 34px 均匀（bug316_row_geometry 探针） |
| DownloadPanel（入库组） | dl-group-list | 108px | 6 | 折叠行实测高；展开行 432px 由 measure-and-cache 逐帧收敛 |

布局同步改为「列表内滚动」：面板根弹性列 + 概览/来源切片/banner 置顶
（shrink-0），页面级滚动因面板 h-full 自然变 no-op。

**契约**：窗口化容器挂 `data-total = items.length`，验收脚本据此断言「渲染行数 <
总数」——拆掉窗口化（恢复全量渲染）必 FAIL 的反向证伪锚点。

**读数对比**（dev + StrictMode，1440×900，Performance longtask 实测）：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| nav-download 首访 | 243+107ms | 220ms |
| nav-download 回切 | 235+114ms | 112ms |
| nav-files | 97+234ms | 125ms |
| nav-tg（未触及） | 99+78ms | 136ms |
| nav-settings | 0 | 0 |

首访 nav-download 残余 ~220ms = 438 节点 × 重行组件 × StrictMode 冷启动固有
成本（热路径 76ms），非本次改动可再压缩项，记录在案。

**正式验收**（`verify/verify_bug316_segment2_render.cjs`，18 断言 ALL PASS）：
① 白屏自证；② 文件域 data-total==API 期望（120 媒体 + 551 成品去重 = 671）+
渲染行数 < data-total + ≤ WINDOW_MAX(80) + longtask < 220ms + 滚到底仍窗口化；
③ 下载域 data-total==唯一 groupKey 数（104）+ 首访 < 300ms + 回切 < 200ms；
④ tg/settings 防回归；⑤ 无页面异常。

**反向证伪（「验收的验收」）**：临时把窗口 useMemo 改为全量（start:0,
end:items.length）⇒ **9 断言 FAIL**（渲染行数 104/104、671/671；longtask
689/607/440ms）——结构与性能双路径证伪均成立。

**受影响验收脚本同步适配**（窗口化 DOM 下全列断言改走「滚到底按 key 去重累积 +
收集数 == data-total」）：verify_bug299_files_explorer_list.cjs（18 断言 ALL
PASS）、verify_bug300_ingest_aggregation.cjs（42 断言 ALL PASS）、
verify_bug320_expand_toggle.cjs（12 断言）、verify_bug318_unavailable_window.cjs
（7 断言，含 orig-tg 受控不可用窗口模拟：banner 出现、12 行 last-known 保留、

**顺带抓出的真 bug**：DownloadPanel 的 VirtualList 初版漏 `overflow-y-auto`
