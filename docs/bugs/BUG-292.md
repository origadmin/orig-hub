# BUG-292: 同一相册被建成**两个剧集**（正常标题 + 占位名标题各一个），同一个 `media_item` 被两条 `media_episode` 同时认领 —— 媒体库同一片子出现两次、文件挂双份

- 状态: open
- 发现日期: 2026-10-12
- 模块: engine
- 严重程度: critical

> 来源：用户 2026-10-12 报障「媒体库现在存在非常严重的异常漏洞，**同一片子出现了正常标题和异常标题同时 2 个**，
> 已经破坏了媒体库的正常功能了。」
> **本档为任务文档**（用户定：纯文档任务，代码由别的组负责）。
>
> **严重程度说明**：用户原话即「非常严重」「破坏了媒体库的正常功能」⇒ 定 `critical`。
> **如实标注**：**没有数据丢失**（`media_item` 无重复行，487 行 487 个不同 `ref`）——坏的是**库的组织层**
> （同一个 item 被两个剧集重复归属）。若实现方认为可降级为 `high`，判据与修复方向**不受影响**。
>
> **数据口径**：遵循「内容数据不入库」（`docs/bugs/BUG-232.md:79`）—— 不含频道名 / caption 文案 /
> 完整频道 id；下表标识按规约掩码，只保留**可核验的结构关系**。

## 现象

媒体库里**同一部片子出现两个条目**：
- 一个标题**正常**（真剧名）；
- 一个标题是**占位名** `TG <chat_id> · <日期>`（BUG-283 的同源形态）。

两者**不是不同片子**：它们的 `media_episode` 指向**完全相同的 `media_item` 行** ⇒
媒体库剧集墙看到两条、文件/分集被挂**双份**，合并、归档、导出全部失去依据。

## 实测（生产库 `%APPDATA%\com.origadmin.orighub\tg\store.db`，只读；`media_series` 共 70 条）

**重复剧集对共 3 对**（按「共享 item 的 `ref`」查出）：

| # | 占位名剧集 | 正常名剧集 | 共享 `item_id` | 说明 |
|---|---|---|---|---|
| 1 | `#281`（1 集） | `#261`（4 集） | 1 / 1 | 占位剧集的唯一集与正常剧集第 4 集同指一个 item |
| 2 | **`#335`（8 集）** | `#315`（8 集） | **8 / 8** | **两个剧集的分集 item_id 逐条完全相同（1401…1408）** |
| 3 | `#337`（1 集） | `#318`（1 集） | 1 / 1 | 同指一个 item |

- `media_item` 总数 **487**、不同 `ref` 数 **487**、差值 **0** ⇒ **条目层没有重复**。
- ⇒ **重复发生在「剧集 / 分集」层：同一个 `media_item` 行被两个 `media_series` 的 `media_episode` 同时引用。**

## 根因（四条，前两条是主因）

### 根因 A：剧集幂等键有**两套**且**互不可认** ⇒ 同相册建两个剧集

`download-engine/crates/orig-tg/src/routes.rs:2289-2297`（`ensure_series`）：
```rust
let key = match self.task_group {
    Some(g) => format!("tg:group:{}:{}", self.chat_id, g),          // 带 group
    None => { let first = self.task_msgs.first()…; format!("tg:msgs:{}:{}", self.chat_id, first) }  // 退化
};
```
- 正常剧集的 key 形如 `tg:group:<chat>:<group>`；**占位名剧集的 key 形如 `tg:msgs:<chat>:<首条消息>`**。
- ⇒ **同一个相册**被入库两次：一次**带** group（→ `tg:group:`），一次**不带**（→ `tg:msgs:`）；
  两个字符串**不相等** ⇒ `find_series_by_source_key`（`:2298`）**命中不到** ⇒ **再建一个剧集**。
- `task_group` 来自 `task.group_id`（`:2075`），即**入队时客户端传的 `req.group_id`**。

### 根因 B：`task.group_id` 与**消息自带的** `media_message.group_id` 是**两套值**（实测恒差 1）

- 3 个正常剧集 key 里的 group，与**同组消息**在 `media_message.group_id` 中存的值**恒差 −1**
  （只摘末四位示意：`…9468` ↔ `…9469`、`…8476` ↔ `…8477`、`…0128` ↔ `…0129`）。
- 同一相册内所有消息的 `group_id` **完全一致**（实测 1196–1199 全同值）⇒ **消息侧的表征是权威且稳定的**。
- ⇒ 幂等键**不用**消息自带的 group_id，而用**入队时客户端传的** `req.group_id`（另一套值）。

### 根因 C：**入队去重键同样源于 `req.group_id`** ⇒ 同相册会被入队两次

`routes.rs:1240-1247`：
```rust
// 去重键：整组按 (chat, group)，单条按 (chat, message)。
let item_key = match req.group_id {
    Some(g) => format!("g:{}:{}", req.chat_id, g),
    None => format!("m:{}:{}", req.chat_id, req.message_ids[0]),
};
… .enqueue_cache_task(req.chat_id, req.group_id, &item_key, &req.message_ids, &dir)
```
⇒ 带 group 的请求与不带 group 的单条请求会得到**两个不同去重键 ⇒ 两个任务**，为根因 A 的两次入库供料。

### 根因 D：`media_episode` **没有 `UNIQUE(item_id)`** ⇒ 数据库层零约束

实测 DDL（生产库）：
```sql
CREATE TABLE media_episode (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    series_id INTEGER NOT NULL, item_id INTEGER NOT NULL,
    season … , episode_no … ,
    UNIQUE(series_id, season, episode_no)      -- ← 只有「同剧集内集号唯一」
);
```
⇒ 同一个 `item_id` 被**多个剧集**认领，**数据库层完全不阻止**（本档 3 对即是）。

### 附带：这解释了 BUG-283 的占位名为何总是「多出来的那一个」
复用同一批 item 的新剧集**拿不到组级 caption**（BUG-283 事实 7：`first_caption` 只扫本批消息）
⇒ 占位名 + 剧集重复是**同源的两个面**。

## 复现

1. 对某相册**带 group_id** 入队并入库（建成正常标题剧集）。
2. 再对**同相册内的某单条消息**（不带 group_id）入队并入库。
3. 媒体库出现**两个同名条目**：`media_series` 中一条 key=`tg:group:…`（正常）、一条 key=`tg:msgs:…`（占位名）。
4. 只读 SQL 佐证（**同一 item 被两个剧集认领**）：
```sql
SELECT item_id, COUNT(*) c FROM media_episode GROUP BY item_id HAVING c > 1;
SELECT id, title, source_key FROM media_series WHERE title LIKE 'TG %' ORDER BY id;
```

## 修复（方向；**本档不改代码**）

**总目标：一个相册只能有一个剧集；一个 `media_item` 只能被一个剧集认领。**

1. **统一幂等键的真源（P0）**：组建剧集键与入队去重键都改用**消息自带的 `media_message.group_id`**
   （实测同组一致、稳定），不再用客户端 `req.group_id`；确实无 group 时才退 `tg:msgs:`。
2. **加数据库层唯一约束（P0）**：`media_episode` 增加 `UNIQUE(item_id)`（迁移时**先合并去重再建约束**），
   从物理上杜绝一个 item 被两个剧集认领。**注意**：该约束会影响计划中的 BUG-284 合并路径（同集归并为多源），
   须与「多源」模型协商口径（是「多 episode 挂同 item」还是「同 episode 挂多源」）。
3. **存量定向收敛（P0）**：对生产库这 3 对重复做合并——保留**正常标题**剧集，把占位剧集的 episode 归属
   并入/删除。**保留所有数据是核心需求**：`media_item` 行**不动**，只收敛剧集归属；不重不删。
4. **登记「两套 group_id」为独立小缺陷（P1）**：`task.group_id` 与 `media_message.group_id` 的固定差值
   **必须先定位哪个是权威值**，否则统一真源会再造出**第三套键**。
5. **不推翻既有裁定**：BUG-031（`tg:group:` 去重）、BUG-152（追加不写 title）、
   BUG-037 / 186（合并能力）、BUG-283（占位名重算）不得回退。

## 取证补充（2026-10-12，只读取证 + **本人独立复核** —— 权威相册身份、存量 key 生态与切键兼容性）

> 追加节，**不改写上文**。上文根因 B 只说「两套 group_id 恒差 −1」；本节把这件事**定性完毕**，
> 并给出「统一真源」时**必须先处理存量**的硬约束。除标注「取证工人」者外，数字均由本人用只读脚本对生产库独立复核。
> 生产库 `%APPDATA%\com.origadmin.orighub\tg\store.db`，全程 `mode=ro`。

### 结论 1：`task.group_id` 就是 Telegram 相册 id 本身；client 侧的值 = 「真实相册 id − 1」的系统性遗产

- 传递链五跳透传、**无算术变换**：`grammers.rs:890-931`（`group_id: m.grouped_id()`）→ feed → `tauri-shell/src/api/tg.ts:423-436` → `TgPanel.tsx:1252-1264`（`groupId: items[0].groupId` 原样）→ `enqueue_cache_task`（`store.rs:1030-1070` 原样 INSERT）→ `routes.rs:2075`（`task_group: task.group_id`）。
- **生产库全量复核（决定性数字）**：`cache_task` 125 条 = 60 带 `group_id` + 65 NULL；**60 个 task 值无一悬空**——
  **8 个本身就是真实相册 id，52 个恰好比真实相册 id 小 1（52/52 的 +1 值都存在于 `media_message.group_id`）**；task 值 58/60 为偶数。
  消息侧 668 个相册 id 中仅 **9** 个偶数 ⇒ 偶数值几乎不可能是真实相册 id。
- ⇒ 上文根因 B 的「恒差 −1」实为**系统性 −1 遗产**（历史某条写入路径的产物）：不是两套实体、也不是当前代码 off-by-one
  （取证工人：`git log -S grouped_id` 全历史仅 2 个提交且写法逐字未变；当前树上该链路无 +1/−1）。
- **权威值 = 消息侧 `media_message.group_id`**（取证方向已定，本轮证据闭合）：唯一写入口 `store.rs:584-616` `upsert_message`（值 ← grammers-client 0.10.0 `grouped_id()` 裸 TL 字段）；
  **668 个相册全量验证**：组内一致、**跨 chat 复用 = 0**、相册 `[min,max]` 消息区间内 NULL 空洞 = **0**。

### 结论 2：存量 key 生态 —— 直接切键 ⇒ **44/50 失配**（会以反方向重演本缺陷）

- `media_series` 70 条 = `tg:group:` **50** + `tg:msgs:` **14** + NULL 6（复核一致）。
- 50 条 `tg:group:` 的 group 值中**仅 6 条**能在 `media_message.group_id` 命中（恰是消息侧 9 个偶数里的 6 个）；**44 条失配，且 44 个失配值的 +1 值 100% 存在**。
- ⇒ **不先处理存量就切键 = 换一个方向重演本缺陷**：这 44 个相册下次入库仍会命中不到旧 key ⇒ 再建一个剧集。
  「修复方向 4：必须先定位哪个是权威值」至此已闭合（消息侧），**剩下的就是迁移兼容性**。

### 结论 3：`None` 分支是常见路径，且 6 条 `tg:msgs:` 正是本档三对重复的占位名剧集

- 65/125（**52%**）任务 `group_id` 为 NULL；14 条有键剧集走了 `tg:msgs:`，其中 **6 条首消息其实带 group**（取证工人点名列：series 112/335/281 等）——
  正是 `#315↔#335` / `#261↔#281` / `#318↔#337` 三对里的**占位名那一侧** ⇒ **根因 A 的在产实证**（本该走 `tg:group:` 却退到 `tg:msgs:`）。
- 入队去重两套键空间（`routes.rs:1241-1244`：`g:{chat}:{g}` / `m:{chat}:{msg0}`）**不相交**：生产库现存 **10 组** `g:`+`m:` 并存（取证工人）；
  −1 遗产还让 `g:` **自身分裂**（同相册 …077/…076 两个键、两个任务）⇒ 根因 C 直接供料。

### 结论 4：统一真源的顺序（三步，**顺序错会以反方向重演本缺陷**）

1. **先收敛**：按「修复方向 3」先合并存量 3 对重复（保留正常标题侧），给切键一个干净基准。
2. **再迁键**：每条 `tg:group:` key，用其分集 item 的 `ref` 回查 `media_message.group_id`（同相册恒定）重写——
   **44/50 变值（偶→奇）、6/50 不变**；14 条 `tg:msgs:` 中首消息有 group 的 6 条改 `tg:group:<消息值>`，无 group 的 8 条保持。
   迁后必须校验 `source_key` **全局唯一**。
3. **后切源**：新键逻辑改为「任务消息集合 → 查消息侧 `group_id` → 有则 `tg:group:`，无则 `tg:msgs:`」，**不再信 `req.group_id`**；
   入队去重键同源改造（否则键换了、任务还是两条）。

### 结论 5：切源前唯一未决实测项（继承给实现方，不得跳过）

- 历史上**两条拉取路对同一相册给过不同值**（10-09 feed/回填出偶数、10-12 monitor 出奇数——取证工人由 `created_at` 与奇偶分布交叉得出）。
  若今天两条路仍不一致，则**消息侧自身会随写入路径漂移**：`upsert` 的 `COALESCE` 偏好新非空值，一条 `getMessages` 回填就能把某相册的奇值改写 ⇒ 迁到消息侧的键会再次失配。
- ⇒ 切源前必须实测：对同一相册分别走 `/api/tg/messages`（feed）与任务回填两条路径取值比对，**确认一致后固定只用一条拉取路写 `group_id`**。

### 新增判据（建议并入「验收证据」清单，编号顺延；本档不改写原清单）

7. **迁键可证伪**：迁移后 `media_series.source_key` 全局唯一；44/50 的 `tg:group:` 键值由「真实 id − 1」变为真实 id。
   **反向证伪**：迁移前后 key 集合完全相同 ⇒ 迁了个寂寞 ⇒ **FAIL**。
8. **不再信任 client 值**：构造「先带 group 入队、再以单条消息入队同一相册」只产出 **1** 条剧集、**1** 个任务。
   **反向证伪**：仍按 `req.group_id` 与 `g:`/`m:` 双键空间 ⇒ 必重现（现存 10 组并存即失败样本）⇒ **FAIL**。

## 验收证据

（状态 `open`，尚无验收证据。修复后必须满足的**可证伪判据（预先声明）**：）

1. **一个 item 不被两个剧集认领**：
   `SELECT item_id, COUNT(*) FROM media_episode GROUP BY item_id HAVING COUNT(*) > 1` 必须返回 **0 行**。
   **反向证伪**：去掉 `UNIQUE(item_id)` ⇒ 必重现双挂 ⇒ 判据必 **FAIL**。

   断言该相册最终只有 **1** 条 `media_series`。
   **反向证伪**：仍按 `tg:msgs:` 退键 ⇒ 必出现第 2 条 ⇒ **FAIL**。
3. **存量清零**：生产库双挂 item 数由 **3** 降为 **0**。
   **反向证伪**：不做合并 ⇒ 恒为 3 ⇒ **FAIL**。
4. **不丢数据**：合并前后 `media_item` 行数**不变**（判据用「`SELECT COUNT(*) FROM media_item` 前后相等」证明）。
