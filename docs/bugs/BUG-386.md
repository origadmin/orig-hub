# BUG-386: cat-all 行集口径分裂——下载成品行不参与搜索过滤、按日期混排挤占媒体行

- 状态: open
- 发现日期: 2026-10-22
- 模块: shell
- 严重程度: mid
- 排期: 2026-11-26

## 现象

用户路径「文件域 → 全类目（cat-all）→ 搜索」的结果不可信：

1. 搜索框输入关键词后，**媒体条目**按 `q` 过滤（服务端），但**受管下载成品行**
   全量混入——与搜索词无关的成品文件照常出现在结果里；
2. `sort=recent`（默认）下两源按日期**交错混排**（`[...items, ...facts].sort(by addedAt)`），
   成品行把目标媒体行挤出虚拟窗口（BUG-305 探针实测：total=39 的行集里，
   目标本地行要滚到 `scrollTop=603` 才进窗口）；
3. 行数与 `total`（服务端过滤后的媒体计数）对不上——界面上多出来的成品行
   永远不在 `total` 里。

## 根因

`MediaLibraryPanel.tsx:1088` `catAllRows` 的两源合并口径分裂：

```ts
const catAllRows = useMemo(() => {
  if (tab !== 'all') return items            // 分类 tab：纯媒体（服务端已过滤）
  const facts = downloadFiles                // ← 全量受管成品，无 q 过滤、无分页
    .filter((f) => !taken.has(norm(f.path)))
    .map(/* 合成 MediaItem 行，source='download' */)
  if (sort === 'recent') return [...items, ...facts].sort((a,b) => b.addedAt - a.addedAt)
  return [...items, ...facts]
}, [tab, items, downloadFiles, sort])
```

- `items` = `listMediaItems({q, kind, tagId, hasBytes:true, sort, limit, offset})`
  —— 搜索/标签/分页全在服务端（`loadItems`，line 484-508）；
- `downloadFiles` = `listFiles()`（daemon 受管根扫描，`loadDownloadFiles`
  line 548-556，**只在 cat-all 拉**）—— 不进 `q`、不进分页、不进 `total`；
- 合并发生在**前端 memo**，两个源的过滤深度不对称 ⇒ 搜索态下成品行是
  「不过滤的常量」，媒体行是「过滤后的变量」。

这不是数据丢失（成品行是真实文件），是**搜索语义破裂 + 行集口径不一致**：
同一个「搜索」动词对两源行各念各的经。

## 修复（待拍板范围）

选项 A（前端补过滤）：`facts` 与 `items` 同样过 `q`（对 `f.name` 大小写
不敏感包含匹配）+ 同 `limit` 截断。改动面最小（单文件 memo 内），但过滤
两份真相（服务端一份、前端一份），与「下载目录唯一真源是引擎」的同源纪律
有摩擦。

选项 B（服务端统一）：受管成品扫描也走带 `q` 的端点（daemon `/api/fs/*`
加查询参数），`total` 含两源。口径最干净，但动 daemon 契约 + 前端两处
读取，回归面大。

选项 C（搜索态隐藏成品行）：`filterActive`（已有：`activeTagId!==null ||
(view==='items' && search.trim()!=='')`，line 1058-1060）为真时 cat-all
只呈现 `items`，成品行整体让位。语义最直白（「搜索只搜已登记内容」），
但用户可能找不到「记得文件名但没登记」的成品。

共同前置：无论选哪档，「行集口径」要写进 BUG-380 契约文档的 UI 数据源节
（现在只写了 activity/downloads 两端点，没写 cat-all 合并规则）。
