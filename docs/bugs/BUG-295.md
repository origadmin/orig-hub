## 现象

用户的诉求是「把下载中的任务置顶」，但实测**「置顶能力已经有了，而用户要找的那一行不在被置顶的集合里」**。

### 实测 1：渲染序 —— 一条**已完成**的任务占着第 0 行，要重试的散落在 116 行里

`GET /api/tg/cache/tasks/all` 的数组序 = 前端渲染序（`CacheManagerDialog.tsx` 的
`visible.map` 直出，无二次排序）。实测前 26 行（复现见 `## 复现` 的 G 节）：

| DOM 下标 | `cache_task.id` | status | done/total | 备注 |
|---|---|---|---|---|
| **0** | `<task_id>` | **done** | 10/10 | **已完成的占着首行**（它 `priority > 0`，被「优先下载」过） |
| 1 | `<task_id>` | interrupted | 0/1 | 需重试 |
| 2 | `<task_id>` | interrupted | 0/1 | 需重试 |
| 3 | `<task_id>` | done | 1/1 | |
| 4 | `<task_id>` | done | 2/2 | |
| 5 | `<task_id>` | done | 4/4 | |
| **6** | `<task_id>` | **interrupted** | **2/10** | **用户要找的那条 —— 埋在第 6 行** |
| 8 | `<task_id>` | interrupted | 2/9 | 需重试 |
| 18 | `<task_id>` | interrupted | 0/2 | 需重试 |
| 21 | `<task_id>` | interrupted | 0/1 | 需重试 |
| 25 | `<task_id>` | interrupted | 0/10 | 需重试 |

- 「全部」档共 **116 行**，**扁平、无分区标题**（`CacheManagerDialog.tsx:1337` 注释即
  `{/* 入库记录列表 */}`，其后是单个 `<div className="mt-3 min-h-0 flex-1 space-y-2 overflow-y-auto">`
  + `visible.map(...)`，中间**没有任何分组渲染**）。
- **15 条 `interrupted`**（实测 `GROUP BY`）散落在 116 行里，靠 `id DESC` 与 90 条 `done` 混排。
- 统计条（`data-testid="cache-ingest-summary"`，`CacheManagerDialog.tsx:1137`）读数实测为
  **「已入库 90 · 入库中 0 · 入库失败 26」** —— **没有「待重试」这一档**，
  而 26 里 15 条是「重启中断」（可重试），11 条才是真失败。

### 实测 2：用户看着「下载中」的那条任务，在一次重启后**不再是「下载中」**

本次取证期间实测到一次 `orig-tg` 重启（**非本会话发起**）：

| 观测点 | 值 |
|---|---|
| `orig-tg` PID | `36804` → **`40204`**（`netstat` 确认 `127.0.0.1:19787` 新持有者） |
| 日志 | `orig-tg bound 127.0.0.1:19787` + `orig-tg listening on http://127.0.0.1:19787 (mode=ready mock=false)`，其后 `2026-10-12T21:48:33` 重新 `connecting...` |
| 库内同一任务 | `<task_id>` 由 **`running 2/10`** 变为 **`interrupted 2/10`** |
| 全库 `interrupted` 计数 | **14 → 15**（同一会话内两次只读快照之间） |
| 日志内累计启动 | **37 次** `orig-tg listening`（同一端口） |

⇒ 用户看到的「下载中」在重启后**变成了「已中断」**，并且因为「已中断」不置顶（见根因 ①），
它**从用户视野里掉了下去**。这就是「下载中任务找不到」的**双重机制**：
**先被改名，再被埋进 116 行**。

## 根因

### ① 引擎：「活跃」的语义集合漏了 `interrupted`

`store.rs:186`：
```rust
pub const CACHE_TASK_ACTIVE_STATES: &str = "('queued', 'running')";
```
`list_cache_tasks`（`store.rs:1239`）的排序：
```sql
SELECT {CACHE_TASK_COLS} FROM cache_task
ORDER BY CASE WHEN status IN {CACHE_TASK_ACTIVE_STATES} THEN 0 ELSE 1 END,
         priority DESC, id DESC
LIMIT ?1
```
⇒ **只有 `queued` / `running` 进 0 号桶**。`interrupted` 落到 1 号桶，
在 1 号桶里按 `priority DESC, id DESC` 排 —— 而 `interrupted` 全是 `priority=0`（实测），
于是它**只能靠 id 大小侥幸靠前**，一旦用户「优先下载」过别的任务（`priority > 0`），
**一条 `done` 就能压在所有待重试之上**（实测 DOM[0] 正是如此）。

`CACHE_TASK_ACTIVE_STATES` 是**被多方依赖的契约常量**，不能随手扩：
- `active_cache_task`（`store.rs:1121`）、`active_cache_task_covering`（`store.rs:1143`）
  用它做**入队去重**；
- `is_cache_task_active`（`store.rs:1523`）用它做**任务是否还该继续跑**的判据
  （`run_one_cache_task` 每个条目开头都会问一次）；
- 部分唯一索引 `cache_task_active_uniq ... WHERE status IN ('queued', 'running')`
  （`store.rs` 建表 DDL 内）用的是**同样的字面量**。

⇒ **扩这个常量 = 改入队去重语义**（一条 `interrupted` 任务会开始**挡住**同组重新入队）
= 直接撞 `BUG-279` 的契约（其 `by-item` 取「最新一次尝试」依赖活跃语义）。
**所以修法必须是「新增一个派生的『待处理』概念」，而不是改这个常量。**

### ② 壳层：列表无分区，且没有「待处理」档

- `CacheManagerDialog.tsx:112` `GROUP_OF` 把 `failed` 与 `interrupted` **合并**成同一个
  `'failed'` 组；`:122` `MAIN_GROUPS = ['ingested', 'ingesting', 'failed']`；
  `:127` `SCOPE_TABS` 只有 `all / success / failed` 三档。
  ⇒ **「待重试」在 UI 里根本不是一个可选的档**，它与真失败挤在同一个 tab 里。
- `:925` 的 `visible` 只做「排除 `cancelled`」这一件事，**不排序、不分组**。
- `:1337` 起的列表是**单个扁平容器** —— 没有任何 section 标题。
  ⇒ 用户无法「一眼看到还有几件要处理」。

### ③ 语义层：「已中断」被呈现为「终态历史」，但它是**待办**

`GROUP_OF` 把 `interrupted` 归入 `failed` 组，而 `failed` 组在 `MAIN_GROUPS` 里
与 `ingested` 平级，**没有任何「需要动作」的视觉层级**。
`BUG-257` 已把 `interrupted` 的 `error` 写成「应用重启：传输被中断，可重试继续」
（`store.rs:1656`）——**文案是对的**，但它躺在第 18、21、25 行的行内小字里，
没有任何聚合读数把它顶到用户眼前。

### ④ 与 `BUG-277` 的边界（**不是复报**）

`BUG-277`（**fixed**）交付了「优先级能力」：`priority` 列（迁移 `migrate_cache_task_priority`）、
`CACHE_TASK_QUEUE_ORDER = "priority DESC, id ASC"`（`store.rs:222`）、
`set_cache_task_priority`（`store.rs:1582`）、以及 UI 的「优先下载 / 取消优先」
（`cache-batch-prefer-download` / `cache-batch-unpin`）。

⇒ **「能不能置顶」已经解决**。本条说的是**另一个问题**：
**该被置顶的语义集合漏了一类**（`interrupted` 是「用户必须处理」，却按「历史」排序），
**且列表没有任何分区/读数帮用户在 116 行里定位**。
判据不同：277 的判据是「用户能否给某条设优先级」，本条的判据是
「**一个需要用户重试的任务，是否在打开面板的第一屏可见**」。

## 复现

```sh
# 只读。B 节给「活跃 vs 不活跃」的分野；G 节给真实 API 渲染序与统计条读数。
python scripts/ingest_forensics.py                       # A~G 全节
python scripts/ingest_forensics.py --api-port 19787      # 只看 G 节需要端口
```

- **B 节**输出「引擎判为『活跃』」与「引擎判为『不活跃』（`interrupted`）」两组的**对照**，
  并硬断言 `interrupted` 明细行数 == `GROUP BY` 计数。
- **G 节**输出 `DOM[下标] id status done/total` 与统计条三段读数，
  并打印任务 JSON 的字段全集。
- **反向证伪**：`--api-port` 指向错误端口 ⇒ G 节必须打印「取不到」，
  **不得**报「0 行」——否则「列表为空」与「端口写错」不可区分（假绿）。

重启机制的复现：重启 `orig-tg` 前后各取一次
`SELECT status, count(*) FROM cache_task GROUP BY status`，
观察 `running` 的条目数是否转为 `interrupted`，且 `done` **保持不变**。

## 修复方向（建议实现，纯文档；改动前需用户拍板）

### 红线（先声明）

1. **不得修改 `CACHE_TASK_ACTIVE_STATES`** —— 它被入队去重、运行判据、部分唯一索引
   三方依赖（见根因 ①）。要「置顶待处理」，加**派生的**概念。
2. **不得改动 `mark_stale_cache_tasks` 的语义**（`running → interrupted` 是 BUG-257 的裁定：
   重启必须降级，否则 UI 卡在永不推进的假「缓存中」）。
3. **不得回退 `BUG-277`** 的 `priority` 能力与 `BUG-249` 的批量条。

### 建议落点

1. **引擎（`store.rs`）**：新增**派生常量 + 排序**，不改既有常量：
   ```rust
   /// 用户**必须处理**的任务（派生概念，不参与去重/运行判据）。
   /// 与 CACHE_TASK_ACTIVE_STATES 的区别：那是「引擎在跑」，这是「人要管」。
   pub const CACHE_TASK_ACTIONABLE_STATES: &str = "('queued', 'running', 'interrupted')";
   ```
   `list_cache_tasks` 的 `CASE` 改用它 ⇒ `interrupted` 与在跑的**同进 0 号桶**，
   桶内再按 `priority DESC, id DESC`。
   - 也可选「`interrupted` 排最前」（它比在跑的更需要用户动作）——
     **建议按「有动作可做」优先**，但需用户拍板（这是一个可见的产品选择）。
2. **接口**：`/all` 的响应加一个**只读计数**（`actionable` / `retryable`），
   或在壳层由 `tasks` 现算（**推荐后者**，零接口变更）。
3. **壳层（`CacheManagerDialog.tsx`）**：
   - `SCOPE_TABS` 增一档 **「待重试 · N」**（`data-testid="cache-scope-retryable"`），
     筛选 `status === 'interrupted'`（**与 `failed` 分开** —— 前者是「重启中断、点一下就继续」，
     后者是「真失败、要看原因」）；
   - 列表加**分区标题**（入库中 / 待重试 / 已入库 / 入库失败），或至少在
     `interrupted` 区块前插一条分隔标题；
   - 统计条（`cache-ingest-summary`）增第四段 **「待重试 N」**；
   - 「选择工具条」（`cache-select-bar`）已存在 ⇒ 只需让「待重试」档下的
     **全选 + 批量重试**（`cache-batch-retry` 已存在）成为一条两步可达的路径。

### 判据（可证伪，预先声明）

1. **排序**：造一条 `priority > 0` 的 `done` 任务 + 一条 `priority = 0` 的 `interrupted` 任务，
   `/all` 返回序中 **`interrupted` 必须排在 `done` 之前**。
   **反向证伪**：把 `CASE` 改回 `CACHE_TASK_ACTIVE_STATES` ⇒ `interrupted` 必落到 `done` 之后 ⇒ **FAIL**。
2. **分区可见**：`interrupted` 任务的 DOM 下标 **< 任何 `done` 任务的下标**（CDP 实测，读 `data-testid`）。
3. **读数**：统计条出现「待重试 N」，且 N == `tasks.filter(status==='interrupted').length`（实测锚 **15**）。
4. **不回归**：`active_cache_task` / `active_cache_task_covering` / `is_cache_task_active` /
   `BUG-279` 的 `cache_task_for_item` 行为**一字不变**；
   `check-bugs.py` 既有 4 项 ERROR 不增。
5. **重启后可找回**：重启 `orig-tg` ⇒ 原先 `running` 的任务变 `interrupted` 后，
   **仍在第一屏（分区「待重试」内）可见** —— 这正是用户「找不到下载中」的验收面。
