# BUG-300: 下载页不是全局任务监控——daemon `/api/activity` 五铁律俱备而前端零消费，来源遍历写死引擎+TG，无控制代理，TG 运行行渲染假暂停按钮（模块重整 M3）

- 状态: open
- 发现日期: 2026-10-13
- 模块: engine+shell
- 严重程度: mid
- 档位: standard

> **来源**：用户 2026-10-13 规划包 `docs/design/module-restructure-2026-10-13/tasks.md` §M3（D7=A）。
> 现状依据：daemon `GET /api/activity`（`activity.rs`）已聚合引擎 + TG 且有五铁律
> （只读聚合 / 控制分流 / 不造假暂停 / 插件不可达恒 200 / 不阻塞），但**前端零消费**。

## 现象

1. **前端不读活动端点**：下载侧仍各自打引擎任务端与 TG 快照端（`BUG-085` 的轮询面），
   聚合器 `activity.rs` 的能力没有出口。
2. **来源遍历写死**：`activity.rs` 只认「引擎 + TG」两个来源；将来任何插件进来都要改内核。
3. **无控制代理**：pause/resume/cancel/retry 仍在前端按来源分流直连各端点，
   没有统一 `POST /api/activity/jobs/:gid/:action`。
4. **TG 行渲染假暂停按钮**：TG 快照端不提供暂停能力，而前端按引擎能力渲染同一套控件
   ⇒ 用户点了没有反应（违反活动端点自己的「不造假暂停」铁律）。
5. **TG 工作区仍有一份任务轮询**（任务与下载双入口），缓存管理入口与任务列表语义混在一起。

## 根因

- 聚合端点是**后端先完工、前端未接线**的典型断层：`activity.rs` 的 Job 模型已有
  （`{plugin_id}:{native_id}` 命名空间的设计已写在 02-backend-architecture.md），
  但 `fetchActivity` 在前端无调用点。
- TG 侧缺「内存快照版全量端点」：`GET /api/tg/cache/tasks/all` 每次两次 SQLite
  （BUG-085 根因），2026-10-13 已去掉被丢弃的 counts（2→1 次），但**仍读 SQLite**。
- 控制动作映射没有能力声明层：插件能干什么没有可枚举来源，前端只能手写 if/else。

## 复现

1. 前端网络面板：无任何 `/api/activity` 请求；下载侧请求打到 `/api/engine/tasks` 与 `/api/tg/cache/tasks/*`；
2. TG 任务行出现「暂停」且点击无效；
3. 停 orig-tg 后下载列表整块报错（而非「来源不可用」标注 + 其余来源照常）；
4. 5s 高频拉取下 `GET /api/tg/cache/tasks/all` 仍有 SQLite 查询证据。

### 出口判据

1. 5s 高频拉取下 **DB 零查询**证据（TG 快照走内存）；`cargo test -p orig-tg`；
2. BUG-085 置 fixed 的证据（根因已除，不只是去掉 counts）；
3. 单测：注册表 0/1/2 插件、超时、部分不可达；控制代理对「无暂停能力」任务的拒绝路径；
4. 树档 × 来源 chips 正交过滤计数与原型一致；引擎 + TG 混合夹具；插件不可达 banner；
5. 非活动任务速度 0；TG 运行行显「运行中不可暂停」且**无暂停按钮**；
6. **反向证伪**：把插件注册表置空或让取回超时 → 端点仍须 200 且标注来源不可用（FAIL 即坏）。
