## 现象

1. **前端不读活动端点**：下载侧仍各自打引擎任务端与 TG 快照端（`BUG-085` 的轮询面），
   聚合器 `activity.rs` 的能力没有出口。
2. **来源遍历写死**：`activity.rs` 只认「引擎 + TG」两个来源；将来任何插件进来都要改内核。
3. **无控制代理**：pause/resume/cancel/retry 仍在前端按来源分流直连各端点，
   没有统一 `POST /api/activity/jobs/:gid/:action`。
4. **TG 行渲染假暂停按钮**：TG 快照端不提供暂停能力，而前端按引擎能力渲染同一套控件
   ⇒ 用户点了没有反应（违反活动端点自己的「不造假暂停」铁律）。
5. **TG 工作区仍有一份任务轮询**（任务与下载双入口），缓存管理入口与任务列表语义混在一起。

## 根因

- 聚合端点是**后端先完工、前端未接线**的典型断层：`activity.rs` 的 Job 模型已有
  （`{plugin_id}:{native_id}` 命名空间的设计已写在 02-backend-architecture.md），
  但 `fetchActivity` 在前端无调用点。
- TG 侧缺「内存快照版全量端点」：`GET /api/tg/cache/tasks/all` 每次两次 SQLite
  （BUG-085 根因），2026-10-13 已去掉被丢弃的 counts（2→1 次），但**仍读 SQLite**。
- 控制动作映射没有能力声明层：插件能干什么没有可枚举来源，前端只能手写 if/else。

## 复现

1. 前端网络面板：无任何 `/api/activity` 请求；下载侧请求打到 `/api/engine/tasks` 与 `/api/tg/cache/tasks/*`；
2. TG 任务行出现「暂停」且点击无效；
3. 停 orig-tg 后下载列表整块报错（而非「来源不可用」标注 + 其余来源照常）；
4. 5s 高频拉取下 `GET /api/tg/cache/tasks/all` 仍有 SQLite 查询证据。

## 实施记录（2026-10-15，M3-T03 核心联动 · 第二次修正）

### 第二次复报：呈现的「度」错了

用户原话：「逻辑有问题,现在针对的是个体而不是笼统的数据,合并显示的实现是完全错误的。
也许不能说完全错误,也可以看做和BT文件夹下载一样,但是这个度没有控制好,没有做到和BT一样程度。」

首版把 daemon 聚合端点返回的 **137 条 `cache_task` 记录逐行平铺**。但 `cache_task` 是
**一次入库操作**，不是内容对象 —— 只读取证：137 条记录只对应 **104 个唯一 `itemKey`**，
最多的键（`m:-1001341930464:208031`）**重复 7 次**（1 次取消 + 6 次完成）。平铺会让用户把
「同一内容的 7 次入库」读成 7 个不同任务；反过来把每条消息单列，又退化成「把种子里的每个
文件都列成顶层行」。BT 的粒度是：**种子一行，文件是明细**。

### 数据源：最终收敛到 daemon `GET /api/activity`（单一聚合入口）

聚合呈现需要 `itemKey` 作合并键，首版 daemon 的 `TaskView` 投影**不下发它**，故首版走
orig-tg 直连；复报后用户授权重启 daemon，补字段已落地：

- `activity.rs::TaskView` 增 `groupKey`：`cache` 侧 = orig-tg `itemKey`，`download` 侧 = 下载 id
  （各自唯一）；`cache_view` / `download_views` 投影赋值；单测
  `cache_view_group_key_equals_item_key` 锁住「cache key == itemKey / download key 唯一」。
- 前端 `useIngestGroups` 数据源由 `listAllCacheTasks()`（orig-tg 直连）切回
  `fetchActivity('all')`（daemon），TaskView 经 `toCacheTask` 投影成 `TgCacheTask`
  （`groupKey→itemKey`、`control.native_id→id`），聚合 / 展开 / 写操作逻辑不变。
- 重启由 `scripts/dev_services.py` 拉起（**本机旧 daemon（PID 828）此前已退出**，故新进程
  以普通完整性启动，无权限障碍）；`cargo build --release -p orig-daemon` → 0 错 →
  `sync-sidecars.sh` 四处副本一致 → `/health` 200、`/api/activity` 137 条 cache 任务均带 `groupKey`。
- `title` 回退（人类可读标题、空白回退 `itemKey`）随本轮一并生效；单测
  `cache_view_name_is_human_title_with_item_key_fallback` 覆盖。

### 前端（tauri-shell）

1. `domains/download/ingestGroups.ts`：**纯聚合层** —— 按 `itemKey` 合组（同键取 `updatedAt`
   最新为代表，其余进 `history`）、概览口径 `summarizeGroups`、动作 `ingestActionsFor`、
   树档映射 `groupInBucket`、`itemKey` 人话翻译。全部纯函数，无 React 依赖。
2. `domains/download/useIngestGroups.ts`：**单一数据源 + 单一轮询**（3s、等值短路、
   有活才轮、卸载即停、失败留旧快照并记 `error`）。
3. `domains/download/IngestGroupRow.tsx`：入库对象行（BT 的「种子」）—— 标题 / 状态 /
   进度（在传且总量已知时用条目内字节进度，让它真的会动）+「共 N 次」徽标；展开给**两层明细**：
   ① 条目清单（`/api/tg/cache/tasks/:id/items`，BUG-296 组清单，懒加载一次）；
   ② 历史批次（runs−1 条，含各自成因）。
4. `domains/download/DownloadPanel.tsx`：**概览条**（入库对象 / 在传 / 待处理 / 已完成 /
   已取消 = 用户说的「笼统的数据」）+ 来源切片（全部 / 下载 / TG 入库）+ 按对象聚合的行；
   挂载时补一次刷新（hook 挂在常驻壳上，面板重挂载时补拉，避免停轮后的旧快照）。
5. `shell/MainLayout.tsx`：唯一轮询点（面板不自拉）；侧栏徽标、状态栏读数与列表同源。

### 教训（本轮新踩，已记入项目记忆）

- **`inFlight` 重入守卫 + StrictMode 双调用 = 死锁**：首轮被守卫短路，而被取消的那次又在
  `finally` 里跳过状态回写 ⇒ `loading` 永久为 `true`（下载页停在「加载中…」，实测复现）。
  修法：首轮**不设防**（`pull(false)`），只有周期轮询防重叠；且 `hasWork` 初值必须为 `true`
  （否则「无活 ⇒ 不拉 ⇒ 永远无活」是第二重死锁）。
- **onClick 挂折叠头，不挂外层容器**：外层还包着展开区，点明细会把整行收起来。

### ① 下载中的 TG 没有状态控制

- 根因：入库行只按终态分派动作（活跃→取消、终态→重试），排队/在跑行没有优先下载出口；
  daemon `TaskView` 也不下发 `priority`/`chatId`/`messageIds`，前端有意图也发不出坐标。
- 修复：
  - `activity.rs::TaskView` 增 `chatId`/`messageIds`/`priority`；`cache_view` 原样转发
    （`chatId=0` 的老数据转 `None` —— 0 不是合法频道坐标），`download_views` 诚实缺省
    （`None`/空数组/0）。单测 `cache_view_forwards_locator_and_priority` 锁转发 + 老数据
    反证 + 下载侧诚实缺省反证；**验牙**：临时破坏转发 → 该单测 FAILED → 还原 → 11/11。
  - `ingestGroups.ts::ingestActionsFor(status, priority)`：queued→prefer、priority>0→unprefer、
    活跃→cancel、停滞/取消→retry。
  - `useIngestGroups.ts`：prefer→`setCacheTaskPriority(id,{top:true})`（置顶数值由后端算
    max+1，前端只表达意图，BUG-277 契约）；unprefer→`{priority:0}`；`signature()` 追加
    priority（等值短路签名漏 priority 会漏刷新）。
  - `IngestGroupRow.tsx`：优先徽标 `data-testid="ingest-group-prioritized"`。
- 真实栈 roundtrip（`tauri-shell/verify/verify_bug300_priority_roundtrip.py`，证据落
  `verify_shots/bug300-ingest-aggregation/priority-roundtrip.txt`）：retry→queued→立即
  置顶 200（priority=max+1，后端算）→ worker 抓起后 `/all` 仍带该 priority（持久化）→
  取消置顶 200（running 态可撤）→ 归零 → 收尾取消 ⇒ **零活跃任务、零残留置顶**（净零）。
  竞态路径亦证：置顶晚于 worker 抓起 ⇒ 422「priority only applies to queued tasks」
  守卫正确拒绝。

### ② 图片与视频混用「集」是基础逻辑错误

- 根因：BUG-044 只防新触发（video-only 才入集），历史脏数据（照片被挂分集、纯图空壳
  自动剧集）仍在库中，呈现上照片与视频共用「集」。
- 修复（orig-tg 启动修复，`media.rs`/`routes.rs`）：启动时摘非视频分集 + 删纯图空壳
  自动剧集；`media_item` 行不动（照片的合法挂载位是 `media_episode_image`）。
- 真实栈取证（store.db 只读；19:14 orig-tg 被监督巡检二次拉起后复证，**幂等**）：
  照片分集 68→**0**；`media_episode` 357 == video 357；`media_episode_image` 121；
  `media_item` 542 不变（file 6 / photo 179 / video 357）。残留 1 个「无视频分集」剧集 =
  `DiagCard_1790177710808`（0 分集、source_key NULL 的空壳诊断项，修复正确地不碰它）。

### ③ 取消后记录消失

- 用户裁定：「除非删除记录，任何情况不应该消除记录」。
- 修复：`summarizeGroups` 计 cancelled（概览「已取消」读数）；取消的任务留在「全部」档
  列表里（可数、可重试），只是从「在传/待处理」口径出账。
- **2026-10-15 夜修正（BUG-314，已 fixed）**：本条初版修复曾把「已取消」加成侧栏独立
  树档 —— 那是越权解读（用户要的是记录可见，不是新导航位；主 NAVI 数量严格标准化）。
  已撤档回 all/running/paused/done 三项，记录可见性由「全部档 + 概览计数」承担，
  验收断言同页改写（三条 BUG-314 断言全 PASS，取消行 8 == 概览读数 8）。

### ④ 入库流水线里面没有跳转查看

- 契约：缓存字节即媒体库条目本体（`cache_one → mark_downloaded →
  upsert_media_item(source="tg", ref="{chat}:{msg}")`）⇒ done 行走 by-ref 查找 + 就地起播。
- 共享 hook `hooks/useGoLibrary.ts`：两个宿主（`CacheManagerDialog` 缓存管理弹窗 与
  `IngestGroupRow` 入库行）共用一份实现，防 ref 约定 / ViewerItem 形状漂移（BUG-082 同款）；
  同一 ref 只查一次后端（`libRefCache`）；未命中由宿主行内写「尚未入库」。
- `hasLibraryLocator(task)` = `chatId !== 0 && messageIds.length > 0` —— 相册/批量组的
  `itemKey` 给不出 msg，这就是 `TaskView` 必须补定位坐标的原因。

### ⑤ 入库流水线里面很多功能应该在下载的

- 优先下载 / 取消优先 / 去媒体库查看全部落在下载域 `IngestGroupRow`（`DownloadPanel` 接线，
  `MainLayout` `onOpenMedia` 切媒体库视图）；缓存管理弹窗与入库行共用 `useGoLibrary`，
  不再各写一份。
