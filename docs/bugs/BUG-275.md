# BUG-275: media.rs 事务错误路径的 `ROLLBACK` 漏 `.await` —— Future 从未被 poll，回滚从未发生，失败后事务悬挂持写锁

- 状态: open
- 发现日期: 2026-10-10
- 模块: engine
- 严重程度: mid

> 来源：BUG-259 修复 set_item_tags/set_series_tags 事务时（`1d246c8`）照抄既有事务先例，
> 发现先例本身错：`switch_episode_source` / `detach_episode_source` 的 Err/COMMIT-fail 分支
> `let _ = self.conn.execute("ROLLBACK", ());` **漏了 `.await`**。lead 已 grep 独立核实。

## 现象与根因

`media.rs` 有 **4 处**（lead 实测行号，2026-10-10）：

- `:3161`（`switch_episode_source` 的 COMMIT 失败分支）
- `:3165`（`switch_episode_source` 的业务 Err 分支）
- `:3227`（`detach_episode_source` 的 COMMIT 失败分支）
- `:3231`（`detach_episode_source` 的业务 Err 分支）

形如：

```rust
let _ = self.conn.execute("ROLLBACK", ());   // ← 无 .await
```

`libsql::Connection::execute` 返回 `Future`，不 poll 就**不执行**：这行等于什么都没做。
后果链：业务失败 → 进入 Err 分支 → 试图回滚（实际没滚）→ 函数返回 Err，
但 SQLite 连接上 **`BEGIN IMMEDIATE` 的写事务还开着**。在 rollback journal 模式下
（见 BUG-274 的取证：本库非 WAL），一个悬挂的写事务会持有写锁，直到下一条
同连接语句或进程重启才消失——期间所有写路径排队，读也可能被 journal 挡。

对照：同文件 `:2560` / `:2628`（BUG-259 新增的 set_item_tags/set_series_tags）是
`execute("ROLLBACK", ()).await`，写法正确——问题只在既有先例的这 4 处。

## 复现

静态可核：

```bash
grep -n 'execute("ROLLBACK", ())' download-engine/crates/orig-tg/src/media.rs
# 每一处都必须带 .await；不带 await 的行号即缺陷点（当前 3161/3165/3227/3231）
```

行为级复现（修复时顺手落单测）：构造 COMMIT 成功但业务前一步已失败/或让 COMMIT 失败的
注入点，断言此后另一条写语句不被 `database is locked` 阻塞（= 事务确实被回滚了）。

## 修复方向

1. 4 处补 `.await`（`let _ = self.conn.execute("ROLLBACK", ()).await;`），语义与既有
   正确先例（`:2560/:2628`）逐字对齐；不改任何正常路径行为。
2. 单测：在 `switch_episode_source` / `detach_episode_source` 各注入一次失败，
   断言错误返回后同连接可立即再次 `BEGIN IMMEDIATE` 成功（若回滚缺失，会得到
   「cannot start a transaction within a transaction」）。
   **反向证伪**：把 `.await` 去掉，该判据必须 FAIL。
3. 全文件 grep 复核：`ROLLBACK` / `COMMIT` 的 execute 调用不再存在任何无 await 形态。

## 修复后必须满足（可证伪判据，预先声明）

1. `grep -n 'execute("ROLLBACK", ())'` 全命中带 `.await`（正控）；
   **反向证伪**：任删一处 `.await`，判据 1 的行为级单测必 FAIL。
2. 既有测试零翻动（本修复不改任何成功路径）。
3. `cargo test -p orig-tg` 全绿；新增判据 ≥2 条（两个函数各一条）。

## 关联

- **BUG-259**：缺陷发现来源（照抄先例时发现先例错）。
- **BUG-274**：同一连接 + rollback journal 模式下，悬挂写事务会直接放大其
  「缓存写入卡顿」现象——本条修的是它的一个放大器。
