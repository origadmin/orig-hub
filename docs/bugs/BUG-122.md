# BUG-122：没有转码 / remux，也没有可播性探测 —— 部分容器下完也播不了（实测 27.6%）

- 状态: open
- 严重程度: mid
- 模块: engine
- 发现日期: 2026-09-22
- 类型: epic
- 延期至: 2027-01-31（理由：设计级工程，需独立里程碑；详见关联设计文档）

## 现象

某些容器 / 编码（HEVC、部分 MKV）**下完了也播不了** —— 播放器直吃原始文件。

## 取证

```
grep -E "ffmpeg|transcode|remux"   （全仓）
→ 无任何转码 / remux 实现
```

## 为什么严重度定 low

它只在「S0（统一投递 + 背压）做完之后仍然播不了」时才成为瓶颈。在背压没修之前，
把问题归给编码会**修错地方**（BUG-034 教训：**先量真实上屏帧与 `videoWidth`**，
`videoWidth=0` 才是编码问题；`readyState` 满格不等于能播）。

## 修复方向

**先做能力探测，不引入全量转码**：

1. 探测容器 / 编码可播性（`probe_mp4_codec.py` 已有轨道与 codec 探测能力）；
2. 不可播时**明确告诉用户**（而不是黑屏或静默失败），给出可行动信息；
   参考 BUG-034 定的要求：解码异常不许静默，文案要给可行动指引；
3. 只有探测确认「确实有相当比例内容不可播」时，才评估按需 remux。
   CPU / 磁盘成本很高，先探测再决定。

## 注意

Playwright 自带 Chromium **不含** HEVC/AAC 等专有编解码器，其表现 ≠ WebView2。
涉编码的判断必须用 `BROWSER=msedge`（与 WebView2 同引擎），否则结论不可信。

## 2026-09-24 实测：**确实有相当比例不可播 —— 27.6%**（本条的门槛问题已回答）

修 BUG-163（本地投递首块延迟）后复测播放路径时，`<item_id>` 的封面抽帧在**修复前后两档都失败**
（`generateVideoPoster` 20 s 超时，`<video>` 从不触发 `loadeddata`），据此排查出本条的第一个真实样本。

**实测口径**：生产库 `media_item` 中 `kind=video` 且 `file_path` 非空、且**排除 `D:\test_videos` 测试夹具**
（94 条历史契约样本，混入会污染统计）后共 **29 条**，逐条读文件头判定：

| 结论 | 条数 | 占比 | 判据 |
|---|---|---|---|
| **不可播：MPEG-TS 流被命名为 `.mp4`** | **8** | **27.6%** | 每 188 字节一个 `0x47` 同步字节；含 `FFmpeg Service01`；**无 `ftyp` / 无 `moov`** |
| 可播：`avc1`（H.264）正常 MP4 | 21 | 72.4% | 首 atom `ftyp` |

不可播的 8 条 = `<item_id 区间>`，`file_path` 全在 `<用户目录>\Downloads\<一个内部文件名>`
（同一批 8 个 Telegram document，**发送方即命名为 `.mp4`**，不是本仓误命名）。

**Chromium / WebView2 没有渐进式 MPEG-TS 解复用器**（TS 只存在于 HLS 的 JS 解复用路径），
故这 8 条**在播放器里必然失败**、封面也永远出不来 —— 与投递节流无关（BUG-163 修复前后同样失败）。

**附带发现（错报 MIME）**：`serve_local_file` 用 `mime_of_ext_opt(path)` **按扩展名**宣告类型，
对这 8 条会宣告 `video/mp4`，而字节是 TS。能力探测落地时这里必须一并改为**按内容判定**，
否则「探测到不可播」与「服务端宣告可播」自相矛盾。

**一个已被排除的伪问题（防止误修）**：这 29 条的 `moov` **全部在文件尾部**（非 fast-start），
但修 BUG-163 后 `mount→playing` 实测仅 **95 ms**（`avc1` 那 21 条）——Chromium 用尾部 Range 处理得当。
**不要**为了「moov 在尾部」去做 remux / faststart 改造，那是修错地方（本条自己的 BUG-034 教训）。

**对「是否评估按需 remux」的结论**：比例门槛已满足（27.6% 不可播），
但**本机无 ffmpeg**（BUG-130 已记）⇒ remux 意味着引入工具链与 CPU/磁盘成本。
故按本条既定顺序，下一步仍是**先做能力探测 + 不可播时明确提示**，remux 单独评估。
