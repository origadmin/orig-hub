# BUG-311: 缺少批量整理命名能力（mp3tag 式模板命名/归位）——库内改名不动物理文件后，用户无可读命名的对外交付手段

- 状态: fixed
- 发现日期: 2026-10-14
- 模块: engine+shell
- 严重程度: low

## 现象

用户需求（2026-10-14 原话）：「剧集修改不涉及实际文件名,但是要支持批量整理命名方式
(类型 mp3 工具的管理命名方式)」。

现状：
- 无任何批量重命名/归位入口；单条改名只写库（见 BUG-310），物理文件保持
  `{msg_id}-{caption_slug}.ext` / `doc-<chat>_<msg>.ext` 等不可读内部名；
- 用户要把剧集交给外部播放器/分享/备份时，文件名不可读、目录不按剧集组织，只能手工在资源管理器整理。

## 根因

功能缺失（非行为缺陷）：系统有归仓（cache.rs house_into）但没有「按用户模板重新组织物理文件」的
受管通道；没有模板引擎、预览 diff、冲突处理与幂等机制。

## 复现

文件域多选若干视频 → 无「批量整理/重命名」操作。

## 修复

按 **D24=A**（2026-10-14）：

- 模板变量（mp3tag 风格）：剧名、季、集、集名、来源、日期、扩展名等，示例
  `{剧名}/S{season:02}E{episode:02} - {episode_title}.{ext}`；
- 执行前**预览 diff 全表**（旧路径→新路径、冲突、越界字符处理）；幂等可重跑；
  同名冲突加序号不静默覆盖；
- 与 hash blob 模型（BUG-309）的关系：内部存储为内容寻址 blob，整理产物为**用户指定目录下的
  硬链接（同卷）/副本（跨卷）**，blob 本体与引用计数不动；整理是显式批量用户动作，
  绝不自动改名；
- 整理后 media_item.file_path 的解释：播放/投递仍以 blob 为准，整理产物登记为「外部发布路径」，
  不作为唯一字节来源（防外部删除造成死链）。

## 验收证据

实现落点（`M2-T09`）：

- 引擎 `crates/orig-tg/src/organize.rs`（新增）：
  - 模板引擎：中英别名（`{剧名}`/`{series}`、`{季}`/`{season}`、`{集}`/`{episode}`、`{集名}`/
    `{title}`、`{来源}`/`{source}`、`{日期}`/`{date}`、`{扩展名}`/`{ext}`），
    格式符 `{season:02}`（零填充到**总宽**）；未识别变量渲染为空串（不报错）；
  - 路径安全：逐段清洗 Windows 非法字符、剥尾随 `.`/空格、`..` 折 `_`（防穿越）；
  - `plan()`（只读预览，全表 diff）+ `apply()`（执行，回填 written/failed）；
  - 执行：同卷 `hard_link` → 失败回退 `copy` 并如实记 `note`；目标已就位且同尺寸 ⇒ `skip`（幂等）；
    尺寸不同 ⇒ 找下一个空位 + `conflict: true`，**绝不覆盖**；
  - 产物登记：`media_publish(item_id, path, mode)`，只作记录、**不作为唯一字节来源**。
- 引擎路由：`POST /api/media/organize/preview`（只读）、`POST /api/media/organize/apply`（执行）、
  `GET /api/media/organize/presets`（模板预设）——「一动词一端点」，预览可反复调用。
- 前端：`tauri-shell/src/components/media/OrganizeWizard.tsx`（新增，四步：模板 → 目录 → 预览全表 → 执行），
  入口在文件域批量工具条 `media-organize`（与「打标签 / 加入剧集 / 移除」并列）；
  `api/media.ts` 补 `organizePreview` / `organizeApply` / `listOrganizePresets`；
  i18n 中英各 +19 键。
- `media_item.file_path` **不被整理改动**，播放永远走 blob ⇒ 外部删产物不会造成死链。

夹具（`cargo test -p orig-tg --lib`，全绿）：

- `organize_never_touches_the_blob_or_the_item_path_bug311`：产物已生成、blob 本体仍在、
  `file_path` 仍指 blob、发布路径已登记；**预览不落盘**；
- `organize_is_idempotent_on_rerun_bug311`：重跑 ⇒ 全部 `skip`、`written=0`、目录内仍是 1 个文件；

  第二条 `(2)` + `conflict: true`，两条都落、都不被覆盖；
- `organize_reports_missing_for_items_without_bytes_bug311`：无字节 ⇒ `missing`，
  **绝不**写成空文件。

附带修正的真缺陷（同一提交内）：

1. `recount_blobs` 的「补缺行」无保护 INSERT，在启动对账路径上可能抛 UNIQUE ⇒ 启动失败。
   已加 `ON CONFLICT DO NOTHING`，权威值交由第 ③ 步重算。
2. 模板格式符宽度原用 `trim_start_matches('0')` 取宽，会把 `02` 削成 `2`（宽 1）⇒ 零填充
   永不触发，用户拿到 `S1E3` 而非 `S01E03`，且**不报错**。已改为取 spec 原长。

已知局限（诚实记录）：blob 无扩展名，`{ext}` 按 `kind` 给默认值（video→mp4 / audio→mp3 /
photo→jpg / 其余→bin）。源若是 mkv/opus 等非默认容器，扩展名与真实容器不一致 —— 播放器多按
内容嗅探故不影响播放，但要精确到真容器需在入库时记下原始扩展名（后续里程碑补列）。
