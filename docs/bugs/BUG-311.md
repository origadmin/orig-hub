# BUG-311: 缺少批量整理命名能力（mp3tag 式模板命名/归位）——库内改名不动物理文件后，用户无可读命名的对外交付手段

- 状态: open
- 发现日期: 2026-10-14
- 模块: engine+shell
- 严重程度: low

## 现象

用户需求（2026-10-14 原话）：「剧集修改不涉及实际文件名,但是要支持批量整理命名方式
(类型 mp3 工具的管理命名方式)」。

现状：
- 无任何批量重命名/归位入口；单条改名只写库（见 BUG-310），物理文件保持
  `{msg_id}-{caption_slug}.ext` / `doc-<chat>_<msg>.ext` 等不可读内部名；
- 用户要把剧集交给外部播放器/分享/备份时，文件名不可读、目录不按剧集组织，只能手工在资源管理器整理。

## 根因

功能缺失（非行为缺陷）：系统有归仓（cache.rs house_into）但没有「按用户模板重新组织物理文件」的
受管通道；没有模板引擎、预览 diff、冲突处理与幂等机制。

## 复现

文件域多选若干视频 → 无「批量整理/重命名」操作。

## 修复

按 **D24=A**（2026-10-14）：

- 模板变量（mp3tag 风格）：剧名、季、集、集名、来源、日期、扩展名等，示例
  `{剧名}/S{season:02}E{episode:02} - {episode_title}.{ext}`；
- 执行前**预览 diff 全表**（旧路径→新路径、冲突、越界字符处理）；幂等可重跑；
  同名冲突加序号不静默覆盖；
- 与 hash blob 模型（BUG-309）的关系：内部存储为内容寻址 blob，整理产物为**用户指定目录下的
  硬链接（同卷）/副本（跨卷）**，blob 本体与引用计数不动；整理是显式批量用户动作，
  绝不自动改名；
- 整理后 media_item.file_path 的解释：播放/投递仍以 blob 为准，整理产物登记为「外部发布路径」，
  不作为唯一字节来源（防外部删除造成死链）。
