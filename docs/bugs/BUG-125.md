# BUG-125：媒体库面板的「占用」是元数据之和，不是磁盘占用

- 状态: open
- 严重程度: mid
- 模块: engine+shell
- 发现日期: 2026-09-22

## 现象

媒体库面板展示的「占用」（`LibraryStats.totalSize`）**不是磁盘实际占用**，
而是 `media_item.size` 这一**元数据列**的求和。

## 取证

```rust
// download-engine/crates/orig-tg/src/media.rs:2453-2478
pub async fn library_stats(&self) -> libsql::Result<LibraryStats> {
    Ok(LibraryStats {
        ...
        total_size: self
            .count_one("SELECT COALESCE(SUM(size), 0) FROM media_item", ())
            .await?,
    })
}
```

即 `total_size = SUM(media_item.size)` —— **一次 DB 聚合，全程不碰文件系统**。

## 为什么这是缺陷（离线优先下尤其）

「占用」是用户做**存储决策**的依据（"还能不能存下"、"该清哪些"），
而这个数字在三种情况下都会**与磁盘事实脱节**：

1. **未落盘的条目照样计入**：`size` 来自 TG 元数据，字节还在 Telegram 上，
   但面板把它算进"我的占用"（BUG-115/116 的同类问题在统计口径上的翻版）。
2. **`size` 为 NULL 的条目计 0**：4 条 NULL `file_path` 的 photo 如果 `size` 也缺，
   就等于「占了空间却显示 0」。
3. **清理字节后数字不变**：`SUM(size)` 只在**删条目**时变化；
   若只清了字节而条目仍在（`byte_state=absent`），面板仍显示原占用 ——
   用户会认为"清了个寂寞"。

> 与 BUG-109 的教训同构：**数字必须反映事实**。
> 那里是"清缓存无论成败都报 removed"，这里是"占用不反映磁盘"。

## 修复方向

区分两个口径，并在 UI 上**标注清楚**：

| 口径 | 含义 | 来源 |
|---|---|---|
| **元数据体积** | 内容在源头的大小之和 | `SUM(media_item.size)`（现状，可保留） |
| **磁盘占用** | 本机实际占用的字节 | 必须来自**落盘路径累计**或**实际 stat**，不能用元数据近似 |

- 落盘时记录实际写入字节（落盘路径本来就知道写了多少），累计成磁盘占用；
- 未落盘 / `absent` 的条目**不计入磁盘占用**，但可以在旁边单列「未落盘：N 项」；
- 若暂时只做一个数字，**必须选"磁盘占用"**并改掉标签，不要让用户误以为元数据体积就是本地占用。
