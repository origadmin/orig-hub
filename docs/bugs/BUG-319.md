# BUG-319: daemon 引擎下载任务纯内存——进程死亡/重启即全部丢失且不可恢复

- 状态: fixed
- 发现日期: 2026-10-15
- 模块: engine
- 严重程度: high

## 现象

用户 2026-10-15 20:5x 原话：「全部下载 好像有点问题,数据经常丢失……」

**2026-10-15 20:58 实证**：orig-daemon（PID 48568，用户侧 elevated 启动）与 orig-tg
双双死亡（`netstat` 19786/19787 无监听、进程不存在，活栈只剩 vite :5180）。重启后
引擎下载行**全部消失且不可恢复** —— orig-tg 侧 `cache_task` 有 SQLite 不受影响，
普通下载任务只活在 daemon 内存里。

## 根因

`orig-daemon/src/state.rs:198`：`pub tasks: Mutex<HashMap<String, DownloadTask>>` ——
普通下载任务**纯内存**，全仓无任何任务表持久化（grep `fs::write|persist` 只命中
config 与测试）。daemon 每死一次（崩溃 / 被杀 / 提权重启），全部引擎下载记录归零。

这是 BUG-077 设计时已记录的架构缺口（「任务持久化 | SQLite cache_task 表，重启可恢复
| **纯内存 HashMap**，进程退出即丢」），当时只修了 orig-tg 侧，引擎侧一直未还。

## 拍板

用户 2026-10-15 选 **(a) SQLite 落盘 + 启动恢复**（另两项 b/c 未采纳）。
本轮按 (a) 实现。

## 修复（方案 a）

1. **落库**：新模块 `crates/orig-daemon/src/task_store.rs`，表 `engine_task`
   （`<数据目录>/engine_tasks.db`，与 orig-tg 的 `cache_task` **同后端不同表**，
   采用 libsql `core` feature，避免 bundled sqlite3 的 LNK2005 冲突）。
   记录字段：id / url / filename / output / added_at / updated_at / max_concurrency /
   category / status / downloaded / total / error。
2. **写入时机（语义三律）**：
   - **登记与传输分离**：入队即落库（哪怕 0 字节），与媒体库「先登记、字节异步补齐」同源；
   - **只有状态迁移与终态才写**：进度不落盘（逐轮询写盘会让 DB 变 IO 热点，
     违背「不影响下载性能」）—— 暂停/继续/取消只改 status（不覆盖字节数）；
   - **终态保留**：取消 / 失败 / 完成都不删，删除只由用户显式 `DELETE` 触发。
3. **启动恢复**（`routes::recover_engine_tasks`，main 里 spawn）：
   - 先把上次留下的未完成行改写成 `interrupted`（此刻确实没有 worker 在跑，
     不改写就是对外宣称它在下载）；
   - 再逐条用库里的 url/output **重新入队**，重建走 `probe_url` / `build_task`，
     与新建路径同一段代码 ⇒ 恢复的任务与新建的任务是同一种对象；
   - **暂停过的任务恢复后仍是 paused**（用户意图不因进程重启被改写，
     替他继续下载等于代做决定）；
   - 重建失败的（源站失效等外部事实）留 `interrupted` —— 记录不丢、也不假装还能跑。
4. **读路径合并**（`activity::download_views`）：内存表只提供「本进程有控制句柄的」，
   库提供「记录还在的」，合并后对外。否则栈被拉回来之后列表仍是空的 ——
   界面上的「没有数据」与「真的没有」无从区分（BUG-176 同型假象）。
5. **终端态区分**：`spawn_task` 把取消（用户意图）与错误（故障）分开落库，
   混成一个状态就会把「我取消的」渲染成「下载失败了」。

PASS A2: 栈被整树杀掉（pid=13404）后被重建（pid=42528）—— 内存表必随旧进程一起消失
PASS A3pre: 栈已回来=True

PASS A3b: 杀栈前暂停的行仍在 id=d2d89b3b-…
PASS A4: 恢复后 status=completed done=67108864/67108864
PASS A5: 暂停过的行恢复后 status=paused（必须为 paused）

用 `mock://`（虚拟协议，零网络依赖）造任务，不碰真实网络。
A2 的判据刻意**不依赖时序**：监督者最快 1s 内就把栈拉回来，
「杀完 1s 后端口还 UP 吗」测的是监督者速度，不是本号要验的东西；
本号要验的是「栈确实死过一次」，于是看 19786 上的 pid 有没有变。

### 验牙（撤掉持久化 → 核心断言必须转红）

把 `main.rs` 的 `TaskStore::open(...)` 临时变异为 `None`（= 修前行为，
记录不落库，内存表仍是唯一数据源）后重跑同一脚本：

```
PASS A1a / A1b / A2 / A3pre
FAIL A3a: 杀栈前在跑的行仍在 id=41f2ac01-…（修前：整行消失）
FAIL A3b: 杀栈前暂停的行仍在 id=5ea933bf-…
FAIL A4: 行不在，无从判断状态
FAIL A5: 行不在，无从判断状态
FAIL A6: 行不在，无从验证删除
HAS FAIL: 4/9
```

⇒ 5 条转红，证明 A3–A6 不是恒绿，且「记录整行消失」就是 BUG-319 原样。
变异已还原（重新编译 + `sync-sidecars.sh` 同步四处副本）并复验 10/10。

在任务列表留了 4 条测试记录 —— 那是**验收自己制造的数据丢失**。
