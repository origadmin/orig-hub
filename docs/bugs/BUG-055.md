# BUG-055 Tauri 壳消费的 sidecar 副本从不随 `cargo build` 更新 → 用户启动的 app 跑旧引擎

- **严重级**: major / delivery（「验过了但用户那儿没变」）
- **状态**: fixed（2026-09-18 已处置；2026-09-19 由 BUG-061 补全为结构性修复）
- **发现日期**: 2026-09-18
- **报告轮次**: 2026-09-18（第八轮收尾核对产物时发现，非用户直接提出）
- **模块**: build / `tauri-shell/src-tauri/tauri.conf.json` + `download-engine/target/release/`

## 现象

源码改了、单测全绿、真实实例 e2e 全绿、dist 也重建了 —— 但用户启动 app 后看不到任何改动。

## 根因

`tauri.conf.json`：

```json
"externalBin": [
  "../../download-engine/target/release/orig-daemon",
  "../../download-engine/target/release/orig-tg"
]
```

`externalBin` 给的是**不含目标三元组**的路径，Tauri 在运行/打包时按当前平台**追加三元组**，
实际消费的是：

```
download-engine/target/release/orig-tg-x86_64-pc-windows-msvc.exe
download-engine/target/release/orig-daemon-x86_64-pc-windows-msvc.exe
```

而 `cargo build --release` 只会写出 **`orig-tg.exe` / `orig-daemon.exe`** ——
**两个名字是不同的文件，cargo 不会去碰带三元组的那份**。实测：

| 文件 | mtime | 大小 | md5 |
|---|---|---|---|
| `orig-tg.exe`（新构建） | Sep 19 04:03 | 11,952,640 | `3e618872…` |
| `orig-tg-x86_64-pc-windows-msvc.exe` | **Sep 16 21:30** | 9,400,832 | `3df01bf0…` |
| `orig-daemon.exe`（新构建） | Sep 17 07:01 | 7,203,840 | `aa69b8a8…` |
| `orig-daemon-x86_64-pc-windows-msvc.exe` | **Aug 27 00:03** | 5,358,080 | 旧 |

即 sidecar 副本比源码**旧 4 天 / 体积小 2.5MB** —— 第 5～8 轮的引擎修复（剧集归档容器化、
BUG-052 触发器 DROP、BUG-054 的 `media_item.description` 列与回填迁移等）**全部不在用户跑的进程里**。

**为什么长期没被发现**：验收脚本（`restart_tg.py`、`probe_*.py`、`shot_*.cjs`）都是直接拉起
`target/release/orig-tg.exe`，读的**始终是新二进制**；于是「开发者自证全绿」与「用户实际体感」
被两份不同的文件隔开，表现为反复的「我这边是好的」。

## 处置

```bash
cd download-engine/target/release
cp -f orig-tg.exe     orig-tg-x86_64-pc-windows-msvc.exe
cp -f orig-daemon.exe orig-daemon-x86_64-pc-windows-msvc.exe
md5sum orig-tg*.exe orig-daemon*.exe   # 两个名字必须一致
```

已同步，md5 对齐：`orig-tg` = `3e618872381e30c9b7f19c9574eb6f28`、
`orig-daemon` = `aa69b8a83f38007c10c3dd32b7fb1d22`。

## 结构性根治（2026-09-19 由 BUG-061 补全）

当时判断「让 build 顺手同步」属于构建编排变更、不在范围内，只落了人工动作。
**该判断不成立**：人工动作没有把错误状态变得不可表达，同一问题随后在**另两处副本**上复现
（`tauri-shell/src-tauri/target/{debug,release}/orig-tg.exe` 一直冻结在 Sep 16 21:30，
而这两份才是壳实际 spawn 的）—— 见 BUG-061。

现行根治方式：

- `scripts/sync-sidecars.sh` 一次同步全部副本，并**在产物比源码旧时 FAIL**；
- `tauri.conf.json` 的 `beforeDevCommand` / `beforeBuildCommand` 前置 `npm run sidecars`，
  无论从哪条路启动壳都会先同步。

## 验收证据

- 四处 `orig-tg` 副本 md5 逐一对齐为 `3e618872381e30c9b7f19c9574eb6f28`
  （`download-engine/target/release/orig-tg.exe`、
  同目录 `-x86_64-pc-windows-msvc.exe`、
  `tauri-shell/src-tauri/target/debug/orig-tg.exe`、
  `tauri-shell/src-tauri/target/release/orig-tg.exe`）；
- `sh scripts/sync-sidecars.sh --check` 通过（含陈旧注入反例：`touch` 任一 `.rs` 后必须 FAIL）；
- 复现与处置细节见 BUG-061。

## 教训

1. **「验收读的对象」必须与「用户读的对象」是同一个文件**。本条与 BUG-052「单测都跑全新库 ⇒
   升级库路径零覆盖」是同一类错误的两种形态：**验证路径与真实路径不重合**，于是绿灯不携带信息。
   凡出现「我这边好的」，第一个要问的是「你和我读的是同一份产物吗」。
2. **产物的名字是契约的一部分**。三元组后缀不是装饰 —— 它是 Tauri 的查找键，而 cargo 不认识它。
   构建系统里凡是「一个产物有两个名字」，就要问「谁负责让它们同步」。
3. 交付清单里 **`.exe` 指纹（mtime + size + md5）** 应当与测试结果一起给出，否则无法排除
   「改的东西没进产物」。
