# BUG-116：入库与落盘行为不一致 —— 4 条图片入库后没有本地字节

- 状态: open
- 严重程度: mid
- 模块: engine
- 发现日期: 2026-09-22

## 现象

同样的「加入媒体库」操作，有的内容有本地文件、有的没有。

## 取证

```
GET /api/media/items?limit=200
→ 115 条 = 85 video + 30 photo
→ 30 条 photo：26 条有 file_path，4 条为 NULL
→ 85 条 video：全部有 file_path
```

## 根因

两条写入路径对「是否落盘」的实现不同：

- worker 缓存成功路径：落盘 + 入库；
- 手动入库路径：**只入库、不落盘**（见 BUG-115）。

`media_item` 缺「字节状态」字段，于是「已入库」这个状态**无法区分**「字节在本地」还是
「字节还在 Telegram」，行为不可预期。

## 影响

- 离线优先下这类记录**就是脏数据**：看起来在库里，实际一个字节都没有。
- 播放时 `media_item_raw` 会现场代理 TG 缩略图（BUG-117），失败则 404。

## 修复方向（分两步，顺序不可颠倒）

1. **先堵住增量**：所有写入路径加校验，**禁止产生「已入库却无字节」的记录**。
   补下载失败须**保留 `absent` 并给重试入口，不得静默成功**（静默成功会重造本条）。
2. **再补存量**：把 4 条 NULL `file_path` 的 photo 补落盘；失败则显式标 `absent`
   并保留重试入口。

对应评审文档改造路线的 **S0.5**。

## 关联

- BUG-115（同一根因的上游）、BUG-117（NULL 路径的下游后果）。
- **BUG-098（`asset_state`）是本条的归口方案** —— 那 4 条 NULL `file_path` 正是
  `asset_state` 要表达的「`pending` / `missing`」态。实施时以 BUG-098 为归口，
  不要另造状态字段；但注意 **`photo` 的默认态须是 `ready` 而非 `remote`**
  （理由与冲突说明见 BUG-115 的「与 BUG-098 的关系」节）。
