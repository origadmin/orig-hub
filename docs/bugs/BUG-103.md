# BUG-103: 合并剧集丢失分集备用源，且孤儿行永久阻塞该条目再挂载

- 状态: in_progress

> 进度：**止血已实施并通过独立验证**（2026-09-21）；**正修待拍板**（见「待拍板」）。
> 本条在正修落地前不标 `fixed` —— 备用源仍会随合并静默消失，缺陷未完全消除。
- 发现日期: 2026-09-21
- 模块: engine
- 严重程度: high

> 立项方式：项目所有者追问「合并剧集时第 1 集不该是一条数据」（同槽多来源语义）时发现，
> 经内存库实测复现。与 BUG-098 同源（两域模型），但本条是**已可复现的具体缺陷**，非评估项。

## 现象

对「启用了备用源」的剧集执行合并，**双重后果**：

1. **备用源静默消失**：源剧集分集挂的备用来源（`media_episode_source`）不会随合并进入目标剧集，
   内容仍在 `media_item` 里，但在剧集视角下**主位、备用位都不在** —— 用户看到「那条内容没了」。
2. **该条目被永久锁死**：源分集行被删后，`media_episode_source` 里对应行变成 `episode_id` 悬空的**孤儿行**；
   由于该表 `item_id` 是**全表 UNIQUE**，孤儿行占着这个 item_id，之后把它挂到**任何**分集都会报错：

   ```
   SQLite failure: `UNIQUE constraint failed: media_episode_source.item_id`
   ```

   用户侧表现是「点了挂不上 + 弹报错」，**不是静默无反应**。且无外键级联，孤儿行**跨进程重启仍残留**，
   阻塞是永久性的，用户无法自愈。

## 根因

`merge_series`（`download-engine/crates/orig-tg/src/media.rs:1386-1545`）整个事务**从不触碰
`media_episode_source`**——全文件该表仅出现在 367（建表）、409（迁移清理）、449/485/486/493
（video-only 触发器）、1261（查询）、1709/1740（`attach`/`switch`），**1386–1545 区间零命中**。于是：

- `:1395-1400` 读源分集只取 `e.item_id`（**主条目**），备用源没被读出来；
- `:1511` `DELETE FROM media_episode WHERE series_id = source_id` 直接删源分集行，
  挂在那些 `episode_id` 上的备用源行随之悬空，且无任何清理；
- `attach_episode_source`（`:1709`）写的是
  `ON CONFLICT(episode_id, item_id) DO NOTHING`——该子句**只覆盖组合约束**，
  `item_id` 的 UNIQUE 冲突不会被它拦下，SQLite/libsql 直接抛错（错误码 2067
  = `SQLITE_CONSTRAINT_UNIQUE`），而非走 `DO NOTHING`。

**更深一层（模型分叉，属 BUG-098 范畴）**：仓内存在两套互不兼容的「多来源」语义——

- **BUG-039 备用源**：同一集槽位可有主条目 + N 个备用来源，带主次（`switch_episode_source` `:1719`）；
- **BUG-037 合并**：不同来源一律**续编成新集号**（`:1463-1464` 从目标各季 `MAX(episode_no)` 递增），
  原始集号只作快照存进 `origin_episode_no`（`:1479`）。

合并路径里根本没有「同槽归并」这个概念，因此也没有理由去处理备用源——这是本条缺陷的设计层根因。
其可见副作用是：同一内容的不同版本（不同频道 / 不同码率压片）合并后**变成两集**，连播会重复播放。

## 影响

- 触发条件具体但后果重：**只要用过备用源 + 执行过合并** 即触发。
- 数据完整性：静默丢失（后果 1，无提示）+ 永久卡死（后果 2，报错但用户无法自愈）。
- 不崩溃、不损坏库文件，故未定 P0；但「静默丢 + 永久锁死 + 报错直接暴露给用户」三项叠加，定 **high**。
- 此前无守护：已有用例 `episode_sources_attach_switch_detach` 只覆盖挂载/切换/摘除，**未覆盖 merge 路径**。

## 修法

两层，止血与正修分离：

1. **止血（必做）—— 已实施并验证，见「止血实施与验证」节**：`merge_series` 在 `:1511` 删源分集**之前**，先
   `DELETE FROM media_episode_source WHERE episode_id IN (SELECT id FROM media_episode WHERE series_id = ?1)`
   —— 不再留孤儿行，`item_id` 随之释放。注意必须在同一 `BEGIN IMMEDIATE` 事务内。
2. **正修（建议同批）**：合并时把源分集的备用源**搬运**到目标对应分集上
   （把 `:1395-1400` 的源分集读取扩展到带出备用源，INSERT 新分集后按其新 `episode_id` 重挂）。
   搬运时注意 `item_id` 全表 UNIQUE：沿用「同一内容只属一集」的不变量，冲突则记入 `report.skipped`
   如实回报，**不静默丢弃**。
3. **模型层（待拍板，见下）**：合并遇到「两边都有第 1 集」时，究竟应**同槽归并为多来源（主+备用）**
   还是维持**续编成两集**。这决定正修是「搬运」还是「归并」，需所有者裁定。

## 待拍板

**同一集的两个来源（不同频道 / 不同压片版本）合并后，应是一集两来源，还是两集？**

- **A（同槽归并）**：合并到同一 `(season, episode_no)` 槽位，一个主、一个备用，契合 BUG-039 已有能力，
  也符合所有者「第 1 集不应该是一条数据」的直觉。代价：合并需新增「是否同一集」的判定
  （靠什么认？集号相同？标题/时长相近？），且要处理「两来源都是主」时谁当主。
- **B（维持续编）**：沿用 BUG-037 现状，不同来源一律编成不同集。代价：同一内容变成两集，连播重复；
  备用源机制在合并场景永远用不上（两套模型长期分叉）。

不拍板则只能先做止血（第 1 项），正修（第 2 项）无法定型。

## 止血实施与验证（2026-09-21）

**改动**（`download-engine/crates/orig-tg/src/media.rs`）：

- `:1508-1523` 新增注释（三要素：为什么必须删 / 本轮只清不搬 / 引用 BUG-103）；
- `:1524-1530` 新增清理语句，位于 `:1533-1538` 删源分集**之前**、`:1423` `BEGIN IMMEDIATE` 事务内：
  ```sql
  DELETE FROM media_episode_source
   WHERE episode_id IN (SELECT id FROM media_episode WHERE series_id = ?1)
  ```
- `:1532` 原注释「删源（分集已搬走、标签已并走）」补为「…分集挂的备用源行已清掉」；
- 测试 `merge_series_loses_sources_and_orphans_them` → 改名
  `merge_series_clears_source_rows_and_frees_item_id`（`:4049`），改为断言修复后行为。
- `git diff` 仅限上述范围；`attach_episode_source` / `switch_episode_source` / 建表 DDL / 集号续编
  （`:1463-1464`）**零改动**。

**实测（修复后）**：

| 观察项 | 实测值 |
|---|---|
| 悬空备用源行（`LEFT JOIN … WHERE e.id IS NULL`） | **0** |
| `item_id=B` 的备用源行数 | **0**（名额已释放） |
| `attach_episode_source(目标分集, B)` | **`Ok(true)`**（止血前 `Err UNIQUE`） |
| B 是否真在目标分集备用源里 | 是（非 `Ok(true)` 空操作） |
| 跨进程重启后悬空行 | **0** |
| `cargo test -p orig-tg media::tests` | **27 passed / 0 failed** |

**反向证伪（证明测试真在守护，非假绿）**：临时注释掉 `:1524-1530` 后重跑 → **FAILED**

```
panicked at media.rs:4105: assertion `left == right` failed:
合并后不得残留指向已删分集的孤儿备用源行
  left: 1  right: 0
```

还原后恢复 27 passed / 0 failed，交付态为修复态。

**边界抽查（独立验证者额外造的场景，实现者未测）**：目标剧集 T 自带备用源 + 源剧集 S 带备用源，
执行合并 T←S 后：目标分集备用源 = `[2]`（**目标自带项原样保留，未被误删**）、悬空行 = 0、
源备用源重新 `attach` = `Ok(true)`。该项排除了「`?1` 误绑成 `target_id` 会删掉目标剧集备用源」
这一最危险错法。

**遗留（本轮未做）**：见「待拍板」——备用源仍不随合并搬入目标剧集，从剧集视角看内容依然消失。

## 备注

- 验证方法学坑（记录以免重犯）：写「跨重启残留」类断言时，临时库辅助函数若每次调用都
  `std::fs::remove_file` 删库，则第二次 `Store::open` 打开的是**全新空库**，断言会假失败。
  必须复用同一路径才能证明「跨重启残留」。本条「永久阻塞」结论依赖该修正（由验证者自查发现并纠正）。
- 本条与 BUG-098 的关系：098 是评估档（域边界与状态机），本条是其中「多来源」语义分叉导致的
  **首个可复现缺陷**。后续如按 A 方案改造合并语义，应回写 098 的模型章节。
