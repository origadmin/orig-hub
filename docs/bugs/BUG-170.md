# BUG-170: 入库过渡窗「缓存→不见了→完成→出现了」—— 条目登记推迟（P1 已修）+ 前端三源状态拼接（本阶段修）

- 状态: fixed
- 发现日期: 2026-09-25
- 模块: engine+shell
- 严重程度: mid
- 档位: standard

修复由两个阶段完成 —— byte-ownership P1（登记前移，commit `d27baea`）与 P4（单源派生，本 commit）。

## 现象

用户原话：

> 「缓存→不见了→完成→出现了」

一次入库任务全程，条目在界面上的可见性/状态经历「消失窗口」：任务进行中条目
可见（或显示缓存中），某段时间突然既不在「缓存中」也不在「已完成」，任务完成后
条目才又冒出来。灯箱/列表闪烁，用户以为内容丢了。

## 根因（两段，分别由两个阶段修掉）

### 1. 登记推迟（engine 侧，byte-ownership P1 已修）

修复前 `run_one_cache_task` 把 `media_item` 登记放在**任务终态**一次性
`append_episodes_ranged`：任务开始 → 任务结束之间，媒体库里**根本没有这一条**。
条目的可见性从 T1（字节落盘）才开始，T0～T1 之间是结构性空白。
P1（设计 I1「事实先登记」）把登记前移到逐消息取字节之前：T0 建立
`media_item` 行（`file_path=NULL` 待回填）+ 剧集槽位，条目自任务开始即持续可见。

### 2. 三源拼接（shell 侧，本阶段修）

登记前移后条目在库列表的结构连续性已由后端保证，但**前端状态拼接**仍在制造闪烁：
条目徽标由三个源各按各的节奏更新——

| 源 | 节奏 | 驱动 |
|---|---|---|
| 任务轮询 `/api/tg/cache/tasks` | 5s 固定节拍 | 「缓存中」转圈 |
| 字节快照 `/api/tg/downloaded/:chat` | feed 加载 + 任务终态各刷一次 | 「已缓存 ▶」 |
| feed 消息行的 DB `downloaded` 标志 | 页面加载时 | 旧口径兜底 |

任务终态到快照刷新之间存在**时间差**：轮询先说「任务结束了」（`activeTask` 变
null，「缓存中」消失），快照还没回来（「已缓存 ▶」未出现），此刻三个源一致地
「都不认识这条」——旧渲染点的 `Boolean(m.downloaded || downloadedPath)` 判出
false，呈现落入空洞。**这就是修复前必现消失窗口的机理**：只要终态事件与快照
到达之间隔了一个网络往返（本机也有几十～几百 ms），窗口就存在；mock 实例
（每条 2.4s 写盘）下以 200ms 采样可直接捕捉到「状态序列出现倒退/空洞」。

## 修法（byte-ownership P4：状态单源）

- 新增 `tauri-shell/src/lib/entryState.ts`：**唯一**派生函数
  `deriveEntryState({ bytesPresence, taskStatus?, downloadedFlag?, kind?, source?, prev?, factPending? })`，
  决策表见模块头注释。要点：
  - tg 图片即时点亮（BUG-049 raw 代理语义不变）；
  - 字节真值 `present` 是唯一「能播」判据（BUG-132）；
  - **过渡规则：持有旧态直到单源新态到来**——任务终态事件本身不是字节事实，
    `factPending` 窗口内禁止跨源推 intermediate 态，等快照源开口；
  - 失败 = 条目在 + 流水线 failed；缺字节 = 禁播 + 「重试缓存」（复用 bytesPresence）。
- 消费点全部改走它：TgPanel `MessageBubble` / `AlbumBubble`（组内已缓存计数）/
  `VideoBlock` 徽标与按钮、`CacheManagerDialog` 任务行状态徽标。
  删除了 `downloading` Set（第二套「缓存中」判据）与 `STATUS_KEY` 查表。
