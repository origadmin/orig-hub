# BUG-418: 缓存任务重跑不幂等——重跑后多出重复条目与分集（`cache_task_rerun_is_idempotent` 红灯）

- 状态: fixed
- 发现日期: 2026-10-23
- 模块: engine
- 严重程度: mid

## 现象

`cargo test -p orig-tg --lib cache_task_rerun_is_idempotent` 稳定 FAIL（非偶发）：

```
assertion `left == right` failed: 重跑后的库状态必须与首次运行完全一致
  left:  [(1,..,"424242:1",..), (2,..,"424242:3",..)]
  right: [(1,..,"424242:1",..), (2,..,"424242:3",..),
          (3,..,"424242:2",..), (4,..,"424242:4",..)]
```

首次运行产出 2 条分集；**同一任务重跑**后又多出 2 条（ref `424242:2` / `424242:4` 各自
成为新条目 + 新分集）。即「同 ref 复用 + append 跳过」这条幂等链在某个分支上失效。

## 影响

重跑一次缓存任务，剧集里就多一份重复内容 —— 与 BUG-126「删了又回来」同族的可见症状：
用户点「重试 / 补缺」后集数变多、连播重复。

## 复现

```sh
cd download-engine
cargo test -p orig-tg --lib cache_task_rerun_is_idempotent
```

## 根因

**字节回填无条件用「扩展名推出来的 kind」覆盖权威 kind**，把照片条目偷改成 `video`，重跑时
被当成新分集追加。链路三段，逐段实测坐实：

1. **权威 kind 来自 TG 元数据**：`register_media_item_t0`（routes.rs:2306-2387）按
   `meta_kind(media_type, mime_type)` 判定 ⇒ 照片 = `photo`；首次运行的 `register_slot`
   （routes.rs:2691）据此把 photos 挂成分集图片而不是分集 —— 这正是首跑快照正确的原因。
2. **落盘时被翻成 video**：`backfill_item_bytes`（media.rs:2559）原语句
   `kind = COALESCE(?3, kind)` **无条件写**入按扩展名推出来的 kind。而扩展名**不是**权威
   事实（BUG-122：27.6% MPEG-TS 被命名成 `.mp4`；本仓缓存夹具 routes.rs:8696 一律落
   `fixture-{chat}-{msg}.mp4`，照片也一样）⇒ `classify_ext("mp4") = "video"` ⇒
   照片条目 kind 静默变成 `video`。同一缺陷存在于 `backfill_item_bytes_with_blob`
   （media.rs:2594，`kind = COALESCE(?2, kind)`）。
3. **重跑据此落成新分集**：重跑走「已缓存」分支（routes.rs:3073-3086），
   `register_item` 的 kind 由 `item_kinds()` **读库**得到 ⇒ 此刻已是 `video` ⇒
   `register_slot` 的 `kind == "photo"` 分支不再命中，落入 `append_slot` ⇒
   photo 变成第 3、4 集，幂等破裂。

`strengthen_registered_item`（routes.rs:2452-2455）早就写明同一条不变量 —— kind 只做
`file` → 真 kind 的**占位升级** —— 但字节回填这条写入路径没遵守它。

## 修复

让字节回填遵守既有的「**占位升级**」不变量 —— kind 只在**当前仍是占位 `file`** 时才用扩展名补强，
绝不覆盖已明确的权威 kind（与 `strengthen_registered_item` 同一把尺子）。两处写入路径一并改：

- `Store::backfill_item_bytes`（media.rs:2559）
- `Store::backfill_item_bytes_with_blob`（media.rs:2594）

```sql
UPDATE media_item SET file_path = ?2,
       kind = CASE WHEN COALESCE(kind, 'file') = 'file'
                   THEN COALESCE(?3, kind) ELSE kind END
WHERE id = ?1
```

`file` 仍是「元数据没到」的占位 ⇒ 补强能力完整保留（`file` → `video`/`photo`/`audio` 照旧发生）；
而 `photo` 不再会被一个 `.mp4` 后缀改写事实。这是「让错误状态不可表达」而非给每处加判断：
写路径本身不再具备用弱事实覆写强事实的能力。

## 验收证据

**状态 `fixed`（2026-10-26，提交 `a291048`）。**

1. **跨机器可核引用**：提交 `a291048`「fix(engine): keep backfilled kind upgrade-only to
   restore rerun idempotency (BUG-418)」——仅改
   `download-engine/crates/orig-tg/src/media.rs`（`backfill_item_bytes` +
   `backfill_item_bytes_with_blob` 两条写入路径）。
2. **红灯 → 绿灯（判据就是这个用例）**
   `cargo test -p orig-tg --lib cache_task_rerun_is_idempotent`
   修复前：`FAILED`（`crates/orig-tg/src/routes.rs:9992`，left=2 集 / right=4 集，
   多出 `(3,..,"424242:2",..)`、`(4,..,"424242:4",..)` 两条 `video` 分集）；
   修复后：`ok`（1 passed，0 failed）。
3. **全回归**
   `cargo test -p orig-tg --lib` ⇒ **340 passed / 1 failed**，唯一的红灯是
   `cache::tests::priority_endpoint_rejects_malformed_requests_bug277`（**与本档无关**）。
4. **该红灯为既有缺陷，非本次改动引入 —— A/B 实证**
   把 `media.rs` 还原到 HEAD 版本（0 处本次改动）后单独跑 `_bug277`：**同样 FAILED**，
   panic 位置与消息完全一致（`cache.rs:2549`）；随后还原本次修复（`grep -c "COALESCE(kind, 'file')" = 2`）。
5. **无副作用**：工作树无残留（`git status` 仅 `media.rs` 一处 `M`，A/B 用的临时备份文件已删除）。
