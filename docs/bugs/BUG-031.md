# BUG-031：已缓存播放仍卡顿 + 组消息缓存不成剧

- **状态**：fixed
- **日期**：2026-09-18
- **模块**：engine（投递/Range/成剧）+ shell（入口裁剪）

## 现象

BUG-028 修完 TG 在线拉流后，用户复测「已缓存」条目仍报三条：

1. 播放还是卡顿，且 DevTools 里出现**大量 `raw` 请求**；
2. 播放器**倍速没有放出来**；「下载」这个功能不需要；
3. 在频道里点**整组消息缓存**，媒体库里没有对应剧集——缓存只是把文件堆进来，没有「剧集思维」。

## 根因

三层叠加，且第一层是「看起来好了」的假象来源：

### 1. `/api/media/items/:id/raw` 的 HTTP 契约有三处缺陷

| 缺陷 | 后果 |
|---|---|
| 无 `Range` 时**只回前 8 MiB 却标 `200 OK`** | 浏览器据此认定「整文件 = 8 MiB」，duration/seek/缓冲全错，随后疯狂重发 Range |
| `Content-Type` 硬编码 `video/mp4` | `.mov` 走错解码路径；图片条目也可能被塞进 `<img>` 失败 |
| 无 `ETag` / `Last-Modified` | Chromium 媒体缓存**无法复用已取字节**，每次都要重下 |

### 2. 两条投递路径各写一套实现（真正的放大器）

| 路径 | 用途 | 修复前 |
|---|---|---|
| `/api/media/items/:id/raw` | 媒体库条目 | 见上表三缺陷 |
| `/api/tg/local/:chat/:msg` | **TG 已缓存（用户实际播的那条）** | 只有 512 KiB 分块、无 validator、MIME 取 DB 值 |

用户播的就是 TG 已缓存条目 —— 只修媒体库那条，现象自然「还是卡」。

### 3. 组消息缓存没有成剧环节

整组缓存只逐条 `upsert_media_item`，没人把「同一个相册/分组」这件事记下来，
媒体库只能看到散条目，剧集数为 0。

### 4. 前端入口与默认落点

「下载」在媒体库已接管后无使用价值；默认视图落在空的「下载中」页。

## 修复

1. **抽单一投递原语** `serve_local_file(path, kind, headers)`，两条路径**必须**收敛到它：
   - 无 Range → `200` + **完整文件**（绝不只给前 N 字节）；
   - `bytes=S-` → `206` + 32 MiB 有界块 + 如实 `Content-Range`；
   - `bytes=S-E` → `206` + 尊重请求（安全阀 64 MiB）；
   - 恒带 `ETag`（`"{size:x}-{mtime:x}"`）+ `Last-Modified` + `Accept-Ranges` + `Cache-Control`；
   - MIME 按**扩展名**判定，未知再由 `kind` 兜底，**不设 `image/jpeg` 之类兜底值**
     （会把 `.mov` 误标成静态图，浏览器走 `<img>` 解码而拒播）。
2. **成剧链路**：`cache_one` 返回入库 id → `run_one_cache_task` 收集 `item_ids` →
   以 `tg:group:{chat}:{first_msg}` 作幂等键复用/新建剧集 → `append_episodes` 追加分集。
   剧集 `kind` 由入组条目实际构成推导（`series`/`album`/`collection`，此前硬编码 video，
   纯图片相册也标成「视频」）；标题带日期（同一频道多组缓存不再同名）。
3. **幂等与一致性**：`append_episodes` 跳过已收录条目；去重粒度对齐
   `UNIQUE(series_id, season, episode_no)` = **剧集 × 季**（同季防重复分集，跨季允许合法编排）；
   删条目/删分集后清理空壳剧集并重排集号（消除 S1E1/S1E3 跳号）。
4. **入口裁剪**（可逆）：`Sidebar` 过滤 `downloads` 导航项；`MainLayout` 默认视图
   `downloading` → `media`。

## 验收

- 投递契约：`probe_media.py` 25/25 —— 两条路径**逐项同断言**（Accept-Ranges / ETag /
  Last-Modified / MIME 非兜底 / open-ended 有界 ≤32 MiB）。
- 用户真实路径端到端：`verify_app_playback.cjs` 全通过 —— `.mov` duration 可解析、
  20s 推进 20.01s（≈墙钟）、起播后**零停顿**、longtask 增量 0、2x 倍速生效。
- 成剧：`run_group_series_verify.sh` 9/9（整组入队 → done → 新建剧集 → 集号 1..3 →
  重复缓存不新建剧集/不重复编集 → 单条缓存不建剧集）。
- 单测：`media::tests::append_episodes_dedups_within_season_only`（同季去重、跨季允许、集号连续）。
- 全量：`bash verify_shots/run_all.sh` → **ALL SUITES PASSED**（日志 `verify_shots/ALL_run_20260918.out`）。

### 关于「大量 raw 请求」的实测结论（不作为缺陷继续追）

新增 `verify_shots/diag_raw_wire.cjs` 走 CDP `Network.*` 出**线上字节账**（含落地区间并集去重）。
禁用缓存后，应用路径 20s：请求 18–28 次（≈1/s，修复前为 88–101 次/25s），
线上 103–115 MiB vs 理论 17.8 MiB ≈ **6x 冗余**，其中 **70% 为白传**（区间重叠）。

对该 6x 做了四组 A/B，**均无杠杆**：

| 组 | 变量 | 请求数 | 冗余 |
|---|---|---|---|
| A | open-ended 直达 EOF | 18 | 6.23x |
| B | 32 MiB 有界块 | 20 | 6.35x |
| C | 8 MiB 有界块 | 28 | 5.80x |
| D | 前端 `preload="metadata"` | 26 | 6.31x |

结论：冗余来自 **Chromium 对「本地快源 + 大文件 + 可拖」的固有投机预读** ——
它并行开 2 个读线程各预取 ~10 MiB 后自行 `ERR_ABORTED`（终态 `net::ERR_ABORTED`，非服务端问题）。
`loadstart=1 / emptied=0` 证明与前端重建元素无关。块大小维持 32 MiB 的理由只有
「响应有界 + 可写入媒体缓存」，与上述数字无关。**后续不要为此再调参**。
