# BUG-077: 缓存是否应与下载功能结合（TG 缓存路径与普通下载路径的关系）

- 状态: fixed
- 发现日期: 2026-09-20
- 模块: engine+shell
- 严重程度: mid

## 现象

用户提出：「关于缓存，是否需要和下载功能结合？能否结合？主要是 TG 的缓存方式不是正常
下载（不清楚区别是什么）。」

核心疑问不是"要改什么"，而是**两条路径到底差在哪、能不能合并**——不清楚差异就没法判断
该不该结合。

## 根因（两条路径的差异，架构师勘察 2026-09-20）

| 维度 | TG 缓存 | 普通下载 |
|---|---|---|
| 数据源/协议 | Telegram MTProto，`iter_download` 拉消息媒体 | HTTP(S) |
| 产物所有权 | **索引**——同时写 `media_item`（`source=tg`, `ref=chat:msg`），条目是主视图 | 只落一个文件，不入库 |
| 可否断点 | 任务级重试（整体重跑 / 续跑缓存文件） | 字节级 Range 续传 |
| 多连接分块 | 无（单流；在线播放走 `parallel_range_stream` K=4，非多连接下载） | 需要（吞吐来源） |
| 任务持久化 | **SQLite `cache_task` 表**，重启可恢复 | **纯内存 HashMap**，进程退出即丢 |
| UI 归属 | 缓存管理面板（仅此处可见） | 导航「全部文件/下载中/已完成」（当前被开关隐藏） |
| 清理语义 | 清字节 ≠ 删条目（`file_path` 置 NULL，见 BUG-080） | 删任务 = 删文件 |
| 失败语义 | 终态可重试（同一 id 复位，BUG-078） | 断点续跑 |

一句话：**普通下载"产出一个文件"，TG 缓存"产出一条索引 + 一份字节"**——
这是两条不同的数据模型，不是同一件事的两种速度。

## 复现

不适用（评估类缺陷）。核对方式：分别跑一次 TG 缓存与一次普通下载，比较落盘目录、
任务表、可断点性、UI 归属。

## 评估结论（架构师 2026-09-20）

**结论：部分能——只统一「视图」，不统一「引擎和存储」。**

| "结合"指什么 | 可行性 | 代价 / 理由 |
|---|---|---|
| 统一任务列表 | 可行 | 低。daemon 侧**只读聚合**两侧任务，不动任何存储 |
| 统一进度 UI | 可行 | 低。统一成 `TaskView{id,kind,name,total,done,speed,status}`，SSE 透传 |
| 统一落盘目录 | **已事实统一** | 零成本（都在生效 `download_dir`），但**清理必须分开** |
| 缓存复用下载引擎 | **不可行** | 引擎 `Source::fetch_block` 要求任意 offset 语义；MTProto 需 chunk 对齐且受 FloodWait / DC 迁移 / 会话态约束。且 orig-tg（`grammers.rs:814`）**已自建 K 路并行分片**，重写收益≈0、风险高 |

**最小方案**：daemon 新增聚合层 `activity.rs`——复用现有 HttpClient 拉
`tg:9877/api/tg/cache/tasks`，与内存 tasks 合并成统一 `TaskView`，新增
`GET /api/activity` + 复用现有 `/api/events` 广播；前端新增一个「传输中」视图消费。
**原则：只读聚合、控制分流**——暂停/删除/重试仍各走 `/api/downloads/:id` 与 `/api/tg/cache/*`。
改动 3 处：`activity.rs`、`routes.rs` 注册、前端视图 + api。**不迁存储、不改清理**。

**风险（强行统一会破坏什么）**：
1. **清理语义**：同一列表里"删除"，在缓存是删副本、在下载是删用户资产，**误删不可逆**；
2. **断点语义**：TG 无真续传，统一 UI 给"暂停/继续"是**假能力**；
3. **产物所有权**：缓存可丢弃、下载不可丢弃，混排后用户无法判断"删了会怎样"；
4. **持久化不对等**（TG 重启有、下载重启无）+ **跨进程耦合**（9877 挂了整列表空白）。

## 修复

已实施（2026-09-21）：**只统一视图，不统一引擎与存储**（评估结论原文未改）。

### 引擎侧（3 处）

1. **新增聚合层** `download-engine/crates/orig-daemon/src/activity.rs`：
   `collect()` 读本进程内存任务表 + HTTP 拉 orig-tg 全量缓存任务 → 统一 `TaskView`；
   `merge()` 是纯函数（不碰网络与状态），便于单测覆盖降级路径。
2. **注册端点** `download-engine/crates/orig-daemon/src/routes.rs`：`GET /api/activity`
   （`?scope=active` 默认 / `?scope=all`）。**不新建 SSE 通道** ——
   复用现有 `/api/events`；该通道只承载下载侧事件，TG 侧随轮询周期一并拉回。
3. **`download-engine/crates/orig-daemon/src/state.rs`**：新增出向 `reqwest::Client`
   （`no_proxy()` + 2s/4s 短超时），并把端口抽成唯一真源 `TG_PORT`

### 前端侧

- `tauri-shell/src/api/activity.ts`：类型 + `fetchActivity()` + `activitySignature()`
  （等值短路用）；**只有 GET**。
- `tauri-shell/src/components/ActivityPanel.tsx`：「传输中」视图，按钮**完全由后端
  `actions` 驱动**（后端不给就画不出来），控制按 `control.side` 分流。
- 接线：`tauri-shell/src/components/Sidebar.tsx`（新增 `activity` 视图项，不带徽标 ——
  侧栏不为此订阅该端点）、`tauri-shell/src/components/ContextBar.tsx`（`TITLE_KEY`）、
  `tauri-shell/src/components/MainLayout.tsx`（渲染 + 内滚动）、
  `tauri-shell/src/i18n/locales/zh-CN.json` / `tauri-shell/src/i18n/locales/en-US.json`
  （各 20 条 `activity.*` + `nav.activity`）。

### 与文档描述的差异（以实际代码为准）

1. **拉取端点不同**：文档写 `tg:9877/api/tg/cache/tasks`，但该端点是**单飞契约**
   （只返回 running → 最老 queued → 最近一条已结束中的**一个**任务）；聚合要的是全量，
   故改拉 `/api/tg/cache/tasks/all`（`{tasks,counts}`，上限 500）。
2. **daemon 侧原本没有 HttpClient**：文档说「复用现有 HttpClient」，实际只有
   `post_proxy_verify` 里现造的一次性 client，故在 `AppState` 新增了一个。
3. **daemon 不代理 `/api/tg/*`**：写操作没有 daemon 侧转发，因此 `TaskView.control`
   给出归属侧，TG 侧由前端直连 9877 的 `/api/cache/tasks/:id/retry`。
4. **TG 侧无速度采样**：`cache_task` 表没有速度字段，`speed` 对 cache 侧给 `null`
   （不是 0 —— 0 会被读成「已停止」）。
5. **TG 侧全量端点读 SQLite**（与 AGENTS.md §5「被轮询的读端点不许碰 DB」有张力）：
   纯内存快照的 `/api/tg/cache/tasks` 只给**单飞一条**，聚合要全量只能走
   `/api/tg/cache/tasks/all`（`list_cache_tasks`，读库）。取舍：本端点由前端 5s 轮询，
   比 TG 面板现状的 1s 单任务轮询更轻；若日后 TG 侧补出「全量内存快照」端点，
   改 `activity.rs::fetch_cache_views()` 里的那一行 URL 即可，其余不动。

## 验收证据

### TaskView 字段定义（最终）

```
TaskView {
  id         "dl:<uuid>" | "tg:<i64>"   全局唯一，仅供视图定位
  kind       "download" | "cache"       来源（存储/引擎仍不统一）
  name       各侧原生名（文件名 / TG itemKey）
  unit       "bytes" | "items"          计量单位（缓存按条目数，混读会失真）
  total/done u64
  speed      f64 | null                 null = 该侧无采样（TG），非运行态下载侧为 0
  progress   f64                        0-100，与 unit 同单位
  status     各侧**原生**状态词         不做跨侧归一化（归一化 = 宣称两侧同构）
  actions    ["pause","resume","cancel","retry"] 的子集 —— 该侧**真实具备**的动词
  control    { side: "daemon"|"tg", native_id }  写操作归属（控制分流）
  updated_at i64
  error      string | null
}
响应 = { tasks: TaskView[], sources: SourceHealth[], generated_at }
SourceHealth = { kind, available, error, count }  // 恒含 download / cache 两条
```

### 实机探活（本机 daemon + 本机真实 orig-tg，非 mock）

以 `PORT=9976` 起一个**本轮编译出**的 `orig-daemon`，对**正在运行的真实 orig-tg
（9877）**取数：

- `GET /api/activity`（默认 active）→
  `sources=[{download,available:true,count:0},{cache,available:true,count:1}]`，
  `tasks=[{id:"tg:63",kind:"cache",name:"m:-1004493170102:5669",unit:"items",total:1,done:0,
  status:"interrupted",actions:["retry"],control:{side:"tg",native_id:"63"}}]` ——
  真实库里 1 条 interrupted + 13 条 done，active 档**只**收 interrupted，符合口径。
- `GET /api/activity?scope=all` → `count=14`（13 done + 1 interrupted 全在）。
- `GET /api/activity?scope=bogus` → 回落 active（`n=1`），不报错。

降级路径（`[tg] enabled = false` 的独立实例，`PORT=9977`）：

- 无下载时：`{"tasks":[],"sources":[...,{"kind":"cache","available":false,
  "error":"tg plugin disabled","count":0}]}` —— **恒 200**，不是 500，也不是空 sources。
- 再 POST 一条真实下载（`http://127.0.0.1:9877/api/tg/cache/tasks/all`）后：
  `sources` 仍是 cache 不可用，而 `tasks` 照常返回该下载任务
  （`kind:"download",unit:"bytes",status:"completed",actions:[],control:{side:"daemon"}`）
  —— 即「9877 挂掉 ≠ 整列表空白」。
- 下载侧动词随状态变化（同一实例）：paused → `["resume","cancel"]`；
  completed → `[]`。cache 侧实测只有 `["retry"]`，**没有** pause/resume。

`connection refused`（进程真挂掉）这一支未做实机复现 —— 需要停掉用户正在运行的
orig-tg，故只由单测覆盖；它与上面 `tg plugin disabled` 走的是同一条
`Err(reason) → merge()` 分支，差别仅在错误字符串。

### 三条铁律的落点（代码级）

| 铁律 | 落点 |
|---|---|
| 只读聚合 | `activity.rs` 全程只读：`st.tasks.lock()` 读 + `st.http.get()` 读，无任何写存储调用；前端 `api/activity.ts` 只有 GET |
| 不清统一删除 | `Action` 枚举只有 `Pause/Resume/Cancel/Retry`，**无删除变体**；`actions_for()` 两侧都不产出删除；前端 `ACTION_LABEL` 亦无删除键，改用 `activity.deleteHint` 告知去各侧原面板删 |
| TG 侧不给假暂停 | `actions_for(Cache, "queued"\|"running") = []`，其余 `=["retry"]`；前端按钮完全由 `task.actions` 渲染 |
