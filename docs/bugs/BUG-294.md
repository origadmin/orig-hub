# BUG-294: 入库任务**没有逐条状态** —— `done` 是计数器而非事实、`interrupted` 不记「哪几条已完成」、重试把 `done` 归零 ⇒ 任务内的「后续 N 个」是未知黑盒，无法管控、无法补档

- 状态: open
- 发现日期: 2026-10-13
- 模块: engine+shell
- 严重程度: high
- 类型: epic
- 延期至: 2026-12-15（理由：设计级工程，需独立里程碑；详见关联设计文档）

> 来源：用户 2026-10-13 原话：「入库流水线 的下载中任务找不到，感觉还是要置顶。内容太多了。
> 还有很多命名是 10 个内容入了 2 个说完成了，后续 8 个丢失状态呢？**完全是未知黑盒，无法管控了解，
> 补档**，这是严重的设计漏洞。」—— 本条登记其中**「后续 N 个丢失状态」**这一半；
> 「找不到下载中」= `BUG-295`，「10 个说完成」= `BUG-296`。三条同源，见 `## 关联`。
>
> **本档为任务文档**（用户 2026-10-10 定：后续一律纯文档任务，代码由别的组负责）。
>
> **登记规范**：遵循「内容数据不入库」原则（见 BUG-232）：**不含真实频道名 / 消息文案**。
> 下文的实测标识一律以占位符表示（`<task_id>` / `<chat_id>` / `<msg_id>` / `<group_id>` 等）。

## 现象

用户面对一个**部分完成**的入库任务，**没有任何办法知道「剩下的那些」各自处于什么状态**。

实测（2026-10-13，生产库 `%APPDATA%/com.origadmin.orighub/tg/store.db` 只读 + 真实
`GET /api/tg/cache/tasks/all`；复现脚本见 `## 复现`）：

| `cache_task.id` | status | done/total | 逐条推导结果 |
|---|---|---|---|
| `<task_id>` | `interrupted` | **2/10** | 2 条在盘、1 条在途、**7 条从未尝试（零记录）** |
| `<task_id>` | `interrupted` | **2/9** | 1 条 photo、1 条在盘、1 条在途、**7 条从未尝试（零记录）** |
| `<task_id>` | `interrupted` | **0/1** | 1 条在途（`started_at` 有值、`accum_ms=0`） |
| `<task_id>` | `interrupted` | **0/10** | 全部从未尝试 |

任务 JSON 的**字段全集**（实测 `GET /api/tg/cache/tasks/all` 的返回键）：

```
['chatId', 'createdAt', 'done', 'groupId', 'id', 'itemKey', 'messageIds', 'priority',
 'status', 'title', 'total', 'updatedAt']
```

**没有 `items` 的状态，也没有任何逐条字段**；`messageIds` 是**裸数组**（只有 id，没有结果）。
`error` 是**一条字符串**。

**危害**：
1. **无法管控**：`2/10` 这个读数**不告诉你哪 2 条成了**。用户只能靠肉眼去媒体库比对。
2. **无法补档**：用户原话要的「补档」需要一个**缺口清单**（缺哪几集 / 缺哪几条消息）。
   库里没有任何一行能产出这个清单 —— 连「缺了几条」都要现推。
3. **重启即失忆**：`interrupted` 的 `error` 恒为固定文案（见根因 ③），
   不写「哪几条已完成」。而 `interrupted` 是**重启制造的**（实测：本次取证期间发生一次
   `orig-tg` 重启，PID `36804 → 40204`，同一窗口内 `<task_id>` 由 `running 2/10` 变为
   `interrupted 2/10`；日志内累计 **37 次** `orig-tg listening`）——**越常重启，越多任务带着
   「只有计数、没有明细」的伤疤留在库里**。实测当前 **15 条 `interrupted`**。
4. **重试抹掉唯一残留**：`retry_cache_task` 把 `done` 归零（见根因 ④），
   于是「重试一次」连那个**不可解释的计数**也一起没了。

## 根因

逐条事实**在四层都被丢掉**，每一层都有确切落点。

### ① 表结构：`cache_task` 只有计数器，没有逐条列

`cache_task` DDL（`download-engine/crates/orig-tg/src/store.rs`，`CREATE TABLE cache_task`）
的列全集是：
`id / chat_id / group_id / item_key / items / total / done / status / current_id / dir / error /
created_at / updated_at / priority`。

- `items` 存的是 `serde_json::to_string(message_ids)`（`store.rs:1073`，`enqueue_cache_task`）
  —— **一串裸 id**。
- `total` = `message_ids.len()`（`store.rs:1090` 同一函数）—— 它记的是**客户端本次发了多少条**，
  不是「这组内容应该有几条」（后者见 `BUG-296`）。
- `done` / `current_id` / `error` 是**三个标量**。

⇒ **没有任何列能承载「第 N 条的结果」**。这是结构性的，不是缺个字段那么简单：
`items` 是 JSON 数组，要记逐条结果就得把数组换成对象数组（或另立表）。

### ② `done` 是**计数器**，三个 `+1` 点的语义各不相同

`run_one_cache_task`（`download-engine/crates/orig-tg/src/routes.rs`，构造名 `run_one_cache_task`）
在**三处**给 `done` 加一，**且都不记是哪条**：

| 落点 | 条件 | 是否真的搬了字节 |
|---|---|---|
| 缓存命中分支 | `cached_path()` 命中 | 否 —— 字节**早就在盘上** |
| photo 规则分支 | `media_type == "photo"` | **否 —— 按 BUG-049 规则图片根本不落盘** |
| 下载成功分支 | `cache_one_bytes` 返回 `Ok` | 是 |

⇒ `done = 4/4` 的真实含义是「**4 条消息都处理过了**」，其中可能**一条字节都没搬**
（photo）或**全部来自缓存**。把它读成「4 条内容入库完成」是**误读**，但 UI 就是这么呈现的。
实测支撑：`media_item` 中 `photo` **145 条未登记字节 / 8 条在盘**（图片不落盘是设计，见 `## 关联` BUG-049）。

### ③ 失败与中断都只留下「一句话」

- **条目级失败**（BUG-257 方向 3）：失败**不终止任务**，只 `failures.push((msg_id, reason)); continue`
  （`routes.rs` 下载失败分支）。循环结束后 `summarize_item_failures`（`routes.rs:2427`）
  把**最多 `MAX_LISTED = 10` 条**拼成**一条字符串**，每条原因**截断到 `MAX_REASON_CHARS = 80`**
  （`routes.rs:2428-2429`），超出的写成 `… and N more (see /api/tg/logs)`。
  ⇒ **失败明细被压进一个字符串字段**，超 10 条即丢，超 80 字符即截。
- **重启中断**：`mark_stale_cache_tasks`（`store.rs:1656`）的 UPDATE 是
  `SET status='interrupted', current_id=NULL, error='应用重启：传输被中断，可重试继续' WHERE status='running'`
  —— **`done` 不动、`error` 是固定文案**。
  ⇒ 重置后你**知道「完成了 2 条」，但不知道是哪 2 条**。
  注释本身写明「用固定文案而非拼接：原因只有一个来源」—— 这是**有意的**，
  但代价正是本条登记的黑盒。

### ④ 重试把计数器归零

`retry_cache_task`（`store.rs:1109`）：
`SET status='queued', done=0, error=NULL, updated_at=?1 WHERE id=?2 AND status NOT IN ('running','queued')`
—— **`done=0`、`error=NULL`**。重试是可用的（已在盘的条目会走缓存命中分支快速 `done+1`），
但**重试把「上次到哪儿」彻底抹掉**。

### ⑤ 接口层：没有「展开一个任务的条目」的通道

缓存端点全集（`routes.rs:55-80`）：
`GET /api/tg/cache/tasks`（当前唯一 running + queued 摘要）、`GET /api/tg/cache/tasks/all`、
`GET/DELETE /:id`、`POST /:id/priority`、`POST /api/cache/tasks/:id/retry`、
`DELETE /api/cache/tasks?ids=`、`GET /api/tg/cache/tasks/by-item`。

**没有 `GET /api/tg/cache/tasks/:id/items`**。`GET /:id` 回的是同一个标量任务对象。

### ⑥ 关键边界：`BUG-279` **已实现**，但它答的是**反方向**

`BUG-279`（「媒体库未缓存条目与入库队列任务无关系联动」）**已在 `HEAD` 落地**：
`store.rs:1185 cache_task_for_item`、`routes.rs:65` 的 `/api/tg/cache/tasks/by-item`、
`tauri-shell/src/lib/mediaSources.ts:181 episodeCacheStatus`。

它的方向是 **条目 → 任务**（「这条视频的任务是什么状态」），入参是**单条** `chat:msg`，
返回**一个**任务。它**不提供**「这个任务的 N 条各自什么状态」——那是 **任务 → 条目**。
⇒ 用户的抱怨**在 BUG-279 完整落地之后依然成立**，两者共享「没有逐条事实」的根因，
但**互不交付**。本条不得被 `BUG-279` 关闭。

### ⑦ 不得推翻的既有裁定

- `mediaSources.ts:189-191`（BUG-220）明确：状态判别**不携带失败原因**，
  「失败详情…只进日志与 `cache_task.error`，界面只呈现『缓存失败』」。
  **该裁定针对的是「剧集行」这一呈现面，本条不推翻它** —— 本条要的是
  **「入库流水线任务行」可展开**这一**新呈现面**，两者是不同 surface（见 `## 修复方向` 红线）。
- `BUG-257`（fixed）修的是「条目不弃单 + 中断文案可读 + 可重试」，
  **它没有、也不打算交付逐条事实**。本条是它的**覆盖缺口**，不是复报。

## 复现

```sh
# 只读，不改任何东西。所有数字均由脚本重跑得到（无缓存、无手工录入）。
python scripts/ingest_forensics.py                       # A~G 全节
python scripts/ingest_forensics.py --tasks 183,181       # 只展开指定任务（C 节）
python scripts/ingest_forensics.py --api-port 0          # 跳过 G 节（不起服务也能跑）
```

脚本内的**硬断言**（不满足即 abort，防「静默少报」）：

- B 节：`interrupted` 明细行数 == `GROUP BY` 计数；
- E 节：普查各行之和 == `media_item` 总数；
- F 节：抽查的 `done` 任务数 == `GROUP BY` 计数。

**反向证伪**（脚本自身必须能失败，否则它不是判据）：

1. `--db` 指向不存在的路径 ⇒ 退出码 2（不得报「0 条任务」）；
2. `--api-port` 指向错误端口 ⇒ G 节打印取不到（不得报「0 行」）；
3. 把 `items` 当对象数组解析（即假设逐条状态已存在）⇒ 直接抛错 ——
   这**正是「逐条状态不存在」的机器可判形式**。

> **路径基准坑（实测踩到，写进脚本注释）**：`media_item.file_path` 有**两种形态** ——
> 绝对路径，与**相对 `<TG 数据目录>/tg/library/`** 的路径（`chat--<chat_id>/<msg>-media.mp4`）。
> 第一版脚本按当前工作目录判 `os.path.exists`，把 **135 条在盘文件误报成「路径不存在」**。
> 多基准解析后：**在盘 240（video 232 / photo 8）、未登记字节 198**，**无数据丢失**。
> 教训：取证脚本的**路径基准**与它的**断言**同等重要。

## 修复方向（建议实现，纯文档；改动前需用户拍板）

**核心结论：逐条状态可以完全「派生」，不需要新建表、不需要改状态机。**
这正是本条能低风险落地的原因 —— 所需事实**已经在库里**，只是没有出口：

| 需要的逐条事实 | 已有真源 |
|---|---|
| 这一条是哪条消息 | `cache_task.items`（裸 id 数组） |
| 字节到没到 | `media_item.file_path` + **磁盘 stat**（派生，见 `ingest-pipeline-redesign-assessment.md` §2.5 踩坑 2：**保留派生、不要换列**） |
| 这一条是不是图片（按规则不落盘） | `media_item.kind` / `media_message.media_type` |
| 这一条有没有被尝试过、烧了多少墙钟 | `cache_task_item_wall(task_id, message_id, accum_ms, started_at)` |
| 任务整体为什么停 | `cache_task.status` / `error` / `current_id` |

### 建议落点

1. **引擎（`store.rs` + `routes.rs`）**：新增**只读**派生查询
   `cache_task_items(task_id) -> Vec<{message_id, state, detail}>`，
   `state` 枚举建议（**新增的是「视图态」，不是状态机值**）：
   `on_disk` / `photo_no_bytes`（按规则） / `in_flight`（`started_at` 非空） /
   `failed(reason)` / `never_attempted`（**零记录 —— 这正是用户说的「丢失状态」**）。
   - `failed` 的 reason 来源：`cache_task.error` 里的 `summarize_item_failures` 汇总
     **只覆盖最近一次尝试且最多 10 条**；更早/更多的只能给 `unknown_failed`，
     **不得**把「查不到原因」渲染成「成功」。
   - **不新建表**（`cache_task_item_wall` 已是 (task_id, message_id) 主键，够用）；
   - **不改** `CACHE_TASK_ACTIVE_STATES`、`retry_cache_task`、`mark_stale_cache_tasks` 的语义。
2. **接口（`routes.rs`）**：`GET /api/tg/cache/tasks/:id/items` → `{ taskId, items: [...] }`。
   与 `BUG-279` 的 `by-item` **反向互补**，两条都要有。
3. **壳层（`CacheManagerDialog.tsx`）**：任务行可**展开**（`data-testid="cache-task-items"`），
   展开后逐条列出 `state` + `reason`，并给**「只重试从未尝试的那几条」**的入口
   （这是「补档」的直接落点：缺口清单 → 一键补）。
   - 红线：**不动 `mediaSources.ts` 的 `episodeCacheStatus`**（BUG-220 的裁定保持），
     本条只在**流水线任务行**这个新面上展开。

### 判据（可证伪，预先声明）

1. **派生正确性**：对已知形态的任务，`cache_task_items` 的
   `never_attempted` 条数 == 「`items` 里不在 `cache_task_item_wall` 且无字节」的条数
   （实测锚：`<task_id>` 2/10 ⇒ **7 条 `never_attempted`**）。
2. **反向证伪**：把派生查询改成「只读 `done` 计数」⇒ 逐条列表必为空 ⇒ 判据 1 **FAIL**。
3. **重启不失忆**：重启 `orig-tg`（`mark_stale_cache_tasks` 生效）后，
   同一任务的逐条列表**逐条一致**（`never_attempted` 集合不变）；
   **反向**：若把逐条状态改成「只在内存里记」⇒ 重启后必退化成全 `unknown` ⇒ FAIL。
4. **重试不掩盖**：`retry_cache_task` 后，逐条列表里**已在盘的条目仍为 `on_disk`**
   （不得因为 `done=0` 就变回 `never_attempted`）。
5. **不回归**：`GET /:id`、`/all`、`by-item`（BUG-279）、批量条（BUG-249）、
   优先级（BUG-277）的响应字段**一个不减**；`check-bugs.py` 的 4 项既有 ERROR 不增。
6. **UI 真实渲染**（CDP，禁读 className、用 `data-testid`）：
   展开行后 `never_attempted` 的条数在 DOM 中**可数**，且与判据 1 的数字一致。
