# BUG-096: AGENTS.md §5 的「双向删除联动」与代码实际分家（缓存清理规约 vs 实现）

- 状态: fixed
- 发现日期: 2026-09-21
- 模块: docs
- 严重程度: mid

> 编号说明：本条原定 BUG-095，动手复核 `ls docs/bugs/` 时该编号已被「TG 开关无状态建模」
> （评估立档，`open`）占用，故顺延至 096。

## 现象

`AGENTS.md` §5 的铁律条目（BUG-029）写着「缓存即入库 + **双向**删除联动」：

> 删除必须**双向联动**：清缓存 → 删对应 media_item；删 TG 来源条目 → 清缓存副本。

代码里这两个方向**只有一半存在**：

- **正向（清缓存 → 删条目）根本没实现**。`cache.rs::purge_item`（清一条的字节）
  只做三件事：unlink 文件 → `set_item_file_path(None)` → 复位 TG `downloaded`
  标记（`reset_tg_flag`）。它不碰 `media_item` 行。`cache.rs::clear` 的文档注释
  把这条不变量写死：「**条目本身永不删除** —— 清字节后条目回到「仅入库」态、
  可重新缓存，删条目属媒体库域（BUG-051 的边界）」。
- **反向（删 TG 条目 → 清字节）是真代码**。`orig-tg/src/routes.rs:1951` 的
  `delete_media_item` 先按 `inside_dir` 删下载目录内的文件，再对 `source == "tg"`
  的条目用 `parse_tg_ref` 解出 `(chat, msg)` 并 `clear_downloaded`。

为那条不存在的正向级联专门写的 `Store::delete_media_item_by_ref`
（原 `download-engine/crates/orig-tg/src/media.rs:1115`）**全仓零调用**，已成死代码
（另外两处出现分别是 `docs/bugs/BUG-029.md` 的历史修复记录和一份本地备忘，均非调用点）。

## 根因

BUG-051 重新划了三模块边界（M1 展示 / M2 缓存 / M3 媒体库），把「缓存」定性为
**「订阅内容 → 媒体库」的入库准备物**：清缓存回收的是缓存自己产出的字节，条目本身
属于媒体库域，删条目只能由媒体库自己的删除链发起。代码按这条新边界演进完成，
但 §5 的 BUG-029 铁律条目**没有跟着回写**——它仍停留在 BUG-029 时期的「双向」措辞，
于是规约与实现分家；为正向级联准备的 `delete_media_item_by_ref` 也随之烂在仓里。

## 影响

1. **规约反过来误导实现**：后来者照 §5 补正向级联，等于「清掉准备物 → 连成品一起删」，
   与用户裁定的「缓存是入库准备物」定位正好相反，属于会丢用户数据的反向修。
2. **死链表象**：清完缓存条目仍在但 `file_path` 为 NULL，`/api/media/items/:id/raw`
   返回 404，变成「还在但打不开」。该表象的呈现侧已由 BUG-080 的 `EpisodeView.has_bytes`
   承接（无字节则占位、不给播放按钮、TG 源给「重新缓存」），因此**引擎侧不需要再改**——
   这正是「只改文档、不补实现」成立的依据。

## 修法

裁定：**改文档承认新边界，不补实现**。

1. `AGENTS.md` §5 的 BUG-029 条目改写为「缓存即入库 + **单向**删除联动
   （BUG-029 / BUG-051 边界）」：
   - 保留仍然成立的前半（缓存成功路径必须 `upsert_media_item(source="tg", ref=...)`，
     媒体库是缓存的主视图）；
   - ①改为「清缓存只回收字节，条目退回仅入库态、可重新缓存」，并**明文禁止**
     再实现「清缓存 → 删 media_item」的正向级联；
   - ②写清唯一存在的方向：删 TG 来源条目必须连带清字节（指向
     `routes.rs:1951` 的 `delete_media_item`），否则下次 upsert 会「复活」；
   - ref 约定（`source="tg"`、`ref="<chat_id>:<message_id>"`）不变。
   只把「双向」改成「单向」并说清方向，不整条重写——它是铁律条目，其他条目与代码
   注释引用它的措辞。
2. 删除死代码 `delete_media_item_by_ref`（零调用、无 `#[cfg(test)]` 用例引用）。

## 验收证据

可核三项（均为入库文件，换台机器同样可核）：

1. **AGENTS.md §5 现文**：BUG-029 条目已是「缓存即入库 + **单向**删除联动（BUG-029 /
   BUG-051 边界）」，并含「**条目本身永不删除**」与「**禁止**为『清了缓存』而回头删
   media_item」两句；仓库内已无「清缓存 → 删对应 media_item」的旧表述
   （`AGENTS.md` 里剩下的唯一一处「双向」是 §7 门禁表的「索引↔文件双向一致」，
   与本条无关，不得改）。
   复核：`grep -n "BUG-029\|单向\|双向" AGENTS.md`
2. **正向级联的死代码已消失**：`grep -rn "delete_media_item_by_ref" download-engine/`
   零命中。若日后有人复活它，本条即为拦截依据。
3. **反向联动仍在**：`download-engine/crates/orig-tg/src/routes.rs:1951` 的
   `delete_media_item` 仍先删下载目录内字节、再对 `source=="tg"` 解 ref 后
   `clear_downloaded`；`download-engine/crates/orig-tg/src/cache.rs` 的
   `purge_item` 仍只清字节、不动条目行。
   复核：`sed -n '1951,1990p' download-engine/crates/orig-tg/src/routes.rs`

`orig-tg/src/media.rs`，该注释未改——若要彻底对齐，只需把注释里的「双向联动」
改为「单向联动（删条目 → 清字节）」，属纯注释改动。
