# BUG-124：另外三个删除入口同样制造孤儿备用源行 —— 条目被永久锁死（BUG-103 只覆盖合并入口）

- 状态: fixed
- 严重程度: high
- 模块: engine
- 发现日期: 2026-09-22

## 与 BUG-103 的关系（先说清楚，避免重复登记）

BUG-103 已经查明并止血了**同一个根因**，但它论证与验收的范围**只覆盖 `merge_series`**：

> BUG-103 原文：「`merge_series`（`media.rs:1386-1545`）整个事务从不触碰
> `media_episode_source`……**1386–1545 区间零命中**」

本条补的是**另外三个入口** —— 它们同样直接 `DELETE FROM media_episode` 而不清
`media_episode_source`，因此制造的是**同一种孤儿行、同一种永久锁死**。

## 取证（逐行核对，非推测）

| 入口 | 位置 | 删除语句 | 是否清 `media_episode_source` |
|---|---|---|---|
| `remove_episode` | `media.rs:1900-1926` | `DELETE FROM media_episode WHERE id = ?1`（1915） | **否** |
| `delete_series` | `media.rs:1629-1639` | `DELETE FROM media_episode WHERE series_id = ?1`（1631） | **否** |
| `delete_media_item` | `media.rs:1059-1074` | `DELETE FROM media_episode WHERE item_id = ?1`（1067） | **否** |

（对照：`merge_series` 是 BUG-103 覆盖的第四个入口。）

三处都是「删分集行 → 删标签 / 删主体 → prune 空剧集」，**没有一处**回头清理
`media_episode_source`。

## 后果（与 BUG-103 完全同构）

`media_episode_source.item_id` 是**全表 UNIQUE**。分集行被删后，挂在它上面的备用源行变成
`episode_id` 悬空的**孤儿行**，而孤儿行**占着那个 `item_id`**，于是：

- 之后把该条目挂到**任何**分集都会失败：
  `UNIQUE constraint failed: media_episode_source.item_id`
- 用户侧表现是「点了挂不上 + 弹报错」，**不是静默无反应**；
- 无外键级联，孤儿行**跨进程重启仍残留**，阻塞是**永久性**的，用户无法自愈。

最刺眼的一处是 `remove_episode`：用户**从剧集里移除一集**（一个正常的整理动作），
就可能把该集的备用源变成孤儿并**永久锁死那些条目** —— 修 BUG-112（图片无法从剧集移除）
时如果把移除入口接上，这个副作用会立刻变得**更容易被用户触发**。

> 换句话说：BUG-112 是「不能删」，本条是「删了会留下永久损伤」。两者必须**一起修**，
> 否则接上删除入口等于**把伤害从「没有入口」升级为「有入口且会破坏数据」**。

## 修复方向：用触发器，不要逐入口补 DELETE

**不要**在三个（将来是 N 个）删除路径上各补一句 `DELETE FROM media_episode_source` ——
这正是 BUG-110 的教训：「逐端点打补丁」是结构性缺陷，**下一条新写路径必然又漏**。

正确做法是把这个不变量交给**数据层**表达（与 BUG-044 用触发器守住「备用源只能是视频」
同一思路）：

```sql
CREATE TRIGGER IF NOT EXISTS trg_media_episode_cleanup_sources
AFTER DELETE ON media_episode
FOR EACH ROW
BEGIN
  DELETE FROM media_episode_source WHERE episode_id = OLD.id;
END
```

一处生效、覆盖全部现有入口，且**将来任何新写路径自动正确**。

注意实现细节：

- 该触发器必须**幂等创建**（`IF NOT EXISTS`），且要意识到
  `CREATE TRIGGER IF NOT EXISTS` 只防重复创建、**不会**让另一个名字的旧触发器失效 ——
  若日后改名，必须**显式 DROP 旧名**（BUG-044 已踩过：退役触发器留在已升级的库里，
  表现为「剧集建成却 0 分集」）。
- 触发器建在 `migrate()` 里，与现有触发器同处；注意建表批（`execute_batch`）只许出现
  新旧库都存在的列（BUG-032）。
- 补一条**旧库 → 新代码**迁移单测：造孤儿行 → `open` 后触发器已就位 → 删分集不再产生孤儿。

## 验收要求

1. 三个入口逐个验证：删分集 / 删剧集 / 删条目后，
   `SELECT COUNT(*) FROM media_episode_source src LEFT JOIN media_episode e ON e.id = src.episode_id
    WHERE e.id IS NULL` **必须为 0**（无孤儿）。
   —— 这正是 BUG-103 已用过的判据，复用即可。
2. **反向证伪**：先造一条孤儿行（直接插），确认判据能报出来 —— 否则断言是假的（假绿）。
3. 顺带修存量：迁移时清理历史孤儿行（可复用 `media.rs:409` 附近既有的迁移清理写法）。

### 反向证伪（验收的验收）

**判据本身非空转**：绕过触发器直插一条孤儿行，计数必须报出 1（测试内第 ③ 步），
否则「= 0」的断言可能是查询写错却恒为 0 的假绿。

**触发器真的被依赖**：把触发器体改成空操作（`DELETE … OLD.id;` → `SELECT 1;`，
**触发器仍存在**，故「触发器应建成」那条断言不受影响），单独重跑该测试：

```
test media::tests::legacy_orphan_source_rows_are_cleaned_and_trigger_prevents_new_ones ... FAILED
panicked at crates\orig-tg\src\media.rs:3216:9:
assertion `left == right` failed: remove_episode 删分集后不得留孤儿备用源行
  left: 1
 right: 0
test result: FAILED. 0 passed; 1 failed; 0 ignored; 73 filtered out
```

即：**去掉触发器行为，测试如实变红** —— 它确实在测触发器，而不是因为别的原因恰好通过。

> **一次失败证伪的记录（值得留档）**：第一次尝试是把触发器的 `AFTER DELETE ON media_episode`
> 改挂到 `media_series`，本以为等价于禁用，结果测试**照样绿**，一度误判为「假绿」。
> 复查后确认是**证伪手法本身不干净**：测试库里剧集 id 与分集 id 在小整数区间重叠，
> 触发器挂在 `media_series` 上删剧集时 `episode_id = OLD.id` 会**偶然命中**分集行。
> 换用「触发器体改空操作」这种**不改变挂载点、只取消行为**的手法后才得到有效结论。
> 教训：**证伪手段本身也要被检验** —— 一个「看起来禁用了」的改动可能什么都没禁用，
> 于是把一个有效的测试误判成假绿。
