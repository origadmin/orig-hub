# BUG-241: TG 面板进入频道即请求爆炸 —— by-ref 逐条 N+1 + 每瓦片一缩略图 + GET 带 `Content-Type` 触发 CORS 预检翻倍；实测 4s 内 90 请求、峰值 78 req/s

- 状态: open
- 发现日期: 2026-10-09
- 模块: shell
- 严重程度: high
- 登记: 用户报告「**请求爆炸问题**：TG 插件 → 每日沙雕墙，**进入后请求了 1000 多个**」

## 现象

**进入 TG 面板（点 `nav-tg`）即发生**：`tauri-shell/src/components/TgPanel.tsx:630-632` 挂载时
**自动选中首个监控频道并拉 feed**（「进入频道」不需要再点）。

CDP Network domain 全量抓取（headful Edge + 真实 UI，**两次独立复现一致**）：

| 指标 | 实测 |
|---|---|
| 挂载后 4s 内 `/api` 请求总数 | **90** |
| 瞬时峰值 | **78 req/s**（sec0: 78、sec1: 10） |
| 时间分布 | **一次性爆发，非周期轮询**（静置 40s 新增 **0**） |
| 逐页成本（滚到顶 +30 消息） | 新增 `/api` **79–91**（`by-ref` 48–58、`thumb` 24–30） |
| 滚 6 页累计 | **593** |

端点族（首屏 90 的构成）：`/api/media/items/by-ref` **×54**、`/api/tg/thumb/{c}/{m}` **×16**、
`/health` ×3、`/api/tg/cache/tasks` ×3，`session`/`dialogs`/`monitor`/`channels`/`folders`/`messages`/`sync`/`downloaded` 各 ×2。

## 根因（三条，全在前端）

**1. `by-ref` 逐条 N+1（最大头，54/90）**
`tauri-shell/src/components/TgPanel.tsx:1035-1056` 的 `useEffect`（依赖 `feed`）
对**每条 photo 各发一次** `by-ref`（调用点 `tauri-shell/src/api/media.ts:246`）。
同一批消息本可一次多 ref 查询。

**2. 每个媒体瓦片一个缩略图请求，且列表无虚拟化**
`TgPanel.tsx:2262` / `:2417` / `:2446` 每个媒体瓦片各渲染一个 `<img src={tgThumbUrl(...)}>`
（`tauri-shell/src/api/tg.ts:298`）；`TgPanel.tsx:1868` 是**全量** `albumUnits.map`，**无虚拟化**。

**3. GET 请求带 `Content-Type: application/json` ⇒ 触发 CORS 预检，请求数翻倍（主因）**
`tauri-shell/src/api/tg.ts:87` 与 `tauri-shell/src/api/media.ts:198` 给**包含 GET 的所有请求**
统一加 `Content-Type: application/json`。这是**非简单头**，于是跨源（`5180` → `19787`）
对每个**首次出现**的 URL 先发一次 `OPTIONS`。

实测 initiator 归因：`preflight ×35` + `script::media.ts request ×27`；`by-ref` 的 54 ≈ **27 张照片 × 2**。
后端 CORS 已设 `max_age(3600)`（`download-engine/crates/orig-tg/src/main.rs:294`），
但它**只对重复 URL 生效**，救不了首屏每个 URL 各一次预检。

**后端无放大**（已排除）：thumb 命中 `TtlLru` 缓存零 RPC（`crates/orig-tg/src/grammers.rs:526-546`）；
`by-ref` 单次 DB 读（`crates/orig-tg/src/routes.rs:2684-2694`）。**放大全部在前端。**

> 规则依据（本仓既有约定）：`docs/bugs/BUG-232.md:30`「每 ref 只问一次（含『查过但无』缓存），
> **不在渲染期发起请求**（请求风暴规则）」—— 本条**违反**该规则（第 1、2 条均为渲染期按条目发请求）。

## 关于「1000+」的定量解释（对照基线未取得，用结构分析替代）

**未取得对照频道数字**，原因是环境限制：本机仅 **1 个监控频道**；非监控频道只能经左栏
「全部订阅」进入，而该列表受面板 `alive` 门约束（`TgPanel.tsx:515`），取证期
**orig-tg 两次退出**（`tgService.lastError: "orig-tg exited without listening on 127.0.0.1:19787"`，
另见 BUG-227）⇒ `alive=false` ⇒ 频道列表恒为「全部订阅 0」，控制频道点不到（多次重试均失败）。

**替代分析**：请求量是「已渲染媒体数」的**确定函数**（photo = `by-ref`×2 + `thumb`×1；
video = 仅 `thumb`×1），且 feed 组件对所有频道**无分叉** ⇒
**1000+ = 内容量 × 每项 N+1，属结构性缺陷，不是「每日沙雕墙」特有**。
按实测密度（30 瓦片 ≈ 90 请求）推算，1000+ 约对应 **~330 个媒体项（≈11 页）**，
与用户滚动/长会话浏览的规模一致。

## 修复方向（未实施）

1. **GET 去掉 `Content-Type`**（`api/tg.ts:87`、`api/media.ts:198` 改为仅在有请求体时设置）
   ⇒ 消除预检，请求数**约减半**；
2. **`by-ref` 批量化**：一次请求带多个 ref（后端加批量端点），消除逐条 N+1；
3. **瓦片/缩略图虚拟化或懒加载**：`TgPanel.tsx:1868` 的全量 `map` 改为按视口渲染；
4. **消除「挂载即自动拉全页」**：`TgPanel.tsx:630-632` 的自动选中 + 拉 feed 改为受控/分页。

## 修复后必须满足（可证伪判据，预先声明）

1. 进入 TG 面板后 4s 内 `/api` 请求总数 **≤ 30**（当前 90），且 `by-ref` 请求数
   **不随照片数线性增长**（批量化后应为 O(1) 批次数）；
2. Network 面板中，**含 GET 的请求不产生任何 `OPTIONS` 预检**（预检数 = 0）；
3. 滚动 +30 消息的新增请求数**不随已渲染瓦片数线性增长**（虚拟化/懒加载生效）；
4. 反向证伪：把 `Content-Type` 加回 GET，判据 2 必须重新 FAIL。
