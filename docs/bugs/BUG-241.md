# BUG-241: TG 面板进入频道即请求爆炸 —— by-ref 逐条 N+1 + 每瓦片一缩略图 + GET 带 `Content-Type` 触发 CORS 预检翻倍；实测 4s 内 90 请求、峰值 78 req/s

- 状态: partial
- 发现日期: 2026-10-09
- 模块: shell
- 严重程度: high
- 登记: 用户报告「**请求爆炸问题**：TG 插件 → 每日沙雕墙，**进入后请求了 1000 多个**」
- 排期: 2026-11-10

## 现象

**进入 TG 面板（点 `nav-tg`）即发生**：`tauri-shell/src/components/TgPanel.tsx:630-632` 挂载时
**自动选中首个监控频道并拉 feed**（「进入频道」不需要再点）。

CDP Network domain 全量抓取（headful Edge + 真实 UI，**两次独立复现一致**）：

| 指标 | 实测 |
|---|---|
| 挂载后 4s 内 `/api` 请求总数 | **90** |
| 瞬时峰值 | **78 req/s**（sec0: 78、sec1: 10） |
| 时间分布 | **一次性爆发，非周期轮询**（静置 40s 新增 **0**） |
| 逐页成本（滚到顶 +30 消息） | 新增 `/api` **79–91**（`by-ref` 48–58、`thumb` 24–30） |
| 滚 6 页累计 | **593** |

端点族（首屏 90 的构成）：`/api/media/items/by-ref` **×54**、`/api/tg/thumb/{c}/{m}` **×16**、
`/health` ×3、`/api/tg/cache/tasks` ×3，`session`/`dialogs`/`monitor`/`channels`/`folders`/`messages`/`sync`/`downloaded` 各 ×2。

## 根因（三条，全在前端）

**1. `by-ref` 逐条 N+1（最大头，54/90）**
`tauri-shell/src/components/TgPanel.tsx:1035-1056` 的 `useEffect`（依赖 `feed`）
对**每条 photo 各发一次** `by-ref`（调用点 `tauri-shell/src/api/media.ts:246`）。
同一批消息本可一次多 ref 查询。

**2. 每个媒体瓦片一个缩略图请求，且列表无虚拟化**
`TgPanel.tsx:2262` / `:2417` / `:2446` 每个媒体瓦片各渲染一个 `<img src={tgThumbUrl(...)}>`
（`tauri-shell/src/api/tg.ts:298`）；`TgPanel.tsx:1868` 是**全量** `albumUnits.map`，**无虚拟化**。

**3. GET 请求带 `Content-Type: application/json` ⇒ 触发 CORS 预检，请求数翻倍（主因）**
`tauri-shell/src/api/tg.ts:87` 与 `tauri-shell/src/api/media.ts:198` 给**包含 GET 的所有请求**
统一加 `Content-Type: application/json`。这是**非简单头**，于是跨源（`5180` → `19787`）
对每个**首次出现**的 URL 先发一次 `OPTIONS`。

实测 initiator 归因：`preflight ×35` + `script::media.ts request ×27`；`by-ref` 的 54 ≈ **27 张照片 × 2**。
后端 CORS 已设 `max_age(3600)`（`download-engine/crates/orig-tg/src/main.rs:294`），
但它**只对重复 URL 生效**，救不了首屏每个 URL 各一次预检。

**后端无放大**（已排除）：thumb 命中 `TtlLru` 缓存零 RPC（`crates/orig-tg/src/grammers.rs:526-546`）；
`by-ref` 单次 DB 读（`crates/orig-tg/src/routes.rs:2684-2694`）。**放大全部在前端。**

> 规则依据（本仓既有约定）：`docs/bugs/BUG-232.md:30`「每 ref 只问一次（含『查过但无』缓存），
> **不在渲染期发起请求**（请求风暴规则）」—— 本条**违反**该规则（第 1、2 条均为渲染期按条目发请求）。

## 关于「1000+」的定量解释（对照基线未取得，用结构分析替代）

**未取得对照频道数字**，原因是环境限制：本机仅 **1 个监控频道**；非监控频道只能经左栏
「全部订阅」进入，而该列表受面板 `alive` 门约束（`TgPanel.tsx:515`），取证期
**orig-tg 两次退出**（`tgService.lastError: "orig-tg exited without listening on 127.0.0.1:19787"`，
另见 BUG-227）⇒ `alive=false` ⇒ 频道列表恒为「全部订阅 0」，控制频道点不到（多次重试均失败）。

**替代分析**：请求量是「已渲染媒体数」的**确定函数**（photo = `by-ref`×2 + `thumb`×1；
video = 仅 `thumb`×1），且 feed 组件对所有频道**无分叉** ⇒
**1000+ = 内容量 × 每项 N+1，属结构性缺陷，不是「每日沙雕墙」特有**。
按实测密度（30 瓦片 ≈ 90 请求）推算，1000+ 约对应 **~330 个媒体项（≈11 页）**，
与用户滚动/长会话浏览的规模一致。

### 已实施 —— Priority 1：去除非请求体请求的 `Content-Type`（根因 3）

三个请求助手改为**由 `body != null` 派生** `Content-Type`，不再对每个请求无条件附加
（`Content-Type` 是非 CORS 安全头，GET/HEAD 带上会让每个首次出现的跨源 URL 先发一次
`OPTIONS`，这正是 by-ref 54 ≈ 27 照片 × 2 的来源）：

- `tauri-shell/src/api/tg.ts:83-92`：
  `headers: init?.body != null ? { 'Content-Type': 'application/json' } : undefined`
- `tauri-shell/src/api/media.ts:208-218`：
  `headers: { ...(init?.body != null ? { 'Content-Type': 'application/json' } : {}), ...(init?.headers ?? {}) }`
- `tauri-shell/src/api/daemon.ts:37-44`：与 tg.ts 同模式。daemon 的 `/health`、`/api/config`
  等 GET 同样跨源（5180 → 19786），一并修；否则判据 2 仍会因这些 GET 预检而 FAIL。

**审计：所有携带请求体的调用点均保留 `Content-Type`** —— tg.ts 8 处（`startTgLogin`/
`submitTgCode`/`submitTgPassword`/`addTgMonitoredChannel`/`downloadTgMessage`/
`setTgDownloadDir`/`setTgLibraryDir`/`enqueueCacheTask`）、media.ts 19 处、daemon.ts 7 处，
全部以 `body:` 传值；`media.ts` 的 `exportMedia` 自带独立 `fetch`（显式带头 + 带体）不受影响。
GET/HEAD 与**无体的 POST/DELETE** 不再带该头。已核后端对应无体处理器
（`monitor_sync`、`cache::clear`、`clear_tasks`、`cancel_cache_task_route`、
`batch_task_action` 等）只用 `State`/`Path`/`Query` 提取器、**无 `Json` body 提取器**，
去掉头不改变其行为。

静态证据：`tsc --noEmit` 退出码 **0**；`git diff` 见本次提交。

## 实测补充（2026-10-10）：探针独立复跑，判据 2 成立、判据 1 未达标

## 探针守卫修复 + 复跑（2026-10-10，本节追加，不改写上文）

**探针侧修复**（`tauri-shell/verify/`）：把「进入频道」窗口的守卫由 `assertTgTraffic`
（断言非零）换成新加的 `assertTgAlive`（断言**端点仍以 orig-tg 的身份存活**）。
理由：该窗口的期望是**状态相关**的 —— 面板挂载时会自动选中首个监控频道，点中的若是同一行
就是幂等重选，修好的构建正确地**不发**新请求；在那里断言非零等于**把修复前的行为当成基线**。
端点失活的防护并未丢失：`resolve()` 的启动探针 + `assertTgAlive` 的运行中复核各覆盖一次。

`assertTgAlive` 的边界经四组实测标定（同一 harness，`tg` 由运行时解析）：

| 组 | 目标端点 | 期望 | 实测 |
|---|---|---|---|
| A | 真实栈 `:19788` | 不抛 | **不抛**，exit 0 |
| B | 死端口 `:9` | 抛 | **抛**（`connect ECONNREFUSED`），exit 2 |
| C | 活但错的端口 `:5180`（vite） | 抛 | **抛**（`content-type is text/html`），exit 2 |
| D | daemon `:19786` | 已知残余 | **不抛** —— 见下 |

**残余局限（实测，不是推测）**：`/health` 的响应体在 orig-tg 与 daemon 上**完全相同**
（都是 `200 application/json {"status":"ok"}`，实测 C 组之所以能被拒是因为 vite 回 `text/html`）。
故本守卫能拒「非 JSON / 非 ok」的冒名者，**不能**区分同机上的 orig-tg 与 daemon。已写进
`_lib_endpoints.cjs` 的注释，不假装它更强。

**复跑结果**（探针现以 **exit 0** 结束，修复前为 exit 1）：

- 窗口 A（面板挂载 0→3.5s）：`/api` **58**、peak **56 req/s**、`OPTIONS` **0**。
  族分布：`by-ref` 30 / `thumb` 14 / `dialogs` 3 / `cache/tasks` 2 / `session` 2 / `health` 2 / 其余各 1。
  ⇒ 判据 1 仍**未达标**（58 > 30；与上次 53 的差异属运行间波动，瓦片/照片数不同）。
  `by-ref` 30 + `thumb` 14 = **44 仍属 N+1**，与上文「须落 Priority 2/3」的结论一致。
- 进入「每日沙雕墙」后 30s：`/api` **6**，**全部**是 `/api/tg/cache/tasks`，
  逐秒 `0:1 4:1 10:1 15:1 20:1 25:1` ⇒ **5s 定时轮询**（不是爆发），`OPTIONS` **0**。

**一处不一致，如实登记、原因未查明**：上文记「窗口 B：再点击监控频道行后 30s —— 新增 0」，
本次同位置测得 **6**（全是 cache/tasks 轮询）。两次**口径不同**（上文是「二次点击」，
本次是「挂载后首次点击」），但**为何二次点击为 0 而首次为 6，本轮未查明**，故不据此改写上文数字。
另记一条**观察（未单独立档）**：空闲时 `/api/tg/cache/tasks` 仍以 5s 轮询，量级 0.2 req/s，
不构成风暴；若后续要压首屏稳态开销可从这里入手。
