# BUG-261: 「未缓存」状态没有配套动作 —— 标记不可点、无剧集级批量缓存入口、重缓存判据绑在「当前主源」而非「可用来源」

- 状态: open
- 发现日期: 2026-10-10
- 模块: engine+shell
- 严重程度: mid

> 来源：用户报告「目前部分视频已能正确显示"未缓存"状态，但视频详情中仍缺少联动操作，需要支持点击缺失内容直接进行缓存以及切换来源。缓存逻辑必须与来源绑定，即只要有可用来源的视频，无论何时都能进行缓存或继续缓存。请重新评估当前入库设计方案是否存在问题。」

## 现象

### 现象 1：「未缓存」只是一个死标记，不可点

分集列表里无字节的那一集，尾列渲染 `data-testid="episode-nobytes"` 的 `<span>`
（`tauri-shell/src/components/media/SeriesDetail.tsx:583-596`，`CloudOff` + 「未缓存」）。
它是**纯展示**：外层 `<button data-testid="episode-pick">` 的 `onClick` 只做
`setFocusedEpisodeId(ep.id)`（`:560-563`）—— **点它只会把右栏切到这一集，不发起任何缓存**。

⇒ 用户看到「未缓存」，要缓存必须走三跳：点该行 → 右栏 → 滚到「操作」行 → 点
`episode-recache`（`:864-877`）。**「状态」与「动作」分处左栏与右栏，屏幕上都不同框。**

### 现象 2：没有「把这部剧缺的补上」的入口

重缓存入口是**逐条**的，全仓共 4 处，全部一次只处理一条：

| 入口 | 位置 | 门控 |
|---|---|---|
| 卡片「重新缓存」 | `components/media/MediaCard.tsx:286,380-395`（`item-recache`） | `!playable` |
| 右栏操作行 | `components/media/SeriesDetail.tsx:864-877`（`episode-recache`） | `!hasMediaBytes(cur)` |
| 播放器遮罩 | `components/media/VideoPlayer.tsx:1266` + `components/MediaViewer.tsx:242-250` | `hasBytes === false` |
| 条目编辑弹窗 | — | **无**（那里只有「清除缓存文件」） |

i18n 里**没有任何**「缓存全部 / 批量缓存 / 继续缓存」键 —— 实测只有 6 个单条语义的键：
`media.recache` / `media.recacheQueued` / `media.recacheFrom` / `media.recacheUnavailable`
/ `media.episode.recacheNoRoute` / `media.episode.recacheQueued`。

⇒ 用户说的「继续缓存」（把这部剧里没缓存的集接着缓存完）**当前不存在**。
实测（只读真库，2026-10-10）**30 / 45 个剧集**的卡片集数 > 有字节集数；最极端的
`id=218`「#投稿」显示 10 集、**0 集有字节** —— 这类剧集要点 10 次、发 10 个请求。

### 现象 3：重缓存判据绑在「当前主源」，不是「这一集有没有可用来源」

4 处入口的判据都是 `canRecacheFromSource(<该条目>.source)`
（`lib/mediaSources.ts:106-108` → `getSourceAdapter(source)?.canRecache`，当前只有 `tg` 为 true）：

- `SeriesDetail.tsx:869` `disabled={!canRecacheFromSource(cur.source)}`
- `MediaLibraryPanel.tsx:502-507` `recacheBlockedReason(source)`
- 备用源的类型 `EpisodeSourceRef`（`api/media.ts:137-142`）**只有 `{itemId, title?, kind?}`，
  没有 `source` / `ref`** ⇒ 前端**拿不到备用源的定位符** ⇒ 即使有备用源也无法「用备用源缓存」。
- 「切来源」是**另一步**：`switchEpisodeSource(ep.id, itemId)`（`api/media.ts:622-628`）——
  切完之后 `cur.source` / `cur.ref` 才变成新主源的。

⇒ 用户诉求「只要有可用来源的视频，无论何时都能进行缓存」在当前实现下只能**两步走**
（先切主源、再点重缓存）；且**当主源是 `local`、备用源是 `tg` 时，重缓存按钮是 disabled 的**
（用户得先想到「去切来源」）。

**实测受害面（如实登记）**：

| 口径 | 实测 |
|---|---|
| 挂剧集且无字节的分集主条目 | **21 个，`source` 全部 = `tg`** ⇒ 重缓存按钮**现在都是可用的** |
| `media_episode_source` 表 | **当前 0 行** ⇒ 备用源功能在生产库里从未被使用 |
| 「主源不可重缓存 + 备用源可用」的分集 | **0 个** |

⇒ **这是一个潜伏缺陷（latent），不是当前可见故障。** 登记它的理由是判据绑错了对象：
一旦出现「本地导入的集 + 挂了 TG 备用源」，或「主源 ref 失效但备用源仍在」，
用户会看到一个**永久禁用且不解释原因**的按钮。

## 根因

### 根因 1：动作挂在「条目」上、状态挂在「集」上，两者之间没有联动

`episode-nobytes`（状态）与 `episode-recache`（动作）分处左栏列表与右栏操作行，
中间隔着整个右栏。设计文档 `docs/design/episode-internal-ia-v2-2026-09-29.md` 定档了
「无选择即无控件」（§5 S4，BUG-210 落地为来源区门控 `SeriesDetail.tsx:738`），
但**从未定过「状态标记是否应承载动作」** —— 全库查无。
⇒ 这是**决策缺失**，不是实现走偏。

### 根因 2：「缓存能力」的判据被写成「当前主源是否支持」，而正确判据是「该集有没有任一可用来源」

`canRecacheFromSource(source)` 的语义是「**这个来源**是否支持原路重取」
（`mediaSources.ts:105-108` 注释原文：「该来源是否支持原路重新缓存」）。
用它 gate 按钮，等于把「**这个条目当前的主源**」当成了「**这一集的全部来源**」。

数据模型上两者明确不同（`docs/design/ingest-pipeline-redesign-assessment.md:189-190`）：
主源 = `media_episode.item_id`；其他来源 = `media_episode_source(episode_id, item_id)`。
而前端**拿不到**备用源的 `ref` ⇒ 判据在数据上**无从**基于备用源。

⇒ 用户说的「缓存逻辑必须与来源绑定」在语义上**是对的**，但现状绑的是**错的那个来源**
（当前主源），而不是**可用来源集合**。

### 根因 3：入库设计**已预见**本现象，但预见只落地了一半

`docs/design/ingest-pipeline-redesign-assessment.md`（2026-09-21）§2.5「反例与踩坑预警」原文：

> - **图片例外分支稀释**：`import_photo_item` 是唯一「无字节也入库」路径，一旦全面先行，
>   `file_path=NULL` 从例外变常态；
> - **空条目会被编进剧集**：自动成剧的门是触发器 `trg_media_episode_*`（`media.rs:472-495`），
>   **只卡 `kind` 不卡字节** → 出现「有集数、无内容」，而 `has_bytes` 目前只挂在
>   `EpisodeView`（`media.rs:643`），网格没有；

**这两条现在都在生产库里成立了**（实测：`media_item` 373 行中 **110 行无字节**；
挂剧集的无字节分集 **21 行**；**30 / 45** 个剧集卡片集数 > 有字节集数）。

而该文档 §1 判定的 **P0 真缺口**（「元数据登记与字节就绪应分离」＋「媒体库应有独立资产状态」）
**至今未实施**：全仓 `asset_state` / 「待获取」**零命中**；`has_bytes` 仍是
`file_path IS NOT NULL` 的派生值。

**并且 §4.1 ① 的仲裁与已落地的实现相反**：

| | 内容 |
|---|---|
| 仲裁原文（§4.1 ①） | 「未就绪条目可见性 → **默认不进媒体库主网格**，走独立『待获取』视图；但媒体库顶部常驻『待获取 N 条』入口」；理由：「满屏空条目 + 空条目进剧集是不可接受的回归」 |
| 实际落地 | 未就绪条目**进了主网格**（`MediaCard.tsx` 的 `item-nobytes` 占位，BUG-250），也进了剧集（集数含无字节）；「待获取」视图不存在 |

**评估结论**：入库设计的判断是对的（「登记与就绪应分离」「空条目进剧集是回归」），
**落地只做了一半** —— BUG-248 做了「入队即登记」（登记前移），没做「资产状态」与「可见性策略」。
用户现在要的「无论何时都能缓存」正是那一半的另一面：
**条目既然提前进了库，就必须同时给它在库内的可操作出路**；否则「提前可见」只是把一个
空洞提前暴露给用户，而用户拿不到填补它的手段。

## 修复方向（未实施）

1. **让「未缓存」标记承载动作**：点它即在原地给出「缓存这一集」与「切换来源」两个动作
   （形态见待确认 3）。这是「联动操作」最直接的落点。
2. **剧集级「把缺的补上」入口**：必须**后端加原子批量端点**（本仓规约：批量操作禁止前端循环调单条），
   例如 `POST /api/media/series/:id/recache-missing`，返回「入队 N 条 / 跳过 M 条（及原因）」。
3. **判据改为「可用来源集合」**：由后端算出并下发（`SeriesView` / `EpisodeView` 增
   `recacheableCount` 或 `hasRecacheableSource`），前端不再自己按主源判 —— 前端本就拿不到备用源的 ref。
4. **`EpisodeSourceRef` 补 `source` / `ref`**：后端在 `media.rs:1748` 已批量补齐来源列表，
   加这两个字段成本很低；否则「用备用源缓存」在前端**无法表达**。
5. **禁用态必须解释原因**：无可缓存来源时，入口要说明「这一集的来源都没有可重新拉取的地址」
   （文案已有 `media.episode.recacheNoRoute`，但现在只在点击后出现，且按钮是 disabled ⇒ 永远点不到）。

## 修复后必须满足（可证伪判据，预先声明）

1. 在分集列表里点「未缓存」那一行/标记，**不离开剧集内页**即可发起该集的缓存（点击次数可数 = 1）。
2. 一个 10 集全未缓存的剧集，**一次操作**把 10 集全部入队，且**只发 1 个 HTTP 请求**
   （可用 CDP 数请求；现状需 10 次点击 + 10 个请求）。
3. 构造「主源 `local` + 备用源 `tg`」的集：其缓存入口**必须可用**。
   **反向证伪**：把判据改回 `canRecacheFromSource(cur.source)`，判据 3 必须 FAIL。
4. 无任何可用来源的集，入口**必须给出「为什么不能缓存」**，不得静默禁用。
5. 不得撤掉 BUG-254 的逐集「未缓存」标注与播放器 `player-nobytes` 遮罩（BUG-149）。
6. 判据 1 / 2 必须在**真实 UI 上验**（BUG-156），不得只看接口返回。

## 待确认（口径）

1. **「切换来源」指的是哪一种？**
   ① 同槽备用源切换（**已有能力** `switchEpisodeSource`，但备用源表当前 0 行、且入口只在有备用源时渲染）；

   与 BUG-103「合并的同一性」是同一类问题）。请指认。
2. **「继续缓存」指的是哪一种？**
   ① 把这部剧集里没缓存的集**补齐**（批量，本档修复方向 2 覆盖）；
   ② 缓存**中断后从断点续传** —— 这与既有裁定冲突：`orig-daemon/src/activity.rs:13-14`
   铁律 4「TG 无真续传（只能任务级重试）」，BUG-257 根因 1 已登记该裁定的边界。
   若指 ②，需先推翻该裁定。
3. **「未缓存」标记点击后是直接缓存，还是展开菜单（缓存 / 切换来源）？** —— 形态决策。
4. **是否要为 §4.1 ① 的仲裁做正式翻转？** 现状是「仲裁说 A、实现做 B」；
   需补一份裁定（「未就绪条目进主网格 + 标未缓存」），否则下一个接手的人会按仲裁改回 A。
