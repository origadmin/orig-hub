# BUG-097: TG 状态是一次性快照 —— 已登录且服务正常，Navi 却不显示、状态永远「启动中」

- 状态: fixed
- 发现日期: 2026-09-21
- 模块: shell
- 严重程度: high

> 本条是 BUG-095（TG 状态建模 + 重试/重启机制，评估已拍板、未实施）的**正在发生的实例**。
> 后端实测全部健康，故障 100% 在**前端状态冻结**，因此可独立于 BUG-095 先修。

## 现象（用户报告，两条同时出现）

1. TG **之前有登录、开关也是开启的**，但左侧 Navi **没有 Telegram 项**。
2. 设置 → 通用里的 TG 状态**永远显示「启动中」**，不随时间变化。

两条都不符合四态模型的任何一种（不可用应置灰、开启正常应显示 Navi、异常应可进并给重试），
即**界面呈现的状态与真实状态脱节**。

## 取证（实测，非推断）

### 后端：全部健康

```
GET 127.0.0.1:9876/api/config   → tg_enabled=true   tg_running=true
GET 127.0.0.1:9877/api/tg/session → {"available":true,"phase":"Authorized","user_id":523058983}
GET 127.0.0.1:9877/api/tg/diag  → {"api_configured":true,"mode":"ready","health":"ok",
                                    "proxy":"socks5://127.0.0.1:7897","session_phase":"Authorized"}
```

**新开一个浏览器页面**跑真实渲染探针（`verify_shots/diag_tg_nav.cjs`）结果：

| 项 | 实测 |
|---|---|
| `nav-tg` 是否存在 | **存在**（nav 项 = downloading / paused / completed / media / **tg** / settings） |
| 页面内 fetch `/api/tg/session` | 200，**3ms**，`phase:Authorized` |
| 页面内 fetch `/api/config` | `tg_enabled=true`、`tg_running=true` |
| console / pageErrors | 仅 favicon 404，无 CORS、无报错 |

→ **后端无病、新页面正常。故障只存在于「已打开的那个页面」的陈旧快照里。**

### 时序：启动竞态

| 进程 | PID | 启动时间 | 二进制 mtime |
|---|---|---|---|
| orig-daemon | 43112 | 09-21 **07:01:57** | 06:59:00 |
| orig-tg | 23860 | 09-21 **17:04:51** | 16:54:01 |

且**冷启动首次**请求极慢（实测 `/health` 3.94s、`/api/tg/session` 首帧近 4s；
一旦就绪后同一端点稳定 4–5ms）——首次 MTProto 握手在请求路径上。

即：应用启动 → 前端 `init()` 立刻探测 → 此刻 orig-tg **尚未监听 9877**（或正在 4s 握手）
→ 拿到 `tg_running=false` + session 失败 → 之后**再也没人刷新过**。

（旁证：17:05 那次 `/api/config` 确实回 `tg_running:false`，此时 orig-tg 刚起来 9 秒、端口绑定未完成；
17:14 再取已是 `true`。所以「启动中」不是谎报，是**快照过期**。）

### 前端：两条状态都只有一次性写入点，无刷新路径

| 状态字段 | 写入点 | 有无刷新 |
|---|---|---|
| `tgRunning` | `useStore.ts:272`（`init()` 读 config）、`:407`（`setTgEnabled` 后） | **无** |
| `tgAvailability` | `useStore.ts:445/450/454`（`refreshTgSession` 内） | 依赖 refresh 被调用 |

`refreshTgSession` 的全部调用点：

- `useStore.ts:279` —— `init()` 里一次（**且被 `.catch(() => {})` 吞掉**，`:279`）
- `MainLayout.tsx:87,93` —— **`useEffect` 依赖 `[tgEnabled, refreshTgSession]`，只在开关翻转时触发**
- `AccountsPanel.tsx:66` —— 账号面板**挂载时**一次（`:66` 同样是 `.catch(() => {})`）
- `lib/tgRetry.ts:62` —— 用户手动点「重试」后

→ **没有定时器、没有 SSE 订阅、没有"orig-tg 起来了"的事件回调。**
只要启动时没赶上，就永久停在 `unreachable` / `启动中`，直到用户手动翻转开关或重启应用。

## 根因

**启动竞态 + 零刷新路径 = 状态冻结。**

1. 启动时序没有握手：前端 `init()` 不等待 orig-tg 就绪，也不重试（相比之下
   `MainLayout.tsx:85-104` 已有一段「开→最多 5×1.5s」的探测，但它**只在开关翻转时**跑）。
2. TG 的两个状态都是**一次性快照**，后端恢复后无人回写。
3. 两处 `.catch(() => {})`（`useStore.ts:279`、`AccountsPanel.tsx:66`）把探测失败静默吞掉，
   连"为什么"都不留（项目明令禁止的失败模式）。
4. 冷启动首次 session 请求 ~4s 落在关键路径上，放大了竞态窗口。

## 修复方向（供实施者参考，本条不含实现）

- **P0-1 给 TG 状态一条刷新路径**：优先**事件驱动**，不得新增轮询（AGENTS.md §5 轮询三律）。
  可用信号：SSE `onOpen`（BUG-090 已有 `setDaemonAlive` 同款写法）、
  daemon 侧"orig-tg 拉起完成"回调、进入 TG 相关面板时补一次（现只有 AccountsPanel 有）。
- **P0-2 启动期不要一次定终身**：`init()` 复用 `MainLayout.tsx:85-104` 那段退避探测
  （把它从"开关翻转"扩展到"启动 + 开关翻转"），让 `tgRunning` 与 `tgAvailability` 在
  orig-tg 就绪后自动转正。
- **P0-3 去掉两处 `.catch(() => {})`**（`useStore.ts:279`、`AccountsPanel.tsx:66`）：
  失败要分类留痕（已有 `lib/tgReason.ts::logTgReason`），不能吞。
- **P1-1 冷启动 4s 握手别挡在 `/api/tg/session` 上**：首次探测可异步预热，
  未就绪时返回"启动中"语义而不是让调用方超时（与 BUG-095 的 `connecting` 态同议题）。
- **P1-2 治本在 BUG-095**：统一状态真源 + 常驻重试入口后，本条的"冻结"将不可表达。

## 验收（建议，供 QA 参考）

必须**真实渲染**，禁止 curl 200 冒充（docs/ACCEPTANCE.md）：

1. 造竞态：停掉 orig-tg → 打开应用（此时 Navi 无 TG、文案"启动中"）→ 再拉起 orig-tg；
   **不做任何用户操作**，等待 ≤10s → 断言 `nav-tg` 出现且文案转"运行中"。
   判据要断 `data-testid` 与真实值，不能只断"三处一致"。
2. 反向证伪：把断言换成"拉起后 Navi 仍不出现"必须 FAIL；换死端口/白屏地址必须 FAIL。
3. `refreshTgSession` 失败路径：不得再出现 `.catch(() => {})`，需可见留痕。
4. 不得新增任何定时轮询（grep `setInterval` 在 TG 相关路径应为 0）。
