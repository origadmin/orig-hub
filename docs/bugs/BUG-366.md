# BUG-366: 下载域顶部两块常驻占位（概览 + 来源切片）挤压列表，用户报「上面死占 2 垃圾」

- 状态: open
- 发现日期: 2026-10-22
- 模块: shell
- 严重程度: mid

## 现象

用户 2026-10-22 复报（原话）：

> 「5. 下载内容占位破坏使用! 上面死占2垃圾!」

`DownloadPanel.tsx:320-360` 在列表**之上**固定渲染两块 `shrink-0` 区块：

1. **概览**（`dl-overview`，`:322-341`）：`入库对象 N · 在传 N · 待处理 N · 已完成 N · 已取消 N` 五个计数，`text-[11px]`；
2. **来源切片**（`dl-source-filter`，`:344-360`）：`全部 / 下载 / TG 入库` 三颗 pill，各带一个计数。

两块都是 `shrink-0` ⇒ 在任何窗口高度下都**恒定占用**首屏纵向空间，把真正的任务列表往下推。当前活动任务为 0 时，概览五个计数全是 `0`、来源切片三个 pill 也全是 `0`，仍然原样占位 —— 用户看到的就是「什么都没干，先吃两块」。

**未修的原因（不擅动）**：这两块是 BUG-298 / M0-T02 / BUG-300 三轮重构里明确落地过的设计（文件头注释：「顶层之上再给**概览口径**（在传 / 待处理 / 已完成 / 已取消 的对象数）—— 这就是『笼统的数据』」）。它们是**有编号裁定的设计件**，不是无意残留。用户这次报的是「占位破坏使用」，属于对既有裁定的否定，但**否定的范围没说清**（是撤掉、是折叠、还是改成随内容有无条件渲染）——三种解读的改法与回归面完全不同，猜一个就退回到 BUG-320「三次诉求只改样式不改结构」的老路。

## 待用户裁定（三选一，附各自代价）

| 选项 | 做法 | 代价 |
|---|---|---|
| A. 全撤 | 两块都删，列表置顶 | 失去「笼统的数据」总览；BUG-300 的复报修正被回退，须新开登记 supersede |
| B. 空态收起 | 有内容才渲染，全 0 时不占位 | 保留能力；但「什么时候出现」本身是个新规则，要定阈值 |
| C. 折成一行 | 两块合并为一行紧凑条 | 占位减半仍占；且改的是 BUG-298 定档的呈现 |
