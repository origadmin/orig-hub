# BUG-219: 播放读量爆炸 + 卡顿：no-store 误改把 6× 预读冗余放大到服务端（orig-tg /raw）

- 状态: in_progress（no-store 已回退源码；rebuild+重启进行中；根因已定位为「用户侧回归 + 基线卡顿待诊」）
- 发现日期: 2026-10-08
- 模块: engine
- 严重程度: high
- 排期: 2026-11-10

## 现象

用户实测两条：
1. 基线（`max-age` 允许缓存）即「缓存进度条很大一截，但播放仍加载且卡顿」。
2. 改成 `no-store` 后「**比以前更卡了**，且一个 <100MB 的视频，读取数据量相当于好几个视频的大小」。

第 2 条说明：`no-store` 不是修复，是**回归**。

## 根因（已读源码核实，高置信）

`serve_local_file`（`download-engine/crates/orig-tg/src/routes.rs:3603`）的响应**刻意**带 `ETag` / `Last-Modified`（`:3716-3717`）。
同文件 **L3601 注释明文**：「Chromium 媒体缓存据此复用已取字节，**缺了就会重复下载**」——即该端点的设计**依赖** HTTP/媒体缓存复用已取字节。

而 **L3021-3026 注释**实测：Chromium 对「快源 + 大文件 + 可拖」有固有投机预读，双读线程各自预取 ~10MiB 后自行 `ERR_ABORTED`，
造成 **6.2x / 5.8x / 6.4x 冗余**；A/B 证明这与服务端 Range 语义无关、调块大小无效（EOF/8MiB/32MiB 请求数 18/28/20、冗余 6.2/5.8/6.4 无差）。

- 基线（`max-age` 允许缓存）：这 ~6× 冗余被**本地缓存吸收**——重复区间命中 `ETag` 复用，服务端只读 ~1×，卡顿低。
- `no-store`（`:3718` 误改）：关掉 HTTP 缓存 ⇒ 直接废掉 L3601 的复用机制 ⇒ 6× 冗余每次都**回源服务端**重新 `open` + `seek` + 首块 TTFB
  ⇒ 服务端读字节涨到 ~6×、每次重取多一次 TTFB ⇒ 正是用户「读量 = 好几个视频」+「比之前更卡」。**no-store 是回归，不是修复。**

## 已排除 / 已纠正

① **卷级磁盘 I/O 争用**：用户证伪「速度和磁盘无关」；同盘压测（播放 + 同盘大文件写）使 `/raw` 读降 36% 但播放端未复现 stall。
② **「max-age 让浏览器把整段视频落盘到 HTTP 缓存 ⇒ 磁盘争用卡顿」**：本档上一版核心假设，现**证伪**——若落盘是坏事，关掉它（`no-store`）应「更顺」，
   但实测「更卡 + 读量暴涨」，反证缓存当时在**吸收**冗余、是在帮忙。故该假设撤回，根因改写为上面的「复用机制被废」。
③ 下载缓存 `.part` 落盘：与播放读路径不同文件，用户已排除。
④ 前端播放期落盘：`VideoPlayer.tsx` / `decodeHealth.ts` 进度条 DOM 直写、无写盘，已查。
⑤ `delivery_bps` 限速：环回默认返回 0（不限速，BUG-199）。
⑥ 非整数倍速 judder：30fps 源 2x/4x 为整数比，无关。

## 遗留（基线卡顿，独立于本次回归，no-store 之前就存在）

基线（`max-age`）下用户已报「缓存进度条大但仍卡」。该卡顿**不是**本次 `no-store` 回归，需另诊。首要嫌疑：
- **HEVC 不被解时的「缓冲 → abort → 重取」循环**（`tauri-shell/src/components/media/VideoPlayer.tsx:511-513` 注释：20s / 97–137 请求 / GB 级无效 IO）。
  若内容确为 HEVC 且客户端无硬件解码，则无界重读 = 读量爆炸的另一来源；自动切 `compatSrc`（服务端 H.264 转码 /stream）本身也产生重复大请求。
- 次嫌疑：6× 冗余在拖拽 / 重缓冲边际上的开销。
- 另：`/stream` 冷启动客户端断开 → 杀 ffmpeg + 清 `.part` → 下次从头重转（`routes.rs:3338+`），仅 HEVC 走 /stream 时触发，是又一「重头再读」点。

## 修复 / 处置

- 已回退 `no-store`（`routes.rs:3718` 恢复 `public, max-age=31536000`），保留 `ETag` / `Last-Modified` 复用机制。rebuild + 重启进行中。
- 待诊基线卡顿：需用户给会卡 item id + 是否 HEVC / 已下完；或查 HEVC 自动转码兜底与 /stream 断流续转。

## 修复后必须满足（可证伪判据）

1. `curl -I /api/media/items/{id}/raw` 现回 `cache-control: public, max-age=31536000`（回退确认）。
2. 用户真实内容读量回落到 ~视频本身大小（不再数倍）。
3. 基线卡顿根因定位并修复后，2x/4x 卡顿消失：以 `waiting` 事件 / `currentTime` 推进速率判 stall，不用被「4x 显示上限正常丢帧」混淆的 `droppedVideoFrames`。

## 验证进展（2026-10-08）

- 无效浏览器基准（错 50fps 代理内容 / headless 关 MediaSuspend / 测裸 `<video>` 而非真实应用 / headless Edge 无 loopback）已弃用。
- **no-store 实验结论翻转**：原以为「关掉 HTTP 缓存落盘 = 消除卡顿」，用户真实应用实测证明反效果——读量暴涨数倍、更卡。
  直接证据链：L3601（设计依赖 ETag 复用）+ L3021-3026（固有 6× 冗余）+ 用户「更卡 + 读量数倍」⇒ `no-store` 废掉复用、把 6× 冗余全压回服务端。
- `no-store` 已回退源码（`:3718` 恢复 `max-age=31536000`）；`cargo build --release` 重启 dev 栈进行中，完成后以判据① curl 复核。
- 判据②/③（读量回落、基线卡顿消失）须在**真实 Tauri/WebView2 应用**中验证（其 loopback 正常；headless 沙箱不可测）。
