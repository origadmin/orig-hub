# BUG-321: 引擎栈非用户操作地整树消失（daemon+orig-tg 一起没），且无任何退出痕迹可查

- 状态: fixed
- 发现日期: 2026-10-16
- 模块: engine
- 严重程度: high

## 现象（用户原话，2026-10-16 01:16）

> 「服务全挂了,什么原因? 我都没有验证呢. 还是说你需要先修?」

实测端口：`19786 NOT-LISTENING`、`19787 NOT-LISTENING`、`5180 LISTEN`
（vite 活着）。用户只是想打开界面验收，撞上一个空栈 —— 界面表现与
BUG-176/BUG-318 同一类假象：`Failed to fetch` + 计数 0，看起来像「数据丢了」。

同型事件已在 2026-10-15 一天内发生两次（20:58、23:4x），此前只记在备忘里，
**从未登记**（违反登记纪律：用户提出的问题必须先入册）。

## 根因

### 1. 引擎进程挂在「启动它的那个控制台」上（直接机制）

`scripts/dev_services.py:96` 起 daemon 时只给了 `CREATE_NEW_PROCESS_GROUP`：

```python
creationflags=getattr(subprocess, "CREATE_NEW_PROCESS_GROUP", 0),
```

`CREATE_NEW_PROCESS_GROUP` 只挡 `CTRL_C`，**不挡 `CTRL_CLOSE_EVENT`**；子进程仍
继承父进程的控制台。父控制台关闭时，Windows 向该控制台上所有进程广播
`CTRL_CLOSE_EVENT`，默认处理即终止进程。orig-tg 是 daemon 的子进程，
于是**整树一起消失**。

旁证（决定性）：死的正好是「由 AI 的 Bash 会话起的进程组」，
用户自己起的 vite（node, pid 45864）在**同一次事件里存活**。

### 2. 栈没有监督者，消失了不会自己回来

- daemon 侧只有 `tg_supervise`（管 orig-tg），**无人管 daemon 自己**；
- 引擎下载行纯内存（`orig-daemon/src/state.rs:198`），回来就是空的 ⇒
  与 BUG-319 叠加成「用户观感＝数据丢失」。

### 3. 消失了也查不出为什么（证据黑洞，本轮一并修）

`stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL` ⇒ daemon 的 panic/退出
信息直接丢进黑洞；本次查 Application/System 事件日志（近 3h，Level 1/2）
**零命中**，只剩「不知道谁杀的、也不知道它自己退没退」。

### 排除项（均已实证，不是原因）

- 端口保留区间：`netsh` 排除区间为 4222/5357/9528–10056/13193–13292/28385/28390/
  50000–50059，**不含 19786/19787**（旧的 9877 区间问题不涉本号）；
- 二进制被覆盖：orig-daemon.exe 最后写入 10-15 21:40、orig-tg.exe 10-15 19:04，
  事发时无构建活动。

## 复现

1. `python scripts/dev_services.py` → 栈健康（19786/19787）；
2. 结束/回收启动它的那个控制台会话（含上下文压缩导致的会话重启）；
3. 再探端口：两个引擎端口全 NOT-LISTENING，vite 仍在；
4. 查事件日志：无任何相关记录。

## 修复

1. **脱离控制台启动**：`creationflags` 加 `DETACHED_PROCESS(0x8)`，
   daemon（及它 spawn 的 orig-tg）不再挂在启动者控制台上；
2. **退出痕迹落盘**：daemon 的 stdout/stderr 追加写入
   `%TEMP%/orighub-dev-services.log`（append、行缓冲），下次再消失有据可查；
3. **栈监督者**：`--supervise` 守护循环（自身也 DETACHED 自举），每 5s 探活，
   栈掉则拉回，并把 `DOWN t=<ISO>/RECOVERED pid=..` 写进同一份日志 ——
   既解决「不自己回来」，也把下一次消失变成可定位的时间戳证据。

## 关联

- BUG-319：引擎下载行无持久化（放大本号的用户观感＝数据丢失）。
- BUG-318：源不可用时 UI 把「取不到」渲染成「没有」—— 栈没了时表现相同。
- BUG-176：同一种假象的上游登记。

⇒ 这同时反证了 01:16 用户看到的全挂：**栈消失后没有任何东西把它拉回来**
（当时 Tauri 壳也不在跑，否则 `ensureDaemon()` 会兜底）。

验牙过程中修掉两个会让断言说谎的坑（均已还原并复验）：

1. MSYS 把 `//PID` 转成空操作，**监督者其实没被杀**，导致第一次「验牙」误判为
   「没有监督者也能自愈」—— 改用 PowerShell 直接 `taskkill /PID` 才真杀掉；
2. A1 与监督者的启动竞态被读成「栈没了」（A1 FAIL 而 A3 `/health` 200）——
   脚本改为先等栈就绪（≤25s）再断言。

A6b 单独设一条断言，就是防历史日志把 A6 喂成恒绿（累计计数永远 ≥1）。

### 脱离关系（父进程实证，01:26）

```
2800  python.exe      parent=14964(DEAD)      alive=True   <- 父已死，自己还在
46252 orig-daemon.exe parent=2800(python)     alive=True
40672 orig-tg.exe     parent=46252(orig-daemon) alive=True
```

父进程 14964（起监督者的那个会话）已 DEAD 而监督者存活 = 脱离成立；
旧实现下这两条引擎进程会跟着一起没。

### 自愈后真实栈态（01:26）

- `GET :19786/health` → `200 {"status":"ok"}`；
- `GET :19787/api/tg/diag` → `available:true, mock:false, session_phase:"Authorized",
  port:19787, unavailable_reason:null`；
- `%TEMP%/orighub-dev-daemon.log` 落盘生效（此前是 DEVNULL）：
  `orig-daemon listening on http://127.0.0.1:19786` / `orig-tg plugin started`。
- `--stop` 顺序实证：先 `taskkill /PID <supervisor> /T /F`（连栈），再停 daemon pid 兜底
  ⇒ 输出 `[dev-services] stopped supervisor pid 2800` / `stopped pid 52404`；
  顺序反了会被监督者 5s 内拉回来，表现为「停不掉」。

### 未完成（不冒充已解决）

- 「谁/什么发的 CTRL_CLOSE_EVENT」只能由下一次 DOWN 时间戳对账定位（监督日志已具备）；
  本号修的是**消失后必回来 + 消失有据可查**，不是消灭触发源。
- 栈回来了但**引擎下载行仍为空**（纯内存，BUG-319 的地盘）——本号不接管。
