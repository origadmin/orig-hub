# BUG-212 倍速下「解码吃力」误报：把呈现丢帧错归因为解码不足

- 状态: fixed
- 发现日期: 2026-10-08
- 模块: shell
- 严重程度: mid

## 现象

用户以 2x / 4x 倍速审看视频时，界面弹出「解码吃力：画面在丢帧，调低播放速度会明显更流畅」
（i18n 键 `tg.decodeStrained`，`tauri-shell/src/i18n/locales/zh-CN.json:318`；渲染于
`tauri-shell/src/components/media/VideoPlayer.tsx:651-655`）。

实测（headless Edge + CDP，脚本 `tauri-shell/verify/verify_playback_rate_profile.cjs`，
产物落 `tauri-shell/verify_shots/rate_profile/`）：

- 1x 丢帧 **0%**（提示不出现）；**2x 丢 10–23%**、**4x 丢 ~53%** —— 「解码吃力」在 2x / 4x **必现**。
- 但**投递与解码均无异常**：10s 窗口缓冲始终领先（472 约 1200s、607 / 598 约 17–53s），
  `waiting` / `stalled` 全 0，`readyState` 恒 4；解码器按需求出帧，`totalVideoFrames` 增量
  恰为 30 / 60 / 120fps（等于**源 30fps × 倍速**）。
- **不是像素吞吐**：607（480×852）@4x 丢 53.7% vs 598（720×1280，像素 2.25×）@4x 丢 53.0%，几乎相同。

⇒ 丢帧是**真实的**，但**归因是错的**：把「倍速下呈现速率超刷新率」这一物理必然，
误报成「解码能力不足」。

## 根因

判据位置 `tauri-shell/src/lib/decodeHealth.ts:144-178`：

- 信号 = `getVideoPlaybackQuality().droppedVideoFrames` 增量；每 500ms 采样（`:39`），
  丢帧速率 > `DROP_PER_SEC`（`:45`，值 3）连续 4 拍（`STRAIN_STREAK` `:41`）= 2 秒 ⇒ 置 `strained`（`:176`）。
- **`:168` 那行 `const severe = delta / (dt / 1000) > DROP_PER_SEC` 完全没有倍速感知** ——
  它把「**呈现**丢帧」当成「**解码**丢帧」。

倍速下的呈现速率 = 源帧率 × 倍速。源帧率实测（ffprobe）：472 = HEVC 720p **60fps**；
607 = H.264 480×852 **30fps**；598 = H.264 720×1280 **30fps**。⇒ 30fps 源在 2x 需 60fps 呈现、
4x 需 120fps 呈现，超过显示器刷新率（60Hz）时按比例丢帧是物理必然，与解码能力无关。

实现侧无任何按倍速的适配：倍速档 `RATES = [0.5,0.75,1,1.25,1.5,2,3,4]`
（`tauri-shell/src/components/media/VideoPlayer.tsx:77`），仅 `v.playbackRate = rate`（`:331-339`），
**无按倍速的画质 / 帧率适配**。

**正解判据应是「有效倍速」**：`ΔcurrentTime / (Δt × playbackRate) < 1` 表示管线被饿死
（真解码 / 投递不足）；它不受呈现丢帧污染，是区分「真卡」与「呈现上限」的正确信号。

**范围说明**：`decodeHealth.ts:133-136` 的 `unsupported`（`videoWidth===0` 持续 3s）是**另一条判据**，
与丢帧无关，**不在本档范围**。

## 复现

1. 启动壳，打开 30fps 源条目（607 或 598）。
2. 切到 2x 或 4x 倍速。
3. 约 2 秒后出现「解码吃力」提示（2x / 4x 必现；1x 干净、不出现）。
4. 脚本复现：`PROBE_ITEM=<id> node tauri-shell/verify/verify_playback_rate_profile.cjs`
   （`BROWSER=msedge`），逐 1s 采样 presented / dropped / 有效倍速。

## 修复

**应改成什么样**（具体代码由实现方定）：

1. 把 `strained` 判据从「呈现丢帧速率」改为「**有效倍速**」：用
   `ΔcurrentTime / (Δt × playbackRate)` 衡量管线是否被饿死（`< 1` = 真解码 / 投递不足）。
2. 呈现丢帧（`droppedVideoFrames`）在倍速下是刷新率物理上限，**不得单独触发**「解码吃力」；
   若确需保留丢帧信号，须先按 `playbackRate` 归一（呈现需求 = 源帧率 × 倍速），
   或在 `playbackRate > 1` 时抑制该提示。
3. 文案随之修正为**可行动且不误导**：不得再把「刷新率物理上限」说成「解码不足」、
   建议「调低播放速度」。
4. **不得影响** `unsupported` 判据（`decodeHealth.ts:133-136`）与 BUG-207 的停载遮罩行为。

## 验收证据

**已修复并验收通过**（2026-10-08）。修复提交 `49d85ba`（判据改为有效倍速）+ `ffd1b4c`（登记已知边界注释）。

验收脚本已入库：`tauri-shell/verify/verify_playback_all.cjs`（提交 `33f87d7`）。**一条命令、一个 headful 浏览器、单会话复用同一 page、全程打印阶段进度**，30/30 判据 PASS、exit 0、耗时 4m18s。产物：`tauri-shell/verify_shots/playback_all/`（`playback_all.json` / `playback_all.md` + 截图）。

浏览器形态自证：UA 不含 `HeadlessChrome`（`…Edg/154.0.0.0`），rAF 实测刷新率 60.5Hz。

逐条结果（对应修复前预先声明的判据）：

1. **误报消除（2x）**：607（H.264 480×852 30fps）@2x，呈现丢帧 **23.6%** 期间提示**未出现** ⇒ PASS。
2. **1x 干净**：由独立实测覆盖（607@1x 丢帧 0%、有效倍速 1.0、提示不出现、缓冲领先 30+ 秒）。按产品决策人 2026-10-08 指令，验收脚本**不再重复测 1x** —— 1x 不是空白，重跑是重复劳动。
3. **反向证伪（真饿死仍可判）**：运行时对 `HTMLMediaElement.prototype.currentTime` 打桩注入「管线饿死」，有效倍速降到 **0.196–0.203**，提示**出现**（真阳性）；自动还原后 **≈1.5s** 撤销 ⇒ PASS。证明改的是**判据**而非把提示关掉。
4. **高倍速不误报**：472（HEVC 720p 60fps）@4x，呈现丢帧 **75.3%**（≈ 1 − 60/240）时提示**未出现** ⇒ PASS。
5. **回归（`unsupported` 判据未受影响）**：运行时注入 `HTMLVideoElement.prototype.videoWidth = 0`，BUG-207 停载遮罩**出现**；还原后 `vwPatched=false` ⇒ PASS。
6. **脚本**：`tauri-shell/verify/verify_playback_all.cjs` 覆盖上述场景并 EXIT 0（30/30 PASS）。

**工作区未被污染自证**：打桩前后 `tauri-shell/src/lib/decodeHealth.ts` 与 `tauri-shell/src/components/media/VideoPlayer.tsx` 的 `sha256` 一致；`tauri-shell/src` 与 `download-engine` 的 `git status --porcelain` 前后一致。

**已知边界（如实登记，未处理）**：`waiting` / `stalled` 也走 `rebase()`，而 `rebase()` 会重设时间轴基线并进入 1.5s 预热；若「饿死」表现为间隔 < 1.5s 的高频间歇 stall，主判据可能凑不满 `STRAIN_STREAK` 拍而**漏报**（属漏报、非误报）。已实测 2x / 4x 下 `waiting` / `stalled` 均为 0，该路径不触发；修它需把「重置丢帧基线」与「重置时间轴基线」拆开，会触碰 BUG-166 的既有裁定，故留待将来一并重新裁定。代码注释已登记。

**未覆盖（如实声明）**：判据 3 的「人为低吞吐」用**运行时打桩**制造（`currentTime` 增量压到 20%），而非真实限速投递 —— 它足以证明判据是活的，但不等于验证了真实网络饿死场景下的表现。
