# BUG-162: `delete_media_item` 在破坏性动作之后才中止 —— 500 文案自称「nothing was deleted」却已把字节删掉

- 状态: fixed
- 发现日期: 2026-09-23
- 模块: engine
- 严重程度: mid
- 档位: standard

## 现象

删除一个 `source=tg` 的媒体条目、且其 TG `downloaded` 标记**清除失败**时，接口返回：

```
500 {"error":"cannot delete media item 7: the tg downloaded flag could not be cleared \
     (see server log), so the entry would reappear on the next sync; nothing was deleted"}
```

但实际后果与文案**自相矛盾**：

- 条目仍在（随后 `GET /api/media/items/7` 仍 200）—— 与「nothing was deleted」相符；
- 可该条目在**下载目录内**的 777 字节**已经被删除** —— 与「nothing was deleted」**相反**。

即：**中止点落在破坏性动作之后**。函数先 `remove_file`（删字节），**才**去清 TG 标记；
标记清不掉时它才返回 500 —— 此时字节已经没了，属于「报错声称什么都没删、实际删了一半」。

对照实验（排除归因于别处）：非 tg 来源 + 同样垃圾 ref → `200 {"removed":1}`。
说明 500 **专属于**「清 TG 标记」这条分支，而非「带 ref 就拒删」。

附带一个窄影响面：`source=tg` 且 `ref` 不可解析的条目**永久删不掉**
（每次删除都在标记判定处 500，条目永远在）。该形态只能由通用 import API 造出，
生产 ingest 恒写 `chat:msg`，故实际数据面很窄。

## 根因

`download-engine/crates/orig-tg/src/routes.rs` 的 `delete_media_item`（修复前 `:2159` 起）：
**破坏性动作 `std::fs::remove_file(...)`（约 `:2130`→修复前）先执行，随后才调用
`crate::cache::reset_tg_flag(...)`（约 `:2155`→修复前）清除 TG 标记**；后者失败即返回 500，
但字节已经没了。

顺序是反的。清除标记是**唯一可能中止**的检查点，它必须排在破坏性动作**之前** ——
函数已经是「失败即中止」的语义（BUG-135 定的规则），但把中止点放在了破坏性动作之后，
于是「中止」变得没有意义：字节已经删了。

> 修复后的精确行号见下方「修复」节；本节括注的是修复前位置，已随修复位移。

## 复现

**构造「TG 标记清除失败」的条件**（QA 用的办法，二选一）：

1. **`ref` 不可解析 + `source=tg`**（确定性、零依赖，推荐）：造一条
   `source='tg'` 但 `ref` 不是 `"<chat>:<msg>"` 形态的条目 —— `reset_tg_flag`
   在 `parse_tg_ref` 处直接返回 `false`（`cache.rs:700-706`）。
   该形态可由通用 import API 写入（`POST /api/media/items` 不受 ref 形态约束）。
2. 让 `store.clear_downloaded` 失败（DB 层错误）—— 不易稳定构造，仅作旁证。

**修复前后三态差异**（同一构造，逐项对比）：

| 观察量 | 修复前 | 修复后 |
|---|---|---|
| `{http_code}` | `500` | `500`（不变） |
| 响应体 | `{"error":"...nothing was deleted"}` | `{"error":"...nothing was deleted"}`（不变） |
| **盘上字节是否还在** | **否 —— 777 字节已被删**（文案说谎） | **是 —— 一字节未删**（文案为真） |
| 条目是否还在（DB） | 是 | 是 |

即：修复**只**把「盘上字节是否还在」这一态从「否」纠正为「是」，使 500 文案与事实一致。

最小复现（单测版，无需 HTTP/前端）：见「验收证据」的
`routes::tests::delete_media_item_aborts_before_deleting_bytes_when_tg_flag_cannot_clear`。

## 修复

**最小外科式改动**：在 `delete_media_item` 内**把「清 TG `downloaded` 标记」提到所有破坏性
动作之前**，标记清除失败时**立即**返回 500（此时一字节未删）；随后才执行
「删下载目录内字节」这步破坏性动作。

- 文件：`download-engine/crates/orig-tg/src/routes.rs`（唯一实现文件）
  - 函数文档注释新增 BUG-162 说明（先判标记、再删字节）。
  - 函数体内顺序对调：`reset_tg_flag(...)` 判定块（现 `:2188`）移到
    `std::fs::remove_file(p)` 块（现 `:2202`）**之前**。
  - **语义零变化**：仍复用 `cache::reset_tg_flag`（唯一实现，与清字节那条链同一套规则）；
    「删字节失败不中止、只 warn + 如实带 `bytesRemoved:false`/`bytesError`」这条既有约定
    原样保留。
- 新增两条单测（见下），直接钉住「顺序」这一契约。

修复后契约：**500 分支下盘上一字节未删、DB 行原封不动，文案与事实一致**；
正常删除路径（标记可清）仍然**真的删掉字节**。

### `source=tg && ref 不可解析` 形态的分类结论

在本修复后，该形态**仍是 500**（不是 4xx）：`reset_tg_flag` 对不可解析 ref 返回 `false`，
位于「失败即中止」的第一检查点，故仍走 500 分支 —— 但此刻**不再破坏任何字节**，
语义已从「报错却删了一半」收敛为「干净地拒绝，什么都不动」。

至于「它是 4xx（语义化拒绝）而非 500（服务端错误）、且因此**永久删不掉**」——
这**属于另一个缺陷**（数据形态校验/错误分级），**不在本修复范围内**，已在此登记备注
（见「关联」），按项目要求**不顺手改**。

## 关联

- **BUG-135**：本函数的「两处失败不再被 `let _ =` 吞掉」规则（清标记失败→中止；删字节失败
  →不中止但如实报）。本 BUG 是 BUG-135 修复中**遗漏的顺序问题**：中止语义正确，但中止点
  晚于破坏性动作。
- **BUG-109**：`cache::reset_tg_flag` 的「失败即如实报错」来源（不再静默吞掉）。
- **BUG-029 / BUG-051**：清标记 vs 删字节的联动来历（「删了又回来」/ 孤儿文件）。
- `cache.rs:695` `reset_tg_flag`（唯一实现，被本函数与清字节链共用）。
- **待决（另一个缺陷，未改）**：`source=tg && ref 不可解析` 的条目永久删不掉，
  且被归为 500（服务端错误）而非 4xx（客户端语义拒绝）。建议另行登记：对
  「`source=tg` 但 ref 非 `chat:msg`」的形态在**入口**做校验/分级，而非在删除时才发现。
