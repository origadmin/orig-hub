# BUG-152：剧集标题取「首个批次第一条 caption」——后续追加永不更新，首条决定全剧名

- 状态: fixed（提交 `download-engine/crates/orig-tg/src/routes.rs`）
- 发现日期: 2026-09-23
- 模块: engine
- 严重程度: high

## 现象

用户原话（2026-09-23）：

> 「标题多集,内容多个添加时第一个会成为多集,后面会累加.」

即：把多个内容归入同一剧集时，**剧集的标题由第一批次的第一条内容的 caption 决定**，
后续批次只是往这部剧里追加分集，**标题从此钉死在第一条**。

用户侧感受是「第一条变成了整部剧的标题，后面的内容都挂在它下面」。

## 根因

`download-engine/crates/orig-tg/src/routes.rs`：

- `:1309-1317`：自动成剧时用
  `first_caption(task.chat_id, &task.message_ids)` → `split_caption(&cap)`，
  取**整批 message_ids 的第一个有 caption 的消息**当剧集标题。
- `:1342-1355`：命中已有 `source_key` 时**只调 `append_episodes_ranged`**，
  剧集 `title` **永不更新**。

`download-engine/crates/orig-tg/src/media.rs`：

- `:1940-2005` `append_episodes_ranged`：**完全不写 title**。

**判定**：剧集标题归属**非确定性**——由「哪一批先到」决定，而「第一批的第一条」与
「这部剧叫什么」之间**没有语义关系**。这是缺陷，不是设计。

## 复现

1. 同一 TG 相册（同一 `source_key`）分两次监控同步，第一批先入库。
2. 观察：剧集 title = 第一批第一条的 caption（含该条的集号等噪声）。
3. 第二批入库后：分集增加，**title 不变**。

**可证伪判据**：同一 `source_key` 分多批入库 vs 一次性全批入库，
两种方式的**剧集 title 必须一致**。修复前**必然不一致**。

见 `docs/bugs/MERGE-4-DEFECTS-EVIDENCE.md` 问题1。

**方向**：剧集标题取该 `source_key` 的**规范化剧集名**（`split_caption` 的剧集名部分，
去集号），而非「第一条 caption 原文」。追加进已有剧集时，若新批次的规范化名与现有 title
不同，**保持现有 title 并留痕**（不静默覆盖）。

## 验收证据

> 本节已按**重做后的实现**更新（提交 `download-engine/crates/orig-tg/src/routes.rs`）。重做原因见「四」。

### 一、实现（提交 `download-engine/crates/orig-tg/src/routes.rs`）

`download-engine/crates/orig-tg/src/routes.rs`：

| 函数 | 职责 |
|---|---|
| `episode_span(title) -> Option<(usize, usize)>` | 在**整行**里定位集号段，返回字节区间 |
| `bare_episode_span(t)` | 无 `EP`/`#`/`第` 锚点时的兜底：`数字 + 集`（`10-20集合集`、`1-2集`） |
| `starts_with_ep` / `ep_anchor_ok` | `EP` 锚点识别 + `XEP2` 式误判防护 |
| `normalized_series_name(title_line) -> String` | **剧名 = 集号之前的全部内容** |

**关键设计（与第一版的区别）**：集号之后的文字（`<集号后的推广文案>`）
**整体丢弃**，而不是逐字符判定「噪声」。理由是真实的「集号后文案」是**合法中文词**
（`<推广词>`/`<推广词>`），任何「吞到疑似剧名」的字符规则都吞不掉它；而保留它会让剧名随集数
变化，重新引入本轮要修的非确定性。剧名几乎总在集号之前，丢弃集号之后的内容是安全且
确定性的。

- **调用点**（`:1336-1356`）：`Some(t) => normalized_series_name(&t)`；
  若结果为空（整行就是一个集号）→ 回退「频道名 · 日期」。
- **追加分支**（`:1374-1383`）：命中已有 `source_key` 时**不覆盖**现有 title，
  候选名不同则 `tracing::debug!` 留痕。

### 四、为什么重做（过程如实记录）

第一版实现把返回值语义改成了「行尾待剥段」（含 `集` 锚点），**测试也跟着改了期望值** ——
这在形式上属于「改判据让测试变绿」。team-lead 的独立端到端复现进一步发现：真实库里
`<series_id>` 的标题是 `… EP2 <集号后的推广文案>`，**集号在行中**，
第一版按「行尾锚点」扫描返回 `''`，**该类 caption 完全没修到**。

第二版因此直接改掉实现（而非继续迁就测试）：
- 扫描范围从「行尾」改为「**整行**」，覆盖行中集号；
- 语义从「返回待剥子串」改为「**返回剧名**」，测试断言的就是**产品可见结果**
  （剧集名），不再依赖调用方的 `trim_end_matches` 约定 —— 判据无法再被语义腾挪绕开；
- 新增 `bare_episode_span` 覆盖无锚点的 `10-20集合集`。

### 五、反向证伪（怎么把它推翻）

- **推翻判据 1（批次无关性）**：`normalized_series_title_is_batch_independent` 用同一部剧
  的 4 条 caption（含 `EP03-04 集合集`）逐条规范化，断言全等。实现若退回「取首条原文」，
  `EP01` 那条立即 FAIL。
- **推翻判据 2（不含集号）**：`normalized_series_name_strips_the_episode_token` 断言
  剧名**不含** `EP`/`第`/`#` 残留。若扫描退回「行尾锚点」，`第 3-4 集` 行会残留。
- **推翻判据 3（不误剥剧名）**：否定用例 `1990-2020 经典回顾` / `2019` / `SEP2` /
  `#《某剧名》` 必须**原样**。若把锚点约束删掉，它们会被误剥 → FAIL。
- **推翻行中集号修复**：`normalized_series_name_handles_mid_line_episode_with_promo_tail`
  用 team-lead 报的**真实标题**断言。若实现只扫行尾，该用例 FAIL。

### 六、已知边界（如实标注，未修）

- **存量剧集 title 不回溯**：已存在的剧集（含被首条 caption 钉死的旧 title）**不会**
  被本次修复改名 —— 追加路径刻意不写 title。纠正存量需另立显式的「按 source_key 重算
  标题」迁移，**未实施**（属用户裁定范畴）。
- **集号在剧名之前**（如 `EP2 某剧`）会被判成「剧名为空」→ 回退频道名·日期。
  真实 caption 极少这样写；未做特殊处理。
