# BUG-389: 服务全灭时界面只说「Telegram 正在启动」——不可达被渲染成启动中

- 状态: fixed
- 发现日期: 2026-10-23
- 模块: shell
- 严重程度: high
- 排期: 2026-11-10

## 现象

用户 2026-10-23 03:45 报：「Telegram 正在启动 / 全挂了」。

实测（三层取证）：

| 层 | 读数 |
|---|---|
| 端口 | 19786 = 000、19787 = 000（5180 vite 仍 200） |
| 进程 | `orig-daemon`、`orig-tg` **均不存在**（PowerShell 实测） |
| 日志 | daemon 生命周期日志止于 02:08 redeploy done，**无任何退出/崩溃记录**；`errors.log` 无新增 |

即：dev 栈被**外部终止**（非代码崩溃、非本次改动所致）。数据未受影响
（库行数与 activity 148 条在起栈后照常返回）。

## 根因

「正在启动」是**唯一**的降级文案：无论 daemon 不可达、TG 插件未起、
还是真的在启动，界面都写这一句。用户因此无法区分「等一等就好」与
「服务没了」，进而把它读成「数据全没了」（上一轮误会的直接来源）。
违反铁律「取不到 ≠ 没有」：`/api/config` 拿不到必须显式说「不可达」，
不能折叠成「正在启动」。

## 修复

降级态按可核原因分流（至少三态，文案各自不同）：

1. 探针不可达（daemon/19786 无响应）→ 「本地服务未运行」+ 起栈指引；
2. 探针可达但 TG 插件 down → 「Telegram 插件未运行」（含 lastError）；
3. 插件 running 但会话未就绪（session 探针未通）→ 才允许写「正在启动」。

三态都带**可复制的诊断串**（与 BUG-384 同一落地方式）。

## 验收证据
服务不可达不再被渲染成「正在启动」：三态分流（不可达 / 插件未运行 / 启动中），
不可达时直出原因并带可复制的诊断串（复用 BUG-384 的结构化错误呈现）。

落点 `tauri-shell/src/components/TgPanel.tsx`、`tauri-shell/src/lib/tgReason.ts`。
反向证伪：把分流改回单一「正在启动」文案，全灭时界面重新说谎。
