# BUG-446: release 壳打开即无响应（Application Hang），WebView2 进程从未创建

- 状态: open
- 发现日期: 2026-10-27
- 模块: shell
- 严重程度: critical
- 排期: 2026-11-03

## 现象

双击 `orig-hub.exe`（release）后窗口标题出现（`Orig Hub`），但界面不可交互：Windows 判定
`Responding=False`，事件日志记录 `Application Hang`（ID 1002，`HangType=Unknown`，
`TerminationTime=10`）。用户表述：「应用打开就卡死」。

**daemon 侧是正常的**：壳调用 `ensure_daemon` 后 `orig-daemon.exe` 在 19786 起来并能应答，
但前端界面始终没有内容。

## 取证（逐条可复核）

| 判据 | 观测 |
|---|---|
| 窗口响应性 | `Get-Process orig-hub → Responding=False`；`MainWindowTitle=Orig Hub`；CPU 累计 0.7s、内存 35MB（无死循环特征，是阻塞等待） |
| 系统事件 | `Application Hang` id=1002，`AppName=orig-hub.exe`，16:57:44 |
| WebView2 进程 | `msedgewebview2.exe` 的 `--user-data-dir` 只有 clash-verge 与 SearchHost，**没有任何属于 `com.origadmin.orighub\EBWebView` 的实例** |
| 壳侧模块 | `EmbeddedBrowserWebView.dll`（wry）**已加载** ⇒ 进入了 webview 创建流程，但 `msedgewebview2.exe` 未启动 |
| 前端代码 | 同一份前端在 vite(5180) 下 `verify_ui_render.cjs` **24/24 PASS**（导航、context-bar、TG 面板均真实渲染）⇒ 前端无责 |
| 资源产物 | `dist/index.html` 引用的 `assets/index-Boo7xNRG.js`、`index-CqktJKIg.css` 均存在，引用一致 |
| 构建产物 | `sync-sidecars.sh --check` 通过；壳与 sidecar 同为 10-27 |

## 已排除

1. **不是本次构建引入**：从 `bundle/nsis/Orig Hub_0.1.0_x64-setup.exe`（10-20 06:45）解出的
   **旧 release 壳同样 `Responding=False`**。
2. **不是 WebView2 数据目录损坏**：把 `%LOCALAPPDATA%\com.origadmin.orighub\EBWebView` 改名后
   用全新目录启动，仍复现（新目录会创建，但 webview 进程仍不出现）。
3. **不是代理**：系统代理 `ProxyEnable=0`；清除 `http_proxy/https_proxy` 等环境变量后启动，
   仍复现。（`curl http://tauri.localhost/` 走环境代理返回 502，但排除代理后问题不变。）
4. **不是 GPU**：`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS="--disable-gpu --disable-gpu-compositing"`
   无效 —— webview 进程都没创建，参数无从下发。
5. **不是透明窗口**：把 `transparent` 改 `false` 重新构建后，`Responding` 变为 `True`，
   但 **webview 进程仍不出现、前端 trace 无任何记录**，界面依旧空白。已恢复原配置。
6. **不是依赖升级**：`Cargo.lock` 与 HEAD 一致（tauri 2.11.5 / wry 0.55.1），工作区未改动。

## 根因（当前结论：运行时层挂起，待定论）

`CreateCoreWebView2EnvironmentWithOptions` 挂起：wry 已加载并进入创建流程，但
`msedgewebview2.exe` 从未被拉起。旁证：**`npx tauri info` 本身也挂起**（120s 无输出被终止）——
该命令同样要探测 WebView2 环境，说明挂起点在 WebView2 运行时探测/初始化，而非本项目代码。

时间线：`%TEMP%/orighub-shell-trace.log` 中最后一次成功的 `[ensure_daemon] reusing daemon`
停在 **10-20 07:32**，此后只有 `spawning daemon`、没有 `spawned ok`。即 10-20 之后应用就再未
正常启动过。10-20 之后的环境变更：Edge 升至 156.0.4314.42（10-24）、安装 Zed（10-24）、
WSL 3.0.3（10-26）、FluxDown（10-27）；WebView2 Runtime 仍为 155.0.4283.62（10-19）。

**未定论项**：同一台机器上 clash-verge 的 WebView2 实例工作正常，故「WebView2 运行时整体不可用」
不成立；差异可能在本项目的 runtime 选择方式（evergreen vs fixed-version）或 Tauri 2.11/wry 0.55
与本机 WebView2 的初始化握手。

## 修复方向（按代价排序）

1. **重装 WebView2 Evergreen Runtime**（微软官方 Standalone Installer）后复测 —— 系统级操作，
   需用户授权。
2. 若重装无效：给壳加 `webview2-com` 的显式环境初始化与超时，把「挂起」变成「可读错误」
   （现在 `spawn` 失败无任何日志，因为 release 是 GUI 子系统）。
3. 用 `WEBVIEW2_BROWSER_EXECUTABLE_FOLDER` 指定固定版本运行时做对照，判定是否 evergreen 路径问题。

### 与 BUG-448 的边界（2026-10-27 新增）

用户当天报的「二进制一开就死 / 卡顿很久后界面正常」，经实测**不是**本条的 webview 挂起，
而是 **BUG-448**（daemon 就绪被 TG 插件阻塞、壳 5s 误判超时、超时不杀子进程、同步命令冻结 UI）。
判别方法：本条的标志是 **`msedgewebview2.exe` 不存在 + 前端 JS 一行不跑**；
BUG-448 的标志是 **JS 跑了、`ensure_daemon` 被调用，但 `/health` 迟迟不 200**。

两条要分开跟踪：修好 BUG-448 **不能**当作本条的证据；本条若再次复现，仍按原修复方向排查。
