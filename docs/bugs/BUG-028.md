# BUG-028: TG 在线播放视频严重卡顿（单连接串行拉流 + 每 Range 1.2s RPC）

## 状态

- **登记时间**: 2026-09-17
- **状态**: fixed
- **报告人**: 用户（「播放器播放视频非常卡顿，不正常卡顿，卡到没法看」）

## 现象

TG 面板在线播放视频持续缓冲卡顿，无法正常观看。媒体库本地播放正常。

## 根因（全部实测取证，非推测）

对真实实例（9877，Authorized）压测三条路径：

| 路径 | 实测 | 结论 |
|------|------|------|
| `/api/media/items/:id/raw`（媒体库本地文件） | 8MiB Range 0.033s，**~105MB/s** | 无问题 |
| `/api/tg/local/:chat/:msg`（TG 已缓存本地文件） | 本地磁盘流 | 无问题 |
| `/api/tg/file/:chat/:msg`（TG 在线流） | 2MiB Range **4.0~6.3s（0.33~0.5MB/s）** | **病根** |

在线流慢的结构性原因（grammers-client 0.10 `files.rs`）：

1. **单连接串行取块**：`DownloadIter::next()` 一次只发一个 `upload.GetFile` 请求，
   单流吞吐 = chunk/RTT = 512KiB / ~1s ≈ 0.5MB/s。播放码率 >0.5MB/s 或与其他
   TG 请求（缩略图等）共享客户端时，缓冲永远追不上 → 持续 rebuffer。
   并发对照实验：2 路并发各 ~0.32MB/s、总 0.64MB/s —— **吞吐随并发线性扩展**，
   证明单路没吃满带宽，纯粹是串行 RTT 瓶颈。
2. **每个 Range 请求固定付 ~1.2s RPC**：`media()` 每次都 `resolve_peer` +
   `get_messages_by_id` 重新解析媒体（bytes=0-0 探针实测 1.23/1.26/1.33s）。
   播放器 seek、续传 Range、缩略图重渲染全都重复付费。
3. 缩略图无缓存：feed 每次渲染对同一批 `(chat,msg)` 反复走完整 RPC + 拉取。

而 grammers 官方 `download_media` 落盘路径本身就是 4 worker 并行
（`files.rs::WORKER_COUNT = 4`）——我们自管的流式路径没用上同样的并行度。

## 修复（结构性）

### 1. 并行分片拉流（`grammers.rs::parallel_range_stream`）

- 把请求区间切成 K=4 个 **chunk 对齐**（512KiB）的连续分片；
- 每个分片一个独立 `iter_download` worker（`tokio::spawn` + 有界 mpsc 通道 cap=2）；
- 合并任务按分片顺序转发（严格有序），统一裁剪 `skip_lead`（chunk 对齐多余字节）
  与 `take`（区间总长）；
- `media()`（在线播放）与 `download()`（缓存任务）都切换到该函数 —— **缓存下载同样提速 ~4×**；
- `take=None`（整段 200）时用固定 16MiB 分段，末 worker 读到 EOF；
- 取消语义：浏览器中断 → 输出端 drop → 合并任务退出 → worker 退出 → iter 析构，零残留。

### 2. 媒体元数据缓存（`lru.rs::TtlLru` + `media_meta`）

- 新增极简容量+TTL LRU（无外部依赖，单测 3 例）；
- `(chat_id, message_id) -> {Media, content_type, total_size}`，cap=256 / TTL=10min；
  `FileLocation` 含 access_hash 跨请求有效，TTL 仅作陈旧保险丝；
- 命中后 `media()` 零 RPC 直接取流 → seek / 续 Range 不再付 1.2s。

### 3. 缩略图字节缓存（`thumb_cache`）

- cap=512 / TTL=30min；缩略图不可变，命中即零 RPC、零 TG 流量；
- `thumb()` 拆为「查缓存 + `thumb_fetch()` 实拉」。

## 验收（真实实例 9877 实测）

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 单流 2MiB Range 吞吐 | 0.33~0.5MB/s | **1.5~2.0MB/s（×3~4）** |
| 双并发总吞吐 | 0.64MB/s | **2.27MB/s** |
| 重复 Range（seek/续传） | 每次 ~1.2s RPC | 命中缓存 0.8s（纯单块 RTT） |

真实浏览器（Playwright/Chromium）端到端：

- **播放流畅度** `verify_shots/verify_playback_smooth.cjs` → `SMOOTH`：12s 墙钟推进
  12.03s 视频时间（满速实时），起播后 0 次 waiting/stalled，缓冲 32.9s（exit 0）。
- **seek 响应** `verify_shots/verify_seek_latency.cjs` → `FAST`：跳 90s 于 2075ms 恢复
  精确到帧（exit 0）。

回归：

- 单测 16/16（含新增 `lru.rs` 3 例）；mock 构建 + `run_cache_task_verify.sh` RC=0。
- 全量 `verify_shots/run_all.sh`（Tier1 实时实例 + Tier2 自包含）：见套件退出码。

## 关联

- BUG-024（缓存任务原子落盘）、BUG-027（缓存单飞 worker）：`download()` 换用并行流后
  缓存吞吐同步提升，单飞/队列语义不变。
- AGENTS.md §5：新增「TG 在线拉流必须并行分片 + 媒体元数据必须缓存」。

## 防再发

- 任何新增流式端点禁止直接用裸 `iter_download` 串行吐流，必须走 `parallel_range_stream`；
- 新增高频读端点先问一句「同一键会被反复请求吗」——会，就先落缓存。
