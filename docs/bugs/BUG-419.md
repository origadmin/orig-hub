# BUG-419: 已置顶任务无法取消置顶（422）——`priority_endpoint_rejects_malformed_requests_bug277` 红灯

- 状态: fixed（2026-10-27）
- 发现日期: 2026-10-23
- 模块: engine
- 严重程度: mid

## 现象

`cargo test -p orig-tg --lib priority_endpoint_rejects_malformed_requests_bug277` 稳定 FAIL：

```
已置顶任务的取消置顶必须始终可用:
(422, {"error": "priority only applies to queued tasks (or to unpinning an already pinned one)"})
```

用例的意图是「**已置顶**任务的取消置顶必须始终可用」，但端点返回 422 —— 说明「取消置顶」
这条分支的判定条件把它自己排除了（错误文案里明明写着「or to unpinning an already pinned
one」，实际却不放行）。

## 影响

用户置顶一个已经开跑 / 已完成的任务后，**再也取消不了**：置顶是队列序的唯一用户意图，
置顶位被钉死等于队列顺序不可恢复。

## 复现

```sh
cd download-engine
cargo test -p orig-tg --lib priority_endpoint_rejects_malformed_requests_bug277
```

## 根因

**不是端点缺陷 —— 红的是这条用例自己的期望，它与 BUG-396 的用户裁定正面冲突。**

链路：`置顶(queued, priority=N)` → `finish_cache_task(..., "done")` → 取消置顶（`priority: 0`）。

BUG-396（用户 2026-10-23 裁定「完成后应该就没有优先这个状态了」）为此改了两处，

1. `store.rs:3467` `finish_cache_task` 离队即写 `priority = 0`（`cancel_cache_task` 同）；
2. `cache.rs:1303` `prioritizable` 排除 done/cancelled。

于是走到第二步时，**待撤的那个 pin 已经被引擎自己撤掉了**：再发 unpin 是「无事可做」，
与同档另外一个 case（终态任务 `top:true` ⇒ 422）必须同口径 —— 不假装成功。

对照取证（`git show`，非推断）：

```
# BUG-396 之前（21f3415^）
fn prioritizable(t: &CacheTask) -> bool { t.status == "queued" || t.priority > 0 }
# 且 finish_cache_task 不归零 priority ⇒ 置顶过的终态任务 priority 仍 > 0 ⇒ 用例当时是绿的
```

⇒ 这条用例是被 BUG-396 的**正确修复**带红的；它编码的需求（「终态也要能取消置顶」）
正好是 BUG-396 要删掉的那个状态。

残留的真问题只有一处：错误文案 `PRIORITY_REJECT_MSG` 里的半句
「or to unpinning an already pinned one」在 BUG-396 之后对终态已成空头支票 ——
界面若直出这句话就是「说了能做、点了不给」，属 BUG-249 那类「界面↔端点判据分裂」。

## 修复

端点行为**保持不动**（那是 BUG-396 的裁定口径），改的是两处不对账的地方：

1. **用例期望对齐 BUG-396**（`cache.rs::priority_endpoint_rejects_malformed_requests_bug277`）：
   - 终态任务（哪怕此前置过顶）的 unpin ⇒ **断言 422**；
   - 并在断言前先钉死因果前提：`get_cache_task(...).priority == 0`
     （「离队即归零」⇒ 终态没有 pin 可撤），否则那条断言只是在替 BUG-396 打补丁，看不出因果；
   - 补上真正还有可观察效果的通道：**在跑**的任务身上挂着的 pin 必须能撤
     （排队时置顶 → `mark_cache_task_running` → `priority: 0` ⇒ 200）。UI 的「取消优先」
     按钮在 BUG-396 之后也只剩这一种情形，按钮存在 ⇔ 端点必须放行。
2. **`PRIORITY_REJECT_MSG` 去掉空头半句**：
   `priority only applies to queued tasks (settled ones carry no pin to unpin)`。

刻意不做：不给终态 unpin 开「200 空操作」通道 —— 那等于承认终态仍携带优先状态，
直接推翻 BUG-396。

## 验收证据

1. **红灯 → 绿灯**：`cargo test -p orig-tg --lib priority_endpoint_rejects_malformed_requests_bug277`
   ⇒ `test result: ok. 1 passed`（修复前 `FAILED ... panicked at cache.rs:2549`）。
2. **全量回归**：`cargo test -p orig-tg --lib` ⇒ **`342 passed; 0 failed`** —— 这是本轮之后
   首次全绿（此前长期挂着 1 条既有红灯，A/B 实证与当批改动无关）。
3. **判据验牙（双向）**：同一用例在两个反向变异下必红 ——
   - `prioritizable` 改成恒 `true` ⇒ FAIL（`cache.rs:2539`，终态置顶必须 422 那条）；
   - `prioritizable` 收紧为 `t.status == "queued"` ⇒ FAIL（`cache.rs:2578`，「在跑的任务
     必须能取消置顶」那条，即本档新增的正向通道）。
   两个方向都咬 ⇒ 新增断言不是恒绿的装饰。
4. **跨机可核引用**：修正落在 `download-engine/crates/orig-tg/src/cache.rs`
   （函数 `prioritizable` + 常量 `PRIORITY_REJECT_MSG` + 上述用例）。
