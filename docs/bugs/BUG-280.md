# BUG-280: 入库队列任务标题被**无意义文件名**遮蔽 —— 组内靠前的 `file_name` 抢在靠后消息的真 `caption` 之前

- 状态: fixed
- 发现日期: 2026-10-12
- 模块: engine
- 严重程度: mid

> 来源：用户 2026-10-12 报障「多集入库时大部分集没有内容、只有某一集有介绍（媒体库显示），但入库队列里什么都没有（只有默认标题）」。
> 本档是其中**队列侧**的一半；**媒体库侧**另立 **BUG-281**（同一批调查，**不同根因**）。
> **本档为任务文档**（用户 2026-10-10 定：后续一律纯文档任务，代码由别的组负责）。
>
> **登记规范**：遵循「内容数据不入库」原则（见 BUG-232）：**不含真实频道名 / 消息文案 / 文件名**；
> 下文的实测标识一律以占位符表示（`<chat_id>` / `<msg_id>` / `任务 A` 等）。

## 现象

多集（相册组）任务在队列里只显示一个**无意义标题**：要么是一个**无意义的内部文件名**
（上传工具自动生成的临时名一类），要么退化成 `频道名 #<消息号>`。
用户**无法从队列判断这批入库的是什么** —— 正是 BUG-220 立项要治的那个问题。

实测（2026-10-12，`GET /api/tg/cache/tasks/all`；真实标识已占位化）：

| 任务 | `item_key` | 条数 | 返回的 `title` | 组内真 caption 在哪 |
|---|---|---|---|---|
| **任务 A** | `b:<chat_id>:<first_msg>` | 8 | **一个无意义的内部文件名** | 靠后某条消息（带完整文案） |
| 任务 B | `b:<chat_id>:<first_msg>` | 8 | 一个无意义的内部文件名 | — |
| 任务 C | — | 6 | 一个无意义的内部文件名 | — |

## 根因

**两处叠加**：标题映射把 `caption` 与 `file_name` **平级**，而取标题用 **first-match**。

### 事实 1：标题映射里 `file_name` 与 `caption` **平级**

`message_captions_for_channels`（`store.rs:620-647`，SQL 在 `:633`）：

```sql
SELECT message_id, COALESCE(NULLIF(caption, ''), NULLIF(file_name, '')) AS title
  FROM media_message
 WHERE channel_id = ?1
   AND (caption IS NOT NULL AND caption <> '' OR file_name IS NOT NULL AND file_name <> '')
```

只要 `caption` 为空就由 `file_name` 顶上。**这是 BUG-220 有意引入的**（为的是「无 caption 时显示文件名，而不是退回频道名」）——
它本身没错，错在与下面的 first-match 组合。

### 事实 2：取标题是 **first-match**

`cache_task_title`（`routes.rs:1308-1315`）：

```rust
t.message_ids.iter()
    .find_map(|m| titles.get(&(t.chat_id, *m)).map(|s| s.as_str()))
```

取 `message_ids` 里**第一条**在映射里有记录的。

### 叠加后果

相册组里**靠前**那条消息的 `file_name`（哪怕是无意义的内部文件名）**抢先**于**靠后**消息的真 `caption`。
`routes.rs:1303-1307` 的注释已经注意到「首条常常是空说明」（所以改成「第一条**有** caption 的」），
但**没有注意到**「`file_name` 回退让‘有 caption’这个条件形同虚设」——只要首条有文件名，搜索就停在那里。

### 实测证据（某相册组，共 8 条消息）

`media_message` 逐条（只读；真实 `message_id` 与文件名已占位化）：

| 组内序位 | `caption` | `file_name` | 会被 first-match 命中？ |
|---|---|---|---|
| 第 1 条 | 空 | 空 | 否 |
| **第 2 条** | **空** | **一个无意义的内部文件名** | **是 ← 停在这里** |
| 第 3–5 条 | 空 | 同类内部文件名（带 `(N)` 序号后缀） | — |
| **第 6 条** | **完整真 caption**（含剧名与集号的多行文案） | 真名（含剧名与集号） | 够不到 |
| 第 7–8 条 | 空 | 真名（含剧名与集号） | — |

**全库量化**：86 个多消息任务中，首命中 `file_name` = **6 个**、首命中 `caption` = 78 个、两者皆无 = 2 个。

### 附：另一半来源（**有意设计，不属本条缺陷**，但必须写明，否则会误判）

1s 轮询端点 `/api/tg/cache/tasks` **不下发 `title`**（`routes.rs:1452-1458`）：
> 「标题**不在这里**取（BUG-232 v2）：这是 1s 轮询端点，读路径契约是「服务内存快照，不碰 SQLite」——
> 为了标题加一次 DB 查询会把流畅度底线换掉。」

⇒ TgPanel 的队列行**恒**走前端回退 `ingestTitleOf`（`CacheManagerDialog.tsx:957-967`）
→ `频道名 #<首个消息号>`（`titleOf(chatId) ?? 频道 <chatId>`）。
**这是「队列看起来什么都没有」的另一半来源，且是有意的性能取舍，不在本条修复范围内**，仅如实登记。

## 复现

1. 构造/找一个相册组：**首条**消息 `caption` 空但 `file_name` 非空，**靠后**某条消息带真 `caption`。
2. 入队该组，读 `GET /api/tg/cache/tasks/all` 的该任务 `title` ⇒ 得到 `file_name`，**不是** caption。
3. 只读 SQL 佐证（`%APPDATA%\com.origadmin.orighub\tg\store.db`，`mode=ro`；`<chat_id>`/`<msg_lo>`/`<msg_hi>` 为占位）：
```sql
SELECT message_id, COALESCE(NULLIF(caption,''), NULLIF(file_name,'')) AS title
  FROM media_message
 WHERE channel_id = <chat_id> AND message_id BETWEEN <msg_lo> AND <msg_hi>
 ORDER BY message_id;
```

## 修复（方向；**本档不改代码**）

- **A（推荐）两遍选取**：`cache_task_title` 先扫**任意**有非空 `caption` 的消息；**找不到**才退回 `file_name`。
  最小改动、不动 schema、不动端点契约。等价做法：在 `message_captions_for_channels` 里多带一个
  `has_caption` 布尔，让调用方排序（`caption 优先、其次 file_name`）。
- **B** 把 `file_name` 回退**降级为「全组无 caption 时才用」**：落在 `message_captions_for_channels`
  的返回结构里（需改签名/返回类型），语义与 A 等价但改动面更大。
- **C** 不做（接受「靠前文件名优先」）—— 与 BUG-220 的立项意图相悖，不推荐。
- **不可推翻**：BUG-220（无 caption 时用 `file_name` 兜底，**别退回频道名**）、
  BUG-232 v2（1s 端点不查 DB 的读路径契约）。
- **不冲突**：本条与 **BUG-281**（分集内容分发）**互不依赖**，可各自独立实施。

## 关联

- **BUG-281**（fixed）：**媒体库侧**分集无内容 —— 同一批调查、**不同根因**，两条须一起看但可分开修。
