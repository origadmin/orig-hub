# BUG-421: 旧库根搬迁漏改写 72 条 `file_path`——文件已在新根下，条目却永远播不了、也拿不到 hash

- 状态: fixed
- 发现日期: 2026-10-23
- 模块: engine
- 严重程度: high

## 现象

真实库（`%APPDATA%/com.origadmin.orighub/tg/store.db`）里 **84 条 video** 的
`file_path` 指向不存在的文件。按前缀归类：

| 前缀 | 条数 | 例 |
|---|---|---|
| 旧库根 `D:/OrigDown/library/` | **72** | `D:/OrigDown/library/chat--1004493170102/8542-完蛋我包养的女大是大佬-….mov` |
| 下载根顶层 `D:/OrigDown/` | 11 | `D:/OrigDown/9月20日(9)--1003842739671-2476.mp4` |
| `C:/…/Temp/…`（测试夹具） | 1 | `orighub-bug214-…` |

那 72 条的文件**全都在**：逐条按「旧根前缀换成新根」去 stat，**72/72 命中**
（如上面那条实际位于 `D:/OrigDown/.orighub/library/chat--1004493170102/8542-….mov`）。

## 根因

2026-10-21 用户裁定「内部文件不入治理」，库根从 `<下载根>/library` 搬进
`<下载根>/.orighub/library`：

- 磁盘搬迁 = `Store::migrate_library_into_engine_dir`（`rename` 整个目录）；
- 行的 `file_path` 改写 = `migrate_legacy_managed_roots`（BUG-323）。

**目录搬全了，行没搬全**：72 条仍指着旧根。后果是双重的——

1. 这 72 条永远播不了（`resolve_item_path` 解析到一个不存在的路径），界面上却与正常
   条目长得一样（BUG-250 同族：不体现「内容存在性」）；
2. 它们**永远拿不到 `content_hash`**：BUG-420 的回填按 `resolve_item_path` 判存在性，
   路径错 ⇒ 被判成「文件不存在」而跳过 ⇒ 归并判据对这 72 条恒失效。

## 复现

```sh
python -c "
import sqlite3,os
p=os.path.expandvars(r'%APPDATA%\com.origadmin.orighub\tg\store.db')
c=sqlite3.connect(f'file:{p}?mode=ro',uri=True)
old='D:/OrigDown/library/'; new=r'D:\OrigDown\.orighub\library'
tot=ok=0
for (fp,) in c.execute('select file_path from media_item where file_path is not null'):
    f=fp.replace(chr(92),'/')
    if f.startswith(old):
        tot+=1
        if os.path.isfile(os.path.join(new, f[len(old):])): ok+=1
print(tot,'条指向旧库根，其中新根下存在',ok,'条')
"
# 实测输出：72 条指向旧库根，其中新根下存在 72 条
```

## 修复

`Store::repair_old_library_root_rows`：扫所有 `file_path` 非空的行，凡以
`<下载根>/library/` 开头者，把前缀换成当前库根；**只在目标文件确实存在时改写**，
否则保持原样并计数（`skipped`）。

- 位置：`main.rs` 里紧接 `migrate_library_into_engine_dir` 之后 —— 必须排在目录搬迁
  之后（否则新根还不存在，无从判定目标），且排在 BUG-420 的回填之前（先修路再补 hash）。
- 只改位置列：`content_hash` 是**内容身份**，与文件放哪无关；这里既不 acquire 也不
  release 引用计数（这些字节不在 `.blobs` 下）。
- 幂等：改写后的路径不再以旧根开头，重跑零改写。
- **不改写悬空行**：把「文件没了」改成「路径对了」等于掩盖事实 —— 那 12 条（11 顶层 +
  1 临时夹具）是真的没有字节，该由「字节存在性」那一层去说，不是路径修复的活。
