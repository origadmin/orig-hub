# BUG-108: 批量操作（全部暂停 / 全部开始 / 清除已完成）失败被双重静默，点击无反应也无提示

- 状态: fixed
- 严重程度: mid
- 模块: shell
- 发现日期: 2026-09-22

## 现象

点「全部暂停 / 全部开始 / 清除已完成」，若后端不可用（daemon 未运行 / 接口报错），
**一条都没成功，界面却毫无反应**：没有错误提示、没有 toast、控制台也没有。
用户无法区分「没有符合条件的任务」与「操作失败了」。

## 根因

两处静默叠加，且**同一功能存在两套容错策略**：

1. `tauri-shell/src/store/useStore.ts` 的 `pauseAll` / `resumeAll` / `clearCompleted`
   在循环里对**每一条**都 `.catch(() => {})` —— 单条失败被逐条吞掉。
2. `tauri-shell/src/components/MainLayout.tsx` 的 `handlePauseAll` 等回调
   再套一层 `.catch(() => {})` —— 连 store 方法本身抛出的错也一并吞掉。

对照**单条**操作：`pause` / `resume` / `cancel` 都是直接 `await`（**不吞**），
由 `DownloadItem` 用 `setError` 提示。也就是说：
**单条有反馈，批量没有** —— 缺的那一半正是批量。

而 `toast` 这套「操作失败的用户可见反馈」基础设施**本来就存在**
（`useStore` 的 `toast` / `setError`，`MainLayout` 已解构并在 324 行渲染），
批量操作只是没用上。

## 修复

- 三个批量方法改为：逐条 `try/catch` 收集失败数与首个错误原因，
  **结束时若有失败则 `set({ toast: ... })` 聚合提示**（形如 `2/3 个任务暂停失败：<原因>`）。
- 保留「尽力而为」语义：单条失败不中断其余任务。
- `MainLayout` 外层 catch 保留（仅防 unhandled rejection），并注释说明
  不再叠加一层 toast，否则同一失败会弹两遍。

为什么聚合而不是逐条弹：批量操作一次可能涉及几十个任务，逐条弹会把屏幕刷满，
且用户关心的是「成了几个」。首个错误原因保留下来用于定位。

## 验收证据

- 类型检查：`node node_modules/typescript/bin/tsc --noEmit -p tsconfig.json` → **0 错误**
  （必须在 `tauri-shell/` 下跑；`npx tsc` 在本仓库是 npm 占位包，无效）。
- 改动文件：`tauri-shell/src/store/useStore.ts`、`tauri-shell/src/components/MainLayout.tsx`。

**未做端到端实测**，原因如实记录：触发这三个按钮需要存在「下载中 / 已暂停 / 已完成」
状态的任务，而当前实例任务列表为空（`0 个下载中 · 0 个已暂停 · 0 个已完成 · 0 个失败`），
无法构造出可失败的目标。修复逻辑为 try/catch 计数 + 复用既有 toast 通道（该通道已被
`AccountsPanel` / `AddDownloadDialog` / `DownloadItem` 使用并被验证可用），
端到端行为待有任务时补验。
