# BUG-395: 下载列表端点混装进程级全局状态——`sources` 不是下载数据，`count` 还随查询参数变

- 状态: open
- 发现日期: 2026-10-23
- 模块: engine+shell
- 严重程度: high
- 报告: 用户 2026-10-23 16:12 原话「`/api/downloads?scope=all` -> sources 的设计有严重问题吧?
  这个是不是全局状态数据? 和下载有什么关系. 我感觉现在的接口设计混乱才是导致当前开发混乱,
  卡顿,以及各种问题的元凶. 怎么解决?」

## 现象（实测，非推测）

`GET http://127.0.0.1:19786/api/downloads?scope=all` 返回：

```json
{
  "tasks": [/* 149 条，全部 kind="cache"，引擎侧 0 条 */],
  "sources": [
    {"kind": "download", "available": true,  "count": 0},
    {"kind": "cache",   "available": true,  "count": 149}
  ],
  "generated_at": 1792743163
}
```

| 端点 | 响应体积 | 耗时（3 次实测） |
|---|---|---|
| `/api/downloads?scope=all` | 58,642 B | 8.6 / 9.3 / 9.1 ms |
| `/api/downloads?scope=active` | 13,530 B | 6.9 ms |
| daemon 内部回源 `orig-tg:19787/api/tg/cache/tasks/all` | 57,257 B | 6.7 / 7.3 / 6.7 ms |

149 条的状态分布：`done` 107 / `cancelled` 17 / `interrupted` 14 / `failed` 11
（**没有一条在途**）。

## 根因：同一个端点混了三种不同生命周期的数据

`sources` 与「下载」无关，它是**进程级/服务级**的两件事：

1. `available` = 该来源本次是否聚合成功（TG 插件开关、orig-tg 可达性、下载根合法性）；
2. `count` = 该来源**过滤后纳入的条数**。

用户直觉正确，而且实际情况比「混了全局状态」更糟三点：

### ① `count` 根本不是全局状态，是查询投影的副产品

`activity.rs::merge` 的注释自陈「该来源最终纳入的条数（过滤后）」。
同一个 `scope` 参数翻转，数字就变：`scope=active` 时 cache count = 25（在途），
`scope=all` 时 = 149。一个叫「来源」的对象，其内容取决于**别的查询参数** ——
读它的人会把「本次响应里有几条」误读成「全局有几个」。

### ② 想知道「TG 挂没挂」必须把整个任务列表拖下来

全仓没有专门讲来源健康的端点（`/health` 只回 `{"status":"ok"}`；`/api/config` 讲设置）。
于是「横幅要不要显示」这个全局问题被绑死在 58KB 的任务列表请求上。
反过来说：**任何想让健康检查变便宜的重构，都会被这个字段挡住**。

### ③ 它把两个变化速率完全不同的东西打进同一个轮询单元

| 数据 | 生命周期 | 变化频率 |
|---|---|---|
| 任务行 `tasks` | 用户操作驱动，**只增不减**（BUG-314：取消记录保留） | 按用户操作 |
| 来源健康 `sources.available` | 进程/服务状态 | orig-tg 每 10–15 分钟被监督者重启一次（BUG-318 实测） |
| `sources[].count` / `generated_at` | 每次查询重算 | 每次请求 |

前端为此打了两个补丁：`sourceUnknown` 单独续轮（BUG-318）+ 退避档位（BUG-343）。
补丁本身没错，但它们是**为「层次混装」付的利息**。

## 为什么会卡顿（诚实口径）

当前库态 0 条在途 ⇒ `hasWork=false` ⇒ **轮询是停的**（`useIngestGroups.ts:292`
`groups.some(isCacheActive)`）。所以不是「一直在拉」。真实的代价出现在
**用户最需要流畅的时刻**——有活的时候：

```
每 3s（DEFAULT_INTERVAL_MS）：
  UI  ← daemon   58 KB，149 条 JSON.parse + signature() 逐条签名比对
  daemon → orig-tg 57 KB，orig-tg 侧一次 SQLite 全表读
  daemon 侧一次 SQLite 全表读（engine_rows）
```

关键性质：这个成本随**历史任务数**单调增长（149 条里 124 条是终态，永不减少），
与「当前在传几条」无关。传得越久、积累越多，跟手轮询越重 —— 而那时用户正在盯进度条。

## 为什么「接口设计混乱是元凶」

精确地说：混乱不在「有几个端点」（BUG-392 已统一成一个），而在
**同一个端点里混了三种不同生命周期的数据**。读的人无法只取其一，
写的人改任一部分都影响另一部分的消费者。BUG-392 修的是形态混乱
（列表两个端点、状态变更两个域），没修层次混乱（列表端点里塞服务健康）——
所以用户这次闻到的是同一股味道的另一个面。

## 解决方案（三步，每步可独立验收；端点始终只有一个，不违背 BUG-392 共识）

### 第一步：健康拆成独立端点（加法改动，先止血）

新增 `GET /api/sources` → `{sources:[...], generated_at}`，`available` 口径与现状逐字一致。
`/api/downloads` 的 `sources` **保留为兼容字段**（旧探针/旧前端仍可读），文档标 deprecated。

前端把 `useIngestGroups` 拆成两个 hook：
- 列表轮询（3s，有活才轮，口径不变）；
- 健康轮询（独立、更慢，与任务列表解耦 —— `sourceUnknown` 续轮不必再拉 58KB）。

收益：健康检查流量 58 KB/3s → 约 200 B/30s。
风险：`verify_bug300_ingest_aggregation.cjs` / `_probe_bug343_polling.cjs`
的轮询档位断言要按新结构重写（判据先翻转型）。

### 第二步：`count` 从「健康」对象里挪走

`sources[].count` 是投影副产品，放在健康里必然误导。移到顶层
`counts: {download, cache}`（仍是本次响应计数，语义不变，但不再假装是全局）。
判据：`scope=active` 与 `scope=all` 的 `counts` 必须与各自响应里 `tasks` 实际条数相等。

### 第三步：终态历史从轮询路径上摘下来（唯一有回归风险的一步）

149 条里 124 条是终态历史。拆成：
- `?scope=active`（在途）→ 跟手轮询；
- `?scope=all`（全量）→ 仅在用户切到「全部 / 已暂停 / 已完成」档时拉一次，
  之后靠事件/手动刷新，不再进 3s 轮询。

这与 UI 树档天然对齐：三个档里只有「下载中」需要跟手（BUG-377 后「已暂停」档
装的是停止项，同样不需要 3s 跟手）。
收益：常规轮询 58 KB → 13.5 KB，且**不再随历史增长**。
风险：动 `useIngestGroups` / `DownloadPanel` / 侧栏徽标三处；徽标与列表必须仍同源
（BUG-377 的 `dlBuckets.ts` 正是为此存在的，判据 `verify_dl_paused_visible.cjs` 须同轮跑）。

## 关联

- BUG-392：已统一「一个列表接口 + 一个状态变更接口」（本条不动端点数量）；
- BUG-077：`/api/activity` 聚合视图五条铁律（第一条「只读聚合」仍然成立）；
- BUG-318 / BUG-343：`sourceUnknown` 续轮与退避档位 —— 第一步后这两个补丁可简化；
- BUG-314：取消记录不删 ⇒ 终态历史只增不减，是第三步的前提事实；
- BUG-377：「已暂停」档收所有停止项（刚修，第三步必须与它同源）。
