# BUG-288: `/stream` 兼容流「单飞表条目泄漏」—— 一次异常终止的转码会把该变体**永久**钉死在 503（重启 orig-tg 才解）

- 状态: open
- 发现日期: 2026-10-12
- 模块: engine
- 严重程度: high
- 排期: 2026-11-10

> 来源：播放卡顿对比诊断的取证副作用发现（用户 2026-10-12「播放依然卡顿，为什么 TG Web 不卡、本地反而卡？」）。
> **本档为任务文档**（用户定：纯文档任务，代码由别的组负责）。
>
> **严重程度说明**：命中该变体的条目**永久不可播**（浏览器拿到 503 ⇒ 黑屏 / 致命遮罩），用户观感即「卡 / 播不了」；
> 且**只能靠重启 orig-tg 进程恢复**，前端与用户侧均无自愈手段 ⇒ 定 `high`。
> 触发前提是「该变体曾有一次 pump 异常终止」，故非每次播放必现，不升 `critical`。
>
> **数据口径**：遵循「内容数据不入库」（`docs/bugs/BUG-232.md:79`）—— 本档只记现象/机制/`file:line`/判据，
> 具体条目 id 以 `<item_id>` 占位、文件名只记「形状」；含具体 id 的原始取证输出由取证方留存，不抄录入库。

## 现象

对某一条目（记作 `<item_id>`）请求 1x 兼容流：

- `GET /api/media/items/<item_id>/stream`（无 `speed`）⇒ **HTTP 503**，且**瞬间返回**（实测 ≈ 0.01 s）。
- 同一时刻 `GET /api/media/items/<item_id>/stream?speed=2` ⇒ **206**，响应头 `x-orig-stream: proxy`（该倍速代理已就位）。
- 期间 `ffmpeg` 进程数 = **0**（没有任何转码在途）。
- **反复请求，结果恒定**（不是抖动，不是首次冷启动等待）。

⇒ 不是「转码慢」、不是「源文件缺失」、不是「ffmpeg 不存在」——
是**该变体的请求被一条永不消失的「在途记录」挡住**，每次都在毫秒级被打回 503。

## 根因

**单飞表 `transcode_inflight()` 的条目只在 `transcode_pump` 的 `finish()` 里移除；若 pump 在调 `finish()` 之前异常终止（panic / 任务被 drop），条目永久残留。而 `Role::Wait` 分支既不删条目、也不自愈 ⇒ 此后每次请求都瞬间 503。**

### 事实 1：503 的唯一出口 = `Role::Wait`（`download-engine/crates/orig-tg/src/routes.rs:4376-4379`）

```rust
Role::Wait(rx) => {
    // ... 等 watch ...
    if tokio::fs::metadata(&final_p).await.is_ok() { /* 代理就位 → 200/206 */ return Ok(res); }
    Err(ApiError::new(StatusCode::SERVICE_UNAVAILABLE,
        "transcode in flight but proxy not ready; retry later"))   // ← 全文唯一的这条 503
}
```
同函数其它前置分支都不是 503：源缺失 = 404（`:4264`/`:4267`）、ffmpeg 缺失 = 501（`:4316-4321`）、代理命中 = 直接 serve（`:4293-4310`）。
⇒ **拿到 503 就一定命中了 `Role::Wait`**（判据可靠）。

### 事实 2：`Role::Wait` 等的是 `watch`，且**从不删条目、无自愈**（`:4349-4359`）

```rust
Role::Wait(rx) => {
    let mut rx = rx;
    let _ = tokio::time::timeout(Duration::from_secs(600), async move {
        while !*rx.borrow_and_update() {
            if rx.changed().await.is_err() { break; }   // ← 发送端已关闭 ⇒ 立刻 break，不阻塞
        }
    }).await;
    if tokio::fs::metadata(&final_p).await.is_ok() { /* ... */ }
    Err(/* 503 */)                                       // 无文件 ⇒ 503
}
```
- 条目由 `Role::Start` 分支 `m.insert(key, rx)` 写入（`:4340-4344`）；**唯一** `remove` 在 `finish()` 里。
- `Role::Wait` 分支**没有**任何「检测到陈旧条目就清掉 / 重新起转码」的逻辑。

### 事实 3：`finish()` 是**唯一**出表口，且正常路径都会调用（`:4466-4476`）

```rust
let finish = |completed: bool| {
    if registered { transcode_inflight().lock().expect("transcode map poisoned").remove(&key); }  // 出表
    let _ = done_tx.send(completed);                                                               // 唤醒等待者
};
```
`finish()` 在**所有**早退/正常路径都调用了：`create_dir_all` 失败 `:4481`、`spawn` 失败 `:4567`、`create .part` 失败 `:4593`、
stall 超时 `:4616`、正常收尾 `:4688`。
⇒ **只要 pump 跑到任一处，条目都会被清掉。**

### 事实 4：⇒ 唯一泄漏路径 = **pump 在 `finish()` 之前异常终止**

- pump 由 `tokio::spawn(transcode_pump(...))` 启动（`:4411-4423`）。若该任务 **panic** 或被 **drop**，
  `finish` 永不执行 ⇒ `done_tx`（被 `finish` 闭包借用、随任务一起 drop）关闭，`watch` 值停在初始 `false`。
- 此后任何请求进 `Role::Wait`：`borrow_and_update()` = `false` → `changed()` 立即 `Err` → `break`
  → `metadata(final_p)` 无文件 → **瞬间 503**；且条目**永不出表**（已无人再调 `finish`）。
- **与「无 ffmpeg 进程 + ≈0.01 s 返回」完全吻合**：若真是转码在途，`Role::Wait` 应阻塞数十秒，而非 0.01 s。

### 事实 5：旁证 —— 孤儿 `.part`（pump 未走收尾的独立痕迹）

`proxies/` 下存在孤儿半成品，形状为 `<item_id>-speed-<N>.mp4.part`（取证样本 3 个）。
`.part` 的清理同样散落在各收尾路径里（`:4614`/`:4659`/`:4677`/`:4683`）
⇒ 孤儿 `.part` = 「pump 未走到任何收尾」的**同源痕迹**，与「条目泄漏」互为印证。

### 事实 6：这是**进程内存态** ⇒ 重启 orig-tg 即解（同时也是判据）

`TRANSCODE_INFLIGHT` 是 `static OnceLock<Mutex<HashMap<TranscodeKey, TranscodeDone>>>`（`:3986-3992`），
纯内存、不落盘 ⇒ **重启进程后表清空，同一请求应恢复为 `live`/`proxy`**。这解释了「为什么有时要重启才恢复」。

## 复现

1. 正常态起 daemon + orig-tg（**不要**用 `ORIG_TG_OFFLINE=1`）。
2. 对某条目请求 1x `/stream`，令其 pump 在一次异常终止中结束（panic / 被 drop —— **成因待定，见「待查」**）⇒ 该变体条目残留。
3. 之后反复请求同一条目同变体 ⇒ **每次瞬间 503**，且 `ffmpeg` 进程数 = 0。
4. **对照**：`?speed=2` 正常 206 / `x-orig-stream: proxy`（不同 `TranscodeKey`，未被污染）。
5. **重启 orig-tg** ⇒ 同请求恢复 `live` / `proxy`（不再 503）。

## 待查（本档未定，交给实现方定位）

- **pump 为什么会「在 `finish` 前异常终止」**：本档已证明「泄漏的**机制**」，但**未定位触发它的具体 panic 点**。候选：
  - `transcode_inflight().lock().expect("transcode map poisoned")` —— 若某处**持锁期间 panic** 会**毒化互斥锁**，
    此后每次 `lock()` 都 panic（级联）。需查是否存在「持锁期间可能 panic」的代码。
  - `tokio::spawn` 任务被运行时取消。
  - 其它 `unwrap` / `expect` 点。
  ⇒ **定位前不得宣称已修**：只加「出表兜底」也能消除用户可见后果，但**根因仍在**。

## 修复（方向；**本档不改代码**）

**总目标：任何情况下，单飞表都不得留下「无 pump 认领」的条目；即便留下，等待方也必须能自愈。**

1. **保证 `finish()` 必定执行（P0）**：把「出表」从「pump 内的闭包」上移为**作用域守卫**（RAII：`Drop` 时出表 + 唤醒），
   使 panic / 任务取消也必然出表；或对 pump 的 `JoinHandle` 加监控，任务结束即校验并出表。
2. **`Role::Wait` 自愈（P0）**：等待方发现「发送端已关闭 / 超时但无代理」时，**主动 `remove` 该键**（确认无新 pump 认领后）
   并**按冷启动重新起转码**（而非直接 503）。可复用既有 `stall_limit`（`:4605`）思路。
3. **孤儿 `.part` 一并处置（P1）**：启动时或 LRU 扫描时清理「无对应在途转码」的 `.part`
   （当前 `enforce_proxy_budget` 明确「不碰 `.part`」）。
4. **不推翻既有边界**：不得回退 BUG-273（投递泵）、BUG-274（资源争用）的既有结论；
   不得改变 `TranscodeKey` 语义（不同倍速独立缓存，BUG-226）。

## 取证补充二（2026-10-12，只读取证 —— 定位泄漏触发点，修正根因排序）

> 本节回答「待查」里的「pump 为何在 `finish()` 前异常终止」，**不改写上文**：
> 上文的机制（条目残留 + `Role::Wait` 无自愈 + 重启才解）全部仍然成立；修正的是**触发点排序**——
> 最可能的路径**不是**「pump panic」，而是 **handler 在占坑后、spawn 前被取消**（该路径下**根本没有 pump**）。
> 取证方式：只读代码 + git log；未改任何文件、未连任何服务。

### 结论 1：互斥锁中毒今日不成立（两处 `lock()` 都在不可能 panic 的区间）

- 注册点 `routes.rs:4337-4346`：持锁区内只有 `HashMap::get/clone/insert`——**无 await、无用户代码、无 IO** ⇒ infallible。
- 出表点 `finish()` `:4466-4476`：guard 是语句级临时量，`remove` 不 panic；`done_tx.send` 在锁释放之后、且 `Err` 已被 `let _` 吞掉。
- pump 内 `unwrap/expect` 全清单里唯一的生产 panic 点是 `:4571` `child.stdout.take().expect("stdout was piped")`——
  但 `command.spawn()` 刚成功且 `.stdout(Stdio::piped())` 已设 ⇒ `stdout` 必为 `Some`，**实际不可达**。
- ⇒ 「持锁期间 panic 毒化 Mutex」是**一次编辑之隔**的脆弱性（一旦毒化：`:4337` 每个新请求 handler panic→500、`:4472` 每次 `finish` 在 `send` 前 panic ⇒ 表只增不减、永久冻结），
  但**不是本次缺陷的触发点**。

### 结论 2：新路径 A（最重要）—— 占坑后、spawn 前 handler 被取消 ⇒ 无 pump 的纯孤儿条目

- 时序：`insert` 在 `:4342`，`tokio::spawn(pump)` 在 `:4411`，中间有 **3 个 await**：
  `:4389`（`.part` metadata）／`:4391`（`serve_local_file`）／`:4410`（`ffmpeg_config().await`）。
- 客户端断开 ⇒ hyper 丢弃 handler future ⇒ 任务在任一 await 点被取消 ⇒ **已入表的条目永无 pump 认领**；
  `tx` 随 future drop ⇒ watch 发送端全灭 ⇒ 该键此后所有请求 `changed()` 立即 `Err` → `break` → 无代理 → **瞬间 503、永不自愈**。
- 放大器（显著提高命中概率）：
  - 首请求的 `ffmpeg_config().await` 要跑 ffmpeg `-hwaccels`、`-encoders`、`nvidia-smi`、powershell CIM **4 个子进程**
    （`download-engine/crates/orig-tg/src/ffmpeg_caps.rs:705-759`），窗口可达数百 ms（`OnceLock` 缓存后才缩到一次 yield）；
  - 这些 HEVC 条目正处于 **BUG-207 已记载的 abort-and-re-request 风暴**中（20 s 内 97–137 次请求），高 churn 反复命中该窗口。
- 附带变体（无需取消也能造成同样孤儿）：`.part` 在 `:4389` 存在、但被并发 pump 失败删除后 `serve_local_file` 打开失败 ⇒ `?` 提前返回（`:4397`）⇒ 同样留下无 pump 的孤儿条目。
- **症状吻合**：`tx` 随 future drop ⇒ `changed()` 立即 `Err` ⇒ 503 在 ≈0.01 s 返回（与实测吻合）；「重启才恢复」证明条目在存活进程内永不出表 ⇒
  唯一泄漏路径 = **没有 pump 来 finish**。这正对应「瞬间 503」这一实测特征。

### 结论 3：原候选路径的降权与排除（附证据）

- **pump panic（`:4571` expect）**：理由齐但代码上不可达 ⇒ 仅作理论存在。
- **pump 被 drop（runtime shutdown）**：= 重启本身，不构成存活进程内的泄漏。
- **pump 挂起不到尾部**（`ever_read=false` 的僵死 ffmpeg 不被 stall 杀——`:4609` 的 stall 检测有 `ever_read` 前置条件）：
  症状应为 **600 s 超时后** 503，与实测「≈0.01 s」矛盾 ⇒ **降权**。
- **同键覆盖/替换**：map 仅在 `None` 时 insert（`:4340-4344`），在途请求只 `rx.clone()` 走 Wait ⇒ 条目永不被替换；
  但这带来放大器：**孤儿键被永久占死**，后续请求全部 Wait、无人能再 Start，重启前无任何重试可能。
- **`.part` 残留 + `:4293` 命中判断**：命中只判 `metadata(&final_p)` ⇒ 不制造假命中、**不构成泄漏**
  （残留 `.part` 只影响 `:4387-4405` 的 Range 206 服务，可能吐出陈旧/截断字节——是正确性问题，非泄漏）。
- **近期改动**：`git log -15 -- routes.rs` 显示并行会话近期动的是 caption / photo bytes / cache-task / N+1，**不触碰转码链路**；
  转码代码最后一次被改是 `99ce3c7`（2026-10-09，BUG-229，proxy 磁盘预算 + per-speed profile）与 `981f877`（2026-09-30，BUG-208，端点初建）
  ⇒ 机制自 `981f877` 即存在，**不是近期回归**。

### 结论 4：修复的必经点（仅位置；本档不改代码）

1. **注册处 `:4337-4346`（特别是 `:4342` insert 点）**：RAII 出表 guard 的诞生点，须持 `TranscodeKey` + `watch::Sender` + 表引用，
   `Drop` 即出表——**兜住路径 A 的「spawn 前取消」窗口**。
2. **spawn 处 `:4411`**：guard 所有权随 pump future 一起 move，使「pump panic / future drop」也触发出表。
3. **`finish()` `:4466-4476`**：现有出表口；RAII 化后 = 显式 early-remove + disarm guard，5 个调用点（`:4481/:4567/:4593/:4616/:4688`）语义不变。
4. **`Role::Wait` 分支 `:4349-4380`**：自愈必须区分「完成但代理没落盘」vs「孤儿（sender 死且表仍有条目）」，并允许孤儿键被接管重置——
   否则「孤儿键被 Wait 永久占死」会让单纯出表也无法恢复该键。

### 新增判据（建议并入「验收证据」清单，编号顺延；本档不改写原清单）

7. **路径 A 可证伪**：在 `:4342` 与 `:4411` 之间注入取消（测试内 abort handler future；**反向证伪**：保证窗口内必被取消）：
   - 修复前：该键残留 + 后续请求瞬间 503；
   - 修复后：条目必被清理（RAII guard 生效），且该键可被重新 `Start`。
   **反向证伪**：若 guard 只挂在 pump 侧而未覆盖 spawn 前窗口 ⇒ 修复后仍复现 ⇒ 判据失败。

## 验收证据

（状态 `open`，尚无验收证据。修复后必须满足的**可证伪判据（预先声明）**：）

1. **泄漏可自愈 / 可恢复**：人为制造「条目在表内、但无 pump 且代理未产出」状态（**反向证伪注入**）后请求该变体：
