# BUG-481: dev_services 在 release 栈共存时静默漂移、静默杀进程、状态误报 —— 整条 dev 流程跑不通

- 状态: fixed
- 发现日期: 2026-10-28
- 模块: build
- 严重程度: high

## 现象

用户原话：「http://localhost:5180/ 全挂. 仍然存在逻辑问题,无法验证dev=没有任何修复. 之前我启动你给我的脚本全坏,全烂. 整条流程完全跑不通.」

实测本机状态（2026-10-28 05:50）：
- 19786/19787 被 **release 壳栈**占用（`tauri-shell\src-tauri\target\release\orig-daemon.exe`，
  pid 39616/32152，2026-10-28 01:47 由壳 orig-hub.exe pid 39552 拉起；二进制为 00:09 构建，
  **早于**当日 03:24 的 dev 修复构建）。
- dev 栈日志显示 daemon 每次启动都被挤漂到 29786，反复重启十余次。
- 5180（vite）无监听 —— 浏览器打开即死页。
- `dev_services.py --status` 对 19786 探活成功但 `tg_port/tg_running` 全为 null，
  误报「orig-tg not running」。

## 根因

`scripts/dev_services.py` 四处逻辑缺陷（release 栈共存时全部触发）：

1. **静默漂移**：19786 被占时 `free_port` 清理失败/未生效后，daemon 内置顺延兜底把 dev
   daemon 漂到随机高位端口（29786），脚本不校验、不报错 —— 前端从 19786 起找，找到的是
   release 栈，dev 修复全部不可见（「无法验证dev=没有任何修复」的直接机制）。
2. **端点文件互覆**：`start_daemon` 注释明言「dev 栈与 release 壳共用数据根时，运行态
   （端口/端点文件/任务库/会话）必须分开，调用方显式给出」，但 `main()` 调用时
   **从未传 `extra_env`** —— dev/release 写同一个 `daemon.endpoint`，后写方顶掉先写方，
   壳与 dev 互相串线。
3. **静默杀用户进程**：`free_port` 对占 19786 的**任何**进程 `taskkill /F`，包括用户
   release 壳的后端 —— 触发「脚本杀壳→壳重启→再杀」的端口战争。
4. **状态误报**：`--status` 只探 `GET /api/config` 成功即报 ready，不区分应答者是谁；
   release daemon 的 config 无 tg 字段，输出全 null 的「假就绪」。

本质：规范端口 19786/19787 是**排他资源**（dev/release 共享数据根，双栈并跑还会引发
SQLite 写锁与 TG 同 session 双连接），但脚本按「可共存」设计，错误状态不可表达。

## 修复

`scripts/dev_services.py` 改为**排他 + 拒绝 + 自证**模型：

1. `listener_pid` / `exe_of` / `classify_owner`：启动与状态探测先回答「19786 上是谁」
   （dev / release-shell / other / unknown，路径 resolve 比对，fail-closed）。
2. `--start`：占端口者为非 dev 栈 → **拒绝启动**（exit 3），打印 holder pid/路径/归属与
   处置指引；绝不漂移、绝不代杀。
3. `--start` 启动后自证：`/api/config` 的 `port` 必须等于规范端口，否则 kill **自己刚拉起
   的子进程**（非第三方进程）并报错（exit 6）—— 漂移状态不可存在。
4. `free_port` 收窄：只清「与 `DAEMON_EXE` 同路径」的 dev 栈自身僵尸，第三方监听者不碰。
5. `--status`：输出 `owner/holder_pid`；应答者非 dev 栈时明确 WARN 并返回非零（exit 7），
   杜绝把 release 栈误报成 dev 就绪。

排他契约写入脚本 docstring：dev 栈与 release 壳**互斥**使用规范端口；数据根共享在排他
前提下是安全的（同一时刻只有一个栈在跑）。

## 关联

- BUG-178（fixed）：端口顺延兜底的来源 —— 该兜底对 release 壳是自愈，对 dev 栈是
  静默漂移的祸根，本修复在 dev 启动路径上把它变成「显式失败」。
- BUG-474（open）：同机多实例抢端口致 TG 断链；与本 bug 同一根（端口排他性未建模）的
  两个面。
- BUG-482（open）：release 壳自身退化出双 daemon + 双 tg，壳侧 spawn 监督逻辑待查。

## 验收证据

验收命令（跨机器可复跑；前置条件=release 壳栈在跑、5180 无监听）：

1. `python scripts/dev_services.py --status`
   → 输出 JSON 含 `"owner": "release-shell"` 与 `"holder_pid"`，stderr 明确提示
   「port 19786 is served by a NON-dev stack」，exit code 7（非零，不再假就绪）。
2. `python scripts/dev_services.py --start`
   → stderr 输出 `REFUSED: port 19786 is held by pid 39616 (...owner=release-shell)`
   及处置指引，exit code 3；执行后 release 栈进程（39552/39616/32152）原样存活
   —— 拒绝路径零杀戮。
3. 修复后 `python scripts/check-bugs.py` 门禁通过。

排他前置解除（用户 2026-10-28 06:03 批准「A：清理 release 栈」）后的整链验收：

4. `Stop-Process` 清掉 release 栈五进程（39552/39616/32152/8500/24064）→ 三端口全空、
   无 orig 残留进程。
5. `python scripts/dev_services.py --start` → dev daemon pid 39788 落在规范端口 19786，
   owner=dev；tg 插件 running:true@19787。
6. 追记修复：`emit_status` 原读的顶层 `tg_port/tg_running` 在 config schema 中不存在
   （真源是 `plugins[]` 按 id 取，与前端 `findPlugin` 同源）—— 已对齐，`--status` 输出
   `ready:true, owner:dev, tg_running:true`，exit 0。
7. vite(:5180) 起服 HTTP 200；`node tauri-shell/verify/_probe_episode_actions.cjs`
   → **10/10 PASS**（几何断言 + 截图），BUG-476~478 挂起的渲染级验收一并闭环。
