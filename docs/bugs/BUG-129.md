# BUG-129：`addEpisode` 默认按槽位 upsert —— 静默覆盖该槽位已有条目

- 状态: fixed
- 严重程度: low
- 模块: engine
- 发现日期: 2026-09-22

## 现象

`POST /api/media/series/:id/episodes`（前端封装 `api/media.ts:314` `addEpisode`）
默认 `episodeNo = 1`，语义是**按槽位 upsert** —— 把条目放进 `S1E1`，
**若该槽位已有条目，则直接覆盖**：不报错、不提示、被顶掉的原条目去向不明。

工程师在 BUG-126 的活体验证里实测到：默认槽位下 `389` **顶掉了** `390`。

## 可达性：当前**无用户可达路径**（已核实）

`addEpisode` **全前端零调用** —— 只在 `tauri-shell/src/api/media.ts:314` 定义：

```sh
grep -rn "addEpisode" tauri-shell/src | grep -v "api/media.ts:314\|export async function"
# => 空
```

前端「加入剧集」实际走的是 `appendEpisodes`（`SeriesDialog.tsx:142`）→
`/api/media/series/:id/episodes/append`，**顺序追加、不挤占已有槽位**，不受本条影响。

所以严重度定 **low**：**不是**「用户现在会丢数据」，而是**潜伏隐患**。

## 为什么仍要登记

1. **端点暴露在 REST 上**，任何外部调用、脚本、或将来新增的前端入口都会踩到，
   而踩到的表现是「静默覆盖」—— 用户只会发现「我的一集不见了」，且无从归因。
2. 这是 **BUG-113 第 5 条**（`attachEpisodeSource` / `detachEpisodeSource` 定义但全前端零调用）
   的**同类**：**定义了却没人用的 API 最容易在无人验证的状态下腐化** ——
   没有调用方，就没有任何一条路径会暴露它的语义问题。
   本项目已两次出现这个模式，值得当成一类问题看待。

## 修复方向（已按**方案 B** 落地）

- **优先确认有没有外部消费者**（脚本 / 文档 / 第三方）。若确认没有：
  - 方案 A：**删掉该端点**（连同 `addEpisode`），让「按槽位覆盖」这种危险语义根本不存在。
  - 方案 B：保留但**要求调用方显式表达覆盖意图**（如必填 `overwrite: true`），
    缺省时返回 **409 冲突**并告知占用者，由调用方决定。
- **不要**只改默认值（例如默认改成「追加到末尾」）—— 那会让端点名与语义更不一致，
  且仍然保留一个「按槽位覆盖」的入口。

### 选 B 的理由（与 A 的取舍）

外部消费者核实结果：**无**（`grep -rn "addEpisode" tauri-shell/src` 只命中定义本身
`api/media.ts:577`，无调用点；`POST /api/media/series/:id/episodes` 亦无仓内调用）。
既已确认零消费者，A（删端点）确实更彻底。但仍选 B，理由三条：

1. **端点是 REST 契约的一部分**，删除会改变已发布接口（外部脚本/文档/第三方工具
   随时可能已在用，只是本仓看不到）。B 把危险语义**关进笼子**而非拆掉梯子，回退成本低。
2. B 的判据（409 + 原条目仍在）**可测**；A 的判据只是「grep 剩一条路由」——
   证明的是「东西没了」，不是「语义安全了」。本条的价值恰恰在语义。
3. 端点名字 `addEpisode` 本身没错，错的是**默认按槽位覆盖**。B 保留端点、只收回
   默认 destructive 行为，符合「不要只改默认值」这条自我约束 —— 我们改的不是默认值，
   是**未经许可就允许覆盖**这件事。

## 验收判据（已补齐）

- 若选方案 A：`grep -rn "series/:id/episodes\"" download-engine/ tauri-shell/` 应只剩 `/append` 一条路由；
  且 `cargo test -p orig-tg` 无回归。
- 若选方案 B：新增一条单测 —— 槽位已被占用且未传 `overwrite` 时返回 **409** 且**原条目仍在**
  （判据要写「原条目仍在」，不能只断言「返回 409」—— 否则「先删后报错」也能过）。

## 关联

- BUG-113 第 5 条（同类「定义但零调用」的 API）、BUG-039（同槽多来源）、
  BUG-126（同一次活体验证中顺带发现，与 tombstone 语义相邻）。

## 修复

按**方案 B**（要求显式覆盖意图，缺省 409）落地，三处改动：

1. **`download-engine/crates/orig-tg/src/routes.rs`** —— `EpisodeReq` 增 `overwrite: Option<bool>`；
   handler 在 `add_episode` **之前**查槽位占用，占用且未获准时返回 **409**，
   错误信息里带占用者的 `itemId`（否则调用方无从决定「换槽还是换条目」）。
2. **`download-engine/crates/orig-tg/src/media.rs`** —— 新增
   `Store::episode_slot_occupant()`（查槽位占用者）与 `EpisodeSlotOccupant`。
   判定键与 upsert 的 `ON CONFLICT(series_id, season, episode_no)` **逐字对齐**。
3. **`tauri-shell/src/api/media.ts`** —— `addEpisode` 的 body 类型补 `overwrite?: boolean`。

### 三条刻意的设计决定

- **查在写之前**：判据「原条目仍在」只有在「先查后写」下才成立。先写后判的话，
  等于已经覆盖完了再告诉调用方「哦原来有人」—— 那正是 BUG-129 本身。
- **占用者就是同一条目时不报 409**（幂等重放）：调用方重试同一次请求不该被逼去开
  `overwrite`，而 `overwrite` 恰恰是本条要拦的危险动作。无副作用的重试不该被当成冲突。
- **合集展开的中间号不算占用**：`episode_no_end`（BUG-039）占的中间号不是 upsert 的冲突键，
  按它判会出现「报了 409 但其实不会覆盖」或「覆盖了却不报」的错位。

### 未采纳的做法

- **只改默认值**（缺省改成「追加到末尾」）—— 登记时已自我否决：端点名与语义会更不一致，
  且「按槽位覆盖」这个入口仍然开着。
- **方案 A 删端点** —— 见上文「选 B 的理由」第 1、2 条。

### 判据 2 的落地（409 且原条目仍在）

测试 `add_episode_occupied_slot_conflicts_and_keeps_original_bug129` 复刻现场
（`390` 已占 S1E1，`389` 带着默认 `episodeNo` 进来），断言**四件事**：

1. 返回 **409**，且错误信息含占用者 `itemId`；
2. **原条目仍在** —— 重读槽位，`item_id` 仍是 `390`、`episode_id` 未变、
   该季行数仍为 1（**顶掉 ≠ 删旧建新**，这是「先删后报错」骗不过去的地方）；
3. 显式 `overwrite: true` **真的能覆盖** —— 否则修复等于把按槽位写入整个焊死；
4. 空槽与别的季**不受影响** —— 闸只拦「已占用」。

### 反向证伪

把闸门条件改成 `if false && ...`（即退回修复前的静默覆盖）后重跑：

```

panicked at crates/orig-tg/src/routes.rs:8618:
BUG-129: 槽位被占用且未传 overwrite 时不得静默覆盖

```

失败被精确归因到被撤掉的那道闸，不是环境问题。
