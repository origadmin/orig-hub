# BUG-129：`addEpisode` 默认按槽位 upsert —— 静默覆盖该槽位已有条目

- 状态: open
- 严重程度: low
- 模块: engine
- 发现日期: 2026-09-22

## 现象

`POST /api/media/series/:id/episodes`（前端封装 `api/media.ts:314` `addEpisode`）
默认 `episodeNo = 1`，语义是**按槽位 upsert** —— 把条目放进 `S1E1`，
**若该槽位已有条目，则直接覆盖**：不报错、不提示、被顶掉的原条目去向不明。

工程师在 BUG-126 的活体验证里实测到：默认槽位下 `389` **顶掉了** `390`。

## 可达性：当前**无用户可达路径**（已核实）

`addEpisode` **全前端零调用** —— 只在 `tauri-shell/src/api/media.ts:314` 定义：

```sh
grep -rn "addEpisode" tauri-shell/src | grep -v "api/media.ts:314\|export async function"
# => 空
```

前端「加入剧集」实际走的是 `appendEpisodes`（`SeriesDialog.tsx:142`）→
`/api/media/series/:id/episodes/append`，**顺序追加、不挤占已有槽位**，不受本条影响。

所以严重度定 **low**：**不是**「用户现在会丢数据」，而是**潜伏隐患**。

## 为什么仍要登记

1. **端点暴露在 REST 上**，任何外部调用、脚本、或将来新增的前端入口都会踩到，
   而踩到的表现是「静默覆盖」—— 用户只会发现「我的一集不见了」，且无从归因。
2. 这是 **BUG-113 第 5 条**（`attachEpisodeSource` / `detachEpisodeSource` 定义但全前端零调用）
   的**同类**：**定义了却没人用的 API 最容易在无人验证的状态下腐化** ——
   没有调用方，就没有任何一条路径会暴露它的语义问题。
   本项目已两次出现这个模式，值得当成一类问题看待。

## 修复方向（待定，取决于有无外部消费者）

- **优先确认有没有外部消费者**（脚本 / 文档 / 第三方）。若确认没有：
  - 方案 A：**删掉该端点**（连同 `addEpisode`），让「按槽位覆盖」这种危险语义根本不存在。
  - 方案 B：保留但**要求调用方显式表达覆盖意图**（如必填 `overwrite: true`），
    缺省时返回 **409 冲突**并告知占用者，由调用方决定。
- **不要**只改默认值（例如默认改成「追加到末尾」）—— 那会让端点名与语义更不一致，
  且仍然保留一个「按槽位覆盖」的入口。

## 验收判据（修复后须补齐，现在还没有）

- 若选方案 A：`grep -rn "series/:id/episodes\"" download-engine/ tauri-shell/` 应只剩 `/append` 一条路由；
  且 `cargo test -p orig-tg` 无回归。
- 若选方案 B：新增一条单测 —— 槽位已被占用且未传 `overwrite` 时返回 **409** 且**原条目仍在**
  （判据要写「原条目仍在」，不能只断言「返回 409」—— 否则「先删后报错」也能过）。
