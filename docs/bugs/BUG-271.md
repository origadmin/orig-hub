# BUG-271: 入库队列缺「慢流」档 —— 90s 空闲看门狗只治「死」不治「慢」，一个每 89s 来一小块的流可无限期占住队首

- 状态: open
- 发现日期: 2026-10-10
- 模块: engine
- 严重程度: mid
- 登记: BUG-257 收口时主理人登记的方向 2，用户裁定「需」立项（2026-10-10 晚）。

## 现象

BUG-257 落地后：卡住的条目可被**立即取消**（实测 0.04s），单条失败不再弃单，重试幂等。
但停滞看门狗（`grammers.rs:625` `STALL_IDLE = 90s`，**空闲**计时）只包住单次 `body.next()`，
任何 chunk 到达即重置 ⇒ 一个「每 89s 来一小块」的慢流**永远不触发看门狗**，
作为队首把整个队列无限期占住——用户只能看到队列「在动」，实则停滞。

## 与 BUG-257 的边界

- BUG-257 治「死」（连接死了、字节停了）→ 可中断、不弃单；
- 本条治「慢」（连接活着、字节极慢）→ 需要独立的判定档位。
两者是不同的问题，混在一起会把「慢」误判成「死」。

## 修复方向（立项，实现时定档）

1. **墙钟上限**：给每条目加总时长死线（如 30min），与 90s 空闲看门狗**并存**——空闲治「死」、
   墙钟治「慢」。超墙钟 ⇒ 条目判失败（进 BUG-257 的失败隔离通道，不弃单、可重试）。
2. **可配置**：照 `resolve_cache_dir` 先例（请求 > DB `app_setting` > config > 默认），
   两个阈值均可配；90s 空闲硬编码现状一并收编。
3. **可观测**：超墙钟的原因串必须可区分（「耗时过长」≠「无字节」），前端经 BUG-257 C 段
   的分类链路落到独立 i18n key，不得落进 `tg.reasonNetwork`。

## 修复后必须满足（可证伪判据，预先声明）

1. 构造「每 89s 来 1 chunk」的夹具 ⇒ 旧代码永不超时（占住队首），新代码在墙钟上限内判失败且**不弃单**
   （后续条目继续）；
2. 反向证伪：去掉墙钟分支 ⇒ 判据 1 必须重新 FAIL；
3. 阈值可配置生效（改 app_setting 后无需重编译）；
4. 超时原因有独立文案，反向证伪：把该原因喂给 `describeTgFailure` 不得返回 `t('tg.reasonNetwork')`。
