# BUG-271: 入库队列缺「慢流」档 —— 90s 空闲看门狗只治「死」不治「慢」，一个每 89s 来一小块的流可无限期占住队首

- 状态: fixed
- 发现日期: 2026-10-10
- 模块: engine
- 严重程度: mid
- 登记: BUG-257 收口时主理人登记的方向 2，用户裁定「需」立项（2026-10-10 晚）。

## 现象

BUG-257 落地后：卡住的条目可被**立即取消**（实测 0.04s），单条失败不再弃单，重试幂等。
但停滞看门狗（`grammers.rs:625` `STALL_IDLE = 90s`，**空闲**计时）只包住单次 `body.next()`，
任何 chunk 到达即重置 ⇒ 一个「每 89s 来一小块」的慢流**永远不触发看门狗**，
作为队首把整个队列无限期占住——用户只能看到队列「在动」，实则停滞。

## 与 BUG-257 的边界

- BUG-257 治「死」（连接死了、字节停了）→ 可中断、不弃单；
- 本条治「慢」（连接活着、字节极慢）→ 需要独立的判定档位。
两者是不同的问题，混在一起会把「慢」误判成「死」。

## 修复方向（立项，实现时定档）

1. **墙钟上限**：给每条目加总时长死线（如 30min），与 90s 空闲看门狗**并存**——空闲治「死」、
   墙钟治「慢」。超墙钟 ⇒ 条目判失败（进 BUG-257 的失败隔离通道，不弃单、可重试）。
2. **可配置**：照 `resolve_cache_dir` 先例（请求 > DB `app_setting` > config > 默认），
   两个阈值均可配；90s 空闲硬编码现状一并收编。
3. **可观测**：超墙钟的原因串必须可区分（「耗时过长」≠「无字节」），前端经 BUG-257 C 段
   的分类链路落到独立 i18n key，不得落进 `tg.reasonNetwork`。

## 修复后必须满足（可证伪判据，预先声明）

1. 构造「每 89s 来 1 chunk」的夹具 ⇒ 旧代码永不超时（占住队首），新代码在墙钟上限内判失败且**不弃单**
   （后续条目继续）；
2. 反向证伪：去掉墙钟分支 ⇒ 判据 1 必须重新 FAIL；
3. 阈值可配置生效（改 app_setting 后无需重编译）；
4. 超时原因有独立文案，反向证伪：把该原因喂给 `describeTgFailure` 不得返回 `t('tg.reasonNetwork')`。

## 关联

- BUG-257（同子系统：可中断 / 不弃单 / 原因可观测——本条复用其全部机制）
- BUG-261（未缓存缺联动动作——失败条目的重试入口在那条覆盖）

  本条立项要「给每条目加**总时长**死线（如 30min）」，实现确实落了（`14e6257`），
  但落地形态是 `tokio::time::timeout(limits.wall, download)`（`routes.rs:983-1004`）——
  计时**只活在进程内的一次尝试里**；而 `main.rs:213-235` 的启动恢复会把任务
  **re-queued after restart** 并重新起一次尝试 ⇒ **重启即清零**。
  实测 `logs/orig-tg.log` 跨 ~3.6 小时有 **16 次进程启动**（部分间隔 ~1.5 分钟）
  ⇒ **30min 死线从未到期**（日志 `too slow` 0 命中；队首 `current_id` 21 小时未推进）。
  **本条状态保持 `fixed`**（「慢流不触发空闲看门狗」已治），缺口由 **BUG-276** 承接。

## 默认值取值理由（墙钟 1800s / 空闲 90s）

- **墙钟 1800s（30min）**：按可比速率反推，1 MB/s 的慢流 30min 可下 ~1.8GB——已覆盖
  绝大多数合法大条目；真正的超低速源（KB/s 级）30min 也足以证明「它就是慢」而非
  「它还在动」。中止是**可重试的**（失败隔离通道，续传已下部分），不弃单，故取保守下限
  无信息损失；来源持续低速的场景应调大 `download_item_max_secs`（app_setting，
  免重编译）。夹具用 0.1–1s 墙钟同路径验证。
- **空闲 90s**：维持原 `STALL_IDLE` 现值不变（本条只收编为可配置，不改语义；
  任意数值行为等价于修复前）。
- 钳制区间：墙钟 [0.1s, 24h]、空闲 [5s, 24h]——下限防止把看门狗配成「永不触发」。
