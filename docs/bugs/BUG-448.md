# BUG-448: 启动时 daemon 就绪被判超时——UI 冻结 5 秒、孤儿进程、界面「像死了很久才活」

- 状态: fixed
- 发现日期: 2026-10-27
- 模块: engine+shell
- 严重程度: high

## 与 BUG-446 的关系（先读这段）

用户这次的原话是「二进制一开就死」，而 **BUG-446**（`critical`，open）的标题就是
「release 壳打开即无响应（Application Hang），WebView2 进程从未创建」——同一个症状词。
必须先分清是哪一条在起作用，否则修了这条也白修：

| | BUG-446 | 本档 BUG-448 |
| --- | --- | --- |
| 现象层 | 窗口 `Responding=False`，**`msedgewebview2.exe` 从未创建** | 窗口响应，但 daemon 迟迟不就绪 / 壳等 5 秒后放弃 |
| 前端 JS | **一行都没跑** | 跑了（`ensure_daemon` 被调用过） |
| 根因层 | WebView2 运行时初始化挂起 | daemon 就绪被 TG 插件阻塞 + 壳超时/孤儿/主线程阻塞 |

**2026-10-27 19:00 实测：BUG-446 的 webview 层症状当前不复现**——`orig-hub` pid 25276
`Responding=True`，`msedgewebview2.exe` 已创建（`--webview-exe-name=orig-hub.exe`，
runtime 155.0.4283.62）。而同一份 trace 里 `ensure_daemon` **被调用过**，反证前端 JS 跑起来了。
⇒ 用户当前经历的「一开就死 / 卡很久才活」**是本档这条链**，不是 BUG-446 的 webview 挂起。

两者仍需分开跟踪：BUG-446 未被证明修复（可能随时复现，见其档内 10-20 后的环境变更），
本档的修复也**不能**当作 BUG-446 的修复证据。

## 现象

用户 2026-10-27 原话：

> 先解决二进制一开就死的问题. 当前整个流程有问题, 不然怎么会出现这种问题, 卡顿很久后界面正常.

三个可分辨的症状，实测指向**同一条链**：

1. 打开 APP ⇒ **界面冻结约 5 秒**（无响应，像死了）
2. 之后界面显示离线/空，**再过十几秒才「活过来」**
3. 全程无任何用户可见解释（没有「正在启动引擎」之类的进度）

## 根因（四段，缺一不可）

### ① daemon 侧：HTTP 服务被 TG 插件的启动等待卡住，最长 30 秒

`orig-daemon/src/main.rs` 的启动顺序：

```rust
let (listener, port) = bind_with_fallback(...).await;   // :121  端口先 bind
write_daemon_endpoint(port);                            // :130
let store = TaskStore::open(...).await;                 // :134
let state = Arc::new(AppState::new(...));               // :140
if config.tg_enabled {
    state.tg_start().await                              // :148  ★ 这里 await
}
let app: Router = routes::router(state.clone());        // :178
axum::serve(listener, app)                              // :210  ← 到这里才开始应答 /health
```

`tg_start_on` 会**等 orig-tg 真的开始监听**（`state.rs:589-620`），上限：

```rust
const TG_START_WAIT_TIMEOUT: Duration = Duration::from_secs(30);   // state.rs:56
```

⇒ **插件能不能用，决定了内核能不能被访问。** 这是顺序错误：`/health` 该回答的是「内核在不在」，与「Telegram 连没连上」无关。

### ② 壳侧：只等 5 秒，对方最长 30 秒 ⇒ 必然误判

```rust
// tauri-shell/src-tauri/src/lib.rs:203
let deadline = std::time::Instant::now() + Duration::from_secs(5);
```

5 < 30。只要 TG 那条腿慢（无凭证 / 无网络 / session 恢复 / 端口被占后重选），`spawn_daemon` **每次都必然返回 `Err("daemon did not become ready within 5s")`**。

### ③ 壳侧：超时不回收子进程 ⇒ 孤儿 daemon

```rust
// lib.rs:198-223
let (mut rx, child) = sidecar.spawn()?;
while … { … }
Err("daemon did not become ready within 5s".into())   // ← child 在此被 drop
```

`tauri_plugin_shell::process::CommandChild` 的 `Drop` **不杀进程**（要显式 `.kill()`）。于是：

- 被判定「失败」的那个 daemon **继续跑**，稍后 bind 成功并开始服务；
- 但 `state.child` 是 `None` ⇒ `daemon_status.managed = false`，壳**不认识它**；
- 下一次 `ensure_daemon` 若再 spawn 一个，两个 daemon 抢 19786，后起者走 `bind_with_fallback` → `panic!("no bindable port found…")`（`main.rs:46`）——**进程直接死**。

「二进制一开就死」正是这一段：用户重开 APP 时，新 daemon 抢不到端口 → panic → 退出。

### ④ 壳侧：`ensure_daemon` 是同步命令 ⇒ 冻结 UI 整整 5 秒

```rust
#[tauri::command]
fn ensure_daemon(app: …, state: …) -> Result<…, String>   // 没有 async
```

Tauri 的非 `async` 命令在**主线程**执行。`spawn_daemon` 里 `std::thread::sleep(100ms)` × 50 次 + 64 端口扫描全部阻塞主线程 ⇒ 窗口无响应 5 秒。这就是「卡顿」。

### ⑤ 前端：失败后不重试，界面停在「像死了」

`MainLayout.tsx:72` `ensureDaemon().then(…).catch(…)` 只跑**一次**，`.catch` 里退化成一次 `health()` 探测；探测也失败就 `setDaemonAlive(false)` 收工。**没有任何重试**，也没有「正在启动引擎（最长 30 秒）」的提示。用户只能自己重开。

## 修复

### ① daemon：先服务，后插件（根因）

把 `tg_start()` 从就绪路径上摘掉，改成 spawn 后台任务：

- `axum::serve` 之前只保留「bind + store + state + router」这些本地动作；
- TG 拉起放进 `tokio::spawn`，与已有的 `tg_supervise` 巡检同一语义（daemon 是 orig-tg 的唯一所有者，本来就有自愈循环）；
- `/health` 只回答内核状态。

> 纪律：**核心服务的可用性不得由可选插件的可用性决定。** 这条以后所有 sidecar 都适用。

### ② 壳：超时必须杀子进程

`spawn_daemon` 的失败分支先 `child.kill()` 再返回 `Err`，并**写 trace**（`daemon spawn timeout, killed pid`）。「我失败了」必须留痕，否则排查只能靠猜。

### ③ 壳：`ensure_daemon` 移出主线程

改 `#[tauri::command(async)]`（或 `async fn` + `spawn_blocking`），阻塞逻辑不再冻结 UI。

### ④ 壳：就绪等待与对方真实就绪时间匹配

deadline 从 5s 提到 **35s**（> `TG_START_WAIT_TIMEOUT`，留余量），并**每 500ms 写一次进度 trace**，让「等了多久、卡在哪一步」可查。

### ⑤ 前端：有界重试 + 可见进度

`ensureDaemon` 失败后按退避重试（3 次：1s / 3s / 6s），并在等待期间显示「正在启动引擎…」。**不做无限重试**（那是把系统的失职变成永不停歇的噪音）。

## 验收证据

### 复现脚本（可重跑，隔离端口 + 临时数据目录，不碰用户真实库）

`tauri-shell/verify/verify_bug448_startup_readiness.cjs`

做法：起一个 daemon，把 `ORIG_TG_PATH` 指向 **`notepad.exe`**（会启动、会常驻、**永不监听端口**）
⇒ `tg_start_on` 必然走满 `TG_START_WAIT_TIMEOUT`。然后每 100ms 打一次 `/health`，记第一次 200 的时刻。

### 修复前（`target/release/orig-daemon.exe`，2026-10-27 16:30 构建）

| 组 | 命令 | `/health` 就绪 | 结论 |
| --- | --- | --- | --- |
| TG 开启 + 替身不监听 | `--label before-fix --port 19890 --expect-max-ms 5000` | **10 387 ms** | FAIL（> 5000） |
| **对照：TG 关闭** | `--label before-tg-off --port 19892 --tg-enabled false --expect-max-ms 5000` | **1 080 ms** | PASS |

对照组的价值：把「慢」精确归因到 **TG 那条腿**（10 387 − 1 080 ≈ **9.3 s** 全是插件启动等待），
而不是 DB 打开 / 端口绑定 / 进程冷启动。**没有这个对照，任何「改完变快了」都不能算证据。**

### 修复后（`download-engine/target-check/release/orig-daemon.exe`，2026-10-27 19:00 构建）

| 组 | 命令 | `/health` 就绪 | 结论 |
| --- | --- | --- | --- |
| 修复后 · 首次 | `--label after-fix --port 19890 --expect-max-ms 5000` | **360 ms** | PASS |
| 修复后 · 复测（热缓存） | `--label after-fix-rerun --port 19892` | **453 ms** | PASS |
| 修复前 · 复测（热缓存，排除冷启动影响） | `--label before-fix-rerun --port 19890` | **8 466 ms** | FAIL |

**同条件 A/B（都是 TG 开启 + 替身不监听）**：

| | 修复前 | 修复后 | 倍数 |
| --- | --- | --- | --- |
| `/health` 就绪 | 10 387 ms / 8 466 ms | **360 ms / 453 ms** | **≈ 19–29×** |

复测这一组的用处：修复前的两次（10.4s / 8.5s）都远高于阈值，说明慢**不是冷启动**造成的；
修复后两次（0.36s / 0.45s）稳定在同一量级。

### 未在本轮验证的部分（如实记录）

- **S-2 无孤儿 / S-3 UI 不冻结 / S-4 失败留痕**：需要真实启动 APP（`ensure_daemon` 走 Tauri 命令、
  窗口是否响应），而本会话是非交互会话（合成输入到不了应用，见 `fluxdown-pages-2026-10-27.md` §1.1），
  且按项目纪律栈由用户手动控制，**未自行重启 APP**。这三项留待用户重启后按判据复核。
- 已验证的部分是**根因**（就绪被插件阻塞）与**修复手段的有效性**（同一二进制、同一输入，19–29× 差异）。

### 代码落地

- `download-engine/crates/orig-daemon/src/main.rs`：`tg_start()` 移出就绪路径，改为 `tokio::spawn`；`axum::serve` 不再等待插件。
- `tauri-shell/src-tauri/src/lib.rs`：
  - `spawn_daemon` 超时分支 **`child.kill()`** + trace（`spawn timeout …, killed pid=…`）；
  - 就绪时限 5s → `DAEMON_READY_TIMEOUT = 35s`（> `TG_START_WAIT_TIMEOUT`）；
  - 每 500ms 一行进度 trace（`waiting for daemon… Nms`）、成功时记 `daemon ready on P after Nms`；
  - `ensure_daemon` 改 `#[tauri::command(async)]`，阻塞逻辑不再占主线程。
- `tauri-shell/src/api/tauri.ts`：新增 `ensureDaemonReady()`——3 次有界重试（退避 1s/3s），
  每次失败先用 `daemonStatus()` 廉价探一次（daemon 可能只是「上次等得不够久」，已自己起来）。
- `tauri-shell/src/shell/MainLayout.tsx`：启动改用 `ensureDaemonReady()`。

### 判据（带被测前提）

- **S-1 就绪解耦**：同上脚本 `--label after-fix --expect-max-ms 5000` ⇒ **PASS**（预期 ≤2s）。
- **S-2 无孤儿**：失败路径下 `tasklist | grep orig-daemon` 恒 1 个；trace 必现 `killed pid=`。
- **S-3 UI 不冻结**：启动瞬间点侧栏立即响应（修复前主线程被占 5s）。
- **S-4 失败留痕**：占满 19786–19850 后启动 ⇒ trace 出现 `spawn timeout …, killed pid=`，不再是只有一行 `spawning daemon`。
