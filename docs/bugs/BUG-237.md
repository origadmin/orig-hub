# BUG-237：ffmpeg 设置未实现——引擎有解析链、壳层零呈现，参考项目未分析

- 状态: open
- 发现日期: 2026-10-09
- 模块: engine+shell
- 严重程度: mid
- 登记: 用户报告「ffmpeg 设置没有实现，参考项目没有分析」，
  参考项目 https://github.com/Lake1059/FFmpegFreeUI

## 现象

设置页无任何 ffmpeg 项：不显示检测到的 ffmpeg 路径/版本、无二进制管理
（内置/指定路径/未安装降级）、无转码参数设置。引擎侧已有第 4 落点解析链
（`routes.rs` resolve_ffmpeg_path：含 `%LOCALAPPDATA%/OrigHub/bin`），但这一事实
对用户完全不可见——本机 ffmpeg 已就位，设置页却无从知晓。

## 根因

ffmpeg 一直是引擎内部实现细节，从未被当作用户可见的**能力/插件**建模（与 BUG-238
同源）。参考项目 FFmpegFreeUI（ffmpeg 的 GUI 封装，参数可视化）尚未做调研分析，
转码参数（preset/crf/fps，见 EncodeProfile）暴露给用户的形态无设计输入。

## 修法方向

1. 先做 FFmpegFreeUI 调研（功能面：参数 UI、二进制管理、任务队列），产出分析结论；
2. 最小闭环：设置页 ffmpeg 状态行（检测路径/版本/是否可用）——与 BUG-233 的
   状态呈现同批实现；
3. 参数 UI 与「ffmpeg 作为插件/未安装走系统默认播放器」的形态随 BUG-238 插件框架
   一起定。

## 用户指令（2026-10-10）：硬解默认 + 多显卡 + 静态能力评估

用户 2026-10-10 三条指令（原文）：

> 3. 所以 ffmpeg 插件这块**需要提升优先级了**。

### 实测依据（2026-10-10，条目 673 = HEVC 1080p，`-t 60` 串行采样）

| 配置 | x 源实时 |
|---|---|
| 4x 档基线（现状：纯软解软编） | 3.37–3.59（全片 403s = 4.12） |
| **4x 档 + `-hwaccel auto`** | **6.76** |
| 4x 档 + 降 720p（单独 / 叠加硬解） | 3.97 / 6.82 ⇒ **降分辨率无增益** |
| 硬件编码 | nvenc 驱动不足（需 610.00+ / 现 560.94）、qsv 4.20x 慢于软编、amf 无卡 ⇒ **不可用** |

⇒ **硬解是唯一有效且零画质代价的杠杆**（4x 档提速 ~1.9×）；**降分辨率不解决**，
故**不引入分辨率切换、也不做「自动最佳分辨率」**（无收益的自适应是白做工）。

### ★ 静态评估的能力边界（必须写清，否则「推荐配置」会变成伪预测）

「根据配置估算」**能**回答：该机器**是否支持**硬解、支持哪些后端、哪些 codec 可硬解、有哪些 GPU 可选、
**有没有可用的硬件编码器**。这些是**布尔/枚举**，从 `ffmpeg -hwaccels` / `-encoders` + GPU 枚举即可得出，**不需要跑基准**。

「根据配置估算」**不能**可靠回答：**吞吐**。同一台机器、同一档位，不同内容的产出速率实测相差 **5 倍**
（720p H.264 = 16.6x vs 1080p HEVC = 3.5x，BUG-226 基准）—— 差异来自**内容**（编码/分辨率），不是来自配置。

⇒ 「推荐配置」的正确形态是 **保守默认 + 可回退**，不是精确预测：

1. **默认开硬解**，后端按 GPU 厂商优先序选择（详见设计档）；
2. **必须保留软件回退**：硬解初始化失败 / 输出像素格式不兼容时**自动回落软解**
   —— 不得让「硬解失败」变成「放不了」；
3. 允许用户在设置里**覆盖**后端与设备；
4. **不承诺**「按配置算出能跑几倍速」——那是基准的活，不是配置的活。
