# BUG-428: 自动连播依赖浏览器 `ended`，而播放一律走 live 转码流 ⇒ 播完浮不出「下一集」

- 状态: fixed
- 发现日期: 2026-10-26
- 模块: shell
- 严重程度: high
- 影响面: 剧集内连续播放；长分集（数分钟以上）上「下一集」倒计时可能永不出现，用户感知为「连续播放没了」

## 现象（用户 2026-10-26 第六次报障）

> 「播放按钮位置拍板错乱！我先次提出问题。同样藐视我的问题！
> 合并播放,连续播放,这些问题完全丢失,严重的记录错误,流程错误。」

用户把「连续播放」当成**已经丢失的能力**。读代码看它是完整的，所以必须拿运行时证据，
不能再用「代码里有」当作已实现。

## 取证一：播放链路本身是完整的（不是接线缺失）

| 环节 | 位置 | 结论 |
|---|---|---|
| 行内 ▶ | `SeriesDetail.tsx` `episode-row-play` | 点它调 `playEpisode(ep)` |
| 播放序列 | `MediaLibraryPanel.playItems` | 拉 `loadSeriesDetail` → `episodesToItems(d)` ⇒ **整部剧集** |
| 下一集 | `MediaViewer` `group` / `nextItem` / `nextUp` | 按 kind 分组后取组内下一项 |
| 倒计时 | `VideoPlayer` `onVideoEnded` | `nextUp && autoPlayNext` ⇒ 浮层 |
| 开关默认 | `usePlayerSettings` | `autoPlayNext: true` |

实测（剧集 219，2 集）：进入播放器后 `playlistCount=2`，`nextUp` 有值 —— **链路通**。

## 取证二：真正的断点 —— live 转码流没有「结尾」

播放器 `currentSrc` 实测是
`http://127.0.0.1:19787/api/media/items/662/stream`。两个端点的响应头对比：

| 端点 | 关键响应头 |
|---|---|
| `/api/media/items/<id>/stream` | `x-orig-stream: **live**`、`transfer-encoding: chunked`、**无 `content-length`**、**无 `accept-ranges`** |
| `/api/media/items/<id>/raw` | `content-length: 277059820`、`accept-ranges: bytes`、`cache-control: public, max-age=31536000` |

在页面里挂**游离** `<video>` 分别加载两个源（`_probe_raw_vs_stream.cjs`，item 1574）：

| 源 | 到 `canplay` | 元素 `duration` | 尺寸 | error |
|---|---|---|---|---|
| `/raw` | **372ms** | **694.07**（= 库内 11:34） | 720×1280 | null |
| `/stream` | 2463ms | **1.13**（且之后一路上涨） | 720×1280 | null |

`/raw` 解码完全正常，但**视频一律走 `/stream`**：`VideoPlayer` 里
`streamFirst = Boolean(compatSrc && compatSrc !== src)`，而视频条目的 `compatSrc`
恒存在 ⇒ `streamFirst` 恒为 `true`。这是 2026-10-09 的用户裁定（raw 直解卡、
转码流流畅），本档**不推翻该裁定**。

后果：live 流的元素 `duration` 只是**随下载量上涨的估算值**。16× 加速实测轨迹
（`duration` 与 `currentTime` 恒差 4~8s，66.6s 内 `ended` 从未触发）：

| t | currentTime | duration |
|---|---|---|
| 11ms | 0.17 | 9.43 |
| 2.2s | 15.05 | 26.1 |
| 4.3s | 29.37 | 35.97 |
| 64.4s | 362.13 | 366.93 |
| 66.6s | 370.59 | 374.07 |

⇒ `onVideoEnded` 绑的是元素 `ended` 事件，**在长分集上不可靠** ⇒ 浮层不出现。

### 补充事实（避免过度归因）

短分集上转码很快跑完，`ended` 是会正常触发的：RF 那一轮（30s 素材、关掉自动连播）
结束时实测 `ended=true, currentTime=30.04, duration=30.04`。
所以本缺陷的准确表述是「**`ended` 何时到、能不能到，取决于转码进度**」，
而不是「`ended` 永远不来」——分集越长、播放倍速越高，越不可靠。

## 修复

`tauri-shell/src/components/media/VideoPlayer.tsx`：

1. 新增常量 `END_EPSILON_SEC = 0.75`。
2. 新增 `onTimeUpdateEnd`（挂到 `<video onTimeUpdate>`）作为**播完兜底判据**，
   四个条件全满足才认：
   - 当前源**不可任意 seek**（`streamSeekableRef === false`，即 live/锚点流）；
     完整代理与 `/raw` 的 `ended` 可靠，不兜底 —— 避免库内时长有偏差时提前切集；
   - 真源总时长已知且 `> 0`（`contentDurationRef`，BUG-253 的权威值）；
   - 换算到**源内容时间**后距末尾 ≤ `END_EPSILON_SEC`；
   - 未在播放起点（`currentTime > 0`）且本次播放未触发过（`endGuardRef` 去重）。
3. `onPlay` 里复位 `endGuardRef`，否则「重播」后不再触发连播。
4. 时间换算必须走 `currentTime * speed + offset`：FRC 流媒体时间轴被压缩 `speed` 倍，
   锚点流的 `0:00` 也不是内容 `0:00`。
5. 浮层加 `data-testid="player-autoplay-next"` + `data-next-title` / `data-next-episode`，
   否则这条能力无法被端到端观测（同 BUG-138 给标题加 testid 的做法）。

**为什么用库内时长而不是元素 `duration`**：BUG-253 已确立「真源总时长来自
`GET /api/media/items/<id>`，不取 live 流的瞬时 `duration`」；实测 item 1574 的
库内 694.07s 与 `/raw` 元素的 694.07s **逐位相同**，可以当权威值。

## 关联

  播完判定不可靠，而非「缺少合并能力」；两档共用同一批取证。
- **BUG-253**：真源总时长来自 `GET /api/media/items/<id>`，不取 live 流瞬时 `duration`
  —— 本档的兜底判据直接复用该权威值。
- **BUG-262**（open→fixed）：整季开播入口。连播的**入口**已落地，本档修的是**播完触发**。
- **BUG-208**：解码不支持时切兼容流（`compatSrc` 的来源）。
- 2026-10-09 「stream-first 翻转」用户裁定：本档**不推翻**，只让连播不再依赖 `ended`。
- **BUG-034**：`timeupdate` 曾因「上报节流」被禁。本档用的是**纯本地数值比较**
  （不发起任何请求、不写存储），与那条铁律不冲突。
