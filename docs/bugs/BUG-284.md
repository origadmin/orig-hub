# BUG-284: 剧集合并把「同一集的内容」续编成新集号，而非按槽位归并为多源 —— 两条第 1 集合并后变成第 1、2 集，「一集多源」在合并场景永远不可达

- 状态: partial
- 发现日期: 2026-10-12
- 模块: engine+shell
- 严重程度: high
- 排期: 2026-11-10

> 来源：用户 2026-10-12 报障「我发现合并好像也有严重问题，比如**都是第一集合并后会变成 1,2**，
> 而不是**全都并入第一集不同源**。所以**单集多源之前说的已修复是严重误判，根本没有丝毫修复**。
> 还有**合并可能需要自动化一点**，简化人工操作，比如有些**有明确集数**的内容的合并操作。」
> **本档为任务文档**（用户 2026-10-12 定：代码由别的组负责，本团队只出登记与判据）。
> **登记规范**：遵循「内容数据不入库」原则（见 BUG-232）：不含真实频道名 / 消息文案。

## 现象

把两条**各含第 1 集**的剧集合并后，目标剧集的分集变成 **第 1 集 + 第 2 集**（两个分集），
而**不是**「第 1 集挂两个源」。用户据此判定「单集多源已修复」为**误判**。

## 根因

**合并去重只按 `item_id`、不按 `episode_no`；声明集号被占用时回退续编 ⇒ 同集内容被拆成连续多集。**

### 事实 1：合并去重维度是 `item_id`，不是槽位

`merge_one_source_in_tx`（`download-engine/crates/orig-tg/src/media.rs:2866`，被单源 `merge_series`（`:2773`）
与批量 `merge_series_batch`（`:2815`）共用）：

```rust
// media.rs:2954
if have.get(season).is_some_and(|s| s.contains(item_id)) { /* skipped */ continue; }
```

只判断「该 `item_id` 是否已在本季」，**不判断「该集号是否已有内容」**。

### 事实 2：集号分配在槽位被占时**续编**

```rust
// media.rs:2975-2985
let declared_free = (*episode_no..=declared_end.unwrap_or(*episode_no)).all(|n| !occupied_season.contains(&n));
let (slot, slot_end) = if declared_free { (*episode_no, declared_end) }
    else { let base = next.get(season).copied().unwrap_or(0) + 1; (base, end) };
```

目标已有 ep1 ⇒ `declared_free=false` ⇒ `slot = next+1` ⇒ **续编成 ep2**。

### 事实 3：端点注释自认不做内容级去重

`routes.rs:5321`（`merge_media_series`）：注释写明「**不做任何内容级去重……原样保留**」。

### 事实 4：这不是回归，是**从未实现** —— D1 挂了 20 天

- `docs/design/episode-multi-source-design-2026-09-22.md:786-793` 的 **D1** 原文：
  「合并剧集遇到『两边都有第 1 集』：同槽归并为多源，还是续编两集？」——状态**待拍板**；
  规划中的 `POST /episodes/:id/merge-sources`（T05）**全仓 grep 零命中**。
- 提交 `0bec3ed`（merge multiple sources atomically）**仅重构**（拆出 `merge_one_source_in_tx` + 加批量包装），
  diff 无任何同槽归并逻辑；`12aa870`（series-wall multi-select）**改动全在 `tauri-shell/`**，引擎零改动。
- 全仓 `docs/` 与项目记忆里**找不到任何**「单集多源已修复」的出处 ⇒ 该说法**无实现依据**（误判）。

### 事实 5：即便归并成多源，用户也**看不到、管不了**

多源结构（`media_episode_source`）与三个端点（挂 / 切 / 摘）都在，但：

- 前端 `attachEpisodeSource()`（`tauri-shell/src/api/media.ts:700-705`）**定义后全仓无调用（死代码）**；
  界面只有「切换 / 摘除」，**无「添加源」**（另见 BUG-113 缺口 5）。
- 生产库 `media_episode_source` 实测 **0 行**（255 集无一挂过第二个源）。

## 复现

1. 建两条剧集，各含「第 1 集」（或合并两条各含第 1 集的剧集）。
2. 合并 ⇒ 目标剧集出现 **第 1 集 + 第 2 集**（不是同集多源）。
3. 只读 SQL 佐证：

```sql
-- 目标剧集不应出现「同 (season,episode_no) 多行」；且 episode_source 应有多行
SELECT season, episode_no, COUNT(*) FROM media_episode WHERE series_id=<目标> GROUP BY 1,2 HAVING COUNT(*)>1;
SELECT episode_id, COUNT(*) FROM media_episode_source GROUP BY episode_id HAVING COUNT(*)>=2;
```

现状：前者 0 行（未归并）、后者 0 行（从未产生多源）。

## 裁定（2026-10-12，产品负责人拍板）

**D1 = A（同槽归并为多源）**：合并时**按 `(season, episode_no)` 同槽归并**，被归并方的条目
**降为该集的备用源**；**不得**续编成新集号。判据用设计文档 §12 D1 已实测的 L1（集号区间）→ L3（身份键）分层。

**同时要求「自动化」**：对有**明确集号**的内容，合并/加入时应**自动匹配**，不必用户手工逐条选。

## 修复（方向；**本档不改代码**）

1. **合并按槽位归并（P0，D1=A）**：`merge_one_source_in_tx`（`media.rs:2866`）在「目标槽位已有同集」时，
   不再续编，而是把源条目**挂为 `media_episode_source` 备用源**（复用既有 attach 语义，幂等）。
   主源归属按设计 §3.1 分层取优；**手动指定优先**（BUG-113 设计问题 1）。
2. **补「添加源」入口（P0，与 BUG-113 缺口 5 合并处理）**：把死代码 `attachEpisodeSource()` 接到 UI
   （分集来源区加「添加源」），否则归并结果用户仍不可见、不可管。
3. **合并自动化（P1）**：按集号（L1）自动匹配候选剧集；L3 身份键命中时**提示 + 用户确认**后归并
   （对应设计 §12 D2，**D2 仍待产品拍板**）。
4. **不可推翻**：`media_episode_source` 只接受 `kind='video'`（BUG-044 触发器）、
   `item_id` 全表 UNIQUE、建表批只允许新旧库共有列（BUG-032）。

## 实测回填（2026-10-23，BUG-407 落地后）

判据 1（同槽归并）与判据 4（自动化）**已成立**，判据 2、3 仍缺 —— 故状态标 `partial`，
不标 `fixed`。

| 判据 | 现状 | 证据 |
|---|---|---|
| 1. 同槽归并（两条各含第 1 集 ⇒ 一集多源、集数不增） | **成立（限于「同一份文件」）** | 单测 `download-engine/crates/orig-tg/src/media.rs` 的 `merge_series_merges_same_slot_into_multi_source_bug407`；端到端 `download-engine/verify/verify_bug407_408_merge.py` 场景 1（`added=1` / `mergedSameEpisode=2` / `episodes=4`）。⚠ 用户 2026-10-23 追加裁定：「没有 hash 说明没有文件，两边都是空，不存在合并」⇒ **两侧都没文件时不归并**（`merge_series_no_hash_never_merges_bug407`），本判据的前提是「两侧是同一个文件」，不是「集号相同」 |
| 2. 主源可控（按 §3.1 分层取优、手动指定不被覆盖） | **未做** | 归并后主源固定为目标原有条目；无「分层取优」，也无「手动锁定主源」字段 —— 与 BUG-113 设计问题 1 同批 |
| 3. 入口可达（分集来源区出现「添加源」） | **未做** | `attachEpisodeSource()`（`tauri-shell/src/api/media.ts`）仍无调用点 —— 同 BUG-113 缺口 5 |
| 4. 自动化（同剧同集号自动归并，不需逐条手工选） | **成立** | 同上；L1（集号）自动、L3（hash）自动且冲突即分开，全程无人工选择 |
| 5. 真实 UI 可核（第 1 集可见 2 个源、可切换） | 结构已具备 | 剧集详情已渲染 `sources` 并支持切换主源（BUG-039 起）；本批未新增 UI 断言 |
| 6. 不推翻（BUG-044 video-only / BUG-032 共有列 / `item_id` 全表 UNIQUE） | **成立** | 归并只写 `media_episode_source`（触发器守 video-only）与 `media_episode_image`；`item_id` UNIQUE 冲突如实记入 `skipped` |

**反向证伪**：关掉 hash 判据 ⇒ 判据 1 的用例 FAIL（`added` 3 ≠ 1，即退回「续编成 1,2」的原缺陷）；
把判据退回「同槽即同一集」⇒ 无 hash 用例 FAIL（两条空记录被错误钉成一集）。

**原报障的「都是第 1 集合并后变成 1、2」现在如何解释**：若两边是同一个文件（hash 相同），
合并后是**一集多源**；若两边都不是文件（无 hash），就是两条空记录，**本来就不该合并**。
用户 2026-10-23 的追加裁定正是把这两种情况分开。

**仍未做（转 BUG-113）**：主源分层取优 + 「添加源」入口。二者是**可见性/可控性**缺口，
不影响「同集归并」本身的正确性。
