# BUG-209 倍速播放丢帧：转码档未限帧率 + UI 倍速封顶 2x

- **状态**: fixed
- **发现日期**: 2026-09-30
- **模块**: engine
- **严重程度**: mid

## 现象

用户以 2x/4x 倍速审看视频时画面丢帧、感知卡顿（「我要的是测试极限,2X甚至4X,而不是默认播放」）；
此前 BUG-207/208 只验证了 1x 默认播放的流畅性，倍速场景从未测量过。

## 根因（A/B 实测，CDP 采样 `getVideoPlaybackQuality`）

| 场景 | 倍速 | 丢帧 | 停顿 | 结论 |
|---|---|---|---|---|
| 60fps 代理（修复前档位） | 2x | 546/1638 = **33%** | 0 | 源 60fps × 2x = 120fps 呈现需求，超显示器刷新率即按比例跳帧 |
| 60fps 代理 | 4x | 1638/3822 = 43% | 0 | 同上，240fps 需求 |
| **30fps 代理（fpsmax 30）** | 2x | **0/544 = 0%** | 0 | 30 × 2 = 60fps，恰好贴住刷新率上限 |
| 30fps 代理 | 4x | 547/1641 = 33% | 0 | 120fps 需求 → 60Hz 物理上限，无停顿、缓冲满 |
| 30fps 代理 | 8x | 1573/3770 = 42% | 0 | eff 7.28x 照跑，跳帧全为呈现上限 |

两个独立缺陷叠加：

1. **转码档（BUG-208）未限帧率**：`libx264 veryfast crf23` 原样继承源帧率，
   60fps 源把倍速下的呈现需求翻倍；
2. **UI 倍速菜单封顶 2x**（`RATES = [0.5..2]`），用户要的 4x 根本选不到。

投递/解码均无嫌疑：全程 0 停顿、缓冲领先 >1000s、无请求风暴——瓶颈是「内容帧率 × 倍速 >
显示器刷新率」的**物理呈现上限**，任何服务端算法都无法消除，唯一杠杆是把代理的帧率降下来。

## 修复

- 引擎（`routes.rs` 兼容流转码档）：加 `-fpsmax 30`——只在源超过 30fps 时丢帧
  （24fps 源不复制帧），解码与代理体积同步减半；ffprobe 复核 60fps 源产物 `avg_frame_rate=30/1`。
- 壳（`VideoPlayer.tsx`）：`RATES` 增加 `3x`、`4x`。

## 验收证据

- 入库脚本 `tauri-shell/verify/verify_playback_rate_limit.cjs`（`PROBE_ITEM=<id>` 可跨机器复跑，
  逐 1s 采样 2x/4x/8x 各 10s 的 presented/dropped/stalls/buffer）；
- 修复后 30fps 代理实测（本机）：2x 丢帧 **0**、4x 33%、8x 42%，全程 0 停顿 0 请求风暴；
- 修复前 60fps 代理对照：2x 33%（见上表），数据落 `verify_shots/probe_playback_smooth/rate_limit_report_*.json`；
- 倍速菜单截图 `verify_shots/probe_playback_smooth/D-speed-menu-4x.png`（8 档含 3x/4x，
  CDP 断言 `menu items 含 3x/4x` PASS）；ffprobe：`1280,30/1`（代理）vs `1280,60/1`（源）；
- `-fpsmax` 参数验证：ffmpeg 9.0.2 20s 样本转码成功且产物 30fps；
- `tsc --noEmit` EXIT 0；`cargo build --release -p orig-tg` + `sync-sidecars.sh` OK。

## 附带事实（不属本缺陷，留档）

- 首次播放的直播转码段在 2x 时曾出现 `aheadMin 0.2s` 的供数紧张与少量丢帧——直播段生产速率
  （~3.6x 实时）高于 2x 消费但冷启动期例外；「入库后台转码」立项后该窗口消失，代理命中后无此问题。
- 4x/8x 的剩余跳帧是 60Hz 显示器物理上限（每秒最多呈现 ~60 帧），观感为「快放的时间采样」，
  非卡顿；「解码吃力」提示文案在倍速下的建议（降速更流畅）方向正确，保留不改。

## 后续变更（2026-10-08）

本档原「验收证据」一节中「30fps 代理 2x 丢帧 **0**」**不可复现**。本机用同一脚本
`tauri-shell/verify/verify_playback_rate_limit.cjs` 的同源实测脚本
（`tauri-shell/verify/verify_playback_rate_profile.cjs`）重测：**2x 仍丢 10–23%**
（472@2x 15%→23% run-to-run），且「解码吃力」提示在 2x / 4x **均出现**、1x 干净。

当年立足点：把代理限帧率到 30fps，确实让「60fps 源 × 2x = 120fps」这一档不再超刷新率 ——
该判断**对 60fps 源成立**。**变的是前提**：库内主力内容实测是 **30fps** 源
（607 = H.264 480×852 30fps、598 = H.264 720×1280 30fps），其 2x = 60fps 正好顶死
60Hz 刷新率，**无余量**。

因此本档修复**有效但不充分**：限帧率把 60fps 源的 2x 从 33% 拉回 0，但对 30fps 源
2x = 60fps 顶死刷新率、呈现丢帧仍会触发「解码吃力」误报。剩余缺口转 **BUG-212** 承接。
本档状态维持 `fixed`（修复本身有效，只是不充分）。
