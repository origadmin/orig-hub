# BUG-226: 冷缓存换档/深位续播「卡」—— live 转码从 0:00 起必须追平全部已播内容；新增 `?t=` 锚点起转 + `?probe=1` 探针

- 状态: fixed
- 发现日期: 2026-10-09
- 模块: engine+shell
- 严重程度: high

## 现象

用户在 BUG-223 上线后真实播放反馈：**缓存加载导致卡的问题没解决**（即 BUG-223 判据⑤的体感残留：换档/首次进某档时卡，深位尤甚）。

## 定性证据（条目 630 = H.264 720x1280/49.8s；415 = HEVC 720p/189.6s；673 = HEVC 1080p/403s）

1. **冷换档位置丢失后再深位恢复会变成「等转码追上」**：BUG-225 修好后，30s 内容位置恢复到从 0:00 起转的 live 流上，浏览器要等转码推进到 15s 媒体（=30s 内容）才能出画；对长视频（40 分钟剧集 @ 深位）这是分钟级黑屏等待。
2. **ffmpeg 不是瓶颈，也不是本机个例**（裸进程基准，`-t 60` 采样）：630 全片 4x FRC = **3.0s（16.6x 源实时）**；415 = 4.8x；673 = **1.0x**（硬解 6.9x、superfast+硬解全管线 2.1x）**〔该「1.0x」2026-10-10 复核未复现，见文末「后续复核」〕**。1080p HEVC 全管线只有 ~1x 源实时，4x 播放消耗 4x 源实时 → 冷缓存 4x 供给必然追不上（旧实现下 673 冷 4x 的「卡」是供给物理上限，任何缓存命中后即消失）。
3. **实测冷 4x 换档首帧构成**（diag-result.json P3）：2.5s 出 metadata、2.81s 首次推进，随后满 4x 干净播完、无 waiting/stalled——供给充足的条目（720p H.264）换档体验已可接受，**卡的主根因就是「深位 + 从 0 起转」的追赶等待**。

## 方案

- **服务端**（`download-engine/crates/orig-tg/src/routes.rs`）：
  - `GET /stream?probe=1` → `{"ready":bool,"duration":s}`：只 stat 代理文件与回读条目时长，**不占单飞坑、不 spawn ffmpeg**；
  - `GET /stream?t=<源内容秒>`：`-ss t`（输入侧，置于 `-i` 前）从指定位置起转，**live-only**——字节与从 0:00 起的正式代理不同源，不落盘、不改名、不进单飞表（`registered=false`），客户端断开即杀 ffmpeg；`t<0.25` 归一为 None，`t` 钳进源内（≥时长-0.5s）。
- **前端**（`VideoPlayer.tsx`）：换档前探针目标变体 → 代理就绪直接换 src（Range 可拖、位置走 currentTime 恢复）；冷缓存且位置 ≥ 10s（`ANCHOR_MIN_CONTENT_SEC`，片头附近从 0 起转追赶代价小、且正式代理缓存只从 0:00 起转的 live 流上累积——这是 BUG-223 判据④「按速独立缓存」语义保持的前提）→ 带 `t=floor(内容秒)` 重锚，恢复媒体时间 = `(contentTime-offset)/speed`（<1s 残差）。live 流拖拽落点超出已转码覆盖范围（`bufferedEnd`+0.5s）时同样重锚（拖拽是显式意图，不设阈值）；覆盖范围内本地 seek。`contentOffset` 全链路（时间文案/进度条/aria/跳转上限）参与内容时间换算。

## 用户可见权衡

- 锚点流不进缓存：同一深位再次冷访问会重新起转（秒级），换取「任何位置即时出画」；从片头自然播放仍会累积完整代理。
- 1080p HEVC 冷缓存 4x 的供给缺口是硬件上限（1.0–2.1x 源实时 vs 4x 消耗），本修复不创造算力；候选后续（未拍板）：高速档降 preset（superfast+硬解实测 1.0x→2.1x）或高速档限输出分辨率。

## 修复后必须满足（可证伪判据）

1. **探针零副作用**：删代理后 `?probe=1` 返回 `ready:false` 且 2s 内磁盘上无 `.part`/新代理（修前：探针 URL 被当普通请求直接起转码 → FAIL）。
2. **冷缓存深位换档免追赶**：630 @30s 暂停态切 2x，wire 请求带 `t=`，首帧推进 ≤ 6s 且恢复后内容位置偏差 ≤ 2s（修前：请求无 `t`，恢复被 BUG-225 钳回 0 / 修好后则会陷入追赶等待）；片头阈值 10s 以内的换档不锚定（保缓存累积语义，BUG-223 回归 C10 依赖它）。
3. **锚点流不落盘**：锚点会话后该速度代理文件仍不存在。
4. **代理就绪时不锚定**：预构建 4x 代理后切 4x，wire 请求不带 `t=`（不浪费已缓存代理）。
5. **live 拖拽重锚**：锚点流上拖到未覆盖位置（0.9×49.8≈44.8s），wire 出现新 `t=44` 请求并 ≤ 6s 在目标 ±2.5s 出画。
   可执行形态：`tauri-shell/verify/verify_bug_226_stream_anchor.cjs`；单测 `parse_stream_start_*` 4 例（归一/放行/拒绝/钳制）。

## 后续复核（2026-10-10）：吞吐数字「673 = 1.0x」在本机未复现

> **本节为追加，不改写上文。** 触发原因：2026-10-10 回答「1080p HEVC 4x 怎么解决」时直接引用了上文
> 第 15 / 28 / 42 行的「673 = 1.0x 供给物理上限」，被一组独立实测推翻 ⇒ 该结论不得再作为前提引用。

**实测条件**：同一条目 673（`chat--1002533442302/2895-存在感零-EP6-….mp4`，HEVC Main 1920x1080 30fps
10.2Mbps 403s）、同机（i7-12700H / RTX3060 Laptop / ffmpeg 9.0.2）、`-t 60` **串行**采样、输出写 `%TEMP%`（不落仓）：

| 单元 | wall(s) | x 源实时 |
|---|---|---|
| 4x 档基线（现状：软解 + libx264 ultrafast）×3 | 16.73 / 16.91 / 17.80 | 3.59 / 3.55 / 3.37 |
| 4x 档基线 **全片 403s**（无 `-t`） | 97.72 | 4.12 |
| 4x 档基线 **深位** `-ss 300 -t 60` | 17.07 | 3.51 |
| **4x 档 + `-hwaccel auto`** | 8.88 | **6.76** |
| 1x 档（veryfast / crf23 / fpsmax30） | 41.25 | 1.45 |
| 1x 档 + `-hwaccel auto` | 32.22 | 1.86 |
| 4x 档 + 硬解 + `scale=-2:720` | 8.80 | 6.82 |
| 4x 档 + **仅** `scale=-2:720` | 15.12 | 3.97 |

**结论**：

1. **没有任何单元 ≈ 1.0x**。4x 档稳定在 **3.37–3.59x**（方差 ±0.11x，非偶发）；全片 4.12x ⇒ 排除「尾部拖慢」；
   深 seek 3.51x ⇒ 排除「深位塌速」。
2. 最接近 1.0x 的是 **1x 档（1.45x）** ⇒ 上文「673 = 1.0x」**极可能测于 1x 档，而非句中 630 所用的 4x FRC 档**；
   原文未标注 673 的档位，标签存在歧义。
3. ⇒ **「1080p HEVC 4x 供给物理上限 ≈1x」不成立**（本机 4x 档 3.4–4.1x）。**不得再作为前提引用。**
4. 本机实测：**硬解对 4x 档提速约 1.9×**（3.5 → 6.8x）—— 足以把 4x 从**临界**（3.5x，恰在 4x 边缘，与「4x 时卡时不卡」吻合）
   抬到**宽裕**（6.8x）。**降分辨率（`scale=-2:720`）无论单独或叠加硬解均无增益**（3.97 / 6.82x）。

**未决**：该数字是否来自另一台机器 / 另一热降频状态，无从考证 —— 上文引用的证据文件
`verify_shots/frc-hotfix/diag-result.json` 实为**条目 630 的播放快照**（键 `t/ct/dur/rs/bEnd/mode`），
**不含吞吐数据**。**若确来自他机，则不可跨机引用**；建议在原机重测后再定论。

**顺带实测（独立于本条，供后续引用）**：

- 生产转码命令**全程无 `-hwaccel`、无 `scale=`**（`download-engine/crates` 全 crate 0 命中）⇒ 现状纯软解软编。
- `media_item.width` / `height` **全库 374 条全 NULL**，且**无 codec 列** ⇒ 系统当前**不知道**内容的分辨率与编码。
- 硬件编码不可用：`h264_nvenc` 驱动版本不足（需 610.00+，现 560.94）；`h264_qsv` 能跑但 4.20x 慢于软编；`h264_amf` 无 AMD GPU。
