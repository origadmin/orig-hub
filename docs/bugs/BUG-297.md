## 现象

媒体库里一条已入库的内容，**说不出自己属于哪个相册组、属于哪部剧的哪一集**：

- 条目卡上只能显示 `item.title`（可能为空）与 `· {item.seriesTitle}`，而 `seriesTitle` 可能取到
  **占位名剧集**（`TG <chat_id> · <日期>`）⇒ 用户看到「丢失信息的视频」（BUG-283 复报的可见形态）；
- 更根本的是：**这不是显示问题** —— 条目在数据层**就没有**存放定位的位置。

### 「定位」是三段，分居三处，只有一段在条目上

| 段 | 内容 | 存放位置 | 是否必填 |
|---|---|---|---|
| 段① | 来源坐标 `<chat>:<msg>` | `media_item.ref`（`UNIQUE(source, ref)`） | **必填**（实测缺失 0） |
| 段② | 相册组 `<group_id>` | **只在 `media_message.group_id`**（流水表）；`media_item` **无此列** | **无**（条目侧不存在该字段） |
| 段③ | 剧集 / 季 / 集号 | **只在** `media_episode`（视频·音频）或 `media_episode_image`（图片） | **无**（挂靠是可选动作） |

⇒ 条目**只强制携带段①**。段②、段③ 都是**外挂**，可缺失、可错、可矛盾。
「入库后丢失自己的定位」= 段②、段③ 未随条目落定。

## 根因

### 事实 1：入库**确实按组**进行，组信息在入库路径上**齐全**

| 证据 | 位置 |
|---|---|
| 入队请求携带 `group_id` | `routes.rs:1267`（`EnqueueReq.group_id`） |
| 入队去重键按组：`g:{chat}:{group}` / 退化 `m:{chat}:{msg0}` | `routes.rs:1286-1292` |
| 任务上下文持有组：`task_group: task.group_id` | `routes.rs:2112` |
| 组级 caption 正文（组级事实）在 `prepare` 取一次：`group_desc` | `routes.rs:2095`、`:2120` |
| 剧集幂等键**组优先**：`tg:group:{chat}:{g}` | `routes.rs:2326-2330` |

⇒ 「按组入库」是**既成事实**：组 id 在入队、在任务、在剧集键上都用到了。

### 事实 2：**组 id 从不写进条目**（DDL + 函数签名双重证据）

**① 条目表没有位置可写**（`media.rs:543-557`）：

```sql
CREATE TABLE IF NOT EXISTS media_item (
    id        INTEGER PRIMARY KEY AUTOINCREMENT,
    source    TEXT NOT NULL,
    ref       TEXT NOT NULL,      -- 只有 "<chat>:<msg>"（段①）
    title     TEXT NOT NULL,
    kind      TEXT NOT NULL,
    file_path TEXT,
    poster    TEXT,
    size      INTEGER,
    duration  INTEGER,
    width     INTEGER,
    height    INTEGER,
    added_at  INTEGER NOT NULL,
    UNIQUE(source, ref)
);
```

**无组列、无剧集列、无槽位列**。全库带 `item_id` 的表只有
`media_episode` / `media_episode_image` / `media_episode_source` / `media_item_tag` / `media_episode_removed`
（后两者是标签与墓碑，**不是定位**）。

**② 注册函数根本不接收组 id**（`routes.rs:1823-1829`）：

```rust
async fn register_media_item_t0(
    st: &Arc<AppState>,
    chat_id: i64,
    msg_id: i64,
    photo_rule: bool,
    group_desc: Option<&str>,   // ← 组级 caption **正文**，不是组 id
) -> Option<(i64, String)> {
```

调用点注释**明确**把条目登记与剧集上下文切开（`routes.rs:2128-2131`）：
> 「这里的 `&self` 只提供 `chat_id`（**剧集上下文在 `register_slot`，与条目登记无关**）
> 与 `group_desc`（BUG-281：组级 caption 正文）」

⇒ 条目注册时**连组 id 都没进函数**，因此**不可能**落库。注意这是**有意的解耦**，不是漏写一行。

### 事实 3：段③ 只能靠**可选**挂靠，且挂靠表不是必填

`register_slot`（`routes.rs:2145+`）在登记之后**另行**把非照片条目编入剧集、照片挂图片位。
挂靠路径**有且只有两条**：`media_episode`、`media_episode_image`
（`media_episode_source` 实测 **0 行**）。
⇒ 挂靠**失败/未执行**时，条目**没有任何兜底** —— 它仍是一条合法条目，只是**没有位置**。

### 事实 4：剧集幂等键**会退化**，退化即切断组绑定

`routes.rs:2326-2334`：

```rust
let key = match self.task_group {
    Some(g) => format!("tg:group:{}:{}", self.chat_id, g),
    None => {
        let first = self.task_msgs.first().copied().unwrap_or(0);
        format!("tg:msgs:{}:{}", self.chat_id, first)   // ← 组绑定被切断
    }
};
```

⇒ 只要某次入库的**任务不带 `group_id`**（实测存在：单条消息单独入库），
该次产出的剧集键就是 `tg:msgs:<chat>:<首条消息>` —— **与同相册的 `tg:group:` 键互不相等**
⇒ `find_series_by_source_key` 命中不到既有剧集 ⇒ **再建一个剧集**（BUG-292 根因 A）。
**组信息在库里明明有**（`media_message.group_id`），却因键退化而**没被采用**。

### 事实 5：三种失效形态（同一条目的定位可以「没有 / 退化 / 矛盾」）

1. **没有**：条目无任何挂靠 ⇒ 段③ 全缺；
2. **退化**：唯一挂靠的剧集是 `tg:msgs:` 键 ⇒ 组绑定丢，剧集名退化为占位名；
3. **矛盾**：同一 item 被多条分集认领且**槽位不一致** ⇒ 同一件内容有两个集号，
   显示名取决于**无关的槽位排序**（`media.rs:1446` 的 `ORDER BY e.season, e.episode_no LIMIT 1`）。

## 复现（只读 SQL）

```sql
-- 段③ 零挂靠（tg 条目）
SELECT COUNT(*) FROM media_item i
WHERE i.source='tg'
  AND NOT EXISTS (SELECT 1 FROM media_episode        e  WHERE e.item_id  = i.id)
  AND NOT EXISTS (SELECT 1 FROM media_episode_image  ie WHERE ie.item_id = i.id);

-- 段② 组绑定退化：条目唯一挂靠的剧集是 tg:msgs: 键
SELECT i.id, s.id, s.title, s.source_key
FROM media_item i
JOIN media_episode e ON e.item_id = i.id
JOIN media_series  s ON s.id = e.series_id
WHERE i.source='tg' AND s.source_key LIKE 'tg:msgs:%';

-- 同一 item 槽位矛盾
SELECT item_id, COUNT(DISTINCT season||':'||episode_no) n
FROM media_episode GROUP BY item_id HAVING n > 1;

-- 同一相册组被多个剧集认领
SELECT m.group_id, COUNT(DISTINCT e.series_id)
FROM media_message m
JOIN media_item  i ON i.ref = m.channel_id||':'||m.message_id
JOIN media_episode e ON e.item_id = i.id
WHERE m.group_id IS NOT NULL
GROUP BY m.group_id HAVING COUNT(DISTINCT e.series_id) > 1;
```

## 实测（2026-10-13，生产库只读）

> **口径声明**：组归属（段②）**只在 `source='tg'` 内统计** —— `local` 条目的 `ref` 是文件路径，
> 不属于任何 TG 相册，混进来会把数字虚高（首轮误算成 100，实为 6，已订正）。

**条目层（`media_item` 共 532 = `tg` 438 + `local` 94）**

| 口径 | `source='tg'`（438） | `local`（94） |
|---|---|---|
| 段③ **完全没有定位**（无 episode 也无 image 挂靠） | **96（21%）** | 52（55%） |
| 其中 `video` / `photo` / `file` | 59 / 31 / 6 | 34 / 18 / 0 |
| 其中**已有字节** | 54 | 52 |
| 定位**退化**（只被 `tg:msgs:` 剧集认领） | **69** | 0（不适用） |
| 定位**矛盾**（多认领且槽位不一致） | **6** | 0 |
| 无 `media_episode` 挂靠（可能靠 image 挂着） | 207 | 52 |

**段② 组归属（仅 `source='tg'`）**

| 口径 | 实测 |
|---|---|
| `ref` 非 `<chat>:<msg>` 形态 | **0**（段① 齐备） |
| `ref` 可解析但**反查不到 `media_message` 行** ⇒ 组**不可恢复** | **6**（全为 `file`、0 有字节） |
| 消息侧**有** `group_id` | **372 / 438** |
| 消息侧本就无组（单条消息） | 60 |
| 退化条目中「组信息其实在库里、**可恢复**」 | **14 / 69** |

**剧集层（`media_series` 79）**：`tg:group:` 键 **57** / `tg:msgs:` 键 **16** / `source_key` 空 6。

**同一相册组被多个剧集认领 = 7 组**（其中 5 组 = 「真名剧集 + `tg:msgs:` 占位名剧集」成对，
另 2 组为两把 `tg:msgs:` 键）。**条目被双认领且槽位矛盾 = 6 条**
（典型：同一 item 在一个剧集里是 `S1E1`、在另一个里是 `S2`/`E7`，显示名由排序决定）。

### 与 BUG-296 的口径交叉验证（非巧合）

BUG-296 记「全库 **96/438** 条未认领」；本档实测 `source='tg'` 且**无 episode 也无 image 挂靠** = **96/438**。
⇒ **两档的分子分母逐字相同**：BUG-296 测的就是本档「段③ 完全缺失」这一种形态。
全库口径 = 96（tg）+ 52（local）= **148 / 532**。

## 修复方向（建议；**需用户拍板**）

**先声明红线**：
- **不得**用「从 `media_message` 现场 JOIN 出来」冒充「条目携带定位」—— 那正是当前状态
  （组在流水表、条目没有），且实测已有 6 条连流水行都没有 ⇒ JOIN 会静默给出空值。
- **不得**为了让键不退化而改动入队去重键的既有语义（BUG-279 / BUG-292 契约）。
- **不得**自动改写用户已手工编辑的剧集标题（BUG-283 既有约束）。

**方向（待拍板，建议顺序实施）**

1. **条目落组**（对应 BUG-060 已提的 `media_item.album_group`）：`register_media_item_t0`
   增参 `group_id: Option<i64>` 并写入；无组时落 `NULL` 而不是 `0`/空串。
2. **剧集幂等键不退化**：`task_group` 为 `None` 时，**先尝试从消息侧取 `media_message.group_id`**
   再决定键；取到组就用 `tg:group:`，取不到才退 `tg:msgs:`（把「组明明在库里却没用」这条堵掉）。
3. **定位必填/可判定**：为「条目是否已定位」建立**可查询的判定**（零挂靠即为 `unplaced`），
   并在任务终态做 reconcile（与 BUG-296 合并实施）。
4. **存量收敛**：按 `media_message.group_id` 回填 `album_group`；对 7 组同组多剧集定向收敛
   （条目行不动、只收敛归属）；对 6 条槽位矛盾给出**显式规则**并登记处置条数。
5. **不新增第三套键**：任何新键必须先定位「权威组 id」是哪个（BUG-292 根因 B：两套 `group_id` 恒差 −1）。

## 验收证据

（状态 `open`，尚无验收证据。修复后必须满足的**可证伪判据（预先声明）**：）

1. **条目自带组**：`media_item.album_group` 存在且对 `source='tg'` 的条目非空率 == 消息侧有组率
   （当前 372/438）；**反向证伪**：只做 `media_message` JOIN 而不落列 ⇒ 该列不存在 ⇒ 判据必 **FAIL**。
2. **零挂靠归零**：`source='tg'` 且无 `media_episode`/`media_episode_image` 挂靠的条目数 **96 → 0**；
   **反向证伪**：不补挂靠 ⇒ 仍为 96 ⇒ **FAIL**。
3. **键不再退化**：对「组内单条消息单独入库」的场景，剧集 `source_key` **必须**为 `tg:group:` 形态；
   `tg:msgs:` 剧集数**不得增加**（当前 16）；**反向证伪**：改回只看 `task_group` ⇒ 必产 `tg:msgs:` ⇒ **FAIL**。
4. **同组不再多剧集**：同一 `media_message.group_id` 被多个剧集认领的组数 **7 → 0**；
   **反向证伪**：仍用两套键 ⇒ 必重现 ⇒ **FAIL**。
5. **槽位不矛盾**：`GROUP BY item_id HAVING COUNT(DISTINCT season||':'||episode_no) > 1` 必须 **0 行**
   （当前 6）；**反向证伪**：不改合并/追加路径 ⇒ 仍为 6 ⇒ **FAIL**。
6. **不丢数据**：修复前后 `media_item` 行数不变（当前 532），`media_episode` 行数**不减少**。
7. **不推翻既有裁定**：BUG-037（跨相册归并须用户表达意图）、BUG-255（集数口径）、
   BUG-279 / BUG-292（入队去重与幂等契约）、BUG-283（不覆盖用户编辑标题）不得回退。
8. **真实 UI 可核**：媒体库条目视图**不再**出现「副标题为占位名」的卡片（按后端口径复算 = 0），
   且剧集墙不再出现同相册的两张不可分辨卡片（DOM 断言，**不读 className**）。
