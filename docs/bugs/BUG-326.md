# BUG-326: release APP 启动会杀掉健康的 daemon（wmic 弃用导致 owner 判定恒 false）+ 端口漂移，APP 与 dev 栈同时不可用

- 状态: fixed
- 发现日期: 2026-10-20
- 模块: shell
- 严重程度: high

## 现象（用户原话：「APP打开有问题,dev打开正常」）

用户报 APP（release 安装版）打开有问题、而 dev（`tauri:dev`）正常。实测复现：

1. dev 栈 daemon 正常跑在 `19786`（`/api/config` 200）。
2. 启动 release `orig-hub.exe`（`target/release/orig-hub.exe`，2026-10-20 03:32 构建）。
3. 壳 stderr 依次输出：

```text
[ensure_daemon] called
[ensure_daemon] alive=true but owner mismatch, will kill stale
[ensure_daemon] killing port owner
[ensure_daemon] spawning daemon
[ensure_daemon] daemon spawned ok on 19787
```

4. 复测端口：`19786 -> 000`（**原本健康的 dev daemon 被杀**）、`19787 -> 404`
   （新 daemon 落在 19787，且 `/api/config` 不通 —— 该端口此时是 orig-tg 的）。
5. 结果：**APP 与 dev 栈同时不可用** —— dev 侧 daemon 没了（vite 前端全部 Failed to fetch），
   APP 侧新 daemon 漂到 19787 且端点文件被改写。

用户报的「APP 打开有问题」与「dev 挂」是**同一根因的两个面**。

## 根因

`tauri-shell/src-tauri/src/lib.rs` 的 `ensure_daemon` 复用判定：

```rust
if alive {                                  // /health 已 200
    if port_owner_is_daemon_on(port) { 复用 }
    else { 杀掉 }                            // ← 恒走这里
}
```

`port_owner_is_daemon_on` 用 **`wmic process where ProcessId=... get ExecutablePath`**
取进程路径。wmic 自 **Windows 11 22H2 起被微软弃用、默认不安装**；调用失败（命令不存在 /
被安全策略拦截）时该函数 `return false` ⇒ `alive=true` 的健康 daemon 被判定为
「owner mismatch」⇒ `kill_port_owner` 直接杀。

**为什么以前没炸**：owner 判定原本是为了排除「改名前残留的 `surge-daemon`」这一历史问题；
改名完成后它已无实际作用，但「判不出 ⇒ 杀」的方向一直是反的 —— 一旦系统没有 wmic，
它就退化成「每次启动 APP 都杀一次健康 daemon」。

**端口漂移是次生伤害**：19786 刚被 kill、端口尚未释放，新 daemon 顺延到 19787 并把
端点文件改写；而 orig-tg 也占 19787 ⇒ `/api/config` 404。

## 修复

1. **去掉 wmic**：`port_owner_is_daemon_on` 改 `tasklist /FI "PID eq <pid>" /FO CSV /NH`
   （系统自带、无弃用风险），首列取映像名比较 `DAEMON_BIN`。
2. **三态化**：返回 `Option<bool>` —— `Some(true)` 是 daemon、`Some(false)` 明确不是、
   `None` 查不出。`ensure_daemon` 对 `None` **按复用处理**（不杀）：
   `/health` 已经 200 说明是本项目的 daemon，**误杀健康实例的代价（打断 dev 栈/上一会话）
   远大于复用一个旧实例的代价**（后者可用 health/版本自检兜住）。
3. 端点文件不再被无谓改写：不杀 ⇒ 不 spawn ⇒ 不漂移。

## 关联

- BUG-321：引擎栈非用户操作地整树消失（daemon + orig-tg 一起没）—— 本条是「被别的进程杀掉」的另一条路径。
- BUG-323：下载路径单一根 / 端口与路径真源归一 —— 端点文件是端口真源，被改写即全局漂移。
- BUG-318 ④：`fetch_cache_views` 用编译期常量 TG_PORT 导致端口顺延后误报不可用 —— 同属「端口漂移未按真源消费」。

## 附带修复：release 下壳侧日志完全不可见

release 构建带 `windows_subsystem = "windows"`（GUI 子系统、无控制台），`eprintln!` 写向
不存在的 stderr 会被丢弃 —— 排查本条时「stderr 空」被误读成「代码没执行」，白查了很久。
新增 `shell_trace()`：同时 eprintln 并 append 到 `%TEMP%/orighub-shell-trace.log`
（失败静默，不影响主流程）；另加 `shell_probe` 命令，前端可在关键节点 invoke 回报。

## 验收证据

- 回归脚本（新增，可复核）：`tauri-shell/verify/verify_bug326_daemon_reuse.cjs`
  → **8 PASS / 0 FAIL**，产物 `verify_shots/bug326-daemon-reuse/`
  （`trace.log` + `result.json`）。脚本锁 6 条判据：APP 存活 / **daemon pid 不变** /
  `/health` 仍 200 / trace 含 `reusing daemon` / trace 不含 `killing port owner` /
  端点文件端口不漂移。
- **反向证伪**：`--expect-kill` 模式（把「pid 必须不变」反置成「必须被杀」）
  → **2 条转红**，证明该判据不是恒绿。修复前用同一脚本跑必然红（pid 会变、trace 出
  `killing port owner`）。

活栈实测（完整 `npm run tauri:build` 产物，`target/release/orig-hub.exe`，2026-10-20 04:46）：

```text
（启动前）19786 -> 200，listening pid = 25728
（启动 APP 后 18s）
trace: [ensure_daemon] port=19786 alive=true busy=true owner=Some(true)
trace: [ensure_daemon] reusing daemon on 19786
19786 -> 200，listening pid = 25728   ← 未变，未被杀
窗口: MainWindowTitle="Orig Hub"，Responding=True
```

- **判据**：`owner=Some(true)` 证明 tasklist 路径取到了真实映像名 `orig-daemon.exe`
  并判定为自家 daemon；`reusing` 而非 `killing` 证明不再误杀；pid 前后一致证明没有
  kill + respawn，端点文件因此不会被改写（无端口漂移）。
- **反向对照（修复前，同一命令序列）**：`19786 -> 000`（pid 消失）、
  `19787 -> 404`、壳 stderr 出现 `killing port owner` / `spawned ok on 19787`。
- 诊断过程沉淀的判据（已写入当日工作日志）：① release 下 stderr 空 ≠ 未执行，
  须用 `shell_trace` 落文件；② `document.title` 不能当探针（Tauri 不同步到原生标题），
  可靠通道是「JS 改 location + 壳读 `win.url()`」。
- 附带发现：`dist/index.html` 曾停在 03:25 而 `tauri build` 03:31 完成 —— 那次构建
  没有重建前端，release 嵌的是旧 dist。完整重建后 dist 与源码同版本。
