# BUG-380: `/api/downloads` 只回一条已完成数据——接口口径没有说明

- 状态: fixed
- 发现日期: 2026-10-22
- 模块: engine
- 严重程度: mid

## 现象

用户 2026-10-22 报：「api/downloads->bug322ui.bin，为什么返回的只有一条数据，
而且这个是已经完成的，这个接口到底干什么的?」

实测（daemon 19786，`GET /api/downloads`）：返回数组长度 1：

```json
[{"id":"9d68522c-…","url":"mock://bug322ui.bin?size=33554432&rate=256k",
  "filename":"bug322ui.bin","dest_path":"D:/OrigDown\\bug322ui.bin",
  "total_size":33554432,"downloaded":33554432,"progress":100.0,
  "status":"completed", …}]
```

## 根因（口径事实，非缺陷数据）

`/api/downloads` = **daemon 引擎任务列表**（HTTP 直下/手动新建的那类），
本机只有这一条 mock 样板（BUG-372 过程错误里被用户删后恢复的那条）。
TG 入库（缓存）任务活在 orig-tg 的 `cache_task` 表，**不经 daemon**——
UI「下载域」看到的水位是 daemon 引擎任务 + orig-tg 入库行的**前端合并**
（`ingestGroups.ts`）。用户拿 API 返回值与界面行数对不上，是因为
两个源在 API 层是分开的、在 UI 层才合并，而没有任何一处把这个口径写清楚。

## 修复

1. 接口契约落文档：`docs/design/download-activity-api-contract-2026-10-22.md`
   —— `/api/downloads`（引擎原生面，不含 TG 入库）/ `/api/activity`（只读聚合面，
   `scope=active|all`、`kind=download|cache`、`sources` 可用性通道）两口径 +
   探针口径（BUG-377 教训：算入库必须 `kind==='cache'` 过滤）。
2. UI 侧来源标注：下载域统一行模型（BUG-372）已给出来源区分——TG 入库行带
   「TG 入库」Badge（`IngestGroupRow.tsx:188`），引擎行是文件名 + URL 副行，
   两态不再混成「为什么这里多一行」。
3. `dest_path` 分隔符随 BUG-379 的 `to_wire` 规范化一并上线（活栈实证
   `dest_path="D:/OrigDown/bug322ui.bin"`，无 `\`）。

## 验收证据

活栈实测（daemon 19786 / orig-tg 19787，2026-10-22）：

| 端点 | 读数 | 结论 |
|---|---|---|
| `GET /api/downloads` | 长度 1（`mock://bug322ui.bin`，completed） | = 引擎任务全集，口径正确 |
| `GET /api/activity?scope=all` | 149 条 = download 1 + cache 148；`sources=[(download,true,1),(cache,true,148)]` | 聚合面双源结构如契约 |
| `dest_path` | `D:/OrigDown/bug322ui.bin` | `/` 规范化（BUG-379 已上线） |

契约文档落库：`docs/design/download-activity-api-contract-2026-10-22.md`
（含 scope/kind/unit/status/control/sources 全字段口径 + 探针口径 + UI 数据源）。
