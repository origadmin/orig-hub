# BUG-259: 标签编辑入口分散在 5 处、其中 2 处对同一件事等价；标签在数据库/接口/渲染三层都没有任何数量与长度上限，全量渲染无虚拟化，规模上千后单次刷新退化到秒级

- 状态: open（部分修复：方向 3 / 4 / 6 已实施并验收，方向 1 入口收敛、方向 2 上限数值待产品拍板）
- 发现日期: 2026-10-10
- 模块: engine+shell
- 严重程度: mid

> 来源：用户报告「标签选择编辑功能分配混乱。当前编辑中有标签，外部也有单独标签按钮修改标签。且标签没有最大数量限制，全部堆叠，没有考虑几千上万的情况后续会怎么爆炸破坏，这些基础问题。」

## 现象

### 现象 1：改标签有 5 个入口，其中 2 个对同一件事等价

| 入口 | 位置 | 作用域 | 语义 |
|---|---|---|---|
| 「编辑」面板里的 `TagPicker` | `tauri-shell/src/components/media/ItemEditDialog.tsx:167-173` | 单条内容 | 覆盖式 `setItemTags` |
| 工具栏「打标签」 | `tauri-shell/src/components/MediaLibraryPanel.tsx:1052-1059` → `BulkTagDialog` | 多选内容 | 覆盖式（**有明确提示**） |
| 工具栏「🏷 标签管理」 | `MediaLibraryPanel.tsx:1120-1128` → `TagManagerDialog` | 全局标签本体 | 新建 / 重命名 / 删除 |
| 剧集「编辑」面板里的 `TagPicker` | `SeriesEditPanel.tsx:161-169` | 单剧集 | 覆盖式 `setSeriesTags` |
| 剧集头「标签」按钮 | `SeriesHero.tsx:90-99`（`data-testid="series-tag-edit"`）→ `SeriesDetail.tsx:333-360` 内联 `TagPicker` | 单剧集 | 覆盖式 `setSeriesTags` |

- **最后两个入口对同一件事（改这个剧集的标签）提供两条路径**，且都只改标签：
  「编辑」面板一次提交 title/description/kind/year/tags，独立的「标签」按钮只提交 tags。
- **「新建标签」也有两处**：`TagPicker` 的就地新建「新建 #xxx」
  （`TagManagerDialog.tsx:131-142`）与 `TagManagerDialog` 顶部的新建行（`:299-324`）。
  两处行为一致，但入口不同，且都会调用同一个 `createTag`。
- **覆盖语义只在批量弹窗里说明**（`media.bulkTagHint` =「所选内容现有的标签会被替换为下面勾选的结果。」），
  单条编辑面板的标签区**没有任何提示**（`ItemEditDialog.tsx:167` 只有「标签」两个字）。

### 现象 2：标签没有任何上限

实测（2026-10-10，只读真库）：标签 **64** 个，名称最长 **14** 字符，单条目/单剧集最多挂 **6** 个。

⇒ **当前规模完全没问题**。问题在于**没有任何东西阻止它变大**：

| 维度 | 约束 | 位置 |
|---|---|---|
| 标签总数 | **无** | `list_tags` 无 `LIMIT`（`media.rs:3573-3577`） |
| 单个标签名长度 | **无**（`TEXT NOT NULL UNIQUE`，无 CHECK） | `media.rs:259-263` |
| 单条目挂标签数 | **无** | `set_item_tags`（`media.rs:3680-3693`） |
| 单剧集挂标签数 | **无** | `set_series_tags`（`media.rs:3696-`） |
| 接口层校验 | 只有「非空」 | `routes.rs:4939-4952`，无长度、无数量 |

**对照**：TG **自动**打标**有**上限 —— `MAX_AUTO_TAGS = 20`（`download-engine/crates/orig-tg/src/routes.rs:1993`，
用于 `collect_hash_tags`）。⇒ **「自动来的」有闸门，「用户手动加的」没有。**

### 现象 3：全量渲染、无虚拟化，规模上千后代价可测

后端 `list_tags` 的 SQL 是 **1 + 2N 次查询**（每个标签单独发两次 `COUNT(*)`，`media.rs:3584-3595`）。
在只读副本上实测（同一套 SQL 序列，本地 SQLite；**仅作量级参考**，非 libsql 进程内实测）：

| 标签数 N | 查询数 | 单次耗时 | 响应载荷 |
|---|---|---|---|
| **64（真库现状）** | **129** | **37 ms** | **5.7 KB** |
| 1,000 | 2,001 | 624 ms | 100 KB |
| 5,000 | 10,001 | 4,265 ms | 508 KB |
| 10,000 | 20,001 | 8,400 ms | 1.0 MB |

前端侧同样是全量、无上限、无折叠。全仓**没有任何虚拟化库**
（`react-window` / `react-virtual` / `react-virtuoso` 零命中；`IntersectionObserver` 只用于卡片的封面懒加载）：

| 渲染点 | 位置 | 上限 |
|---|---|---|
| 左栏标签区 | `MediaLibraryPanel.tsx:892-953` | 无，**且没有 `max-height`**（对照剧集列表在 `:830` 有 `max-h-72`） |
| 内容卡片标签行 | `tauri-shell/src/components/media/MediaCard.tsx:468-474` | 无（每条目挂多少画多少） |
| 剧集卡片标签行 | `SeriesCard.tsx:244` | 无 |
| 剧集详情标签行 | `SeriesDetail.tsx:412-416` / `SeriesHero.tsx:191-193` | 无 |
| `TagPicker` 已选区 | `TagManagerDialog.tsx:69-89` | 无 |
| `TagPicker` 可选项 | `TagManagerDialog.tsx:109-130` | 无（`max-h-40` 只是滚动，节点全在 DOM） |
| 标签管理列表 | `TagManagerDialog.tsx:342-417` | 无 |

⇒ 5,000 个标签时：左栏一次渲染约 **2 万个 DOM 节点**（每个 chip = 1 个 `button` + 3 个 `span`，
这是算术不是实测），`list_tags` 一次 4.3 秒；10,000 个标签 8.4 秒。

### 现象 4：写入路径是 1+N 条语句且没有事务

`set_item_tags`（`media.rs:3680-3693`）= 1 次 `DELETE` + N 次单条 `INSERT`，**没有包在事务里**。
挂 5,000 个标签就是 **5,001 条语句**；中途失败会留下**半套标签**（先清后写，清完只写了一半）。

> 说明：该路径的**耗时**实测不具可比性（受页缓存影响，实测出现 5000 个比 1000 个还快），
> 故此处只登记「语句数 = 1+N」这一确定事实，不登记耗时。

### 现象 5（旁支）：标签相关界面文案整体未本地化

`TagPicker` 与 `TagManagerDialog` 里几乎所有文案都是**硬编码中文**（该文件只有
`BulkTagDialog` 用了 `t()`）：`"标签管理"`、`"标签以 #名称 的形式挂在内容或剧集上，用于交叉归类检索。"`、
`"新建"`、`"重命名"`、`"删除"`、`"完成"`、`"取消"`、`"搜索标签"`、`"搜索标签，如 短剧"`、
`"暂无标签"`、`"没有匹配的标签"`、`"还没有标签，先在「标签管理」里新建"`、`"新建 #"`、
`"应用中…"`、`"应用"`。`TagToken.tsx` 同理。

## 根因

### 根因 1：标签被当成「条目/剧集的属性」，而不是「独立实体」

`media_tag` 是一张独立表（`media.rs:259-263`），但**没有对应的独立界面**：
新建/改名/删除混在工具栏的「标签管理」弹窗里，而「给某条打标签」又散落在编辑面板与批量弹窗。
于是同一件事的**两个语义层次**（标签本体 vs 标签关联）在 UI 上被拉平成 5 个并列入口。

判据：**同一实体在同一界面出现 ≥2 个入口且行为等价，就是分配混乱** ——
剧集的「编辑」（含标签区）与「标签」按钮正是如此。

### 根因 2：没有任何一层定义过「上限」这个决策

- 数据库：无 `CHECK`、无长度限制。
- 接口：只校验非空（`routes.rs:4943-4945`）。
- 前端：无 `slice`、无「还有 N 个」折叠。

⇒ 不是某处写错，而是**「标签规模的上限是多少」这个决策从未存在过**（全库查无）。
只有自动打标一侧定义了 `MAX_AUTO_TAGS = 20`。

### 根因 3：`list_tags` 是 N+1 查询，每次刷新全量重算计数

`media.rs:3584-3595` 对每个标签发两条 `COUNT(*)`。用一条 `GROUP BY` 就能取回全部计数。
这是现象 3 里 4.3 s / 8.4 s 的直接来源。

## 修复方向（未实施）

1. **收敛入口**（根因 1）：剧集的「编辑」与「标签」二选一 —— 建议保留「编辑」面板内的标签区，
   撤掉独立的「标签」按钮。**撤入口必须走 BUG-149**：先查它是否来自已验收需求
   （本档已查到 `series-tag-edit` 有 `data-testid`，说明被验收脚本用过，撤之前必须先跑一遍受影响的验收）。
   同理，`TagPicker` 与 `TagManagerDialog` 的「新建标签」二选一。
2. **定义上限**（根因 2，**需要产品决策**）：至少要有
   ① 单个标签名长度上限；② 单条目/单剧集挂标签数上限（超出时是截断还是拒绝？）；
   ③ 全局标签数达到某阈值时的处置（折叠 / 分页 / 归档）。
   参考值（工程建议，不是结论）：名称 ≤ 32 字符；单条目 ≤ 20（与 `MAX_AUTO_TAGS` 对齐）；
   左栏与卡片**只渲染前 K 个 + 「+N」**（K 建议 8），完整列表进「标签管理」。
3. **把 N+1 改成一条 `GROUP BY`**（根因 3），让 `list_tags` 的代价与标签数解耦。
4. **`set_item_tags` / `set_series_tags` 包事务**，避免「清完写一半」的半套标签。
5. **统一「覆盖式」提示**：单条编辑面板的标签区也要说明是覆盖，不能只在批量弹窗里说。
   这不是「实现约束」（BUG-148 允许隐藏的那一类），而是**会影响结果的语义**，必须让用户知道。
6. **标签界面文案接入 i18n**（现象 5）。

## 验收证据（第一部分：无需拍板三件套）

> 2026-10-10 实施。只覆盖修复方向 3 / 4 / 6（`list_tags` N+1、写入事务、界面 i18n）；
> 方向 1（入口收敛）与方向 2（上限数值）**仍待产品拍板，未实施**。状态保持 open（部分修复）。

### 三件套 1：`list_tags` N+1 → 单条聚合（根因 3）

- 改法：`media.rs` 的 `list_tags` 改为**一条** `media_tag LEFT JOIN` 两个
  「按 `tag_id` GROUP BY 计数」子查询的聚合 SQL。选**单条 LEFT JOIN**而非
  「两次 GROUP BY 后在 Rust 里合并」：一条语句一次往返，集合运算不搬应用层；
  `LEFT JOIN`（而非 `FULL OUTER JOIN`）无 SQLite 版本兼容性顾虑；
  **0 计数标签经 LEFT JOIN + COALESCE 照样成行**——BUG-068 的「0 计数不渲染」
  是展示层行为，SQL 层不丢行。
- 单测（`cargo test -p orig-tg`，174 passed / 0 failed）：
  - `list_tags_statement_count_constant_and_zero_count_kept_bug259`：
    语句计数用 libsql `Connection::prepare` / `execute` 每条 SQL 发出的
    `tracing::trace!` 事件（自定义 Subscriber 计数），N=8 与 N=64 两规模
    断言语句数相等（旧实现 33 条 vs 129 条必 FAIL）；同时断言 0 计数标签
    全量保留、各计数正确。

### 三件套 2：`set_item_tags` / `set_series_tags` 包事务（现象 4）

- 改法：照 `Store::open` 事务先例（`BEGIN IMMEDIATE` / `COMMIT` / `ROLLBACK`）
  包裹 1 次 DELETE + N 次 INSERT。
- 单测：`set_tags_atomic_on_midway_failure_bug259` —— 用触发器
  `WHEN NEW.tag_id = C SELECT RAISE(ABORT)` 精确拦截「写到 C」那一条 INSERT
  （先清后写、写一半就断），断言失败后标签集合保持**全旧** {X, Y}，
  且回滚后下一次正常写入不受影响。
- **反向证伪（实跑）**：临时去掉 `BEGIN IMMEDIATE` / `COMMIT` / `ROLLBACK` 后
  本测试必 FAIL —— 实测输出：
  `assertion 'left == right' failed: set_item_tags 中途失败必须整体回滚（全旧）`
  `left: [1, 2] right: [5, 6]`（半套 {A, B} 残留）。已还原事务后重跑 PASS。
- **顺带发现（未越权修复，另行上报）**：既有先例
  `switch_episode_source`（`media.rs`）与 `detach_episode_source` 等
  Err 分支的 `let _ = self.conn.execute("ROLLBACK", ());` **漏了 `.await`**
  （`execute` 返回 Future，不 poll 就不执行 ⇒ 回滚从未发生，事务挂着不关）。
  本次两个 set_*_tags 均已 `.await`。该先例自身是否有行为影响建议另行立案核查。

## 修复后必须满足（可证伪判据，预先声明）

1. **入口唯一性**：在剧集详情页，「改这个剧集的标签」只存在**一条**路径
   （可用 `data-testid` 计数）。**反向证伪**：把被撤掉的入口加回去，判据 1 必须 FAIL。
2. **上限可证伪**：构造超过上限的输入（超长名称 / 超量标签），接口必须返回**明确错误**
   （而非静默截断），且 UI 在到达上限前就禁用新增入口并说明原因。
   **反向证伪**：把上限常量改回「无」，判据 2 必须 FAIL。
3. **渲染有界**：把标签数灌到 5,000，左栏与内容卡片的标签 chip **DOM 节点数不超过某个常量**
   （与 N 无关，用 `document.querySelectorAll` 计数即可验）。
4. **`list_tags` 的查询数与 N 无关**：N=64 与 N=5,000 的 SQL 语句数相同（都是常数条），
   且 N=5,000 的响应时间在本档实测值（4,265 ms）的 **1/10 以内**（同机、同数据）。
5. **写入原子性**：在 `set_item_tags` 中途注入失败，该条目的标签集合必须**要么全旧、要么全新**，
   不得出现半套。**反向证伪**：去掉事务，判据 5 必须 FAIL。
6. 判据 1 / 3 必须在**真实 UI 上验**（BUG-156），不得只看接口。
