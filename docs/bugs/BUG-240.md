# BUG-240: 媒体库「大量重复数据」实为不可辨识条目 —— 86/320 条空标题 + 80/320 条无字节，卡片外形一致；**不是**重复行、**不是**重复渲染

- 状态: open
- 发现日期: 2026-10-09
- 模块: engine+shell
- 严重程度: high
- 登记: 用户报告「进入媒体库请求了 42 个，而且**大量重复问题数据**」
  （请求放大另行建档，见 BUG-239）

## 现象

用户进入媒体库后看到「大量重复数据」：网格里出现成片**长得一模一样、无法分辨**的卡片。

## 判据链（先排除「重复」，再定成因）

三条独立实测，全部指向同一结论 —— **这里不存在任何意义上的"重复"**：

| 检查 | 方法 | 结果 |
|---|---|---|
| 数据库是否有重复行 | `curl --noproxy '*' 'http://127.0.0.1:19787/api/media/items?limit=2000'` | total **320**，**唯一 id 320 / 唯一 ref 320 / 重复 0** |
| DOM 是否重复渲染同一 id | CDP + React fiber 读 `MediaCard` 的 `item.id`（`_probe_libstorm_ids.cjs`） | 「全部内容」**120 张卡 → 唯一 id 120**，重复 id 组 **0**；全部同属单一区块，无跨区块重复 |
| 默认视图是否重复 | 同上，读 `data-series-id` | 剧集墙 **28 张 → 唯一 28** |

**真实成因 = 数据不可辨识**（同一批真实条目因缺标题、缺字节而在网格里渲染成外形一致的占位卡）：

| 指标 | 数值 | 说明 |
|---|---|---|
| `title` 为空字符串 | **86 / 320**（**全部 source=tg**；kind: video 82 / file 2 / photo 2） | 样例 id `672` `671` `669` `662` `647` |
| `bytesPresence = missing`（`filePath=null`） | **80 / 320**（**全部 source=tg**） | 有标题但无字节样例：id `674`（`#《剧名》EP3`）、`670`、`668` |
| 两者同时缺失 | **5** | 样例 id `671` `643` `510` |
| 「全部内容」网格中空标题卡片 | **70 / 120** | 与 API 侧空标题逐条对上；DOM 唯一标题仅 **50** |

即：TG 来源 226 条里，**38% 没有标题、35% 没有字节**。空标题 + 无缩略图 ⇒ 卡片只有一块占位图与一行空文本。

## 根因

**1. 呈现层无标题回退**
`tauri-shell/src/components/media/MediaCard.tsx:377-378` 直接渲染 `{item.title}`，**没有回退**：

```tsx
<p className="truncate text-[12px] font-medium text-fg-strong" title={item.title}>
  {item.title}
</p>
```

标题为空 ⇒ 该行渲染为空字符串；`thumbSrc`（`:209-210`）= `poster ?? (kind==='photo' ? url : null)`
⇒ 视频无 poster 时也是 `null` ⇒ 走占位图。两者叠加，卡片彼此不可分辨。
（`player.untitled`「未命名」键存在于 `tauri-shell/src/i18n/locales/zh-CN.json:496`，
但**播放器路径**在用，媒体库卡片路径未用。）

**2. 无字节条目没有可辨识的异常态**
80 条 `bytesPresence=missing` 的卡片与正常卡片**外观无差异**，用户无法区分
「这条本来就没下载」与「这条下载失败/文件丢了」。
按本仓既有产品语义（编目与落盘正交；`cached` 是常态、`absent`/`partial` 是异常且
UI 必须给重试入口），这类条目**必须有可辨识的缺失态**，而不是长得和正常条目一样。

**3. 上游：TG 入库没有落标题（与 BUG-232 同一根因族）**
空标题 86 条**全部来自 TG**，说明入库时未把消息 caption 落成条目 `title`。
`docs/bugs/BUG-232.md` 的「剩余范围」已记录同一缺口
（「failed/queued 行的内容标题需引擎落 caption」）；`docs/bugs/BUG-231.md`
已确立原则「**分组维度 ≠ 内容标题**」。

## 复现

```bash
curl --noproxy '*' 'http://127.0.0.1:19787/api/media/items?limit=2000'   # 320 条：唯一 id 320 / 空 title 86 / filePath null 80
node tauri-shell/verify/_probe_libstorm_ids.cjs                          # DOM 120 卡 → 唯一 id 120，唯一标题 50
node tauri-shell/verify/_probe_libstorm.cjs                              # 同批抓取的请求侧数据（见 BUG-239）
```

## 修复方向（未实施）

> **明确不做**：不加去重。本仓既有硬规则
> `docs/design/media-library-layout-design-2026-09-28.md:343`：
> 「**去重是渲染期规则，不是写入期规则** —— 绝不因为两层相同就去改数据（会毁单一真源、丢用户数据）」。
> 本条连"重复"都不存在，加去重只会掩盖真实缺陷（缺标题、缺字节）。

1. **呈现层**：空标题给可辨识回退（如「未命名 · <来源/ref 摘要>」），且**同一批空标题卡片必须互相可区分**；
2. **缺失态**：`bytesPresence=missing` 的卡片给明确标记 + 重试入口，与正常卡片视觉可分；
3. **上游**：TG 入库时把 caption 落成 `title`（与 BUG-232 剩余范围合并处理）。

## 修复后必须满足（可证伪判据，预先声明）

1. 媒体库「全部内容」网格中，**任意两张卡片的可见标题不逐字相同**（除非对应条目的
   `title` 本身逐字相同）—— 即空标题条目不再产生成片同形卡片；
2. `bytesPresence=missing` 的条目在网格中**有可机检的差异标记**（`data-*` 属性或可见文案），
   且能从中进入重试；
3. 反向证伪：把判据 1 的回退逻辑移除，判据 1 必须重新 FAIL；
4. **不得**通过删除/合并条目来让判据 1 通过（本条的 `total` 与唯一 id 数在修复前后必须不变）。
