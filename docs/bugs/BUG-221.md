# BUG-221: 入库流水线看不到进度：单条大文件全程 0%，且无从判断「在下载 / 卡死 / 已恢复」

- 状态: fixed
- 发现日期: 2026-10-09
- 模块: engine+shell
- 严重程度: critical

## 现象

用户原文：「入库流水线完全无法看到进度，无法了解下载是否正在下载，下载是否卡住、有无问题，
以及问题解决，这是一个充满 BUG 的实现。」

三个可观察症状：

1. **进度条长期 0%**：单条任务（一条几百 MB 的视频）下载数分钟，进度条停在 `0/1` 即 0%；
2. **无法区分「在下载」与「卡死」**：行尾只显示 `fmtWhen(task.updatedAt)`（分钟级时间戳），
   下载期间这个时间**数分钟不变**，界面没有任何「仍在推进 / 已停滞 N 秒」的信号；
3. **问题与恢复都不可见**：失败只有一行 error，且重试后是否真的恢复推进，界面无反馈。

## 根因

1. **进度分母是消息数，不是字节**（`CacheManagerDialog.tsx:185`）：
   `pct = task.done / task.total`。单条任务 `total = 1`，在完成前恒为 0/1 = 0%。
   这意味着**最耗时的大文件恰恰是进度最不可见的那一类**。
2. **字节进度能力已存在但没接上**：后端 `task_with_progress`
   （`routes.rs:1147-1158`）会为 `running` 任务注入 `itemBytes`/`itemBytesTotal`，
   且 `/api/tg/cache/tasks/all` 也走这个函数（`routes.rs:1216`）；前端类型里也有
   （`types.ts:296-297` `itemBytes?: number`）—— 但 `IngestTaskRow` **完全没有读它**。
   TgPanel 用了（`TgPanel.tsx:698`），流水线面板没接。
3. **没有停滞判据，且时间戳本身不随字节推进**：`updated_at` 只在**消息边界**与状态变更时写
   （`store.rs:1034-1042` `update_cache_task_progress`：`SET done, current_id, updated_at`），
   条目内的字节进度只存在于内存 `cache_dl`（`state.rs:175`），既不落库也不刷新 `updated_at`。
   ⇒ 界面上「最后更新时间」在大文件下载期间**天然不动**，用户据此只能判定「卡住了」，
   界面却又没有任何停滞/存活提示来消解这个误判。
4. **刷新粒度**：活跃时 5s 轮询（`CacheManagerDialog.tsx:505-509`），无速度、无剩余时间估算。

## 复现

1. 起服务，对一条 ≥100MB 的视频发起缓存；
2. 打开入库流水线 → 该行进度条 0%、`0/1`、时间戳停在发起时刻；
3. 一直观察到下载完成，界面全程无「在推进」的可见信号；
4. 此刻若网络真的中断，界面表现与 2 完全一致 —— 卡死与正常下载**不可分辨**。

## 修复方向（让「卡死」可表达、可自证）

- **进度改以字节为准**：行内优先用 `itemBytes/itemBytesTotal` 渲染条目内进度；消息级
  `done/total` 降为次要读数。无字节进度（未起步）时如实显示「准备中」，不得假造百分比。
- **后端给活跃任务注入字节心跳**：`progressAt`（`cache_dl` 最后一次推进的时间戳）与
  `progressBytes` 一并进入任务 JSON（内存快照，不落库、不碰 DB，符合高频读端点只读约束）。
- **前端据此派生停滞态**：`now - progressAt` 超过阈值（如 15s）且任务仍 running ⇒ 行内显示
  「已 N 秒无进展」并给出可行动提示；恢复推进即自动消失（判据**必须成对**：停滞时能断言出来、
  恢复后断言不成立 —— 禁 always-green）。
- 速度/剩余时间由两次采样的字节差派生（复用现有 5s 轮询，**不新增轮询源**，AGENTS.md §5 流畅优先）。
