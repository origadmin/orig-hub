## 快速概览（TL;DR）

| 项 | 说明 |
|---|---|
| 问题 | Telegram 频道大量高频发布，内容重复、分散在多频道；TG 搜索差、视频直链播放卡顿 |
| 根因 | 现有引擎是纯 HTTP 下载器，无 Telegram 源；Bot API 有 20MB/history 硬限制；TG 流式播放不稳 |

| 不改 | 现有 HTTP/BT 下载链路、HTTP 传输内核、转码（Phase 2 再做，本期仅原格式归档） |
| 关键验证 | 登录→枚举订阅→拉历史/增量→手动择优→去重→系列归并→本地搜索→点播本地化播放 |
| 核心洞察 | "不允许下载"真相是 Bot API 限制；用户账号 + MTProto 可读全量历史且无大小限制。**播放不稳问题用"下载后本地播"根治**。守住**个人订阅归档**边界，不做反滥用规避 |

## 1. 背景与问题

- Orig Hub 目前是通用下载管理器（HTTP 源），用户无法整理 Telegram 频道内容。
- 用户订阅大量 Telegram 频道，内容高频重复、跨频道分散；希望**集中汇总 + 择优、去重、按作品归并**后归档到本地媒体库。
- 需求不只"全自动"，更强调**手动择优**：频道每日发布重复多，要挑"比较好的那一个"。
- 系列内容（连续剧第 1/2/3 集）发布日期不同但属同一作品，下载后要**管理在一起**。
- **TG 搜索不友好**：频道发现与检索体验差，需要本地化查询渠道。
- **TG 视频播放不稳**：流式直链常卡顿/失败，需要"播放即本地化"来保证稳定观看。

## 2. 需求边界（本期 MVP）

### 2.1 核心（MVP 必须）
1. **TG 登录**：桌面端授权登录用户账号（非 Bot），本地安全持久化会话。
2. **订阅频道筛选**：拉取用户订阅的频道/群组，多选、搜索、管理订阅。
3. **多频道内容汇总视图**：把多个频道的待选内容聚合成一个统一列表（全局去重/择优），可按频道/发布者筛选。
4. **手动择优下载**：待选内容默认不下载，用户勾选/单选后下载；自动模式可选（默认关）。
5. **重复检测**：同一内容跨频道/多次出现时，按文件指纹+发布时间聚类，仅保留一份，余者标为重复。
6. **系列聚类**：识别同作品分集，归入同一"系列"分组，按集号排序、同集仅留一份。
7. **自动整理归档**：下载后按分类（Videos/Images/...）+ 系列落盘，含元数据记录。
8. **频道本地索引/搜索**：把访问/搜索过的频道元数据（标题、简介、username、标签、缩略图）落本地，用全文检索做本地查询，并按需从 TG 增量刷新。
9. **点播即下载本地播放**：媒体库点开视频/图片时，若本地无该文件则先触发完整下载，完成后用本地文件播放/查看，完全绕过 TG 流。

### 2.2 附加（开发过程中细化、可裁剪）
- 收藏/标签、更丰富的搜索/筛选/排序、导出/备份、下载稳健性（断点/重试/并发）——**未知项，按"核心优先"逐项评审后决定取舍**，避免过度工程。

### 2.3 明确不做（本期）
- 统一转码（ffmpeg）→ **Phase 2**。本期只下载原格式 + 按扩展名/元数据归档。
- 渐进式边下边播 → Phase 3 可作增强；MVP 采用"下载后本地播放"的稳妥策略。
- 媒体库海报墙 / go 级视频编辑（另议，非本次核心）。

## 3. 可行性结论

| 方案 | 结论 |
|---|---|
| Bot API | ❌ 下载 20MB 上限、无法读频道历史、不能主动加频道 → 不满足 |
| 用户账号 + MTProto | ✅ 读全量历史、枚举订阅、单文件 2GB(free)/4GB(Pro) → 唯一可行 |

> "部分视频不允许下载"的真相：Telegram 的「限制保存内容」仅约束客户端 UI 的复制/转发/录制，MTProto 原始媒体流订阅成员可解密落地。**技术上无硬封锁**；但方案聚焦"个人订阅归档"，不设计针对反滥用/版权控制的规避。**播放卡顿**通过"先同步下载、再用本地文件播放"根治，不依赖 TG 流稳定性。

## 4. 架构设计（控制面 / 数据面分离）

```
tauri-shell (React)
      │ REST/SSE
      ▼
orig-daemon (Rust) ─── 控制面：任务编排 / 归档合并 / 频道目录索引 / 系列聚合
      ├── orig-core            (下载/归档抽象, 已存在)
      │       └── orig-protocol-http   (HTTP 源, 已存在, 不动)
      │
      ▼ HTTP（本机）
orig-tg-service (独立 daemon / sidecar, 新增) ─── 数据面：Telegram 拉取
      ├── 登录/会话(MTProto, grammers)  / 长连重连/心跳
      ├── 枚举订阅频道 / 分页拉历史 / 增量 new-messages
      ├── 频道元数据采集 → 回写主 daemon 的目录索引
      └── 媒体下载(MTProto 流) → 落共享目录 → 交给 orig-core 归档
```
- `orig-tg` 以**独立二进制 / 第二个 sidecar**形态运行，通过 HTTP 与主 daemon 交互（沿用现有 REST/SSE 风格）；文件经**共享下载目录**交接。
- 进程隔离：TG 的长连接/重连/FloodWait/风控等"危险活"不影响主 daemon，可独立重启、独立伸缩。
- 归档维度两层叠加：**分类**（文件类型）× **系列**（内容/作品）。
- 会话文件本地加密存储（等同密码凭证），Tauri 走授权流程。

### 4.1 频道目录索引（本地搜索）
- 频道元数据（id、title、username、about、photo、subscribe 关系、标签、来源）落 SQLite。
- 用 **SQLite FTS5** 做本地全文检索，替代 TG 低效搜索。
- **定期/按需**从 TG 增量刷新简介等元数据；为空搜索词/冷启动时提供"最近浏览/最常访问"启发式列表。

### 4.2 播放本地化（点播即下载）
- 媒体库点开项：本地已有 → 直接本地播；没有 → 触发一次完整下载，完成态自动续播。
- 图片：落盘后本地查看，不走 TG 缩略图/流。
- 结果：观看/查看稳定，与网络质量解耦；后续可演进为"先下头部 + 边下边播"。

## 5. 系列识别策略（分层，不指望单一规则）

| 层级 | 手段 | 覆盖 | 说明 |
|---|---|---|---|
| 1 规则快判 | 集号标记（第N集/S0xExx/EP） | 规范命名 | 自动 |
| 2 相似聚类建议 | 标题/发布者相似度归成候选分组 | 大概率自动 | 给出候选，可一键采纳 |
| 3 人工确认归并 | 手动将分集拖入同一系列 | 兜底 | 最可靠 |
| 4 可选·AI 解析 | 本地 LLM 读"介绍"文字提取作品+集号 | 描述型内容 | 需人工复核，增强项 |

> 共识：不依赖 TVDB/TMDb（私域原创数据缺失）；**规则优先 + 候选建议 + 人工兜底**，AI 为可选增强，不作主依赖。

## 7. 风险评估

| 风险 | 影响 | 缓解 |
|---|---|---|
| userbot 高频拉取触发 FloodWait/临时封禁 | 高 | 节流 + 退避 + 并发控制；隔离在独立服务 |
| 会话安全/泄漏 | 高 | 本地加密、等同密码凭证、授权流程 |
| 系列识别误判/漏判 | 中 | 分层策略 + 人工兜底兜住 |
| 本地索引过期/不一致 | 中 | 定期 + 事件驱动刷新；标注元数据时间戳 |
| 点播下载的等待体验 | 中 | 提示进度 + 后台任务；Phase 3 演进边下边播 |
| 版权/ToS 合规 | 中 | 限定个人订阅归档场景，不做反滥用规避 |
| grammers 偏底层、登录/2FA 要自踩 | 中 | MVP 先做最小链路 + 文档沉淀 |

## 9. 阶段划分

- **MVP（本期）**：独立 orig-tg 服务、登录、订阅枚举、多频道汇总、手动择优下载、去重、系列聚类、频道本地索引/搜索、点播即下载本地播放、按分类+系列归档。
- **Phase 2**：统一转码（ffmpeg，新建转码模块）。
- **Phase 3**：附加需求（收藏、丰富搜索、导出等）+ 渐进式边下边播，按用户优先级逐项评审后裁剪落地。
