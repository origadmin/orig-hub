# TG 监控频道历史回溯（第 2 点）

- **日期**：2026-10-22
- **来源**：用户第 2 点「数据大小问题，频道数据只会加载一部分数据，这点不符合过滤筛选需求。
  我们应该给监控添加历史数据加载功能，设置一个回溯日期，或者慢慢加载全部（可能会数据太大）。」
- **状态**：已落地（后端 + 界面 + 判据）

---

## 一、问题：增量同步只有「向新」一条腿

| 事实 | 位置 |
| --- | --- |
| 每轮每频道只拉最新 100 条 | `monitor.rs:SYNC_LIMIT` |
| `sync_cursor` 只存 `last_message_id`（最大值） | `store.rs` schema |
| `messages(chat, limit, None)` 的 `before_id` 恒为 `None` | `run_sync_pass` |

⇒ **筛选覆盖面 = 已入库范围 = 最新一窗 + 之后每轮新增的 100 条**。
频道早期内容永远进不来，用户「按关键词筛 3 个月前的资源」必然筛不到。

这不是缺陷，是**结构性边界**：增量同步的职责就是「保持最新」，它没有
「往回补」的语义。

## 二、方案：加一条「向旧」的腿

### 2.1 数据结构

`sync_cursor` 加两列（`migrate_sync_cursor_backfill`，幂等补列）：

| 列 | 含义 |
| --- | --- |
| `backfill_until` | 目标日期（unix 秒，**0 = 不回溯**） |
| `backfill_before_id` | 向旧翻页游标（0 = 未开始，下一轮重新算起点） |

**两个游标分开存**，因为方向相反：

```
backfill_before_id ──→ ←── 消息 id ──→ last_message_id
   （往回补到这里）        （越小越旧）      （增量已到最新）
```

如果共用一列，回溯每推进一步就会把增量游标往回拽，下一轮增量会把回溯过的
消息**再算一次新增**（未读徽标虚高）。

### 2.2 为什么「指定日期」而不是「慢速全量」

用户给了两个选项（回溯日期 / 慢慢加载全部）。选日期：

| | 指定日期 | 慢速全量 |
| --- | --- | --- |
| 终点 | 明确（到达该日期即停） | **没有**（频道最早一条在哪不知道） |
| 用户可预期 | 能估算「大概多久」 | 不能，只能等 |
| 中途可判断「够了」 | 能（看日期进度） | 不能 |
| 数据量 | 由用户决定 | 可能远超需要（8302 行里 51% 连 caption 都没有） |

全量的唯一优势是「不用选日期」，代价是把决定权交给一个看不见的终点。

### 2.3 为什么后台慢翻而不是一次打完

`BACKFILL_LIMIT = 100` 条/轮/频道，理由与 `SYNC_LIMIT` 同源：`messages` 的
clamp 上限是 100。一次打完「回溯三个月」会连打几十上百个 RPC，
直接触发 Telegram **flood-wait**（账号级限流，恢复要几十分钟）。

代价是慢——所以**进度必须可见**（见 §3.2）。这是刻意的交换：
慢但可预期 > 快但可能被限流。

### 2.4 与增量同步共用单飞

`backfill_once` 和 `sync_once` 都走 `state.claim_sync()`：

- 同一个账号、同一份 RPC 预算，**不能并行**；
- 抢不到名额立即返回 `Skipped`（不排队——排队等于把并发的轮次推迟后照样执行）；
- 后台 tick 的顺序是 **先增量、后回溯**（新消息优先，历史慢慢补）。

## 三、落地

### 3.1 后端

| 位置 | 内容 |
| --- | --- |
| `store.rs` | schema 两列 + `migrate_sync_cursor_backfill` |
| `store.rs` | `get_backfill` / `list_backfill_pending` / `set_backfill` / `advance_backfill` / `clear_backfill` |
| `store.rs` | `MonitoredChannel.backfillUntil`（列表能看见进度） |
| `monitor.rs` | `backfill_once` / `run_backfill_pass` / `parse_date_utc` / `days_from_civil` / `civil_from_days` |
| `monitor.rs` | tick 循环里排在 `sync_once` 之后 |
| `routes.rs` | `POST /api/tg/monitor/backfill` `{channelId, untilDate}` |
| `routes.rs` | `DELETE /api/tg/monitor/backfill/:id` |

### 3.2 界面

- 每个监控频道行尾一个「回溯」按钮（**条目级动作，不上提到节头**——层级纪律 BUG-324）；
- 点开在**行下方**展开内联表单：日期输入 + 「开始回溯」；
- 回溯进行中，行下方常驻一条状态条：「回溯中（至 2026-01-01）」+「取消回溯」。

**为什么表单内联而不是弹窗**：弹窗要处理定位/遮挡/关闭，而这只是
「选个日期 + 一个按钮」，内联更稳也更好测。

**为什么进度必须显示**：回溯是长跑（每轮一页）。不显示状态的话，用户点了
「回溯到 1 月」之后毫无反馈，只会以为按钮没生效——BUG-327「存在≠可用」
的同一个坑。

### 3.3 四个终点（都会 `clear_backfill`）

| 终点 | 判据 |
| --- | --- |
| 频道最早一条已入库 | `messages(...)` 返回空 |
| 到达目标日期 | 本页最旧一条的 `date < until_ts` |
| 游标没动（**死循环防护**） | `min_id >= before` |
| 用户取消 | `DELETE /api/tg/monitor/backfill/:id` |

第 3 条是**防护不是「慢」**：游标不动意味着下一轮会重复同一页，
继续跑只会把 RPC 预算烧在一个不动的窗口上。宁可停下报错。

### 3.4 「取消」不回滚

取消只停翻页，**已入库的历史消息保留**。理由：那些消息本来就在
「已入库范围」里，删掉会让用户已经看到、已经筛到的内容凭空消失。

## 四、判据

| 判据 | 位置 |
| --- | --- |
| 已知日期映射（含闰日 `2024-02-29`） | `monitor.rs::backfill_date_tests::parse_date_utc_maps_known_dates` |
| 拒绝非法日期（`2026-02-31` / 平年 `2-29` / 带时间 / 早于 epoch） | `parse_date_utc_rejects_garbage_and_impossible_dates` |
| 日期往返校验有牙齿（`2-31` 反解必然 ≠ 原输入） | `days_from_civil_roundtrip_detects_overflow` |

**期望值不由被测函数自己算**：`2026-10-22 = 1792627200`、`2024-02-29 = 1709164800`
由独立实现给出（`datetime.date(2026,10,22) - date(1970,1,1)`），否则是自证循环。

## 五、契约细节

- **时区**：`untilDate` 只收 `YYYY-MM-DD`，服务端按 **UTC 当日 00:00** 解释。
  不用本地时区：边界差几小时对「补历史」没有影响，而引入时区就要处理夏令时
  （还要多一个依赖）。前端显示走 `toISOString().slice(0,10)` 同一口径——
  不用 `toLocaleDateString()`，否则会出现「我选 1 月 1 日，状态显示 12 月 31 日」。
- **只收日期不收时间戳**：用户说的是「回溯到几月几号」，时分秒对他没有意义，
  却会让前后端各算一套时区。
- **只允许已监控频道**：给未监控频道回溯 = 把用户没要的数据塞进库（404）。

## 六、未做 / 待观察

- **没实测吞吐**：回溯 1 万条需要多久、DB 涨多少，需要真跑一次才有数。
  按每轮 100 条、tick 间隔 30s 估算，1000 条约 5 分钟、10000 条约 50 分钟
  （假设 tick 不被前端轮询抢占）。这是估算不是实测，跑过再改这段。
- **没有「批量回溯全部频道」**：目前逐频道设置。若用户要「一次给所有频道设
  同一个日期」，那是一个独立的小端点（`POST /api/tg/monitor/backfill/all`），
  未做——先看单频道用起来够不够。
- **回溯期间的未读徽标**：补进来的历史消息 `message_id` 可能小于
  `last_read_message_id`（已读游标），因此**不会**被算成未读——这是正确行为
  （历史不是新消息），但未实测确认。
