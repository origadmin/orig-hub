# 剧集来源区 + 媒体库可读性 + 连播跳过：增量设计

> 范围：四项**用户已明确提出**的改动。全部为 `shell`（前端），**无 schema 变更**。
> 与本文件同批的缺陷档：`docs/bugs/BUG-182.md`（多源区摘除接错端点）。
> 存储模型部分**不在此文件裁定** —— 见 `docs/design/episode-segment-model-2026-09-29.md`。

## 1. 来源区：从「常驻技术面板」改为「有选择时才出现的播放来源」

### 1.1 判定依据

`docs/bugs/BUG-148.md`：**实现约束 ≠ 产品信息**；能力边界只在用户**正因此受阻**时出现。
`#itemId` 与 `ref` 是**溯源用内部标识**，用户不能拿它们做任何事 —— 属于典型「替实现道歉」。

### 1.2 改动

| # | 现状 | 改为 |
|---|---|---|
| C1 | 无备用源时仍渲染整个区块 | `sources.length === 0` ⇒ **整个区块不渲染**（无选择即无控件） |
| C2 | 区块标题与行标签都叫「来源」 | 区块标题改「播放来源」；行标签改「当前」/「备用」 |
| C3 | 主版本行显示 `#itemId` | **移除**；需要时移入 `title` 悬浮 |
| C4 | 来源行显示 `ref`（`chat:msg`） | **移入 `title` 悬浮**，不常驻 |
| C5 | 备用源行只显示标题 + 两个裸按钮 | 每行补**用户能用来决策的客观量**：分辨率（有则显示）/ 体积 / 时长 / 是否已缓存 |
| C6 | 「切为主版本」「摘除」两个动作语义不明 | 见 §1.3 |

> **不显示「最高质量」徽标** —— 系统当前无法客观判定质量
> （`media_item.width/height` 在产库实测长期为空；详见 `episode-multi-source-design-2026-09-22.md` §1.3）。

### 1.3 两个动作的语义必须分开（**本设计最关键的一条**）

用户原话：「来源混乱（**要的是切换视频**，实际混乱）」。

现状只有一个动作：「切为主版本」= **永久改数据**。而用户要的是「这次播这个」= **当次生效**。
两者混为一谈的后果是可验证的：切主会置 `primary_locked=1`（`episode-multi-source-design-2026-09-22.md` §3.2），
而该锁会让自动选主**永久短路** —— **用户只是想换个版本看看，却永久改变了这一集的主版本。**

| 动作 | 语义 | 作用域 | 是否改数据 |
|---|---|---|---|
| **播这个**（主区） | 当次播放用哪个来源 | 仅本次播放 | **否** |
| 设为默认播放（溢出区） | 永久改主 + 锁 | 影响所有后续播放 | 是 |

## 2. 媒体库卡片：让标题能被读完

| # | 改动 | 量化 |
|---|---|---|
| C7 | 网格最小列宽 `150px` → **`200px`**（剧集卡 `160px` → `200px`） | 1900 窗：9 列 → **7 列**，每列约 208px；标题可用约 192px ≈ 16 中文字符 |
| C8 | 卡片标题 `truncate`（单行） → **`line-clamp-2`**（两行） | 同宽度下可读字符数**翻倍**；`title` 悬浮仍保留全文 |
| C9 | 文本区在标题两行后不得挤压元信息 | 元信息行（体积/来源/剧集名）保持单行，标题超出由 clamp 截断 |

**900 最小窗复核**（内容区约 500px，见长期约定 §十二）：`200px` ⇒ **2 列**，每列约 244px。
2 列在窄窗下仍可用；**不接受**「窄窗只剩 1 列」——若实测如此，则该断点回落到 `170px`。

## 3. 剧集选集器：N 条 + 显示更多

**问题**：F8 —— 全量渲染。用户原话：「剧集导航列表数据过多会导致查询复杂，重改逻辑建议 N 条 + 显示更多（全部）」。

| # | 改动 | 说明 |
|---|---|---|
| C10 | 默认渲染前 **N = 20** 集 | 超过时底部出现「显示全部（共 M 集）」按钮 |
| C11 | 「显示全部」= 一次性展开全部（**不做分页滚动**） | 剧集不是无限流；真实剧集量级 10–100 集，全展开的 DOM 成本可接受 |
| C12 | 已聚焦集**不在前 20 条时自动滚入视野** | 否则「从第 30 集进来」会看不到自己选中的那一集 |
| C13 | 保留既有「收起」开关（`:417`） | 与「显示更多」语义不同：前者折叠整个选区，后者限制条数，**两者并存不冲突** |

**「查询复杂」的边界**：本改动**只动前端渲染**。后端 `get_series` 一次返回全部集
（现有行为），**不引入分页端点** —— 引入分页会让「播放第 30 集」需要额外请求，
而单次响应体量（百集级元数据）远低于前端一次 DOM 渲染的成本。**若将来实测响应体成为瓶颈，再单独立项。**

## 4. 连播：跳过片头 / 片尾预告

用户原话：「视频连播，考虑前后会有概览和预告，添加跳过时间功能」。

### 4.1 形态

| 层 | 内容 |
|---|---|
| **手动跳过**（P0） | 播放到片头区间内时，右下角出现「跳过片头」（可点）；点击后跳到片头终点 |
| 区间来源 | **用户设置**：全局默认片头时长（秒），剧集级可覆盖 |
| 自动跳过 | **不做**（自动跳会让用户失去「回看前情」的选择权，且误判区间时不可挽回） |
| 片尾预告 | 同机制，独立配置项；到片尾区间时出现「跳过片尾」→ 直接触发连播 |

### 4.2 为什么是「设置 + 剧集级覆盖」而不是自动识别

系统**没有**片头识别能力（无音频指纹、无章节元数据、无 ffmpeg）。
凭空引入「智能识别」= 造一个必然误判的黑盒。**用户填一个秒数**是当前唯一可解释、可预期的做法。

### 4.3 与既有连播的关系

跳过片尾后**复用既有 `nextUp` 通路**（F9），**不新增第二条连播路径**
（`AGENTS.md` §5 记的 BUG-031 教训：两条路径分叉必生不一致）。
本设计**不修改** `VideoPlayer` 的连播回调签名 —— 只在片尾区间结束时调用同一个 `onEnded` 语义。

## 5. 存储模型（不在本文件裁定，仅登记证据）

用户要求「从扩展性、设计优雅考虑正确方案，不要历史债务堆叠」。

**在产库实测（2026-09-29，只读查询 `%APPDATA%\com.origadmin.orighub\tg\store.db`）**：

| 表 | 行数 | 含义 |
|---|---|---|
| `media_episode` | 56 | 分集 |
| **`media_episode_source`** | **0** | 备用源 —— **全库零使用** |
| **`media_episode_image`** | **28** | 挂图 |
| `media_item` | 193 | 条目 |
| `media_series` | 13 | 剧集 |

⇒ **「统一绑定模型」的迁移成本 = 28 行**。
这是做对模型**最便宜的时机**：备用源 0 行（连迁移都不需要），挂图 28 行。
一旦数据涨起来，同样的重构就不再可行。

**因此建议**：不要把「多版本源」「顺序片段」「挂图」继续做成三张各自为政的表，
而是按 `episode-segment-model-2026-09-29.md` 的方向做**统一读模型 + 角色互斥不变量**。
存储形态（独立表 vs 统一表）的选择与代价对比见该文档 §2.2/§2.3，**待裁定**。

## 7. 回归风险

| # | 风险 | 缓解 |
|---|---|---|
| R1 | 卡片列宽变大 ⇒ 单屏可见条目变少，用户抱怨「内容变少了」 | 1900 窗从 9 列降到 7 列；**需实机截图确认观感**，不接受纸面推断 |
| R2 | 标题两行 ⇒ 卡片高度不一，网格参差 | `line-clamp-2` 固定两行高度（不足两行也占位），保持网格对齐 |
| R3 | 来源区不渲染 ⇒ 用户找不到「这个文件从哪来」 | 溯源信息移入 `title` 悬浮 + 条目详情；**不删除信息，只改呈现位置** |
| R4 | 选集器默认 20 条 ⇒ 用户以为「集数少了」 | 按钮文案必须含总数（「显示全部（共 56 集）」），不得只写「更多」 |
| R5 | 片头秒数配错 ⇒ 每次跳到错误位置 | 只在**片头区间内**显示按钮，且按钮文案标注将要跳到的时间点 |
| R6 | 动多源区时踩到死代码 | **活落点只有 `SeriesDetail.tsx`**；`EpisodeBoard`/`EpisodeRow`/`EpisodeExpanded`/`SeriesHero` 全仓零 importer，**改它们等于没改** |

## 8. 待拍板

### D1. 来源区的「播这个」是否立为 P0？

- **问题**: 是否把「当次播放用哪个来源（不改数据）」立为 P0，与「设为默认播放（永久改主）」并存为两个独立动作？
- **现状与代价**: 现状只有一个动作「切为主版本」，而它会置 `primary_locked=1` 永久短路自动选主（`episode-multi-source-design-2026-09-22.md` §3.2）。用户「只是想换个版本看看」必须承担**永久改数据**的后果；且备用源在切主前**根本不可播**（`MediaLibraryPanel.tsx:297-315` 的 `episodesToItems` 只用 `e.itemId`）。不立 ⇒ 用户抱怨的「要的是切换视频，实际混乱」不解决。
- **设计锚点**: `docs/design/episode-source-and-library-ux-2026-09-29.md` §1.3
- **请求**: 立 / 不立（不立请确认接受「换视频只能永久改数据」）

**A. 立为 P0：主区「播这个」+ 溢出区「设为默认播放」**
- 涉及: `tauri-shell/src/components/media/SeriesDetail.tsx`、`tauri-shell/src/components/MediaLibraryPanel.tsx`
- 量化: 1 处播放源状态上提、2 个文件、0 端点变更（`detachEpisodeSource` 等既有 API 已够用）
- 回归风险: 低 —— 不改数据模型，不改端点；播放源为组件内状态，切集即重置
- 后果: 「换个版本看看」不再留下永久痕迹；代价是「当前播的是哪个版本」成为**瞬态状态**，不跨会话记忆

**B. 不立：维持「切为主版本」单动作**
- 涉及: 无
- 量化: 0 改动
- 回归风险: 无新增
- 后果: 用户继续只能通过永久改主来换视频；且第一次试探即锁死自动选主，后续新源永不自动上位

**C. 不做（连 BUG-182 的端点修复也一并搁置）**
- 涉及: 无
- 量化: 0 改动
- 回归风险: 无新增（既有缺陷保留）
- 后果: 「摘除备用源」按钮继续点了无效，且**验收脚本继续是绿的** —— 缺陷被 testid 掩盖

### D2. 卡片尺寸取 200px 还是更保守的 170px？

- **问题**: 网格最小列宽从 150px 提到多少？
- **现状与代价**: 现状 150px ⇒ 1900 窗 9 列、标题约 11 中文字符即截断（F5+F6 量化）。不定 ⇒ T02 无法开工。
- **设计锚点**: `docs/design/episode-source-and-library-ux-2026-09-29.md` §2
- **请求**: 选 A（我的建议）还是 B？

**A. 200px + 标题两行（推荐）**
- 涉及: `tauri-shell/src/components/MediaLibraryPanel.tsx`、`tauri-shell/src/components/media/MediaCard.tsx`
- 量化: 2 个文件、2 处类名；1900 窗 9→7 列、标题可读字符约 11→32（两行 ×16）
- 回归风险: 中 —— 单屏可见条目减少约 22%，**需实机截图确认**是否引发「内容变少」的新抱怨
- 后果: 标题基本可读全；代价是列表更长，滚动更多

**B. 170px + 标题两行**
- 涉及: 同 A
- 量化: 2 个文件；1900 窗 9→8 列、标题可读约 24 字符（两行）
- 回归风险: 低 —— 列数几乎不变，观感变化最小
- 后果: 标题改善幅度较小（长标题仍需截断），但**不改变列表密度**，用户无感知成本

**C. 不做（保持 150px 单行）**
- 涉及: 无
- 量化: 0
- 回归风险: 无新增
- 后果: 「标题显示不全」持续；用户只能靠 hover 逐个看全文

### D3. 剧集选集器的 N 取多少？

- **问题**: 默认渲染前 N 集，N = 10 / 20 / 30？
- **现状与代价**: 现状全量渲染（F8）。真实剧集量级：在产库 `media_episode` 56 行、13 部剧集 ⇒ 单剧集数不大，但存在百集级内容。不定 ⇒ T03 无法开工。
- **设计锚点**: `docs/design/episode-source-and-library-ux-2026-09-29.md` §3
- **请求**: 选 A（我的建议）还是 B？

**A. N = 20（推荐）**
- 涉及: `tauri-shell/src/components/media/SeriesDetail.tsx`
- 量化: 1 个文件、1 个常量；56 集时默认渲染 20 条（减少 64% DOM）
- 回归风险: 低 —— 有「显示全部（共 M 集）」兜底；聚焦集自动滚入视野（C12）
- 后果: 20 集以内的剧集**完全无变化**；超过时多一次点击

**B. N = 30**
- 涉及: 同 A
- 量化: 1 个文件、1 个常量；56 集时默认渲染 30 条（减少 46%）
- 回归风险: 低
- 后果: 更少用户会碰到「显示更多」按钮，但首次渲染成本更高

**C. 不做（保持全量渲染）**
- 涉及: 无
- 量化: 0
- 回归风险: 无新增
- 后果: 百集级剧集首次打开时渲染全部条目；用户抱怨的「数据过多」不改善
