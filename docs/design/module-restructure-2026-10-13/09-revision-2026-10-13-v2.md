## 1. 评估一：下载升级为全局任务监控（含 TG 缓存任务）

### 1.1 结论：可做。跨插件聚合的关键原型已在生产代码中跑通

取证（`download-engine/crates/orig-daemon/src/activity.rs`）：

- `GET /api/activity`（BUG-077 方案 a）已实现**只读跨进程聚合**：引擎内存任务表 + HTTP 拉取 orig-tg `/api/tg/cache/tasks/all`，统一成 `TaskView`（[activity.rs:185-198](file:///d:/workspace/project/golang/origadmin/framework/projects/orig-hub/download-engine/crates/orig-daemon/src/activity.rs#L185-L198)）。
- 五条铁律正是插件化需要的制度：①只读聚合不写两侧存储；②控制分流（`control:{side,native_id}` 指回原端点）；③不造统一删除；④不造假暂停/继续（TG 无真续传，至多 retry）；⑤跨进程容错（orig-tg 不可达恒 200，引擎任务照常，`sources[]` 如实标注来源健康）。
- 异构保留：`unit`（bytes/items）、原生状态词、TG 侧 `speed=null`（非 0）。
- TG 侧任务持久化与跨重启恢复已具备：`cache_task` 表（`orig-tg/src/store.rs:460`，状态 `queued/running/done/cancelled/failed/interrupted`）、服务重启恢复 queued（`orig-tg/src/main.rs:222-235`）。
- daemon 已是 orig-tg 的**唯一所有者**：拉起/端口顺延/就绪等待/巡检自愈（`orig-daemon/src/state.rs` tg_child、`main.rs:134-146` tg_supervise）。
- **前端当前完全没有消费 `/api/activity`**（全仓 grep 无引用）——全局监控是「后端等前端」，不是从零开坑。

### 1.2 需要的架构调整（硬编码 TG → 通用插件注册表）

1. **聚合器泛化**：`collect()` 从「引擎 + 写死的 19787」改为「引擎 + 遍历已启用插件注册表」，每插件声明 `capabilities.jobs` 才参与。`TaskView.id` 由 `dl:`/`tg:` 改为 `{plugin_id}:{native_id}`（引擎自身 plugin_id=`core`）。
2. **jobs 快照端点成为插件准入条件**：`GET /plugin/v1/jobs` 必须返回**内存快照、不碰 SQLite**。现状豁免（TG 该端点每次读两次库，BUG-085，5s 轮询缓解）**必须在插件泛化前偿还**——插件数 N 放大后等于每 5s 2N 次 DB 读。准入化以后这不是「TG 的历史债」而是「契约的一部分」，conformance kit 强制。
3. **控制代理**：新增 `POST /api/activity/jobs/:gid/:action`，daemon 按注册表把 pause/resume/cancel/retry 路由到对应插件端口；前端不再持有任何插件端口（端口动态顺延，前端也不该知道）。
4. **扇出预算**：聚合并发执行、单插件短超时（300ms）、daemon 内存缓存快照（1s TTL，多客户端共享一次拉取）；任一插件慢/挂不拖整列表（铁律 5 泛化）。
5. **TaskView v2 增补**：`plugin_id`、`plugin_label`、`account_id?`、`kind`（download/cache）、`unit`、`actions[]`（真实能力，TG 活跃态永无 pause）、来源健康行。**不做跨侧状态归一化**（现状注释已论证：归一化即宣称同构）。

### 1.3 前端形态

- 下载模块 = 全局监控。状态 tabs（全部/下载中/暂停/完成；失败任务行内红字，不占导航——沿用现状裁定）；来源筛选 chips（全部来源 / 引擎 / TG / 未来插件）；行内展示来源徽标与真实单位（字节进度条 vs 条目数）。
- TG 工作区**移除任务管理职责**：缓存任务的发起结果一律进下载监控。CacheManagerDialog 两入口重新分工——**任务队列/运营入口归下载模块**；**字节清理入口归设置·插件**（清缓存只回收字节的规则不变）。
- 轮询纪律（AGENTS §5）：单一轮询源（daemon 聚合端）、有活才轮、5s 上限、等值短路、失败退避；高频行 `memo` + useEvent。
- 来源异常态：健康条「TG 插件不可用（任务行保留最近快照/灰显）」；引擎任务恒显示。

### 1.4 性能与红线

- 播放热路径零接触：活动聚合是独立控制面，daemon raw 投递**禁止**因任何插件调用而增加回源跳（07 红线不变）。
- 插件在播放期间产生的字节一律先经 `/host/v1/ingest` 归仓，再由宿主 `serve_local_file` 统一投递——播放器永远只认宿主。
- 风险：多插件扇出（§1.2.4 预算覆盖）；对账责任边界——宿主只呈现不纠偏，插件自持任务持久化与重启恢复（TG 模式即范本）。

## 2. 评估二：TG 之外的插件调查 + 共通接口 + 生命周期

### 2.1 生态调查（2026-10 联网核实）

| 候选 | 形态/版本 | 覆盖 | 许可证 | 机器接口 | 适配分型 |
|---|---|---|---|---|---|
| **yt-dlp** | 单文件 exe，2026.08 仍在高频发布 | 1000+ 视频站（YouTube/B 站/播客等） | Unlicense（公有领域） | `--dump-json`、`--progress-template` 行式 JSON、postprocessor hooks | fetcher |
| **gallery-dl** | 单文件 exe，1.32.x（2026） | 200+ 图站（X/IG/Pixiv/Reddit…） | GPLv2 | `--exec`、JSON job 模块、配置文件 | fetcher |
| **BBDown** | .NET 单 exe，活跃 | 哔哩哔哩音视频/字幕/互动 | MIT | CLI 参数 + 日志解析 | fetcher |
| **tickstep/aliyunpan** | Go CLI+可引库，v0.4.0（2026-06） | 阿里云盘文件树/上传下载/WebDAV/同步 | Apache-2.0 | CLI 交互式 shell（需适配层）、API 库可参考 | drive |
| tickstep 天翼云盘 | 同作者 Go CLI | 天翼云盘登录/上传下载/分享 | Apache-2.0 | 同上 | drive |
| BaiduPCS 系（维护 fork） | Go CLI | 百度网盘文件/离线 | 开源（fork 分散，供应链需钉版本） | CLI | drive |

调查结论：

1. 所有候选都能以「**独立 exe + JSON 行协议/退出码**」稳定驱动，与既定插件模型天然契合；其中两个 GPL/强 Copyleft 候选（gallery-dl GPLv2、ffmpeg GPLv3）进一步反证进程边界是正确选择。
2. Go 库（aliyunpan）**不建议**跨语言链接进 Rust（cgo Go 重型、崩溃传导），需要时以其 API 契约为参考在插件二进制内重写或直接包 CLI——插件是独立进程，语言自由。
3. 三类业务形态收敛为三型（下节），没有出现需要第四种导航形态的候选。

### 2.2 插件分型（对 08 文档的修订）

| 型 | 特征 | 标准屏 | 代表 | 任务来源 |
|---|---|---|---|---|
| `source` | 可浏览远端、选会话/频道、看媒体流 | **source-browser**（两栏：列表+媒体流） | TG | 用户在流中点「缓存」 |
| `fetcher` | 无浏览面，URL/粘贴框 → 任务 | **url-task**（输入框+解析建议+任务） | yt-dlp / gallery-dl / BBDown | URL 提交 |
| `drive` | 网盘文件树浏览+批量传输 | **drive-tree**（树+传输列表） | 阿里/百度/天翼云盘 | 文件树勾选 |

一个插件可在 manifest 声明多型与多能力；**能力清单**：`jobs`（必有，接入全局监控）、`browse`、`accounts`、`search`、`ingest_types`。

### 2.3 共通契约（08 增补后的最终面）

manifest（`plugins/<id>@<ver>/manifest.json`）：

```json
{
  "manifest_version": 1,
  "id": "tg",
  "version": "1.4.0",
  "kinds": ["source"],
  "capabilities": ["jobs", "browse", "accounts", "search"],
  "screens": [{"type": "source-browser", "browse": "/plugin/v1/browse"}],
  "account_schema": "tg-phone",
  "config_schema": { },
  "min_host": "1.4.0",
  "start_mode": "always",
  "sha256": "…", "signature": "…"
}
```

- 插件→宿主端点（环回，动态端口由 daemon 注入）：`GET /plugin/v1/manifest`、`GET /plugin/v1/health`、`GET /plugin/v1/jobs`（**内存快照**）、`POST /plugin/v1/jobs`、`POST /plugin/v1/jobs/:id/{cancel,retry}`、`GET /plugin/v1/browse/*`、`/plugin/v1/accounts/*`。
- 宿主→插件回调：`POST /host/v1/ingest`（FileFact + 字节交接：move 进库根或声明 ref 路径）、`GET /host/v1/library/resolve`（去重查询）。
- 字节投递契约不变：任何插件产出的可播字节，归仓后一律走宿主 `serve_local_file`（07 红线）。

### 2.4 前端统一化：有限「标准屏注册表」（对 D5 的修订）

D5-A 原表述「描述符驱动」过于笼统，TG 2600 行定制 UI 证明一块万能描述符装不下真实插件。修订为**宿主内置有限标准屏类型注册表**：

- `source-browser` / `url-task` / `drive-tree` / `accounts-login` 四块标准屏，由宿主统一实现导航、列表虚拟化、播放器、任务行、缓存/入库、i18n、主题；
- 插件只提供数据端点 + schema（字段映射、过滤维度定义、登录步骤 schema），**v1 仍不带 JS**——第三方改不到宿主，兼容性锁死；
- TG 改造 = TgPanel 数据模型/接口保留，视图壳换成标准 source-browser（业务代码大量可复用，废弃的是三栏布局与自定义任务轮询）；
- 表达力边界：四块屏覆盖不了的插件 v1 不接收；签名 Web Bundle（D5-B）仍是 v2 议题。

### 2.5 安装 / 注册 / 启动模式

1. **安装**（复用 ffmpeg 受管安装范式）：在线（官方清单+sha256+签名+代理）/ 本地包 / 离线目录三路径；落 `%LocalAppData%\OrigHub\plugins\<id>@<ver>\`；原子替换，失败留旧版。
2. **注册**：daemon 启动扫描插件目录 → 读 manifest → `min_host` 兼容门禁 → 能力/屏类型登记 → 出现在设置·插件列表。未签名/哈希不符 = 不注册并明示。
3. **启用/禁用**：用户显式开关，持久化；禁用 = 不拉起，**数据不清**（会话/库/字节保留）。
4. **启动三模式**（manifest 声明，用户可在设置覆盖）：
   - `always`：长连接/需要推送与监控的（TG、网盘推送类）；daemon 启动即拉起，崩溃指数退避重启；
   - `on-demand`：打开其工作区或有它的任务时拉起，空闲 N 分钟退出（yt-dlp 类典型，省内存）；
   - `manual`：仅用户手动启动。
5. **supervisor 泛化**：`state.rs` 的 `tg_child: Mutex<Option<Child>>` 泛化为 `HashMap<plugin_id, PluginProc>`，沿用已验证机制：Popen+wait 托管（AGENTS §5 TG 重启托管铁律）、端口顺延、就绪探测（spawn 成功≠可用，BUG-177/227）、单一所有者。
6. **更新/卸载**：禁用→替换→重注册；卸载可选「同时删除账号会话与字节」，默认只删二进制。

## 3. 评估三：TG 采集——两级化 + 账号进设置

### 3.1 禁止第三级 Navi（用户明确）

现状层级取证（`tauri-shell/src/components/TgPanel.tsx`）：左栏分组导航（`groupMode`：全部订阅/未分组/Telegram folders）→ 中栏组内频道列表（`detail`）→ 右栏消息流，三套互斥钻取状态（L330-343、L1484-1820）。这就是用户感知「菜单乱」的来源。

**新布局（两栏，source-browser 标准屏）**：

- **左栏 = 一个会话列表**，不产生任何下钻列：
  - 顶部 segmented 过滤：全部 / 监控 / 群组 / 私聊（对**同一列表**过滤，不是导航）；
  - Telegram 收藏夹（folders）= 过滤行下方一排横向 chips（多选筛选），不再点进新列；
  - 行内「监控」开关（现状组内页已有，提到行内）；
  - 搜索：跨会话搜索维持在顶部上下文栏（BUG-100 方案 A 不变）。
- **右栏 = 选中会话的媒体消息流**（现状右栏气泡/相册组/全局查找结果直接保留）。
- 层级规则写入前端架构文档：任何插件屏最多「列表 → 详情」两级；筛选维度只许用 segmented/chips/tabs。

### 3.2 账号全部移入设置，多账户必须支持

- 删除 TgPanel 左上账号块（含「切换」按钮）；右栏顶只留**只读**当前账号 chip +「管理」→ 跳设置·账号。
- **设置·账号**（新分区）：按插件分组的账户列表；TG 支持多账户：添加（手机号→验证码→2FA 状态机，复用 AccountsPanel）、登出、设为当前、每账户监控数/字节占用；未来 fetcher/drive 插件的账号（cookie/OAuth 由 `account_schema` 驱动同屏渲染）。
- **多账户技术评估**：
  - 现状：单 `session.session` + 单 client（AGENTS §6：`%LocalAppData%\OrigHub\tg\`）。改造：`sessions/<account_id>.session` + client 池，端点按 `X-Account-Id` 或 query 选路；
  - 数据作用域：`monitored_channel` 归账户；`cache_task` 加 `account_id`；媒体条目 ref 现状 `"<chat>:<msg>"` 全局唯一——推荐加 `account_id` **列**（旧行回填默认账户），ref 字符串保持兼容，避免全量改投递链路；
  - 量级：Telethon 多 session 为官方支持模式，无协议风险；工程量集中在 client 池路由与四张表加列迁移，中等。
- **分期裁定**：M6 TG 参考化仍交付**单账户**（控制爆炸半径），但契约/表结构本期预留可空 `account_id`；多账户单列 **M7**。

### 3.3 既有实现处置（用户：当前设计问题不大，主要是渲染卡顿）

- 数据模型与后端接口（dialogs / folders / monitored / messages / sync_cursor）**原样保留**；
- 卡顿治理（有据可依）：①缓存任务进度轮询随全局监控上线而**移出 TG 视图**（视图不再每秒拉任务）；②消息气泡沿用 memo + useEvent（TgPanel 头部注释已记载这是历史卡顿根因）；③长列表补虚拟滚动（新增强制项，纳入 M6 验证）；④缩略图继续 TtlLru、媒体流继续 K=4 parallel_range_stream（AGENTS §D3 不动）。

## 4. 评估四：共享两级启用

回答用户「设置里面开启插件？然后共享里面开启具体功能？」——**是，明确两级**：

1. **第一级 · 设置 → 共享服务**（服务生命周期）：总开关、绑定网卡/端口、令牌根策略、数据目录。共享是**内置服务**（`orig-daemon/src/modules/share/`，axum 静态实现，非第三方二进制），但开关/启停交互与插件服务同构。关 = 端口不监听，任何外部请求拒绝。
2. **第二级 · 共享域 → 共享目标**（共享什么）：服务关闭时该域为 onboarding 卡（「去设置开启共享服务」，同 TG 未启用态范式）；服务开启后管理目标——
   - 目标类型：整个库 / 剧集 / 标签 / 任意条目集；
   - 每目标：独立开关、独立令牌（可单独撤销不影响其他）、二维码、有效期、访问记录；
   - 全局服务停用 → 所有目标立即不可达；目标开关不动监听。
3. 安全口径不变：只读、无令牌不出字节（401）、写方法全拒绝、仅绑定用户显式选择的网卡。

## 5. 评估五（核心）：下载 / 文件 / 媒体库设计——从现有 Nav 演进

### 5.1 导航：7 项 → 6 项（只收不放）

**层级铁律**：一级永远 6 项；模块内 tabs、segmented、chips、分类下钻均为**筛选**，不占导航层级；禁止任何模块再出现第三级钻取（TG 是最后一个被拆掉的特例）。

### 5.2 三主模块职责切分

- **文件（事实层，默认首页）**：库根/下载根下**全部受管字节**，含 zip/pdf 等非媒体；文件夹浏览、来源徽标（引擎/导入/TG/插件）、孤儿条目处理、定位/打开目录；对应既有「全部文件」+ 自动分类。
- **媒体库（策划层）**：只看媒体；内容卡片、剧集/季编排、标签、播放器**唯一出口**（VideoPlayer 只在媒体域实例化，07 红线）。
- **下载（工具层：监控+发起）**：全局任务监控（所有来源）+ 新建下载；行内跳转：「定位文件」→ 文件模块定位行；「来源 TG」→ TG 工作区对应会话。

三层关系：下载/插件产出字节 → ingest 成文件事实（文件层立即可见）→ 媒体库识别媒体后提供策划与播放。清缓存只回收字节不删条目、删来源条目连字节清（§D4 规则不变）。

### 5.3 保留的现状资产（不重写清单）

Sidebar 计数徽标与折叠、分类下钻数据链、DownloadList/DownloadItem/DetailSheet、MediaLibraryPanel 全套（卡片/剧集/标签/播放器）、tgReady 入口门控、播放/投递/缓存全部既有纪律与 verify 脚本。

## 9. 三轮修订（2026-10-13 同日，用户四点裁定）—— 最高效力

### 9.1 导航终态：五项一级 + 两棵树（取代 §5.1 六项）

```
📁 全部文件 128  ⟩   点击父行 = 全部成品内容；chevron = 展开/收起（两个独立点击区，沿用现状原语）
   ── 分类（事实轴：自动分类，对成品文件筛选）
     视频 / 音乐 / 图片 / 文档 / 压缩 / 其他
   ── 资料库（策划轴：原媒体库能力合并于此）
     剧集 / 标签 / 未归档（新增）
⬇ 下载 3  ⟩         点击父行 =「全部任务」（全局监控默认态）；chevron = 展开/收起三档
     下载中 / 已暂停 / 已完成          （三档是全部任务的预设过滤，可整组缩起）
✈ TG 采集           🔗 共享           ⚙ 设置
```

- 一级**五项**：全部文件 / 下载 / TG 采集 / 共享 / 设置。**媒体库一级按钮取消**（D13 合并方案，见 §9.3）。
- 两棵树的展开态独立于导航选中态（现状 `catOpen` 已验证该模式，`Sidebar.tsx:130-149`）；chevron 只翻转
  展开，父行文字只做导航——禁止再做成杂交按钮（BUG-058/089 的教训直接沿用）。
- 树内只有**一层**子项：分类子项与资料库入口同属「全部文件」的一层子项（用组标签分隔，不是两级钻取）；
  「剧集 → 剧集详情」是主区全屏 drill-in（现状 MediaLibraryPanel 已如此），不产生侧栏层级。
- 三档子项与下载页状态 tabs **双向联动同一状态**（点侧栏=预设过滤，页内切 tab 同步高亮侧栏）；
  计数徽标沿用现状（下载中数量在父行，三档数量在子行）。
- 折叠侧栏时两棵树退化为父行单按钮（现状 collapsed 范式）。

### 9.2 「全部文件」只显示成品；失败/未完成任务归入下载（修订 §5.2 与 BUG-082 旧口径）

- **成品定义**：下载已完成的产物、已入库 media_item、本地导入文件。进行中/暂停/失败/cancelled/interrupted
  的任务记录**一律不出现在全部文件**——文件层是「真的内容」，不是任务表。
- 现状取证：`MainLayout.tsx:177-189,267-268` 的「全部文件」与三档共用 `DownloadList`，全部文件实际是
  **下载记录总表**（含失败行）。这正是用户指出的核心错误：点进分类看到的应是内容本身，不是任务。
- **失败任务可见性迁移**：BUG-082（2026-09-21 裁定）原规定「error|cancelled 不单列档，由全部文件兜底」。
  三轮改判：**兜底位置改为下载页「全部任务」**（行内红字 + 行内重试/删除，不给一级/树位）。M0 实施时
  同步在 BUG-082 追加「后续变更」节锚定本次改判（不新开 BUG）。
- 主区「真的内容的单独展示」：媒体类成品用海报/缩略图墙（视频带时长角标、图片组显示张数、音频可播），
  非媒体（pdf/zip/…）用紧凑文件行；两类同屏时分区呈现，不用任务行样式。孤儿条目（有条目缺字节）
  仍在文件层可见并标缺失、给移除入口（现状规则不变）。
- TG 未登录/插件关闭不影响文件层：文件事实不依赖任何插件存活（媒体库后端探活「不探 TG」的既有原则推广）。

### 9.3 媒体库合并方案（如何合并）—— 双轴一树，去内容平铺

媒体库不是「降级为子页面」，而是把它的**入口与内容平铺**归位到全部文件树，策划能力零裁剪：

| 原媒体库位置 | 合并后位置 | 呈现 |
|---|---|---|
| 左 rail「内容 1,320」海报墙 | 全部文件父行 + 分类子项（视频/图片/音乐…） | 成品内容墙；范围扩到含非媒体文件行；这是内容平铺的**唯一**位置 |
| 左 rail「剧集」 | 树 · 资料库 → 剧集 | 剧集墙；点剧集 = 主区全屏剧集详情，**成员管理保留**（增/移成员、季集编排；BUG-112 的「从剧集移除图片」入口在此补齐） |
| 左 rail「标签」 | 树 · 资料库 → 标签 | 标签云；点标签 = 该标签条目墙（是过滤结果，不是新层级） |
| —（新增） | 树 · 资料库 → **未归档** | 有条目、但 `series_id IS NULL` 的媒体；给「归入剧集」批量入口。定义：标签是交叉分类，不改变归档态 |
| 播放器起播 | 不变：07 红线唯一播放器 | 从内容墙/标签结果/剧集详情均可起播，VideoPlayer 仍只在媒体域实例化 |

- **去内容化的准确含义**：资料库入口页（剧集墙/标签云/未归档收纳）本身不平铺「全部内容」；内容只在
  「全部文件/分类」与各收纳口的**结果集**里出现。散内容通过「未归档」永远可达，不会因合并而丢失。
- 数据层**零变更**：media_item / series / tags 表现有结构足够；未归档=单条 `WHERE series_id IS NULL` 查询，
  不新建表、不加冗余列。
- 现状 `MediaLibraryPanel.tsx` 处置：rail 外壳删除；items 海报墙并入文件内容浏览器；series/tags/
  seriesDetail 三套面板保留为 files 域子视图；`pendingMediaFocus`、ImportDialog、批量标签/剧集对话框原样复用。

### 9.4 下载页 = 全局监控（确认 D7，细化交互）

### 10.2 全部文件：关系、内容、冲突评估（第 2 点）

**关系三轴（复述并固化）**：

| 轴 | 数据 | 组织方式 | 典型入口 |
|---|---|---|---|
| 任务轴 | 下载记录（含过程态） | 状态/来源 | 下载（全局监控） |
| 事实轴 | 成品字节（FS + 完成任务 + media_item） | 自动分类（classify 规则） | 文件·分类组 |
| 策划轴 | 剧集 / 标签 / 未归档归属 | 人工 | 文件·资料库组 |

同一成品可同时出现在「分类/视频」「标签 #4K」「剧集 X」三处——**多轴有意重复，不是数据重复**。
删除/解耦语义沿用现状红线：删文件 = 事实消失、各轴同步消失（TG 来源连带清字节，AGENTS §5）；
从剧集/标签移除 = 只断归属，字节与事实保留（BUG-112/051）。

  **结论（用户已拍 D2=A）**：按 `media-service-deployment-decision-2026-09-28.md` 推荐路径
  **D2-A 拆 library.db → D1-B 媒体迁入 orig-daemon**，新增 0 个 sidecar、前端一行改向、
  BUG-172 以 P1-P4 闭环。它是独立成立的核心修复，**措辞上不再表述为「文件域 M1 前置」**——

  TG 反向依赖保持单向：迁后 orig-tg 仅经 daemon 的库接口访问，4 处跨域读只取
  `media_message.caption`（F9，窄而单向）。
- **C2（数据缺口，随 C1 落地自然归位）：引擎下载完成不自动入库。** `upsert_media_item` 目前只存在于

### 10.4 TG 两级设计的优缺点评估（对照现状 TgPanel，第 3 点）

保留为优点：

1. 数据/接口零改动（folders/dialogs/monitored/messages/sync_cursor），只换前端 IA，回归面可控；
2. 消除「文件夹→频道→消息」三级钻取栈；segmented 与文件夹 chips 是过滤不是导航，与 D8 标准屏一致；
3. 任务轮询移出（直接消灭一个卡顿源），账号区移设置给多账户腾位；
4. 监控圆点、右栏媒体流「缓存/入库并打开」、TgGlobalSearch 等现状高频能力全部有对应承载。

风险与必须吸收的改进（写入线框，不作为新决策）：

- **文件夹 chips 的扩展性**：用户文件夹可能 10+，单行 chips 排不下 → 横向滚动 + 末尾「更多 ▾」弹层，
  或与 segmented 合并为「范围 ▾」筛选器；不允许出现挤压换行的第二行 chips。
- **复合过滤的可见语义**：segmented（全部/监控/群组/私聊）× 文件夹 chips × 搜索是交集关系；
  列表顶部须把生效条件渲染成可单独清除的 chip（含「清除全部」），避免「列表为什么变短」无解释。
- **列表信息密度不退步**：现状中栏含未读数、最新预览、监控态；压平后保留未读标记与分区标题
  （私聊/群组分区或排序），不允许只剩一串名字。
- **监控切换防误触**：保留现状监控操作的确认口径，圆点点击区域与打开会话区域视觉分离。
- **账号切换路径**：M7 多账户下「去设置切账户」对频繁切换者太长 → 右栏账号只读 chip 允许带
  「切换账户 ▾」快捷菜单（状态机仍只在设置，这里仅快捷入口，M7 范围，本期单账户只读）。
- **发起缓存后的反馈**：任务已可在下载页追踪；toast 提示「已加入下载」即可，不强制切视图。

### 10.5 三级分布（L1/L2/L3）：概念统一、载体分治（第 4 点）

三级作为**概念骨架**全应用统一：L1 = 侧栏一级（恒定五项 + 按 D17 可能出现的插件位）；
L2 = 模块内次级选择；L3 = 内容/详情。但 **L2 的载体按模块类型分三型，不全部塞进侧栏树**
（否则重蹈 TG 三级导航塞进侧栏、侧栏膨胀的覆辙）：

| 模块 | 类型 | L2 载体 | L3 |
|---|---|---|---|
| 文件 / 下载 | 列表型 | **侧栏树子项**（已定双树） | 内容区 |
| TG / 未来 drive 插件 | 主从型 | **模块内左栏列表**（会话/文件树），侧栏无子项 | 右栏详情 |
| 设置 | 配置型 | **内容区左侧分区导航**（现状八分区） | 分区表单 |
| 共享 | 管理型 | 服务开启时内容区内轻量 **segmented：共享目标 / 访问记录**；关闭时无 L2（onboarding） | 目标表/日志表 |
| fetcher 型插件（yt-dlp 等） | 无浏览面 | **无 L2**：入口在「新建下载」的来源选择 | — |

结论：**共享不进侧栏树**（两项二级内容不值得一个树），采用内容区内 segmented；三级模型因此
「逻辑统一、视觉分治」。该条作为 D15 请批。

### 10.6 查漏：fetcher/drive 型插件的入口此前未定义（进入 D17）

§2/D8 定义了 source / fetcher / drive 三型，但只设计了 TG（source 型）的一级工作区；
fetcher（yt-dlp，无浏览面、只有 URL 解析任务）与 drive（有文件树）的入口 IA 此前缺失。
推荐：fetcher 不占导航位——「新建下载」对话框提供来源/解析器选择，产出的任务进全局下载；
drive 型在其插件启用后按品牌名动态获得一级工作区（主从型 L2，见 §10.5）；source 型同 drive。
一级位因此是「固定五项 + 已启用的 source/drive 插件品牌项」，数量受启用数自然约束。
