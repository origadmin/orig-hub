# TG 插件「过滤下载」三项设计问题评估

- **日期**：2026-10-22
- **来源**：用户提出的三点设计问题（筛选字段 / 数据量 / 加载模式）
- **性质**：**评估，不改代码**。第 3 点用户明确要求「评估改动和优缺点」。
- **结论摘要**：第 1 点诉求成立但**不能直接照做**（会砍掉 1183 条唯一可筛线索）；第 2 点是**结构性边界**而非缺陷，需要新增「回溯游标」；第 3 点建议走**组级封面 + 点击展开**的中间路线，不是「全列表无图」。

| 指标 | 数值 | 取法 |
|---|---|---|

## 一、筛选不该筛文件名

### 1.1 现状（代码事实）

筛选是 SQL 层做的，`file_name` **与 caption 平级参与匹配**：

```sql
-- store.rs:1361 / 1366 / 1396 / 1407 / 1496 / 1503 / 1590 / 1607 等多处
AND (m.caption LIKE ?1 ESCAPE '\' OR m.file_name LIKE ?1 ESCAPE '\')
```

前端还有一处**显示**层面的同类问题：`TgFilterPanel.tsx:49 hitTitle()`
```ts
const cap = (h.caption ?? '').split('\n')[0].trim()
if (cap) return cap
const name = (h.fileName ?? '').trim()   // ← 无 caption 时直接显示文件名
if (name) return name
return `#${h.messageId}`
```

### 1.2 但「文件名是随机的」这个前提，数据只支持一半

用户说「文件名是随机的」。实测：

| 分类 | 条数 | 说明 |
|---|---|---|
| 匹配 `isRawFileName` 正则（`^[a-z]+--\d+_\d+`） | **0** | 这个正则一条都不命中 |
| 其他文件名 | 1647 | 里面有真有假 |

**随机名不止一种形态**。`isRawFileName` 只认 `photo--1004418016251_2000` 这种下载器命名，而库里实际的随机名是：

```
C_DUM7FbyLCHsjxK.mp4                              ← 随机 token
mUeNvHbMgx08Bg0f0X7y010412000PGO0E010.mp4         ← 哈希
42522643430-1-30112_merged.mp4                     ← 数字拼接
image_2026-10-01_15-55-30.png                      ← 时间戳（半可读）
```

真正可读的只有少数：
```
2048原创 - 母子性爱游戏 第2集 - AI短剧.mp4
```

⇒ **用户判断对（多数文件名不可读），但现有识别规则太窄（0 命中）**。

### 1.3 关键约束：直接删掉文件名，会砍掉一半可筛内容

```
可筛总数（caption 或文件名非空）= 8302 − 4227 = 4075（49%）
其中仅靠 caption            = 2892（35%）
仅靠文件名（无 caption）     = 1183（14%）
```

**如果筛选完全不再看 `file_name`**：可筛内容从 49% 掉到 35%，1183 条消息**彻底无法被任何文字筛到**（它们没有 caption，只剩文件名这唯一线索）。

而 51% 的消息两样都没有 —— 这部分本来就筛不到，是另一件事（见第三节）。

### 1.4 三个方案

| 方案 | 做法 | 优点 | 缺点 | 改动量 |
|---|---|---|---|---|
| **A（推荐）** | 匹配时排除「随机名形态」：扩宽 `isRawFileName` 成一组规则（`photo--x_y`、纯 token、纯哈希、时间戳），SQL 侧改为 `caption LIKE ? OR (file_name LIKE ? AND NOT is_raw(file_name))` | 噪音消失，同时保住 1183 条里**有可读名**的那部分 | 规则永远不全；判定要在 SQL 里做（或入库时打标记列） | 中：正则 + 入库列 `file_name_readable` + SQL 改 8 处 |
| **B** | 筛选完全不匹配 `file_name` | 最简单，一行改动 | 丢 1183 条唯一线索；用户以后想按「短剧名」搜就没了 | 小 |
| **C** | 保持筛选，但**显示**不用随机名（`hitTitle` 接入 `isRawFileName`） | 界面噪音立刻消失，不影响命中率 | 搜「photo」仍会命中随机名（筛选噪音还在） | 极小 |

**建议**：先做 **C**（立刻消除用户看到的乱码标题，零风险），再评估 **A**。**不建议 B**——数据不支持「文件名一律无用」。

> 顺带一个已有的设计意图：`tgmedia.ts:68 isRawFileName` 的注释写着「这类字符串不是标题……直接展示会让界面充满乱码般的噪音」。**规则早就定了，只是 `hitTitle` 没接它**，且正则太窄。这不是设计要改，是实现没跟上。

## 二、频道数据只加载一部分

### 2.1 现状：这不是 bug，是两处刻意的边界

**同步侧**（`monitor.rs` `run_sync_pass`）：
```rust
let items = state.client.messages(ch.channel_id, SYNC_LIMIT, None).await?;  // SYNC_LIMIT=100，before=None
// cursor 只向新推：new_max = max(new_max, it.id)
```
⇒ 每轮只取**最新 100 条**，游标只记「已同步到的最新 id」（`sync_cursor.last_message_id`），**没有向旧回溯的游标**。

**查询侧**（`routes.rs:3380` 注释原文）：
> 只查本地已同步消息（查询语义，不做网络回补）。

⇒ 筛选覆盖面 = 已入库范围。用户没滚动到过的历史，压根不在库里。

所以「只加载一部分」是**同步深度**的设计边界，不是加载失败。

### 2.2 影响面

| 场景 | 现在 | 期望 |
|---|---|---|
| 新内容 | 每轮拉最新 100，够用 | 不变 |
| 频道列表浏览 | 滚到顶按 `beforeId` 回补一页（30 条） | 不变 |
| **筛选历史内容** | **只能筛已入库的 8302 条** | 覆盖指定日期之后的全部 |

### 2.3 方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A（推荐）回溯日期** | 给监控频道加 `backfill_until`（日期）；后台低优先级任务按 `before_id` 逐页向旧翻，翻到日期为止；限速（如每轮 1 页/频道） | 目标明确、可控、可中断；用户说「设置一个回溯日期」正是这个 | 需要新游标列 + 新任务 + 限速；日期之前的内容仍不在库 |
| B 慢速全量 | 不设日期，后台一直往旧翻到频道开头 | 最终覆盖全部 | 大频道（几万条）跑很久；DB 增长不可控；RPC 预算与下载抢 |
| C 筛选时实时回补 | 筛选时发现本地不足就向 TG 翻页 | 无需预设 | 筛选变慢、不确定；与「查询语义不回补」的既有裁定冲突 |

**推荐 A**，并明确三点：
1. **回溯是后台任务，不阻塞下载**（走现有 `claim_sync` 单飞机制，或独立低优先级通道）
2. **必须有进度与上限**：`backfill_until` + 每频道已回溯到的最小 id，界面显示「已回溯到 YYYY-MM-DD」
3. **DB 增长要有心理预期**：8302 条现在约占多少空间需实测；按 100 条/轮估算，一个 2 万条的频道要 200 轮

### 2.4 需要的结构改动

`sync_cursor` 现在只有 `last_message_id`（向新）。需要新增：

```sql
ALTER TABLE sync_cursor ADD COLUMN backfill_min_id INTEGER NOT NULL DEFAULT 0;
ALTER TABLE sync_cursor ADD COLUMN backfill_until  INTEGER;   -- unix 秒，NULL=不回溯
```

配套：`get/set_backfill_cursor`、`run_backfill_pass`（与 `run_sync_pass` 并列，共用单飞名额但优先级更低）。

## 三、加载模式：聊天式 vs 列表点击展开

### 3.1 现状（代码事实）

| 项 | 现状 |
|---|---|
| 布局 | **聊天式媒体流**：最新在底部，滚到顶加载更早（`TgPanel.tsx:296`） |
| 分页 | 30 条/页，`beforeId` 游标 |
| 虚拟化 | **无**（没有 react-window / content-visibility） |
| 缩略图 | 每条 1 张，`<img src=/api/tg/thumb/...>` |
| 缩略图服务端缓存 | **无**——`thumb` 直接 `client.thumb()` 回源 Telegram，只有浏览器 `max-age=86400` |
| 组（相册） | 已有：`albumGridClass` / `ALBUM_MAX_TILES=10`，组内平铺 |

⇒ 打开一个频道页 = 30 个缩略图请求 = 最多 30 次 MTProto 往返（浏览器缓存过的除外）。

### 3.2 用户提议的评估

> 图片即时加载是否改成「列表点击加载整个组内容」，排版改成适合过滤下载的模式？

**先说结论**：方向对，但**不能做成「无图列表」**——因为 51% 的消息既无 caption 也无文件名，**缩略图是它们唯一的识别手段**。砍掉即时缩略图 = 让一半内容变成盲选。

### 3.3 三个层次，不是二选一

| 层次 | 做法 | 首屏缩略图请求 | 识别能力 |
|---|---|---|---|
| L0 现状 | 每行都出缩略图 | 30 | 最强 |
| **L1（推荐）组级封面** | 每个**条目**（单条 or 相册组）只出 **1 张**封面（组取第一张），点击展开组内全部成员再加载 | 单条页 30 → 组页 **组数**（通常 5–10） | 保留视觉识别，请求降 50–70% |
| L2 纯列表 | 列表只有文字（caption/类型/大小/日期），点击才加载内容 | 0 | **最弱**：51% 无文字内容变盲选 |

### 3.4 L1 的优缺点

**优点**
- 首屏 MTProto 请求从 30 降到组数（相册频道实测能降 50–70%）
- 列表更短更整齐，滚动手感更像「待下载清单」而非聊天记录
- 组结构与「勾选 = 整组入库」（BUG-341 已定）**天然对齐**——现在组是勾选单位，但渲染还是逐条平铺，L1 让呈现与语义一致
- 配合第 2 节回溯，列表可以按「组 + 日期」组织，更像下载清单

**缺点 / 风险**
- **组内成员看不见**（要点击）⇒ 相册满员 10 条时，用户少了一次「一眼扫完」的能力
- 需要新增展开态与「已展开组的成员图」加载策略，**改动面不小**
- 「聊天式」是既有交互习惯（BUG-300 那批定型），改布局要重新走一遍验收
- 无虚拟化的问题**不会因为 L1 而消失**：翻到 500 条时 DOM 仍会堆积，L1 只是减缓首屏

### 3.5 改动面估算（L1）

| 部分 | 内容 | 量级 |
|---|---|---|
| 列表渲染 | 由「逐条平铺」改为「按 `(chatId, groupId)` 收敛成条目」 | 中（`TgPanel` 内渲染函数，约 200 行区域） |
| 组展开 | 新增展开态 + 成员图懒加载 | 中 |
| 缩略图策略 | 封面取组内首条；成员图仅在展开后请求 | 小 |
| 虚拟化（可选） | 若同时做，需固定行高估计 | 大（参考 BUG-316/BUG-328 的教训） |
| 验收 | 新判据：首屏请求数 ≤ 组数、组内成员数一致、展开后请求数 = 成员数 | 中 |

**建议**：L1 单独一轮做，不要和「回溯日期」混在一起——两者都动数据链路，混做会让归因变难。

## 四、建议顺序与需要拍板的点

**顺序**
1. **C（显示层去随机名）**——零风险、立刻消除用户看到的噪音，可当天做
2. **第 2 点 回溯日期**——真正解决「筛不到历史」，用户明确要的功能
3. **A（筛选层排除随机名）**——依赖 1 的规则，等规则稳定后再进 SQL
4. **第 3 点 L1 组级封面**——改动最大，单独一轮

**需要用户拍板**
1. **第 1 点**：接受「排除随机名而不是排除文件名」吗？（完全排除会丢 1183 条唯一线索）
2. **第 2 点**：回溯用「指定日期」还是「慢速全量」？日期从哪天开始（比如各频道统一回溯到 2026-01-01）？
3. **第 3 点**：L1 组级封面（保留视觉识别）还是 L2 纯列表（请求最少但一半内容盲选）？

**本评估未做的事**：没有改任何代码；没有实测「回溯 1 万条需要多久 / DB 涨多少」（需要先有实现才能量）。
