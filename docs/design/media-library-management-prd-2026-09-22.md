### 1.9 取证结论（一句话）

**「入库、归档、打标、编辑、删除、剧集编排」已经相当完整；缺的是三块：**
1. **字节状态在库内不可见、不可筛**（离线承诺无法自证）；
2. **磁盘占用与库条目对不上号**（占用统计在 TG 域，媒体库只显示元数据之和）；
3. **检索/视图维度不全**（无来源、无剧集筛选、无字节状态、无列表视图），且批量动作只覆盖「标签/剧集/删除」。

## 4. 需求池

> **本表分为两类。** 用户 2026-09-22 指出：R10（续播/最近播放）被当成了他提的需求，而他**从未提过** —— 根因是「缺口」与「提案」混排、且统一给「用户价值」列，使**提案看起来像发现**，读的人（团队）就会把提案端到用户面前要拍板。故拆分如下：
> - **缺口（§4.1）**：现有数据/字段/API **已有半成品**（存在但未接通，或口径算错），修它属**收尾**而非造新功能；每条附 `file:line` 取证。
> - **提案（§4.2）**：需要**新增数据或新交互范式**的能力，**无用户原话支撑**；每条显式标注「价值为推断」并写清「若不做，现状如何」。
>
> **用户原话基线（2026-09-22 本轮，仅四条）**：
> ① 单集多视频必须有主版本　② 剧集里的图片删不掉　③ 所有问题必须有跟踪列表　④「媒体库设计不足，缺乏管理」
> 另有**定位原话**（同日拍板）：「当前是一个下载工具，缓存不就为了流畅本地播放的么？」
> 说明：① ② 分别对应已登记的 BUG-113 / BUG-112，按既定约束**不在本 PRD 重复**；③ 是流程要求（跟踪列表），非功能需求。故本 PRD 的功能性支撑**实际只有 ④ + 定位原话**。
>
> **P0 判定规则**：必须同时满足「是缺口」+「有用户原话支撑」。凡仅由 ④ 这类概括性原话支撑者，其**具体形态**（做成筛选还是分组、一个数还是几个数）仍属**推断**，需用户点头。

### 4.1 缺口（有取证）

| ID | 需求描述 | 可核证据（当前做不到） | 用户证据（原话） | 用户价值 | 优先级 · 依赖 |
|---|---|---|---|---|---|
| **R1** | **字节状态可见 + 可筛（以磁盘 stat 为准，不读 DB 承诺）**：媒体库字节状态**复用 `cache::probe_cached_bytes(path) -> BytesPresence`（`cache.rs:112`）的三态**，与 BUG-105 同一口径：`Present`→**已落盘**（可本地播）；`Missing`→**文件丢失**（确认缺失，**复位状态**，使「重新缓存」入口自然出现）；`Unknown`→**状态未知**（stat 失败但非 NotFound：权限/被独占/路径非法，**不下结论、不复位**，界面只提示）。叠加既有的「无 `file_path` = **仅入库**」，共四种展示态；卡片/列表显示并支持按状态筛选。`MediaItem` 下发该状态（**不新增 DB 列**，沿用「`has_bytes` 不落列」的既定克制）。 | `MediaItem` 结构无字节状态字段（`media.rs` 的 `MediaItem`）；`has_bytes` 仅分集视图有（`media.rs:643/1256`），条目侧只能靠 `filePath` 推断（`tgmedia.ts:130-136`）；**无「按字节状态筛」入口**（`MediaLibraryPanel.tsx` 全文无此参数） | 定位原话「缓存不就为了流畅本地播放的么？」；④「媒体库设计不足，缺乏管理」 | 离线承诺可被验证；既避免「点开才发现打不开」，也避免「文件被手工删除后仍显示已缓存、且不出现重新缓存入口」的卡死。 | **P0** ｜ 后端：条目列表需为每条 `file_path` 做**一次 stat**（复用既有函数，**零新 DB 读**；成本见 §6 Q9）。**不得复用 `file_path IS NOT NULL` 派生**——那是 BUG-105 明确「未覆盖」的缺陷（`BUG-105.md:83-86`）。长期归口 BUG-098 的 `asset_state`（「权威但可自愈、以 stat 为准」）。**「补齐后仍不落盘」的根因属 BUG-115/116，本需求只负责「可见」，不修落盘**。 |

### 5.1 媒体库面板布局（在现有左栏 + 主区基础上增量）

### 5.2 关键交互（表格）

| 场景 | 交互 | 反馈（必须如实） |
|---|---|---|
| 筛「未落盘」 | 左栏点「仅入库 / 文件丢失 / 状态未知」→ 列表只留对应条目 | 空结果区分「库真的没有」与「当前筛选无匹配」（沿用现有 `libraryEmpty` 判据）；「状态未知」需与「文件丢失」分开呈现，避免被误当缺失而触发无谓重下 |
| 批量补落盘 | 勾选 N 条 → 点「补落盘」→ 确认条「将入队 N 条」→ 执行 | 「已入队 X 条，跳过 Y 条（非 TG 来源，无原路可取）」；**入队 ≠ 成功**，措辞不得暗示已完成 |
| 批量清字节 | 勾选 N 条 → 点「清字节」→ 确认条「将清理 N 条、释放 X」→ 执行 | 「已清理 N 条，释放 X；条目保留，可重新缓存」；**external（本地导入）条目不参与**，需显式排除并说明 |
| 占用核对 | 打开媒体库即见「磁盘占用 / 元数据合计 / 未落盘条数」 | 必须同时给出，避免把元数据之和当磁盘占用；磁盘占用须**含 external 字节**，否则低估 |
| 字节状态核对（网格或列表） | 扫视卡片徽标（或列表列）→ 按状态筛出 | 丢失项以警示色标注，并直接给出「重新缓存」（TG 来源）或「文件已丢失」（本地来源）；「状态未知」另给中性提示，不给重下入口。（列表视图本身为**提案 R7**；未点头前在网格卡片上以徽标呈现同一信息） |

### 5.3 不可违反的交互不变量（沿用既有设计原则）

1. **无字节不给播放入口**：一个点了必然 404 的按钮比没有按钮更糟（现状 `MediaCard.tsx:204-228` 已如此，新视图必须保持一致）。
2. **清字节 ≠ 删条目**：两个动作在 UI 上必须可区分、动词不重叠（BUG-121 教训）。
3. **危险动作先给影响面**：批量清字节必须走「预览 → 确认条 → 执行」，沿用 `CacheBytesPanel` 的三条不变量（只删缓存产出字节、不删条目、预览只读）；**external（本地导入）文件永不删除**，与 `delete_media_item`（`routes.rs:2118-2123`，仅在 `inside_dir` 时删文件）保持一致。
4. **不新增第二份真值**：字节状态的唯一判据是**磁盘 stat**（`probe_cached_bytes` 三态），不是 DB 里的 `file_path`；前端不得自行推断，也不得把「DB 有路径」当「字节在」。`Unknown` 必须与 `Missing` 分开、不得合并成布尔（BUG-105 教训：一次瞬态 stat 失败不得触发无谓重下）。

## 8. 一页结论

- 现状的**内容管理**（入库/归档/打标/编辑/剧集编排/删除）已经可用；**缺口集中在「字节」与「检索维度」两条线上**。
- 最小可交付闭环 = **R1 + R2 + R3 + R5**（均**无新表**：R1 复用 `probe_cached_bytes`、R2 复用 `cache/stats`、R5 复用 `cache/clear?ids=`；仅 R1/R2/R3 各需后端小改——条目逐条 stat、external 补字节累加、`ItemQuery` 加 `source`），即可把「管理不足」中**最影响离线承诺**的部分补上。
- **字节状态的判据必须是磁盘 stat，不是 DB 的 `file_path`**：这是 BUG-105 明确留白、且已被 `probe_cached_bytes` 三态实现好的口径；直接复用 `file_path IS NOT NULL` 会在媒体库重蹈「已缓存却 404」的覆辙。
- **磁盘占用必须含 external 字节**，否则本地导入（`source='local'`）占盘却不出现在任何数字里，用户会低估。
- **R4 必须与 BUG-115/116 同期**，否则会制造「操作成功但离线仍打不开」的新一类不一致。
- **需求分两类**：**缺口（有取证）7 条** R1/R2/R3/R4/R5/R6/R11；**提案（需用户点头）7 条** R7/R8/R9/R10/R12/R13/R14。**P0 只有 5 条**：R1/R2/R3/R5，加 R4（条件：与 BUG-115/116 同期）。
- **R10（续播/最近播放）、R14（播放列表）已移入 §4.2 提案区**：**无用户原话支撑**（用户已明确「最近播放不是我提出的功能需求」），需用户点头才立项。
- **移除类操作（R9 批量移出剧集、R11 摘除备用源）依赖 BUG-126**：tombstone 落地前，
  「移除」会被下一次同步 / 重新加入**撤销**（BUG-112 已实测复现）。
