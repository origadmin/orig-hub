### 1.9 取证结论（一句话）

**「入库、归档、打标、编辑、删除、剧集编排」已经相当完整；缺的是三块：**
1. **字节状态在库内不可见、不可筛**（离线承诺无法自证）；
2. **磁盘占用与库条目对不上号**（占用统计在 TG 域，媒体库只显示元数据之和）；
3. **检索/视图维度不全**（无来源、无剧集筛选、无字节状态、无列表视图），且批量动作只覆盖「标签/剧集/删除」。

## 2. 产品目标

| # | 目标 | 对应定位 |
|---|---|---|
| G1 | **让「收进库」= 「离线能看」可被验证**：库内每条内容都能一眼看出字节是否在本地，缺失项可筛出、可批量补齐。 | 离线优先的核心承诺 |
| G2 | **让 115 条平铺内容可被组织与定位**：补齐「按来源 / 按剧集 / 按字节状态」的检索与「列表视图」，批量动作覆盖归档与字节两类。 | 下载工具的内容管理 |
| G3 | **让磁盘占用可被理解与回收**：库内可见真实占用与每条占用，可按条目/剧集回收字节而**不丢条目**。 | 缓存为本地播放服务，缓存需可管 |

## 3. 用户故事

| 角色 | 用户故事 |
|---|---|
| **整理者**（大量 TG 订阅 + 本地导入混在一起） | As 整理者, I want 按「来源 / 未归入剧集 / 无字节」筛出待处理条目并批量加剧集、批量打标 so that 我不用在 115 条里逐页翻找。 |
| **观看者**（离线场景，如通勤/断网） | As 观看者, I want 打开库就能看到「哪些是已落盘可离线看的」，并能从上次看到的位置继续 so that 我不必点开一条才发现打不开、也不必重新找位置。 |
| **存储焦虑者**（磁盘紧张） | As 存储焦虑者, I want 知道库占了多少真实磁盘、每条占多少，并能按剧集/按勾选清掉字节而保留记录 so that 我能腾空间且不丢「我看过什么」。 |
| **整理者（剧集）** | As 整理者, I want 在剧集内一次性清掉不属于正片的图片/预告、并把缺失字节的集数筛出来补回 so that 剧集在离线时是完整可连播的。 |
| **观看者（图集）** | As 观看者, I want 图片与视频在库里被明确区分、图片有独立浏览位 so that 我不会点图片却进了播放器。（现状已部分具备：`MediaViewer` 按 kind 分流；本条为保持性需求，防止回退） |

## 4. 需求池

> 优先级：**P0 = Must have**（不做则「管理不足」未被解决）、**P1 = Should have**、**P2 = Nice to have**。
> 「依赖」列明确标注是否需先修已知缺陷（BUG-115/116 等）。

### P0

| ID | 需求描述 | 用户价值 | 依赖 |
|---|---|---|---|
| **R1** | **字节状态可见 + 可筛（以磁盘 stat 为准，不读 DB 承诺）**：媒体库字节状态**复用 `cache::probe_cached_bytes(path) -> BytesPresence`（`cache.rs:112`）的三态**，与 BUG-105 同一口径：`Present`→**已落盘**（可本地播）；`Missing`→**文件丢失**（确认缺失，**复位状态**，使「重新缓存」入口自然出现）；`Unknown`→**状态未知**（stat 失败但非 NotFound：权限/被独占/路径非法，**不下结论、不复位**，界面只提示）。叠加既有的「无 `file_path` = **仅入库**」，共四种展示态；卡片/列表显示并支持按状态筛选。`MediaItem` 下发该状态（**不新增 DB 列**，沿用「`has_bytes` 不落列」的既定克制）。 | 离线承诺可被验证；既避免「点开才发现打不开」，也避免「文件被手工删除后仍显示已缓存、且不出现重新缓存入口」的卡死。 | 后端：条目列表需为每条 `file_path` 做**一次 stat**（复用既有函数，**零新 DB 读**；成本见 §6 Q9）。**不得复用 `file_path IS NOT NULL` 派生**——那是 BUG-105 明确「未覆盖」的缺陷（`BUG-105.md:83-86`）。长期归口 BUG-098 的 `asset_state`（「权威但可自愈、以 stat 为准」）。**「补齐后仍不落盘」的根因属 BUG-115/116，本需求只负责「可见」，不修落盘**。 |
| **R2** | **真实占用与按条目占用（必须含 external 字节）**：媒体库显示磁盘**真实**占用 = 下载目录内字节 **+ external 文件字节**（`/api/cache/stats` 现对 external **只计数不累加字节**，需补 stat 累加）；条目级展示实际磁盘字节（复用 `/api/cache/clear/preview` 的 `items[].bytes`）；修正面板头部 `totalSize` 的「元数据之和」口径，并列给出「元数据合计 / 磁盘占用」。同时标注两类条目的**删除语义不同**：缓存目录内的可清、external（本地导入）**永不删除**（`routes.rs:2118-2123 delete_media_item` 仅在 `inside_dir` 时删文件——「那些是用户自己的文件，不是缓存」）。 | 存储决策有据可依；既消除「显示 10GB、实际 2GB」的高估，也消除「本地导入占着磁盘却不出现在任何数字里」的低估。 | 复用 `GET /api/cache/stats` 与 `clear_preview`；**需后端小改**：`stats` 的 external 分支补 stat 累加（`cache.rs:860-863` 现为 `external += 1; continue;`）。 |
| **R3** | **按来源筛选**：`ItemQuery` 增加 `source`（`local` / `tg`），工具条给出来源筛选。 | 本地导入与 TG 入库是两种生命周期（前者字节天然在盘、后者可清可补），管理动作必须能分开。 | 后端新增查询参数（低成本，`media_item.source` 已存在）。 |
| **R4** | **批量补落盘**：对当前筛选结果或勾选集合，一键批量入队补字节（复用 `enqueueCacheTask` 的单条路径）；结果如实回报「已入队 N 条 / 跳过 M 条（非 TG 来源）」。 | 「缺失」从「看得见」变成「一键可修」，离线优先闭环。 | **强依赖 BUG-115/116**：若入库仍不落盘，补落盘会「入队成功但字节仍不来」，本需求应在 115/116 修复后上线或与之同期。 |
| **R5** | **库内批量清字节（保留条目）**：把 `POST /api/cache/clear?ids=` 的集合通道接进媒体库批量工具条，前置确认条报出「将清理 N 条、释放 X」。 | 腾空间不丢记录；与「删除条目」严格区分。 | 复用 `clearCacheBytes({ids})`，无后端新增。 |

### 明确排除（与离线优先定位冲突或超出范围）

| 排除项 | 理由 |
|---|---|
| 「在线播放优先」/ 在线流体验优化（含 BUG-114 零背压） | 与「离线优先」定位直接冲突；在线流只是兜底，不作为管理台的目标。 |
| 云同步 / 多端同步 / 社交分享 | 超出「离线优先的下载工具」范围，会引入网络依赖。 |
| 推倒重来的数据模型（如把 `media_item` 拆表、引入独立资产库） | 与「优先复用现有数据与接口」约束冲突；现有 `media_series/episode/tag/source` 结构足以承载 P0/P1。 |
| 转码 / remux / 可播性探测（BUG-122） | 属播放内核能力，不属「库管理」；已在缺陷池跟踪。 |

## 5. 关键交互设计

### 5.1 媒体库面板布局（在现有左栏 + 主区基础上增量）

| 区域 | 现状 | 本次改动 |
|---|---|---|
| 左栏顶部统计 | `115 项 · 元数据 3.2 GB`（元数据之和） | 拆成多个数：**元数据合计** 与 **磁盘占用**（`/api/cache/stats`，**含 external 字节**）；磁盘占用建议再分「可回收 / 不可回收（本地导入）」两档（见 §6 Q3）；并加「未落盘 N 条」快捷筛选入口（R1/R2） |
| 左栏导航 | 剧集 / 内容（按类型）/ 标签 | 新增一级分组「**存储状态**」：仅入库 / 已落盘 / 文件丢失 / 状态未知（R1，四态）；新增「**来源**」：本地 / TG（R3） |
| 工具条 | 搜索、排序、未归入剧集、全选/导入/新建剧集/标签管理 | 新增视图切换（网格/列表，R7）；勾选后新增「补落盘」「清字节」两个批量动作（R4/R5），与既有「加入剧集/打标/移除」并列 |
| 主区 | 网格卡片 / 剧集墙 / 剧集详情 | 卡片右下角增加**字节状态徽标**（仅入库/已落盘/文件丢失/状态未知）；列表视图新增一列字节状态（R1/R7） |

### 5.2 关键交互（表格）

| 场景 | 交互 | 反馈（必须如实） |
|---|---|---|
| 筛「未落盘」 | 左栏点「仅入库 / 文件丢失 / 状态未知」→ 列表只留对应条目 | 空结果区分「库真的没有」与「当前筛选无匹配」（沿用现有 `libraryEmpty` 判据）；「状态未知」需与「文件丢失」分开呈现，避免被误当缺失而触发无谓重下 |
| 批量补落盘 | 勾选 N 条 → 点「补落盘」→ 确认条「将入队 N 条」→ 执行 | 「已入队 X 条，跳过 Y 条（非 TG 来源，无原路可取）」；**入队 ≠ 成功**，措辞不得暗示已完成 |
| 批量清字节 | 勾选 N 条 → 点「清字节」→ 确认条「将清理 N 条、释放 X」→ 执行 | 「已清理 N 条，释放 X；条目保留，可重新缓存」；**external（本地导入）条目不参与**，需显式排除并说明 |
| 占用核对 | 打开媒体库即见「磁盘占用 / 元数据合计 / 未落盘条数」 | 必须同时给出，避免把元数据之和当磁盘占用；磁盘占用须**含 external 字节**，否则低估 |
| 列表视图核对 | 切到列表 → 按「字节状态」列排序/扫视 | 丢失项以警示色标注，并直接给出「重新缓存」（TG 来源）或「文件已丢失」（本地来源）；「状态未知」另给中性提示，不给重下入口 |

### 5.3 不可违反的交互不变量（沿用既有设计原则）

1. **无字节不给播放入口**：一个点了必然 404 的按钮比没有按钮更糟（现状 `MediaCard.tsx:204-228` 已如此，新视图必须保持一致）。
2. **清字节 ≠ 删条目**：两个动作在 UI 上必须可区分、动词不重叠（BUG-121 教训）。
3. **危险动作先给影响面**：批量清字节必须走「预览 → 确认条 → 执行」，沿用 `CacheBytesPanel` 的三条不变量（只删缓存产出字节、不删条目、预览只读）；**external（本地导入）文件永不删除**，与 `delete_media_item`（`routes.rs:2118-2123`，仅在 `inside_dir` 时删文件）保持一致。
4. **不新增第二份真值**：字节状态的唯一判据是**磁盘 stat**（`probe_cached_bytes` 三态），不是 DB 里的 `file_path`；前端不得自行推断，也不得把「DB 有路径」当「字节在」。`Unknown` 必须与 `Missing` 分开、不得合并成布尔（BUG-105 教训：一次瞬态 stat 失败不得触发无谓重下）。

## 6. 待确认问题

| # | 问题 | 为什么需要用户拍板 |
|---|---|---|
| Q1 | **R10（继续播放/最近播放）是否进 P0？** | 它需要**新增播放进度存储**（新表或本地持久化），是本次唯一「新数据」需求。若用户认为「离线看长视频必须续播」，应升 P0；若可接受先手动找集，留 P1。我无法从现有数据判断使用频次。 |
| Q2 | **R4 批量补落盘与 BUG-115/116 的排期关系** | 若 115/116 未修，R4 会表现为「入队成功、字节不来」。需用户确认：是先修缺陷再上 R4，还是 R4 与缺陷同期上线（接受阶段性不完整）。 |
| Q3 | **「磁盘占用」是一个数还是几个数？** | 已按评审意见修订为**必须计入 external 字节**（否则本地导入占盘却不出现在任何数字里，系统性低估）。但 external **永不删除**（`delete_media_item` 仅在 `inside_dir` 时删文件），把它与「可清理的缓存字节」加成一个数，会让用户以为「这个数都能腾出来」。建议并列「可回收（下载目录内）/ 不可回收（本地导入）/ 合计」三数——需用户确认接受三数，还是坚持只给一个合计。 |
| Q4 | **R13 重复检测的判定口径** | `mergeSeries` 明确「刻意不做内容级去重」（同名不同内容、多源导入、预告一律保留）。若引入重复检测，需用户确认：是「只提示不自动处理」，还是允许一键合并/删除？后者会与现有「刻意不去重」的设计原则冲突。 |
| Q5 | **R9 批量移出剧集后，空剧集如何处理？** | 删掉最后一集会留下空壳剧集（现状删除确认已会提示 `confirmGroupedWarn`）。批量移出是否顺带清理空剧集，需用户拍板（影响是否有隐性数据残留）。 |
| Q6 | **R8 手动封面的来源范围** | 是「只能从该剧集内已有的图片/视频帧中选」，还是允许「从本地上传一张图」？后者涉及字节落盘与 `poster` 存储形态（现为 data-uri），成本差异大。 |
| Q7 | **左栏新增「存储状态 / 来源」分组后，信息密度是否可接受？** | 左栏已含 剧集 / 内容 / 标签 三组，再加两组可能过载。备选方案是放进工具条的筛选下拉。此项需用户对「左栏 vs 下拉」的偏好拍板。 |
| Q8 | **R1 三态中的「状态未知」如何呈现？** | 采用 `probe_cached_bytes` 三态后，`Unknown`（stat 失败但非 NotFound：权限/被独占/路径非法）既不能声称可本地播，也不得复位状态。界面是显示为「状态未知（不参与筛选结论）」还是并入「文件丢失」？并入会诱发无谓重下（BUG-105 明确要避免），但多一个状态增加认知成本。需用户拍板。 |
| Q9 | **R1 的 stat 成本在库规模增长下是否可接受？** | BUG-105 的场景是「单频道几十行」；媒体库当前 115 条、列表分页 `PAGE=120`，即每页至多 120 次 `tokio::fs::metadata`（微秒级、**零新 DB 读**）。若用户预期库增长到数千条，是否接受「列表接口逐条 stat」，还是改为惰性探测（进入视口才 stat）/ 缓存探测结果（需权衡陈旧窗口）？需用户对规模预期拍板。 |

## 8. 一页结论

- 现状的**内容管理**（入库/归档/打标/编辑/剧集编排/删除）已经可用；**缺口集中在「字节」与「检索维度」两条线上**。
- 最小可交付闭环 = **R1 + R2 + R3 + R5**（均**无新表**：R1 复用 `probe_cached_bytes`、R2 复用 `cache/stats`、R5 复用 `cache/clear?ids=`；仅 R1/R2/R3 各需后端小改——条目逐条 stat、external 补字节累加、`ItemQuery` 加 `source`），即可把「管理不足」中**最影响离线承诺**的部分补上。
- **字节状态的判据必须是磁盘 stat，不是 DB 的 `file_path`**：这是 BUG-105 明确留白、且已被 `probe_cached_bytes` 三态实现好的口径；直接复用 `file_path IS NOT NULL` 会在媒体库重蹈「已缓存却 404」的覆辙。
- **磁盘占用必须含 external 字节**，否则本地导入（`source='local'`）占盘却不出现在任何数字里，用户会低估。
- **R4 必须与 BUG-115/116 同期**，否则会制造「操作成功但离线仍打不开」的新一类不一致。
- R10（续播）是唯一需要新数据的项，优先级待用户拍板。
- **移除类操作（R9 批量移出剧集、R11 摘除备用源）依赖 BUG-126**：tombstone 落地前，
  「移除」会被下一次同步 / 重新加入**撤销**（BUG-112 已实测复现）。
