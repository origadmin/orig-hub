## 0. 结论前置

**用户的抱怨不是「某个功能坏了」，而是「同一件事有四个实现、且没有一处是权威」。**

入库流水线（TG 媒体入库的过程态）当前**散落在 4 个前端组件 + 1 处后端特判**里，
每处各有一套轮询、一套状态口径、一套入口。这不是实现质量差异，是**模块边界缺失**：
TG 的「缓存任务（`cache.tasks`）」能力被**写死在 TG 面板**，而不是作为**宿主通用能力** ——
所以第二个来源插件（网盘/BT）的入库任务无处安放，只能再抄一份。

**修法是一处判断**：

> **入库流水线是「任务」，不是「来源」的私产。**
> 任务归**下载域**（宿主核心域，所有来源的任务汇聚处）；
> 来源插件只负责**浏览**与**发起**，以及**两个跳转出口**。

这与 [08] §7「宿主拥有导航/播放器/媒体卡片/缓存任务/设置全部核心组件；插件只提供描述、不提供代码」
逐字一致 —— 用户说的「统一插件形式维护」「后续插件共通处理」，就是 [08] 的 `cache.tasks` 能力 + 宿主统一渲染。

**同时必须指出**：本条**已经拍板过两次**却从未实施 ——
D21=A（2026-10-14，「TG 面板移除 CacheManagerDialog 挂载、入库改跳转按钮」）与
M3（下载=全局任务监控）都写进了 `tasks.md`，但代码仍是老样子（§1.3）。
**这才是用户说「仍然没有修复」的真实含义** —— 不是没设计，是**设计没落地**。

## 2. 概念收口：三个词的定义（沿用 D21，重申为不变量）

> 用户 2026-10-14 已给出定义（`09-revision §13` 复述）。本文件把它升为**词汇表不变量**——
> 任何新 UI 文案、组件名、接口名都不得偏离。

| 词 | 定义 | 归属域 | 反例（禁止） |
|---|---|---|---|
| **入库** | TG 插件**下载的索引**：一条消息有没有被本应用取到字节 | 来源侧（TG 面板的条目徽标） | 不得把「入库」当任务名（任务在下载域） |
| **下载** | **全部下载（含 TG 入库）的状态监控**：任务跑到哪了 | 宿主核心域（下载域） | 不得在 TG 面板里再列一份任务 |
| **剧集** | **视频集展示与管理**（含图片、来源、视频） | 宿主核心域（文件域） | 不得在下载域里做剧集管理 |

**关键区分（本次诊断的核心）**：

- **条目级状态**（这条消息能不能播）= `entryState.ts:93` 的 `registered/queued/caching/cached/bytesMissing/failed`
  —— 这是**来源侧事实**，随浏览自然呈现，**不是监控**。
- **任务级进度**（这批入库跑到哪了）= `cacheTask` 的 `done/total/status/error`
  —— 这是**任务监控**，归下载域。

⇒ 用户说「这里只监控本身 TG 的简单状态」的精确含义：
**TG 面板保留条目级状态（浏览的自然一部分），移出任务级进度。**

## 3. 目标形态：模块边界

```
┌──────────────────────── 宿主核心域（origin-daemon 提供数据）────────────────────────┐
│                                                                                      │
│  下载域 domains/download/                     文件域 domains/files/     设置域        │
│  ├─ 任务汇聚（所有来源的「任务组」）           ├─ 成品浏览             ├─ 插件启停     │
│  │   ├─ 引擎下载（N=1）                        ├─ 剧集/标签           ├─ 缓存管理入口 │
│  │   ├─ TG 入库（N 条消息）                    └─ 重缓存入口           └─ 账号（TG）  │
│  │   └─ 未来插件任务（BT/网盘…）                                                    │
│  ├─ 统一进度/明细/条目控制 ← 唯一权威                                                │
│  └─ 来源切片 chips（全部/引擎/Telegram/…）                                            │
│                                                                                      │
└──────────────────────────────────────────────────────────────────────────────────────┘
                                   ▲ 上报 cache.tasks 能力 + 状态事件
                                   │
┌──────────────────────── 插件域（独立进程 + 稳定契约）────────────────────────────────┐
│  TG 插件面板 domains/tg/（= 来源浏览器）                                             │
│  ├─ 账号态 / 频道树 / 消息流 / 搜索        ← 浏览                                    │
│  ├─ 条目级状态徽标（entryState）            ← 浏览的自然一部分（只读事实）             │
│  ├─ 发起入库（媒体流动作）                  ← 动作                                    │
│  └─ 两个跳转出口：                                                                   │
│       ①「入库」按钮 + 活跃计数徽章 → 下载域（看进度）                                │
│       ② 完成 toast → 文件域（看成品）                                                │
│  ✗ 无任务轮询  ✗ 无 CacheManagerDialog  ✗ 无失败上报                                 │
└──────────────────────────────────────────────────────────────────────────────────────┘
```

**一句话**：**来源插件只「看」和「交出去」；任务的一切「进度/队列/重试/明细」由宿主统一承载。**

## 4. TG 面板的专业划分（回应用户提议）

> 用户提议：「浏览 + 下载跳转 + 完成后库跳转，你觉得这样可行吗? 给出专业划分建议.」

**判断：方向完全正确，且优于我原先给的三个选项。** 它同时抓住了「动作发起留在来源侧」
与「进度监控交出去」两条 —— 这正是关注点分离。**但落地需精化三条边界**，否则会出现新的模糊：

### 边界一：什么留在 TG 面板，什么必须走

| 留（来源侧） | 走（任务侧 → 下载域） | 判据 |
|---|---|---|
| 条目级徽标（`entryState`：这条消息能不能播） | 任务级进度（`done/total/status/error`） | 「回答的是**这条**还是**这批**」 |
| 发起入库（媒体流「缓存/入库」动作） | 队列/暂停/取消/重试 | 「是**动作**还是**进度**」 |
| 账号/频道/消息流/搜索 | 缓存管理器（CacheManagerDialog） | 「是**来源**还是**任务资产**」 |

**理由**：条目徽标回答「这条消息我处理过没有」——它是**来源浏览的静态事实**，
随消息流一起出现是自然的；去掉它反而要用户跳去下载域逐条找。**它不是监控**（无轮询、无进度条）。

### 边界二：「下载跳转」是**交接**，不是「看一眼再回来」

- 发起入库后，TG 面板的职责**结束**；进度归下载域。**不做**「TG 面板内联显示正在入库」。
- 实现：`入库`按钮（**带活跃任务计数徽章**）→ 深链 `下载?来源=Telegram`（D21 原文）。
- **徽章数据源必须是只读快照**（`/api/activity` 或 SSE 推送），**不得新增轮询源**（D21 原文：
  「读 /api/activity 只读快照，不新增轮询源」）—— 否则 TG 面板又变成第二个监控点，
  正是 BUG-082「三处同源」纪律要防的病。

### 边界三：「完成后库跳转」是**离散事件**，不是常驻列表

- 「完成」由 SSE 事件触发（一次性 toast「已加入文件」+ 跳转入口），**不做**常驻的「已完成列表」。
- 理由：常驻列表 = 第二份任务列表 = 又一个权威源。**一个任务只有一处权威（下载域）。**

### 结论：用户提议的最终形态

> **TG 面板 = 来源浏览器 + 两个跳转出口。**
> 它**不知道**任务队列、进度、失败重试 —— 那些是下载域的事。
> 这条边界同时就是**插件契约**：任何来源插件只要声明 `cache.tasks` 能力，
> 它的任务自动出现在下载域，插件面板只留浏览与跳转 —— **无需各自实现任务 UI**。

## 7. 红线 / 不变量（改动前逐条对照）

1. **不得把「入库」当任务名** —— 入库是 TG 下载的索引（来源侧）；任务是「下载」（宿主侧）。§2 词汇表。
2. **不得在 TG 面板新增任何轮询源** —— 计数徽章只能读只读快照/SSE（D21 原文；BUG-082 三处同源纪律）。
3. **不得删掉条目徽标** —— 它是来源浏览的自然一部分（§4 边界一）；删了用户要跳去下载域逐条找。
4. **不得让 `CacheManagerDialog` 继续挂在 TG 面板** —— D21 已拍板移除（§1.3）。
5. **不得为「完成」做常驻列表** —— 一个任务只有一处权威（下载域）；完成走离散事件。
6. **不得以现有 TG 实现拼凑插件契约**（[08] §10 铁律）—— 先 demo 插件验证宿主，再改 TG。
7. **不得推翻 `entryState.ts` 单源派生**（BUG-170）—— 它已是条目状态的唯一入口，迁移只换数据源不换派生。
8. **不得让插件直接写 library.db / 碰媒体端口**（[08] §5.2）—— 唯一入库通道是 `POST /host/v1/ingest`。
9. **不得在下载域与 TG 面板各留一份任务列表** —— 这正是本次要治的病。
10. **P1 必须零后端改动** —— 用户痛点在前端归位，先摘低垂果实；后端通用化（P2）独立可验证。
