## 2. 逐条结论

### 需求① 内容 `#标签` 高亮 + 频道内筛选

**关键前提（改变了这条需求的性质）**：`#《xxx》` 的解析**后端已经实现且很完整**，不是从零定义语法。

- `download-engine/crates/orig-tg/src/media.rs:2682` `extract_hash_tags()` 已支持括号型标签，`PAIRS`（:2685）含 `《》（）()[]`，必须成对闭合、不跨行、Unicode 字母数字、大小写不敏感去重、`MAX_TAG_CHARS = 32`（:2683），并有 30+ 条单测。
- 注释（:2675-2678）明确写了取舍理由：`#《…》` 在 Telegram 里**不成链接**，但中文频道普遍这样标剧名，不扩展则"一个都提取不到"，实测样例就是 `#《异世界男妓-瓦尔哈拉神枪馆》 EP-2`。
- **但全仓库唯一真实调用点是 `media.rs:2269`**（`collect_hash_tags`，:2248），走"加入媒体库"路径 → **未入库/未缓存的消息一条标签都没有**。消息流里大部分内容不会高亮，这是本条需求的真正缺口。

**推荐方案**：
- **高亮**：把 `extract_hash_tags` 重构为带偏移的 `scan_tags`，后端直接派生 `caption_segments` 返回，前端只负责渲染。**这样前端不写第二份正则**，彻底消灭"两套真源漂移"的风险（本项目已因此付过两次学费：BUG-069 分集标题 vs 条目标题、BUG-087 连接态三处）。
- **筛选**：`listTgMonitorMessages` **已支持 `q` 参数**（`api/tg.ts:150`、`:158`），后端 `store.search_messages`（`routes.rs:1475-1483`、`store.rs:513-554`）已可用且 `%`/`_` 已转义 —— 通道现成，前端只是没传。
  但 `q` 是 **caption 子串**匹配，点 `#A` 会误命中 `#AB` 和正文里的 `A`。故推荐再加 `?tag=`：`caption LIKE` 粗筛取候选 → Rust 侧 `extract_hash_tags` 精筛 → 截断。**零 schema 变更、零回填**；代价是 `hasMore` 保守（而当前 `hasMore` 本来就是保守估计，`store.rs:1492`）。
- **不推荐**本期新建 `media_message_tag` 关联表：唯一增量是"精确分页"，却要背 schema 迁移 + 全量回填 + 与媒体库 `media_tag` 划边界的债（AGENTS.md §5 迁移铁律）。

**必须拍板的语法细节**：`#《A》《B》`（一个 `#` 跟两对书名号）现在**只产出 A，B 被丢**（`media.rs:2713-2736`：括号型只试探一组，消费完游标后 `prev='》'`，后面的 `《B》` 前面没有 `#`，压根不进标签分支）。`#《甲》#《乙》` 各带 `#` 时正常（单测 :3072 覆盖的正是这种）。用户只举了单数样例，这是**最容易被做错的点**。

### 需求② 搜索框移到 Telegram 标题层

**现状**：搜索框**已经在频道标题栏**（`TgPanel.tsx:1472-1478`），但行为是**跨全部监控频道**（`globalSearch` → `searchTgMonitorMessages`，`api/tg.ts:177`）。位置暗示"频道内"、行为是"全局" —— 用户感受到的错位正来源于此，**改位置是唯一有效解法**。

**推荐 A**：移到 ContextBar 同层居中（与"Telegram"标题同层，"位置 = 全局作用域"）。三条硬约束必须同时满足：
1. 输入 state 走 zustand 切片 + **独立 memo 子组件** + 300ms 防抖，**禁止**放进 ContextBar/MainLayout 本体 —— `ContextBar.tsx:19-22` 注释明确写着它只吃低频 props 以守 §5 流畅约束，否则每次按键会重渲染 2000+ 行的 TgPanel。
2. 三槽各自可收缩（否则重演 BUG-040 的 min-content 钉死）。
3. 切视图时清空搜索词，需先定死。

**退路 B**：TgPanel 顶部 toolBar 居中（:1046-1073 那行，目前只有"缓存管理"按钮，`justify-end`）。成本约为 A 的 1/3，语义错位同样消除。

**不推荐 C（portal）**：隐式 DOM 锚点 + 首帧时序坑（view 初始为 tg 时锚点尚未插入 DOM）。

**注意**：tg 视图的 ContextBar 右槽**不是空的**（是 `ContextBarStatus` 连接态/速度/进行中），所以只能居中，不能靠右。

### 需求③ 折叠控件 + 立即同步

**③-a 折叠控件（P0 真 BUG）**
- 现状 `TgPanel.tsx:1195-1203`：箭头是 10px 的文本字符 `{monitorOpen ? '▾' : '▸'}`（`text-[10px]`），确实"小到看不到"。
- **比尺寸更像 BUG 的是**：箭头与标题**共用同一个 `<button>`**（:1196 `onClick={() => setMonitorOpen(v => !v)}`），点标题就折叠 —— 用户没提这条，是评估中发现的。
- 推荐：SVG chevron 换成独立按钮、热区 ≥24×24（与 `TgPanel.tsx:1742-1743` 既有口径一致）、**与标题解耦**；位置**保持左侧**（用户未给倾向，左侧符合"层级树"惯例且与右侧操作按钮区隔）。

**③-b「立即同步」**
- 后端**确实全自动**：`monitor.rs:21` `spawn()` 后台 tokio 循环，间隔 `config.monitor_interval_secs`（默认 **30 秒**，见 `config.rs:44`，可用 `ORIG_TG_MONITOR_INTERVAL` 覆盖）。
- 按钮只是手动跑同一个 `sync_once`，源码自述"手动触发一轮增量同步（**调试**/即时入库）"（`routes.rs:1537`）。**用户的质疑成立。**
- 推荐：移出监控标题行 → 放进「入库流水线」面板并带说明文案（保留"刚加监控立刻要内容"的路径，不硬删）；后端 `monitor_sync`（`routes.rs:1538`）改 fire-and-forget + `AtomicBool` 单飞；前端不再 await、**不再重载 feed** —— 现在 `doSync` 同步完会 `stickBottomRef=true` 重拉一页，**直接拽走滚动位置**，这正是用户反对的"影响前端展示"。

## 3. 评估中发现、但用户没提的问题（按严重度）

### ① 三个同步触发源并发，后端无任何单飞 —— **最严重，有 FLOOD_WAIT 风险**

`monitor.rs:44-99` 的 `sync_once` 全程**没有** `Mutex`/`tokio::sync` 保护。当前触发源有三个：

| # | 触发源 | 位置 | 频率 |
|---|---|---|---|
| 1 | 后台定时循环 | `monitor.rs:21` `spawn()` | 默认 30s（`config.rs:44`） |
| 2 | **前端每 60s 主动 POST** | `TgPanel.tsx:760-777`（BUG-038 引入），且**进入频道立即跑一轮**（:771 `void run()`） | 60s |
| 3 | 用户手点按钮 | `TgPanel.tsx:1204-1212` | 手动 |

三路可同时跑同一批频道，游标交错推进。upsert 幂等所以不产生脏数据，但后果不是界面卡 —— 而是 **Telegram RPC 预算被叠加消耗 → FLOOD_WAIT 风险**（连在线播放、缩略图取流都会被拖慢）+ SQLite 写放大。

**放大因子**：`sync_once` 单频道不是 1 次 RPC，而是最多扫 **600 条原始消息**（`grammers.rs:64` `MEDIA_RAW_SCAN_CAP`，用于 `while out.len() < want && raw_seen < MEDIA_RAW_SCAN_CAP`，:344）才凑够 100 条媒体。架构师估算 10 频道量级 3–90s、50 频道分钟级（**估算，未实测**，建议用 `/api/tg/logs` 加计时校准）。

> 这条比"按钮语义不清"严重得多，建议单独立号。

### ② 前端 60s 催同步是 BUG-038 的补丁，不能裸摘

`TgPanel.tsx:756-759` 注释写明：消息流本地满页即不回网，"若没有任何主动同步动作，停留在面板里永远看不到新内容（BUG-038）"。它用返回的 `added` 驱动「有 N 条新内容」提示条。

所以**不能直接摘** —— 摘了就退回 BUG-038 的"面板永不更新"。必须先有**只读**的"新增条数"端点（内存快照，符合 §5"被轮询的读端点不许碰 DB"）替代。这也是 BUG-098 已提 SSE 方向的最小子集。**后端未就绪前不要摘前端。**

### ③ 搜索框有两个 input 实例绑同一 state

`TgPanel.tsx:1319-1326`（结果视图内）与 `:1472-1478`（频道标题栏）是**两个** input，都绑 `globalSearchInput`。上移时应收敛成一个。

### ④ 代码异味

`media.rs:2758-2759` 连续两行完全相同的 `let body = body.trim().to_string();`（重复 shadowing）。无害，改动时顺手清掉。

| 项 | 结论 | 原话依据 |

| A-3 搜索框落位 | **方案 A：顶部上下文栏那一行居中** —— 即左槽显示「Telegram」的那行（`nav.tg`，`zh-CN.json:7`）。方案 B 排除 | 「我说的是 TG 的 Telegram 这个文字标题 居中」 |

| 本轮是否改代码 | **不改**，只评估 + 立档 | 「给方案，不改代码」 |

### A-1（阻塞）`#《xxx》` 语法与去重
- ① `#《A》` 与 `#A` 是否同一标签（推荐：是，只差呈现）
- ② 《》内是否允许空格/多词（推荐：允许，整段为名，仅 trim）
- ③ **`#《A》《B》` 是否改为产出两个标签**（推荐：改，中文频道"一次标多部剧"是高频写法，丢了等于功能残缺；代价是改 Rust 解析器 + 补单测）
- ④ 缺右《》→ 维持现状"丢弃并退回裸规则"（推荐，兜底会造成半个标题变标签）
- ⑤ 括号型长度上限 32 → 64（推荐，中文剧名 32 字偏紧），裸标签维持 32

### A-2（阻塞）标签筛选的路径与作用域
- 路径：`?tag=` **挂 `/api/tg/stored`** + 可选 `channelIds`（推荐，零迁移） vs 新增 `media_message_tag` 关联表（精确分页，但要迁移+回填）
  - **⚠️ 落点已修正**：原推荐挂 `/monitor/messages`，但它是**单频道**端点，不满足跨频道。
    `/api/tg/stored`（`routes.rs:1567`）是唯一同时满足「跨频道 + `beforeId` 分页 + 含未缓存行」的现成通路。
  - 判据 = 数据量：数千级用前者；单频道上万条且需精确翻到末页才用后者。**实施前先统计 `media_message` 行数**。
- 作用域：**已定「跨频道 + 频道内都要」**（用户明确要求）。待定：是否支持勾选任意频道子集（要不要加 `channelIds`）、与全局搜索是否互斥

### A-3（阻塞）搜索框落位
- A（ContextBar 同层居中，需接受跨层状态提升） vs B（TgPanel 顶部 toolBar 居中，成本 1/3）
- 切走再切回时关键词**保留**还是**清空**

### B-1 是否复用媒体库 `media_tag`
推荐**不复用**：消息流标签 = caption 的只读派生投影（不落库、不可编辑）；媒体库标签 = 用户可编辑的持久资产。代价是同一内容在两处标签可能不一致，需在文案层面说明。

### B-2「立即同步」去留
弱化到「入库流水线」面板（推荐）还是直接移除。

### B-3 是否同批摘掉前端 60s 轮询
推荐摘，但**必须后端只读"新增条数"端点先就绪**（B-3 不可早于其后端端点）。是否单独立号，还是并入 BUG-098。

### B-4 折叠箭头左右
推荐保持左侧（用户未给倾向）。低风险。

## 7. 「用户说的」vs「团队推断的」

汇报与实施时不要把推断说成用户需求。以下 **10 条均为推断**：

| 推断项 | 出处 |
|---|---|
| `#《A》` 与 `#A` 同一标签 | 现有实现 + "《》是显示标志"的字面暗示 |
| `#《A》《B》` 应产出两个标签 | 用户只举了单数样例 |
| 括号型上限放宽到 64 | 用户未提 |
| 筛选走"粗筛 + Rust 精筛" | 工程路径 |
| 筛选与全局搜索互斥 | "频道内"来自用户，"互斥"是设计建议 |
| 不复用媒体库 `media_tag` | 工程边界判断 |
| 折叠控件保持左侧 | 用户只说"重新考虑左右"，未给倾向 |
| 折叠与点标题解耦 | 实现隐患，用户未提 |
| 「立即同步」弱化到入库流水线面板 | 用户只质疑其存在，未说搬到哪 |
| 新增只读"新增条数"端点 | 用户只主张"应是后台操作" |

**用户明确说的**：标签要高亮 / 要支持频道内筛选 / `#《xxx》` 要识别且《》是特殊化显示标志 / 搜索框移到 Telegram 层居中 / 折叠控件小到看不到 / 左右需重新考虑 / 质疑「立即同步」与自动入库 / 主张入库应是后台操作不影响前端展示。
