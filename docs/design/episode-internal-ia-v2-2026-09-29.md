## 2. 左栏：剧集封面（海报）的替换 / 编辑 —— 本轮核心新增

### 2.1 产品需求：用户要能做什么

| # | 能力 | 说明 |
|---|---|---|
| R-a | **换封面** | 给这部剧指定一张新的封面图，左栏海报立即更新 |
| R-b | **从已有图片里选** | 从**资料库里已有的图片条目**中挑一张（用户已经收过的图，不该被迫重新上传） |
| R-c | **用本地新图** | 从本机选一张图片文件作为封面 |
| R-d | **回到自动封面** | 显式取消自定义封面（`poster = null`），回退到自动推导的封面；**并让用户知道会回退成什么** |
| R-e | **重新生成封面**（与 R-d **不是同一件事**，架构勘察后拆分） | 让系统**重新抽帧**产出一张新封面。`poster = null` **只回退、不重抽**：后端 `media.rs:1467` 是 `explicit.or(cover_poster)`（null 时回退首集 poster），而前端 `SeriesCard.tsx:31` 的门控是 `if (poster || coverFailed) return` —— 只要回退后 poster 非空，就**永远不会再抽帧** |

**不可接受的形态**（防返工）：
- 只有一个「上传」按钮，逼用户为"换封面"重新准备一张图（库里已有图用不上）。
- 设置了封面但界面无任何反馈（N2 的陷阱）。
- **把「回到自动封面」与「重新生成封面」合成一个按钮**：前者只是清空、后者要重抽，行为不同（Q3），合成一个必然让一半用户得到非预期的结果。
- **写入封面导致导出失败**（见 §9 验收口径 AC-1）：这不是"显示不好看"，是把既有能力弄坏。

### 2.2 用户故事

1. 作为**整理这部剧集的人**，我想点一下海报就能换一张封面，并从**我已经收进库里的图片**里挑，而不是重新找图 —— 这样我的库看起来是我整理过的样子。
2. 作为**刚收完一部剧的人**，我想把系统自动抽的那张黑帧/无关帧换掉，因为它是别人第一次看到这部剧时的第一印象。
3. 作为**误操作的人**，我想把封面清除、回到自动封面，并且**在清除前就知道会回退成哪一张** —— 这样我不会清完才发现更难看了。
4. 作为**有图片分集的人**，我设完封面后如果界面没变化，我想知道为什么（N2）—— 而不是以为功能坏了。

### 2.3 期望交互形态

```
左栏海报区
├─ 常态：海报（点击 = 打开大图灯箱，沿用现有行为）
└─ 悬停 / 聚焦时浮现一个「换封面」入口（不是常驻按钮 —— 见下）
        ↓ 点击
   封面编辑弹层（对话框）
   ├─ 预览：当前封面（大图）
   ├─ 三种来源（三选一，同屏并列，不藏进二级菜单）
   │   ├─ 从资料库选图   → 图片网格（复用既有图片选择器形制）
   │   ├─ 用本地图片     → 文件选择
   │   └─ 用自动封面     → 回到默认（等价于"清除"）
   ├─ 保存 / 取消
   └─ 若命中 N2 的优先级冲突 → 就地说明"这部剧含图片分集，将优先显示图片原图"
```

**三条形态规则**：
- **「换封面」不做常驻按钮**：按铁律（BUG-148），它是低频动作，常驻会与"剧集是什么"这类信息位抢权重。悬停/聚焦浮现即可，键盘可达（Tab 到海报即出现）。
- **三来源同屏**：用户是"想换张封面"，不是"想选择一种技术路径" —— 把路径藏进二级菜单是把实现分层暴露给用户。
- **保存前必须能看到结果**：预览用即将生效的那张图；N2 命中时提前说明，禁止"保存了但页面没变"。

### 2.4 勘察结论（已由架构查清，本文据此定稿）

| # | 开放点 | 结论 | 对产品的影响 |
|---|---|---|---|
| **Q1** | `poster` 的值域 | **任意字符串、零校验**，但三个消费者口径不一：① `<img src>` 直传（`CoverImage.tsx:46`）→ 接受 data-URI 与 `mediaItemUrl(id)` 这类**绝对 URL**，不接受库内相对路径；② **导出侧**（`media.rs:2006-2017`）对**非 data-URI** 的值按**库根相对路径**处理（`resolve_item_path` + `fs::copy(...)?`，`?` 直接传播错误）；③ 全仓实际写入值**只有 data-URI 一种**（`MediaCard.tsx:164`、`SeriesCard.tsx:39`，均为抽帧产物） | **⚠️「从库里已有图片选一张」不是零后端改动**：若把 `mediaItemUrl(itemId)`（`http://127.0.0.1:9877/api/...`）写进 `poster`，显示正常但**导出会整批失败**（不是跳过该图，是整批 `?` 中断）。⇒ 要么导出侧补 URL 识别（1 处），要么约定第三种值域（如 `item:<id>`，两端各加解析）。**这使 D1 的 A/C 与"只差一个 UI"差出一档成本**，也是 §9 AC-1 的来源 |
| **Q2** | 「用本地新图」是否已有通路 | **无**。`orig-tg/src/routes.rs` 与 `orig-daemon/src/routes.rs` 全文 grep `multipart|upload` **零命中** | R-c 必须**新增端点** + 落盘 + 字节归属，成本与 R-b 差一个量级（D1 选项 B 的量化依据） |
| **Q3** | 「重新生成」的触发方式 | `poster = null` **只回退、不重抽**：后端 `media.rs:1467` `explicit.or(cover_poster)`；前端 `SeriesCard.tsx:31` `if (poster || coverFailed) return` ⇒ 只要回退后有非空 poster 就永不重抽。真重抽需额外机制（清 `markPosterFailed` 记忆 + 显式跳过回退） | 已把 R-d（回到自动封面）与 R-e（重新生成）**拆成两个动作**（§2.1），并写入 AC-2 |
| **Q4** | N2 的优先级能否改 | **能，且必须改**：产品裁定（`media-library-layout-prd-2026-09-28.md:78`/`:118`）要求**显式封面优先、回退只在未设封面时发生**；实现照抄了设计文档里与正文矛盾的代码块。**这是修实现对齐裁定，不是改裁定** | V9 直接写「让显式封面优先」（交换 `episodePresentation.ts:117-128` 的 ①② 顺序），**不需要"提前告知"退路** |

## 3. 左栏「功能比较混乱」的具体化：8 个元素逐一评判

| # | 截图元素 | 性质 | 评判 | 处置 |
|---|---|---|---|---|
| 1 | **封面图** | 视觉标识（主） | **主任务缺口**：唯一"用户想主动改"的视觉元素没有编辑入口 | **补「换封面」**（P0 V1） |
| 2 | 标题 | 内容标识（主） | 合理，且上轮用户已裁定"一行显示、超出省略"（现实现 `SeriesDetail.tsx:328-334` 已符合） | **不改**（防工程师顺手改成换行） |
| 3 | `剧集 1 集` | 元信息 | 合理。与 `seasonCount` 同排（`:335-340`） | 不改 |
| 4 | 标签行 | 内容分类（主） | 位置合理（标签是内容属性，不是管理动作） | 保留；**溢出治理**见 P1 V11 |
| 5 | 内容行 `📺😀😀😀😀 《超能旅行团》 EP1-10` | 疑似**又一个标签**（名称含 emoji） | 活代码里标签只有**一个**容器（`:342-348` `series-hero-tags`），故第 4、5 行应同属标签集合；若确为标签，则"标签长到占用一整行"是需要治理的溢出问题 | **待确认**（仅凭文字清单无法判定该行是标签还是别的信息位）；若是标签 → 并入 V11 |
| 6 | **剧情简介** | 内容（主） | **活代码里不存在这个展示位**（N3） | **补展示位**（P1 V7） |
| 7 | 按钮行一：`编辑` `标签` | 低频管理动作 | **位置过高**：两个管理动作被放在"读剧集信息"的动线上，且与下方危险动作视觉同级 | **降级**：收进"管理"区，与危险动作分级呈现（P0 V5） |
| 8 | 按钮行二：`合并到…` `导出预览` `删除` | 危险级别**不同** | **危险级别被同等呈现**：`删除`＝破坏性且不可逆；`合并到…`＝结构性且跨剧集搬分集（不可逆、影响面大于删除单条）；`导出预览`＝**只读安全**。三者同为描边按钮、同排、同尺寸（活代码 `SeriesDetail.tsx:376-407`） | **分级**：安全动作（导出）与破坏性动作（合并/删除）分区；破坏性动作用破坏性视觉 + 二次确认（P0 V5） |

### 3.1 一句话结论（左栏功能混乱的实质）

> **左栏把「读剧集是什么」（封面/标题/元信息/标签/简介）与「管理这部剧」（编辑/标签/合并/导出/删除）混在同一条纵向动线里，动作内部又不区分主次与危险级别；而这条动线上唯一真正高频的视觉动作 —— 换封面 —— 根本没有入口。用户看到一排按钮，却找不到想做的第一件事。**

**判据（可验证）**：左栏首屏应满足"① 一眼读到这部剧是什么；② 一眼找到换封面；③ 破坏性动作不与只读动作同排"。

## 4. 右栏：主次层级重排（按截图 2 复核）

### 4.1 现状违反的是哪三条产品原则

| 违反 | 现状证据 | 为什么是违反 |
|---|---|---|
| **BUG-148：绝不做常驻 UI 构件** | `SeriesDetail.tsx:612-619` 的 `<EpisodeEditPanel>` **无条件渲染**（无 `editing` 开关）⇒ 一进剧集内页就常驻一个完整编辑表单 | 编辑表单是**实现态**（一个可能被进入、也可能不进入的状态），不是"这一集是什么"的信息位。把它常驻 = 把"我随时可以改"渲染成"你正在改" |
| **主次由使用频次决定** | 恒显表单占据右栏最大视觉体量；而「播放」按钮在 `:678-688`，与挂图/前往条目/重缓存同排同尺寸（`h-7 px-2.5 text-[11px]`），仅靠实心 `variant` 区分 | 播放是高频主任务，编辑是一次性任务。用户原话"主要是播放，编辑是一次性的，主次倒置"（上一轮已裁定），本轮截图确认**仍未修复** |
| **无选择即无控件** | 来源区 `:543` 外层 `<div>` 无条件渲染；`:544`（区块标题）与 `:553-555`（行标签）**复用同一个 i18n 键** `media.episode.sourcesTitle` ⇒ 界面出现两个「来源」 | 只有一个来源时，用户没有任何选择可做，却看到一整块"来源"面板 |

**「原因不明」的成因（用户原话"原因不明"）**：用户进页面后看到编辑表单，但**没有任何动作导致它出现** —— 他没有点"编辑"，也没有进入任何编辑态。界面无法解释自己为什么是现在这样。这正是常驻化的典型症状：**状态没有成因**。

### 4.2 期望形态（右栏）

```
右栏 · 单集焦点
├─ 主区（首屏恒显 · 顺序固定）
│   ├─ 本集标题 + 集号 + 时长
│   ├─ 大封面 / 图组
│   └─ ▶ 播放本集        ← 唯一实心主按钮，独占一行，位置随集不变
├─ 次区（**默认不渲染**，按需展开）
│   ├─ 本集介绍（只读）
│   ├─ ▸ 编辑本集 → 点开后**才渲染**表单（标题 / 介绍 / 槽位 + 计数 + 上限）
│   ├─ ▸ 本集动作：挂图 · 上移 / 下移 · 从剧集中移除
│   └─ 来源（**仅 sources ≥ 1 时渲染**，见 §5）
└─ 溢出区（⋯ / 仅在受阻时出现）
    └─ 设为默认播放 · 重新缓存 · 前往条目
```

**硬性要求**：
- **未进入编辑态时，编辑表单在 DOM 里不存在**（不是 `hidden`、不是 `opacity-0`）—— 否则占位与 Tab 序仍被污染，"常驻"只是换了种藏法。
- 播放按钮的位置**不随内容长度/挂图数量漂移**（固定位是"主操作"的唯一可验证判据）。

### 4.3 「编辑本集」按钮点击后应该发生什么

| 现状 | 期望 |
|---|---|

## 7. 待拍板（3 条，按「挡住用户使用」排序）

### D1. 封面替换的来源范围：只做"从库里已有图片选"，还是同时做"上传本地图片"？

- **问题**: 封面的三种来源（资料库选图 / 本地图片 / 自动封面）里，本轮做哪些？
- **现状与代价**: 用户明确要求"图片替换、编辑功能"（原话 1），这是本轮**唯一被用户点名缺失的能力**。后端 `poster` 写路径已存在（`media.rs:3688-3690`、`routes.rs:3443-3458`），但**值域与是否有上传通路待架构确认**（§2.4 Q1/Q2）。不定 → V1 无法开工，用户继续无法换封面。
- **设计锚点**: `docs/design/episode-internal-ia.md` §2（左栏信息位与动作分级）、`docs/design/media-library-layout-design-2026-09-28.md` §3.1.1（海报宽高比与封面回退链的既有裁定）
- **请求**: 选 A、B 还是 C？

**A. 只做「从资料库已有图片选」+「回到自动封面」**
- 涉及: `tauri-shell/src/components/media/SeriesDetail.tsx`（左栏海报区加入口）、`tauri-shell/src/components/media/`（封面编辑弹层，将新建）、`tauri-shell/src/api/media.ts:400-412`（`patchSeries` 已声明 `poster`）、**`download-engine/crates/orig-tg/src/media.rs:2006-2017`（导出侧需补 URL 识别，见 Q1）**
- 量化: 1 个新组件 + 1 处入口 + **1 处导出侧兼容**（Q1 已查清：直接写 `mediaItemUrl(id)` 会让导出整批失败，**不是零后端改动**）
- 回归风险: 中 — 触碰导出侧；若不改导出侧，则**导出能力被弄坏**（AC-1）
- 后果: 用户能给这部剧换封面，且用的是**已收进库的图**（不产生新文件、不涉及上传与存储策略）。可逆（回到自动封面即回退）

**B. 只做「上传本地图片」**
- 涉及: 需新增媒体上传端点（将新建，路径待架构定）；`tauri-shell/src/components/media/`（文件选择 + 封面弹层）
- 量化: 新增 1 个端点 + 1 个新组件；涉及存储落盘策略（与 `docs/design/blob-store-design.md` 的字节归属约定需对齐）
- 回归风险: **中高** — 引入新的字节入口，须遵守既有投递与字节归属铁律
- 后果: 用户能用任意本机图片；但**库里已有的图仍用不上**（用户被迫重新准备文件），且成本显著高于 A

**C. 两者都做（推荐，分两步落地）**
- 涉及: A 与 B 的并集
- 量化: 1–2 个新组件 + 1 处导出侧兼容 + 1 个新上传端点；工作量约为 A 的 2–2.5 倍（Q1 已把 A 的成本上调一档，Q2 确认 B 需新增端点）
- 回归风险: 中高 — 覆盖导出侧与存储/投递两条既有能力
- 后果: 覆盖全部真实场景（先选库内图，找不到再上传）。**建议按 A 先落地、B 随后追加**，避免整个需求被上传端点阻塞

**D. 不做（维持现状）**
- 涉及: 无
- 量化: 0
- 回归风险: 无新增（但既有问题保留）
- 后果: 用户明确点名的缺失继续存在；封面只能靠自动抽帧，黑帧/无关帧无法替换 —— 这是用户最先看到的那张图。只要用户还在意封面，就会被反复提出

## 9. 验收口径（架构勘察提出的两条"实现阶段会各理解一半"的风险，写死为判据）

| ID | 判据 | 为什么必须写死 | 反向证伪（失败长什么样） |
|---|---|---|---|
| **AC-1** | **写入封面后，导出能力必须完好**：设过自定义封面的剧集，走一次 `POST /api/media/export` 必须成功，且导出包内该剧集封面文件存在 | Q1：`poster` 值域零校验，而导出侧（`media.rs:2006-2017`）对**非 data-URI** 的值按库根相对路径 `resolve_item_path` + `fs::copy(...)?` 处理。若写入 `mediaItemUrl(itemId)`（`http://127.0.0.1:9877/api/...`），**整批导出失败**（`?` 中断，不是跳过该图） | 设完封面后导出报错；或导出"成功"但封面文件缺失/为 0 字节 |
| **AC-2** | **「回到自动封面」与「重新生成封面」必须是两个可分别验证的结果**：前者设 `poster = null` 并回退到自动推导封面（不重抽）；后者能产出**一张新的抽帧封面** | Q3：`media.rs:1467` 是 `explicit.or(cover_poster)`（null 只回退），`SeriesCard.tsx:31` 是 `if (poster || coverFailed) return`（回退后有非空 poster 就永不重抽）。若合成一个按钮，一半用户会得到非预期结果 | 点「重新生成」后封面**没变**（因为只是回退）；或点「回到自动封面」却触发了抽帧、结果又变了 |
| **AC-3** | **未进入编辑态时，编辑表单在 DOM 中不存在**：`[data-testid="episode-edit-panel"]` 数量为 0；点击「编辑本集」后才出现，且焦点在标题输入框 | V2 的"不渲染"与"隐藏"是两回事：`hidden`/`opacity-0` 仍会占位并污染 Tab 序，"常驻"只是换了种藏法 | 用 `hidden` 或 CSS 隐藏 ⇒ DOM 查询仍能命中，判 FAIL |
| **AC-4** | **单来源时来源区不存在**：`sources.length === 0` 时，来源区标题与行在 DOM 中均不存在（不是隐藏） | V4 的判据；「无选择即无控件」 | 区块仍在 DOM 里、只是不可见 |
| **AC-5** | **显式封面优先**：设过 `poster` 的剧集（含含 photo 分集的剧集），左栏海报必须显示**用户设的那张** | V9；有产品裁定背书（`media-library-layout-prd-2026-09-28.md:78`/`:118`） | 设了封面但左栏仍显示 photo 首集原图（现状行为） |
| **AC-6** | **破坏性动作的对象身份必须可区分、且以服务端为准**：① 合并二次确认展示的源剧集身份必须能区分两部**同名**剧集（至少含 分集数 + 封面 + 创建时间；**只有名字不算**）；②【**本轮缓办 / deferred，非本轮交付**】完成后回执里的「被删源」由**服务端按实际使用的 id 解析后返回**（不是客户端自己那份副本拼的），含目标剧集名 + 搬入分集数 + 被删源身份 | V5；2026-09-29 事故实证：108 与 112 **同名**（同一群组/消息经 `tg:group:{chat}:{grp}` 与 `tg:msgs` 两条 key 各建一部）⇒ **只显示名字的确认当场就会放行这次误删**（名字对得上，删的不是用户以为的那部）。故判据从"名字可见"升级为"身份可区分 + 服务端为准" | 确认框只写"确定合并吗"；**或确认框列了源剧集名、但两部同名、用户无从区分**（本次事故正是如此）；或回执的源名来自客户端副本，于是只能说"我删了你选的那部"、说不出"服务端删的是另一部" |

> **AC-6 的实证与成本（2026-09-29 事故后修订；原"已知局限"已被实证）**：**108 与 112 同名** —— 108 是相册 `-1004493170102/8520`（`cache_task` id=83，`group_id 14324684376715077`，`total=1`）经 `tg:group:{chat}:{grp}`（`routes.rs:1656`）自动建的剧集；112 是**同一条消息**经 `tg:msgs` 回落 key 另建的剧集，两者标题规范化后一致。⇒ 这**实测证伪了"只列源剧集名即可防护"**（是已发生的案例，不是假想）。同时**内容未丢失**：108 的那一集与 112 的是同一 item，合并时被**跳过**（"并入 0 集，跳过 1 集"），消失的只是一条重复的剧集行。⇒ AC-6 ① 仍为纯前端；**AC-6 ② 需后端新增**：现有合并 HTTP 只回 `added` / `skippedCount` / `skipped`（`routes.rs:3698-3702`），`sources_attached`（`media.rs:961`，**既有遗留字段**，不出 HTTP）也不是它。故"回执的源由服务端按实际 id 解析"是**新增的后端需求**（见 §10）。**本轮裁定（team-lead, 2026-09-29）：② 缓办（deferred，非本轮交付）** —— ② 是**新 engine 能力**（新增端点字段 + 自带测试与验收，等于一个特性）；当前正处于同一代码路径的 data-loss 缺陷（BUG-189）修复窗口，此时扩大 engine 面会放大正在修复区域的爆炸半径。**对"删错剧集"的真正防护是 BUG-189 修复本身**，回执属 defense-in-depth，可后补。⇒ ② 记为**已登记但非本轮交付**；未来会话**不得读作"已交付"或"遗漏"**；不为其新开 BUG 档（如需记录由 team-lead 另定）。
