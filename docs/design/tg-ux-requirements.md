## 1. 需求一：内容 `#标签` 高亮 + 频道内筛选（BUG-099）

### 1.1 用户原话 → 需求陈述

> 用户原话：「内容#标签需要高亮，且支持频道内筛选。#《xxx》这样的格式也要能正确识别其中的xxx标签。《》是特殊化显示标志。」

拆解成三条可执行的陈述：

- **R1-a（呈现）**：消息流中每条 caption 里出现的 `#标签`，其标签部分必须**可辨识地高亮渲染**（不是纯文本），且高亮块是**可点击**的。
- **R1-b（交互）**：点击某个标签，能**在当前频道内**把消息流筛成"只含该标签的消息"，并有可见的、可退出的筛选态。
- **R1-c（语法）**：`#《xxx》` 必须被识别为一个标签，标签名取《》内的 `xxx`；《》是**显示层面的特殊化标志**（暗示：它改变呈现形式，但未必改变标签的身份）。

### 1.2 澄清：`#《xxx》` 的精确规则定义

**先说结论：后端已经实现了一套规则（取证 #11），本需求的关键不是"从零定义语法"，而是"前端必须遵守同一套规则 + 把含糊处拍板"。**

现有 `extract_hash_tags` 已确立的规则（**这是现状，不是建议**）：

| 规则 | 现状行为 | 证据 |
|---|---|---|
| 词首判定 | `#` 必须是词首（行首，或前一字符**非**字母数字/`_`；闭合括号不阻断 ⇒ `#《A》#B` 两个都成标签） | `media.rs:2698-2706` |
| 括号型标签 | `#` 后紧跟 《（ ( [ 之一，且**必须成对闭合、不跨行**，标签体 = 括号内**全部**文本（允许空格、标点、多词） | `:2711-2736` |
| 未闭合兜底 | 未闭合 → **退回裸标签规则**（`《` 不是合法标签字符）→ 该 `#` 不产出标签，且不吞掉后续正文 | `:3079-3085` |
| 空括号 | `#《》` → 无标签 | `:3087` |
| 裸标签 | Unicode 字母数字 + `_`，词内允许 `-._·`，**结尾**的 `-._·` 剥离（`#tag.` → `tag`） | `:2738-2756`、`:2673-2674` |
| 去重 | 大小写不敏感去重，保留首次出现的写法（`#Action` 与 `#action` 同一标签） | `:2680`、`:2761` |
| 长度上限 | **>32 字符直接丢弃**（括号型同样受限） | `:2683`、`:2760` |
| 实测样例 | `"😀😀 #《异世界男妓-瓦尔哈拉神枪馆》 EP-2\n关键词：#西瓜短剧 #AI短剧 #熟女档案"` → `["异世界男妓-瓦尔哈拉神枪馆","西瓜短剧","AI短剧","熟女档案"]` | `:3060-3069` |

**仍然含糊、必须拍板的 5 点（详见第 5 节 A-1）：**

1. `#《A》` 与 `#A` 算**同一个**标签还是两个？
   → 按现有实现，两者的 `body` 都是 `A`，**是同一个标签**；用户说"《》是特殊化显示标志"也支持"同名异写"。但这需要用户确认。
2. 《》内允许空格 / 多个词吗？（现状：允许，整段作为标签名，仅 `trim`）
3. **连续写法 `#《A》《B》`（一个 `#` 带多对书名号）怎么切？**
   → 现状只产出 `["A"]`，`B` 会被丢；必须写成 `#《A》#《B》` 才得 `["A","B"]`（单测 `:3071-3074` 只覆盖了带第二个 `#` 的写法）。**这是最大的歧义点**：中文频道实际写法里 `#《A》《B》` 是否常见，直接决定要不要改解析器。
4. 缺右《》时：现状是"丢弃"（见上表）。接受，还是要兜底？
5. 32 字符上限对中文长剧名的适用性：`#《异世界男妓-瓦尔哈拉神枪馆》` 是 14 字，安全；但更长的剧名会被**静默丢弃**。括号型是否放宽（如 64）？

### 1.3 用户故事

- As a 浏览监控频道内容的用户，I want caption 里的 `#标签` 被高亮且与正文可区分，so that 我扫一眼就知道这条内容属于哪个题材/剧集，不用逐字读正文。
- As a 只想看某一类内容的用户，I want 点击一个标签就能把当前频道筛成"只含该标签"，so that 我不用靠搜索框猜关键词（关键词搜索会把正文里的同名词也捞出来）。
- As a 追某部剧的用户，I want `#《剧名》` 这种带书名号的写法被正确识别成剧名标签，so that 频道主用这种写法标注的内容不会在我的面板里"沉没"。
- As a 点击标签后继续浏览的用户，I want 筛选态可见、可一键清除、且往上翻更早内容时筛选不失效，so that 我不会"点进去出不来"或翻着翻着筛选悄悄没了。

### 1.4 现状差距（三条，按从"已有"到"全无"排列）

| 能力 | 现状 | 差距性质 |
|---|---|---|
| 解析 `#标签`（含 `#《》`） | **后端已实现**（取证 #11） | 已存在，但只在**入库时**用于媒体库标签收集 |
| 消息流里高亮 | **完全没有**（取证 #10） | 纯呈现层缺失 |
| 按标签筛选 | **完全没有** | 后端有近似的单频道子串搜索（取证 #14），但 UI 未接、且是子串不是标签匹配 |
| 未入库消息的标签 | **没有标签**（取证 #12） | 决定了"复用媒体库 tag 体系"是否可行 —— 见第 5 节 B-1 |

### 1.5 方案轮廓（只到"动哪里"，不含代码）

- **解析层（关键决策）**：caption 文本已在前端手里，前端解析零网络成本；但**两个实现 = 两套真源**在本项目已有惨痛前例（BUG-069 分集标题 vs 条目标题漂移、BUG-087 连接态三处各写各的）。因此无论选哪条路，都必须保证**规则单一真源**（见第 5 节 A-2 选项）。
- **呈现层**：把 `{m.caption}` 换成"分段渲染"（普通文本段 + 标签段）。标签段需带 `data-tag` 便于验收，并保留原文（`#` 与《》是否显示取决于 A-1 的拍板）。渲染组件必须 `memo` 化（AGENTS.md §5），且不能被 5s 缓存任务轮询带着整列表重建。
- **筛选层**：见第 5 节 A-2 的三条实现路径。

### 1.6 验收标准（可观测 / 可测）

| # | 验收项 | 判据 |
|---|---|---|
| AC1 | 高亮存在且原文不丢 | 频道 X 中 caption 含 `#短剧` 的消息，`短剧` 被渲染为带 `data-tag="短剧"` 的元素；该条 caption 的 `textContent` 与原始 caption **逐字相等**（不删字符、不改顺序） |
| AC2 | `#《》` 正确识别 | caption 含 `#《异世界》` 的消息，`《异世界》` 整体是一个元素且其 `data-tag` 值为 `异世界`；DOM 中不出现"只高亮了半个书名号"的残块 |
| AC3 | **前后端规则一致（最重要的一条）** | 新建前端解析器单测/verify 脚本，用与 `media.rs::extract_hash_tags` **同一组黄金用例**（≥12 条，必含 `#《甲》#《乙》`、`#《没闭合`、`#《》`、`#（全角）`、`http://x/a#b`、`C#`、`#tag.`、`33 字超长`）逐条对拍，输出完全一致 |
| AC4 | 频道内筛选生效 | 在频道 X 点标签 `异世界` → 消息流只剩解析后含 `异世界` 的消息；条数与后端 `?tag=`（或等价路径）返回值一致 |
| AC5 | 筛选态可见可退 | 筛选激活时有常驻的可视标记与「清除」入口；点清除后回到全量列表，且滚动位置回到最新一条 |
| AC6 | 筛选与翻页不打架 | 筛选态下向上滚动加载更早内容，新加载的一页**仍在筛选集合内**（不会混入未匹配项、也不会把筛选悄悄清空） |
| AC7 | 覆盖范围 | **未缓存（未入库）**的消息同样高亮、同样可被筛中（这是"只读派生"路线的核心可测收益） |
| AC8 | 不违反流畅约束 | 高亮/筛选开启后，5s 缓存任务轮询期间消息流不被整体重建：断言 `MessageBubble` 已 `memo` 且其 props 不含每次渲染新建的对象/回调（回调走 `useEvent`） |

## 2. 需求二：搜索框移到 Telegram 标题层并居中（BUG-100）

### 2.1 用户原话 → 需求陈述

> 用户原话：「监控搜索，我感觉这个搜索的 Bar 应该放到顶部 Telegram 标题这层，放中间，因为放在频道内让人感觉是频道内搜索。」

- **R2-a（位置）**：搜索框从"频道标题栏"移到"顶部 Telegram 标题那一层"（= `ContextBar`，取证 #1/#2）。
- **R2-b（对齐）**：在该层**水平居中**。
- **R2-c（动机，我认为这才是真需求）**：消除**"位置暗示频道内 / 行为却是跨频道"**的语义错位（取证 #3/#4）—— 用户已经明确说出这个错位了。

> 注意：用户说"放在频道内"指的是**观感**，不是代码位置 —— 它在代码里确实已经在频道标题栏（取证 #3）。所以本需求**不是**"把搜索从频道内部挪出来"（它本来就在频道标题行），而是"把它上移一层，让它读作全局作用域"。

### 2.2 用户故事

- As a 想找某条内容的用户，I want 搜索框出现在"Telegram"这一全局层，so that 我一眼就知道它搜的是所有监控频道，而不是当前这个频道。
- As a 被误导过的用户，I want 搜索框的位置与它的实际作用域一致，so that 我不会"在当前频道搜不到 → 以为没有 → 其实它在别的频道"。
- As a 在窄窗口下使用的用户，I want 搜索框居中后不与左右元素打架，so that 不出现标题被挤没、状态被裁切（BUG-040 类回归）。

### 2.3 三条落位路径（见第 5 节 A-3 拍板）

| 方案 | 位置 | 代价 | 语义纠正力 |
|---|---|---|---|
| **A. ContextBar 中间槽** | `MainLayout` 的 `<header>`（h-12）内，标题与状态区之间 | `ContextBar` 是跨视图共享组件且靠 `memo` + 低频 props 守流畅约束；需新增"视图专属中间槽"扩展点，且 TG 搜索状态要跨层提升（切视图是否保留需定义） | **最强**（与"Telegram"同层 = 全局作用域） |
| **B. TgPanel 顶部 toolBar 居中** | `TgPanel.tsx:1045-1074` 那一行，改 `justify-end` → 三槽 | 改动最小、状态不外溢；但仍在 TgPanel 内，视觉上是"Telegram 层的下一行" | 中 |
| **C. 保持现状 + 改文案/提示** | 频道标题栏不动 | 零布局改动 | 弱（用户已经说了位置本身就是误导源） |

**我的推荐是 A**，理由：用户字面要求就是"Telegram 标题这层"，且只有这一层能真正让"位置 = 作用域"；居中在该层是可行的（左槽"Telegram"很短，右槽状态区可 `shrink-0`）。
但 A 有三个必须同时解决的点，否则会踩 AGENTS.md §5 或留下残件：
1. 输入框是**高频**状态（每次按键），不能直接塞进 `ContextBar` 本体（会让整个 header 重渲染，连带 `ContextBarStatus`）。做法：中间槽渲染一个**自带 state 的独立 `memo` 子组件**，ContextBar 只透传一个稳定的 `centerSlot` 节点。
2. 窄窗口下三槽必须能各自收缩（标题 `truncate`、搜索框 `min-w-0` 可缩、状态区 `shrink-0`），重演 BUG-040 的 min-content 钉死。
3. **必须顺带收敛实例**：现状同一个搜索框有两份 DOM（取证 #3b），只搬不删会变成三份。正确做法是**删掉两个旧实例、只留一个常驻输入框**，让它始终在同一位置（不再随有无关键词而"跳"到另一个 header）。

**边界态（方案 A 特有，需在实现时定义行为）**：TG 面板的可用性门控全在 `TgPanel` 内部（取证 #16），`MainLayout` 侧不可见。因此会出现"顶部搜索框在、面板却显示配置卡/离线卡"的组合。**建议在 TG 不可用（`needConfig` / 未绑定 / `unreachable` / 调试离线）时隐藏顶部搜索框**，与面板状态保持一致 —— 这条需一并拍板（并入 A-3）。

## 3. 需求三：折叠控件重设计 + 「立即同步」去留（BUG-101）

### 3.1 用户原话 → 需求陈述

> 用户原话：「监控中导航栏的展开/缩起按钮现在小到看不到，需要重新设计，放右边还是左边也需要重新考虑。还有立即同步这个按钮功能是什么？监控入库不是自动的吗？而且这个入库动作应该是后台 TG 操作，不影响前端展示。」

拆成四条：

- **R3-a（真 BUG）**：监控列表标题行的展开/收起控件**视觉上不可辨识**（10px 文本 `▾`/`▸`），需重新设计。
- **R3-b（位置）**：该控件放左还是放右，需要重新决定。
- **R3-c（语义质疑）**：「立即同步」的作用不明；用户已自行举证"入库本来是自动的"（**取证 #8 证明确实是自动的**），按钮语义含混。
- **R3-d（架构主张）**：入库应该是**后台 TG 操作**，不应由前端驱动、不应影响前端展示。

### 3.2 关键取证结论（直接回答用户的两个疑问）

- **「立即同步」功能是什么？** = 手动触发一次 `monitor::sync_once`，与后台循环跑的是**同一个函数**。源码自述"调试/即时入库"（取证 #7/#8）。**用户的质疑成立**：这是调试期遗留入口。
- **但比用户知道的更严重（额外取证 #9 / #9b / #9c）**：
  - 前端还在**每 60s 主动 POST 一次 `/api/tg/monitor/sync`**（BUG-038 引入），用来驱动「有 N 条新内容」提示条。也就是说"入库是后台自动的"这句话**在架构上目前并不成立** —— 前端也在催。这与用户的 R3-d 主张直接冲突，也与 AGENTS.md §5「轮询三律」「被轮询的读端点不许碰 DB」的精神相悖（被轮询的是一个**写**端点）。
  - **实际是三源且后端无互斥**：后台循环（默认 30s）+ 前端 60s + 用户手动点击，三路都调同一个 `sync_once`，而 `AppState` 里**没有任何"同步进行中"标志 / 互斥 / 排队**，三路可同时飞行 → Telegram RPC 叠加 → **FLOOD_WAIT**。一旦限流，在线播放与缩略图取流会一起被拖慢 —— 这才是用户所说"影响前端展示"的**真实机制**（不只是"卡顿"）。
  - **一轮同步并不便宜**：`client.messages(ch, 100, None)` 会循环翻页直到凑够 100 条**媒体**消息，最多扫 600 条原始消息，再加 ≤100 次串行 upsert（取证 #9c）。所以手动按钮点下去可能是**长时间挂起**，不是"一瞬间"。

### 3.3 用户故事

- As a 使用监控列表的用户，I want 展开/收起控件一眼可见、一次点中，so that 我不用眯着眼找那个 10px 的小箭头。
- As a 点击列表标题的用户，I want 点标题文字只做"选中/聚焦"而不是把列表折叠掉，so that 我不会因为想看标题而误关列表（**这是当前实现的既有行为**，见取证 #6）。
- As a 添加新监控后的用户，I want 知道"内容什么时候来"，so that 我不用盯着空白列表猜是不是坏了。
- As a 关心性能的用户，I want 入库在后台跑、前端只负责展示，so that 面板不会因为同步而卡顿或打扰我的浏览。

### 3.4 我的处置建议（待拍板）

**R3-a / R3-b：**
- 控件从文本字符换成 **SVG chevron**（≥12×12px 渲染尺寸），点击热区 ≥24×24px（参照 BUG-033 把入口按钮 27×23 → 40×32 的既有口径），带 `aria-expanded` / `aria-controls` / `data-testid`。
- **位置：推荐保持左侧**。理由：右侧是操作区（当前是「立即同步」），折叠属于层级/导航控件，与"纵向列表标题左箭头"的通行心智一致；且左箭头 + 标题的组合已经建立，换到右边反而要重新适应。
- **解耦：推荐拆开** —— 标题文字不再触发折叠，只有箭头按钮触发。当前"整行都是折叠热区"（取证 #6）是可用性隐患。

**R3-c：**
- 推荐**弱化而非硬删**：从"监控列表标题行"移到「入库流水线」面板内（那里本来就是入库的可观测面），文案与 hint 说明"后台已自动同步，这里只是立即拉一次"。
- 理由：完全删掉会丢掉一个真实场景 —— 刚添加监控时首轮游标为 0，用户点一下能立刻拿到内容，否则要等后台下一轮（默认 30s）。
- **必须改成 fire-and-forget**：一轮同步可能是多频道 × 多次 RTT × 多次写（取证 #9c），不是"一瞬间"。若保留按钮，点击后应**立即返回**（入队/后台跑），进度在「入库流水线」面板里呈现 —— 与 AGENTS.md §5「单飞呈现」「执行侧单飞」的既有范式对齐（同一时刻至多一个同步在跑，其余排队或直接拒绝并如实回报）。

**R3-d（这是本条里最有价值也最需要拍板的一项）：**
- 若要真正落实"入库是后台 TG 操作"，就要把前端 60s 的 `syncTgMonitor()` 摘掉。但**不能直接摘** —— 它是 BUG-038 用来解决"面板看不到新内容"的手段，摘掉必须有替代：
  - **推断的可行路径**：新增一个**只读**端点返回"各监控频道自上次以来的新增条数"（走内存快照，符合 §5），前端只轮询这个只读计数（≥5s 节拍），把「有 N 条新内容」提示条从"同步的返回值"改成"只读计数的返回值"。
  - 这与 BUG-098 已提出的"SSE 事件 + 轮询 ≤5s 兜底"方向一致，可作其最小子集。
  - **风险**：若后端不提供只读计数，摘掉前端同步 = 回到 BUG-038 的"面板永不更新"。所以这是**后端 + 前端联改**，不能只改前端。
- **「后端加单飞」应与「摘前端 60s」绑成同一条**（architect 建议，采纳）：只摘前端不加单飞，剩下的后台 + 手动仍可能并发；只加单飞不摘前端，写端点仍在被轮询。两者合成一条才真正消除 FLOOD_WAIT 风险，也才配得上用户"不影响前端展示"的主张。

## 5. 待拍板问题清单

> 按 AGENTS.md §8 的口径写（因果 / 处置 / 请求）。

### A-1（阻塞）`#《xxx》` 的精确语法与去重规则

- **因果**：现状后端 `extract_hash_tags` 已实现括号型标签，但 `#《A》《B》`（一个 `#` 带多对书名号）**只产出 `["A"]`，`B` 被丢**（`media.rs:3071-3074` 只覆盖了带第二个 `#` 的写法）；`#《A》` 与 `#A` 在当前实现下是**同一标签**、32 字符上限会静默丢弃长剧名。不决定 → 前端解析器无法定型，R1-a/R1-b 全部无法开工；且拍板结果与现状不同时，需要**同时改 Rust 解析器及其 30+ 条单测**。
- **处置**：五个小项一次性定死：① `#《A》` 与 `#A` 同一标签（只差呈现）；② 《》内允许空格与多词（整段为名，仅 `trim`）；③ `#《A》《B》` 的切法（**推荐改成"一个 `#` 后可跟多对书名号，产出 A、B 两个标签"** —— 中文频道"一次标多部剧"是高频写法，丢了等于功能残缺；代价是改 Rust 解析器 + 补单测）；④ 缺右《》→ 维持现状"丢弃并退回裸规则"（推荐，兜底会造成半个标题变标签）；⑤ 括号型的长度上限放宽到 64（推荐，中文剧名 32 字偏紧），裸标签维持 32。
- **请求**：请确认 ③ 是否按推荐改为"一个 `#` 跟多对书名号"，以及 ①⑤ 是否照推荐定案。

### A-2（阻塞）标签筛选的实现路径与作用域

- **因果**：现状"按标签筛选"完全不存在；后端只有**近似的**单频道 caption 子串搜索 `?q=`（取证 #14，前端 API 已支持但 UI 未接）。子串匹配会误命中（点 `#A` 会捞出 `#AB`，正文里出现 `A` 也会命中）—— 标签筛选一旦不准，功能立刻失去可信度。不决定 → R1-b 的工作量在"半天"与"一周"之间摆动。
- **处置**：三条路径，影响面差别很大：
  1. **(a) 纯前端过滤** —— 只筛当前已加载页，零后端改动。**缺陷**：向上翻页时"加载更多"仍在未筛选集合里取，筛选态与分页语义打架（AC6 必挂）。不推荐。
  2. **(b) 复用 `?q=` 并在后端加精筛** —— 新增 `?tag=<name>` 参数：`caption LIKE '%name%'` 粗筛取 `limit*K` 候选 → Rust 侧 `extract_hash_tags(caption)` 精筛 → 截断到 limit。**精确、零迁移、零回填**；代价是分页近似（`hasMore` 保守）。**推荐**。
  3. **(c) 新增 `media_message_tag` 关联表**（upsert 时用 `extract_hash_tags` 写入）+ 全量回填 → 可 SQL 精确分页、可跨频道。**代价**：schema 迁移 + 存量回填 + 必须与媒体库 `media_tag` 体系划清边界（见 B-1）。
- **作用域**（与路径独立，也需拍）：**推荐"仅当前频道"**（用户原话就是"频道内筛选"）；筛选态与全局搜索框**互斥**（激活筛选时清空搜索词，反之亦然），理由是两者都是"第二列内容视图的过滤条件"，叠加会让空态无法解释。
- **请求**：选 (b) 还是 (c)？作用域是否确认为"仅当前频道 + 与全局搜索互斥"？

### A-3（阻塞）搜索框究竟放哪一层

- **因果**：现状框在频道标题栏而行为跨频道（取证 #3/#4），用户已明确指出这个错位；且**同一个框有两份 DOM 实例**（取证 #3b），只搬不删会变成三份。不决定 → 需求二无法开工。
- **处置**：三条路径见 §2.3。**推荐 A（ContextBar 中间槽）**，因为只有与"Telegram"同层才能让"位置 = 全局作用域"；但必须同时做三件事：① 中间槽做成自带 state 的独立 `memo` 子组件，避免输入把整个 header 拖进重渲染（AGENTS.md §5）；② 三槽各自可收缩，避免 BUG-040 的 min-content 钉死；③ **删掉两个旧实例、只留一个常驻输入框**（验收 AC3b：`input[type=search]` 恒为 1）。若认为跨层状态提升成本过高，**退路是 B（TgPanel 顶部 toolBar 居中）**，改动最小且已不在频道标题行。
- **附带的边界态**（方案 A 特有，需一并定）：TG 面板的可用性门控在 `TgPanel` 内部、`MainLayout` 不可见（取证 #16），会出现"顶部能搜、面板显示配置卡/离线卡"。**推荐 TG 不可用时隐藏顶部搜索框**。
- **请求**：选 A（ContextBar 中间，需接受跨层状态提升 + 边界态约定）还是 B（TgPanel toolBar 居中）？切走再切回时关键词**保留**还是**清空**？

### B-1（可延后）标签是"自动从 caption 解析"还是"可人工维护"，是否复用媒体库 `media_tag`

- **因果**：媒体库已有一套完整标签体系（`media_tag`/`media_item_tag`/`media_series_tag` + `TagManagerDialog`，取证 #12/#13），但它是 **item/series 级、入库时收集、用户可手工编辑**的；TG 消息流里的 caption 标签是**消息级**，且**未入库的消息一条都没有**（取证 #12）。复用 → 只有已缓存消息有标签，与"消息流里每条都高亮"的需求直接冲突；不复用 → 多一套"只读派生"的标签，但要防止它与媒体库标签看起来像一回事。
- **处置**：**推荐不复用** —— 消息流标签定义为"caption 的只读派生投影"，不落库、不可编辑、不经 `media_tag`；媒体库标签维持"用户可编辑的持久资产"。这样两边各有一条清晰语义，避免重演 BUG-069「两套真源漂移」。代价：同一条内容在 TG 流与媒体库里的标签**可能不一致**（前者现场解析、后者入库快照），需要在文案层面说明。
- **请求**：确认"消息流标签 = 只读派生、不进 `media_tag`"；人工维护是否本期完全不做。

### B-2（可延后）「立即同步」的去留

- **因果**：后台已有自动循环（取证 #8），该按钮只是手动跑同一个 `sync_once`（取证 #7），源码自述调试入口；用户的质疑成立。不决定 → 只影响信息架构，不影响功能。
- **处置**：**推荐弱化**（移出监控列表标题行 → 放进「入库流水线」面板，带说明文案），而非硬删 —— 保留"刚加监控立刻要内容"的路径。
- **请求**：弱化到「入库流水线」面板，还是直接移除？

### B-3（可延后）是否摘掉前端每 60s 的同步轮询

- **因果**：前端 60s `POST /api/tg/monitor/sync`（取证 #9）是 BUG-038 为"面板看不到新内容"加的；它与用户"入库应是后台操作"的主张冲突，且让一个**写**端点被轮询。更严重的是**三源并发无互斥**（取证 #9b）：后台 30s + 前端 60s + 手动点击可同时飞行 → RPC 叠加 → **FLOOD_WAIT**，一旦限流会连带拖慢在线播放与缩略图取流 —— 这才是"入库影响前端展示"的真实机制。但**直接摘掉会退化为 BUG-038 的原症状**（面板永不更新），必须先有替代。
- **处置**（建议打包成一条，不要拆）：① 后端给 `sync_once` 加**单飞**（同一时刻至多一个在跑，其余排队或被拒并如实回报，对齐 AGENTS.md §5「单飞呈现 / 执行侧单飞」）；② 新增**只读**的"新增条数"端点（内存快照，符合 §5），「有 N 条新内容」改由只读计数驱动；③ 摘掉前端 `syncTgMonitor()` 定时调用；④ 手动按钮（若保留，见 B-2）改 fire-and-forget。这是 BUG-098 已提 SSE 方向的最小子集。**后端未就绪前不要摘前端；只摘前端不加单飞同样不够。**
- **请求**：是否批准"单飞 + 只读计数 + 摘前端同步"打包成一条（跨 engine+shell，需单独立 BUG），还是本期只做按钮去留（B-2）、把架构项留到 BUG-098 一起做？

## 7. 约束与风险（AGENTS.md §5 相关，写方案时不得违反）

1. **流畅优先**：消息流组件（`MessageBubble` / `AlbumBubble`）必须 `memo` 化，回调走 `useEvent`（引用恒定）。新增的高亮分段渲染不得让每次 `feed` 变化都重建全部气泡。
2. **轮询三律**：`ContextBar` 中间槽若承载输入框，必须做成独立 `memo` 子组件自带 state，**不得**让输入把 header 拖进重渲染（ContextBar 当前的 memo + 低频 props 设计是有意为之，`ContextBar.tsx:19-22`）。
3. **轮询 ≥5s、写端点不被轮询**：若要落实 B-3，新增的"新增条数"端点必须是**只读内存快照**；摘掉前端同步前必须先有替代，否则退化为 BUG-038。
4. **单飞呈现 / 执行侧单飞（BUG-027）**：`sync_once` 若保留多条触发路径，必须**同一时刻至多一个在跑**（多请求排队 FIFO 或被拒并如实回报），手动入口不得同步等待整轮（fire-and-forget）。这与 §5 既有的缓存任务范式一致，不要另造一套。
5. **原文不进 DOM（BUG-088）**：本文讨论的 caption 是**用户内容**，不属于该约束（该约束针对后端 HTTP 报文）；但高亮渲染时**不得**改动 caption 原文（AC1 已锁死）。
6. **单一真源**：标签解析规则无论落前端还是后端，**只允许有一份**。若最终是 TS + Rust 双实现，必须有对拍脚本（AC3）把它钉住 —— 本项目已因"两套真源"付过两次学费（BUG-069、BUG-087）。
7. **窄窗口回归**：任何在 `header` 里加元素的改动都要过 720px 宽度检查（BUG-040 类回归，AC5）。
8. **TG RPC 是共享瓶颈**：`sync_once` 与在线播放/缩略图取流共用同一个 MTProto 客户端（取证 #9b/#9c）。任何增加同步频率或并发的改动，都要先确认不会把 FLOOD_WAIT 引到播放通路上（机制为 architect 推断，**未实测，标待核**）。
