## 1. 缓存清理：从「全清动作」改成「选择驱动的清理中心」（BUG-059）—— 已实施

### 现状与问题

设置页的「清除缓存文件」是一个**动作**：点确认 → `POST /api/cache/clear` → 下载目录内缓存字节全清。
粒度只有「全清」和「逐条」两档，中间整层缺失，所以最危险的档位被直接摆在一个按钮下面。
「清除缓存文件」的正确形态是**入口**，不是动作 —— 与 BUG-054 对任务记录侧做的改造同构。

### 目标

清理 = 先选范围、看到影响面、再执行。用户要能表达：全部 / 某频道 / 某类型 / 早于 N 天 /
未归属剧集 / 失败任务残留 / 孤儿文件（磁盘有、库里无）/ 具体勾选的条目。

### 方案

**后端（engine）** —— 沿用任务记录侧已确立的「动词唯一、差异走参数」：

| 端点 | 语义 |
|---|---|
| `GET /api/cache/clear/preview?scope=...&ids=...` | 返回分档影响面：`items`（字节数/条数）、`orphans`（磁盘有库里无）、`external`（目录外文件，永不删）、`byChat` 分频道聚合。**只读，不产生任何删除** |
| `POST /api/cache/clear?scope=all\|orphan\|failed\|stale&olderThanDays=N&chatId=..&kinds=..` | 按整档清理（与 `ids` 互斥） |
| `POST /api/cache/clear?ids=1,2,3` | 按**集合**清理，复用 `parse_ids()`（非法/0/负数/空选择一律 422） |

不变量：`external` 档永远不删（沿用 `inside_dir()` 判定，跳过并计数）；返回值必须如实报
`{removed, skipped, bytesFreed}`；清理与「复位 `media_item.file_path` + TG `downloaded` 标记」
在**同一事务**内（否则状态会说谎）。

**前端（shell）**：

- `CacheManagerDialog` 升级为**清理中心**，两个页签：`任务记录`（现有勾选能力）/ `缓存字节`（新增勾选）；
- 设置页「清除缓存文件」按钮 = 打开该对话框的「缓存字节」页签，**不再直接清理**；
  同屏给出实时占用（`clear-cache-usage`，含孤儿字节 —— `stats.bytes` 不含孤儿，漏报即低估）；
  **判据读回且为 0** 时禁用（读回之前不禁用：那时读数是「正在读取占用…」，灰按钮同屏＝谎报「没什么可清」）；
- 对话框内先出预览（预计释放 X、涉及 N 条、其中孤儿 M 条、外部文件 K 条不参与），
  用户按档 / 勾选 / **按频道**（整频道 = 一次勾选，仍走 `?ids=`）后再执行。

### 不做

- 不做「按大小阈值自动清理」的策略引擎（无诉求，且引入后台行为）；
- 不删 `download_dir` 之外的文件（`external` 只计数、不参与）；
- 「全部」档**不含孤儿**：孤儿来源不可考（可能是被删条目遗留，也可能是用户自己丢进下载目录的文件），
  保留为独立档 = 保留这道区分；因此按钮命名是「清理全部缓存**条目**」而非「全部缓存字节」。

### 验收

1. 预览读数与 `GET /api/cache/stats` 及磁盘实际占用三方一致（逐字）；
2. 点取消 → 占用读数、条目数、`file_path` **逐字未变**（验牙）；
3. `?ids=999999999` → `removed:0, selected:1`，不误删其它；`?ids=` 空 → 422；`?ids=abc` → 422；
4. `external` 文件在 `scope=all` 下 `skipped` 计数增加且文件仍在；
5. 设置页按钮在**判据读回且为 0** 时禁用（读回前不禁用）。

**落地证据**：引擎契约 `download-engine/verify/verify_cache_scopes.py` **46/46**（隔离实例 9878，
由 `verify_shots/run_cache_clear_verify.sh` 拉起）；界面 `tauri-shell/verify/shot_clear_center.cjs`
**33/33**（真实实例 9877 + 5180）。两者均已入库、可跨机器复跑。

### 覆盖面清点（用户问：「里面的所有内容能否在外部哪个选项中单独删除」）

逐项实地核对**每一类持久化内容是否都有自己的删除入口**（结论：是；下表同时标出本轮补的那一处）：

| 内容 | 存放位置 | 独立删除入口 | 状态 |
|---|---|---|---|
| 缓存任务记录 | `cache_task`（store.db） | 缓存管理对话框逐行 / 表头全选 / 批量 `DELETE /api/cache/tasks?ids=` | ✅ 已有（BUG-054） |
| 缓存字节 · **全部条目** | `<download_dir>/` | 设置 → 常规 → 「清除缓存文件」→ **清理中心**「缓存字节」页签 → 「清理全部缓存条目」（先出确认条） | ✅ 本轮改为入口（原为就地全清） |
| 缓存字节 · **单个条目** | 同上 | 条目编辑框「清除缓存文件」→ `DELETE /api/cache/items/:id`（**记录保留**，可重新缓存） | ✅ **本轮补上** |
| 缓存字节 · **按频道 / 故障 / 陈旧 / 孤儿档** | 同上 | 清理中心：按频道 chip（选定该频道全部条目）+ `?scope=orphan\|failed\|stale&olderThanDays=` | ✅ 本轮已实施 |
| 媒体库条目（含其字节） | `media_item` | 卡片逐条 + 批量 + 确认（删除会连字节） | ✅ 已有 |
| 剧集 / 分集 | `media_series` / `media_episode` | 剧集详情「删除剧集」/ 分集「移除」 | ✅ 已有 |
| 标签（含 0/0 孤儿） | `media_tag` | 「标签管理」对话框删除 | ✅ 已有（BUG-068 后孤儿不再在左栏显形，但管理里仍可删） |
| TG 消息流水 | `media_message` | **无用户入口** | ⛔ 有意为之：它是事实源，随频道同步自动增删 |
| 设置 / 登录态 | `app_setting` | 设置页各字段 | ✅ 已有 |

**本轮补的那一处值得说明**：`DELETE /api/cache/items/:id`（清单个条目的字节）后端**一直存在**，
但全仓 `grep` 显示**没有任何前端调用方** —— 端点是死的，于是磁盘上 GB 级缓存只有「整目录清」
和「逐条删记录（不动字节）」两条路。缺的不是能力，是入口。入口已加在条目编辑框内
（与「删除条目」并排但语义分明：清缓存 = 只删字节、记录保留；删除 = 连记录一起），
验收见 §1 附注（`tauri-shell/verify/shot_item_cache.cjs`，13/13，**零副作用**）。

**「全部」为什么不叫「全部缓存字节」**：全部档清的是**条目背书**的字节（`stats.bytes` 口径），
孤儿（磁盘有、库里无）只认独立档 —— 因为孤儿的**来源不可考**（可能是被删条目的遗留，也可能是
用户自己丢进下载目录的文件），把它塞回最常用的那个按钮等于取消这道区分。旧文案
「清空全部缓存字节」会让人清完之后看见 1.1 GB 孤儿仍在而以为没清干净；现改名为
**「清理全部缓存条目」**，与「清理孤儿文件 / 陈旧文件 / 失败残留」同为条目式命名。
该语义由契约测试 `4b-2` 钉死（孤儿经 `scope=all` 必须仍在磁盘）。

## 2. 媒体库快捷删除（BUG-057）—— 已实施

### 现状与问题

媒体库**已经有**：勾选框（`MediaCard`）、Shift 范围选择、表头全选（`media.selectAll`）、
已选计数、批量「移除」、确认弹窗（`confirmDelete`）。缺的是**逐条**入口 ——
删除被建模成批量动作，单条删除只能退化成「大小为 1 的批量」，且动作条挂在
`selected.size > 0` 之下，未选中时界面上**不存在**删除。

### 目标

与缓存管理面板同构：**每条有自己的删除入口，批量是选择的结果而不是前置仪式**。

### 方案

- `MediaCard` 增删除入口，与编辑入口同一呈现策略（该策略已在本轮定为「常驻可见」：
  运行期几何判定 `opacity === '1'` 且中心点 `elementFromPoint` 命中自身）；
  点击后 `setConfirmDelete({kind:'items', id})`，**复用现有确认状态机**，不新开第二套；
- 确认文案按范围分岔：单条「删除这条内容」/ 批量「删除所选 N 条」；
- **归属告知**：若所选条目中有正在被剧集引用的，确认条必须如实报出
  「其中 M 条已归入剧集，删除后对应剧集可能变空」——避免制造空剧集这一隐性状态；
- 剧集卡片同款加逐条删除（`kind:'series'` 分支已存在）。

### 不做

- 不做「移到回收站」的中间态（`media_item` 无回收位，引入等于新增生命周期，需单独设计）；
- 不做「删除文件与删除记录」的二选一 —— 媒体库条目删除**只删记录**，
  磁盘字节归缓存域（第 1 节）。这条边界必须写进确认文案，否则用户会以为文件也没了。

### 验收

1. 未 hover 与 hover 两态删除入口均可见（几何判定，不看类名）；
2. 删除 → 取消 → 条目数与剧集列表**逐字未变**；
3. 删单条 → 该 id 消失，其它 id 集合不变（集合差集断言）；
4. 删到剧集最后一集 → 确认条**事先**报出该影响（不能事后才发现）。

**落地证据**：`tauri-shell/verify/shot_media_delete.cjs` **17/17**（真实实例 9877 + 5180；
真实库只走取消路径，幂等与端点半径由 200/`removed:0` 锁定）。已入库、可跨机器复跑。

## 3. 媒体库左栏标签：单行原语 + 零计数省略（BUG-058 / BUG-068）—— 已实施

> **定位纠偏**：本项首轮被写成「导航标签」，实际对象是**媒体库面板左栏底部**的
> 「标签」chips 区（`MediaLibraryPanel` 的 `[data-testid="media-tag-list"]`）——
> 与主侧栏 `Sidebar` 是两回事。用户第 9 轮的反馈「媒体库底部标签仍然显示大量 0」正是
> 因为首轮只看了侧栏、没打开媒体库面板。

### 现状与问题（实测）

| 位置 | 事实 |
|---|---|
| 标签 chip | `rounded-full border px-2 py-0.5 text-[10.5px]` —— **既无 `truncate` 也无 `max-w` 也无 `whitespace-nowrap`**，长名把 chip 内部撑成两行 |
| 计数渲染 | `tags.map()` **无条件渲染全部标签**（含计数 0 的）；而计数为 0 的入口点下去必然是空列表 |
| 计数语义 | 内容侧算 `itemCount + seriesCount`，但内容侧筛选**只匹配条目** ⇒ 显示 8、点开 6 条 |
| 数据来源 | 删条目/剧集只 `DELETE FROM media_item_tag`，**不 GC `media_tag` 行** ⇒ 每次删除都留下 0/0 孤儿，越积越多（真实库 28 个标签里 **10 个是 0/0**） |

### 方案（已落地）

```
分类行/剧集行: flex items-center gap-2 w-full min-w-0
  名称:      min-w-0 flex-1 truncate
  计数:      shrink-0 tabular-nums text-[10px]
chip:        inline-flex max-w-full items-center gap-1 whitespace-nowrap
  chip 名:   min-w-0 truncate            # 全名保留在 title 属性
  计数:      shrink-0 tabular-nums       # 永不先被压掉
渲染规则:    每侧只算该侧计数（内容=itemCount，剧集=seriesCount）；
            计数 0 不渲染；**唯一例外 = 当前选中项**（否则选中态消失、无取消入口）
```

要点：`min-w-0` 是「允许收缩」，`truncate` 是「允许截断」，**两者缺一都不成立**；
`shrink-0` 保证「名称被截断而不是计数被挤掉」；容器 `flex-wrap` 仍可让**不同 chip 之间**
换行（这是期望行为，不是破绽）。**隐藏 ≠ 删除**：孤儿标签只在渲染层过滤，
数据层原样保留（不替用户销毁数据）。

### 验收（实测 18/18，`verify_shots/shot_round9_tags.cjs`）

| 形态 | 实测结果 |
|---|---|
| 最小：计数 0 | 内容侧 19 个 chip **零个 0**；库内 10 个 0/0 孤儿**一个都没出现**；分类行 `音频 0` 不渲染 |
| 最小非零：计数 1 + **超长名（33 字）** | chip 高 **21.8px**（单行）、宽度 183 ≤ 容器 191、名称 `scrollWidth > clientWidth`（截断生效）、计数宽 6.2px 未被压掉、显示 1 |
| 最大：计数 94（库内最大） | 数字宽 12.3px、未被裁切 |
| 全部 chip | `white-space: nowrap` 且高度 ≤ 24px（19 个） |
| **显示的数 = 点下去得到的数** | 点「冰蝶网调冰山妈妈 2」→ 网格 2 张卡片（旧实现在此会显示 8 而筛出 6） |
| 剧集侧各算各的 | 7 个 chip 全 > 0；只在内容侧挂载的标签（`1080p` series=0）正确不出现；挂到剧集的标签显示 `seriesCount`（2，非 item+series） |
| 隐藏不销毁 | 10 个孤儿在数据层仍在；探针标签可经 `DELETE /api/media/tags/:id` 显式删除（200） |

## 4. 图片按「归属」分组浏览（BUG-060）—— 数据结构是关键

### 现状与问题

图片以**分集**身份进入剧集（`media_episode` 行，`kind='photo'`，BUG-044 已禁止图片进播放序列），
但剧集详情把全剧集图片收成一个数组、一条横向行平铺（`photoEps` → `series-gallery`）。
合并多个剧集后，不同视频的图片混在同一条行里，无法分辨归属；播放某视频时灯箱在**全部**图片里翻页。

**根因不是 UI，是模型**：图片与视频之间「同批发布」这一关系没有建模。
好消息是数据已经在库里：TG 相册同批媒体共享 `group_id`
（`media_message.group_id`、`cache_task.group_id`），只是止步于流水表，**没透传到媒体库模型**。

**实测证据（用户指出「不同的消息很可能指向同一图片」——已验证成立）**：

对真实库 27 条 `kind='photo'` 逐文件算 SHA-256：

| 指标 | 值 |
|---|---|
| 有字节的图片 | 26 |
| 唯一 hash | **22** |
| 重复组 | **4**（`149+157`、`150+158`、`151+159`、`152+254`） |
| 当前可省空间 | 438 KB（照片量级） |

即 **8 条记录只对应 4 张图**；视频侧也有 1 组（`34+35` 共用一个 554 KB 文件）。
所以「图片按分集铺开」看到的不只是归属混乱，还包含**同一张图被当作不同图重复展示/重复落盘**。
这决定了下面的方案必须同时有**内容寻址（hash）**与**归属派生**两条正交的线。

### 方案（四层：内容寻址 → 归属派生 → 分组浏览 → 删除引用计数）

**⓪ 内容寻址（engine）—— 用户指名的方向**

- `media_item` 增 `content_hash TEXT NULL`（**只对 `kind='photo'` 强制**；视频 hash 成本高，
  暂只做「同路径」判重）+ 索引 `idx_media_item_content_hash`；
- 写 hash 的时机：文件**落盘成功那一刻**（`upsert_media_item` 传入 / `/raw` 首次产生字节时补算），
  不在查询期重复 I/O；历史数据用一次性回填迁移（`app_setting` 标记键收口，与 BUG-054 同款）；
- **同 hash ⇒ 同一物理文件**：后续记录不再重复落盘，`file_path` 直接复用已存在路径；
- 浏览层：同一 hash 的组**只展示一次**，组内其余记录折叠为「另有 N 处引用」的角标
  （用户点开能看见引用它的消息，不会以为图丢了）。

**① 归属批次透传（engine）**

- `media_item` 增 `album_group TEXT NULL`，来源：TG 相册的 `group_id`（本地导入为 NULL）；
  写入路径在 `upsert_media_item` 一并落库，历史数据用一次性回填迁移
  （`app_setting` 标记键收口，与 BUG-054 同款做法）；
- 建索引 `idx_media_item_album_group`（分组查询是高频路径）。

**② 归属计算（engine，不落冗余关系表）**

分组在**查询时**派生，规则按优先级：

1. 同 `album_group` 且 `kind='video'` 的条目存在 → 该图片归属**那个视频**；
2. 同 `album_group` 但无视频（纯图相册）→ 归属「该批次」分组；
3. 无 `album_group` → 归「未分组」。

理由：归属是**派生量**，落一张关系表会与 `album_group` 冗余，且剧集合并/条目删除时
需要额外维护一致性 —— 用派生规则则天然跟随。

**③ 展示层（shell）**

- 剧集详情的图册由「一条平铺行」改为**分组浏览**：每个分组一个分组头（视频标题 / 批次 / 未分组）
  + 组内横向滚动；顶部保留「全部」总览图册；
- `EpisodeView` 增 `albumGroup` 与 `attachedItemId`（归属视频条目 id，可为 NULL），
  前端按它分组；
- 播放器灯箱的翻页范围**收敛到当前播放项所属分组**（从视频点入 → 只看该视频的图；
  从「全部」点入 → 在全部里翻）。

**④ 删除的引用计数（engine）—— hash 方案引入的新不变量，必须同时落地**

多条记录共享一个 `file_path` 之后，「删一条」不再等价于「删这个文件」：

- `DELETE /api/cache/items/:id`（清单条字节）与 `DELETE /api/media/items/:id`（删条目）
  在 `unlink` 之前**必须**查「同 `content_hash`（或同 `file_path`）还有几条记录」，
  `count > 1` 时**只解绑当前记录、不删文件**，并在响应里如实回报
  `{removed: 0, unlinked: 1, sharedWith: N}`；
- 反过来，若不做这一步，删一条重复图片会把仍在被引用的文件删掉 —— 这比「多占几 MB」严重得多，
  所以**引用计数与内容寻址必须同批实现**，不允许先上 hash 后补计数。

### 不做

- 不做人工「把这张图挪到那一集」的编辑器（无诉求；派生规则已能覆盖相册场景）；
- 不改 `media_episode` 的唯一约束（图片仍占分集槽位，BUG-039/044 的模型不动）；
- **不重建磁盘目录布局**（不改成 `downloads/<hash>` 桶式存储）：`file_path` 已被大量行引用、
  且 UI 会显示路径，重排收益（省几 MB）不抵迁移风险；去重靠「同 hash 复用同一路径」达成。

### 验收

1. 造数：第 1 批（1 视频 + 3 图）、第 2 批（1 视频 + 2 图），两剧集合并后断言分组计数逐字为 3 / 2；
2. 播放第 2 个视频 → 灯箱总页数 = 2，且逐张命中该组（不是「不等于旧值」这种弱断言）；
3. 无 `album_group` 的图片落在「未分组」，且**守恒**：各组计数之和 == 图片总数；
4. 删除某视频条目后，其图片不被静默吞掉 —— 落入「未分组」或随批次重算，且库里总数守恒；
5. **hash 回填**：回填后所有有字节的 photo 记录 `content_hash` 非空，且与 `sha256(文件)` 逐字相等；
   再次跑回填**不产生任何变化**（标记键幂等）；
6. **重复组行为**：对真实库那 4 组重复（149+157 / 150+158 / 151+159 / 152+254）断言 ——
   浏览层只出现 1 项 + 「另有 1 处引用」角标；
7. **删除安全（验牙）**：删掉重复组中的 A 条 → 文件**仍在**（B 条仍可播放）；
   再删 B 条 → 此时才 unlink；两步都要断言磁盘文件的存在性（不能只看接口 200）。

## 5. 合并槽位语义统一（BUG-056）

### 现状与问题

「一个条目占哪些槽位」在仓内有**三条实现、三种规则**：

| 路径 | 槽位规则 | 是否保留 `episode_no_end` |
|---|---|---|
| `append_episodes_ranged()` | 占用快照含终点，`COALESCE(episode_no_end, episode_no)` | 是（BUG-039 确立） |
| `add_episode_ranged()` | 显式传参 | 是 |
| `merge_series()` | `COALESCE(MAX(episode_no), 0)`，**只看起点** | **否**（INSERT 列清单没有该列） |

后果：源剧集含「EP01-02 合集」时，合并后合集退化为单集，其后的单集被编成 `2`，
与合集占用的第 2 槽**语义撞位**。用户说的「1-2 合集问题」与「多个 1 集视频没处理」是同一缺口。

### 方案

**统一到一条规则**，不让第三条存在：

- `merge_series()` 的槽位分配改为**复用 `append_episodes_ranged()`**（抽成内部函数或直接调用），
  彻底删掉 `COALESCE(MAX(episode_no),0)` 这份重复实现；
- 搬移 INSERT 补上 `episode_no_end`（区间随条目走）；
- 同槽冲突（多个条目都声明占第 1 槽）时，**不静默改号**：
  首次落主条目，后续落 `media_episode_source`（BUG-039 已建的备用来源表，同槽多源），
  `MergeReport` 增 `sourcesAttached` 如实回报；
- 保留既有裁定不变：**搬移 + 保序，禁任何内容级去重**，唯一跳过依据仍是
  「`item_id` 在目标同季已存在」，且必须回报。

### 验收

1. 合集区间保留：合并后 `episode_no_end` 逐字相等（非空）；
2. 后继集号正确：不出现两个语义第 2 集（断言占用集合无重叠）；
3. 同槽多源：两个「第1集」合并后 `sources` 长度 = 1、主条目不变、`sourcesAttached = 1`；
4. 幂等：同一对剧集重复合并，第二次全部走 `skipped` 且库状态不变；
5. 回归 BUG-037 的 22 项断言与 BUG-039 的区间断言全绿（合并语义不许被本轮改动破坏）。

## 8. CI 门禁（已落地，`.github/workflows/ci.yml`）

背景：本地钩子可以被 `--no-verify` 绕过，且「产物与源码脱节」这类腐化**只在构建期**可见。
所以 CI 按**能独立失败**的三件事分 job：

| job | 平台 | 内容 | 为什么必须在这里 |
|---|---|---|---|
| `engine` | windows | `cargo test -p orig-tg --lib` → `cargo build --release -p orig-tg -p orig-daemon` → `sync-sidecars.sh` → `sync-sidecars.sh --check` | 单测是功能闸；**陈旧检测是交付闸**（BUG-055/061：脚本全绿但用户进程跑旧引擎） |
| `shell` | windows | `npm ci` → `tsc --noEmit` → `vite build` | 「改了源码但产物没跟上」在前端同样成立（BUG-054 的观感来源） |
| `registry` | ubuntu | `check-bugs.py` + `check-commit-msgs.py` | 登记册一致性需要**完整 git 历史**（校验引用的提交 hash 真实存在），故 `fetch-depth: 0`；提交信息规约在本地可被 `--no-verify` 绕过，这里兜底 |

新建 `scripts/check-commit-msgs.py`：按**范围**复验 `AGENTS.md` §2 两条硬规 ——
提交信息一律英文（**扫全文 `%B`**，只看 `%s` 会假阴性）、`fix` 类必须引用 `BUG-<编号>`；
`Merge`/`Revert` 跳过；`--all` 为审计模式（报告违规但退出 0，避免历史欠账把流水线永久染红）。

CI 的失败语义必须清晰，故：
- 定时任务每周一兜底跑一次 —— 即便没人提交，也能发现「产物比源码旧」这类**时间性腐化**；
- 仓库根白名单检查（AGENTS.md §6）先做成 **advisory（`continue-on-error`）**：
  现状有历史遗留（`overview.md` / `tg_store.db`），把它设成阻断等于用一个未清偿的欠账
  永久染红流水线；先让污染**可见**，处置见待拍板。

## 10. 剧集/条目文案单一真源 + 播放页只读化（BUG-069 / BUG-070）—— 已实施

### 现状与问题（实测）

用户第 9 轮复测（BUG-054 发版后）三问：剧集里标题改不了 / 介绍没填进视频 / 播放页只读却有编辑按钮 /
右侧列表有无用播放图标 / 进播放页同一部剧集被请求多次（用户记 8 次）。

取证：

- `media_episode` 自带 `title`/`description` ⇒ 与 `media_item` 构成**两套真源**。
  实测真实库：分集介绍非空 **1/45** 行、条目介绍非空 **7/110** 行 —— 两条写路径早已漂移。
  `EpisodeView` 同时下发 `title`（分集行）与 `item_title`/`item_description`（条目），
  前端各处按分支挑名字读，`EpisodeList` 甚至写着 `ep.title || ep.itemTitle` 的兜底链
  —— **兜底链本身就是「没人知道该信哪个」的证据**。
- 分集编辑面板字段只有季/集/介绍 ⇒ 剧集路径下标题**完全不可改**。
- `viewer.editable` + `requestEditItem` 让播放器（只读消费者）持有写入口。
- `EpisodeList` 当前行尾的 `<Play>` **无 `onClick`**。
- 剧集详情被三个消费者各 `getSeries` 一次（`openSeries` / `playItems` / `useSeriesDetail`），
  StrictMode 再翻倍。

### 方案

| 议题 | 处置 | 结构性理由 |
|---|---|---|
| 两套真源 | 分集只是**位置**，文案真源 = 条目；`EpisodeView` 删冗余字段，`update_episode` **写穿**条目，`add_episode`/`merge_series` 不再写分集列 | 同一份数据只留**一个名字**，前端无处可挑错 —— 从「对齐两个值」变成「不存在第二个值」 |
| 存量数据 | 一次性迁移 `collapse_episode_text`（标记 `mig.episode_text_to_item_v1`）：条目介绍为空时回填，随后清空死列 | 只搬**介绍、不搬标题**：条目 `title` 是 NOT NULL 必有值，分集标题只是无权威快照，反向搬会覆盖用户真值（单测钉死） |
| 分集标题不可改 | 面板补标题输入框；空标题前端即拦 | 与后端「空标题不可表达」同一语义（BUG-054 已定） |
| 播放页可写 | 删 `viewer.editable` / `editItemId` / `requestEditItem` | 让「播放页可写」这个状态**不可表达**，而不是本次把按钮藏起来 |
| 装饰图标 | 删无 `onClick` 的 `<Play>` | 无行为的控件不得长得像控件 |
| 重复请求 | `lib/fetchCache.ts` 会话内共享同一个 Promise（并发合流）+ 写操作后显式 `invalidateCache()` | 缓存**不做时间过期**：陈旧窗口是不可解释的中间态，失效必须由写操作表达 |

### 不做

- 不给缓存加 TTL / SWR：本域写操作少而明确，显式失效足够；TTL 只会引入「偶发读到旧值」。
- 不用生成列/视图去「让两处保持一致」：那等于承认两套真源合法。

### 验收

| 层 | 证据（入库，可跨机器复跑） | 结果 |
|---|---|---|
| 引擎契约 | `download-engine/verify/verify_episode_text_source.py` | **15/15** |
| UI 真实渲染 | `tauri-shell/verify/shot_series_text_edit.cjs` | **18/18** |
| 单元测试 | `cargo test -p orig-tg --lib`（新增 4 项） | **50 passed; 0 failed** |

按阶段请求计数实测：`A-open=1` / `B-play=0`（进播放页零增量）/ `C-refresh=1`；播放页按钮集合里
**无任何编辑入口**；右侧分集行内 **svg = 0**。

**探针自身缺陷（首轮 14/16 的两次假阳性，非产品缺陷）**：①「播放页无编辑入口」扫了整个
`document`，而媒体库面板仍挂在播放器浮层**背后**的 DOM 里 ⇒ 作用域锚到 `[data-testid="media-viewer"]`；
②请求计数把 CORS **预检**算作真实请求（「1 次」读成「2 次」）⇒ 排除 `initiator.type === 'preflight'`
并改为阶段化计数。
