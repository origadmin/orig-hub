# 播放投递性能：把编码移出播放路径（实测取证 + 最优形态）

- 日期: 2026-10-13
- 类型: 性能归因 + 架构方案 + 任务分解
- 触发: 用户实测「**全都卡，一顿一顿**」，并要求「**最优方案**，不要再打补丁」
- 前置裁定: `docs/bugs/BUG-230.md`（2026-10-09 用户裁定 **stream-first**，raw 退役为下载/导出端点）
- 关联计划: `docs/design/product-direction-and-ffmpeg-2026-10-09.md`（ffmpeg 组件化；本文**不**替代它，只处理播放投递形态）
- 取证方式: 全部为**本机 2026-10-13 03:26–03:40 实测**，命令与读数逐条可复核

> **本文与既有结论的关系（先声明，避免被读成翻案）**：
> BUG-230 当年裁定 stream-first，其立足点是「raw 直解全程卡顿，stream 转码流流畅」。
> **那个立足点在当时的被测内容上成立**（见 §1.3：被测条目 472/673 均为 **HEVC**，且 472 是 **60fps**）。
> 本文不改写该结论，而是补上它**没有覆盖的前提**：**编码类别与源帧率**。
> 结论差异全部来自**新证据**，不是对旧结论的否定。

## 0. 结论摘要

| # | 结论 | 依据 |
|---|---|---|
| 1 | **投递侧不是瓶颈。** 产物就绪时，`/stream` 命中代理 **TTFB 14.7 ms、8 MiB / 71 ms（117 MB/s）**；`/raw` **TTFB 13.9 ms、81 MB/s**。两条都是**可 seek** 的 206 + `Content-Range` + `ETag` | §1.1 |
| 2 | **编码器也不是瓶颈（1x）。** 同一台机器上按生产参数整片转码 221 s 内容耗时约 **45 s（≈4.9× 实时）** | §1.2 |
| 3 | **但 live 流是「一冲一顿」的**：冷启动 TTFB **1.91 s**，25 s 内 **20 次 >0.5 s 的空档、15 次 >1.0 s**（平均吞吐 4.4× 实时，但**以 0.6–1.7 s 为周期成簇到达**） | §1.1 |
| 4 | **真正的结构性错误是「播放时才转码」**：它把编码器放到了关键路径上，并**顺带废掉了浏览器唯一的免费倍速机制**（原生 `playbackRate` 被强制为 1）。此后所有补丁（FRC 变体、代理缓存、LRU 预算、单飞表、`?t=` 锚点）都是为这个决定还债 | §2 |
| 5 | **`-fpsmax 30` 正在毁掉 60fps 内容**：条目 472 源为 **HEVC 720p **60fps**，产物是 **H.264 30fps** —— 时域分辨率被硬编码砍半，这正是「一顿一顿」的直接来源之一 | §1.3 / §3.3 |
| 6 | **运行期还有三处确定性缺陷**：代理缓存 **2.0 GB / 预算 2 GiB** 已满并在逐出（含 322 MB 的 0.5x 变体）；**4 个 `.part` 孤儿永不回收**（最早 10-09）；**1x 转码在客户端断开时被整个丢弃**（`routes.rs:4854/4867`），而 1x 恰是最常用档位 | §1.5 |

**一句话**：不是「投递不够快」，是**我们把一件本该在开播前做完的事，放到了开播之后、并且放在了关键路径上**。

## 1. 实测事实底座（2026-10-13，本机）

### 1.1 投递侧：产物就绪 = 秒开；live 冷启动 = 一顿一顿

**A. 代理命中（`GET /api/media/items/472/stream`，1x）**

```
HTTP/1.1 206 Partial Content
content-type: video/mp4
accept-ranges: bytes
etag: "da08843-6acd365a"
content-range: bytes 0-1048575/228624451
x-orig-stream: proxy

code=206  ttfb=0.014679s  total=0.071486s  bytes=8388608  speed=117346165 B/s
```

**B. 原文件（`GET /api/media/items/472/raw`）**

```
HTTP/1.1 206 Partial Content
accept-ranges: bytes
etag: "6f3e1ad7-6abb8fa9"
content-range: bytes 0-1048575/1866341079

code=206  ttfb=0.013872s  total=0.103016s  bytes=8388608  speed=81430146 B/s
```

⇒ **两条路径都是「可 seek 的普通文件」形态，且都是瞬时**。`/raw` 的 1.87 GB 原文件同样 206 + `Accept-Ranges`，**没有任何形态缺陷**。

**C. live 冷启动流（`GET /api/media/items/1437/stream?t=60`，25 s 采样）**

```
HTTP 200  x-orig-stream=live
sampled 25s, bytes=34013184 (32.44 MiB), chunks=519
first-byte TTFB = 1.912 s
max inter-arrival gap = 1.912 s
median gap = 0.0004 s
gaps > 0.5s: 20 ; > 1s: 15 ; > 2s: 0
  t=  1.912s  gap=1.912s
  t=  2.558s  gap=0.635s
  t=  4.173s  gap=1.579s
  t=  5.669s  gap=1.408s
  ...（此后每 0.6–1.7 s 重复一次）
```

**读法（必须说清楚，否则会被误读成「投递不足」）**：25 s 内送 **32.44 MiB**，而 1x 只需约 **7.3 MiB** ⇒ **平均 4.4× 实时，玩家不缺缓冲**。
真正的形态问题是：**数据以 0.6–1.7 s 为周期成簇到达**（中位间隔 0.0004 s = 簇内几乎连续）。
⇒ 播放器拿到的是**「一冲一顿」的供给**，而不是**「平稳且可预读」的文件**。这是 §2 的直接后果。

### 1.2 编码侧：1x 有约 5× 余量（编码器不是瓶颈）

条目 1437（H.264 1080×1920 30fps，221 s），按生产参数（`libx264 -preset veryfast -crf 23 -fpsmax 30`，`frag_keyframe+empty_moov`）整片转码：

```
WALL ≈ 45 s  （源时长 221 s）
out  = 62,669,604 bytes
```

⇒ **≈4.9× 实时**。硬件：`i7-12700H`（20 线程）；ffmpeg 已启用硬解（日志 `ffmpeg config resolved: 硬解 cuda（设备 0）`）。
**结论：1x 下编码器跑得赢实时。** 但注意：**「跑得赢平均」不等于「每一瞬间都跑得赢」** —— live 流的簇状供给（§1.1 C）正是瞬时抖动的外化。

### 1.3 内容侧：库内**大多数是 H.264**，而用户实际在播的是 **HEVC**

抽样探测 `tg/library/**/*.mp4`（30 条）：绝大多数为 `h264`，少数 `hevc`；帧率混杂 30 / 24 / 60；存在 VFR（如 `137850000/4511869`）。

**用户实际播放条目的源编码（关键）**：

| item | 源编码 | profile | 分辨率 | 源帧率 | 源大小 | 转码产物 |
|---|---|---|---|---|---|---|
| **472** | **hevc** | Main | 1280×720 | **60 fps** | 1.87 GB | h264 30 fps |
| **673** | **hevc** | Main | 1920×1080 | 30 fps | 523 MB | h264 30 fps |
| 1437 | h264 | High | 1080×1920 | 30 fps | 226 MB | h264 30 fps |
| 1444 | h264 | High | 720×1280 | 30 fps | 198 MB | h264 30 fps |
| 1446 | h264 | High | 720×1280 | 30 fps | 131 MB | h264 30 fps |

**两条决定性事实**：

1. **用户点开最多的 472 / 673 是 HEVC。** 这解释了 BUG-230 当年「raw 直解全程卡顿」的观测 —— 那次观测**是在 HEVC 内容上做的**，不能推广到库内占多数的 H.264 条目。
2. **472 的源是 60fps，产物被压到 30fps**（`encode_profile` 硬编码 `fps: 30`）。时域分辨率被砍半 —— 对 60fps 内容而言，这本身就是**可见的「一顿一顿」**。

### 1.4 显示与硬件

| 项 | 值 | 手段 |
|---|---|---|
| 显示刷新率 | **60 Hz** | `gdi32.GetDeviceCaps(hdc, VREFRESH)` |
| 分辨率 | 2560×1080 | `HORZRES` / `VERTRES` |
| CPU | i7-12700H，20 逻辑核 | `/proc/cpuinfo` |
| ffmpeg 硬解 | 已启用（cuda，设备 0） | orig-tg 日志 |

⇒ 60 Hz 下：**30fps 是干净的 2:1**；**24fps 是 3:2 pulldown（经典抖动）**；**60fps 内容降到 30fps 是人为的平滑度损失**。
库内存在成批 24fps 条目（`2743`–`2748`：720×1280 24fps）⇒ 这批内容在 60 Hz 上**天生抖动**，与投递无关。

## 2. 结构性根因

### 2.1 流畅播放需要两个**正交**条件同时成立

| | 投递可 seek（Range/206，浏览器驱动预读） | 投递为单向增长流 |
|---|---|---|
| **字节可解**（浏览器硬解） | ✅ **两边都不卡** —— Telegram Web；OrigHub 的「完整代理」也是这个形态 | ❌ 卡：**编码器在关键路径上** —— OrigHub `/stream` 冷启动 |
| **字节不可解**（HEVC 无硬解） | ❌ 卡：**解码能力问题** —— OrigHub `/raw`（HEVC 内容） | ❌ 必然不可播 |

- **Telegram Web 同时占第一行两格**：上传时已编好 H.264（可解）＋ Service Worker 按 `Range` 回 **206 + `Content-Range`**（可 seek，分片 0.5 MB，浏览器自己驱动预读）。**播放路径上没有任何编码器。**
- **OrigHub 的三条路径各只占一格**：
  - `/raw` → 可 seek ✅ / 可解 ❌（HEVC 内容）；
  - `/stream` 冷启动 → 可解 ✅ / 可 seek ❌（单向增长流）；
  - `/stream` 命中完整代理 → **两格全占 = 与 Telegram 同形**，但**只在整整一趟转码之后才存在**。

⇒ **我们其实已经有「最优形态」的那条路径（`serve_local_file`），问题只在于它的产物来得太晚、且会被清掉。**

### 2.2 「播放时才转码」是这些补丁的共同祖先

一旦决定「开播时才转码」，就**必然**依次长出：

| 后果 | 补丁 | 现状 |
|---|---|---|
| 流不可 seek ⇒ 倍速不能靠浏览器 | 服务端 FRC 变体（每倍速一份产物） | 已实现，即缓存膨胀之源（F1/F2） |
| 转码要时间 ⇒ 不能每次重转 | 代理缓存 + LRU 预算 | 已实现，已撑满（F1） |
| 单飞防重复转码 | 单飞表 + watch + 孤儿自愈 | BUG-288 |
| 冷缓存深位换档要等「从 0 追上来」 | `?t=` 锚点 live-only 流 | BUG-226 |
| 单向流时长未知、不可拖 | 时长/进度条/续播一系列特判 | `VideoPlayer.tsx` |

**其中「服务端 FRC 变体」是最贵的一笔**：它为**每一个倍速**都存一整部视频（`472` 一个条目就有 7 个变体，合计 ≈1.4 GB），直接造成 F1/F2 的逐出抖动。
而它要换来的能力 —— **改倍速** —— 浏览器**本来就免费提供**（`playbackRate`），前提是**源可 seek**。**当前设计在 `VideoPlayer.tsx:810` 明确把 `playbackRate` 强制为 1**，等于主动放弃了这条免费路径。

### 2.3 与 BUG-230 的关系（不改写，只补前提）

BUG-230 的裁定在**其被测内容**（HEVC，且 472 为 60fps）上是正确的：HEVC 内容直解确实会卡。
本文补的是它**没有写下的前提**：**「能不能直解」由编码类别决定，不由「raw 还是 stream」决定。**

⇒ 正确的问题不是「raw 还是 stream」，而是 **「这份字节，浏览器解得动吗？」**

## 3. 最优方案（目标形态）

> **一句话原则：播放路径上不允许存在编码器；播放源必须可 seek；帧率必须保真。**

### 3.1 三档路由（按「浏览器能不能解」分流，而不是按端点分流）

| 档 | 条件 | 播放形态 | 代价 |
|---|---|---|---|
| **A 直解** | 源编码浏览器可硬解（本机绝大多数 H.264；HEVC 视 MF/硬解实测而定） | 直接 `serve_local_file` **原文件**，Range/ETag/可 seek | **零** |
| **B 预转码** | 源编码不可解（实测确认的 HEVC 等） | **入库/缓存期**后台转成 H.264 一份，落盘持久化；播放时仍走 `serve_local_file` | 一次转码，且**不在播放路径上** |
| **C 兜底** | 转码未就绪且用户要立刻看 | 保留现有 live 流作为**降级路径**，并在 UI 如实标注「正在准备，可稍后拖动」 | 仅兜底，非常态 |

**关键**：A 档覆盖库内多数条目 ⇒ **大多数播放应当零转码、零等待、可随意拖动**。

### 3.2 倍速：改用浏览器原生 `playbackRate`

- 前提：源可 seek（A/B 档都满足）。
- 做法：撤销 `VideoPlayer.tsx:810` 对 `/stream` 强制 `playbackRate = 1` 的分支；倍速一律交浏览器（音高由浏览器保持）。
- **收益**：删除整个 FRC 变体机制 ⇒ 缓存条目从「每倍速一份」降为「每条目一份」，容量压力降约一个数量级（F1/F2 消失），改倍速**不再重转、不再重缓冲**。
- **待验证**：浏览器在 4x 下的丢帧是否可接受（须实测，见 §4）。

### 3.3 帧率保真（修「一顿一顿」的直接来源）

- **禁止把 60fps 源降到 30fps**。输出帧率必须满足：`源帧率`（保真）**或** `刷新率的整除因子`（60 → 60/30/20/15）。
- 具体规则：
  - 源 ≤ 刷新率 ⇒ **原样保留**（60fps 源 → 60fps 输出）；
  - 源 > 刷新率 ⇒ 降到不超过刷新率的最大整除数；
  - **24fps 源在 60 Hz 上的 3:2 pulldown 是物理事实**，不由转码引入，但**不应再被 `-fpsmax 30` 破坏**（24 → 30 的上采样同样产生抖动）。
- 影响面：`encode_profile`（`routes.rs:4234`）的 `fps` 硬编码，与 BUG-289 同源。

### 3.4 缓存与孤儿（让产物「存在且留得住」）

1. **产物粒度**：每条目一份（3.2 之后不再需要每倍速变体）。
2. **预算**：默认 2 GiB 对「每条目一份」已足够；须在设置面暴露（`PD-T03` 已规划）。
3. **孤儿回收**：`.part` 必须纳入清理（按 mtime 阈值），当前 `enforce_proxy_budget` 明确跳过它们（F3）。
4. **1x 也持久化**：删除 `routes.rs:4854` 的 `speed_hundredths.is_none()` 短路，使 1x 断线后同样转完落盘（F4）。

## 4. 判据与反向证伪（决定 A 档能否成立的 A/B）

> **这是本文最重要的一节。** §3.1 的 A 档（直解）能否成立，取决于一个**可证伪的实验**，不能靠推理。

**实验设计**（每项必须能**反向证伪**，即「喂错条件必须 FAIL」）：

| # | 判据 | 手段 | 反向证伪（必 FAIL） |
|---|---|---|---|
| **PB-P1** | H.264 源**直解**（`/raw` + `playbackRate`）的**帧间隔抖动**不劣于 stream 代理 | `requestVideoFrameCallback` 采集帧间隔 + `getVideoPlaybackQuality()`；`BROWSER=msedge`（AGENTS.md §D6） | 把 src 换成 HEVC `/raw` ⇒ 抖动必显著劣化 |
| **PB-P2** | H.264 源直解的**有效倍速** `ΔcurrentTime/(Δt×playbackRate) ≥ 0.9`（1x/2x/4x） | 同 `decodeHealth.ts` 主判据 | 指向不存在的地址 ⇒ 必须报错，不得报「正常」 |
| **PB-P3** | HEVC 源（472/673）直解的**有效倍速 < 0.9** ⇒ 证明 B 档必要 | 同上 | 若 HEVC 直解也 ≥0.9 ⇒ **A 档应扩展到 HEVC**，B 档可取消 |
| **PB-P4** | 60fps 源输出 60fps 后，**帧间隔分布**优于输出 30fps | 同一素材两种档位对比 | 若两者无差 ⇒ 本判据不成立，须登记并停止引用 |
| **PB-P5** | 改倍速**不再触发**新转码（`x-orig-stream` 恒非 `live`） | 观察响应头 + 日志无新 `proxy ready` | 若改倍速仍 spawn ffmpeg ⇒ 3.2 未落地 |

**硬约束**：判据必须在**真实 Tauri/WebView2** 中跑（`docs/bugs/BUG-219.md` 已记录：headless 基准不可用）。
**PB-P3 是分水岭**：它决定 B 档是「必要」还是「多余」。

## 6. 待拍板（2 条）

### D1. 播放路径的根本形态：直解优先（按编码类别分流），还是维持 stream-first？

- **问题**: 播放主路径是否改为「**能直解就直解，不能直解才预转码**」，即把编码器移出播放路径？
- **现状与代价**: 现状为 **stream-first**（BUG-230，2026-10-09）：**每一个视频都转码**。代价已实测 —— 库内多数条目是 H.264（§1.3），**本可零转码直解**，却被转码；由此长出 FRC 变体缓存（`472` 单条目 7 变体 ≈1.4 GB）、预算逐出（F1/F2）、`.part` 孤儿（F3）、1x 进度丢弃（F4）。**1x 下编码器有 4.9× 余量，却仍把编码器放在关键路径上。**
- **设计锚点**: `docs/design/playback-delivery-optimal-2026-10-13.md` §2.1（两轴判据）/ §3.1（三档路由）/ §1.3（源编码分布）；被补前提的裁定见 `docs/bugs/BUG-230.md`
  - 冲突: **与 BUG-230 的「一律 stream-first」表述冲突**。处置见 §2.3 —— 补前提（编码类别），不改写该档正文；若裁定为 A，须在 `docs/bugs/BUG-230.md` **追加**「后续复核」节，**不翻状态**。
- **请求**: 选 A（我的建议）还是 B？

**A. 直解优先 + 编码类别闸门（推荐）**
- 涉及: `tauri-shell/src/components/media/VideoPlayer.tsx`（路由逻辑）、`download-engine/crates/orig-tg/src/routes.rs`（探测与预转码）、`store.rs`（编码字段）
- 量化: 1 个探测点 + 1 个路由分支 + 1 份预转码产物；**库内多数条目转为零转码**
- 回归风险: **中** —— 需先由 `PBD-T01` 确认 A 档覆盖范围；若 PB-P3 证明 HEVC 直解也可行，则风险降为低。**须保留 C 档兜底**，不得一次性拆除 stream 路径
- 后果: 大多数播放**零等待、可任意拖动、可随意改倍速**；缓存压力降约一个数量级。可逆（保留兜底路径）

**B. 维持 stream-first，只修性能细节**
- 涉及: 仅 `routes.rs`（帧率保真 + 孤儿 + 1x 持久化）
- 量化: 3 处改动，0 新增模块
- 回归风险: **低**
- 后果: 「一顿一顿」可缓解（§3.3 帧率保真），但**编码器仍在关键路径上**、FRC 缓存仍在膨胀、改倍速仍重转。用户已明确否定的正是这个方向

**C. 不做（维持现状）**
- 涉及: 无
- 量化: 0 改动
- 回归风险: 无新增
- 后果: 用户已实测「全都卡，一顿一顿」。按 §1 的读数，**投递与编码都不是瓶颈**，继续在投递侧找原因将无法收敛

### D2. 倍速实现：浏览器原生 `playbackRate`，还是保留服务端 FRC 变体？

- **问题**: 改倍速时，是**让浏览器自己重定时**（原生 `playbackRate`），还是**继续由服务端为每个倍速预生成变体**？
- **现状与代价**: 现状为服务端 FRC 变体，且 `VideoPlayer.tsx:810` **强制 `playbackRate = 1`**。代价：每个倍速一整部视频（`472` 7 变体 ≈1.4 GB），直接撑爆 2 GiB 预算并触发逐出（F1/F2）；改倍速 = 新转码 + 重新缓冲。**而原生 `playbackRate` 是浏览器免费提供的**，前提仅是源可 seek。
- **设计锚点**: `docs/design/playback-delivery-optimal-2026-10-13.md` §3.2（原生倍速）；受影响的既有条款见 `docs/design/product-direction-and-ffmpeg-2026-10-09.md` §2.5.7 ④
  - 冲突: 与 `docs/design/product-direction-and-ffmpeg-2026-10-09.md` §2.5.7 ④「输出仍为 CFR 30fps H.264（BUG-230 stream-first 裁定）」相关 —— **若 D1 选 A，该条须同步修订**（走该文 `## 变更记录` 追加，不改写正文）。
- **请求**: 选 A（我的建议）还是 B？

**A. 原生 `playbackRate`（推荐）**
- 涉及: `tauri-shell/src/components/media/VideoPlayer.tsx:810`、`:649`–`:712`；`download-engine/crates/orig-tg/src/routes.rs` 的 FRC 分支（保留兜底）
- 量化: 前端 2 处改动；**缓存条目数下降约一个数量级**
- 回归风险: **中** —— 4x 下浏览器丢帧率须实测（PB-P4）；音高保持依赖浏览器实现
- 后果: 改倍速**即时生效、零转码、零重缓冲**；FRC 变体缓存可停用。可逆

**B. 保留 FRC 变体，仅调大缓存预算**
- 涉及: `download-engine/crates/orig-tg/src/routes.rs:4917`（`ORIG_TG_PROXY_MAX_BYTES` 默认值）
- 量化: 1 个常量
- 回归风险: **低**
- 后果: 只是把逐出推迟（磁盘换时间）。`472` 一类条目的 7 个变体合计 ≈1.4 GB ⇒ 预算须开到数十 GB 才够，**结构问题不解**

**C. 不做（维持现状）**
- 涉及: 无
- 量化: 0 改动
- 回归风险: 无新增
- 后果: 每倍速一份产物持续膨胀（F1/F2 不解），改倍速持续重转重缓冲；`VideoPlayer.tsx:810` 继续把浏览器唯一免费的倍速机制关掉
