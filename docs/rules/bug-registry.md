# 细则：缺陷登记规格与门禁（`docs/bugs/README.md` 展开）

> **权威链**：本文件是缺陷**登记格式**与**门禁行为**的唯一真源。
> `docs/bugs/README.md` 只保留索引表与指向本文件的指针 —— 索引每轮必被 AI 读取，
> 规格说明只在「新建 / 修改登记」时按需加载。
>
> **判据真源**：门禁的**强制不变量**以 `scripts/check-bugs.py` 的模块 docstring 为准
> （脚本与规则同源，避免两处各说各话）。本文件解释「为什么」与「怎么用」。

## 一、登记文件规格

每个缺陷一个文件，命名 `BUG-<编号>.md`，编号自 `BUG-001` 起自增。

### 标准档（默认）

适用于**缺陷**（行为不符合预期、有根因需要定位）与**契约/架构类改动**。

```markdown
# BUG-<编号>: <一句话标题>

- 状态: open | in_progress | fixed | wontfix | closed
- 发现日期: YYYY-MM-DD
- 模块: engine | shell
- 严重程度: low | mid | high | critical

## 现象
<用户/测试观察到的现象>

## 根因
<定位到的代码位置与原因，附 file:line>

## 复现
<最小复现步骤 / 验证脚本>

## 修复
<改动摘要 + 验收方式>

## 关联
<相关 BUG / 提交 / 文档>

## 验收证据
<状态为 fixed/closed 时必需。必须含至少一条「跨机器可核验」的引用：
 入库路径（被 git 跟踪）或真实存在的提交短 hash。只写 verify_shots/ 引用
 换台机器无从复核，等于没有证据。>
```

### 轻量档（`fix` 类小改）

适用于**用户可见行为单一、无独立根因分析价值**的小改：
i18n 文案、常量、样式、拼写、单个 label、无逻辑分支的配置项。

**判据：无法在索引行一句话内说清根因的，不属于轻量档。**

```markdown
# BUG-<编号>: <一句话标题>

- 状态: fixed
- 发现日期: YYYY-MM-DD
- 模块: engine | shell
- 严重程度: low
- 档位: light

## 修复
<改了哪个文件、改成什么，一行。>

## 验收证据
<一条可核验引用：入库路径或提交 hash。>
```

> **轻量档不减履历**：编号照样唯一、照样进索引、照样被 `commit-msg` 引用、
> 照样带验收证据。减掉的只是「现象/根因/复现/关联」四段 ——
> 对 i18n 这类改动，这四段写出来只会是「某处缺键 → 没加 → 打开界面 → 无」的空话。
>
> **升档要求**：同一编号若在修复过程中发现需要根因分析（例如「缺键」背后是键名约定不一致），
> **必须就地升为标准档**，不得留在轻量档。

## 二、索引行规格（`docs/bugs/README.md`）

| 编号 | 标题 | 状态 | 模块 |
|---|---|---|---|
| BUG-007 | 内置分类标签不支持多语言设置 | fixed | shell |

强制要求（门禁逐条检查）：

1. **列数 ≥ 4**（`| 编号 | 标题 | 状态 | 模块 |`）。
   3 列会让 `parse_index_row` 返回 None，门禁报「有文件无索引行」——
   **症状与病因相距很远：看到「索引里没有对应行」先数列数，不要怀疑文件名。**
2. **标题列禁止裸 `|`**。例如写 `grep ffmpeg|transcode` 会把表格切碎，
   门禁取「倒数两列」时取到描述片段，报「状态与索引不一致」。
3. **状态列取值必须在枚举内**，且必须与文件内 `- 状态:` 一致。
4. **标题列不得内嵌完整根因分析。** 标题是**索引**，不是**报告** ——
   细则进 `BUG-<编号>.md`，索引行超出约 120 字符即视为塞错地方。
   实测教训：曾有索引行长达 878 字符（把整段根因贴进表格），
   使索引膨胀到 62KB 并在每次改动时产生大体积 diff，而信息与 BUG 文件完全重复。

## 三、门禁

```sh
python scripts/check-bugs.py     # 编号连续 / 索引双向一致 / 字段枚举 / 证据可核
bash scripts/install-hooks.sh    # 安装 pre-commit 与 commit-msg（钩子不入库）
```

- `check-bugs.py` 一次跑 **3.5~4 分钟**（逐条核 hash 与入库路径）。别用 2 分钟超时 ——
  超时会被 SIGTERM 且无输出，看着像「脚本挂了」，其实是没跑完。
- `fix` 类提交必须引用 `BUG-<编号>`，否则 `commit-msg` 拒绝 —— 让「绕过登记直接修」不可表达。

## 四、建档与改索引的操作要点

1. **建档前必须现查最新编号**，不能用 `ls | tail -N` 快照 —— 本仓有并行会话会同时建号。
   先跑 `python scripts/check-bugs.py` 取「N 条登记」，编号 = N+1。
2. **删整行就删整行，别用行内片段当锚点。** 用片段替换会把邻行截断/粘连，
   同时报「索引重复行」+「有文件无索引行」+「状态不一致」**三个看似无关的错**。
3. **`## 验收证据` 必须一字不差。** 写成 `## 验收判据` 会报「状态 fixed 但没有 `## 验收证据` 节」，
   并连带报「没有跨机器可核验的引用」（因为节没被识别）。
4. 每次改完索引，用一行 python 回读校验（列数、状态列、模块列），别只靠眼睛。

## 五、批量登记（同一提交关联合并多条时）

当一次提交关掉多条同类缺陷（例如一个批次修了 5 处 i18n 缺键），
**不要在索引里写 5 条互相重复的长行**。做法：

- 每条缺陷**仍各自有文件与索引行**（履历可查不减）；
- 但文件用**轻量档**，索引行标题保持一句话；
- 提交信息 body 一次列出全部编号。

### 批量提交模板

```
fix(shell): localise the media card kind badges and monitor labels

Closes: BUG-123, BUG-127, BUG-128
Files:
  - tauri-shell/src/components/media/MediaCard.tsx (kind signal, i18n labels)
  - tauri-shell/src/i18n/locales/{zh-CN,en-US}.json (badge + collapse keys)
Evidence: tauri-shell/verify/verify_card_kind_signal.cjs
```

- `check-commit-msgs.py` 用 `BUG_REF.search(body)` 判定 —— **body 里出现一个编号即通过**，
  因此多编号并列天然被支持，**门禁无需修改**（已实测确认）。
- `fix` 的 scope 取**改动面最大**的那一侧；混舱批次用 `fix(shell,engine)` 或拆两条提交。

> 这样「一个批次 = 一条提交 = N 条可追溯记录」，而不是「N 条提交 = N 次门禁 = N 次索引重写」。
> 实测教训：曾有单条 4 行的 i18n 修复独占一次提交，走完整套固定成本（登记 + 证据 + 索引 + 门禁）。

### 什么必须单独提交

批次化不得吞掉**需要独立审阅**的改动。以下一律单独成条：

- 涉及契约的改动（投递、迁移、删除联动）；
- 任何 `engine` 侧行为变更（Rust 改动回归面大）；
- 状态从 `open` 转 `fixed` 时**证据需要单独呈现**的缺陷。

> 判据：**审阅者需要单独看 diff 才能判断对错的，就不许合批。**
> 合批是为了省固定成本，不是为了把审阅单位搅浑。
