# 细则：决策项规格（可拍板 / Decidable）

> **权威链**：本文件是「什么算一个可拍板决策项」的唯一真源。
> `AGENTS.md` §8 保留**交付汇报**的四件事与三条铁律，**决策项的强制结构**（下述六字段）
> 以本文件为准。机器门禁为 `scripts/check-decisions.py`。
>
> **为什么需要它（缺陷根因）**：2026-09-22 的 `pending-decisions` 文档形式合规
> （每条都有「背景 / 我的建议 / 不拍板的后果」），但**实测 6 条决策的「选项列举」全部为 0** ——
> 只给了单一建议。后果是决策人「无逻辑性猜测、随机决策、结果不可预测」：
> 无选项 ⇒ 无差别可比；无量化 ⇒ 无判据；无后果预测 ⇒ 无法预判；无设计锚点 ⇒ 拍完脱离设计。
> **「给了建议」不等于「给了选择」。建议是替你决定，选择是让你决定。**

---

## 一、一个决策项 = 六段，缺一段即不可拍板

| 段 | 必须回答 | 缺失的后果 |
|---|---|---|
| **① 问题** | 一行说清要定的是什么。**写成问句**，不问「要不要做 X」这种含预设的问法，而问「X 与 Y 之间选哪个」 | 决策人不知道在定什么 |
| **② 现状与代价** | 现在是什么样、为什么现在必须定、**不定要付什么代价**（含时间/风险） | 无法判断该不该现在花时间 |
| **③ 选项对比** | **≥2 个实质选项 + 1 个「不做」选项**，逐个给出：具体改哪里（文件/表/端点/界面）、量化影响、回归风险 | 无差别可比 → 只能猜 |
| **④ 后果预测** | 每个选项**拍完之后会发生什么**：用户可见变化 + 对既有能力的影响 + 可逆性 | 结果不可预测 |
| **⑤ 设计锚点** | 该决策挂在**哪份设计文档的哪一条**（`docs/design/X.md` §N）；若与某条现设计冲突，**显式指出冲突** | 拍完脱离核心设计 |
| **⑥ 请求** | 要对方拍的**那一句**（「选 A 还是 B」「是否批准」「是否延后到何时」） | 只能回「你说呢」 |

### 硬性要求（机器门禁逐条检查）

1. **选项数 ≥2**（不含「不做」）。只有一个选项 = 没给选择，是**逼签**不是**决策**。
2. **必须含「不做 / 维持现状」选项**，并写明其后果。不给「不做」选项 = 隐性地把失败成本
   从决策人身上转移掉 —— 而「不做」常常是正确的选择。
3. **每个选项必须有 `涉及:` 字段**（具体文件/表/端点的仓内路径），且路径**必须真实存在**
   （或明确标注为「将新建」）。
4. **每个选项必须有 `量化:` 字段**：能给出数字就给数字（影响条目数 / 文件数 / 表数 /
   迁移次数 / 端点个数）；实在给不出就写**为什么给不出**（写「无法量化」而无论证 = 空字段）。
5. **每个选项必须有 `回归风险:` 字段**（低/中/高 + 一句话说明受影响的既有能力）。
6. **每个选项必须有 `后果:` 字段**（拍完会发生什么；可逆/不可逆）。
7. **必须有 `设计锚点:` 字段**，指向 `docs/` 下的真实文件；冲突要写 `冲突:`。
8. **必须有 `请求:` 字段**，且是**一句可回答的话**（以问号结尾或含「选」/「批准」/「延后」）。
9. **「不做」选项按 `涉及:` 的实质判定，不按标签措辞** —— 它的 `涉及:` 必须是
   「无 / 0 / 不改代码」。**标签写了「维持现状」但 `涉及:` 指向仓内文件 = 仍是实质量选项**，
   门禁不认。

> 第 9 条来自一次**真实假绿**（2026-09-23 反向证伪实测）：选项 B 命名为
> 「续编两集（维持现状的显式选择）」、`涉及: 无`，标签命中「维持现状」使旧门禁放行，
> 从而掩盖了「该决策没有真正的不做选项」。**措辞能骗过门禁，实质不能。**

> 字段用固定前缀（`涉及:` / `量化:` / `回归风险:` / `后果:`），是为了让门禁能解析、
> 让决策人能扫读。**前缀缺失 = 门禁视为字段不存在**（不是「格式小瑕疵」）。

## 二、决策项模板（照抄）

```markdown
### D1. <一行问题，写成选择问句>

- **问题**: <X 与 Y 之间选哪个？>
- **现状与代价**: <现在是什么样 → 为什么必须现在定 → 不定的代价（时间/风险）>
- **设计锚点**: `docs/design/<file>.md` §<N>（<该条怎么说>）
  - 冲突: <若与现设计冲突，写明冲突点；无则省略此行>
- **请求**: <选 A 还是 B？ / 是否批准？ / 是否延后到 <时点>？>

**选项**

**A. <选项名>**
- 涉及: `<path/a.rs>`、`<path/b.tsx>`
- 量化: <影响 N 条 / M 个文件 / 1 次迁移；或为什么无法量化>
- 回归风险: <低/中/高 — 受影响的既有能力>
- 后果: <拍完会发生什么；可逆性>

**B. <选项名>**
- 涉及: ...
- 量化: ...
- 回归风险: ...
- 后果: ...

**C. 不做（维持现状）**
- 涉及: 无
- 量化: 0
- 回归风险: 无新增（但既有问题保留）
- 后果: <该问题继续存在，具体表现是什么；什么情况下会被迫回头做>
```

## 三、反例与正例（都真实发生过）

### 反例（实测 6/6 条都长这样 —— 形式合规、实质不可拍板）

> ### D3. 「继续播放 / 最近播放」是否进 P0？
> - **背景**：这是 PRD 里唯一需要新增数据存储的需求。
> - **我的建议**：**做，且与「单集多视频」同期做**。理由：两者都在 episode 维度加字段。
> - **不拍板的后果**：PRD P0 范围不确定，R10 悬空。

**为什么不可拍板**：只有「建议」没有选项 → 决策人只能选「同意」或「不同意」，
而不同意的理由是什么、不同意之后什么方案会顶上，文档里没有。**这是逼签，不是决策。**

### 正例（同一件事）

> ### D3. 续播与最近播放：进 P0，还是延后？
> - **问题**: 续播（R10）与「单集多视频」一起做，还是单独排期？
> - **现状与代价**: R10 是 PRD 里唯一需新增存储的需求（`media_episode` 加 2 列：
>   `play_pos_ms`、`last_played_at`）。不定 → PRD P0 边界不明，R10 悬空，
>   且 implementation-plan 无法收口。
> - **设计锚点**: `docs/design/media-library-management-prd-2026-09-22.md` R10
> - **请求**: 选 A 还是 B？
>
> **A. 与「单集多视频」同期做**
> - 涉及: `download-engine/crates/orig-core/src/media.rs`（迁移 +2 列）、
>   `tauri-shell/src/components/media/`（续播入口）
> - 量化: 1 次迁移覆盖 2 列（而非分 2 次各 1 列）；影响 3 个组件
> - 回归风险: 低 — 纯增量列，无既有字段语义变更
> - 后果: P0 变大；播放器需同步改，得一次性做完。可逆（列可留空不用）
>
> **B. 单独排期，先不做**
> - 涉及: 无（推后）
> - 量化: 0 改动；后续单独 1 次迁移 + 3 组件
> - 回归风险: 无新增
> - 后果: 看长视频无法续播；将来做时 episode 表要**再改一次**
>
> **C. 不做**
> - 量化: 0
> - 后果: PRD R10 永久悬空；用户每次看剧从头开始。若用户实际抱怨续播缺失，
>   会被迫回头做，且届时仍要付一次迁移成本。

**为什么可拍板**：A/B/C 三选一，每条的代价、可逆性、量化影响都摆在桌上。
决策人不需要理解代码细节也能选 —— **选择应当只需要判断取舍，不需要补充信息。**

## 四、与「工程师自决」的界线（防止把该自己定的抛回来）

- **方案/模式选择 = 待拍板**（本文件规格）。
- **方案内的执行细节 = 工程师自决**，不得回抛（用户口径：「目的已定 ⇒ 结论已定」）。
- 判据：**如果选项之间的差别不影响用户体验、不影响数据模型、不影响既有能力，
  那它就不是待拍板项** —— 自己定，在提交信息里说明即可。

> 反例（应自决却回抛）：「third_party 是否需要 tracked」——
> 它的答案由既有约定唯一确定，属于应结论而未结论。

## 五、一次交付的待拍板项上限

- 一次**不超过 3 条**（AGENTS.md §8），按「挡住用户使用」优先排序。
- 超出的写进 `docs/review/` 的决策清单（本规格），**不塞进当次汇报**。
- 同一次汇报里的决策项若**互相依赖**，必须显式写出依赖顺序
  （例：「D2 依赖 D1 的结论」），否则决策人会以错误顺序决定。

## 六、门禁

```sh
python scripts/check-decisions.py            # 校验 docs/review/ 下所有决策清单
python scripts/verify_decision_spec.py       # 反向证伪：缺字段必须 FAIL
```

- 门禁解析 `### D<n>.` 开头的决策块，逐条核对第一节的 8 条硬性要求。
- **空字段 = 字段不存在**（`涉及: ` 后面没内容 → FAIL）。
- 路径类字段会做存在性抽查（标「将新建」的除外）。
