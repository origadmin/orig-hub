| 取证点 | 方法 | 结果 |
|---|---|---|
| 媒体库内容构成 | `GET /api/media/items?limit=200` | **115 条 = 85 video + 30 photo**，全部平铺在 `media_item` 单表 |

| 图片字节来源 | `media_item_raw` 源码 | `file_path` 为空时现场调 `client.thumb(chat,msg)` 代理 **TG 缩略图**（非原图），失败则 404 |
| 前端分流逻辑 | `MediaViewer.tsx` | **已有** `modeOf(kind)`：photo→browse，video/audio→play；`toViewerItem` 也确实传了 `kind` |
| 按钮语义 | `TgPanel.tsx:1885-1915` | 同一按钮**按内容类型变文案**：含视频→「缓存」（落盘+入库）；纯图/单图→「加入媒体库」（**只入库、不落盘**） |

把责任归给"分流逻辑缺失"会修错地方。

## 2. 问题清单（按严重程度）

### P0

**P0-1 在线流零背压（架构视角）**
- 现象：未缓存内容在线播放卡顿/卡死。
- 根因：`media_file()`（`/api/tg/file/:chat/:msg`）直接 `Body::from_stream` 透传，`DELIVERY_BUDGET_FACTOR` / `DELIVERY_FALLBACK_BPS` 只在 `serve_local_file` 生效。BUG-033 只修了本地文件那条路径。
- 影响：所有未缓存内容的播放。缓冲区无界增长 → 浏览器读满即 abort → 同一区域反复重取。

**P0-2 加入媒体库后离线打不开（用户视角）**
- 用户遇到：点了「加入媒体库」，断网后打不开。
- 用户以为：进了我的库 = 在我电脑上。
- 实际：只有索引，字节还在 Telegram（图片路径甚至为 NULL）。
- 根因：`media_item` **没有"字节状态"字段**，编目与落盘被压成同一个动作。

**P0-3 入库与落盘行为不一致**
- 现象：同样操作，26 条图片有本地文件、4 条没有。
- 根因：两条写入路径（worker 缓存 / 手动入库）对"是否落盘"的实现不同。
- 影响：行为不可预期，且内容域直接调用传输域 `client.thumb()`（**越界**）。

**P0-4 单集多视频：结构已有，缺质量与主版本语义**（2026-09-22 更正）
- ~~根因：`media_episode.item_id` 是 1:1 外键，缺"集 → 资产"的一对多中间层~~ ——
  **此判读错误**：只看 `media_episode.item_id` 是 1:1，忽略了已存在的 `media_episode_source`。
  「主入口 1:1」不等于「整模型 1:1」。
- **真实缺口**：① 无质量字段（无码率、无 `quality`），多源的**高低质量无法表达**；
  ② 主源是隐式的 `media_episode.item_id`，**无 `is_primary`**；
  ③ 排序只按 `created_at` → **先来的是主**，与质量无关；
  ④ UI 只有一个「N 源」按钮，**盲目把 `sources[0]` 提为主**，用户看不到质量也无从选择。
- 用户诉求（2026-09-22）：单集多视频**是需求，必须实现**；多个源有高低质量之分，
  **必须有且仅有一个主版本**。详见 BUG-113 与 `docs/design/episode-multi-source-design-2026-09-22.md`。

**P0-5 点图片进入视频播放器**
- 根因（重述）：**不是分流缺失**，是"封面（展示物）"与"内容（播放物）"在视觉与层级上未分离 —— 网格里视频条目和图片条目都只呈现一张缩略图，点击前无类型信号。
- 影响：核心浏览路径错位。

### P1

**P1-6 封面与内容同级**：`poster` 与 `file_path` 并列，封面更新/失效/误删策略无法定义。
**P1-7 图片大图是缩略图**：`file_path` 为空时代理 TG 缩略图，画质受限，"查看原图"无入口。
**P1-8 图片无归属层级**：无法表达"某一集下的某个视频的图片"，详情页图集/按集清理做不到。
**P1-9 「编辑」与「改名」割裂**：实现视角的拆分，改标题要找两个地方。

### P2

**P2-10 按钮语义重叠**：两个动作被做成"按类型变文案"的假并列。
**P2-11 无转码/remux**：无专有编解码器的 Chromium 播不了 HEVC/MKV（与 BUG-034 相关）。

## 3. 专题一：按钮语义 —— 定案：用户可见一个动作，内部仍是两个正交模块

> **用户已拍板（2026-09-22）**：本产品是**下载工具**，缓存的目的就是**流畅的本地播放**。
>
> **用户同日追加澄清（关键，修正了本文档的一处过度外推）**：
> 「视频、图片、内容**有先后**，原本分离式是为了让**两个模块各自工作、不互相影响**。」

### 先纠正本文档此前的一处过度外推

原方案是「拆成两个正交动作」。本文档一度写成「**合并为一个动作**」——
**这个表述把架构层的解耦也一起否掉了，属于过度外推**，现更正。

正确的区分是**两个层次，不要混为一谈**：

| 层次 | 结论 |
|---|---|
| **产品语义层**（用户看到什么） | **一个动作**：「缓存到媒体库」。用户不必理解内部有几步 |
| **实现结构层**（模块怎么分） | **仍是两个正交模块**：内容域（编目）与传输域（落盘）**各自工作、互不影响**，由**编排层按序驱动** |

「取消只入库、不落盘」的**准确含义**是：取消**用户可见的那个终态**「已入库、却永不落盘」——
**不是**取消两个模块的分离。这两件事此前被本文档混为一谈。

### 为什么解耦必须保留（用户给出的理由）

- **有先后**：先**编目**（知道「这是什么」），再**落盘**（决定「字节放哪」）。
  视频与图片的落盘时机、策略可以不同 —— 这需要**编排**，不是**合并**。
- **互不影响**：落盘失败**不毁编目**（条目仍在库里，可重试落盘）；
  编目也不需要知道字节从哪来（TG / 本地 / 将来其它通道）。
- 两个模块可**独立测试、独立演进**。

### 于是定案是

- 用户点一次「缓存到媒体库」→ 编排层按序驱动：**编目 → 落盘 → 置 `byte_state=cached`**；
- **取消「只入库、不落盘」这个用户可见终态** —— 它是 P0-2（离线打不开）、
  P0-3（行为不一致）、P1-7（大图是缩略图）三个问题的**共同源头**；
- **图片同样落盘**：离线优先下"只能看 TG 缩略图"毫无价值；
- **落盘失败**：编目**保留**，标 `absent` 并给**显式重试入口**，
  **不得静默降级为「仅入库」**（静默降级就是当前 P0-2 的成因）。

### 最终按钮定义

| 状态 | 呈现 | 含义 |
|---|---|---|
| 未缓存 | **缓存到媒体库** | 落盘 + 入库，一步完成 |
| 缓存中 | 进度 + 取消 | 进行中，进度可见 |
| 已缓存 | 「已缓存」+ 播放入口 | **不再有第二个按钮** |
| 缓存失败 | **重试**（显式） | 失败必须可见，**不得静默降级为"仅入库"** |

### 对其它部分的连带影响

- **数据模型**：字节状态的**常态是「已落盘」**；「无字节 / 部分」是
  **异常或过渡态**，UI 必须能解释且能重试，不能当作一种合法的"已入库"状态。
  - **命名与归口以 BUG-098 的 `asset_state` 为准**（`pending` / `ready` / `missing` / `remote`），
    本节此前用的 `byte_state` 是同一件事的临时叫法，**不要另造第二套字段**。
  - ⚠️ **一处必须对齐**：BUG-098 把 **`remote`（按需取）定为 photo 常态**，
    这与 2026-09-22 的离线优先拍板（**图片同样落盘**）**相悖**。
    正确语义：**`ready` 是常态（video 与 photo 一视同仁）**；`remote` 只在用户
    **显式选择「仅云端」**时出现且必须显式标记 + 一键补下载。
    照原规划实施会把图片做成「永远不落盘」，等于**把缺陷固化进新状态机**。
- **播放链路**：播放**默认走 Local**（有背压那条）。`Remote` 只在"尚未落盘"时出现，
  属**过渡态兜底**，不是主流路径 —— 故 S0 的 Remote 背压仍要做，但定位是兜底而非主流。
- **存量数据**：30 条 photo 里 4 条 `file_path` 为 NULL 属历史脏数据，
  需补落盘或显式标 `absent` 并允许重试（见路线 S0.5）。

## 4. 专题二：功能定位与播放性能

### 定位结论

**媒体库是独立核心模块（内容资产权威层）；Telegram 是它的一个可替换采集/传输通道。**

- 播放、浏览、检索、离线、编辑这些用户价值全部发生在媒体库；Telegram 只在"字节从哪来"一点上提供服务。
- 数据反证：115 条已能脱离 Telegram 独立存在，断网后媒体库仍须可用。
- 由此推出硬要求：媒体库条目必须显式带**来源**与**本地化状态**（仅索引 / 已落盘 / 源失效）。缺这两个字段，"离线打不开"在 UI 上永远无法解释。

### 播放链路：统一投递契约

当前两条路径**契约不一致**（本地有背压、在线没有）。应统一为：

```
DeliverySource::Local{path} | Remote{chat,msg}
        ↓ 单一入口
deliver(source, range) -> (stream, size, mime)
        ↓ 两条路都过同一个
throttle(reader, budget)
```

- **背压**：`budget = bitrate × 6.0`，无码率回落 16MiB/s；Remote 额外加**有界预读缓冲**（约 32MiB）反压 grammers。
  *假设：grammers 拉取速度显著高于播放码率，故 Remote 必须有界缓冲。*
- **Range**：Local 支持 `bytes=`；Remote 走 `parallel_range_stream`（BUG-028 既有要求），不支持 Range 的源声明 size 未知并禁 seek。
- **MIME**：由扩展名/内容探测决定，不透传 TG 的 mime；未知则 `application/octet-stream` 且前端禁播。
- **预加载**：Local 填满 budget；Remote 并发预取首尾两个分片。

### 卡顿排查顺序（按此顺序，不要跳步）

1. **能否解码** —— 判据必须是 `videoWidth`，不是 `readyState`（BUG-034）。若 `videoWidth=0`，瓶颈在**编解码**而非传输，修传输是白费。
2. **budget 算错** —— `bitrate` 缺失导致回落到 16MiB/s 兜底值，对高码率源等于没节流。
3. **Remote 是否走分片并行 + 有界缓冲**（当前：**没有**，见 P0-1）。
4. **磁盘 IO / RTT**。
5. **状态不一致** —— `byte_state=cached` 但 `file_path` 为空，实际没命中 Local（当前 4 条 photo 正是此类）。

> 本项目已有零依赖诊断工具：`tauri-shell/verify/` 下的
> `diag_playback_smooth.cjs`（上屏帧账，须用 `requestVideoFrameCallback`）、
> `diag_rate_storm.cjs`（逐请求字节账）、`probe_mp4_codec.py`（轨道/codec 探测）。
> 涉编码的判断必须用 `BROWSER=msedge`（Playwright 自带 Chromium 无专有编解码器）。

## 5. 专题三：数据模型与交互设计

### 「编辑」vs「改名」：**不合理，应合并**

这是**实现视角**（改元数据 vs 改标题字段），不是用户视角（"我要改这条内容的信息"）。

改进：合并为单一「编辑」面板，标题是其中一个字段；保留双击标题 / 右键重命名作为**快捷方式**，
但两个入口写同一份数据、同一套校验。改名不该是"另一种操作"。

### 图片到底是"内容"还是"附件"：按来源判定

两个角色在此处结论不同，裁决如下 —— **两类图片都要支持，按来源判定归属**：

| 图片类型 | 归属 | 判定依据 |
|---|---|---|
| **内容型**（图集） | `media_asset(kind=photo)`，挂 `episode` | 在 Telegram 里**独立成组**发送的图片 |
| **展示型**（封面） | `media_attachment(role=poster)`，挂 series / episode / asset | 视频或剧集的封面，**不是内容**，不进内容列表、不占条目计数 |

这同时回应用户提出的"合理归属应为某一集下的某个视频"：
与视频**同组发送**的图片 → 归于该视频的附件（`attachment.owner=asset`）。

### 视觉区分（解决"以为点图片、实际进播放器"）

- **视频卡片**：右下**时长角标** + 居中播放三角 + 类型徽标「视频」。
- **图片卡片**：左上**张数徽标**（如「9 张」）+ 徽标「图片」，**无时长、无播放图标**。
- 任何"只用一张缩略图代表条目"的设计都会复现这个缺陷 —— 这是**交互层**的硬约束。
- 点击行为：图片 → 灯箱看图器（切换/缩放/查看原图）；视频/音频 → 播放器。

## 6. 专题四：层级结构缺失

### 现状

```
media_series ──< media_episode(item_id) ──> media_item      ← 主源，1:1
                    │
                    └──< media_episode_source(item_id) ──> media_item   ← 备用源，1:N
```

`media_episode` 本质是 `(series_id, item_id)` 的桥接表，**主源只能挂一个 item**；
但 `media_episode_source`（BUG-039）已经提供了**同槽多来源**，所以：

- ~~"单集多视频"是**数据模型上不可能**~~ —— **此结论错误，2026-09-22 更正**。
- 真实状态：**结构已能容纳多源，但表达不了「哪个质量高、哪个是主」**。
  质量维度缺失 + 主版本隐式 + 排序按创建时间 + UI 盲目切主 = 用户要的能力**没有真正落地**。
- 详见 BUG-113。

### 重新设计的核心数据模型

四层：**series → episode → asset → file / attachment**

```sql
-- "是什么"（元数据，不含字节位置）
media_asset(id, episode_id NULL, kind, ref, source, title,
            duration, width, height, added_at, role, sort_order)

-- "字节在哪"（与元数据分离，支撑一资产多版本/多码率）
media_asset_file(id, asset_id FK, role: primary|variant,
                 file_path NULL, byte_state: absent|partial|cached,
                 bitrate, size, checksum)

-- "图在哪"（封面与内容分离）
media_attachment(id, owner_type: series|episode|asset, owner_id,
                 role: poster|gallery|thumb, source: local|tg,
                 tg_chat, tg_msg, file_path NULL, sort_order)

-- Telegram 定位（可据此重建字节）
media_source_ref(asset_id, chat, msg_id, ...)

-- 去掉 item_id
media_episode(id, series_id, season, episode_no, title)
```

**切分理由**：把「是什么」（asset）、「字节在哪」（asset_file）、「图在哪」（attachment）
三者分离。一集多视频 = episode 下多行 asset；图片归属 = `attachment.owner_type/owner_id`；
封面与内容分离 = poster 只存在于 attachment，不再与 `file_path` 同级。

### 迁移路径（旧表不动，双读过渡）

1. 建新表，旧表保留为 `*_legacy`；
2. `media_item` kind=video → `media_asset`（经 `media_episode` 反查 series_id）+ `media_asset_file`（`file_path` 非空→`cached`，NULL→`absent`）；
3. `media_item` kind=photo → 按来源判定：独立成组→`asset(kind=photo)`；同组→`attachment(role=gallery, owner=asset)`；
   *假设：photo 的 `ref` 可解析出 chat/msg*；
4. `media_series.poster` / `media_item.poster` → `attachment(role=poster)` 并回填 owner；
5. 读路径新表优先、缺失回落旧表，观察一个版本后下线；老 `episode.item_id` 保留为 asset 别名，UI 不必一次性改。

## 7. 模块边界

- **传输域**（`grammers.rs` / orig-tg）：只负责"给定 (chat,msg) 产出字节流 + 元信息（size/mime/duration/width/height）"。**不写库、不决定落盘。**
- **内容域**（`media.rs`）：持有元数据层级与归属、持有"字节位置"（`file_path` + `byte_state`），决定何时落盘、何时清理。
- **缓存 vs 入库**：入库 = 写元数据（**编目**）；缓存 = 写字节并置 `byte_state=cached`（**落盘**）。
  两者是**两个正交模块**，由**编排层按序驱动**（编目 → 落盘）。
  - **产品语义上**：默认「入库即落盘」，一次点击完成两件事（用户不需要理解内部两步）。
  - **结构上**：两者**互不依赖** —— 落盘失败**不毁编目**（条目保留、标 `absent`、可重试），
    编目也不需要知道字节从哪来。**这正是用户要保留的解耦收益**。
  - ~~「缓存是入库的可选增强，不是前置条件」~~ —— 此句在 2026-09-22 拍板下**已不成立**：
    默认编排是两者都做；但**做两件事 ≠ 揉成一个模块**。
- **铁律**：内容域不 import grammers 类型；传输域不 import 表结构。
  当前 `media_item_raw` 现场调 `st.client.thumb()` 属**越界**，应改为内容域只返回 attachment 定位，由路由层调传输域代理。

## 8. 分阶段改造路线

| 阶段 | 交付物 | 优先级理由 | 回归风险 |
|---|---|---|---|
| **S0**（P0）统一投递契约 + Remote 背压 | `delivery` 模块、throttle 复用、Remote 接入 `parallel_range_stream` | 直接修用户可感知的卡顿，**不碰数据模型**，可独立先行 | Remote seek 行为变化；Local 节流回归（确认 factor 未改）；冒烟断言必须用 `videoWidth` |
| **S0.5**（P0）存量补落盘 + 禁止空路径入库 | 补 4 条 NULL `file_path` 的 photo；写入路径加校验，禁止产生"已入库却无字节"的记录 | 离线优先下这类记录就是脏数据，且是 P0-2/P0-3 的直接成因 | 补下载失败须保留 `absent` 并给重试入口，不得静默成功 |
| **S1**（P0）数据模型落地 | 建表 SQL、backfill、legacy 双读 | S2/S3 的地基 | photo 挂错 owner（先挂 series 再校正）；新旧重复展示，需以 `source+ref` 去重 |
| **S2**（P1）读路径切换 + 一集多视频 | 层级化 API、UI 支持集内多 asset | 交付 BUG-113（质量维度 + 主版本） | 分页/计数口径变化；`episode.item_id` 别名失效 |
| **S3**（P1）封面/图片外置 + 按钮语义修正 | poster 迁移、thumb 代理上移到路由层、按钮拆为「入库」+「下载」 | 收口 P0-2 / P0-3 / P0-5 / P1-6 | 迁移期 poster 空窗（回落旧字段）；4 条 NULL `file_path` 的 photo 需补字节或显式标 `absent` 并允许现场代理 |
| **S4**（P2）按需 remux 评估 | 能力探测（容器/编码可播性），**非**全量转码 | 仅在 S0 之后仍"下完却播不了"时启动 | CPU/磁盘成本，先探测再决定 |

**依赖**：S0 可独立先行；S1 → S2 → S3 线性；S4 依赖 S0 结论。
