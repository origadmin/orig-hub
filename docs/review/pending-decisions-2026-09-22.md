## 一、待拍板（2 项）

### D1. 合并/加入剧集遇到「两边都有第 1 集」：归为同集多源，还是续编两集？

- **问题**: 同一集内容的多个版本，是聚成「一集多源」，还是各占一个集号排到末尾？
- **现状与代价**: 当前实现**续编到末尾** —— `download-engine/crates/orig-tg/src/media.rs:1985`
  的区间冲突分支回退到「最大终点之后」，于是同一集被拆成两集。
  **实测已发生**：同一片源的 14 个版本在真实库里被存成 14 集
  （`episode-multi-source-design-2026-09-22.md` §0.4）。
  不定 → BUG-103 的正修与 BUG-113（多源 + 主版本）都无法收口，多源机制永远用不上。
- **设计锚点**: `docs/design/episode-multi-source-design-2026-09-22.md` §4.5 D1
  （该节判定 A 为建议；§6.4 新增 `POST /api/media/episodes/:id/merge-sources` 为其落地接口）
  - 冲突: `docs/bugs/BUG-103.md` 的待拍板与本项是**同一个问题**，拍完须回写该 BUG。
- **请求**: 选 A 还是 B？

**A. 同槽归并为多源**

- 涉及: `download-engine/crates/orig-tg/src/media.rs`（`append_episodes_ranged` 冲突分支 +
  `merge_series` 槽位分配）、`download-engine/crates/orig-tg/src/routes.rs`、
  `tauri-shell/src/components/media/SeriesDetail.tsx`（来源面板）
- 量化: 改 1 处核心分支（`media.rs:1985`）+ 1 处合并分支（`media.rs:1661`）；
  影响 2 个端点（`merge-sources` 新增、`series/:id` 响应加 `suspectedDuplicates`）；1 张表加列
- 回归风险: 中 — 需「是否同一集」判定，误判会把**两集并成一集**（丢掉一个集号）。
  由 L1 身份键（实测 50% 命中）+ L3 提示用户确认兜住
- 后果: 14 集那种重复消失，一集能看到多个版本并可切主；连播不再重复同一内容。
  **可逆**（拆回多集是纯数据操作）

**B. 续编两集（维持现状的显式选择）**

- 涉及: 无（不改代码，仅把该行为写成明确产品语义）
- 量化: 0 改动
- 回归风险: 无新增
- 后果: 同一内容在剧集里出现多次（实测 14 集），连播必然重复；备用源机制在合并场景
  永远用不上，BUG-113 的多源+主版本无意义。可逆，但用户会持续看到重复集

**C. 不做（不拍板，维持悬空）**

- 涉及: 无
- 量化: 0
- 回归风险: 无新增（但 BUG-103 / BUG-113 继续 blocking）
- 后果: 重复集继续累积；多源设计整份文档的 P1 部分无法开工，等于白写。若日后用户抱怨
  「为什么同一集出现两遍」，会被迫回头做，届时仍要付同样的判定成本

### D2. 续播 / 最近播放：立为需求，还是确认不做（当前无用户证据）？

- **问题**: R10（播放进度 + 最近播放）是否立项？若立，与「单集多视频」同期还是单独排期？
- **现状与代价**: 全库**无播放进度概念**（`MediaViewer.tsx` 无进度持久化；
  `localStorage` 仅存播放器设置/历史目录/账号）。
  **关键事实：该项无任何用户证据** —— 你于 2026-09-22 明确指出
  「最近播放好像不是我提出的功能需求」，PRD 已将其从 P0 移入 §4.2 提案区
  （`media-library-management-prd-2026-09-22.md` §6 Q1、§4.2）。
  不定 → PRD 提案区边界不清，且若日后要做，`media_episode` 需**再迁一次**。
- **设计锚点**: `docs/design/media-library-management-prd-2026-09-22.md` §4.2 提案区 R10 +
  §6 Q1（该节要求「若用户认为需要，再单独立项；**不因离线优先默认它该做**」）
  - 冲突: 旧 `pending-decisions` 把它写成「P0 悬空」，与 PRD 现行结论
    （已移出 P0、无证据）**直接矛盾** —— 本项按 PRD 为准。
- **请求**: 选 A 还是 B（还是 C？）

**A. 立项并与「单集多视频」同期做**

- 涉及: `download-engine/crates/orig-tg/src/media.rs`（`media_episode` 加 2 列：
  `play_pos_ms`、`last_played_at`）、`tauri-shell/src/components/media/`（续播入口）
- 量化: 1 次迁移覆盖 2 列（而非分 2 次各 1 列）；影响 3 个前端组件
- 回归风险: 低 — 纯增量列，无既有字段语义变更
- 后果: P0 变大；播放器须同步改，得一次性做完。可逆（列可留空不用）

**B. 确认为「不做」（关闭提案）**

- 涉及: 无
- 量化: 0 改动；PRD §4.2 的 R10 标记为「已否决」
- 回归风险: 无
- 后果: 看长视频无法续播、看不到最近播放。**这是当前无证据下的诚实默认**；
  若日后真需要，届时仍要付一次迁移成本（且**不保证**当时表结构还适合加列）

**C. 不做（不拍板，维持提案区悬空）**

- 涉及: 无
- 量化: 0
- 回归风险: 无新增
- 后果: PRD 长期挂一条无证据提案，团队每次都可能在「要不要顺手做」上重复讨论；
  参考本项目的历史教训 —— 无证据提案被端上台面要求拍板，正是本清单上一版被批评的形态

### ✓ 「用户主动重新加入」如何与「系统自动编回」区分？—— 已决，已实现

- **结论**：tombstone 只拦**自动路径**；用户显式加入一律清墓碑。即「用户意图 > 系统惯例」。
- **落地证据**：`BUG-126.md` 状态 `fixed`；实现在 `media.rs` ——
  `media_episode_removed` 表 + `trg_media_series_cleanup_removed` 触发器；
  自动路径 `append_episodes_ranged`（`media.rs:1979`）命中墓碑即 `continue`；
  四条显式入口 `add_episode` / `append_episodes` / `attach_episode_source` / `merge_series`
  先调 `clear_episode_tombstones`（`media.rs:2259` 文档明写「**自动路径不得调用**」）；
  低层 `delete_series` 刻意不清墓碑（供自动回滚用），`delete_series_explicit` 两种形态全清。
  回归测试 `low_level_delete_keeps_keyed_tombstones_but_explicit_delete_clears_them` 等 6 项。
- **处置**：本项从「待拍板」**撤下**。若对结论有异议，应按缺陷流程立 BUG，而不是当决策项重开。

### ✓ 「缓存完成后是否允许自动改主？」—— 已决（见设计 §3.4 的处置）

- **结论**：缓存成功路径触发 `auto_pick_primary`，但受 `primary_locked` 短路
  （用户锁过的主不会被悄悄改掉）。
- **落地证据**：`episode-multi-source-design-2026-09-22.md` §3.4 已给「处置」；
  §3.3 五道闸防覆盖、§3.5 历史 `primary_locked` 初值取 0（依据实测 `episodes_with_sources = 0`，
  「抹掉历史手动选择」风险实测为零）。
- **处置**：撤下。若对「自动改主」本身有异议，按 §3.4 的请求句单独提。
